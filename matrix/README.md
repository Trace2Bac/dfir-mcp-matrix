# matrix/ — 셀 구조와 정의

이 폴더에는 매트릭스의 축, 셀, 상세 항목을 정의한 파일이 있습니다. 셀 하나마다 파일이 하나씩 있습니다.
이 폴더의 파일을 고친 뒤에는 `python tools/pilot.py validate`를 실행해 확인합니다.
축, 셀, 상세가 무엇인지는 아래 [용어](#용어)에서 설명합니다.

셀과 상세는 바뀌는 빈도가 다르므로 다루는 방법도 다릅니다.

- **셀은 거의 바뀌지 않습니다.** 지금 있는 셀로 분류할 수 없는 새 기능이 나올 때만 셀을 더하거나 나눕니다. 이때는 결정 기록을 씁니다.
- **상세 항목은 서버를 조사하면서 자주 바뀝니다.** 이름을 고치거나, 새로 더하거나, 합치거나, 지우는 일이 잦습니다. 그래서 상세 번호는 한 번 정하면 고정하고, 이름은 자유롭게 바꿀 수 있게 했습니다(아래 [상세 다루기](#상세-다루기) 참고).
- **상세는 그 방식을 실제로 구현한 사례가 있어야 의미가 있습니다.** 다음 둘 중 하나이면 "구현 사례 있음"으로 봅니다.
  - 그 상세에 연결된 원고가 있는 경우
  - `seen_in`에 구현을 확인한 서버가 적혀 있는 경우

  둘 다 없으면 그 상세는 화면에 **후보**로 흐리게 표시되고, `validate`가 후보 개수를 알려 줍니다.

```
matrix/
├─ axes.yaml          축 차례·이름
├─ config.yaml        화면에 보일 서버, 시범 셀
├─ cells/<ID>.mdx     셀 하나의 질문과 상세 항목
└─ schema/            위 파일들과 원고 머리말의 JSON Schema(validate가 쓴다)
```

## 용어

이 저장소의 문서는 아래 용어를 이 뜻으로 씁니다.

| 용어 | 뜻 | 번호 형식 |
|---|---|---|
| **축** | 셀을 묶는 큰 갈래입니다. 예를 들어 "원본 증거 관리"가 축 하나입니다. | 글자 하나(P·E·T·R·L·D·I) |
| **셀** | 서버를 관찰할 때 던지는 질문 하나입니다. | `축 글자 + 두 자리`(예: `E03`) |
| **상세 항목**(상세) | 셀의 질문에 답하는 구현 방식 하나입니다. | `셀 번호.두 자리`(예: `E03.02`) |

서버가 어느 상세에도 해당하지 않거나 아직 조사하지 않았을 때는 다음 표시를 씁니다.

- **미구현**: 서버가 셀이 묻는 일을 하는데 어느 방식도 없는 경우입니다.
- **비적용**: 셀이 묻는 일의 전제를 서버가 아예 하지 않는 경우입니다.
- **미확인**: 아직 조사하지 않은 경우입니다. 이 표시는 화면에서만 씁니다.

원고에서는 다음 용어도 씁니다.

- **원고**: 서버 하나가 셀 하나에서 어느 상세에 해당하는지, 구현과 예외를 근거와 함께 적은 문서입니다. 형식은 [reports/README.mdx](../reports/README.mdx)에 있습니다.
- **구현**: 원고에서 그 방식이 서버의 어느 도구나 경로에 있고 어떻게 동작하는지 쓰는 단락입니다.
- **예외**: 원고에서, 적용 범위 안인데도 그 방식이 적용되지 않는 경우를 쓰는 단락입니다.
- **예외 표시(†, `exception`)**: 예외가 있다는 표시입니다. 원고의 구현 단락에 적은 적용 범위 안에서 그 방식이 적용되지 않는 경우가 있으면 붙입니다. 원고 머리말의 `exception: true`가 †입니다.

## axes.yaml

```yaml
axes:
- id: E                         # 축 글자. 축 이름 영어의 첫 글자
  name: 원본 증거 관리
  english: Evidence management
  description: 파생물이 아닌 원본 증거 데이터의 확보·등록·해시·보존·입력 준비
```

목록에 적힌 차례대로 화면에 축이 나옵니다. 셀이 어느 축에 속하는지는 셀 파일 이름의 첫 글자로 정해집니다.

## cells/<ID>.mdx

셀 파일 하나가 사이트의 셀 페이지 하나가 됩니다.
머리말(`---` 사이)에는 아래 YAML을 씁니다. 본문에는 제목 `# <ID> <name>` 한 줄만 둡니다. `validate`가 이 형식을 검사합니다.

```yaml
id: E03                          # 파일 이름과 같아야 한다
name: 원본 변경 방지              # 묻는 일을 명사로
question: 원본에 닿는 경로에서 누가 어떤 장치로 변경을 막는가?
conditional: false               # 지원 기능이 있는 서버에만 보는 셀이면 true
# applies_to: …                  # conditional: true일 때 적용 범위
boundary: …                      # (선택) 다른 셀과의 경계 설명. 화면에 셀 설명으로 보인다

# ── 아래는 정의를 쓴 셀만 둔다. 시범 셀(config.yaml의 pilot_cells)은 반드시 쓴다 ──
scope: …                         # 적용 범위. †를 판단하는 범위
not_implemented: …               # 이 셀에서 미구현의 뜻
not_applicable: …                # 이 셀에서 비적용의 뜻

details:                         # 상세 항목. 목록 차례가 화면 차례다
- id: E03.01                     # 한 번 정하면 바꾸지 않는다. 새 상세는 쓰지 않은 다음 번호
  name: 실행 환경의 읽기 전용 강제  # 언제든 바꿔도 된다(원고는 번호로 연결된다)
  include: …                     # 정의를 쓴 셀만. 포함 기준(아직 못 썼으면 validate가 경고만 한다)
  exclude: …                     # 정의를 쓴 셀만. 제외·범위 주의
  seen_in: [mulder, ChainsawMCP] # (선택) 원고는 아직 없지만 구현을 확인한 서버

retired:                         # (선택) 지운 상세. 번호를 다시 쓰지 않으려고 남긴다
- id: E03.04
  name: 출력 대상 검사
  merged_into: E03.02            # 다른 상세로 합쳤거나 셀을 나눠 옮겼으면 그 번호(다른 셀의 상세도 된다)
  reason: 서버 코드가 막는 방식으로 묶었다
```

- 정의를 아직 쓰지 않은 셀은 `details`에 `id`와 `name`만 둡니다.
- 값이 길어도 한 줄에 씁니다.
- YAML 문법상 따옴표가 필요한 값은 큰따옴표로 감쌉니다. 예를 들어 값이 `:`·`#`·`"`로 시작하는 경우가 그렇습니다.
- 다른 셀을 가리킬 때는 번호로 씁니다(예: "사본 생성은 E04").

## config.yaml

```yaml
servers: [ChainsawMCP, mcp_dfir, …]   # 화면에 보일 서버. reports/<서버>/가 없으면 모든 셀이 미확인
pilot_cells: [E03, T03, R02, L02]     # 원고가 담아야 하는 셀. 원고 폴더마다 이 셀 파일이 모두 있어야 한다
labels:
  미확인: 이 셀의 새 정의로 아직 조사하지 않았다.
```

## 상세 다루기

서버를 조사하다 보면 상세가 자주 바뀝니다. 상세를 바꿀 때는 결정 기록을 쓰지 않습니다. 셀 파일만 고치고, 바꾼 이유는 커밋 메시지에 씁니다.
하려는 일별로 셀 파일과 원고에서 할 일은 다음과 같습니다.

| 하려는 일 | 하는 법 | 원고 |
|---|---|---|
| 이름 바꾸기 | `name`만 고칩니다. | 고치지 않아도 됩니다. 소제목 이름이 다르면 `check`가 경고만 합니다. |
| 새 상세 더하기 | 이 셀에서 아직 쓴 적 없는 다음 번호로 `details`에 더합니다. `retired`에 있는 번호도 쓴 번호로 칩니다. 화면에 보이는 차례는 목록 안의 위치로 정합니다. | 그 서버 원고에 연결합니다. 원고를 아직 쓰지 못했다면 `seen_in`에 서버를 적습니다. |
| 구현은 확인했지만 원고는 나중에 쓰기 | `seen_in`에 서버 이름을 더합니다. | 원고를 쓰면 `seen_in`에서 그 서버를 지웁니다. |
| 둘을 하나로 합치기 | 남길 상세에 기준을 합치고, 없앨 상세는 `retired`로 옮겨 `merged_into`를 적습니다. | 옛 번호를 쓰는 원고가 있으면 `validate`가 "합쳤다"고 알립니다. 그 원고의 머리말과 소제목을 새 번호로 고칩니다. |
| 없애기 | `retired`로 옮기고 `reason`을 적습니다. | 그 번호를 쓰는 원고를 다른 상세나 미구현으로 고칩니다. |
| 차례 바꾸기 | 목록에서 위치만 옮깁니다. 번호는 그대로 둡니다. | 고치지 않습니다. |

**주의: 상세 번호는 다시 매기지 않습니다.** 중간에 빈 번호가 생겨도 그대로 둡니다. 지운 번호를 다시 쓰면 `validate`가 오류를 냅니다.

## 셀 다루기 (드묾)

셀은 거의 바뀌지 않습니다. 셀을 바꿔야 할 때는 다음 표를 따릅니다.

| 하려는 일 | 고칠 곳 |
|---|---|
| 셀 질문·이름 고치기 | `cells/<ID>.mdx`의 `question`과 `name`을 고칩니다. `name`을 고치면 셀 파일의 본문 제목도 함께 고칩니다. 원고의 제목(`# ID 이름`)이 새 이름과 다르면 `check`가 경고합니다. |
| 셀 새로 만들기 | 지금 있는 셀로 분류할 수 없는 새 기능이 나왔을 때 만듭니다. `cells/`에 `<ID>.mdx`를 만들고, 번호는 그 축의 마지막 번호 다음 번호로 정합니다. |
| 셀 나누기·합치기·번호 바꾸기 | 파일을 만들고 지운 뒤 원고와 문서의 옛 번호를 고칩니다. 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md#셀을-나누거나-합치거나-번호를-바꾸는-경우)에 있습니다. |
| 셀의 범위(`scope`·미구현·비적용) 바꾸기 | `cells/<ID>.mdx`를 고칩니다. |
| 축 차례·이름 바꾸기 | `axes.yaml`을 고칩니다. |
| 시범 셀 바꾸기 | `config.yaml`의 `pilot_cells`를 고칩니다. 시범 셀로 정한 셀에는 정의(`scope` 등)가 있어야 합니다. |

셀을 바꾸면 [docs/decisions/](../docs/decisions/)에 결정 기록을 하나 더합니다.
