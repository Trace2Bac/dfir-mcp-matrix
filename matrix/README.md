# matrix/ — 셀 구조와 정의

이 폴더에는 매트릭스의 축, 셀, 상세 항목을 정의한 파일이 있습니다. 셀 하나마다 파일이 하나씩 있습니다.
이 폴더의 파일을 고친 뒤에는 `python tools/pilot.py validate`를 실행해 확인합니다.
축, 셀, 상세 같은 용어의 뜻은 [용어 사전](../docs/glossary/README.mdx)에 있습니다.

셀과 상세는 바뀌는 빈도가 다르므로 다루는 방법도 다릅니다.

- **셀은 거의 바뀌지 않습니다.** 지금 있는 셀로 분류할 수 없는 새 기능이 나올 때만 셀을 더하거나 나눕니다. 이때는 결정 기록을 씁니다.
- **상세 항목은 서버를 조사하면서 자주 바뀝니다.** 이름을 고치거나, 새로 더하거나, 합치거나, 지우는 일이 잦습니다. 그래서 상세 번호는 한 번 정하면 고정하고, 이름은 자유롭게 바꿀 수 있게 했습니다(아래 [상세 다루기](#상세-다루기) 참고).
- **상세는 그 방식을 실제로 구현한 사례가 있어야 의미가 있습니다.** 다음 둘 중 하나이면 "구현 사례 있음"으로 봅니다.
  - 그 상세에 연결된 원고가 있는 경우
  - `seen_in`에 구현을 확인한 서버가 적혀 있는 경우

  둘 다 없는 방식은 셀 정의에 두지 않고 [`candidates.yaml`](candidates.yaml)에 **후보**로 적어 둡니다. 후보는 화면에 보이지 않습니다. 사례가 없는 상세가 셀 정의에 있으면 `validate`가 알려 줍니다.

```
matrix/
├─ config.yaml               화면에 보일 서버, 시범 셀, 매트릭스 버전
├─ candidates.yaml           구현 사례가 아직 없는 상세 후보(화면에 보이지 않는다)
├─ cells/
│  ├─ index.mdx              매트릭스 화면(셀 표)
│  └─ <축>/                  축 하나(P·E·T·R·F·L·D·I)
│     ├─ index.mdx           축의 차례·이름·설명
│     └─ <ID>.mdx            셀 하나의 확인 사항과 상세 항목
└─ schema/                   위 파일들과 원고 머리말의 JSON Schema(validate가 쓴다)
```

## cells/<축>/index.mdx

축 폴더마다 축 파일 하나를 둡니다. 축 파일 하나가 사이트의 축 페이지 하나가 되고, 그 아래에 축의 셀 목록이 붙습니다.
머리말에는 아래 YAML을 씁니다. 본문 첫 줄은 제목 `# <axis> <name>`이고, 그 아래에 축이 다루는 내용을 씁니다. `validate`가 이 형식을 검사합니다.

```yaml
axis: E                         # 축 글자. 축 이름 영어의 첫 글자이고 폴더 이름과 같다
name: 원본 증거 관리
english: Evidence management
order: 2                        # 화면에 보이는 축 차례. 축끼리 겹치지 않는다
```

`order` 차례대로 화면에 축이 나옵니다. 셀은 셀 번호의 첫 글자와 같은 축 폴더에 둡니다.

## cells/<축>/<ID>.mdx

셀 파일 하나가 사이트의 셀 페이지 하나가 됩니다.
머리말(`---` 사이)에는 아래 YAML을 씁니다. 본문에는 제목 `# <ID> <name>` 한 줄만 둡니다. `validate`가 이 형식을 검사합니다.

```yaml
id: E03                          # 파일 이름과 같아야 한다
name: 원본 변경 방지              # 묻는 일을 명사로
question: 원본 증거에 닿는 경로에서 원본 변경을 막는 주체와 장치를 분류합니다.   # 확인 사항. "~하는 방식을 분류합니다."로 쓴다
conditional: false               # 지원 기능이 있는 서버에만 보는 셀이면 true
# applies_to: …                  # conditional: true일 때 적용 범위
boundary: …                      # (선택) 다른 셀과 차이점. 화면에 「다른 셀과 차이점」으로 보인다

# ── 아래는 정의를 쓴 셀만 둔다. 시범 셀(config.yaml의 pilot_cells)은 반드시 쓴다 ──
scope: …                         # 확인 범위. 상세를 연결하는 범위. 화면에 「확인 범위」로 보인다
not_implemented: …               # 이 셀에서 미구현의 뜻
not_applicable: …                # 이 셀에서 비적용의 뜻

details:                         # 상세 항목. 목록 차례가 화면 차례다
- id: E03.01                     # 한 번 정하면 바꾸지 않는다. 새 상세는 쓰지 않은 다음 번호(결번도 쓴 번호로 센다)
  name: 실행 환경의 읽기 전용 강제  # 언제든 바꿔도 된다(원고는 번호로 연결된다)
  include: …                     # 정의를 쓴 셀만. 포함 기준(아직 못 썼으면 validate가 경고만 한다)
  exclude: …                     # (선택) 비슷하지만 이 상세에 들지 않는 것. include·exclude에는 사실만 쓰고 셀·상세 번호를 쓰지 않는다
  seen_in: [mulder, ChainsawMCP] # (선택) 원고는 아직 없지만 구현을 확인한 서버
```

- 정의를 아직 쓰지 않은 셀은 `details`에 `id`와 `name`만 둡니다.
- 값이 길어도 한 줄에 씁니다.
- YAML 문법상 따옴표가 필요한 값은 큰따옴표로 감쌉니다. 예를 들어 값이 `:`·`#`·`"`로 시작하는 경우가 그렇습니다.
- `boundary`에서 다른 셀을 가리킬 때는 셀 번호로 씁니다(예: "사본 생성은 E04"). 상세 번호(E04.02)는 쓰지 않습니다. 화면은 셀 번호를 그 셀 페이지 링크로 보여 줍니다.
- 셀 정의의 다른 값에도 상세 번호를 쓰지 않습니다. 원고에는 다른 셀 번호를 쓰지 않습니다.

## config.yaml

```yaml
servers: [ChainsawMCP, mcp_dfir, …]   # 화면에 보일 서버. reports/<서버>/가 없으면 모든 셀에서 미확인
version: "2026-10-06"                 # 매트릭스 정의 버전. 정의를 바꾼 날짜
pilot_cells: [E03, T03, R02, L02]     # 원고가 담아야 하는 셀. 원고 폴더마다 이 셀 파일이 모두 있어야 한다
```

`servers`에는 아직 원고 폴더가 없는 서버도 적습니다. 그런 서버는 모든 셀에서 미확인으로 보이고, 셀 정의의 `seen_in`에 쓸 수 있습니다.

## 상세 다루기

서버를 조사하다 보면 상세가 자주 바뀝니다. 상세를 바꿀 때는 결정 기록을 쓰지 않습니다. 셀 파일만 고치고, 바꾼 이유는 커밋 메시지에 씁니다.
하려는 일별로 셀 파일과 원고에서 할 일은 다음과 같습니다.

| 하려는 일 | 하는 법 | 원고 |
|---|---|---|
| 이름 바꾸기 | `name`만 고칩니다. | 고치지 않아도 됩니다. 소제목 이름이 다르면 `check`가 경고만 합니다. |
| 새 상세 더하기 | 그 셀에서 아직 쓰지 않은 다음 번호로 `details`에 더합니다. 지운 번호와 결번도 쓴 번호로 셉니다. 화면에 보이는 차례는 목록 안의 위치로 정합니다. | 그 서버 원고에 연결합니다. 원고를 아직 쓰지 못했다면 `seen_in`에 서버를 적습니다. |
| 구현은 확인했지만 원고는 나중에 쓰기 | `seen_in`에 서버 이름을 더합니다. | 원고를 쓰면 `seen_in`에서 그 서버를 지웁니다. |
| 둘을 하나로 합치기 | 남길 상세에 기준을 합치고, 없앨 상세는 `details`에서 뺍니다. 어디로 합쳤는지는 커밋 메시지에 적습니다. | 옛 번호를 쓰는 원고가 있으면 `validate`가 "정의에 없는 상세"로 알립니다. 그 원고의 머리말과 소제목을 새 번호로 고칩니다. |
| 없애기 | `details`에서 빼고 이유를 커밋 메시지에 적습니다. | 그 번호를 쓰는 원고를 다른 상세나 미구현으로 고칩니다. |
| 차례 바꾸기 | 목록에서 위치만 옮깁니다. 번호는 그대로 둡니다. | 고치지 않습니다. |
| 사례 없는 방식 적어 두기 | `candidates.yaml`의 그 셀 아래에 `name`·`include`·`exclude`만 적습니다. 후보에는 번호를 두지 않습니다. | 연결하지 않습니다. 후보에는 번호가 없어 원고에서 가리킬 수 없습니다. |
| 후보를 상세로 올리기 | 사례를 찾으면 그 항목을 `candidates.yaml`에서 셀 파일의 `details`로 옮기고 새 상세처럼 번호를 붙입니다. | 그 서버 원고에 연결합니다. |

**주의: 상세 번호는 다시 매기지 않습니다.** 중간에 빈 번호가 생겨도 그대로 둡니다.

## 셀 다루기 (드묾)

셀은 거의 바뀌지 않습니다. 분석 중에 셀을 바꿔야 할 것 같으면 GitHub 이슈나 토론에 올리고, 검토 주기에 모아서 바꾸며 `config.yaml`의 `version`을 그 날짜로 바꿉니다([CONTRIBUTING.md](../CONTRIBUTING.md#정의를-바꾸는-때와-버전)). 셀을 바꿀 때는 다음 표를 따릅니다.

| 하려는 일 | 고칠 곳 |
|---|---|
| 셀 확인 사항·이름 고치기 | `cells/<축>/<ID>.mdx`의 `question`과 `name`을 고칩니다. `name`을 고치면 셀 파일의 본문 제목도 함께 고칩니다. 원고의 제목(`# ID 이름`)이 새 이름과 다르면 `check`가 경고합니다. |
| 셀 새로 만들기 | 지금 있는 셀로 분류할 수 없는 새 기능이 나왔을 때 만듭니다. `cells/<축>/`에 `<ID>.mdx`를 만들고, 번호는 그 축의 마지막 번호 다음 번호로 정합니다. |
| 셀 나누기·합치기·번호 바꾸기 | 파일을 만들고 지운 뒤 원고와 문서의 옛 번호를 고칩니다. 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md#셀을-나누거나-합치거나-번호를-바꾸는-경우)에 있습니다. |
| 셀의 범위(`scope`·미구현·비적용) 바꾸기 | `cells/<축>/<ID>.mdx`를 고칩니다. |
| 축 차례·이름·설명 바꾸기 | `cells/<축>/index.mdx`를 고칩니다. 이름을 고치면 본문 제목도 함께 고칩니다. |
| 시범 셀 바꾸기 | `config.yaml`의 `pilot_cells`를 고칩니다. 시범 셀로 정한 셀에는 정의(`scope` 등)가 있어야 합니다. |

셀을 더하거나 나누거나 합치면 [docs/decisions/](../docs/decisions/)에 결정 기록을 하나 더합니다. 셀 하나의 문구만 고치면 커밋 메시지에 무엇을 왜 바꿨는지 남깁니다.
