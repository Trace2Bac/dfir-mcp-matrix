# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 `windows_event_log_cleared` 한 도구에 적용된다 [1].
도구 설명은 이 도구가 Windows 이벤트 로그 삭제 사건을 찾는다고 적는다 [1].
서버는 채널 정규식 `Security|System`과 이벤트 ID 정규식 `104|1102`를 코드에 정해 두고 Velociraptor 아티팩트 `Windows.EventLogs.EvtxHunter`의 `ChannelRegex`와 `IdRegex`로 넘긴다 [1].
모델이 정하는 인자는 대상 `client_id`·`org_id`, 날짜 범위 `DateAfter`·`DateBefore`, 반환할 열 `Fields`다 [1].
두 정규식을 사건마다 대는 일은 단말에서 실행되는 아티팩트의 VQL이 한다 [2].
서버는 조건에 맞아 돌아온 행을 `data`에 그대로 싣고 행마다 판정 값이나 이유를 덧붙이지 않는다 [3].
응답에 실리는 열은 `Fields`가 정하고 기본값은 `EventTime`·`Computer`·`Channel`·`EventID`·`EventData`·`Message`다 [1].
아티팩트가 사건마다 내는 `Provider`와 `UserData`는 이 기본값에 없다 [1][2].
아티팩트는 `EventData`·`UserData`·`Message` 가운데 하나라도 값이 있는 사건을 고르므로 내용이 `UserData`에만 있는 사건은 기본 응답에 그 내용 없이 실린다 [2].

탐지를 내세운 다른 도구에는 서버가 정한 규칙이 없다.
`windows_timestomp`·`windows_malfind`·`windows_wmi_persistence`·`windows_mutants`·`windows_evidence_of_download`는 모델이 준 인자만 넘겨 `Windows.NTFS.Timestomp`·`Windows.Detection.Malfind`·`Windows.Persistence.PermanentWMIEvents`·`Windows.Detection.Mutants`·`Windows.Analysis.EvidenceOfDownload`의 수집을 요청하고 돌아온 결과 행을 옮긴다 [4].
이 아티팩트가 무엇을 이상으로 고르는지는 Velociraptor의 아티팩트 정의가 정한다.
Velociraptor v0.77.1 시험 서버에는 이 가운데 `Windows.NTFS.Timestomp`와 `Windows.Detection.Malfind`의 정의가 없었다 [5].
`windows_event_logs`의 `WhitelistRegex`, `windows_mutants`의 `MutantWhitelistRegex`, `windows_powershell_history`의 `StringWhiteList`는 결과에서 뺄 항목을 모델이 정하는 인자이고 서버가 정해 둔 값은 빈 문자열이다 [6].
`yara_scan_files`·`yara_scan_process`·`linux_yara_scan`은 모델이 써서 넘긴 YARA 규칙을 아티팩트 매개변수로 그대로 넘긴다 [7].
`windows_powershell_scriptblock`은 채널 `Microsoft-Windows-PowerShell/Operational`과 이벤트 ID `4104`를 정해 두지만 이는 조회할 기록의 종류를 정한 조건이고 도구 설명은 돌아온 행을 탐지 결과로 내세우지 않는다 [8].
`validate_hunt_parameters`는 만든 hunt에 실린 매개변수를 요청한 매개변수와 대조하는 인자 검사다 [9].
같은 저장소의 `agent_poc/mcp_agent.py`는 도구 응답의 행을 키워드 목록, 사용자 쓰기 가능 경로, 서명 상태, 사설 대역 밖 주소로 맺은 연결 같은 조건으로 골라 `highlights`에 담는다 [10].
이 조건은 MCP 클라이언트 코드에 있고 서버의 도구 응답에는 실리지 않는다 [10].

**한계.** `Windows.EventLogs.EvtxHunter`는 두 정규식을 채널 이름과 이벤트 ID 문자열에 `=~` 연산으로 댄다 [2].
VQL의 `=~`는 문자열 어디에든 맞으면 참이고 대소문자를 가리지 않는다 [11].
그래서 `104|1102`는 1104나 4104처럼 그 숫자를 담은 다른 이벤트 ID에도 맞고 `Security|System`은 이름에 그 낱말을 담은 다른 채널에도 맞는다 [11].
서버는 채널과 이벤트 ID를 함께 대조하지 않아 Security 채널의 104와 System 채널의 1102도 조건에 맞는다 [1].
이벤트 제공자는 조건에 없다 [1].
응답에는 서버가 정한 두 정규식이 실리지 않는다 [3].
`Windows.EventLogs.EvtxHunter`는 운영체제가 Windows일 때만 실행된다는 전제 조건을 두고 서버는 대상 단말의 운영체제를 확인하지 않는다 [2][1].
Linux 단말을 대상으로 이 도구를 부르자 응답은 오류 없이 빈 목록이었다 [12].
그래서 빈 응답만으로는 삭제 사건이 없는 경우와 아티팩트가 실행되지 않은 경우를 구분할 수 없다.
Windows 단말에서 이 도구가 돌려주는 행은 실행으로 확인하지 않았다.

```python
def realtime_collection(
    client_id: str,
    artifact: str,
    parameters: Mapping[str, ParameterValue] | None = None,
    fields: str = "*",
    result_scope: str = "",
    org_id: str | None = None,
) -> list[dict]:
    normalized_artifact = normalize_artifact_name(artifact)
    normalized_result_artifact = normalize_artifact_name(f"{artifact}{result_scope}")
    normalized_fields = normalize_fields(fields)
    normalized_parameters = normalize_env_dict(parameters)
    vql = (
        f"LET collection <= collect_client(urgent='TRUE',client_id={vql_literal(client_id)}, "
        f"artifacts={vql_literal(normalized_artifact)}, env=dict({normalized_parameters})) "
        f"LET get_monitoring = SELECT * FROM watch_monitoring(artifact='System.Flow.Completion') WHERE FlowId = collection.flow_id LIMIT 1 "
        f"LET get_results = SELECT * FROM source(client_id=collection.request.client_id, flow_id=collection.flow_id,artifact={vql_literal(normalized_result_artifact)}) "
        f"SELECT {normalized_fields} FROM foreach(row=get_monitoring, query=get_results) "
    )

    return run_vql_query(vql, org_id=org_id)
```
