# E04 분석 입력 준비

### E04.02 선택 추출

**구현.** 이 방식은 SleuthKit과 WSL로 준비한 이미지의 파일을 읽는 공통 경로, 레지스트리 폴더 추출, Windows 아티팩트 도구와 FSEvents 도구의 파일 고르기에 적용된다 [1][2][3][4].
공통 경로 `get_readable_file_path`는 `/<이미지 ID>/…` 경로를 받으면 SleuthKit `fls`로 경로를 한 조각씩 따라가 inode를 찾고 `icat`으로 그 파일 하나를 꺼낸다 [1][5].
꺼낸 파일은 사건 폴더의 `extracted_files/<경로 MD5 앞 8글자>/inode_<번호>_<이름>`에 두고 같은 경로를 다시 읽으면 그 파일을 돌려준다 [1][6].
파일 읽기 도구, `identify_file_type`, `analyze_sqlite_database`, macOS 도구가 이 경로로 받은 파일을 읽는다 [1][7].
`analyze_sqlite_database`는 꺼낸 파일을 사건 폴더의 `extracted_files`에 한 번 더 복사해 그 사본을 연다 [7].
WSL로 마운트한 이미지는 마운트 아래 파일을 `cp`나 `cat`으로 사건 폴더의 `extracted`에 꺼낸다 [8].
`analyze_registry`는 요청 경로의 폴더를 `fls -r`로 훑어 파일을 모두 `extract/<이미지 ID>/<내부 경로>`에 꺼내고 그 폴더를 KAPE에 넘긴다 [2].
`kape_parse_artifact`는 요청한 파일 하나를 `kape_extract_<inode>` 폴더에 꺼내 그 폴더를 KAPE에 넘긴다 [9].
`analyze_prefetch`·`analyze_lnk_files`·`analyze_shellbags`·`analyze_jump_lists`는 폴더에서 이름과 확장자가 맞는 파일만 임시 폴더에 꺼내 KAPE에 넘긴다 [3].
`analyze_macos_fsevents`는 이름이 16글자인 FSEvents 파일을 골라 앞의 10개를 임시 폴더에 꺼내 파싱한다 [4].
시험 이미지에서 `read_text_file`은 `inode_103_notes.txt`를 꺼내 읽었고 `analyze_registry`는 `Windows/System32/config` 폴더를 꺼내 KAPE에 넘겼다 [10][11].

꺼내는 경로는 부속 자료를 찾아 함께 옮기지 않는다.
SQLite DB는 본 파일 하나만 꺼내므로 `-wal`에만 있는 행은 조회에 나오지 않는다 [1][7].
`-wal`에 두 번째 행이 있는 시험 DB를 조회하자 `moz_places`는 1행으로 나왔다 [10].
`analyze_shellbags`는 `NTUSER.DAT`·`USRCLASS.DAT`만 꺼내고 같은 폴더의 트랜잭션 로그는 꺼내지 않는다 [3].
`analyze_registry`의 폴더 추출은 경로 아래 파일을 모두 꺼내므로 `SYSTEM.LOG1` 같은 로그도 함께 꺼낸다 [2][11].
AmcacheParser와 AppCompatCacheParser는 하이브와 같은 폴더의 `.LOG?` 파일을 스스로 찾아 적용한다 [12].
SleuthKit 4.14.0은 EWF 이미지의 첫 조각을 받으면 libewf의 glob으로 나머지 조각을 스스로 찾는다 [13].
이미지 전체를 작업 위치로 복사하거나 파일시스템 전체를 꺼내는 경로는 없다.

**한계.** `analyze_registry`는 `/<이미지 ID>/…` 꼴의 경로를 받으면 접근 폴더 경로의 길이로 앞부분을 잘라 내부 경로를 만들고 결과가 비면 `Windows\System32\config`를 쓴다 [2].
그래서 이 꼴의 경로가 접근 폴더 경로보다 짧으면 무엇을 주어도 `Windows/System32/config` 폴더를 꺼낸다 [2].
`/<이미지 ID>/Users/alice`를 주자 `extract` 아래에는 `Windows/System32/config`가 꺼내졌다 [11].
더 길면 경로 끝의 남은 글자가 내부 경로가 된다 [2].
접근 폴더 경로보다 두 글자 긴 경로를 주자 내부 경로가 `/x`가 되어 추출이 실패했고 응답은 결과가 없다는 문장만 적었다 [14].
`fls -r`은 하위 폴더 항목 앞에 `+`를 붙여 적는데 추출 함수는 그 줄에서 inode를 읽지 못해 하위 폴더 안의 파일을 꺼내지 않는다 [2][15].
`RegBack/SAM`이 있는 시험 이미지에서 `RegBack` 폴더는 비어 있었고 추출 기록은 `file_count` 2, `failed_count` 0이었다 [11].
`analyze_prefetch`는 접근 폴더 아래 경로로 폴더를 받으면 그 폴더 대신 파티션 루트의 목록에서 `.pf`를 찾아 0개를 꺼낸다 [16][11].
`analyze_event_logs`는 SleuthKit으로 준비한 이미지의 경로를 꺼내지 않고 디스크에 없는 경로로 보고 뺀다 [17][11].
WSL 경로는 꺼낸 파일을 파일 이름만으로 `extracted/<이름>`에 두고 그 이름의 파일이 이미 있으면 다른 폴더의 같은 이름 파일이어도 그 파일을 돌려준다 [8].
이 경로는 코드로만 확인했다.
Arsenal로 마운트한 이미지의 DB는 원래 이름으로 사건 폴더에 복사하고 같은 이름과 크기의 사본이 이미 있으면 다른 폴더의 파일이어도 그 사본을 연다 [7][18].
이 경로도 코드로만 확인했다.
`kape_parse_artifact`도 받은 경로에서 접근 폴더 경로의 글자 수만큼 앞부분을 잘라 내부 경로를 만든다 [19].
그래서 접근 폴더 경로보다 짧은 `/<이미지 ID>/…` 꼴의 경로는 루트 폴더로 해석되어 `icat`이 inode 없이 실행되고 파일을 꺼내지 못한다 [19][9].
시험 이미지의 `SYSTEM`을 이 꼴로 주자 `kape_parse_artifact`는 `Failed to extract file from forensic image`를 돌려주었다 [20].

### E04.03 전체·부분 마운트

**구현.** 이 방식은 `prepare_disk_image`의 네 준비 방식에 적용된다 [21].
Arsenal Image Mounter는 이미지 전체를 Windows 드라이브로 마운트하고 새로 생긴 드라이브 가운데 읽을 수 있는 첫 드라이브를 접근 위치로 정한다 [22].
WSL LVM 경로는 이미지를 loop 장치로 붙이고 논리 볼륨과 파티션 가운데 LVM을 앞세워 크기가 가장 큰 것 하나를 마운트한다 [23].
WSL APFS 경로는 apfs-fuse로 이미지의 컨테이너를 마운트한다 [24].
SleuthKit 경로는 서버가 고른 파티션의 시작 위치를 `fls`·`icat`의 `-o`로 넘겨 그 파티션만 읽는다 [25][26].
파티션은 설명에 NTFS·FAT·Linux가 있거나 파일시스템을 알아본 것 가운데 가장 큰 것을 고른다 [26].
시험 이미지에서 SleuthKit 도구는 모두 `-o 2048`로 실행되었다 [10].
이 마운트 경로들은 실행 확인에서 실행하지 않았다.

**한계.** SleuthKit 경로는 파티션 하나만 등록하고 다른 파티션을 고르는 인자를 받지 않는다 [21][25].
파티션 표 파서는 `DOS`가 들어 있는 줄과 20000섹터보다 작은 파티션을 후보에서 뺀다 [27].
Arsenal 경로는 드라이브가 여럿 생겨도 첫 드라이브만 접근 위치로 등록하고 경로 대조는 그 접근 위치 아래만 이미지로 본다 [22][28].
WSL LVM 경로는 후보 하나만 마운트하고 나머지 논리 볼륨과 파티션은 마운트하지 않는다 [23].
LVM 마운트가 실패하면 SleuthKit이 읽을 수 있는 첫 파티션으로 바꾸고 이 전환은 서버 로그에만 남는다 [29].

### E04.04 추출·생략 범위 기록

**구현.** 이 방식은 Prefetch·점프 목록·FSEvents 도구의 응답, 이미지 준비 응답, 레지스트리 폴더 추출 기록, 경로 대응표에 적용된다 [30][4][31][6][32].
`analyze_prefetch`와 `analyze_jump_lists`는 폴더에서 꺼낸 파일 수를 응답에 싣는다 [30].
`analyze_macos_fsevents`는 찾은 파일 수와 꺼낸 파일 수를 따로 싣는다 [4].
`prepare_disk_image`는 찾은 파티션 수와 쓰는 파티션 번호를 싣고 Arsenal 경로에서는 마운트한 드라이브와 읽지 못한 드라이브를 싣는다 [31].
`ExtractionManager`는 꺼낸 폴더마다 위치, 시각, 꺼낸 파일 수 `file_count`, 실패한 수 `failed_count`, 파티션 위치를 `extraction_registry.json`에 남긴다 [6].
`PathMapper`는 꺼낸 파일마다 이미지 안 경로, 꺼낸 경로, inode, 크기를 `path_mapping.json`에 남긴다 [32].

**한계.** 하위 폴더 안이라 꺼내지 않은 파일은 `file_count`에도 `failed_count`에도 들어가지 않는다 [2][11].
`file_count`는 `icat`이 실패한 파일도 세고 `failed_count`는 예외가 난 파일만 센다 [6][33].
`icat`이 실패하는 항목을 둔 시험 폴더에서 기록은 `file_count` 3, `failed_count` 0이었고 그 파일은 0바이트로 남았다 [34].
`analyze_registry`의 응답에는 꺼낸 파일 수와 위치가 없다 [35].
`analyze_macos_fsevents`의 응답은 10개만 꺼낸다는 상한을 적지 않는다 [4].
`analyze_lnk_files`와 `analyze_shellbags`는 꺼낸 파일 수를 서버 로그에만 남긴다 [3].
`analyze_prefetch`는 꺼내지 못한 파일을 서버 로그에만 남기고 응답에는 꺼낸 수만 싣는다 [30].

```python
                             'Primary' in p['description'] or
```

```python
        Args:
            linux_path: Original Linux path in image
            windows_path: Extracted Windows file location
            inode: Inode number
            size: File size in bytes (optional)
            
        Returns:
            True if mapping added successfully
        """
        linux_path = self.normalize_linux_path(linux_path)
        windows_path = str(windows_path)
        
        self.path_mapping[linux_path] = {
            'windows_path': windows_path,
            'inode': inode,
            'timestamp': datetime.now().isoformat(),
            'size': size
        }
        
        self.reverse_mapping[windows_path] = linux_path
        
        self._save_mappings()
        
        return True
```
