# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 KAPE를 쓰는 `analyze_registry`·`analyze_prefetch`·`analyze_jump_lists`·`kape_parse_artifact`·`get_kape_modules_catalog`, MFTECmd, AppCompatCacheParser, EvtxECmd, Volatility 3의 `analyze_memory`, chainbreaker, hashcat, SleuthKit의 `mmls`·`icat` 실행에 적용된다 [1][2][3][4][5][6][7].
`analyze_registry`는 KAPE의 종료 코드가 0이면 `SUCCESS`, 아니면 `FAILED (Return code: <값>)`와 표준 오류 앞 200자를 그 모듈의 결과로 적는다 [1].
`analyze_prefetch`와 `analyze_jump_lists`는 종료 코드가 0이 아니면 `KAPE execution failed (exit code <값>)`와 표준 오류 앞 500자를 적고 출력 파일을 찾지 않는다 [2].
`kape_parse_artifact`는 종료 코드가 0일 때만 `Success: Yes`로 적고 `get_kape_modules_catalog`는 0이 아니면 표준 오류를 오류로 돌려준다 [3].
MFTECmd, AppCompatCacheParser, EvtxECmd, Volatility 3는 종료 코드가 0이 아니면 그 실행을 실패로 정한다 [4].
chainbreaker는 종료 코드 0, -1, `4294967295`를 성공으로 보고 그 밖의 값이면 `Chainbreaker returned error code <값>`과 출력을 적는다 [5].
hashcat은 종료 코드가 0이거나 출력에 `Cracked`가 있을 때만 작업을 마쳤다고 적는다 [6].
SleuthKit의 `icat`은 종료 코드가 0이 아니면 그 파일 추출을 실패로 정하고 `mmls`가 0이 아니면 파티션 표가 없는 이미지로 다시 읽는다 [7].
실행 확인에서 종료 코드 2로 끝나는 시험용 KAPE로 `analyze_registry`를 부르면 그 모듈의 결과는 `FAILED (Return code: 2)`였다 [8].

**한계.** 다음 실행은 종료 코드로 성공과 실패를 정하지 않는다.

- `analyze_amcache`는 AmcacheParser의 종료 코드를 보지 않고 출력 폴더에 CSV가 있으면 성공으로 정한다 [9].
- `analyze_shellbags`와 `analyze_lnk_files`는 KAPE의 종료 코드가 0이 아니면 서버 기록에 경고만 남기고 출력 폴더의 파일로 성공을 정한다 [10].
- `list_memory_plugins`와 `get_memory_plugin_help`는 종료 코드를 보지 않고 표준 출력이 비면 표준 오류를 그대로 돌려준다 [11].
- SleuthKit로 폴더를 꺼낼 때 `extract_folder`는 `extract_file`이 돌려준 실패를 보지 않고 꺼낸 파일 수에 더한다 [12].

실행 확인에서 종료 코드 1로 끝나는 시험용 KAPE로 `analyze_lnk_files`를 부르면 응답은 `Status: SUCCESS`였다 [8].

hashcat의 종료 코드는 다 찾지 못한 경우와 오류를 나누지 않는다.
hashcat 7.1.2는 다 찾지 못하고 끝나면 1을, 오류면 -1을 비롯한 음수를 종료 코드로 쓴다 [13].
`crack_hash`는 0이 아닌 종료 코드를 모두 `Cracking did not complete`와 `The hash was not cracked with the current wordlist`로 적고 hashcat의 표준 오류는 응답에 싣지 않는다 [6].
실행 확인에서 표준 오류에 오류 문구를 쓰고 255로 끝나는 시험용 hashcat으로 부르면 응답은 단어 목록으로 찾지 못했다는 문구였고 오류 문구는 없었다 [8].

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 EZ Tools 4개, Volatility 3, hashcat, chainbreaker, `get_kape_modules_catalog`, SleuthKit 실행, UnifiedLogReader와 `lz4` 처리에 적용된다 [4][14][15][16][17][18][19].
EZ Tools는 `subprocess.run`의 시간 제한으로 끊고 시간 초과를 따로 적는다 [4][14].
MFTECmd는 300초, AmcacheParser는 600초, AppCompatCacheParser는 60초, EvtxECmd는 1800초다 [14].
Volatility 3는 설정 `volatility3.max_execution_time`(기본 600초)을 넘으면 `Command timed out after <초> seconds`로 끝낸다 [4][15].
`crack_hash`는 인자 `timeout`이나 설정 `hashcat.max_execution_time`(기본 3600초)을 넘으면 `Timeout after <초>s`로, `--show` 실행은 30초로 끊는다 [16].
chainbreaker는 300초, `kape.exe --mlist`는 60초, SleuthKit의 `mmls`·`fls`는 30초, `icat`은 60초로 끊는다 [17][18].
UnifiedLogReader 분석은 서버 프로세스 안의 스레드에서 실행하고 `asyncio.wait_for`로 300초만 기다린다 [19].
실행 확인에서 8초 동안 멈추는 시험용 hashcat을 `timeout` 2로 부르면 `Timeout after 2.0s`가 왔다 [8].
같은 실행 확인에서 설정의 시간 제한을 3초로 둔 사본으로 10초 동안 멈추는 시험용 `vol.py`를 부르면 `Command timed out after 3 seconds`가 왔다 [8].

**한계.** KAPE로 모듈을 실행하는 도구 6개는 시간 제한 없이 KAPE가 끝날 때까지 기다린다 [20].
설정 `kape.max_execution_time`은 어느 코드도 읽지 않는다 [20].
UnifiedLogReader는 기다리기만 끊고 스레드의 분석은 계속된다 [19].
`decompress_mozilla_lz4`는 `asyncio.wait_for`로 30초 시간 제한을 두지만 그 호출을 감싼 `ThreadPoolExecutor`를 닫으면서 풀기 스레드가 끝날 때까지 기다린다 [19].
처리기 안의 시간 제한을 2초로 줄이고 6초 걸리는 풀기로 부르자 응답은 6초 뒤에 왔고 그동안 같은 이벤트 루프의 다른 작업은 실행되지 않았다 [21].
`decompress_mozilla_lz4`는 시간 초과를 `asyncio.TimeoutExpired`로 처리하는데 이 이름은 `asyncio`에 없다 [19].
그래서 시간 초과는 `Decompression failed: module 'asyncio' has no attribute 'TimeoutExpired'` 문구로 끝나고 시간 초과로 구별되지 않는다 [19][22][21].
chainbreaker의 시간 초과는 따로 처리하지 않고 `Failed to analyze keychain` 뒤에 예외 문구를 붙여 돌려준다 [17].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 KAPE를 쓰는 도구 6개, AmcacheParser, AppCompatCacheParser, EvtxECmd, hashcat, chainbreaker 실행에 적용된다 [1][2][3][9][10][23][24][25][26].
`analyze_registry`와 `kape_parse_artifact`는 KAPE 출력에서 `Administrator privileges not found`를 찾으면 관리자 권한이 필요하다는 실패로 정한다 [1][3].
`analyze_prefetch`와 `analyze_jump_lists`는 종료 코드가 0이어도 출력 폴더에 CSV·JSON·HTML 파일이 없으면 `No output files generated`로 정한다 [23].
`analyze_shellbags`와 `analyze_lnk_files`는 출력 폴더에 크기가 0보다 큰 파일이 하나라도 있으면 성공으로 정한다 [10].
`analyze_amcache`와 `analyze_shimcache`는 CSV가 없으면, `analyze_event_logs`는 고른 형식의 출력 파일이 없으면 실패로 정한다 [9][24].
`crack_hash`는 hashcat 출력에서 진행 상태 줄을 빼고 `<해시>:<암호>` 모양의 줄을 찾아 찾은 암호로 적고 `All hashes found` 문구가 있으면 `--show`로 다시 읽는다 [25].
`analyze_macos_keychain`은 chainbreaker 출력에 `[Invalid Password / Keychain Locked]`나 `[Keychain Locked]`가 있으면 암호가 필요하다는 안내를 붙인다 [26].
실행 확인에서 출력 파일을 만들지 않고 0으로 끝나는 시험용 EvtxECmd로 `analyze_event_logs`를 부르면 `EvtxECmd completed but no output files found`가 왔다 [8].

**한계.** 출력 파일을 찾는 폴더에 앞선 실행의 파일이 남아 있으면 그 파일로 판정한다.

- `analyze_amcache`는 이미지가 아닌 경로를 늘 같은 출력 폴더 `local_analysis\amcache\AmcacheParser_amcache`에 쓰고 그 폴더의 CSV를 모두 이번 실행의 출력으로 센다 [9][27].
- `analyze_shimcache`는 정한 CSV 이름이 없으면 폴더의 다른 CSV를 출력으로 쓴다 [24].
- `analyze_registry`는 실행 전에 출력 폴더 아래 `Registry` 폴더를 만들고 출력 폴더가 비어 있지 않으면 KAPE를 실행하지 않고 `CACHED (already analyzed)`로 적는다 [28].

실행 확인에서 CSV를 쓰는 시험용 AmcacheParser로 한 번 부른 뒤 CSV 없이 1로 끝나는 시험용으로 다시 부르면 두 번째 응답도 `Successful: 1`이었고 첫 실행의 CSV를 출력으로 적었다 [8].
같은 실행 확인에서 종료 코드 2로 끝나는 시험용 KAPE로 `analyze_registry`를 두 번 부르면 첫 응답은 `FAILED`, 두 번째 응답은 `CACHED (already analyzed)`였다 [29].

`analyze_shellbags`와 `analyze_lnk_files`는 출력 파일의 종류를 보지 않는다 [10].
KAPE 문서는 실행 기록 `ConsoleLog`가 오류가 없으면 `--mdest` 폴더에 남는다고 적는다 [30].
실행 확인에서 출력 폴더에 콘솔 기록 파일만 쓰고 1로 끝나는 시험용 KAPE로 `analyze_lnk_files`를 부르면 응답은 `Status: SUCCESS`와 `Output Files: 1`이었다 [8].
`analyze_mft`는 MFTECmd의 종료 코드가 0이면 출력 파일 목록이 비어도 성공으로 둔다 [4].
`analyze_memory`는 Volatility 3의 출력을 읽지 않고 종료 코드만 본다 [4].

### T08.04 입력별 부분 완료 집계

**구현.** 이 방식은 `analyze_shellbags`, `analyze_jump_lists`, `analyze_mft`, `analyze_amcache`, `analyze_macos_fsevents`에 적용된다 [31][32][33].
`analyze_shellbags`는 모듈과 경로의 조합마다 실행 결과를 성공과 실패로 나누고 `Successful`과 `Failed` 개수를 적는다 [31].
`analyze_jump_lists`는 실행마다 성공 여부를 정하고 `Total operations`, `Successful`, `Failed` 개수를 적는다 [31].
`analyze_mft`와 `analyze_amcache`는 입력과 모듈의 조합마다 `success`와 `error`를 정하고 `Successful`, `Failed`, `Total Modules` 개수와 조합마다의 오류를 적는다 [32].
`analyze_macos_fsevents`는 SleuthKit로 준비한 이미지에서 찾은 FSEvents 파일 수와 꺼낸 파일 수를 따로 적는다 [33].
실행 확인에서 이미지가 아닌 `$MFT` 경로로 `analyze_mft`를 부르면 `Successful: 0`, `Failed: 2`와 모듈마다의 오류가 왔다 [8].

**한계.** 다음 도구는 항목마다 성공과 실패를 정하지만 개수를 세지 않거나 일부 실패를 전체 결과에 반영하지 않는다.

- `analyze_registry`는 실패한 모듈 결과도 `Results Generated`에 세고 끝에 늘 `Analysis completed successfully.`를 적는다 [34].
- `analyze_lnk_files`는 성공한 항목이 하나라도 있으면 성공한 항목만 적고 실패한 항목과 그 수는 적지 않는다 [35].
- `analyze_shimcache`는 오류가 하나라도 있으면 전체를 `Shimcache Analysis Failed`로 정하고 성공한 입력의 출력 파일은 적지 않는다 [36].
- `analyze_prefetch`는 경로와 모듈마다 결과를 적고 성공과 실패 개수는 적지 않는다 [37].

실행 확인에서 종료 코드 2로 끝나는 시험용 KAPE로 `analyze_registry`를 부르면 그 모듈은 `FAILED`였고 응답 끝은 `Analysis completed successfully.`였다 [8].
같은 실행 확인에서 두 입력 가운데 하나만 실패하게 둔 시험용 AppCompatCacheParser로 `analyze_shimcache`를 부르면 응답은 실패한 입력의 오류만 적었다 [8].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 서버 프로세스 안에서 `plistlib`, `sqlite3`, `xml.etree`, `csv`, `json`, `lz4`, UnifiedLogReader, FSEvents 파서로 증거를 읽는 도구에 적용된다 [38][39][40][19].
`analyze_macos_plist`, `analyze_sqlite_database`, `parse_xml_evidence`, `read_csv_data`는 읽다 난 예외를 처리해 `ERROR:`로 시작하는 오류 문구로 돌려준다 [38].
`analyze_macos_unified_logs`는 분석 스레드 안의 예외를 오류 문구로 바꿔 `ERROR: <문구>`로 돌려준다 [39].
`analyze_macos_fsevents`는 FSEvents 파서의 예외를 처리해 `Failed to parse FSEvents` 문구를 응답에 적는다 [40].
처리기가 예외를 다시 내면 `server.py`의 `call_tool`이 `ERROR: Tool execution failed: <문구>`로 돌려준다 [41].
`analyze_mft`와 `analyze_amcache`는 잘못된 모듈 이름이나 설정 오류를 예외로 다시 낸다 [32].

**한계.** `decompress_mozilla_lz4`는 `lz4` 풀기에서 난 예외를 실제 문구로 돌려주지 못한다 [19].
`asyncio.wait_for`가 낸 예외를 `except asyncio.TimeoutExpired`와 맞춰 보다 `AttributeError`가 나고 그 문구가 응답에 실린다 [19].
실행 확인에서 머리말만 맞고 내용이 손상된 `.jsonlz4` 파일로 부르면 `Decompression failed: module 'asyncio' has no attribute 'TimeoutExpired'`가 왔다 [22].
