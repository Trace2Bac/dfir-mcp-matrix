# T04 실행 방식

### T04.01 서버 프로세스 안 분석

**구현.** 이 방식은 plist, Unified Logs, FSEvents, SQLite, XML, CSV, Mozilla LZ4 도구와 `identify_file_type`·`browse_files_and_folders`에 적용된다 [1][2][3][4].
`analyze_macos_plist`는 이진 형식 plist를 Python `plistlib` 모듈로 읽고 XML plist는 글로 읽는다 [1].
`analyze_macos_unified_logs`는 저장소 밖 `Tools\macos_forensics\UnifiedLogReader`를 `sys.path`에 더해 `UnifiedLogReader`를 불러오고 `run_in_executor`로 서버 프로세스의 다른 스레드에서 파싱한다 [2].
`analyze_macos_fsevents`는 mac_apt에서 옮겨 온 `utils/fsevents_parser.py`로 FSEvents 파일을 파싱한다 [3].
`analyze_sqlite_database`는 Python `sqlite3`로, `parse_xml_evidence`는 `xml.etree.ElementTree`로, `decompress_mozilla_lz4`는 `lz4.block`으로 서버 프로세스 안에서 처리한다 [4].
`identify_file_type`은 파일 앞 32바이트를 읽어 서버 코드의 표로 형식을 고른다 [5].
SleuthKit·WSL 이미지의 파일은 외부 도구로 꺼낸 뒤 이 코드들이 읽는다 [6].

### T04.02 같은 권한의 별도 프로세스

**구현.** 이 방식은 KAPE, MFTECmd·AmcacheParser·AppCompatCacheParser·EvtxECmd, SleuthKit 도구, Volatility 3, chainbreaker, hashcat, Arsenal Image Mounter의 실행에 적용된다 [7][8][9][10][11][12][13].
처리기는 실행 파일과 인자를 `list`로 `asyncio.create_subprocess_exec`, `subprocess.run`, `subprocess.Popen`에 넘긴다 [7][8][9][10].
`analyze_memory`와 `get_memory_plugin_help`는 설정 값이 `python`이면 서버 해석기 `sys.executable`로, `list_memory_plugins`는 이름 `python.exe`로 `vol.py`를 실행한다 [10][14].
chainbreaker는 모듈을 불러올 수 있으면 `sys.executable -m chainbreaker`로 실행한다 [11].
Arsenal의 `aim_cli.exe`는 `--background`로 실행한 뒤 마운트가 유지되는 동안 프로세스를 남겨 둔다 [13].
도구는 모두 서버와 같은 계정과 권한으로 실행되고 서버는 계정이나 권한을 낮추지 않는다 [7][8][9][10][11][12][13].
KAPE와 Arsenal은 관리자 권한을 요구하고 서버는 그 권한을 따로 얻지 않으므로 사용자가 서버를 관리자 권한으로 실행해야 한다 [15].
시험용 AmcacheParser는 서버의 작업 위치에서, 시험용 `vol.py`는 서버 해석기로 Volatility 폴더에서, 시험용 hashcat은 hashcat 폴더에서 실행되었다 [16].

작업 위치는 도구마다 다르고 호출마다 새로 만들지 않는다.
KAPE는 실행 파일 폴더를, Volatility 3는 `vol.py` 폴더를 `cwd`로 받는다 [7][10].
레지스트리 처리기와 EZ 도구 직접 실행은 `cwd`를 정하지 않아 서버의 작업 위치를 쓴다 [8][9].
`crack_hash`는 다른 스레드에서 `os.chdir(HASHCAT_DIR)`로 서버 프로세스 전체의 작업 위치를 바꾼 뒤 hashcat을 실행하고 끝나면 되돌린다 [12].
SleuthKit 추출 처리기는 `temp_directory` 아래에 `<도구>_extract_<inode>` 폴더를 만들어 꺼낸 파일을 두지만 그 폴더를 작업 위치로 쓰지 않는다 [17].

### T04.03 셸 명령 문자열 실행

**구현.** 이 방식은 WSL 안에서 실행하는 이미지 마운트·목록·추출 명령에 적용된다 [18][19][20][21].
`WSLLVMMounter._run_wsl`은 `wsl -d <배포판> -u root bash -c '<명령>'` 문자열을 `shell=True`로 실행한다 [18].
`WSLAPFSMounter._run_wsl`은 `wsl`에 인자 `list`를 넘기지만 마지막 인자를 `bash -c`가 해석하는 명령 문자열로 둔다 [19].
`browse_files_and_folders`의 WSL 경로 나열은 `find`·`stat` 명령을 문자열로 만들어 `wsl bash -c`로 감싼 뒤 `shell=True`로 실행한다 [20].
이 함수는 처리 중 예외가 난 뒤 등록 항목에 `wsl_access_point`가 있을 때만 호출되고 서버 코드는 이 값을 등록 항목에 쓰지 않는다 [20][22].
`prepare_disk_image`는 LVM 마운트가 남아 있는지 `wsl ... mount | findstr` 문자열을 `shell=True`로 실행한다 [21].
명령 문자열에는 마운트 위치와 함께 모델이 준 경로에서 만든 이미지 안 경로가 큰따옴표나 작은따옴표로 감싸여 들어간다 [18][19][20][23].
WSL 명령은 Windows 드라이브의 이미지를 `/mnt/<드라이브>/` 아래 경로로 읽고 APFS 추출은 꺼낸 파일을 같은 꼴의 경로로 서버의 사건 폴더에 써서 서버와 같은 파일에 닿는다 [24].
`analyze_macos_fsevents`도 APFS 이미지의 FSEvents 파일을 `find "<경로>"` 문자열로 찾는다 [23].
이 경로는 WSL과 이미지 마운트가 필요해 실행하지 않고 코드로만 확인했다.

### T04.04 권한을 나눈 실행

**구현.** 이 방식은 WSL LVM 마운터의 명령과 `prepare_disk_image`의 LVM 마운트 확인에 적용된다 [18][21].
두 경로는 `wsl`에 `-u root`를 붙여 WSL 배포판의 기본 사용자가 아닌 root로 명령을 실행한다 [18][21].
이 root 권한이 WSL에서 연결한 Windows 드라이브의 파일에 미치는 범위는 확인하지 못했다.
`losetup`, `vgchange`, `mount`, `find`, `cat`이 이렇게 실행된다 [25].
권한을 높이는 방향만 있고 권한을 낮추거나 다른 일반 계정으로 바꾸는 코드는 없다.
WSL APFS 마운터는 `-u`를 붙이지 않아 배포판의 기본 사용자로 실행한다 [19].
이 경로는 실행하지 않고 코드로만 확인했다.
