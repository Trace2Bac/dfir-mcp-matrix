# T07 도구 부재 처리

### T07.01 실행 전 도구·참조 자료 가용성 검사

**구현.** 이 방식은 KAPE, EZ Tools 실행 파일 4개, Volatility 3, hashcat, chainbreaker, `lz4` 모듈, WSL, Arsenal Image Mounter를 쓰는 경로에 적용된다 [1][2][3][4][5][6][7][8][9].
`analyze_registry`, `analyze_prefetch`, `kape_parse_artifact`는 실행 전에 `verify_tool_requirements`로 `kape.binary_path`의 `kape.exe`가 있는지 확인하고 없으면 실행하지 않는다 [1].
`analyze_shellbags`, `analyze_lnk_files`, `analyze_jump_lists`, `get_kape_modules_catalog`도 KAPE를 실행하기 전에 같은 파일이 있는지 확인한다 [2].
`analyze_mft`, `analyze_amcache`, `analyze_shimcache`, `analyze_event_logs`는 `kape.modules_path` 아래 `bin` 폴더에 MFTECmd, AmcacheParser, AppCompatCacheParser, EvtxECmd 실행 파일이 있는지 확인한다 [3].
Volatility 3를 쓰는 도구 3개는 `vol.py`가 있는지 확인한다 [4].
`crack_hash`는 설정의 `enabled`, hashcat 실행 파일, 단어 목록, 규칙 파일이 있는지 확인한다 [5].
`analyze_macos_keychain`은 `chainbreaker` 모듈을 import해 보고 실패하면 `PATH`와 인터프리터의 `Scripts` 폴더에서 실행 파일을 찾는다 [6].
`decompress_mozilla_lz4`는 호출 때 `lz4.block`을 import하고 실패하면 실행하지 않는다 [7].
WSL로 APFS나 LVM 이미지를 붙이는 클래스는 만들 때 `wsl uname`을 시험 실행해 실패하면 예외를 낸다 [8].
`ArsenalMounter`는 만들 때 `aim_cli.exe`가 있는지 확인한다 [9].
실행 확인에서 분석 도구가 없는 작업 사본으로 KAPE, AmcacheParser, AppCompatCacheParser, Volatility 3, hashcat을 쓰는 도구를 부르면 모두 외부 프로그램을 실행하지 않고 오류 문구로 끝났다 [10].

**한계.** 다음 도구는 실행 전에 확인하지 않고 실행이 실패한 뒤에야 없다는 것을 안다.

- `prepare_disk_image`의 실행 전 확인 `verify_sleuthkit_available`은 설정의 `sleuthkit.enabled`와 파이썬 모듈 import만 보고 SleuthKit 실행 파일은 보지 않으며 `mmls`를 시작하지 못한 `FileNotFoundError`가 나야 `SleuthKit not installed`로 정한다 [11][12].
- `analyze_macos_unified_logs`는 UnifiedLogReader가 있는지 확인하지 않고 분석 스레드 안에서 바로 import한다 [13].
- `analyze_macos_fsevents`는 SleuthKit로 준비한 이미지에서 설정의 경로가 아닌 이름 `icat`으로 실행 파일을 찾는다 [14].

KAPE를 쓰는 도구는 `kape.exe`만 확인하고 `--module`로 넘기는 모듈 정의와 그 모듈이 부르는 RECmd·PECmd 같은 실행 파일은 확인하지 않는다 [1][15].
KAPE는 소스가 공개되어 있지 않아 모듈 정의나 실행 파일이 없을 때 KAPE가 어떻게 끝나는지는 확인하지 못했다.
서버는 EvtxECmd에 맵 폴더를 넘기지 않고 EvtxECmd 옆의 `Maps` 폴더가 있는지도 확인하지 않는다 [16].
EvtxECmd(`EricZimmerman/evtx` `03a7a1f`)는 맵 폴더가 없으면 경고를 남기고 맵 없이 처리를 계속한다 [17].

### T07.02 대체 없는 실패 처리·도구 부재 알림

**구현.** 이 방식은 실행 전 확인을 거치는 모든 도구와 `prepare_disk_image`의 SleuthKit 실행에 적용된다 [1][2][3][4][5][6][7][12].
도구가 없으면 응답 글에 없는 도구의 이름과 찾은 경로를 적는다.

- KAPE: `KAPE/RECmd NOT AVAILABLE`나 `KAPE NOT AVAILABLE - CANNOT PROCEED` 같은 머리말 뒤에 `KAPE not found at: <경로>`를 적는다 [1][2].
- EZ Tools: `AmcacheParser.exe not found: <경로>`, `AppCompatCacheParser not found: <경로>`, `MFTECmd not found: <경로>`, `EvtxECmd.exe not found at: <경로>`를 적는다 [3].
- Volatility 3: `Volatility3 not found at <경로>`를 적는다 [4].
- hashcat: `Hashcat executable not found: <경로>`와 설정 파일을 고치라는 안내를 적는다 [5].
- chainbreaker와 `lz4`: 설치 명령을 적은 `chainbreaker not found. Install: pip install chainbreaker`와 `lz4 library not installed`를 적는다 [6][7].
- SleuthKit: `Filesystem detection failed - SleuthKit not installed`를 적는다 [12].

실행 확인에서 KAPE, AmcacheParser, AppCompatCacheParser, Volatility 3, hashcat, SleuthKit이 없는 작업 사본으로 부르면 응답에 위 문구와 확인한 경로가 실렸다 [10].
같은 실행 확인에서 chainbreaker가 없는 환경으로 `analyze_macos_keychain`을 부르면 `chainbreaker not found. Install: pip install chainbreaker`가 왔다 [18].
서버는 빠진 도구를 내려받거나 설치하지 않는다.

**한계.** `analyze_macos_unified_logs`는 UnifiedLogReader가 없으면 import 오류 문구와 호출 추적 글을 `Failed to analyze unified logs` 뒤에 붙여 돌려주고 도구가 없다는 사실을 따로 적지 않는다 [13][19].
실행 확인에서 UnifiedLogReader가 없는 작업 사본으로 부르면 `No module named 'scripts.UnifiedLogReader'`와 호출 추적 글이 왔다 [10].

### T07.03 알림 없는 대체 실행

**구현.** 이 방식은 `prepare_disk_image`의 마운트 방법 선택, hashcat 실행 파일 찾기, chainbreaker 실행 방법 선택, SleuthKit 실행 파일 이름 정하기에 적용된다 [20][21][22][6][23].
`prepare_disk_image`는 Arsenal Image Mounter로 마운트하다 실패하면 경고 기록만 남기고 SleuthKit 추출 방식으로 준비한다 [20].
이때 응답은 `Mount Type: SleuthKit (On-Demand Extraction)`만 적고 Arsenal 마운트가 실패했다는 사실과 이유는 적지 않는다 [20][24].

SleuthKit이 APFS 물리 저장소를 읽지 못하면 WSL의 apfs-fuse로 이미지를 마운트한다 [21].
이 경로의 등록부 항목은 `mount_type`을 `wsl_apfs_fuse`로 두지만 응답은 `Access Method: On-Demand File Extraction`으로 적고 WSL이나 apfs-fuse를 적지 않는다 [21].
WSL로 LVM 이미지를 마운트하지 못하면 경고 기록만 남기고 LVM이 아닌 첫 파티션을 SleuthKit로 읽는다 [22].
이때 응답은 파티션 수와 쓴 파티션 번호만 적는다 [22][25].

hashcat은 설정의 `executable_path`에 파일이 없으면 `PATH`에서, 그다음 저장소 `Tools` 아래 `hashcat*` 폴더에서 찾은 실행 파일로 바꾸고 단어 목록 경로도 그 폴더로 옮긴다 [26].
`crack_hash`의 응답은 단어 목록의 파일 이름만 적고 실행한 hashcat의 경로나 설정 경로를 바꾼 사실을 적지 않는다 [27].
실행 확인에서 설정 경로에 hashcat이 없고 `Tools\hashcat-7.1.2` 아래에만 시험용 실행 파일을 둔 작업 사본에서 `executable_path`는 그 폴더의 파일로 바뀌었고 `crack_hash`의 응답에는 `Wordlist: rockyou.txt`만 실렸다 [18].

`analyze_macos_keychain`은 `chainbreaker` 모듈을 import하지 못하면 `PATH`의 실행 파일, 인터프리터 `Scripts` 폴더의 실행 파일 차례로 바꾸고 이 사실을 서버 기록에만 남긴다 [6].
SleuthKit 실행 파일 경로는 설정을 읽지 못하거나 `sleuthkit.enabled`가 거짓이면 `PATH`에서 찾는 이름 `mmls`·`fsstat`·`fls`·`icat`으로 바뀌고 이 사실도 서버 기록에만 남는다 [23].

### T07.04 실행 환경별 경로 분기

**구현.** 이 방식은 `prepare_disk_image`의 마운트 방법, hashcat 실행 파일, chainbreaker 실행 방법을 고르는 데 적용된다 [28][26][6].
`prepare_disk_image`는 서버가 Windows에서 실행되고 `ArsenalMounter`를 import했고 SleuthKit이 찾은 OS가 Windows일 때만 Arsenal Image Mounter를 쓰고 그 밖에는 SleuthKit 추출 방식을 쓴다 [28].
APFS 물리 저장소와 LVM2 이미지는 WSL 배포판 `Ubuntu`의 apfs-fuse와 LVM 도구로 마운트하며 배포판 이름은 코드에 정해 두었다 [21][22].
hashcat은 설정 경로, `PATH`, 저장소 `Tools\hashcat*` 폴더 차례로 처음 찾은 실행 파일을 쓴다 [26].
chainbreaker는 `chainbreaker` 모듈, `PATH`의 실행 파일, 인터프리터 `Scripts` 폴더의 실행 파일 차례로 처음 쓸 수 있는 것을 쓴다 [6].

다른 분석 도구는 실행 파일을 찾는 경로가 하나다.
KAPE와 EZ Tools는 설정 `kape.binary_path`와 `kape.modules_path` 아래 정해 둔 경로를 쓴다 [1][3].
Volatility 3는 설정의 `vol.py` 하나를 쓴다 [4].
`analyze_memory`와 `get_memory_plugin_help`는 설정 값이 `python`이면 서버와 같은 인터프리터로, `list_memory_plugins`는 이름 `python.exe`로 `vol.py`를 실행한다 [4].

```python
    """Verify if KAPE is available"""
    from app_config import CONFIG

def verify_tool_requirements(tool_name):

    """
    if tool_name in ['prepare_disk_image', 'browse_prepared_image_files',

    # Other tools don't have special requirements
    return True
```
