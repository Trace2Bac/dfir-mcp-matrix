# T03 실행 조건 확인

### 미구현

**판단.** 서버에는 앞선 작업 상태, 모델 밖 승인, 원격 호출자 신원, 실행 자원으로 호출을 막거나 미루는 코드가 없다.
`call_tool`은 도구 이름으로 처리기를 골라 바로 부르고 그 사이에 조건을 보지 않는다 [1].
여러 도구가 준비된 이미지 안의 경로만 받는 것은 경로 인자를 등록부 `PREPARED_IMAGES`와 대조하는 검사이고 앞선 호출의 결과를 따로 확인하지 않는다 [2].
KAPE가 관리자 권한이 없다는 문구를 내면 처리기는 그 문구를 찾아 안내 글을 돌려주지만 실행 전에 권한을 확인하지는 않는다 [3].

원격 진입점 `remote_server.py`는 Starlette 앱에 `/sse`와 `/messages/` 경로를 두고 호출자를 확인하는 코드를 두지 않는다 [4].
`SseServerTransport`는 `security_settings` 없이 만들어 MCP Python SDK 1.29.1의 Host·Origin 헤더 검사가 꺼진 상태로 동작한다 [4][5].
앱에는 모든 출처·메서드·헤더를 허용하는 CORS 미들웨어가 붙는다 [4].
직접 실행하면 `0.0.0.0`에 열리고 `USE_NGROK`의 기본값 `true`에서는 ngrok 공개 터널도 연다 [6].
SSE 연결마다 생기는 세션 ID는 메시지를 그 연결로 보내는 데 쓰이고 서버는 그 ID를 받은 쪽이 누구인지 확인하지 않는다 [5].
모듈의 Starlette 앱을 `127.0.0.1`에만 열고 인증 헤더 없이 연결하자 초기화, 도구 31개 목록, `list_prepared_images` 호출이 모두 처리되었다 [7].
다른 호스트 이름을 적은 `Host`·`Origin` 헤더로 요청한 SSE 연결도 받아들였고 메시지 요청은 세션 ID가 없거나 없는 ID일 때만 거부되었다 [7].
`0.0.0.0`에 여는 실행과 ngrok 터널은 확인하지 않았다 [6].
stdio 진입점 `main.py`는 원격 연결을 받지 않는다 [8].

설정 파일에는 `max_memory_usage`와 `max_concurrent_operations`가 있지만 서버 코드는 두 값을 읽지 않는다 [9].
메모리, CPU, 디스크 여유 공간을 확인하는 코드는 없다.
동시 실행 수를 정하는 장치도 없다.
KAPE 처리기는 `asyncio.create_subprocess_exec`로 실행하고 hashcat·chainbreaker·Unified Logs 파싱은 `run_in_executor`로 다른 스레드에서 실행한다 [3][10].
MFT·Amcache·ShimCache·이벤트 로그·Volatility 3 처리기는 비동기 처리기 안에서 `subprocess.run`을 부르므로 그 실행이 끝날 때까지 서버는 다른 요청을 처리하지 않는다 [11].
`decompress_mozilla_lz4`는 시간 제한이 지난 뒤 풀기 스레드가 끝날 때까지 기다리므로 그동안 서버는 다른 요청을 처리하지 않는다 [12][13].
이는 서버가 정한 제한이 아니라 처리기가 동기 호출을 쓰는 방식에서 생기는 동작이다.
