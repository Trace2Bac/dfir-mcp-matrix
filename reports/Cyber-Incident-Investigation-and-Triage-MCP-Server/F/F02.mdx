# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 `analyze_macos_plist`의 `login_items`·`launch_agent` 해석과 `analyze_shimcache`의 경로 분류에 적용된다 [1][2].

`analyze_macos_plist`는 이진 plist를 `plistlib`로 읽고 모델이 준 `plist_type`에 따라 해석 함수를 고른다 [1].
`plist_type`이 `login_items`이면 `_parse_login_items`는 `LoginHook`이나 `LogoutHook` 키가 있을 때 그 값 앞에 경고 기호(⚠️)를 붙이고 지속성 수단 후보(`Potential persistence mechanism`)라고 적는다 [3].
`plist_type`이 `launch_agent`이면 `_parse_launch_agent`는 `RunAtLoad`·`KeepAlive`가 참이거나 `StartInterval`이 있을 때 경고 기호와 그 키의 동작 설명을 붙인다 [4].
`LoginHook`·`LogoutHook`을 넣은 이진 plist를 `login_items`로 주자 두 키에 경고 기호와 지속성 수단 후보 문구가 실렸다 [5].
`RunAtLoad`·`KeepAlive`·`StartInterval`을 넣은 이진 plist를 `launch_agent`로 주자 세 키에 경고 기호가 실렸다 [5].

`analyze_shimcache`는 AppCompatCacheParser가 쓴 CSV를 `_analyze_shimcache_output`으로 다시 읽어 행마다 `Path` 값을 정해 둔 규칙으로 분류한다 [2].

- 경로에 `\temp\`, `\tmp\`, `\downloads\`, `\$recycle.bin\`, `\appdata\local\temp\`, `\programdata\` 가운데 하나가 있으면 의심 경로 수 `suspicious_count`에 더한다 [2].
- 경로가 `E:`부터 `Z:`까지의 드라이브 문자로 시작하면 USB 실행 파일 수 `usb_count`에 더한다 [2].
- 경로가 `\\`로 시작하면 네트워크 공유 실행 파일 수 `network_count`에 더한다 [2].

처리기는 이 수를 결과의 `summary`에 모아 서버 로그에 적고 응답 글에는 싣지 않는다 [6].
처리기는 AppCompatCacheParser가 쓴 CSV를 고치지 않아 분류 결과가 CSV에도 남지 않는다 [2][7].
AppCompatCacheParser 자리에 시험용 대체를 두고 경로 6개를 쓴 CSV를 만들게 하자 서버 로그에 의심 경로 3, USB 1, 네트워크 공유 1이 적혔고 응답에는 처리한 하이브 수, 항목 수, 출력 파일만 실렸다 [8].
같은 처리기의 `get_suspicious_executable_paths`와 Amcache 처리기의 `get_suspicious_execution_paths`도 의심 경로 목록을 돌려주지만 저장소에서 부르는 곳이 없다 [9].

다른 도구는 분석 도구가 낸 값을 옮기거나 건수를 셀 뿐 서버 코드의 규칙으로 항목을 판정하지 않는다.

- KAPE와 Zimmerman 도구를 실행하는 도구는 분석 도구가 쓴 출력 파일의 목록, 첫 행 몇 줄, 행 수를 응답에 싣고 행의 값을 판정하지 않는다 [10].
- `analyze_event_logs`는 EvtxECmd CSV의 줄마다 `,4624,`·`,4625,` 같은 이벤트 ID 글자가 있는지 보고 종류별 줄 수를 세지만 응답에는 전체 이벤트 수와 Security 로그의 이벤트 수만 싣는다 [11].
- `analyze_mft`의 `mft_timeline` 모듈은 `MFT_Timeline.csv`의 글 전체에서 `DELETED`와 `:`가 나온 횟수를 삭제 파일 수와 ADS 수로 싣도록 짜여 있다 [12].
- `analyze_memory`는 Volatility 3 출력을 5,000자까지 옮기고 `windows.malfind` 같은 플러그인의 판정은 Volatility가 정한다 [13].
- `identify_file_type`은 파일 머리 바이트와 이름으로 파일 형식을 정하고 형식마다 정해 둔 도구 이름과 메모를 싣는다 [14].
- `crack_hash`의 `detect_hash_mode`는 해시 문자열의 길이와 앞머리로 hashcat 모드 번호를 정한다 [15].
- `analyze_lnk_files`의 `lnk_removable` 모듈은 LECmd가 쓴 `DriveType` 값에 `removable`이나 `usb`가 있거나 값이 `2`인 행만 골라 `_Removable.csv`로 따로 쓴다 [16].

`analyze_mft`는 MFTECmd에 `--csvf` 없이 `--csv`만 넘긴다 [17].
MFTECmd `6aadd87`은 `--csvf`가 없으면 실행 시각을 붙인 이름으로 CSV를 쓰므로 `MFT_Timeline.csv`가 없어 응답의 삭제 파일 수와 ADS 수 자리에는 `File not found`가 실린다 [12][17].

**한계.** plist 해석 함수는 모델이 준 `plist_type`으로만 고르고 파일 이름이나 내용으로 고르지 않는다 [1].
같은 이진 plist를 `plist_type` 없이 주자 `LoginHook`과 `LogoutHook`의 키와 값만 실리고 표시는 붙지 않았다 [5].
XML plist는 해석 함수를 거치지 않고 파일 글 전체를 돌려주어 `login_items`를 주어도 표시가 붙지 않았다 [1][5].
`_analyze_shimcache_output`은 CSV를 읽다 예외가 나면 경고 로그만 남기고 그때까지 센 수를 돌려준다 [2].
README의 예시 대화는 의심 실행 표시, 횡적 이동 추적, IOC 상관을 보이지만 서버 코드에는 결과끼리 잇는 처리가 없고 서버가 붙이는 의심 표시는 위 두 경로뿐이다 [18].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 `analyze_macos_plist`의 응답에 적용된다 [1].
응답은 읽은 plist 경로를 `File`로, 준비한 이미지의 파일 이름을 `Source`로, 고른 해석 종류를 `Type`으로 적는다 [19].
경고 기호를 붙인 줄은 그 표시를 낳은 키 이름과 값을 함께 적는다 [3][4].

`analyze_shimcache`의 분류는 서버 로그에 실행한 명령, 출력 CSV 이름, 분류별 수를 남긴다 [6][20].
어느 행이 어느 규칙에 맞았는지와 규칙의 경로 목록은 서버 로그에도 응답에도 남지 않는다 [2][6].
