# D05 파생물 저장 실패 처리

### D05.01 오류·부분 완료 표시

**구현.** 이 방식은 서버가 파생물을 쓰는 경로, 곧 `analyze_memory`의 출력 저장, `analyze_sqlite_database`의 CSV 쓰기, 모든 처리기의 출력 폴더 만들기에 적용된다 [1][2][3].

`analyze_memory`는 `_save_output_to_file`에서 출력 폴더를 만들고 결과를 파일에 쓴다 [1].
이때 난 예외를 따로 처리하지 않아 처리기의 바깥 `except`까지 올라가 `ERROR: <예외>` 글로 끝난다 [1][4].
`analyze_sqlite_database`는 조회·내보내기 CSV를 쓰다 난 예외를 따로 처리하지 않아 바깥 `except`가 `ERROR: <예외>`로 돌려준다 [2][5].
`get_case_output_directory`는 출력 폴더를 `mkdir`로 만든다 [3].
여기서 난 예외도 각 처리기의 `except`까지 올라가 오류 글로 끝난다 [3].

KAPE와 EZ Tools로 파생물을 만드는 처리기는 실행 파일의 종료 코드와 출력 파일 유무로 성공과 실패를 가른다 [6][7].
레지스트리 처리기는 종료 코드가 0이 아니면 `FAILED`와 종료 코드, 표준 오류 앞부분을 결과에 싣는다 [8].
셸백 처리기는 출력 파일이 하나도 없으면 그 모듈을 실패로 적는다 [9].
성공한 모듈이 없으면 응답 전체를 실패로 돌려준다 [9].

**한계.** `analyze_amcache`와 `analyze_shellbags`는 출력 폴더에 파일이 있는지로 성공을 판정하고 그 파일을 이번 실행이 썼는지 가리지 않는다 [7][10].
`analyze_amcache`는 출력 폴더를 비우지 않으므로 AmcacheParser가 실패해도 앞 실행의 CSV가 남아 있으면 성공으로 돌려준다 [10].

### D05.03 알림 없이 계속

**구현.** 이 방식은 `kape_parse_artifact`가 KAPE 콘솔 로그를 출력 폴더로 옮기는 경로, `analyze_registry`가 KAPE 출력의 하위 폴더를 미리 만드는 경로, `ExtractionManager`가 이미지의 폴더를 푸는 경로, `analyze_lnk_files`의 `lnk_removable` 모듈이 걸러 낸 CSV를 쓰는 경로에 적용된다 [11][12][13][14].
`kape_parse_artifact`는 KAPE 실행 파일 폴더의 `*_ConsoleLog.txt`를 출력 폴더로 옮긴다 [11].
옮기기와 복사가 모두 `OSError`나 `PermissionError`로 실패하면 경고만 로그에 남기고 다음 단계를 실행해 성공 응답을 돌려준다 [11].
레지스트리 처리기는 KAPE 출력의 하위 폴더를 미리 만들다 난 예외를 경고로 남기고 이어서 KAPE를 실행한다 [12].

`ExtractionManager`는 SleuthKit 이미지의 폴더를 풀 때 파일마다 SleuthKit `icat`을 실행하고 그 결과를 보지 않는다 [13].
`icat`이 실패해도 미리 연 출력 파일이 남고 그 파일도 푼 수 `file_count`에 세며 `extraction_registry.json`에 푼 것으로 적는다 [13][15].
이때 경고 로그도 남기지 않는다 [13].
실행 확인에서 한 inode의 `icat`을 실패시키자 0바이트 파일이 남았고 등록부의 `file_count`에 들어가고 `failed_count`는 0이었다 [16].

`analyze_lnk_files`의 `lnk_removable` 모듈은 걸러 낸 CSV를 쓰다 예외가 나면 오류 로그만 남기고 이어서 응답을 만든다 [14].
