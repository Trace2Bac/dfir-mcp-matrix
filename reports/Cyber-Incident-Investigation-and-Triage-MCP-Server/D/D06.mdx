# D06 산출물 식별·재생성 처리

### D06.02 입력·작업별 고유 이름

**구현.** 이 방식은 서버가 정하는 출력 폴더 이름과 EZ Tools가 정하는 출력 파일 이름, SQLite 조회 결과 파일 이름에 적용된다 [1][2][3].
서버는 파생물을 `cases/<이미지 ID>/<도구 종류>/<모듈>_<식별자>/` 아래에 둔다 [1].
이미지 ID에는 이미지 이름과 앞부분 해시가 들어가므로 다른 이미지의 파생물과는 폴더가 갈린다 [1].
입력별로 폴더가 갈리는 것은 입력 경로의 마지막 이름을 식별자로 넣는 `analyze_registry`·`analyze_lnk_files`와 이미지 안 상대 경로를 넣는 `kape_parse_artifact`다 [4][5].
`analyze_memory`는 출력 폴더에 메모리 파일 이름을 넣는다 [6].
나머지 YAML 도구 7개는 식별자에 고정 문자열을 넣어 같은 이미지의 다른 입력도 같은 폴더를 쓴다 [5].
같은 입력을 다시 분석한 결과는 같은 폴더에 들어가 구별하지 않는다 [7].

EZ Tools 실행 파일은 출력 CSV 이름에 실행 시각 `yyyyMMddHHmmss`를 접두어로 붙인다 [2][8].
그래서 `analyze_amcache`·`analyze_mft`·`analyze_event_logs`처럼 EZ Tools를 다시 실행하는 도구에서는 재실행마다 이름이 달라진다 [2][9].
`analyze_sqlite_database`의 `query`는 조회문의 해시로 지은 `query_<숫자>.csv`에 결과를 쓰므로 조회문마다 이름이 갈린다 [3].
`analyze_sqlite_database`는 DB 파일을 `extracted_files`로 복사할 때 같은 이름의 파일이 있고 크기가 다르면 이름 뒤에 번호를 붙여 둘을 구분한다 [10].

**한계.** `analyze_sqlite_database`의 `query` 파일 이름에 쓰는 해시는 파이썬 `hash`로 구한다 [3].
같은 조회문이라도 서버를 다시 시작하면 다른 이름이 되고 한 실행 안에서는 같은 이름을 쓴다 [3].
한 실행 안에서 같은 조회문을 다시 실행하면 앞 CSV를 알리지 않고 덮어쓴다 [11][12].

### D06.03 버전·이력 보존

**구현.** 이 방식은 `analyze_amcache`·`analyze_mft`·`analyze_event_logs`에 적용된다 [9].
이 규칙은 서버 코드가 아니라 EZ Tools가 정한다 [2].
이 세 도구는 EZ Tools 실행 파일을 직접 부르고 출력 폴더를 비우지 않으며 같은 결과가 있는지 보지 않는다 [9].
EZ Tools는 출력 CSV 이름에 실행 시각을 붙인다 [2][8].
그래서 같은 입력을 다시 분석하면 앞 CSV를 지우지 않고 시각이 다른 새 CSV를 같은 폴더에 남겨 둘을 구분할 수 있다 [2].

`analyze_shimcache`는 `AppCompatCacheParser`에 고정 이름 `<하이브 이름>_AppCompatCache.csv`를 넘긴다 [13].
그래서 다시 분석하면 앞 CSV를 알리지 않고 덮어쓴다 [14].
`analyze_prefetch`·`analyze_shellbags`·`analyze_lnk_files`·`analyze_jump_lists`는 KAPE에 `--mflush`를 준다 [15].
KAPE는 출력 폴더를 지운 뒤 다시 만들어 앞 산출물을 지운다 [16].
이 가운데 `analyze_prefetch`·`analyze_shellbags`·`analyze_jump_lists`는 준비된 이미지 안에서 출력 폴더를 입력별로 나누지 않으므로 같은 이미지의 다른 입력을 분석하면 앞 입력의 산출물을 지운다 [5][15].
`analyze_sqlite_database`의 `export_table`은 `<table_name>.csv`로 쓰므로 같은 표를 다시 내보내면 앞 CSV를 알리지 않고 덮어쓴다 [17].

### D06.04 덮어쓰기 선택·충돌 감지

**구현.** 이 방식은 `kape_parse_artifact`와 `analyze_registry`의 출력 폴더 재사용, `ExtractionManager`의 추출 재사용, `analyze_sqlite_database`의 DB 복사 재사용, `get_readable_file_path`의 WSL APFS·LVM 추출 재사용에 적용된다 [18][19][20][21].
`kape_parse_artifact`와 `analyze_registry`는 출력 폴더가 이미 있고 비어 있지 않으면 KAPE를 실행하지 않고 그 폴더의 앞 결과를 돌려준다 [18][22].
`ExtractionManager`는 같은 이미지의 같은 내부 경로가 등록부에 있고 그 폴더가 남아 있으면 다시 풀지 않고 그 폴더를 쓴다 [19].
등록부에는 있는데 폴더가 없으면 등록을 지우고 다시 푼다 [19].
`analyze_sqlite_database`의 DB 복사는 목적지에 같은 이름의 파일이 있고 크기가 같으면 다시 복사하지 않고 그 파일을 쓴다 [20].
이미지 안 파일을 읽는 도구가 거치는 공통 함수 `get_readable_file_path`는 WSL APFS·LVM으로 준비한 이미지의 파일을 사건 폴더의 `extracted/<파일 이름>`으로 꺼낸다 [21].
이 파일이 이미 있으면 다시 꺼내지 않고 그 파일을 돌려준다 [21].
덮어쓸지를 호출 인자로 고르게 하는 도구는 없다.

**한계.** `kape_parse_artifact`와 `analyze_registry`의 재사용은 출력 폴더 이름으로만 판정한다 [22].
`analyze_registry`의 폴더 이름에는 입력 경로의 마지막 이름만 들어가므로 다른 위치의 같은 이름 입력을 분석하면 앞 결과를 그대로 돌려준다 [5][22].
`analyze_registry`는 KAPE 실행 전에 `Registry` 하위 폴더를 만들고 `kape_parse_artifact`는 실패한 실행의 콘솔 로그도 출력 폴더로 옮겨 앞 실행이 실패해도 출력 폴더가 비지 않는다 [23].
그래서 실패한 뒤 같은 입력을 다시 부르면 KAPE를 실행하지 않고 앞 결과로 응답한다 [18][22].
실행 확인에서 종료 코드 1로 실패한 레지스트리 분석을 다시 부르자 빈 `Registry` 폴더만 있는 출력 폴더로 `CACHED (already analyzed)`가 성공 표시와 함께 돌아왔다 [24].
실패한 `kape_parse_artifact`를 다시 부르자 콘솔 로그 하나만 있는 출력 폴더로 `CACHED ARTIFACT PARSING RESULTS`가 돌아왔다 [24].
`ExtractionManager`는 일부 파일을 풀지 못한 추출도 등록부에 푼 것으로 적어 다음 호출에서 다시 풀지 않고 그 폴더를 쓴다 [19][25].
`analyze_sqlite_database`의 DB 복사는 이름과 크기만 보므로 크기가 같고 내용이 다른 파일은 앞 파일을 쓴다 [20].
크기가 같은 두 `History` DB를 같은 사건에서 조회하자 뒤 조회가 앞 DB의 행을 돌려주었다 [26].
`get_readable_file_path`의 재사용은 사건 폴더 안의 파일 이름만 보므로 같은 이미지에서 경로가 다르고 이름이 같은 파일을 요청하면 앞에 꺼낸 파일을 돌려준다 [21].
이 동작은 WSL 마운트를 실행하지 않아 코드로만 확인했다.
