# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 MCP Python SDK가 인자 schema를 어기는 호출을 처리하는 경로에만 적용된다 [1].
SDK 1.29.1의 저수준 `call_tool`은 처리기를 부르기 전에 도구의 `inputSchema`로 인자를 검사하고 어기면 `isError`가 참인 결과를 돌려준다 [1].
서버의 `create_server`가 등록한 `call_tool`은 처리기에서 난 예외를 모두 처리해 `ERROR: Tool execution failed:`로 시작하는 글을 `isError`가 거짓인 결과로 돌려준다 [2].
필수 인자를 뺀 호출에는 `isError`가 참인 `Input validation error`가 왔다 [3].

**한계.** 서버가 스스로 낸 실패는 모두 `isError`가 거짓인 글로 나가고 성공과 글의 문구로만 갈린다 [2].
응답에 성공과 실패를 나누는 필드나 상태 값은 없다 [2].
알 수 없는 도구 이름에는 `ERROR: Unknown tool:`을, 준비한 증거가 아닌 경로에는 `ACCESS DENIED`를 `isError`가 거짓인 글로 돌려준다 [2][4].
인자 이름이 schema에 없어 처리기가 받지 못하는 호출도 schema 검사를 지나 처리기 예외가 되어 `isError`가 거짓인 글로 돌아왔다 [2][3].

### R03.03 입력별 성공·실패·생략 목록

**구현.** 이 방식은 경로와 모듈 여러 개를 처리하는 `analyze_mft`, `analyze_amcache`, `analyze_registry`에 적용된다 [5][6][7].
`analyze_mft`와 `analyze_amcache`는 경로와 모듈마다 성공과 실패를 나눠 싣고 성공이면 경로와 집계 값을, 실패면 경로와 오류 `error`를 싣는다 [5][6].
두 도구는 응답 머리에 성공 수와 실패 수를 센다 [5][6].
`analyze_registry`는 실행한 모듈마다 `Status`를 `SUCCESS`, `CACHED (already analyzed)`, `FAILED - Administrator privileges required`, `FAILED (Return code: N)`, `EXCEPTION` 가운데 하나로 싣고 원본 파일 이름을 함께 적는다 [7][8].

**한계.** `analyze_shellbags`·`analyze_jump_lists`는 성공한 항목만 목록으로 싣고 실패한 항목은 머리의 실패 수로만 센다 [9][10].
`analyze_lnk_files`는 일부가 실패하면 성공한 항목과 그 수만 싣고 실패 수는 적지 않는다 [11].
`analyze_registry`는 이미지에서 파일을 꺼내지 못한 항목, 파일에 맞지 않아 건너뛴 모듈, 설정에 없는 모듈을 응답에 싣지 않는다 [12].
`analyze_registry`는 모든 모듈이 실패해도 응답 끝에 `Analysis completed successfully.`를 적는다 [13].
