# P01 분석 방법 적합성 확인

### P01.01 이름·확장자 판별

**구현.** 이 방식은 `identify_file_type`의 형식 판별, Windows 아티팩트 도구가 이미지 폴더에서 꺼낼 파일을 고르는 경로, 레지스트리 도구의 모듈 고르기에 적용된다 [1][2][3].
`identify_file_type`은 머리 바이트 규칙 뒤에 파일 이름과 확장자 규칙을 적용하고 이름 규칙에 맞으면 그 결과로 형식을 바꾼다 [1].
이름이 `system`·`software`·`sam`·`security`·`ntuser.dat`·`usrclass.dat`이면 레지스트리 하이브로, 확장자가 `.db`·`.sqlite`·`.sqlite3`이거나 이름에 `sqlite`가 있으면 SQLite DB로, `.evtx`·`.evt`면 이벤트 로그로, `.pf`면 Prefetch로 정한다 [1].
정한 형식에 따라 `Primary Tool`과 KAPE 모듈 이름을 응답에 싣는다 [1].
SleuthKit으로 준비한 이미지에서 폴더를 받으면 `analyze_prefetch`는 이름이 `.pf`로 끝나는 파일만, `analyze_lnk_files`는 `.lnk`로 끝나는 파일만 꺼낸다 [2].
`analyze_jump_lists`는 `.automaticdestinations-ms`·`.customdestinations-ms`로 끝나는 파일만, `analyze_shellbags`는 이름이 `NTUSER.DAT`·`USRCLASS.DAT`인 파일만 꺼낸다 [2].
`analyze_mft`와 `analyze_amcache`는 폴더를 받으면 그 아래 `$MFT`와 `Amcache.hve`를 입력으로 정한다 [4].
`analyze_registry`는 모듈마다 `config/forensic_tools.yaml`의 `applies_to_files`에 적힌 하이브 이름이 파일 이름에 들어 있을 때만 그 모듈을 실행한다 [3].
`read_csv_data`는 확장자가 `.csv`가 아니면 읽지 않고 경고를 돌려준다 [5].

**한계.** `identify_file_type`은 확장자만으로 형식을 정하므로 SQLite가 아닌 글 파일도 이름이 `.db`로 끝나면 SQLite DB로 판별하고 `analyze_sqlite_database`를 권한다 [1][6].
`analyze_registry`는 하이브 이름을 부분 문자열로 대조하므로 `SYSTEM.LOG1`처럼 하이브 이름이 들어 있는 파일에도 그 하이브의 모듈을 실행한다 [3].
이 대조는 실제 파일인 경로에만 적용되고 `/<이미지 ID>/…` 꼴의 경로와 폴더 경로에는 적용되지 않는다 [3].
SleuthKit으로 준비한 이미지의 `/<이미지 ID>/…` 경로는 꺼낸 파일의 이름 `inode_<번호>_<이름>`으로 이름 규칙을 대조하고 확장자 규칙은 받은 경로로 대조한다 [1][7].
그래서 하이브 이름과 `.DS_Store`처럼 이름 전체로 정하는 규칙은 이미지 안 파일에 적용되지 않는다 [1][7].
머리에 `regf`가 없는 `SOFTWARE`는 이미지 안 경로로 주자 `Unknown`으로, 같은 내용의 이미지 밖 로컬 파일은 레지스트리 하이브로 판별되었다 [8].

### P01.02 메타데이터 조회

**구현.** 이 방식은 디스크 이미지를 준비하는 `prepare_disk_image`에 적용된다 [9].
`prepare_disk_image`는 SleuthKit `mmls`로 파티션 표를 읽고 파티션마다 `fsstat`으로 파일시스템 종류를 읽는다 [10][11].
`fsstat` 출력에 `ntfs`·`fat`·`exfat`이 있으면 OS를 `windows`로, `ext`·`xfs`·`btrfs`·`lvm2` 등이 있으면 `linux`로, `hfs`·`apfs`가 있으면 `macos`로 정한다 [10].
OS가 `unknown`이나 `macos`이면 `fls`로 루트 폴더 목록을 읽어 `windows`·`program files`나 `/etc/passwd` 같은 이름이 있는지로 OS를 다시 정한다 [12].
파티션이 여럿이면 설명에 NTFS·FAT·Linux가 있거나 파일시스템을 알아본 파티션 가운데 가장 큰 것을 고른다 [13].
`mmls`가 실패하면 파티션 표가 없는 이미지로 보고 시작 위치 0에서 `fsstat`을 실행한다 [14].
판별한 OS와 파일시스템으로 준비 방식을 고른다 [15].
OS가 `windows`이면 Arsenal Image Mounter로 마운트한다 [15].
파일시스템이 `lvm2`이고 OS가 `linux`이면 WSL에서 LVM을 마운트한다 [15].
그 밖에는 SleuthKit으로 파일을 꺼내 읽는다 [15].
판별 결과는 응답과 등록부의 `fs_type`·`os_family`에 남는다 [16].
기준 커밋을 시험용 SleuthKit 실행 파일로 실행하자 NTFS 파티션 하나를 가진 이미지에서 `os_family`가 `windows`, `partition_offset`이 2048로 등록되었다 [17].
그 실행에서 Arsenal의 `aim_cli` 실행 파일이 없자 서버는 SleuthKit 방식으로 준비를 이어 갔고 응답은 이 전환을 적지 않았다 [17].

**한계.** 파티션 표 파서는 줄에 `DOS`가 들어 있으면 건너뛴다 [18].
SleuthKit 4.14.0의 `mmls`는 FAT16 파티션을 `DOS FAT16 (0x06)`처럼 적으므로 이런 파티션은 후보에서 빠진다 [18][19].
20000섹터보다 작은 파티션도 후보에서 빠진다 [18].
`fls`로 OS를 다시 정할 때는 파일시스템 종류를 늘 `hfs+`로 정해 실행하므로 다른 파일시스템에서는 이 판별이 결과를 내지 못한다 [12].
Arsenal 마운트가 실패하면 서버 로그에만 경고를 남기고 SleuthKit으로 준비한다 [15].

### P01.03 내용·헤더 검사

**구현.** 이 방식은 `identify_file_type`, `analyze_sqlite_database`, `decompress_mozilla_lz4`, `analyze_macos_plist`, `prepare_disk_image`의 형식 판별에 적용된다 [1][6][20][21][14].
`identify_file_type`은 파일 앞 32바이트를 읽어 gzip, XML, 이진 plist, `.DS_Store`, Mach-O, 레지스트리 하이브 서명 `regf`, EVTX 서명 `ElfFile`, Prefetch 서명 `SCCA`를 찾는다 [1].
이름이 `hidden.bin`인 레지스트리 하이브를 주자 `identify_file_type`은 `regf` 서명으로 레지스트리 하이브로 판별했다 [22].
`analyze_sqlite_database`는 꺼낸 파일의 앞 16바이트가 `SQLite format 3\x00`인지 확인한다 [6].
`decompress_mozilla_lz4`는 파일이 `mozLz40\0`으로 시작하지 않으면 풀지 않는다 [20].
`analyze_macos_plist`는 머리가 `<?xml`이면 글로 읽고 아니면 이진 plist로 읽는다 [21].
`prepare_disk_image`는 파티션 표가 없는 이미지의 앞 512바이트를 읽어 그 가운데 앞 64바이트에서 APFS 서명 `NXSB`를 찾고 있으면 WSL의 apfs-fuse로 마운트하는 경로로 바꾼다 [14][23].
`fsstat`이 파일시스템을 알아보지 못한 파티션은 그 시작 위치의 1024바이트에서 LVM 서명을 찾는다 [11].

**한계.** `identify_file_type`의 SQLite 서명은 코드에 `b'SQLite format 3\\x00'`으로 적혀 있어 끝의 널 바이트 대신 역슬래시 문자열과 대조한다 [1].
그래서 SQLite 파일은 서명으로 판별되지 않고 확장자로만 판별된다 [1].
SQLite DB를 확장자 `.sqlite`로 주자 응답의 머리 바이트는 `53 51 4C 69 …`였고 판별은 확장자 규칙으로 이루어졌다 [22].
`prepare_disk_image`의 APFS·LVM 서명 확인은 이미지 파일의 바이트를 그대로 읽으므로 EWF 이미지에서는 담긴 매체가 아니라 EWF 파일 자체의 바이트를 본다 [14][11].

### P01.04 방법과 형식·OS 대조

**구현.** 이 방식은 `analyze_sqlite_database`, `decompress_mozilla_lz4`, `analyze_registry`에 적용된다 [6][20][3].
`analyze_sqlite_database`는 모델이 고른 SQLite 도구가 입력과 맞는지 머리 서명으로 확인하고 맞지 않으면 열지 않는다 [6].
이때 `identify_file_type`과 같은 판별 함수로 정한 형식과 권하는 도구를 응답에 싣는다 [6].
`decompress_mozilla_lz4`는 이름과 머리 서명이 Mozilla LZ4 형식이 아니면 풀지 않는다 [20].
`analyze_registry`는 모듈이 적용되는 하이브와 파일 이름이 맞지 않으면 그 모듈을 건너뛴다 [3].
모든 모듈을 건너뛴 호출은 결과 없이 적용되는 모듈이 없을 수 있다는 문장을 돌려준다 [3][24].

다른 도구는 고른 방법을 입력과 대조하지 않는다.
`analyze_memory`는 받은 Volatility 3 플러그인을 OS 확인 없이 실행하고 처리기 설명은 OS 판별과 검사를 Volatility에 맡긴다고 적는다 [25].
`kape_parse_artifact`는 받은 KAPE 모듈 이름을 파일 형식과 대조하지 않는다 [26].
macOS 도구 4개는 준비한 이미지의 `os_family`를 보지 않는다 [21].

**한계.** `analyze_sqlite_database`는 SQLite가 아닌 파일을 거부할 때 확장자로 정한 형식을 그대로 싣는다 [6][1].
SQLite가 아닌 글 파일 `fake.db`를 주자 거부 응답은 형식을 `SQLite Database`로 적고 `analyze_sqlite_database`를 대신 쓰라고 적었다 [22].
`analyze_registry`의 이름 대조는 실제 파일인 경로에만 적용되므로 SleuthKit으로 준비한 이미지의 경로와 폴더 경로에서는 모든 모듈이 실행된다 [3].

    def _select_primary_partition(self, partitions: List[Dict]) -> Optional[Dict]:
        """Select the primary partition to mount (usually the largest data partition)"""
        if not partitions:
            return None
        
        data_partitions = [p for p in partitions 
                          if 'NTFS' in p['description'] or 
                             'FAT' in p['description'] or
                             'Linux' in p['description'] or
                             'Primary' in p['description'] or
                             p.get('fs_type', 'unknown') != 'unknown']
        
        if not data_partitions:
            data_partitions = partitions
        
        return max(data_partitions, key=lambda p: p['length'])
