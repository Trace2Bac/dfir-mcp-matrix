# P04 조사 단위 관리

### P04.01 사건 시작 시 ID 확정

**구현.** 이 방식은 디스크 이미지를 준비하는 `prepare_disk_image`에 적용된다 [1].
조사 단위는 준비한 이미지 하나이고 사건을 따로 만들거나 여는 도구는 없다.
`prepare_disk_image`는 이미지 파일 이름, 판별한 OS, 이미지 해시의 앞 12글자를 이어 `unique_image_id`를 정한다 [1].
해시는 이미지의 앞 10 MiB만 읽은 SHA-256이다 [2].
같은 이름의 사건 폴더 `cases/<unique_image_id>`를 만들고 응답에 `Image Root: /<unique_image_id>/`와 사건 폴더 경로를 싣는다 [1][3].
`unique_image_id`와 사건 폴더 경로는 등록부 `PREPARED_IMAGES`의 그 이미지 항목에 들어간다 [3].
이후 도구는 `/<unique_image_id>/…` 꼴의 경로나 준비한 접근 폴더 아래 경로로 이미지를 가리키고 서버는 그 경로로 찾은 항목의 `case_dir` 아래에 출력을 쓴다 [4][5].
이미지를 여럿 준비하면 항목이 나란히 남아 경로마다 다른 이미지에 묶인다 [3][4].
이름 줄기가 `disk01`인 시험 이미지를 준비하자 `unique_image_id`는 `disk01_windows_5e492a138d5e`가 되었고 같은 이름의 사건 폴더가 생겼다 [6].

`analyze_memory`는 등록부를 쓰지 않아 이미지 ID에 묶이지 않는다 [7].

**한계.** 앞 10 MiB 뒤의 바이트만 다른 두 이미지는 이름과 OS가 같으면 같은 `unique_image_id`와 같은 사건 폴더를 받는다 [1][2].
10 MiB 뒤의 바이트 하나를 바꾼 사본의 해시는 원래 이미지의 해시와 같았다 [8].
해시를 계산하다 예외가 나면 이미지 경로 문자열의 MD5를 해시 자리에 쓴다 [2].
준비하지 않은 로컬 경로를 받는 Windows 아티팩트 도구와 `identify_file_type`의 대체 경로는 등록부를 거치지 않으므로 이미지 ID에 묶이지 않는다 [9][10][11].

### P04.02 호출마다 사건 ID 전달·검사

**구현.** 이 방식은 경로 대조 함수 `validate_file_access`를 부르는 파일 읽기 도구와 분석 도구, 둘러보기 도구에 적용된다 [4][12].
`/`로 시작하는 경로는 첫 조각을 등록부의 `unique_image_id`들과 대조하고 같은 항목이 있으면 그 이미지로 정한다 [4].
같은 항목이 없고 경로가 준비한 이미지의 접근 위치나 사건 폴더 아래에도 없으면 `SecurityError`로 거부한다 [4].
`browse_files_and_folders`도 경로의 첫 조각을 `unique_image_id`와 대조하고 맞는 이미지가 없으면 쓸 수 있는 이미지 경로의 앞부분을 돌려준다 [12].
시험 이미지를 준비한 뒤 첫 조각이 등록되지 않은 ID인 경로와 접근 폴더 위로 올라가는 경로를 주자 둘 다 거부되었다 [6].

`analyze_memory`는 이 대조를 부르지 않는다 [7].

**한계.** SleuthKit으로 준비한 이미지 가운데 OS가 `linux`나 `macos`인 것이 있으면 첫 조각이 ID가 아닌 `/` 경로도 받아들이고 등록부 차례에서 처음 만난 그 이미지로 정한다 [4].
준비한 이미지가 하나도 없을 때는 사건 폴더 이름에 첫 조각이 문자열로 들어 있고 그 폴더의 `extracted`에 같은 이름의 파일이 있으면 그 폴더를 사건으로 정해 받아들인다 [4].
`analyze_registry`·`analyze_prefetch`·`analyze_mft`·`analyze_shimcache`는 대조에 실패해도 디스크에 있는 경로이면 이미지 없이 분석한다 [9].
`analyze_jump_lists`·`analyze_lnk_files`·`analyze_amcache`도 등록부에 없는 경로를 디스크에 있으면 받는다 [10].
`identify_file_type`은 대조에 실패하면 받은 경로를 그대로 읽는다 [11].

### P04.03 폴더·DB·manifest에 사건 ID 연결

**구현.** 이 방식은 사건 폴더, 등록부 항목, 분석 도구의 출력 폴더, 추출 폴더에 적용된다 [1][3][5][13][14].
사건 폴더 이름과 등록부 항목의 `unique_image_id`·`case_dir`가 이미지 ID를 담는다 [1][3].
Windows 아티팩트 도구의 출력 폴더는 공통 함수 `get_case_output_directory`가 `<case_dir>/<자료 이름>/<모듈>_<식별자>`로 정한다 [5].
SleuthKit으로 꺼낸 파일은 `cases/<unique_image_id>/extracted_files` 아래에, 레지스트리 폴더 추출은 `extract/<unique_image_id>` 아래에 둔다 [13][14].
레지스트리 폴더 추출 기록 `extraction_registry.json`은 이미지 ID를 키로 쓴다 [14].

**한계.** 이미지 ID를 이름에 쓰지 않는 저장물이 있다.
`analyze_sqlite_database`는 CSV를 `cases/<이미지 이름>_<전체 해시>/sqlite_analysis` 아래에 쓴다 [15].
시험 이미지에서 SQLite 조회 결과는 `disk01_windows_5e492a138d5e`가 아닌 `disk01_<전체 해시>` 폴더에 쓰였다 [6].
`analyze_memory`는 메모리 파일 이름의 줄기로 `cases/<줄기>/memory/<플러그인>` 폴더를 정한다 [7].
`kape_parse_artifact`와 SleuthKit을 쓰는 Windows 아티팩트 도구는 꺼낸 파일을 설정의 임시 폴더 아래 `<도구>_extract_<inode>` 폴더에 둔다 [16].
이미지에 묶이지 않은 호출은 `local_analysis`, `local_kape_<모듈>`, `standalone_event_logs_<시각>`, `<상위 폴더>_prefetch` 같은 폴더에 쓴다 [5][17].
서버 로그, `operations_logs`의 기록, `kape_operations.log`는 이미지와 관계없이 한 파일씩이고 항목에 이미지 ID 필드가 없다 [18].

### P04.04 사건별 폴더·DB 분리

**구현.** 이 방식은 준비한 이미지마다 두는 사건 폴더에 적용된다 [1].
서버는 준비한 이미지마다 `cases/<unique_image_id>` 폴더를 따로 두고 그 이미지를 가리키는 호출의 출력과 꺼낸 파일을 그 아래에 쓴다 [1][5][13].
SleuthKit 파일 추출의 경로 대응표 `path_mapping.json`도 그 이미지의 사건 폴더 안에 둔다 [13].
`analyze_registry`와 `kape_parse_artifact`는 같은 출력 폴더가 비어 있지 않으면 다시 실행하지 않고 그 폴더를 돌려주므로 앞선 결과도 사건 폴더별로 남는다 [19][20].

서버는 연결이나 세션마다 상태를 나누지 않는다.
`remote_server.py`의 SSE 연결은 모두 같은 프로세스의 `create_server` 객체와 모듈 전역 `PREPARED_IMAGES`를 쓴다 [21].

**한계.** 여러 경로를 받는 `analyze_event_logs`·`analyze_jump_lists`·`analyze_amcache`는 처음 대조에 성공한 경로의 이미지 항목으로 모든 경로의 출력 폴더를 정한다 [10][17].
그래서 다른 이미지의 경로를 함께 주면 그 출력도 첫 이미지의 사건 폴더에 쓰인다 [10][17].
`<도구>_extract_<inode>` 임시 폴더는 이미지 ID 없이 inode 번호로만 이름을 짓는다 [16].
`kape_parse_artifact`는 이 폴더를 지우지 않으므로 다른 이미지에서 같은 inode의 파일을 꺼내면 앞 이미지에서 꺼낸 파일이 남은 폴더 전체를 KAPE의 `--msource`로 넘긴다 [16][22].
이 경로는 코드로만 확인했다.
`analyze_memory`는 이름이 같은 메모리 파일을 위치가 달라도 같은 폴더에 쓴다 [7].
다른 폴더의 `mem.raw` 두 개를 차례로 분석하자 두 결과가 같은 `cases/mem/memory/windows.pslist` 폴더의 같은 파일에 쓰였다 [8].
WSL LVM 경로는 이미지마다 `/mnt/ubuntu_forensics`에 마운트한다 [23].
그래서 LVM 이미지를 둘 준비하면 두 항목이 같은 마운트 위치를 가리키고 앞 이미지의 경로로 읽어도 나중에 마운트한 파일시스템의 파일을 읽는다 [23][24].
이 경로는 코드로만 확인했다.
SleuthKit 준비 객체의 접근 폴더는 이미지 파일 이름의 줄기로만 짓는다 [25].
그래서 이름 줄기가 같은 두 이미지는 접근 폴더와 메타데이터 파일 하나를 함께 쓰고 한 이미지를 정리하면 다른 이미지의 메타데이터 파일도 지워진다 [25][26].
이 경로는 코드로만 확인했다.

            if not os.path.exists(image_path):
                raise FileNotFoundError(f"Image path does not exist: {image_path}")

            if file_size == 0:

            hash_obj = hashlib.sha256()
            sample_size = min(sample_size_mb * 1024 * 1024, file_size)
            
            with open(image_path, 'rb') as f:
                chunk = f.read(sample_size)
                if not chunk:
                    logger.warning(f"Could not read from image file: {image_path}")
                    return hashlib.md5(image_path.encode()).hexdigest()
                hash_obj.update(chunk)
            
            full_hash = hash_obj.hexdigest()
            
            logger.info(f"Image hash calculated: {full_hash} (Sample size: {len(chunk)} bytes)")
            return full_hash
            
        except Exception as e:
            logger.error(f"Failed to calculate image hash: {e}")
            fallback_hash = hashlib.md5(image_path.encode()).hexdigest()
            logger.info(f"Using fallback hash: {fallback_hash}")

    def extract_file(self, image_path: str, file_path: str) -> Dict:
        """Extract file from mounted image"""
        ensure = self.ensure_mounted(image_path)
        if not ensure['success']: return ensure
        
        mount_point = ensure['mount_point']
        target = os.path.join(mount_point, file_path.lstrip('/')).replace('\\', '/')
        result = self._run_wsl(f'cat "{target}"', timeout=60)
        return {'success': True, 'content': result.stdout} if result.returncode == 0 else {'success': False, 'error': result.stderr}
