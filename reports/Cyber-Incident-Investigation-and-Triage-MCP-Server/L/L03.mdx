# L03 기록 실패 처리

### L03.01 실행 후 응답 차단

**구현.** 이 방식은 `get_kape_modules_catalog`와 `kape_parse_artifact`가 KAPE 실행을 마친 뒤 쓰는 KAPE 기록 항목에 적용된다 [1][2].
`log_kape_operation`은 기록 파일을 열고 쓰다 난 예외를 처리하지 않고 호출한 쪽으로 넘긴다 [3].
`get_kape_modules_catalog`는 KAPE를 실행한 뒤 이 함수를 부르고 예외가 나면 결과 대신 `ERROR: KAPE Module Info Error: …` 글을 돌려준다 [1].
`kape_parse_artifact`의 실행 함수 `execute_kape_parsing`도 실행 뒤 항목에서 예외가 나면 결과 대신 `ERROR: KAPE execution failed: …` 글을 돌려준다 [2].
두 처리기는 이 오류를 응답에만 싣고 로거에 쓰지 않는다 [1][2].
`kape_operations.log` 자리에 같은 이름의 폴더를 두고 `get_kape_modules_catalog`를 부르자 시험용 KAPE는 실행되었고 응답은 `Permission denied` 오류 글이었다 [4].
시험용 KAPE가 실행 중에 `kape_operations.log`를 폴더로 바꾸게 하고 `kape_parse_artifact`를 부르자 KAPE는 실행되었고 응답은 같은 오류 글이었다 [5].
그 호출의 `mcp_server_<시각>.log`에는 `Tool called`와 `Executing KAPE command` 줄만 있었다 [5].

**한계.** `kape_parse_artifact`는 실행 뒤 항목 쓰기가 실패해도 KAPE 출력을 결과 폴더에 남긴다 [2].
같은 인자로 다시 부르면 저장해 둔 결과를 돌려주는 경로가 기록 함수를 부르지 않고 그 출력을 돌려준다 [6].
시험용 KAPE가 결과 파일을 쓰고 `kape_operations.log` 자리에 폴더를 만들게 한 뒤 같은 인자로 두 번 부르자 첫 호출은 오류 글이었고 두 번째 호출은 저장된 결과 목록이었다 [7].

### L03.02 경고 후 계속

**구현.** 이 방식은 Python `logging`으로 쓰는 항목에 적용된다 [8][9].
`call_tool`의 `Tool called` 줄, 처리기들의 로거 줄, 운영 기록 `operations_<날짜>.log`의 항목이 여기에 해당한다 [8][9].
이 항목은 표준 라이브러리 `FileHandler`가 쓰고 서버는 처리기의 오류 처리를 바꾸지 않는다 [8][9].
CPython 3.13.14의 `StreamHandler.emit`은 쓰기에서 난 예외를 `handleError`로 넘긴다 [10].
`handleError`는 `raiseExceptions`가 기본값인 참이면 `--- Logging error ---`, 예외 추적 정보, 그 항목의 메시지와 인자를 `sys.stderr`에 쓰고 예외를 호출한 쪽으로 넘기지 않는다 [10].
stdio 진입점 `main.py`는 `sys.stderr`를 저장소 폴더의 `stderr.log`로 바꾸므로 이 알림은 `stderr.log`에 남는다 [11].
`remote_server.py`는 표준 오류를 바꾸지 않아 알림이 서버 프로세스의 표준 오류로 나간다 [12].
`main.py`와 같은 차례로 로깅을 설정하고 두 기록 파일의 쓰기가 모두 실패하게 한 뒤 `list_prepared_images`·`prepare_disk_image`를 부르자 두 도구 모두 평소와 같은 결과를 돌려주었다 [13].
같은 실행에서 표준 오류 자리의 파일에 `--- Logging error ---` 알림이 31번 남았다 [13].

**한계.** `handleError`는 `sys.stderr`에 쓰다 `OSError`가 나면 아무것도 하지 않는다 [10].
그래서 `stderr.log`에도 쓸 수 없으면 기록 실패 사실도 남지 않는다 [10][11].
운영 기록 `forensic_operations`는 처리기 모듈을 처음 불러올 때 `operations_logs` 폴더를 만들고 기록 파일을 연다 [14].
`call_tool`은 처리기 모듈을 처음 부를 때 불러오고 `handlers` 패키지는 불러올 때 `image_handlers`를, `image_handlers`는 `operation_logging`을 불러온다 [15].
이 단계에서 난 예외는 처리하지 않아 처리기 모듈을 불러오지 못하고 `call_tool`이 `ERROR: Tool execution failed: …`를 돌려준다 [15][16].
그래서 이 폴더나 파일을 만들지 못하면 어느 도구를 불러도 같은 오류 글로 끝난다 [15][16].
Python은 불러오기에 실패한 모듈을 저장해 두지 않으므로 같은 실패는 호출마다 되풀이된다.
`operations_logs` 자리에 같은 이름의 파일을 두고 stdio 서버에 `list_prepared_images`·`kape_parse_artifact`를 부르자 두 호출 모두 `FileExistsError`를 담은 오류 글로 끝났고 시험용 KAPE는 실행되지 않았다 [17].
`main.py`는 시작할 때 `stderr.log`와 `mcp_server_<시각>.log`를 열고 `remote_server.py`는 불러올 때 `remote_server.log`를 연다 [11][18][12].
이 단계에서 난 예외도 처리하지 않아 파일을 열지 못하면 서버가 시작되지 않는다 [11][18][12].

### L03.05 실행 전 중단

**구현.** 이 방식은 `kape_parse_artifact`가 KAPE를 실행하기 전에 쓰는 KAPE 기록 항목에 적용된다 [2].
`execute_kape_parsing`은 KAPE를 실행하기 전에 `log_kape_operation`을 부르고 예외가 나면 KAPE를 실행하지 않고 `ERROR: KAPE execution failed: …` 글을 돌려준다 [2].
이 실패는 응답에만 실리고 로거에는 그 앞에 쓴 `Executing KAPE command` 줄만 남는다 [2].
`kape_operations.log` 자리에 폴더를 두고 `kape_parse_artifact`를 부르자 오류 글이 돌아왔고 시험용 KAPE는 실행되지 않았다 [4].

```python
def log_kape_operation(operation_type, command, return_code, output, error, kape_logs_dir):
    """Log KAPE operations to audit log for forensic defensibility"""
    from datetime import datetime
    import hashlib
    
    log_file = Path(kape_logs_dir) / "kape_operations.log"
    log_file.parent.mkdir(parents=True, exist_ok=True)
    
    timestamp = datetime.now().strftime('%Y-%m-%d %H:%M:%S')
    operation_hash = hashlib.sha256(f"{timestamp}{command}".encode()).hexdigest()[:16]
    
    log_entry = f"""
{'='*80}
OPERATION ID: {operation_hash}
TIMESTAMP: {timestamp}
TYPE: {operation_type}
COMMAND: {command}
RETURN CODE: {return_code}
{'='*80}
OUTPUT:
{output}
{'='*80}
ERRORS:
{error}
{'='*80}
"""
    
    with open(log_file, 'a', encoding='utf-8') as f:
        f.write(log_entry)
```
