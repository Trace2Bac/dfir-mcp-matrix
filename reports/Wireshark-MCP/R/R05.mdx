# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 이 방식은 탐지 도구, `wireshark_extract_credentials`, BLE 분석, `wireshark_get_file_info`, 파일 검사 오류에 적용된다 [1][2][3][4][5].
탐지 도구, `wireshark_extract_credentials`, BLE 분석은 결과의 `scope.pcap_file`에 모델이 준 캡처 파일 경로를 싣는다 [1][2][3].
`wireshark_get_file_info`는 `capinfos`가 적은 `File name:` 줄로 읽은 파일의 경로를 싣는다 [4].
파일을 찾지 못한 오류는 `message`에 받은 경로를 적는다 [5].

다른 도구의 결과에는 캡처 파일 경로가 없다.
`wireshark_aggregate`는 필터와 묶음 조건을 싣지만 파일 경로는 싣지 않는다 [6].
패킷 목록·필드 추출·통계 도구, BLE 분석을 뺀 프로토콜 분석기, 이상 탐지 도구의 결과는 `tshark` 출력이나 서버 문장만 싣는다 [7][8].

참조 지식을 싣는 도구는 원문 위치를 싣지 않는다.
`wireshark_geoip_enrich`는 나라·도시·AS 값만 싣고 조회한 GeoLite2 데이터베이스의 경로나 버전을 싣지 않는다 [9].
`wireshark_extract_fingerprints`는 사용자 목록과 맞은 JA3에 목록의 `label`·`category`만 붙이고 어느 목록 파일에서 왔는지 싣지 않는다 [10].
`wireshark_yara_scan`은 일치한 규칙 이름과 규칙의 `meta` 설명·등급·분류를 싣고 규칙이 함께 들어 있는 규칙인지 사용자 규칙인지 싣지 않는다 [11].
`wireshark_yara_scan`에 `dest_dir`를 주면 그 폴더에 이미 있던 파일도 검사해 이번에 내보낸 객체와 구별 없이 파일 이름만 싣는다 [11][12].
BLE 분석이 서버 코드의 표로 붙이는 연산 이름과 UUID 이름은 원래 코드 값과 다른 필드에 실리지만 그 필드가 증거 값이 아니라고 밝히는 문구는 없다 [13].

### R05.03 레코드 키·번호

**구현.** 이 방식은 패킷 목록, 근거 항목, BLE 결과에 적용된다 [7][14][3].
`wireshark_get_packet_list`의 기본 열 첫째는 캡처 파일 안 패킷 번호 `frame.number`다 [7].
근거 항목 `FindingEvidence`는 패킷 번호 `frame`과 TCP 스트림 번호 `stream`을 싣는다 [14].
`wireshark_extract_credentials`는 근거마다 그 자격 증명이 실린 패킷 번호와 스트림 번호를 싣는다 [2].
`wireshark_detect_port_scan`과 `wireshark_detect_dns_tunnel`은 근거 항목마다 표본 패킷 번호 하나를 싣는다 [1].
BLE 분석은 장치·스캐너마다 첫 패킷과 마지막 패킷 번호를, ATT·SMP 연산과 연결 사건마다 그 패킷 번호를 싣는다 [3].
`wireshark_get_packet_details`·`wireshark_get_packet_bytes`는 이 번호로 패킷 하나를 다시 읽는다 [15].

**한계.** 근거 항목의 패킷 번호는 표본 하나다 [1].
포트 스캔 근거는 출발지마다 SYN 패킷 번호를 5개까지 모으지만 그 가운데 첫 번호만 `frame`에 싣는다 [1].
DNS 터널의 긴 질의와 TXT 질의 근거는 맞은 질의 수를 적고 첫 질의의 패킷 번호만 싣는다 [1].
`wireshark_detect_dos_attack`의 근거, DNS 터널의 하위 도메인 수 근거, Telnet 근거에는 패킷 번호가 없다 [1][2].
`wireshark_aggregate`의 묶음, 이상 탐지 도구의 결과, `frame.number`를 고르지 않은 프로토콜 분석기의 행에는 패킷 번호가 없다 [6][8][16].
`custom_columns`를 준 패킷 목록에는 고른 열만 실린다 [7].

### R05.04 바이트·섹터·행 오프셋

**구현.** 이 방식은 `wireshark_get_packet_bytes`에 적용된다 [15].
이 도구는 `tshark -x`로 패킷 번호 하나의 16진 덤프를 돌려주고 줄마다 그 패킷 안의 바이트 오프셋을 적는다 [15][17].
오프셋은 캡처 파일 안의 위치가 아니라 패킷 데이터의 처음부터 센 값이다 [17].
다른 도구는 바이트 오프셋을 싣지 않는다.
