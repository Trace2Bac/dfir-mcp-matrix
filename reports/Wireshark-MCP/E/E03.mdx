# E03 원본 변경 방지

### E03.01 실행 환경의 읽기 전용 강제

**구현.** 이 방식은 저장소 문서 `docs/deployment-scenarios.md`가 안내하는 컨테이너 실행에 적용된다 [1].
README의 문서 표는 이 문서를 배포 시나리오 안내로 가리킨다 [2].
안내 명령은 공식 이미지를 실행하면서 호스트의 캡처 폴더를 컨테이너의 `/captures`에 읽기 전용(`:ro`)으로, 결과 폴더를 `/results`에 쓰기 가능하게 붙이고 `WIRESHARK_MCP_ALLOWED_DIRS`를 `/captures,/results`로 둔다 [1].
이미지는 일반 사용자 `wireshark-mcp`로 서버를 실행하고 기본 명령은 파일을 쓰는 도구를 뺀 `analysis` 프로필이다 [3].
이 구성으로 실행한 컨테이너에서 `full` 프로필로 서버를 만들고 쓰기 도구의 출력 경로를 `/captures` 안의 원본 캡처 파일로 주자 `editcap`과 `tshark`가 읽기 전용 파일 시스템이라 파일을 만들 수 없다는 오류로 끝났다 [4].
`wireshark_export_objects`의 `dest_dir`를 `/captures`로 주자 `/captures`에 새 파일이 생기지 않았다 [4].
`wireshark_yara_scan`의 임시 폴더는 `/captures`에 만들지 못해 다음 허용 폴더인 `/results`에 만들어졌다 [4][5].
실행 뒤 원본 캡처 파일의 SHA-256은 실행 전과 같았다 [4].
같은 구성의 `analysis` 프로필에서 `wireshark_set_protocol_prefs`의 해석 설정으로 `/captures` 안의 캡처 파일을 출력 파일로 주자 호출은 성공했고 그 파일의 크기와 SHA-256은 바뀌지 않았다 [6].

이 장치가 적용되지 않는 실행 방식도 있다.
`Dockerfile` 자체는 읽기 전용 볼륨을 정하지 않고 읽기 전용 연결은 안내 명령의 `docker run` 인자에만 있다 [1][3].
README가 안내하는 클라이언트 플러그인 설치와 `pip install` 뒤 `wireshark-mcp install`로 등록하는 실행은 호스트에서 서버를 실행하고 캡처 폴더를 읽기 전용으로 붙이는 장치가 없다 [2].

**한계.** `wireshark_export_objects`가 `/captures`에 파일을 만들지 못했을 때 응답은 성공(`success: true`)이었고 실패 문구는 `stderr` 필드에만 있었다 [4].

### E03.03 외부 도구·플랫폼에 위임

**구현.** 이 방식은 캡처 파일을 읽는 모든 도구에 적용된다 [7].
서버 코드는 캡처 파일을 직접 열지 않고 경로를 검사한 뒤 `tshark`, `capinfos`, `editcap`, `mergecap`에 명령 인자로 넘긴다 [7][8].
원본을 지키는 것은 서버 개요의 버전 기준대로 설치된 이 도구들이 입력 파일을 읽기 모드로 연다는 동작이다.
Wireshark 4.0.17의 파일 읽기 라이브러리 wiretap은 입력 캡처 파일을 `O_RDONLY`로 열고 `tshark`, `capinfos`, `editcap`, `mergecap`은 이 라이브러리로 입력을 연다 [9].
`capinfos`는 해시를 계산할 때 파일을 한 번 더 `rb`로 연다 [10].
`text2pcap`은 입력 글 파일을 `rb`로 연다 [11].
Wireshark 4.6.7의 wiretap도 입력을 `O_RDONLY`로 연다 [12].

파일을 쓰는 도구 11개는 Wireshark 실행 파일로 출력 파일을 만든다 [13].
`WIRESHARK_MCP_ALLOWED_DIRS`가 없으면 이 도구들은 쓰기를 거부한다 [14].
설정이 있으면 출력 경로가 허용 폴더 안인지만 확인하고 출력 경로가 입력이나 다른 원본 캡처 파일과 같은지는 확인하지 않는다 [14].
서버는 읽을 수 있는 폴더와 쓸 수 있는 폴더를 나누지 않고 같은 허용 폴더 목록으로 둘 다 검사한다 [14][15].
`SECURITY.md`의 설정 예는 캡처 폴더와 결과 폴더를 따로 적지만 서버 코드는 두 폴더를 구별하지 않는다 [16].
같은 저장소의 `skills/tshark-cli-analysis`는 클라이언트 모델이 MCP를 거치지 않고 `tshark`를 직접 실행하게 하는 skill이다 [17].
이 skill의 실행 스크립트는 `-w`·`--export-objects` 같은 파일 쓰기 인자를 거부하지만 서버는 이 스크립트를 실행하지 않는다 [17].

**한계.** 원본 캡처 파일이 허용 폴더 안에 있으면 쓰기 도구로 원본을 덮어쓸 수 있다 [14].
외부 도구는 출력 파일을 `wb`로 열어 기존 내용을 지우고 새로 쓴다 [18].
허용 폴더 안의 원본 캡처 파일을 입력과 출력으로 함께 주자 `wireshark_editcap_trim`, `wireshark_editcap_time_shift`, `wireshark_editcap_deduplicate`, `wireshark_extract_frames`, `wireshark_filter_save`, `wireshark_merge_pcaps`가 모두 성공 응답을 돌려주었다 [19].
여섯 경우 모두 원본의 내용과 크기가 바뀌었다 [19].
`wireshark_capture`도 출력 경로가 허용 폴더 안인지만 검사하고 Wireshark 4.0.17 `dumpcap`은 링 버퍼를 쓰지 않는 캡처에서 출력 파일을 `O_TRUNC`로 연다 [20].
이 도구의 출력 경로로 원본 캡처 파일을 준 경우는 실행해 확인하지 않았다.
`wireshark_export_objects`의 `dest_dir`를 원본 캡처 파일이 있는 폴더로 주자 그 폴더에 내보낸 파일이 생겼다 [19].
원본 폴더에 같은 이름의 파일이 있으면 `tshark` 4.0.17은 번호를 붙인 다른 이름으로 써서 그 파일을 덮어쓰지 않는다 [21].
번호를 붙인 이름을 기본 한도 1,000개까지 시도해도 모두 있으면 마지막으로 시도한 이름의 기존 파일을 지우고 쓴다 [21][22].
`wireshark_yara_scan`은 허용 폴더 가운데 처음으로 쓸 수 있는 곳에 임시 폴더를 만들므로 첫 허용 폴더가 원본이 있는 폴더이면 원본 옆에 임시 폴더가 생겼다가 지워진다 [5][23].
`wireshark_set_protocol_prefs`는 받은 해석 설정 문자열을 검사하지 않고 `tshark -o`로 넘긴다 [24].
`tshark`에는 파일 경로를 값으로 받아 그 파일을 쓰기 모드로 여는 해석 설정이 있어 이 도구의 해석 설정으로 출력 파일 경로를 줄 수 있다 [25].
이 경로는 출력 경로 검사를 거치지 않고 파일 쓰기 도구를 뺀 `analysis` 프로필에도 있다 [24][26].
허용 폴더 안의 다른 캡처 파일을 이 출력 파일로 준 실행에서 호출은 성공했고 그 캡처 파일은 `tshark`가 쓴 78바이트 기록으로 바뀌었다 [27].
입력 캡처 파일 자신을 출력 파일로 준 실행에서는 호출이 오류로 끝났고 입력 파일도 같은 기록으로 바뀌었다 [27].
