# R07 증거 내용과 지시 구분

### 미구현

**판단.** 모델이 받는 `Execute` 응답은 `CallToolResult`의 글 블록 두 개다 [1][2][3][4].
첫 블록은 스크립트가 `log`·`error`·`table`로 쓴 줄을 이은 `output.ToString()` 한 덩어리이고 `exit`로 끝난 응답과 실패한 응답도 같은 모양이다 [1][2][3].
응답에는 `StructuredContent`가 없고 증거에서 온 값을 서버 문구와 다른 필드에 담지 않으므로 R07.01에 해당하지 않는다 [1].
증거에서 온 값은 스크립트가 고른 모양으로 이 글 안에 들어가고 서버는 그 값을 감싸거나 따로 표시하지 않는다 [1].
서버가 쓰는 문구도 같은 글에 섞인다.
`error`는 줄 앞에 `Error: `를 붙이고 `auditFinding`·`auditReviewRec`은 서버가 정한 형식의 줄을 같은 출력에 더한다 [1][5].
스크립트가 실패하면 서버는 그때까지의 출력 뒤에 JavaScript 오류 문구와 API 착각 안내를 이어 붙인다 [2].
서버 문구 가운데 따로 떨어진 것은 응답 끝의 `[audit]` 블록 하나이고 이 블록은 사건 ID와 실행 ID만 담는다 [4].

SDK 객체는 결과 `Result`와 요약 `Message`를 다른 속성에 담는다 [6].
이 구분은 스크립트 안에서만 있고 모델에게는 스크립트가 출력한 글로만 간다 [1].
`Message`와 요약 목록 문자열에도 증거에서 온 값이 서버 문장 안에 들어간다 [6][7].
`TriageHostAsync`의 `TopFindings`는 shell 기록의 명령과 지속성 항목의 내용을 서버가 붙인 머리표와 한 문자열로 잇는다 [7].

도구 설명과 MCP 리소스에는 증거 속 지시를 따르지 말라는 문구가 없다 [8].

public class WorkflowResult<T>
{
    public bool IsSuccess { get; }
    public T? Result { get; }
    public string? Message { get; }

    private WorkflowResult(bool isSuccess, T? result, string? message)
    {
        this.IsSuccess = isSuccess;
        this.Result = result;
        this.Message = message;
    }

    /// <summary>A successful result carrying <paramref name="result"/> and an optional summary message.</summary>
    public static WorkflowResult<T> Success(T result, string? message = null) => new(true, result, message);

    /// <summary>A failed result carrying an explanatory <paramref name="message"/> and no value.</summary>
    public static WorkflowResult<T> Failure(string message) => new(false, default, message);
}
