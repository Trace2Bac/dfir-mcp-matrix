# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 이 절은 SDK 메서드가 Execute 스크립트에 돌려주는 객체를 결과로 본다.
그 객체가 응답 글에 실리는지는 호출자 코드가 정한다(R01.10).
`Execute`는 스크립트 출력 문자열을 자르지 않고 응답에 싣는다 [1].
서버는 응답 길이와 출력 줄 수에 상한을 두지 않는다.
toolkit 메서드도 대부분 외부 도구 출력 전체를 돌려준다.
`GrepLinesAsync`는 `maxMatches`를 주지 않으면 일치한 줄을 모두 돌려준다 [2].

항목 상한은 workflow와 이상 탐지 엔진에 있다.
`AnalyzeWebServerLogsAsync`는 일치한 줄을 20,000줄까지 읽고 상세 항목 `Findings`를 `maxFindings`(기본 100)개로 자른다 [3].
`ListDeletedFilesAsync`는 삭제 파일을 크기순으로 정렬해 `maxFiles`(기본 2000)개까지 싣는다 [4].
`AnalyzeAuthLogAsync`는 일치한 줄을 50,000줄까지 읽고 사건 표본 `Events`를 200개로 자른다 [5].
`DetectTimelinePivotsAsync`는 hayabusa 경보를 분마다 하나로 묶은 뒤 `maxPivots`(기본 20)개까지 싣는다 [6].
`AnalyzeBrowserActivityAsync`는 Chromium·Firefox 이력을 DB마다 마지막 방문 시각이 늦은 차례로 5,000행까지, Chromium 다운로드를 DB마다 시작 시각이 늦은 차례로 2,000행까지만 SQL로 읽는다 [7].
같은 메서드가 `WebCacheV01.dat`와 Hindsight에서 읽은 항목에는 건수 상한이 없다 [8].
이력과 다운로드의 두 상한은 SQL 문에 고정된 값이라 인자로 바꿀 수 없다 [7].
`BrowserActivityReport`와 `Message`에는 읽기가 상한에 닿았는지 알리는 값이 없다 [9].
`AnomalyDetectionToolkit`의 `TriageTimeline`은 순위 목록을 `budget`(기본 200)개로 자른다 [10].
그 전에 탐지기마다 `budget`을 탐지기 수로 나눈 올림값 `quota`만큼만 묶음을 남긴다 [11].

SDK가 돌려준 객체는 `Session` 저장소에 넣어 다음 `Execute` 호출에서 다시 쓸 수 있다 [12].
이 저장소는 스크립트가 넣은 객체만 보관하고 workflow가 잘라 낸 항목은 담지 않아 R02.04·R02.08에는 연결하지 않는다 [12].

**한계.** `maxFindings`·`maxFiles`·`maxPivots`·`budget`은 호출 인자이고 최댓값이 없어 스크립트가 값을 올리면 상한이 커진다 [3][4][6][10].

### R02.02 전체·반환 건수 표시

**구현.** `AnalyzeWebServerLogsAsync`는 일치한 줄 가운데 분류한 줄 수 `SuspiciousLineCount`와 잘린 표본 `Findings`를 따로 싣는다 [13].
`DetectTimelinePivotsAsync`는 받은 경보 수 `AlertsConsidered`와 잘린 `Pivots`를 함께 싣는다 [14].
이상 탐지의 `TriageReport`는 탐지기에 넣은 사건 수 `TotalEvents`, 후보 묶음 수 `Candidates`, `budget`으로 자른 순위 목록 `Shortlist`를 함께 싣는다 [15].
`TotalEvents`는 시각이 없는 사건과 `highSignalOnly`로 거른 사건을 뺀 수이고 workflow 보고서의 `TotalEvents`와 `AnalyzeUsnJournalAsync`의 `RecordsScanned`도 같은 수다 [15][16][17].
`RunIdsAsync`는 Suricata 경보 전체 수 `AlertCount`와 200건으로 자른 `Alerts`를 함께 싣는다 [18].
`Candidates`는 탐지기마다 `quota`개씩 고른 묶음을 같은 사건 종류·60초 칸끼리 합친 뒤의 수다 [11].
그래서 `Candidates`는 탐지기 수와 `quota`의 곱을 넘지 않고 탐지기가 표시한 후보 전체의 수가 아니다 [11].

**한계.** `ListDeletedFilesAsync` 보고서의 `Count`는 상한으로 자른 뒤의 항목 수다 [4].
자르기 전 삭제 항목 수는 `Message` 문장에만 들어간다 [4].
`AnalyzeAuthLogAsync`는 `Events`를 200개로 자르면서 파싱한 전체 사건 수를 보고서 필드에 싣지 않는다 [5][19].
`RunIdsAsync`는 서명별 집계 `BySignature`를 25개로 자른 뒤 그 길이를 `Message`에 서명 수로 적는다 [18].
그래서 서명이 25개를 넘으면 문구의 서명 수는 실제 서명 수보다 작다 [18].
`AnalyzeWebServerLogsAsync`의 `SuspiciousLineCount`는 20,000줄 상한 안에서 센 값이라 상한에 걸리면 전체 일치 수가 아니다 [3][13].
이 경우의 표시는 R02.07에서 본다.

`TriageReport`의 `Candidates` 설명은 이 값을 탐지기가 표시한 서로 다른 사건 수라고 적는다 [15].
코드는 `quota`에 걸려 버린 묶음을 빼고 센 값을 넣으므로 `Shortlist`와 `Candidates`를 견줘도 탐지기 단계에서 잘린 후보의 양을 알 수 없다 [11].

### R02.06 값 단위 잘림

**구현.** Linux·패킷 workflow의 `Truncate`는 문자열을 정한 길이에서 자르고 끝에 `…`를 붙인다 [20].

### R02.07 건수 없는 잘림 표시

**구현.** `AnalyzeWebServerLogsAsync`는 일치한 줄이 20,000줄 상한에 닿으면 `Truncated`를 참으로 둔다 [13].
`Message`는 이때 건수 뒤에 `+ (capped)`를 붙인다 [24].

```csharp
    /// <param name="maxMatches">When set, stop after this many matching lines (server-side <c>head</c>).</param>
    public async Task<string[]?> GrepLinesAsync(string path, IEnumerable<string> patterns, bool ignoreCase = true, int? maxMatches = null)
    {
        var pats = patterns.Where(p => !string.IsNullOrWhiteSpace(p)).ToArray();
        if (pats.Length == 0) return [];
        if (!auditEnvironment.FileExists(path)) return null;

        // Ship the pattern set as a base64 temp file so regex metacharacters never hit the shell; grep -f gives
        // OR semantics across the lines. rc==1 (no match) is normalised to success; rc>=2 (real error) propagates.
        var b64 = Convert.ToBase64String(System.Text.Encoding.UTF8.GetBytes(string.Join("\n", pats)));
        var tmp = "/tmp/camel_grep_" + Guid.NewGuid().ToString("N") + ".pat";
        var flags = ignoreCase ? "-E -i" : "-E";
        var cap = maxMatches is int n and > 0 ? $" | head -n {n}" : "";
        var script = $"echo {b64} | base64 -d > {tmp}; grep {flags} -f {tmp} {Q(path)}{cap}; rc=${{PIPESTATUS[0]}}; rm -f {tmp}; exit $((rc==1?0:rc))";
        var r = await auditEnvironment.ExecuteCommandAsync("bash", $"-c \"{script}\"", false);
        return r.IsCompleted ? r.Output.Split('\n', StringSplitOptions.RemoveEmptyEntries) : null;
    }
```

```csharp
    public TriageReport Triage(CanonicalEvent[] baseline, CanonicalEvent[] target, int budget, double episodeGapSeconds = 60.0)
    {
        long bucket = Math.Max(1, (long)(episodeGapSeconds * 1_000_000));
        int quota = Math.Max(1, (int)Math.Ceiling((double)budget / detectors.Length));

        // Per-detector quota: each detector collapses its findings into episodes (same token within a time bucket,
        // so one burst is one entry) and contributes only its top `quota`. This keeps the shortlist DIVERSE across
        // kinds of anomaly — a detector that emits astronomically-large bits (a volume burst) can't crowd out a
        // detector whose signal is smaller in magnitude but just as interesting (a rare event type).
        var picked = new List<(string Token, long Bucket, double Bits, Finding Peak, int[] Members)>();
        foreach (var d in detectors)
            picked.AddRange(d.Detect(baseline, target)
                .GroupBy(f => (f.Token, f.Ts / bucket))
                .Select(g =>
                {
                    var peak = g.MaxBy(f => f.Bits)!;
                    return (peak.Token, g.Key.Item2, peak.Bits, peak, g.Select(f => f.EventIndex).Distinct().ToArray());
                })
                .OrderByDescending(e => e.Bits)
                .Take(quota));
```
