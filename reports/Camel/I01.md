# I01 외부 연동 대상 관리

### I01.01 명시적 설정으로 활성화

**구현.** 이 방식은 SIFT 워크스테이션에 SSH로 붙어 명령을 실행하는 실행 환경 `SshAuditEnvironment`에 있다 [1].
서버는 시작할 때 설정 파일 `appsettings.json`의 `SIFT:Environment` 값이 `Ssh`이면 SSH 실행 환경을 쓰고 `Local`이면 서버 호스트에서 바로 명령을 실행한다 [1][2].
시작 인자 `--ssh`·`--local`은 이 값을 덮어쓴다 [1].
`--host`·`--user`·`--pass`·`--port` 가운데 하나라도 주면 `--local`이 없는 한 SSH로 바꾼다 [1].
SSH로 정해지면 서버는 시작할 때 한 번 접속해 보고 연결되지 않으면 종료한다 [1].
그 뒤에는 MCP 세션마다 첫 도구 호출에서 `AuditEnvironment.CreateFromConfig`가 SSH 연결을 하나씩 연다 [3].
저장소에 든 `appsettings.json`은 `SIFT:Environment`를 `Ssh`로 두고 호스트·사용자·비밀번호에는 `<sans-host>` 같은 자리표시 값만 둔다 [2].
README는 운영자가 이 파일에서 `Local`·`Ssh`를 고르고 SSH 접속 정보를 적으라고 안내한다 [2].

### I01.03 기본 활성화

**구현.** 이 방식은 툴킷이 빠진 분석 도구와 참조 자료를 실행 환경에 받아 까는 준비 단계에 있다 [4].
`Toolkit` 생성자는 마지막에 `InstallMissingTools`를 부른다 [4].
`WindowsAnalysis`·`Yara`·`Timeline`·`PacketAnalysis`·`DiskAnalysis` 툴킷이 이 함수를 고쳐 써서 내려받기와 패키지 설치를 한다 [5].
툴킷은 세션마다 처음 쓸 때 만들어진다 [6].
`Execute`는 스크립트 글에 툴킷 이름이 있으면 그 툴킷을 만들어 스크립트에 묶고 워크플로가 툴킷을 쓸 때도 툴킷을 만든다 [6].
준비 함수는 `test -e`로 확인할 경로가 있으면 아무것도 받지 않는다 [7].
경로가 없으면 `wget`을 실행하거나 `apt-get update` 뒤에 `apt-get install -y`를 실행한다 [7].
`PacketAnalysis` 툴킷은 `suricata`를 설치한 뒤 룰 파일이 비어 있으면 `suricata-update`도 실행한다 [5].
이 명령은 모두 `AuditEnvironment.ExecuteCommand`로 돌아 SSH 환경이면 워크스테이션에서, 로컬 환경이면 서버 호스트에서 연결이 생긴다 [7].
이 준비 단계를 끄는 설정이나 인자는 없다 [4][7].
받은 파일의 해시를 기대값과 대조하는 단계도 없다 [7].
문장 임베딩 모델을 HuggingFace에서 받는 `SentenceEmbedder`는 `Camel.Search`에 있고 서버 프로젝트가 이 프로젝트를 참조하지 않아 서버 실행 중에는 돌지 않는다 [8].

### I01.05 고정 목적지

**구현.** 이 방식은 준비 단계의 `wget` 내려받기 다섯 곳에 있다 [9].
`RECmd` zip, `DFIRBatch.reb`, `lolbas.json`, Yara-Rules 룰 묶음, hayabusa 3.9.0 release zip의 주소를 코드에 고정했다 [9].
준비 함수는 `protected`라 스크립트가 직접 부르지 못하고 주소를 바꾸는 설정·인자도 없다 [7][9].
`DFIRBatch.reb`와 Yara-Rules는 `master` 브랜치를 가리키고 `lolbas.json`은 버전 없는 주소라 목적지는 같아도 받는 내용은 받는 때에 따라 달라진다 [9].
툴킷의 `auditEnvironment` 필드와 그 `ExecuteCommandAsync` 메서드는 `public`이다 [10].
Jint가 이 필드를 스크립트에 드러낸다면 스크립트가 고정 주소를 거치지 않고 `wget` 같은 명령에 임의의 주소를 넣어 실행할 수 있지만 실행해 보지 않아 확인하지 못했다 [10].

### I01.06 설정으로 목적지 지정

**구현.** 이 방식은 SSH 실행 환경과 준비 단계의 `apt-get`·`suricata-update`에 있다 [1][5].
SSH 접속 대상은 `SIFT:Host`·`SIFT:Port`이고 설정 파일이나 시작 인자가 정한다 [1][3].
SSH인데 설정과 시작 인자 어디에도 포트가 없으면 22를 쓴다 [1].
MCP 도구 `SetCaseId`·`SetEvidence`·`VerifyEvidence`·`Execute`의 인자에는 접속 대상이 없다 [11].
`HostKeyReceived` 처리기는 호스트 키 지문을 로그에 남기기만 하고 키를 거부하는 분기가 없다 [12].
SSH.NET은 이 처리기가 `CanTrust`를 바꾸지 않으면 키를 받아들이는 것으로 알려져 있으나 라이브러리 코드는 이 저장소에 없어 확인하지 않았다 [12].
`apt-get`은 실행 환경의 패키지 저장소 설정을 따르고 `suricata-update`는 그 도구의 룰 출처 설정을 따르며 서버 코드는 주소를 넘기지 않는다 [5][7].

**예외.** SCP로 파일을 내려받는 연결을 만드는 `CreateScpClient`는 호스트·사용자·비밀번호만 넘기고 설정의 포트를 넘기지 않는다 [13].
SSH.NET의 세 인자 `ScpClient` 생성자는 기본 포트 22를 쓰는 것으로 알려져 있어 `SIFT:Port`를 22가 아닌 값으로 두면 이 경로만 같은 호스트의 22번 포트로 갈 것으로 보이나 실행해 보지 않아 확인하지 못했다 [13].
이 SCP 경로는 EZ 도구의 JSON 출력과 줄인 Plaso 타임라인을 내려받을 때 쓴다 [14].
SCP 연결에는 호스트 키 처리기를 달지 않는다 [13].

    {
        if (auditEnvironment.ExecuteCommand("test", $"-e {checkPath}", out _, false))
            return true; // already installed — nothing to do

        Info($"Installing missing tool {name} from {url} ...");
        string zip = $"/tmp/camel_ez_{name}.zip", extract = $"/tmp/camel_ez_{name}";

        }
        finally { auditEnvironment.ExecuteCommand("rm", $"-rf {zip} {extract}", out _, false); }

    {
        if (auditEnvironment.ExecuteCommand("test", $"-e {checkPath}", out _, false))
            return true; // already installed — nothing to do

        Info($"Installing missing apt package {package} ...");
        // Refresh package lists first — a fresh SIFT image often has a stale/empty apt cache, which makes
        // 'apt-get install' fail with "Unable to locate package".
        auditEnvironment.ExecuteCommand("apt-get", "update", out _, true);
        if (!auditEnvironment.ExecuteCommand("apt-get", $"install -y {package}", out string o, true))
        { Error($"Failed to install apt package {package}: {o}"); return false; }
        return auditEnvironment.ExecuteCommand("test", $"-e {checkPath}", out _, false);
