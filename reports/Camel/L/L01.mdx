# L01 기록 방식

### L01.08 도구별 기록 호출

**구현.** Camel의 MCP 도구 4개(`SetCaseId`·`SetEvidence`·`VerifyEvidence`·`Execute`)는 모두 도구 본문에서 기록 함수를 불러 호출 기록을 남긴다 [1].
도구는 `WithTools`로 등록하고 등록과 도구 실행 사이에 기록하는 공통 단계가 없다 [2].
기록 함수 `AuditEvent`·`AuditExecution`·`AuditCommand`는 서버를 시작할 때 `WithAuditLog`가 만든 별도 Serilog 기록기에 사건 종류 `EventType`을 붙여 쓴다 [3].
이 기록기는 `CaseId` 속성 값마다 `audit-<CaseId>.clef` 파일 하나를 두고 항목마다 JSON 한 줄(CLEF)을 쓴다 [3].
`camel create-case`가 만든 사건 설정으로 서버를 실행하면 이 파일은 사건 폴더의 `logs/` 아래에 생기고 사건 폴더 없이 실행하면 실행 파일 옆 `logs/`에 생긴다 [4].

도구마다 기록하는 지점은 이렇다.
`SetCaseId`는 바꾼 사건 ID를 `case` 항목으로 새 사건 파일에 쓴다 [1].
`SetEvidence`는 등록, 두 번째 등록 거부, 파일 없음 거부의 세 경로에서 각각 `evidence` 또는 `evidence-spoliation` 항목을 쓴다 [5].
`VerifyEvidence`는 해시 대조를 마친 뒤 모두 맞으면 `evidence-verification`, 어긋나면 `evidence-spoliation` 항목을 쓴다 [6].
`Execute`는 스크립트를 실행하기 전에 `started` 항목을 쓰고 끝난 방식에 따라 `completed`·`failed`·`cancelled`·`exited` 항목을 쓴다 [7].
스크립트는 `auditInfo`·`auditFinding`·`auditReviewRec` 같은 전역 함수를 불러 판단 항목을 더 쓸 수 있다 [8].

사건 ID를 정하기 전의 호출도 기록된다.
세션을 만들 때 사건 ID의 기본값은 세션 ID이고 stdio 연결의 세션 ID는 `default`라서 `SetCaseId` 전의 항목은 `audit-default.clef`에 쌓인다 [9].

클라이언트 쪽 기록도 함께 구성된다.
`create-case`가 사건 폴더에 쓰는 Claude Code 설정은 `Stop`·`SessionEnd` 훅에서 이 CLI의 `preserve-chatlog`를 실행해 대화 기록을 `logs/chatlog-*.jsonl`로 복사한다 [10].
이 대화 기록에는 모델이 보낸 도구 호출이 모두 들어가지만 Claude Code로 붙을 때만 남는다.

**예외.** `VerifyEvidence`는 등록된 증거가 없으면 기록 함수를 부르지 않고 오류를 돌려준다 [6].

기록 전에 난 예외를 대신 기록하는 공통 처리가 없다 [2].
네 도구는 첫 줄에서 `registry.GetOrCreate`로 세션 환경을 얻는다 [11].
동시 세션 상한에 걸리거나 환경을 만들다 실패해 이 호출이 예외를 내면 항목 없이 끝난다 [11].
`Execute`는 스크립트에 이름이 나온 toolkit 객체를 `started` 항목을 쓰기 전에 만든다 [12].
toolkit 생성자는 설정의 `Tools:<이름>` 절을 읽고 빠진 도구를 설치하므로 설정 절이 없어 생성자가 예외를 내면 `Execute` 호출은 `started` 항목 없이 끝난다 [12][13].
`SetEvidence`의 파일 확인과 `VerifyEvidence`의 해시 계산에서 예외가 나도 그 도구의 결과 항목은 남지 않는다 [5][6].

### L01.09 실행기 안 기록

**구현.** SDK의 toolkit·workflow가 SIFT 도구를 실행하는 명령은 실행 환경의 `ExecuteCommand`·`ExecuteCommandAsync`를 거친다 [14].
두 함수는 명령이 끝나면 성공·실패와 관계없이 `AuditCommand`로 `command` 항목을 하나 쓴다 [14].
항목의 사건 ID·실행 ID·toolkit·workflow 이름은 위쪽 호출이 문맥에 넣어 둔 값으로 붙는다 [3].
toolkit 공통 실행 함수 `ExecuteTool`·`ExecuteToolText`·`ExecuteToolAsync`·`ExecuteToolTextAsync`가 모두 이 두 함수를 부른다 [15].
toolkit 생성자가 실행하는 도구 설치 명령(`wget`·`apt-get`·`unzip`)과 임시 파일 정리 명령도 같은 함수를 거쳐 항목이 남는다 [13].
`VerifyEvidence`가 실행하는 해시 명령도 `ExecuteCommandAsync`를 거친다 [16].

**예외.** SSH 환경의 `FileExists`·`GetFileSize`는 `sshClient.RunCommand`로 `stat`을 직접 실행하고 기록하지 않는다 [17].
SDK의 `GrepLinesAsync`는 대상 파일을 이 `FileExists`로 확인하고 `SetEvidence`는 증거 파일마다 `FileExists`·`GetFileSize`를 부른다 [18].
SSH 환경에서 도구 출력 파일을 SCP로 내려받는 `GetFileAsLocal`도 항목을 남기지 않는다 [19].
명령이 취소되면 실행 함수가 `OperationCanceledException`을 다시 던져 `ExecuteCommandAsync`가 `AuditCommand` 줄에 닿지 않는다 [20][14].
이때 `Execute` 호출 자체는 `cancelled` 항목으로 남는다 [7].

    {
        CallerInformation here = this.Here();
        Stopwatch sw = new Stopwatch();
        sw.Start();
        ScpClient? c = this.CreateScpClient();
        if (c == null) return null;
        c.BufferSize = 16 * 16384;        
        try
        {
            FileInfo f = new FileInfo(local_path);
            c.Download(remote_path, f);
            sw.Stop();

        }

            return null;
        }
