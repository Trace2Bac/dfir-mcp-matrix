# L02 기록 구성

### L02.01 요청 원문 기록

**구현.** `Execute`가 받은 인자는 스크립트 `script` 하나이고 서버는 실행 전에 `started` 항목의 `Script`에 그 스크립트를 그대로 넣는다 [1].
도구 이름을 담는 필드는 따로 없고 사건 종류 `EventType`이 `execution`인 항목이 `Execute` 호출이다 [1].
SIFT 도구를 돌리는 일은 모두 이 스크립트 안의 SDK 메서드 호출에서 일어나므로 이 항목이 모델이 요청한 분석 단계의 원문이다.
실제 기록에서도 `started` 항목에 스크립트 전문이 들어 있다 [2].

다른 도구 3개는 받은 인자를 기록 문구의 속성으로 남긴다.
`SetCaseId`는 새 사건 ID와 이전 사건 ID를 넣는다 [3].
`SetEvidence`는 등록에 성공하면 증거 경로와 크기를 넣는다 [4].
`VerifyEvidence`는 인자를 받지 않는다 [5].

**예외.** `SetCaseId`는 받은 값 대신 앞뒤 공백을 지운 값을 넣고 빈 값이면 세션 ID로 바꾼 값을 넣는다 [3].
`SetEvidence`는 증거마다 받은 `HashType`·`HashValue`를 넣지 않는다 [4][6].
두 번째 등록 거부 항목에는 다시 등록하려던 증거 목록이 없고 파일 없음 거부 항목에는 없는 경로만 들어간다 [4].

### L02.03 실제 실행 명령 기록

**구현.** SDK 메서드가 실행 환경으로 넘긴 명령마다 `command` 항목이 남는다(L01.09) [7].
항목에는 실행 호스트 `Host`, 실행 파일 `Command`, 인자 문자열 `Arguments`, `sudo` 여부 `Sudo`, 종료 코드 `ExitCode`, 완료 여부 `Completed`, 소요 시간 `DurationMs`가 들어간다 [7].
`Command`와 `Arguments`는 실행 함수에 넘긴 두 문자열 그대로다 [7].
SSH 환경은 `command + " " + arguments`를 원격 셸에 넘기고 Unix 로컬 환경은 같은 문자열을 `/bin/bash -c`에 한 인자로 넘긴다 [8].
`sudo`로 돌리면 실행 함수가 `sudo`를 앞에 붙여 실행하고 항목에는 `Sudo`를 참으로 넣는다 [7].
그래서 두 필드를 공백 하나로 이으면 셸이 받은 명령 줄이 되고 인자 경계는 그 명령 줄의 따옴표가 정한다.

toolkit 생성자가 빠진 도구를 내려받는 `wget` 명령도 내려받을 URL을 인자에 담은 `command` 항목으로 남는다 [9].
항목에는 명령의 출력이 없어 내려받은 내용은 남지 않는다 [7].
그래서 외부 요청의 응답을 남기는 L02.09에는 연결하지 않는다.
서버 코드에는 언어 모델 API를 부르는 곳이 없어 L02.05는 볼 대상이 없다.

### L02.04 요청과 실행의 연결

**구현.** `Execute`는 호출마다 8자리 실행 ID를 만들어 `ExecutionId`로 문맥에 넣고 실행이 끝날 때까지 유지한다 [10].
그래서 `started` 항목의 스크립트 원문과 그 스크립트가 일으킨 `command` 항목이 같은 `ExecutionId`로 묶인다 [10][1][7].
toolkit 공통 실행 함수 `ExecuteToolText`·`ExecuteToolTextAsync`는 `Toolkit`·`Operation`을, workflow 메서드는 `AuditScope`로 `Workflow`·`WorkflowOperation`을 문맥에 넣는다 [11].
이 값이 있는 `command` 항목은 어느 SDK 메서드가 그 명령을 돌렸는지 보여 준다 [11].

**예외.** toolkit 공통 실행 함수 가운데 `ExecuteTool`·`ExecuteToolAsync`는 `Toolkit`·`Operation`을 넣지 않는다 [12].
메모리 분석 toolkit의 Volatility 메서드가 `ExecuteToolAsync`를 쓰므로 그 `command` 항목에는 SDK 메서드 이름이 없다 [12].
실제 기록에서도 `Promise.all`로 Volatility 메서드 4개를 함께 부른 실행의 `command` 항목에 `Toolkit`·`Operation`이 없다 [13].
이런 실행에서 같은 `ExecutionId` 아래의 명령이 스크립트의 어느 호출에서 나왔는지는 실행 파일과 인자로만 짐작한다 [13].
저장소 문서는 `command` 항목에 `Toolkit`·`Operation`이 담긴다고 설명한다 [14].

`VerifyEvidence`는 문맥에 `CaseId`만 넣으므로 그 해시 명령 항목에는 `ExecutionId`가 없다 [5].
이 명령 항목은 `evidence-verification` 항목과 시각으로만 이어진다 [5].

### L02.06 실행 시작·종료·결과 상태 기록

**구현.** `Execute` 한 번은 `started` 항목과 끝을 알리는 항목 하나로 남는다 [15].
끝 항목의 `Phase`는 `completed`·`failed`·`cancelled`·`exited` 가운데 하나이고 `Success`와 `DurationMs`가 함께 들어간다 [15][1].
스크립트 오류가 SDK에 없는 toolkit·workflow 이름에서 났으면 `hallucination` 항목을 따로 쓴다 [16].
명령마다 남는 `command` 항목은 `ExitCode`·`Completed`·`DurationMs`로 그 명령의 결과를 담는다 [7].
`SetEvidence`의 거부와 `VerifyEvidence`의 해시 불일치는 `evidence-spoliation` 항목으로, 성공은 `evidence`·`evidence-verification` 항목으로 남는다 [4][5].

**예외.** `failed` 항목에는 오류 문구가 없고 오류 문구는 응답에만 실린다 [16].
그래서 증거 경로를 건드리는 쓰기를 `FailIfEvidenceSpoliationRisk`가 거부해 스크립트가 끝난 경우와 다른 스크립트 오류가 기록에서 구별되지 않는다 [17][16].
`command` 항목에는 시작 시각을 따로 남기지 않고 끝난 시각 `@t`와 소요 시간만 있다 [7].

### L02.08 호출 ID·시각으로 항목 연결

**구현.** `Execute` 안에서 쓰는 항목은 모두 `ExecutionId`와 `CaseId`를 갖는다 [10].
`started`·끝 항목, `command` 항목, 스크립트가 쓴 `finding` 같은 판단 항목이 이 ID로 묶인다 [10].
`Execute` 응답 끝에는 `[audit] case=<CaseId> execution=<ExecutionId>` 한 줄이 붙어 클라이언트 대화 기록의 도구 결과와 호출 기록 항목을 같은 ID로 맞춰 볼 수 있다 [18].
모든 항목에는 기록 시각 `@t`가 들어간다 [2].

**예외.** `SetCaseId`·`SetEvidence`·`VerifyEvidence`는 호출 ID를 만들지 않아 그 항목에 `ExecutionId`가 없다 [3][4][5].
`VerifyEvidence`가 한 호출에서 낳는 해시 명령 항목과 결과 항목은 `CaseId`와 시각으로만 이어진다 [5].

    {
        // Concurrency limiting is enforced in ExecuteAsync (the primitive both this wrapper and any direct
        // caller funnel through), so it is intentionally not applied here to avoid acquiring twice.
        CommandResult? r;
        var sw = System.Diagnostics.Stopwatch.StartNew();

            if (this.IsUnix)
            {
                r = await this.ExecuteAsync("sudo", command + " " + arguments);
            }
            else throw new NotImplementedException("ExecuteCommandAsAdmin is not implemented for Windows environments.");
        }
        else
        {
            r = await this.ExecuteAsync(command, arguments);
        }

        // Record this command in the per-case audit trail. CaseId/ExecutionId/Toolkit/Operation/Workflow are
        // enriched ambiently from the log context, so this single chokepoint ties every tool execution to the
        // case and agent step that drove it — the row a judge traces a finding back to.
        AuditCommand(AuditHostName, command, arguments, admin, r.ExitCode, sw.ElapsedMilliseconds, r.IsCompleted);
