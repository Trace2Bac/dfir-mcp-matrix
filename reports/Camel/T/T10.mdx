# T10 도구 명세 구성

### T10.01 처리 함수에서 명세 생성

**구현.** 이 방식은 MCP 도구 `SetCaseId`·`SetEvidence`·`VerifyEvidence`·`Execute` 넷에 적용된다 [1][2].
도구 이름과 설명은 메서드에 붙인 `McpServerTool`·`Description` 특성에 있다 [1].
C# MCP SDK 1.4.0은 메서드의 `Description` 특성을 도구 설명으로, 메서드 인자에서 만든 schema를 입력 schema로 쓴다 [3].
모델이 넘기는 인자는 `SetCaseId`의 `caseId`, `SetEvidence`의 `EvidenceInfo` 배열 `evidence`, `Execute`의 `script`이고 `VerifyEvidence`는 인자가 없다 [1][2][4].
`RequestContext`와 진행 알림, 취소 토큰 인자는 SDK가 요청마다 넣는다고 코드 주석이 적는다 [2].
SDK는 `ReadOnly` 같은 annotation 값이 주어졌을 때만 annotation을 싣고 서버는 그 값을 주지 않는다 [1][3].
stdio와 HTTP 전송은 같은 도구 클래스와 리소스 클래스를 등록한다 [5].
서버는 지침(`instructions`), MCP 프롬프트, 목록 변경 알림을 두지 않는다 [5].

### T10.03 묶음 도구의 연산별 인자를 schema가 구분하지 않음

**구현.** 이 방식은 `Execute`에 적용된다 [2].
`Execute`의 입력 schema는 JavaScript 문자열 `script` 하나이고 스크립트가 부를 SDK 객체와 메서드, 반환 값의 모양은 schema에 없다 [2].
SDK 명세는 MCP 리소스 `camel://sdk/core`(`camel-sdk-core`)와 `camel://sdk/schema`(`camel-sdk-schema`)에 있다 [6].
`camel-sdk-core`는 실행 규칙과 객체별 메서드 서명을, `camel-sdk-schema`는 메서드가 돌려주는 모델 형식의 JSON schema를 적는다 [6].
`Execute`의 도구 설명은 스크립트를 쓰기 전에 두 리소스를 반드시 읽고 거기 적힌 메서드와 속성만 쓰라고 적는다 [2].
리소스 내용은 저장소 `docs/`의 Markdown 파일을 어셈블리에 넣어 둔 것을 그대로 돌려준다 [6][7].
이 문서를 SDK 코드에서 만들거나 SDK 코드와 대조하는 장치는 저장소에서 찾지 못했다 [7].
스크립트 엔진에는 `Session`, 이상 탐지 툴킷, 워크플로 객체가 늘 들어가고 툴킷 객체는 스크립트 글에 그 이름이 있을 때만 들어간다 [8].
절차 문서로서의 리소스 내용은 P02.01에서, 스크립트가 없는 메서드를 부를 때의 응답은 P02와 L02에서 본다.

**한계.** `camel-sdk-core`는 `Session` 저장소가 세션마다 있고 조사 사이에 공유되지 않는다고 적는다 [9].
`SetCaseId`는 같은 세션의 사건 ID만 바꾸고 `Execute`는 사건 ID와 관계없이 세션의 같은 저장소를 `Session`으로 넣는다 [10][8].
그래서 한 세션에서 사건을 바꾸면 앞 사건의 `Session` 값이 뒤 사건의 스크립트에 보이고 문서의 설명과 다르다 [9][10].
이 동작은 P04의 한계에도 적었다.

```csharp
    public string SetCaseId(string caseId, RequestContext<CallToolRequestParams> context)
    {
        var session = registry.GetOrCreate(SessionId(context.Server));
        var previous = session.CaseId;
        session.CaseId = string.IsNullOrWhiteSpace(caseId) ? session.SessionId : caseId.Trim();
        // Record the case association in the (new) case's audit file so the switch itself is auditable.
        using (PushAuditProperty("CaseId", session.CaseId))
            AuditEvent("case", "Case id set to {CaseId} (was {Previous}) for session {SessionId}",
                session.CaseId, previous, session.SessionId);
        return $"Case id set to '{session.CaseId}' for this session. Audit trail file: audit-{session.CaseId}.clef";
    }
```
