# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 로컬·SSH 실행 환경은 외부 명령의 종료 코드가 0이면 `Completed`, 아니면 `Error` 상태를 정한다 [1].
SSH 연결 오류·시간 초과 예외가 나도 `Error` 상태로 돌려준다 [1].
툴킷의 도구 실행 함수는 `Completed`가 아니면 서버 로그에 `Error`를 남기고 `null`을 돌려준다 [2].
작업 흐름은 툴킷이 `null`을 돌려주면 실패 결과 `WorkflowResult.Failure`와 실패 문구를 돌려준다 [3].
`GrepLinesAsync`는 `grep`의 종료 코드 1(일치 없음)을 성공으로, 2 이상을 실패로 나눈다 [4].

**예외.** `DiskAnalysisToolkit.FindFilesAsync`는 `find`의 종료 코드를 보지 않고 표준 출력을 파싱한다 [5].
코드 주석은 일부 항목을 읽지 못해도 찾은 결과를 살리려는 것이라고 적지만 결과에는 일부만 찾았다는 표시가 없다 [5].

### T08.02 시간 제한·종료 신호 처리

**구현.** 서버가 스크립트 실행에 거는 시간 제한은 Jint 엔진의 `PromiseTimeout` 24시간 하나다 [6].
저장소 문서는 엔진 기본값 10초가 긴 분석을 끊어 24시간으로 늘렸다고 적는다 [7].
서버는 스크립트가 실행되는 동안 20초마다 진행 알림을 보내 클라이언트의 대기 시간 제한을 넘지 않게 한다 [8].
클라이언트가 호출을 취소하면 `Execute`는 세션 실행 환경의 `CancelExecutions`를 불러 진행 중인 비동기 명령을 취소하고 호출 기록에 `cancelled` 단계를 남긴다 [9].
`CancelExecutions`는 그 실행 환경의 비동기 명령이 함께 쓰는 취소 토큰 소스를 새것으로 바꾼 뒤 이전 소스를 취소한다 [10].
그래서 같은 세션에서 겹쳐 실행 중인 다른 `Execute` 호출의 비동기 명령도 이전 토큰을 쓰고 있으면 함께 취소된다 [10].
stdio 연결처럼 세션 ID가 없는 연결은 모든 호출이 `default` 세션 하나를 쓴다 [11].
서버가 쓰는 `ModelContextProtocol` 1.4.0은 같은 세션에서 받은 메시지마다 처리를 따로 시작하고 앞 요청이 끝나기를 기다리지 않는다 [12].
같은 세션의 요청이 실제로 겹쳤을 때의 간섭은 실행해 보지 않았다.
로컬 환경은 취소될 때 자식 프로세스 트리를 끝내고 SSH 환경은 명령 채널을 닫는다 [13].
YARA를 쓰는 작업 흐름은 `--timeout=120`을 넘겨 `yara`가 파일 하나에 120초를 넘기면 그 파일을 건너뛰게 한다 [14].

**예외.** `PromiseTimeout`이 지나 스크립트가 실패하면 `Execute`의 일반 예외 처리는 `CancelExecutions`를 부르지 않아 진행 중인 명령을 끊는 경로가 없다 [15].
실행 환경의 동기 함수 `Execute`는 취소 토큰을 받지 않아 취소돼도 명령이 끝날 때까지 기다린다 [16].
Jint 4.9.2의 `ExecuteAsync`는 promise가 끝나기를 기다리는 동안에만 취소 토큰을 확인한다 [17].
서버는 엔진에 실행 중단 제약을 걸지 않으므로 스크립트의 동기 구간은 다음 `await`에 이를 때까지 취소로 끊기지 않는다 [6][17].
SSH 명령 채널을 닫았을 때 원격 프로세스가 실제로 끝나는지는 확인하지 못했다 [13].
`yara`가 시간 제한으로 건너뛴 파일을 결과에서 가리는 코드는 찾지 못했다 [14].
저장소 문서는 실행마다 시간 제한을 둔다고 적지만 코드의 제한은 위의 24시간 하나다 [18].

### T08.04 입력별 부분 완료 집계

**구현.** `MemoryAnalysisWorkflow.FindMalwareAsync`는 하위 분석 7개를 동시에 실행하고 결과를 나눠 다룬다 [24].
프로세스 목록·조상 관계·코드 주입 분석 가운데 하나라도 실패하면 전체를 실패로 돌려준다 [24].
네트워크·루트킷 분석이 실패하면 빈 보고서로 바꾸고 결과 문구에 건너뛴 사실을 붙인다 [24][25].
결과 문구는 의심 프로세스 수, 덤프한 실행 파일 수, YARA 일치 수를 센다 [25].

**예외.** 같은 작업 흐름에서 명령 행·SID 조회가 실패하면 빈 목록으로 바꾸고 결과 문구에 적지 않는다 [24].
프로세스 실행 파일 덤프와 덤프 YARA 검사가 실패해도 빈 목록으로 바꾸고 VAD YARA 검사가 실패하면 그 항목을 비워 요청하지 않은 경우와 구별되지 않는다 [26].

### T08.08 라이브러리 예외를 실패로 구별

**구현.** `Execute`는 엔진 실행 중 난 예외를 처리해 `IsError = true`인 응답으로 돌려주고 호출 기록에 `failed` 단계를 남긴다 [27].
스크립트의 JavaScript 오류와 거부된 promise는 `JavaScript error:`로, 그 밖의 예외는 `Error executing script:`로 앞에 붙여 구별한다 [27].
없는 툴킷·작업 흐름이나 메서드를 부른 오류는 호출 기록에 `hallucination` 사건으로도 남긴다 [27].
툴킷이 도구 출력을 JSON으로 바꾸다 난 예외는 툴킷에서 처리하지 않으므로 `Execute`의 이 처리로 올라간다 [28].
스크립트가 `exit`를 부르면 그 예외는 오류가 아닌 일반 출력으로 돌려준다 [29].

**예외.** `WindowsAnalysisToolkit.SqliteQueryAsync`는 모든 예외를 처리해 빈 배열을 돌려주므로 JSON 변환 실패가 결과 없음과 구별되지 않는다 [21].

```csharp
    // it (via CancelExecutions) aborts all in-flight and pending async commands — e.g. on client disconnect.
    private CancellationTokenSource executeCts = new();

    /// <summary>The token all async Execute methods on this environment observe. Trip it via <see cref="CancelExecutions"/>.</summary>
    public CancellationToken ExecuteCt => executeCts.Token;

    /// <summary>
    /// Cancels every in-flight and pending async command on this environment, then swaps in a fresh source
    /// so subsequent calls execute normally. The old source is intentionally not disposed: a caller may have
    /// read it but not yet built its linked token, and disposing it would make that read throw
    /// <see cref="ObjectDisposedException"/>; a plain (timer-less) source holds no unmanaged handle, so GC
    /// reclaims it safely once the cancellation callbacks have run.
    /// </summary>
    public void CancelExecutions()
    {
        var old = Interlocked.Exchange(ref executeCts, new CancellationTokenSource());
        old.Cancel();
    }
```
