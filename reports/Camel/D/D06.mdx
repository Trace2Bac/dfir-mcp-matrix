# D06 산출물 식별·재생성 처리

### D06.02 입력·작업별 고유 이름

**구현.** 유일한 이름을 쓰는 방식은 `ListDeletedFilesAsync`의 내부 bodyfile과 `RunIdsAsync`의 기본 출력 폴더에만 있다 [1][2].
`ListDeletedFilesAsync`는 삭제 항목을 찾으려고 `/tmp/camel_deleted_<GUID>.body`에 bodyfile을 만들고 그 파일을 지우지 않는다 [1].
이름에 호출마다 새로 만든 GUID가 들어가므로 다른 실행의 bodyfile과 겹치지 않는다 [1].
결과에는 이 경로를 싣지 않는다 [1].
`RunIdsAsync`는 `outDir`가 없으면 `/tmp/camel_suricata_<GUID>` 폴더를 만들어 Suricata 로그를 쓰고 그 폴더를 지우지 않는다 [2][3].
이 두 경로 밖의 파생물 이름은 스크립트가 정하고 서버는 앞 파생물과 구분하지 않는다.
툴킷 공통 함수가 만드는 `/tmp/camel_ez_<GUID>` 같은 임시 폴더는 호출 안에서 지우므로 이 상세에 넣지 않는다 [4].

이 두 경로 밖의 파생물은 같은 작업을 다시 하면 앞 파생물이 따로 남지 않거나 이번 결과와 섞인다.
표준 출력을 셸 `>`로 인자 경로의 파일에 쓰는 메서드는 같은 경로로 다시 부르면 앞 파일을 알리지 않고 덮어쓴다 [5].
`Log2TimelineAsync`는 `storageFile`이 이미 있으면 그 파일에 이어 쓰고 그 뒤 `PsortAsync`는 두 실행이 넣은 사건을 가리지 않고 함께 내보낸다 [6].
`PsortTagAsync`는 저장 파일 안의 태그를 그 자리에서 고친다 [7].
`RunToDirAsync`는 도구를 실행한 뒤 `outputDir`의 파일을 모두 나열해 돌려주므로 같은 폴더를 다시 쓰면 앞 실행의 파일이 이번 결과 목록에 섞인다 [8].
`ForemostAsync`·`BulkExtractorAsync`의 설명은 `outputDir`이 미리 없어야 한다고 적지만 서버 코드는 폴더가 있는지 보지 않고 외부 도구에 맡긴다 [9].
foremost와 bulk_extractor가 이미 있는 폴더를 거부하는지는 실행해 보지 않아 확인하지 못했다.

`GenerateFilesystemTimelineAsync`의 기본 bodyfile 이름은 오프셋으로만 정해져 같은 오프셋으로 다시 부르면 다른 이미지·다른 사건의 실행이라도 같은 파일을 쓴다 [10].
fls 출력은 셸 `>`로 이 파일에 쓰이므로 앞 bodyfile을 알리지 않고 덮어쓴다 [11].
그러면 앞 실행이 돌려받은 `BodyfilePath`는 나중 실행이 쓴 내용을 가리킨다 [10].
메모리 타임라인 워크플로 `GenerateTimelineAsync`는 bodyfile 이름을 `volatility.body`로 고정한다 [12][13].
그래서 같은 폴더에 다른 이름의 타임라인을 다시 만들면 두 타임라인이 bodyfile 경로 하나를 함께 쓴다 [12].
이때 앞 bodyfile이 남는지는 Volatility 3이 같은 이름의 파일을 어떻게 다루는지에 달려 있고 확인하지 못했다 [12].
같은 타임라인 경로로 다시 부르면 `MactimeToFileAsync`가 셸 `>`로 앞 타임라인 파일을 덮어쓴다 [14].

    {
        using var _audit = AuditScope();
        using var op = Begin("Listing deleted files in {0} (offset {1})", image, offset?.ToString() ?? "none");

        var bodyfile = $"/tmp/camel_deleted_{Guid.NewGuid():N}.body";
        if (!await DiskAnalysis.FlsBodyfileAsync(image, bodyfile, offset))
            return WorkflowResult<DeletedFilesReport>.Failure(

            return WorkflowResult<DeletedFilesReport>.Failure($"Could not read the bodyfile '{bodyfile}'.");

            .OrderByDescending(e => e.Size).Take(maxFiles).ToArray();

    public async Task<WorkflowResult<FilesystemTimeline>> GenerateFilesystemTimelineAsync(
        string imageFile, int? offset = null, string timezone = "UTC", string? bodyfilePath = null)
    {
        bodyfilePath ??= $"/tmp/camel_bodyfile_{offset ?? 0}.txt";
        using var _audit = AuditScope();
        using var op = Begin("Generating filesystem timeline for {0} (offset {1})", imageFile, offset?.ToString() ?? "none");

        // Confirm a filesystem actually lives at the offset before walking it (avoids an empty/garbage timeline).
        var fs = await DiskAnalysis.FsStatAsync(imageFile, offset);
        if (fs is null || string.IsNullOrWhiteSpace(fs.FileSystemType))
            return WorkflowResult<FilesystemTimeline>.Failure(
                $"No valid filesystem found at sector offset {offset} of '{imageFile}'. " +
                $"Check the partition table (mmls) for a correct partition start sector.");

        // Walk the filesystem into a mactime bodyfile, then sort it into a timeline.
        if (!await DiskAnalysis.FlsBodyfileAsync(imageFile, bodyfilePath, offset))
            return WorkflowResult<FilesystemTimeline>.Failure(
                $"Failed to generate the fls bodyfile for '{imageFile}' (offset {offset}).");

        var entries = await DiskAnalysis.MactimeAsync(bodyfilePath, timezone);
        if (entries is null)
            return WorkflowResult<FilesystemTimeline>.Failure($"mactime failed to process bodyfile '{bodyfilePath}'.");

        op.Complete();
        return WorkflowResult<FilesystemTimeline>.Success(
            new FilesystemTimeline(bodyfilePath, entries),
            $"Generated {entries.Length} timeline entries for the {fs.FileSystemType} filesystem (offset {offset}).");
    }
