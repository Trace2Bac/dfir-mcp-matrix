# P01 분석 방법 적합성 확인

### P01.01 이름·확장자 판별

**구현.** 확장자로 처리 경로를 정하는 곳은 등록한 증거의 해시를 다시 계산하는 MCP 도구 `VerifyEvidence`다 [1].
해시가 주어진 증거의 경로가 `.e01`·`.ex01`로 끝나면 `ewfverify`로 이미지에 담긴 매체 내용의 해시를 계산하고 그 밖의 파일은 파일 전체를 `md5sum`·`sha1sum`·`sha256sum`으로 계산한다 [1][2].
코드 주석은 EWF 컨테이너 파일의 해시가 수집 때 적은 매체 해시와 같을 수 없어서 이렇게 나눈다고 적는다 [2].

**한계.** 이 판별은 경로 끝의 확장자만 본다 [2].
디스크 workflow `MountEwfImageAsync`·`VerifyImageAsync`는 같은 파일을 `ewfinfo`로 열어 EWF인지 정한다 [3].
그래서 `ewfinfo`가 읽는 EWF 이미지라도 이름이 `.e01`·`.ex01`로 끝나지 않으면 `VerifyEvidence`는 컨테이너 파일 전체의 해시를 수집 해시와 비교해 `MISMATCH`로 알린다 [1][2].

### P01.02 메타데이터 조회

**구현.** 형식과 대상 영역을 정하는 일은 `Execute` 스크립트가 부르는 디스크 workflow 안에서 외부 도구의 출력으로 한다 [3][4][5].
`MountEwfImageAsync`는 `ewfinfo`가 이미지 메타데이터를 읽지 못하면 마운트하지 않고 마운트한 뒤에는 `mmls`로 읽은 파티션 표를 돌려준다 [3].
`MountFileSystemAsync`는 모델이 준 시작 섹터에서 `fsstat`가 파일 시스템 종류를 읽지 못하면 실패로 돌려준다 [4].
`GenerateFilesystemTimelineAsync`와 `RecoverFilesAsync`도 같은 `fsstat` 검사를 먼저 한다 [6].
`InspectBitLockerVolumeAsync`·`UnlockBitLockerVolumeAsync`는 `bdeinfo` 출력으로 그 시작 섹터가 BitLocker 볼륨인지 정한다 [5].
`ewfinfo`·`bdeinfo`는 형식 라이브러리로 헤더를 읽는 외부 도구이고 서버는 그 출력을 해석할 뿐 입력의 바이트를 직접 읽지 않는다 [3][5].
이 workflow들은 분석할 파티션을 스스로 고르지 않고 모델이 파티션 표를 보고 준 시작 섹터를 검사한다 [3][4].

**한계.** `mmls`가 실패하면 `MountEwfImageAsync`는 서버 로그에 경고만 남기고 빈 파티션 표로 성공을 돌려준다 [3].
응답은 파티션 0개를 찾았다고만 적어 파티션 표를 읽지 못한 경우와 파티션 표가 없는 단일 볼륨 이미지를 구별하지 않는다 [3].

### P01.04 방법과 형식·OS 대조

**구현.** `MountFileSystemAsync`는 `fsstat`가 읽은 종류에 `NTFS`가 들어 있으면 NTFS 옵션 loop 마운트를 먼저 하고 실패하면 `ntfs-3g`로 붙인다 [4].
그 밖의 파일 시스템은 일반 읽기 전용 loop 마운트로 붙인다 [4].
`GenerateFilesystemTimelineAsync`·`RecoverFilesAsync`는 `fsstat`가 파일 시스템을 찾지 못하면 `fls`·`tsk_recover`를 실행하지 않는다 [6].
`UnlockBitLockerVolumeAsync`는 `bdeinfo`가 BitLocker 볼륨으로 판별하지 않으면 `bdemount`를 실행하지 않는다 [5].

판별·대조가 없는 경로도 있다.
`Execute`는 스크립트가 이름을 쓴 툴킷을 그대로 묶어 주고 툴킷 메서드는 받은 경로를 외부 도구 인자로 넘길 뿐 형식을 보지 않는다 [7].
그래서 스크립트가 `DiskAnalysisToolkit.EwfMountRawAsync`나 `FsStatAsync`를 바로 부르면 위의 검사를 거치지 않는다 [7].
`MemoryAnalysisWorkflow.FindMalwareAsync`는 Windows 메모리 이미지용 플러그인만 실행하고 이미지의 OS나 Windows 버전을 판별하지 않는다 [8].
Windows 10 이전 이미지를 위한 조정 `legacyMode`는 모델이 인자로 켠다 [8].
툴킷에 `windows.info`를 실행하는 `WindowsInfoAsync`가 있지만 기준 커밋의 workflow는 이 메서드를 부르지 않는다 [9].
서버가 형식·OS별로 지원하는 방법 목록을 두고 대조하는 곳은 없다.

**한계.** `UnlockBitLockerVolumeAsync`는 복호화한 볼륨에서 `fsstat`가 종류를 읽었는지만 보고 그 종류와 관계없이 NTFS 옵션 loop 마운트와 `ntfs-3g`만 시도한다 [10].
두 마운트가 모두 실패하면 서버 로그에 경고를 남기고 파일 시스템을 붙이지 못했다는 문구와 함께 성공을 돌려준다 [10].

        //    volume boot record / superblock at the offset; it reports a File System Type only when one is
        //    recognised (it otherwise prints "Cannot determine file system type", leaving the type unset).

        // 2. Ensure the mount point exists (sudo mkdir -p; harmless if it already does).

        // 3. Mount read-only. NTFS gets the Windows-aware kernel driver, falling back to ntfs-3g 'force' for
        //    dirty/hibernated volumes the kernel driver refuses; everything else uses a plain ro,loop mount.

              || await DiskAnalysis.EwfMountNtfsAsync(imageMount.RawDevice, mountDir, offset)
            : await DiskAnalysis.DDMountAsync(imageMount.RawDevice, mountDir, offset);
