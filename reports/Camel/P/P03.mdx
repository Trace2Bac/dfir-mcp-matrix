# P03 조사 진척 판단

### P03.04 미조사 범위·생략 사유 보고

**구현.** 여러 단계를 묶은 workflow 두 개가 건너뛴 단계를 응답에 싣는다 [1][2].
`MemoryAnalysisWorkflow.FindMalwareAsync`는 원격 연결 조회나 커널 루트킷 검사가 실패해도 분석을 멈추지 않고 응답 문구에 그 단계를 건너뛰었다는 말과 사유를 붙인다 [1].
프로세스를 찾는 세 검사 가운데 하나라도 실패하면 전체를 실패로 돌려준다 [3].
`LinuxAnalysisWorkflow.TriageHostAsync`는 실패한 하위 검사의 영역을 보고서에서 `null`로 둔다 [2][4].
이 메서드의 docstring은 저널 분석과 악성코드 검사를 묶음에서 뺐다고 적지만 응답에는 그 사실이 없다 [4].

다른 묶음 workflow는 실패한 단계를 응답에 알리지 않는다.
`PacketAnalysisWorkflow.TriagePcapAsync`는 하위 단계 6개를 함께 실행하고 `CapInfoAsync`와 `ProtocolHierarchyAsync`가 모두 실패할 때만 실패 결과를 돌려준다 [5].
대화·종단점·DNS·HTTP 단계가 실패하면 그 결과를 빈 목록으로 두고 응답 문구에 건너뛴 단계를 적지 않는다 [5].
`MemoryAnalysisWorkflow.FindCodeInjectionAsync`는 `WindowsHollowProcessesAsync`가 실패하면 빈 목록으로 두고 응답 문구에 hollowed process 0개로 적는다 [6].

서버가 대상마다 해야 할 작업 목록을 두거나 수행한 작업을 대상별로 세는 곳은 없다.
그래서 P03.01~P03.03에는 연결하지 않는다.
사건 `CLAUDE.md` 견본은 보고서에 다루지 못한 범위를 적는 절을 두라고 모델에게 적는다 [7].

**한계.** `FindMalwareAsync`의 생략 사유는 실제 실패 원인과 관계없이 고정 문구다 [1].
툴킷의 공통 실행 함수는 명령이 완료 상태가 아니면 이유와 관계없이 `null`을 돌려주므로 `windows.netscan`이 다른 이유로 실패해도 응답은 그 이미지·OS에서 netscan을 쓸 수 없다고 적는다 [1][8].
명령줄·SID 조회가 실패하면 빈 목록으로 바꿔 용의자의 명령줄과 SID가 비어 있을 뿐 실패를 알리지 않는다 [9].
덤프나 YARA 검사가 실패해도 빈 목록으로 바꿔 응답은 덤프 0개, YARA 일치 0건으로 적는다 [10].
VAD 영역 YARA 검사가 실패하면 결과를 `null`로 두고 응답 문구에는 아무것도 붙이지 않는다 [11].
`TriageHostAsync`의 응답 문구는 `null`인 영역이 있어도 계정·로그인·지속성·셸 기록·파일을 모두 훑었다고 적고 찾은 항목이 없으면 침해 흔적이 드러나지 않았다고 적는다 [12].

### P03.05 모델이 적은 진행 기록 보관

**구현.** `Execute` 스크립트의 전역 함수 `auditMissingEvidence`가 이 방식을 쓴다 [13].
모델은 이 함수로 확인하지 못한 범위(증거 공백)를 적고 서버는 그 문장을 사건 호출 기록에 `missing-evidence` 유형으로 남기며 같은 줄을 응답에도 붙인다 [13].
기록은 사건 ID로 이름을 지은 `audit-<CaseId>.clef` 파일에 쌓여 서버를 다시 시작해도 남는다 [14].
서버는 저장한 기록을 다시 읽거나 요약해 돌려주는 도구를 두지 않고 응답에는 방금 적은 줄만 돌아온다 [13].
적힌 공백이 실제 호출과 맞는지 서버는 대조하지 않는다 [13].
마친 작업이나 다룬 질문을 적는 전용 함수는 없다.
CLI의 `bake-report`가 호출 기록 전체를 보고서 화면 파일에 넣어 사람이 이 기록을 읽는다 [15].

          // auditInfo/auditError additionally record the line in the per-case audit log (CLEF) as an
          // information/error event, so agent-surfaced output survives in the trail, not just the response.
          .SetValue("auditInfo", new Action<string>((s) => AuditInfo(s, output)))
          .SetValue("auditError", new Action<string>((s) => AuditError(s, output)))
          // auditFinding stages a structured forensic finding (observation/interpretation/confidence + the
          // execution ids that prove it) as a `finding` event; auditReviewRec marks a high-consequence decision
          // a human should review as a `human-judgement-recommended` event. Both also echo to the response.
          .SetValue("auditFinding", new Action<string, string, string, string>(
              (observation, interpretation, confidence, evidenceExecutionIds) =>
                  AuditFinding(observation, interpretation, confidence, evidenceExecutionIds, output)))
          .SetValue("auditReviewRec", new Action<string>((s) => AuditReviewRec(s, output)))
          // IR-accuracy events: auditFalsePositive (a lead checked and rejected as benign), auditMissingEvidence
          // (a gap — absent/cleared/disabled logs), auditHallucination (the agent caught itself inventing an
          // artifact/method/field). Surfacing these in the trail is positive evidence of investigative rigour.
          .SetValue("auditFalsePositive", new Action<string>((s) => AuditFalsePositive(s, output)))
          .SetValue("auditMissingEvidence", new Action<string>((s) => AuditMissingEvidence(s, output)))
          .SetValue("auditHallucination", new Action<string>((s) => AuditHallucination(s, output)))
