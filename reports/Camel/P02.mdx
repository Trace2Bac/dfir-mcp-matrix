# P02 다음 작업 결정

### P02.01 고정 문서·프로필 반환

**구현.** 서버는 MCP 리소스 `camel-sdk-core`·`camel-sdk-schema`·`camel-sdk-discipline`을 둔다 [1].
세 리소스는 빌드 때 어셈블리에 넣은 `docs/Camel.core.md`·`docs/Camel.schema.md`·`docs/Camel.discipline.md`를 그대로 읽어 돌려주므로 조사 상태와 관계없이 같은 내용이다 [1][2].
`Execute` 도구 설명은 스크립트를 쓰기 전에 `camel-sdk-core`와 `camel-sdk-schema`를 반드시 읽고 거기 적힌 메서드와 속성만 쓰라고 적는다 [3].
`camel-sdk-discipline`은 질문마다 분석·수집·교차 확인·기록을 되풀이하라고 하고 `*Workflow`, `*Toolkit`, 이상 탐지 엔진의 차례로 고르라고 적는다 [4].
같은 문서는 근본 원인이나 행위자 지목 같은 결정에서 멈추지 말고 `auditReviewRec`를 부른 뒤 조사를 이어 가라고 적는다 [5].

`camel create-case`는 사건 폴더에 Claude Code가 읽는 `CLAUDE.md`를 써 둔다 [6].
이 파일은 첫 단계로 세 리소스를 읽고 `SetCaseId`·`SetEvidence`를 부르라고 하고 조사 목적마다 쓸 workflow와 끝낼 때 풀어야 할 마운트를 적는다 [7].
이 파일은 서버 응답이 아니라 클라이언트에 주는 설정이라서 이 상세의 구현으로 세지 않고 사실로만 적는다.

### P02.02 규칙·조사 상태로 추천

**구현.** MCP 도구 세 개가 세션 상태와 결과에 따라 다음 호출을 응답 문구로 알린다.
`SetEvidence`는 이미 증거를 등록한 세션이면 거부하고 새 세션을 시작하라고 알린다 [8].
증거 파일이 워크스테이션에 없으면 등록하지 않고 빠진 경로를 보인 뒤 파일을 둔 다음 다시 부르라고 알린다 [9].
`VerifyEvidence`는 등록한 증거가 없으면 `SetEvidence`를 먼저 부르라고 하고 검증이 실패하면 보관 연속성 문제로 보고 멈추라고 알린다 [10][11].
`Execute` 스크립트가 없는 `*Toolkit`·`*Workflow` 이름이나 메서드를 불러 오류가 나면 응답에 `camel-sdk-core`를 다시 읽으라는 문구를 붙인다 [12].
디스크 workflow는 실패 응답에 이미 마운트된 폴더를 풀고 다시 하라거나 `mmls` 파티션 표에서 시작 섹터를 다시 확인하라는 문구를 넣는다 [13].
이 권고는 응답 문자열이고 서버가 다음 호출을 대신 고르거나 권고를 따르지 않은 호출을 막지는 않는다.

**예외.** `VerifyEvidence`는 해시를 계산하지 못한 항목도 일치하지 않은 항목으로 센다 [14].
그때도 응답 첫머리는 디스크의 파일이 주어진 해시와 다르다고 단정하고 멈추라고 하며 호출 기록에 `evidence-spoliation` 사건을 남긴다 [11].
줄별 결과에 `actual=(unreadable)`가 찍혀 계산 실패를 가릴 단서는 남는다 [10].
P01.01에서 본 확장자 판별 때문에 이름이 `.e01`·`.ex01`로 끝나지 않는 EWF 이미지도 파일 전체 해시로 비교되어 같은 불일치 판정과 멈춤 권고를 받는다 [14].

### P02.04 서버 코드에 고정한 분석 절차

**구현.** `Execute`는 스크립트마다 workflow 객체 8개를 전역 이름으로 묶어 둔다 [15].
workflow 메서드는 한 조사 목적의 단계와 차례를 코드로 정하고 모델은 메서드와 인자만 고른다 [15][16].
`MemoryAnalysisWorkflow.FindMalwareAsync`는 숨은 프로세스 교차 확인, 프로세스 계보 검사, 원격 IP 조회, 코드 주입 검사, 커널 루트킷 검사와 명령줄·SID 조회를 함께 돌린다 [16].
두 범주 이상에서 걸린 프로세스를 높은 신뢰도 용의자로 올리고 `dumpDir`를 주면 그 실행 파일을 덤프해 YARA로 검사한다 [17].
`LinuxAnalysisWorkflow.TriageHostAsync`는 계정·로그인·인증 로그·지속성·셸 기록·이상 파일 검사 6개를 함께 돌리고 눈에 띄는 항목을 `TopFindings`로 모은다 [18].
`DiskAnalysisWorkflow.MountEwfImageAsync`는 `ewfinfo` 확인, 마운트 폴더 생성, `ewfmount`, `mmls`를 이 차례로 돈다 [19].
`camel-sdk-discipline`과 사건 `CLAUDE.md`는 목적에 맞는 workflow가 있으면 먼저 쓰고 없을 때 툴킷으로 내려가라고 적는다 [4][7].
스크립트는 workflow를 쓰지 않고 툴킷 메서드로 단계를 직접 짤 수도 있다 [20].
서버 안에서 모델을 불러 계획을 세우는 경로는 없어 P02.03에는 연결하지 않는다.

```csharp
    static string? ClassifyHallucination(string? jsErrorMessage)
    {
        if (string.IsNullOrEmpty(jsErrorMessage)) return null;
        var namesApi = jsErrorMessage.Contains("Toolkit", StringComparison.Ordinal)
                       || jsErrorMessage.Contains("Workflow", StringComparison.Ordinal);
        if (!namesApi) return null;
        if (jsErrorMessage.Contains("is not defined", StringComparison.OrdinalIgnoreCase))
            return $"referenced a toolkit/workflow that does not exist ({jsErrorMessage})";
        if (jsErrorMessage.Contains("is not a function", StringComparison.OrdinalIgnoreCase))
            return $"called a method that does not exist on a Camel toolkit/workflow ({jsErrorMessage})";
        return null;
    }
```

```csharp
        // Bind a SIFT toolkit global only when the script actually references it by name. Constructing a toolkit
        // can run one-time provisioning (Toolkit.InstallMissingTools = synchronous wget/apt for the EZ tools,
        // YARA rules pack, hayabusa, …). Binding every toolkit on every call would make the first call in a fresh
        // session block on installing tools the script never uses — e.g. a mount-only script (DiskAnalysis only)
        // would otherwise stall on the YARA/hayabusa downloads and exceed the client's tool timeout. Workflows
        // resolve their toolkits lazily through the api, so a workflow that needs a toolkit still provisions it.
        void BindToolkitIfUsed(string name, Func<object> resolve)
        {
            if (script.Contains(name, StringComparison.Ordinal)) jsinterp.SetValue(name, resolve());
        }
```
