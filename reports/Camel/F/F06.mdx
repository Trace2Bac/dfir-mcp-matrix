# F06 보고 산출물 구성

### F06.01 증거·환경 manifest 포함

**구현.** 이 방식은 사용자가 CLI 명령 `camel bake-report`를 실행하거나 `camel create-case`가 사건 폴더 설정에 넣은 `Stop`·`SessionEnd` 훅으로 Claude Code가 `camel preserve-chatlog`를 실행해야 만들어지는 `reports/report.html`에 있다 [1][2].
MCP 도구에는 보고 산출물을 만드는 도구가 없다.
두 명령은 사건 호출 기록 `logs/audit-<caseId>.clef` 전체를 `reports/audit-data.js`에 담고 `report.html`의 Audit Log 탭이 그 항목을 한 줄씩 싣는다 [3][4].
`SetEvidence`가 남기는 `evidence` 항목에는 등록한 증거의 경로와 크기가 들어 있고 Audit Log 탭은 이를 등록 개수와 경로 목록으로 싣는다 [5][6].
등록 때 받은 해시 값과 `VerifyEvidence`가 계산한 해시 값은 호출 기록 항목에 없다 [5][7].
해시 값은 Conversation 탭이 싣는 대화 기록의 도구 입력·응답 글에만 나오고 그 글은 4000자·2000자에서 자른다 [8].
분석 환경으로는 Conversation 탭이 대화 기록의 `usage`를 모델 이름별로 모아 모델마다 차례 수와 토큰 수를 싣는다 [9][10].
`command` 항목에는 명령을 실행한 호스트가 들어 있어 Audit Log 탭에서 행을 펼치면 보인다 [11][12].
호출 기록 항목 어디에도 서버·SDK·외부 도구의 버전이 없어 보고서에 실리지 않는다 [11].

**한계.** `SetCaseId`를 부르기 전의 호출은 세션 ID(stdio 연결에서는 `default`) 이름의 다른 호출 기록 파일에 쓰인다 [13].
`logs/`에 호출 기록 파일이 둘 이상이면 굽는 코드는 사건 폴더 이름의 파일 하나만 싣는다 [3][14].
그 이름의 파일이 없으면 먼저 찾은 파일 하나만 싣는다 [3][14].
그래서 `SetEvidence`를 `SetCaseId`보다 먼저 부르면 `evidence` 항목이 보고서에 실리지 않는다 [13][14].
`audit-data.js`에 넣을 호출 기록을 읽다 실패하면 표준 오류에 한 줄 적기만 하고 파일을 쓰지 않으므로 이전에 쓴 `audit-data.js`가 그대로 남는다 [15].
클라이언트 설정은 모델이 `reports/` 아래 파일을 쓰고 고치게 허용하므로 남은 파일이 모델이 고친 것일 수도 있다 [16].

### F06.02 수행·누락 범위 포함

**구현.** 이 방식은 사용자가 `camel bake-report`를 실행하거나 `Stop`·`SessionEnd` 훅으로 `camel preserve-chatlog`가 실행되어야 만들어지는 `reports/report.html`의 Audit Log 탭에 있다 [1][2].
Audit Log 탭은 호출 기록의 모든 항목을 시각·종류·실행 ID·호출한 workflow와 toolkit 메서드·요약과 함께 싣고 종류·실행 ID·글자로 거르게 한다 [12][17].
`execution` 항목에는 `Execute`가 받은 스크립트 원문, 끝난 상태(`completed`·`failed`·`cancelled`·`exited`), 걸린 시간이 실린다 [18][12].
`command` 항목에는 실행 환경에서 실행한 명령과 인자, 종료 코드, 완료 여부, 걸린 시간이 실린다 [11].
실패한 범위를 따로 모은 절은 없고 실패는 `failed` 상태의 `execution` 항목과 `command` 항목의 종료 코드로 나타난다 [18][11].
`Findings` 탭의 실행 블록은 0이 아닌 종료 코드를 빨간색으로 표시한다 [19].
모델이 `auditMissingEvidence`·`auditFalsePositive`로 남긴 `missing-evidence`·`false-positive` 항목도 종류로 걸러 볼 수 있다 [20][17].
Conversation 탭은 대화 기록의 사용자·모델 차례와 도구 입력·응답을 싣는다 [8].
명령의 출력은 호출 기록에 남지 않아 Audit Log 탭에는 없다 [11].

**한계.** `SetCaseId`를 부르기 전의 호출은 다른 호출 기록 파일에 쓰인다 [13].
`logs/`에 호출 기록 파일이 둘 이상이면 굽는 코드는 그중 하나만 싣는다 [14].
그래서 `SetCaseId` 전에 부른 `Execute`의 실행과 명령은 보고서의 범위에서 빠진다 [13][14].
`audit-data.js`에 넣을 호출 기록을 읽다 실패하면 표준 오류에 한 줄 적기만 하고 파일을 쓰지 않으므로 보고서에는 이전에 쓴 `audit-data.js`의 옛 범위가 실린다 [15].
클라이언트 설정은 모델이 `reports/` 아래 파일을 쓰고 고치게 허용하므로 남은 파일이 모델이 고친 것일 수도 있다 [16].

### F06.03 발견사항과 근거 링크 포함

**구현.** 이 방식은 사용자가 `camel bake-report`를 실행하거나 `Stop`·`SessionEnd` 훅으로 `camel preserve-chatlog`가 실행되어야 만들어지는 `reports/report.html`의 `Findings` 탭에 있다 [1][2].
`Findings` 탭은 호출 기록의 `finding` 항목마다 확신도, 관찰, 해석, 근거로 인용한 실행 ID를 싣는다 [21][22].
인용한 실행 ID마다 그 실행의 스크립트 원문, 그 실행 중에 실행된 명령의 목록과 종료 코드, 끝난 상태를 펼쳐 보여 준다 [22][19].
실행 ID를 누르면 Audit Log 탭을 그 실행 ID로 걸러 보여 준다 [23].
인용한 실행 ID가 호출 기록에 없으면 `(execution not found in this log)`로 적는다 [19].
명령의 출력 원문은 호출 기록에 없어 `Findings` 탭에서 이어지지 않는다 [11].
`finding` 항목은 모델이 `auditFinding`에 넘긴 값을 서버가 그대로 기록한 것이고 서버는 인용이 맞는지 심사하지 않는다 [21].
모델이 쓰는 `reports/report.md`의 발견사항과 실행 ID 인용은 굽는 코드가 `report.html`에 넣지 않는다 [4][24].

**한계.** `SetCaseId`를 부르기 전의 실행은 다른 호출 기록 파일에 쓰인다 [13].
`logs/`에 호출 기록 파일이 둘 이상이면 굽는 코드는 그중 하나만 싣는다 [14].
그래서 실제로 있었던 실행을 인용한 발견사항도 그 실행이 다른 파일에 있으면 `(execution not found in this log)`로 나온다 [14][19].
`audit-data.js`에 넣을 호출 기록을 읽다 실패하면 표준 오류에 한 줄 적기만 하고 파일을 쓰지 않으므로 보고서에는 이전에 쓴 `audit-data.js`의 옛 발견사항이 실린다 [15].
클라이언트 설정은 모델이 `reports/` 아래 파일을 쓰고 고치게 허용하므로 남은 파일이 모델이 고친 것일 수도 있다 [16].

### F06.04 검증·한계 포함

**구현.** 이 방식은 사용자가 `camel bake-report`를 실행하거나 `Stop`·`SessionEnd` 훅으로 `camel preserve-chatlog`가 실행되어야 만들어지는 `reports/report.html`의 Audit Log 탭에 있다 [1][2].
`VerifyEvidence`가 남기는 `evidence-verification` 항목과 해시가 맞지 않을 때의 `evidence-spoliation` 항목이 Audit Log 탭에 그 종류로 실린다 [7][12].
`evidence-verification` 항목은 검증한 개수만 적고 `evidence-spoliation` 항목은 맞지 않은 경로만 적는다 [7].
다루지 못한 범위로는 모델이 `auditMissingEvidence`로 남긴 `missing-evidence` 항목이 실린다 [20].
검증 결과나 다루지 못한 범위를 따로 모은 절은 없고 검토자가 종류로 걸러 본다 [17].
`VerifyEvidence`를 부르지 않은 조사에는 검증 항목이 없고 화면은 검증하지 않았다는 표시를 따로 하지 않는다 [7][17].
Accuracy 탭은 모델이 쓴 `reports/accuracy.md`를 그대로 보여 주며 이 셀의 구현으로 세지 않는다 [4][25].

**한계.** `VerifyEvidence`는 등록 때 해시를 받지 않은 항목을 해시를 계산하지 못해도 맞은 것으로 센다 [26].
그런 항목이 있어도 `evidence-verification` 항목은 그 항목까지 넣은 개수를 검증했다고 적고 Audit Log 탭은 이를 그대로 싣는다 [7][26].
`SetCaseId`를 부르기 전의 검증 기록은 다른 호출 기록 파일에 쓰인다 [13].
`logs/`에 호출 기록 파일이 둘 이상이면 굽는 코드는 그중 하나만 싣는다 [14].
`audit-data.js`에 넣을 호출 기록을 읽다 실패하면 표준 오류에 한 줄 적기만 하고 파일을 쓰지 않으므로 보고서에는 이전에 쓴 `audit-data.js`의 옛 검증 기록이 실린다 [15].
클라이언트 설정은 모델이 `reports/` 아래 파일을 쓰고 고치게 허용하므로 남은 파일이 모델이 고친 것일 수도 있다 [16].

### F06.05 내보내기

**구현.** 이 방식의 파일은 사용자가 `camel bake-report`를 실행하거나 `Stop`·`SessionEnd` 훅으로 `camel preserve-chatlog`가 실행되어야 만들어진다 [1][2].
`camel create-case`는 사건 폴더에 `logs/`·`exports/`·`reports/`를 만들고 데이터가 빈 `reports/report.html`·`report.js`를 템플릿으로 만들며 훅 명령을 `.claude/settings.json`에 넣는다 [27][2].
`Stop` 훅은 모델 차례가 끝날 때마다 실행되고 `SessionEnd` 훅은 세션이 끝날 때 실행된다 [2].
`preserve-chatlog`는 Claude Code가 넘긴 대화 기록을 `logs/chatlog-<session_id>.jsonl`로 복사하고 `logs/token-usage.json`을 쓴 뒤 보고서를 굽는다 [28].
굽는 코드는 `report.html`·`report.js`를 템플릿에서 다시 쓰고 호출 기록·대화 기록·토큰 사용량을 `audit-data.js`·`chatlog-data.js`·`token-usage-data.js`로 써서 `reports/`에 둔다 [4][3][29].
`report.html`은 서버 없이 파일로 열리는 HTML 문서이고 같은 폴더의 데이터 파일을 `<script>`로 읽는다 [30].
`bake-report`는 끝나면 `report.html` 경로와 쓴 데이터 파일 수를 출력한다 [31].
표준 교환 형식의 파일은 만들지 않는다.

사건 템플릿 `CLAUDE.md`는 클라이언트 모델에게 `reports/report.md`·`iocs.csv`·`accuracy.md`를 쓰라고 안내한다 [24].
이 세 파일은 모델이 쓰는 글이라 이 셀의 구현으로 세지 않는다.
굽는 코드는 그중 `iocs.csv`·`accuracy.md`를 base64로 `report.html`에 넣어 IOCs·Accuracy 탭에 보여 주고 `report.md`는 넣지 않는다 [4][25].
클라이언트 설정은 모델이 `reports/`·`exports/` 아래에만 파일을 쓰게 허용한다 [16].

**한계.** 데이터 파일 하나를 쓰다 실패하면 표준 오류에 한 줄 적고 나머지를 계속 쓰며 명령은 실패로 끝나지 않는다 [15][31].
훅은 받은 `transcript_path`가 없으면 굽지 않고 끝난다 [32].
훅은 굽다 실패해도 표준 오류에 적을 뿐 세션을 멈추지 않는다 [28].
`audit-data.js` 없이 연 `report.html`은 HTTP로 열 때만 `../logs/audit-<caseId>.clef`를 직접 읽고 그렇지 않으면 파일 고르기 화면을 보여 준다 [33].
실패한 데이터 파일 자리에는 이전 파일이 그대로 남는다 [15].
클라이언트 설정은 모델에게 `reports/` 쓰기를 허용하므로 남은 파일이 모델이 고친 것일 수도 있다 [16].

    static int BakeReport(string caseDir)
    {
        var reportsDir = Path.Combine(caseDir, "reports");
        var logsDir = Path.Combine(caseDir, "logs");
        Directory.CreateDirectory(reportsDir);
        var caseId = ResolveCaseId(caseDir, logsDir);

        static string B64OfFile(string p) =>
            File.Exists(p) ? Convert.ToBase64String(Encoding.UTF8.GetBytes(File.ReadAllText(p))) : "";

        // report.html + report.js — regenerated from the embedded template (they are viewer files, not user-edited),
        // so re-baking also upgrades an older case's viewer to the current template.
        File.WriteAllText(Path.Combine(reportsDir, "report.html"),
            ReadEmbedded("Camel.CLI.CaseTemplate.report.html")
                .Replace("__CASE_ID__", caseId)
                .Replace("__ACCURACY_B64__", B64OfFile(Path.Combine(reportsDir, "accuracy.md")))
                .Replace("__IOCS_B64__", B64OfFile(Path.Combine(reportsDir, "iocs.csv"))));
        File.WriteAllText(Path.Combine(reportsDir, "report.js"), ReadEmbedded("Camel.CLI.CaseTemplate.report.js"));

  if (!CASE_ID) return false;
  // report.html lives in the case's reports/ dir, so the log is one level up.
  const path = `../logs/audit-${CASE_ID}.clef`;
  try {
    const res = await fetch(path, { cache: "no-store" });
    if (!res.ok) return false;
    load(await res.text(), path);
    return true;
