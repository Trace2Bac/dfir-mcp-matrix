# F06 보고 산출물 구성

### F06.02 수행·누락 범위 포함

**구현.** 이 방식은 사용자가 같은 저장소의 CLI `scripts/investigate.py`를 실행할 때 반복마다 쓰는 진행 기록 파일에 있다 [1].
CLI는 `claude -p`로 조사를 한 번 실행한 뒤 서버의 `assess_coverage`를 같은 프로세스에서 불러 조사 범위 보고를 받는다 [1][2].
반복 기록 `iteration-NN.json`에는 그 반복에서 늘어난 호출 기록 항목 수 `tool_calls_this_iteration`, 범위 판정 `coverage_clean`, `assess_coverage` 응답 전문 `coverage_report`가 실린다 [1].
`assess_coverage` 응답은 기록된 도구 실행 수, 쓴 도구 종류 수, 증거에 있는 아티팩트 분류마다의 위치와 조사 여부를 담는다 [3].
반복 기록은 `claude` 실행 결과에서 모델이 쓴 글 `result_text`를 빼고 실행 정보만 담는다 [1].

서버에는 보고 산출물을 만드는 도구가 없다.
`finalize_report`는 받아들인 주장 목록을 응답으로만 돌려주고 IR 보고서는 클라이언트 모델이 서버 지침에 따라 쓴다 [4][5].
`scripts/capture_example_run.py`는 LLM 없이 도구 함수를 직접 불러 저장소의 예시 증거 `attack-scenario-01`에 정해 둔 도구 순서를 실행한다 [6].
이 CLI가 실행할 수 있는 시나리오는 01 하나다 [6].
실행 뒤에는 호출 기록 `audit.json`을 가공하지 않고 출력 파일로 그대로 복사한다 [6].
그래서 이 CLI는 서버 기록을 정해진 코드로 가공해 보고 산출물을 만드는 경로가 아니다.

`scripts/extract_token_usage.py`는 Claude Code가 저장소 밖에 남긴 세션 대화 기록에서 findevil 도구 호출과 토큰 사용량을 꺼내 `token_usage.jsonl`과 `token_usage_summary.md`를 쓴다 [7].
`token_usage_summary.md`에는 토큰 사용량 총계와 도구별 호출 수 표만 실린다 [8].
이 파일에는 조사 범위, 방법, 결과, 한계, 발견사항의 확정 상태가 실리지 않는다 [8].
그래서 이 파일은 검토자가 조사를 확인하도록 만든 보고 산출물이 아니다.

**한계.** CLI가 부르는 `assess_coverage`는 조사 대상 폴더가 아니라 증거 폴더 전체를 훑고 호출 기록 파일의 모든 항목으로 조사 여부를 정한다 [2][9].
그래서 진행 기록의 범위 보고에는 다른 사건 폴더의 아티팩트가 실리고 앞선 조사에서 부른 도구도 조사한 것으로 세어진다.
CLI는 `findings_json` 없이 `assess_coverage`를 부르므로 IOC 조회 공백과 확정 주장 검증 공백은 범위 보고에 실리지 않는다 [2][10].
CLI가 읽는 호출 기록 폴더는 CLI 프로세스의 작업 폴더 기준으로 정해지고 `claude`는 저장소 루트에서 실행된다 [11].
CLI도 서버 모듈을 불러오므로 CLI가 부른 `assess_coverage`는 CLI의 호출 기록 폴더에 항목을 남긴다 [12].
폴더가 같을 때도 반복 기록의 호출 수에는 반복마다 이 항목 1건이 더해진다 [1][12].
환경변수 `FINDEVIL_LOGS_DIR` 없이 CLI를 저장소 루트가 아닌 곳에서 실행하면 서버와 CLI의 호출 기록 폴더가 달라진다 [11].
그러면 반복 기록의 호출 수에는 서버의 호출이 실리지 않고 CLI가 부른 `assess_coverage` 항목 1건만 세어진다 [11][12].
CLI의 증거 폴더도 CLI 프로세스의 작업 폴더 기준으로 정해진다 [13].
그 폴더가 없으면 `assess_coverage`는 아티팩트 목록을 비운 채 `COVERAGE CLEAN`을 돌려주고 반복 기록의 `coverage_clean`은 참이 된다 [13][1].
CLI는 `assess_coverage` 응답 전문에 `COVERAGE CLEAN` 글자가 있는지로 `coverage_clean`을 정하고 판정 줄만 따로 읽지 않는다 [2].
`assess_coverage` 응답의 표 줄과 남은 작업 줄에는 증거 폴더 기준 경로가 실린다 [14].
그래서 경로에 이 글자가 들어 있으면 판정 줄이 `GAP(S) REMAIN`인 응답에서도 반복 기록의 `coverage_clean`이 참으로 기록된다 [2][3][14].
요약 파일 `summary.json`의 `coverage_clean`도 같은 값이다 [15].

### F06.04 검증·한계 포함

**구현.** 이 방식도 `scripts/investigate.py`의 반복 기록과 요약 파일에 있다 [1][15].
반복 기록의 `finalize_accepted`는 그 반복 동안 호출 기록에 `finalize_report`의 `ACCEPTED` 항목이 새로 생겼는지를 담는다 [1][16].
`coverage_report`의 `Coverage gaps` 절은 증거에 있지만 조사하지 않은 아티팩트 분류와 권하는 도구를 싣는다 [3].
요약 파일 `summary.json`은 반복 수, 마지막 범위 판정, 마무리 수락 여부를 담는다 [15].

**한계.** `finalize_accepted`는 `ACCEPTED` 항목이 생겼는지만 담고 어떤 주장을 어떤 확신도로 받아들였는지는 담지 않는다 [16].
다른 증거를 조사한 `finalize_report` 호출이 같은 반복 동안 `ACCEPTED`를 남겨도 같은 값이 된다 [16].

```python
def _audited_tool_calls() -> list[dict]:
    """Return every audit.json entry as a dict (best-effort, never raises)."""
    audit_path = LOGS_DIR / "audit.json"
    if not audit_path.is_file():
        return []
    try:
        raw = audit_path.read_text(errors="replace").splitlines()
    except OSError:
        return []
    out: list[dict] = []
    for line in raw:
        line = line.strip()
        if not line:
            continue
        try:
            out.append(json.loads(line))
        except json.JSONDecodeError:
            continue
    return out


def _called_tool_names(entries: list[dict]) -> set[str]:
```

```python
def _finalize_accepted_since(n_before: int) -> bool:
    """Was a finalize_report ACCEPTED recorded after the first n_before entries?"""
    entries = _read_audit()[n_before:]
    return any(
        e.get("tool") == "finalize_report"
        and str(e.get("result_summary", "")).startswith("ACCEPTED")
        for e in entries
    )
```
