# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 로그, 설정 파일, 파일시스템, Volatility 출력, 모델이 넘긴 주장을 읽어 판정하는 도구 대부분에 있다.
`auth_sudo_commands`는 sudo 명령에 `/etc/shadow`·`authorized_keys`·`nc`·`curl https://` 같은 정규식이 맞으면 의심 표시를 붙인다 [1].
`auth_successful_logins`는 실패 기록이 있는 IP를 모으고 그 IP에서 온 로그인 성공에 `brute-force-preceded` 표시를 붙인다 [2].
`auth_summary`는 실패가 5회 이상인 IP에서 로그인에 성공했으면 `LIKELY COMPROMISE` 판정을 낸다 [3].
`analyze_journal`도 journald 기록에서 같은 표시와 같은 5회 기준을 쓴다 [4].
`find_persistence`는 cron·systemd·셸 초기화·rc.local·udev·at 작업 파일에 내려받기, 리버스 셸 도구, 쓰기 가능한 폴더 실행, 난독화, 일부 공인 IP 대역 같은 정규식을 댄다 [5].
systemd unit에서는 파일 전체가 아니라 `ExecStart` 줄에만 이 정규식을 댄다 [6].
cron·셸 초기화·rc.local은 정규식이 맞으면 `high`로 분류하고 at 작업은 맞지 않아도 `medium`으로 싣는다 [7].
udev 규칙은 이유에 쓰기 가능한 폴더 실행·내려받기·난독화·리스너가 있을 때만 `high`이고 그 밖에는 정규식이 맞아도 `medium`이다 [8].
같은 검사는 40자 이상 base64 덩어리를 디코딩해 같은 정규식을 다시 대고 맞으면 이유 끝에 `(decoded from base64)`를 붙인다 [5].
`verify_package_integrity`는 `/var/lib/dpkg/info/*.md5sums`에 적힌 MD5와 실제 파일의 MD5가 다르면 변경 파일로 싣는다 [9].
변경 파일에 `usr/sbin/sshd`·`usr/bin/sudo`·`bin/login` 같은 경로가 있으면 `CRITICAL` 판정을 낸다 [9].
`baseline_diff`는 기준선과 지금 상태를 경로를 키로 맞대어 추가·삭제·변경으로 나누고 추적 경로 목록에 정한 등급이 `critical`인 변경이 있으면 `LIKELY COMPROMISE`를 낸다 [10].
`analyze_nginx_access`는 요청 경로·User-Agent·Referer에 SQL 삽입·경로 탐색·명령 삽입·웹셸 이름 같은 정규식을 대어 표시를 붙인다 [11].
같은 도구는 업로드 폴더의 실행 확장자에 대한 POST와 같은 경로의 GET을 경로를 키로 이어 웹셸 업로드 사슬로 싣는다 [11].
`find_webshells`·`analyze_container_artifacts`·`analyze_package_logs`·`find_ai_signatures`·`analyze_bash_history`도 정한 정규식과 이름 목록으로 파일이나 기록을 분류한다 [12].
`analyze_memory_processes`는 Volatility `linux.pslist` 출력에서 알려진 악성 프로세스 이름과 부모 PID가 목록에 없는 프로세스를 이상으로 고른다 [13].
`analyze_memory_modules`는 `linux.check_modules`의 모듈 이름 집합에서 `linux.lsmod`의 이름 집합을 뺀 차집합을 숨은 모듈로 내놓는다 [14].
`correlate_memory_and_disk`는 그 숨은 모듈 이름과 디스크의 모듈 설정에서 뽑은 이름을 맞대어 네 경우로 나누고 판정을 낸다 [15].
`analyze_memory_network`는 소켓 목록에서 4444·1337·31337 같은 정해 둔 포트의 `LISTEN`과 RFC1918·루프백이 아닌 주소로 향한 `ESTABLISHED`·`SYN_SENT` 연결을 표시한다 [16].
`find_persistence`의 sshd_config 검사와 `analyze_sshd_config`는 `PermitRootLogin`·`PasswordAuthentication`·`PermitEmptyPasswords` 같은 지시어 값을 정한 규칙과 맞대어 표시한다 [17].
`find_persistence`의 sudoers 검사와 `analyze_sudoers`는 `NOPASSWD: ALL`, root가 아닌 계정의 `ALL` 권한, 인자 없이 허용한 셸 탈출용 실행 파일 목록 `_DANGEROUS_NOPASSWD_CMDS`를 표시한다 [18].
`analyze_systemd_unit`은 `ExecStart` 줄마다 같은 지속성 정규식을 대어 이유를 붙인다 [19].
`stat_file`은 mtime이 ctime보다 뒤이면 timestomping 의심을, mtime이 지금 시각보다 뒤이면 미래 시각을 표시한다 [20].
`find_timestamp_anomalies`는 mtime이 ctime보다 1초 넘게 뒤인 파일과 지금 시각보다 60초 넘게 뒤인 파일을 고른다 [21].
`find_shell_histories`와 `analyze_bash_history`는 기록 파일이 0바이트이거나 매우 짧으면 변조 가능성 표시를 붙인다 [22].
`bulk_ioc_lookup`은 글에서 뽑은 공인 IP·도메인·해시를 서버에 묶인 IOC 목록 `threat_intel.json`과 값으로 맞대어 범주와 태그를 붙인다 [23].
이때 확신도는 목록 항목의 값을 그대로 옮긴다 [23].
도메인이 목록에 없으면 앞 조각을 하나씩 떼어 낸 상위 도메인을 차례로 찾는다 [24].
맞는 항목이 있으면 그 항목의 `category`와 `confidence`를 그대로 쓰고 `tags`에 `subdomain_match`를 더한다 [24].
도메인 결과 줄 앞에는 `category`가 `legitimate`이면 `✓`를, 그 밖의 범주이면 `⚠`를 붙인다 [24].
목록의 `github.com`은 `category`가 `legitimate`여서 그 하위 도메인은 `✓`와 함께 실린다 [24][25].
`verify_finding`은 모델이 넘긴 주장 유형과 인자로 증거 파일을 다시 읽어 `SUPPORTED`·`CONTRADICTED`·`INSUFFICIENT_EVIDENCE` 가운데 하나를 정한다 [26].
`find_contradictions`는 모델이 넘긴 주장들을 같은 로그 경로, IP, 지속성 분류, 사용자 이름, 파일 경로를 키로 맞대어 정해 둔 6가지 모순 유형을 찾는다 [27].

판정 규칙 안에는 알려진 정상 목록으로 의심 후보를 정하는 제외 조건이 있다.
`find_persistence`는 `/etc/init.d`의 스크립트 가운데 배포판 기본 이름 목록에 있는 것을 검사하지 않고 그 밖의 스크립트는 정규식이 맞지 않아도 `medium`으로 싣는다 [28].
PAM 설정에서는 기본 모듈 목록에 없는 모듈 이름을, `/etc/modules`에서는 흔한 모듈 목록에 없는 모듈 이름을 `high`로 싣는다 [29].
`find_persistence`의 sudoers 검사는 `%`로 시작하는 그룹 규칙을 `ALL` 권한 표시에서 빼지만 `analyze_sudoers`는 그룹 규칙도 표시한다 [18].
`bulk_ioc_lookup`은 RFC1918 주소를 목록과 맞대지 않고 흔한 도메인 몇 개를 IOC에서 뺀다 [30].
`analyze_memory_network`도 RFC1918·루프백 주소로 향한 연결은 표시하지 않는다 [16].

판정에는 서버 코드에 정한 이름 목록도 쓴다.
`find_persistence`는 `ld.so.preload`에 `libprocesshider` 같은 루트킷 라이브러리 이름이 있으면 이유에 적는다 [31].
`analyze_package_logs`는 PyPI 유사 이름 목록과 보안 도구 이름 목록으로 유사 이름 패키지 설치와 보안 도구 제거를 표시한다 [32].
`analyze_container_artifacts`는 위험 권한 목록과 민감한 호스트 경로 목록으로 컨테이너 설정을 표시한다 [33].
`analyze_nginx_access`는 스캐너 User-Agent 이름 목록으로 스캐너 요청을 표시한다 [34].

**한계.** `auth_successful_logins`의 `brute-force-preceded` 표시와 `auth_summary`의 "실패 뒤에 인증" 판정 문구는 실패와 성공의 차례를 보지 않는다 [2][3].
두 도구는 로그 전체에서 실패가 있는 IP 집합을 먼저 만들고 성공 줄의 IP가 그 집합에 있는지만 본다 [2][3].
그래서 로그인 성공 뒤에만 실패가 있는 IP도 같은 표시와 판정을 받는다.
`analyze_nginx_access`의 웹셸 업로드 사슬도 POST를 모두 모은 뒤 GET을 찾으므로 업로드보다 앞선 GET도 사슬로 잇는다 [11].
사슬은 GET의 상태 코드를 보지 않아 404로 끝난 GET도 실행으로 잇는다 [35].
사슬이 하나라도 있으면 응답은 `LIKELY WEBSHELL COMPROMISE` 판정을 싣는다 [35].
`find_persistence`의 파일 검사는 파일마다 앞 65,536바이트만 읽어 그 뒤 내용에는 정규식을 대지 않는다 [36].
이유 문구 `non-RFC1918 IP in config`는 첫 옥텟이 185·45·91·194인 주소에만 붙는다 [5].
base64 덩어리는 파일마다 앞 10개만 디코딩해 다시 검사한다 [5].

`analyze_memory_network`는 점으로 나눈 네 부분이 아닌 주소를 RFC1918 밖 주소로 본다 [16].
그래서 `::1`이 아닌 IPv6 주소로 향한 연결도 RFC1918 밖 연결로 표시된다 [16].

`_parse_sshd_config`는 같은 지시어가 여러 번 나오면 마지막 값을 쓰고 지시어 이름을 대소문자를 가려 비교한다 [37].
OpenSSH 9.6p1의 sshd_config는 지시어마다 처음 얻은 값을 쓰고 지시어 이름의 대소문자를 가리지 않는다 [38].
이 해석기는 `Include`가 가리키는 파일을 읽지 않고 `Match` 블록 안의 값도 전역 값처럼 덮어쓴다 [37].
`find_persistence`의 sshd_config 검사는 지시어가 없으면 기본값을 넣어 판정하므로 `PasswordAuthentication`이 없는 파일도 `PasswordAuthentication yes`로 표시한다 [17].
`analyze_sshd_config`는 파일에 적힌 지시어만 판정하므로 같은 파일에서 이 표시를 내지 않는다 [17].

`verify_package_integrity`는 MD5를 계산하지 못한 파일을 비교한 수에 넣고 변경 여부 판정에서는 뺀다 [9].
바뀐 파일이 없으면 응답은 그런 파일이 있어도 패키지 파일 변경 흔적이 없다는 판정 문구를 싣는다 [39].
`baseline_diff`는 지금 읽지 못한 추적 파일을 기준선에는 있고 지금은 없는 파일로 분류한다 [40][10].
그 파일의 등급이 `critical`이면 `LIKELY COMPROMISE` 판정이 나온다 [10].

`correlate_memory_and_disk`는 디스크 쪽 모듈 이름을 `scan_kernel_modules`의 이유 문장에서 백틱 안이 영문자·숫자·밑줄로만 이루어진 값으로 뽑는다 [15].
`/lib/modules/*/extra/`의 `.ko` 파일 이유는 백틱 안에 점이 들어간 파일 이름을 적고 `modprobe.d`의 `install` 지시 이유는 백틱 안에 지시 줄 전체를 적는다 [41].
그래서 이 두 경로에서 찾은 모듈은 디스크 쪽 이름에 포함되지 않는다 [15][41].
`/etc/modules`에 적혀 있어도 흔한 모듈 목록에 있는 이름은 이유 문장이 없어 디스크 쪽 이름에서 빠진다 [29].
흔하지 않은 모듈도 앞 10개만 이유 문장이 되므로 11번째부터는 디스크 쪽 이름에서 빠진다 [42].
응답의 `Disk: N module name(s) in /etc/modules or modprobe.d/` 줄은 이렇게 뽑힌 이름의 수다 [15].

### F02.02 시각·위치 근접 연결

**구현.** 이 방식은 `find_timestamp_anomalies`에 있다 [21].
도구는 파일마다 mtime과 ctime을 초 단위 정수로 바꾼 쌍을 키로 묶고 같은 쌍인 파일이 4개 이상이면 한 번에 바뀐 묶음으로 싣는다 [21].
이 묶음은 응답의 `Identical-timestamp batches` 절에 시각과 함께 실린다 [21].
`build_timeline`은 여러 기록의 사건을 시각순으로 정렬해 표로 내놓을 뿐 사건끼리 잇지 않는다 [43].

### F02.03 통계·점수 산정

**구현.** 이 방식은 `auth_failed_logins`와 `find_ai_signatures`에 있다 [44][45].
`auth_failed_logins`는 IP마다 실패 시도 수와 대상 사용자 수를 센다 [44].
시도가 50회 이상이거나 사용자가 10명 이상이면 `high`, 시도가 10회 이상이면 `medium`, 그 밖은 `low`로 확신도를 정한다 [44].
`find_ai_signatures`는 셸 기록의 `#<epoch>` 시각 줄에서 이웃한 명령의 시각 차이를 구한다 [45].
0초보다 크고 하루보다 짧은 차이만 남긴 뒤 2초 미만인 차이가 절반 이상이고 차이가 5개 이상이면 기계 속도로 실행한 기록으로 싣는다 [45].
이때 2초 미만 차이 수, 전체 차이 수, 비율을 함께 싣는다 [45].

**한계.** `auth_failed_logins`는 sshd의 `Failed ... for invalid user` 줄과 `Invalid user` 줄을 모두 실패 시도로 처리한다 [46].
sshd가 없는 사용자에 대한 비밀번호 시도 하나를 두 줄로 남기면 그 시도는 2회로 집계된다.
`find_ai_signatures`는 셸 기록 파일의 앞 65,536바이트만 읽어 비율을 구한다 [45].
기록의 시각이 초 단위 정수라서 2초 미만으로 세는 차이는 실제로 1초 차이뿐이다 [45].
같은 초에 실행된 이웃 명령의 차이 0은 셈에서 빠진다 [45].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 규칙으로 판정한 결과를 내는 도구의 응답에 있다.
인증 로그·journald·웹 로그 도구는 판정한 항목마다 원래 로그의 줄 번호를 싣는다 [47].
`auth_failed_logins`는 IP마다 처음과 마지막 줄 번호를 싣는다 [44].
`find_persistence`의 발견사항은 파일 경로, 맞은 규칙의 이름 목록 `reasons`, 내용 일부 `sample`을 담고 응답은 이 세 가지를 모두 싣는다 [48].
`verify_finding`의 판정 이유는 맞은 줄 번호처럼 확인한 값을 적는다 [26].
`build_timeline`은 사건마다 원래 파일 이름과 줄 번호를 `Provenance` 열에 싣는다 [43].

**한계.** `auth_summary`의 `LIKELY COMPROMISE` 판정은 IP와 실패 수만 싣고 그 판정에 쓴 줄 번호를 싣지 않는다 [3].

### F02.08 확신 수준·추정 범위 표시

**구현.** 이 방식은 `auth_failed_logins`, `verify_finding`, 메모리 도구, 판정 문구를 싣는 분석 도구, `bulk_ioc_lookup`에 있다 [44][26][49].
`auth_failed_logins`는 IP마다 `Confidence:` 줄에 `high`·`medium`·`low`와 판정 문장을 싣는다 [44].
`verify_finding`의 인증 로그·웹 로그 검증은 증거 경로가 증거 폴더 밖이거나 로그를 읽지 못하면 판단 보류에 해당하는 `INSUFFICIENT_EVIDENCE`를 싣는다 [26][50].
`analyze_memory_summary`는 숨은 모듈이나 주입 의심 영역이 있으면 `LIKELY MEMORY-RESIDENT COMPROMISE`를 싣는다 [49].
프로세스·네트워크 이상만 있으면 단독으로는 결론을 내릴 수 없다는 `Moderate signals` 판정을 싣는다 [49].
`analyze_memory_modules`는 숨은 모듈이 있으면 `high-confidence rootkit indicator`와 `LIKELY KERNEL ROOTKIT` 판정을 싣는다 [51].
`correlate_memory_and_disk`는 메모리와 디스크가 함께 가리키면 `CONFIRMED KERNEL ROOTKIT`, 메모리에만 있으면 `MEMORY-RESIDENT ROOTKIT`, 디스크에만 있으면 설정이 남은 것일 수 있다는 단계로 판정을 나눈다 [52].
`auth_summary`·`analyze_journal`·`baseline_diff`는 `LIKELY COMPROMISE` 판정을 싣는다 [3][53][10].
`verify_package_integrity`는 주요 실행 파일이 바뀌었으면 확인 전까지 침해로 다루라는 `CRITICAL` 판정을 싣는다 [9].
`analyze_nginx_access`와 `analyze_package_logs`는 신호가 적으면 단정할 수 없다는 판정 문구를 싣는다 [54].
`bulk_ioc_lookup`은 묶인 IOC 목록 항목의 `confidence`를 그대로 싣는다 [23].

### F02.09 판정 제외 조건의 공개

**구현.** 이 방식은 `find_persistence`, `analyze_memory_modules`, `bulk_ioc_lookup`의 응답에 적용된다 [57][58][59].
`find_persistence`는 요약에 등급마다 건수를 싣고 의심하지 않은 `info` 항목의 건수도 함께 싣는다 [57].
상세 목록에서는 `info` 항목을 뺀다 [57].
high·medium 항목이 하나도 없으면 "persistence files present but not flagged" 제목 아래 `info` 항목을 10개까지 싣는다 [57].
`analyze_memory_modules`는 숨은 커널 모듈을 찾는 규칙이 후보에서 뺀 `lsmod`에만 있는 모듈을 "likely benign"이라는 제목과 개수로 따로 싣는다 [58].
`bulk_ioc_lookup`은 조회하지 않는 사설 IP를 "RFC1918 IPs" 제목과 개수로 따로 싣고 조회하지 않았다는 문구 "not looked up"을 붙인다 [59].

**한계.** 같은 도구 안에도 판정 규칙이 항목을 빼고 그 사실을 밝히지 않는 곳이 있다.
`find_persistence`는 정해 둔 정상 init.d 스크립트를 결과에서 아무 표시 없이 뺀다 [60].
정상 PAM 모듈과 흔한 커널 모듈도 아무 표시 없이 판정 이유에서 뺀다 [60].
`bulk_ioc_lookup`이 쓰는 IOC 추출은 정해 둔 잡음 도메인을 아무 표시 없이 뺀다 [61].
`analyze_memory_modules`는 `lsmod`에만 있는 모듈의 이름을 20개까지만 싣고 `bulk_ioc_lookup`도 사설 IP를 20개까지만 싣는다 [58][59].

```python
def _diff_modules(lsmod_rows: list[dict], check_rows: list[dict]) -> dict:
    """Compare linux.lsmod and linux.check_modules to find hidden modules.

    A module that appears in `check_modules` (which walks kernel structures
    directly) but NOT in `lsmod` (which uses the canonical loaded-modules
    list a rootkit can hide from) is the classic hidden-LKM signature.

    Vol3 v2.28 uses "Module Name" (with a space) for linux.lsmod output.
    Older variants use "Name" or "Module". We accept all three.
    """
    def _mod_name(row: dict) -> str:
        n = row.get("Module Name") or row.get("Name") or row.get("Module")
        return str(n) if n else ""

    lsmod_names = {_mod_name(r).lower() for r in lsmod_rows if _mod_name(r)}
    check_names = {_mod_name(r).lower() for r in check_rows if _mod_name(r)}

    only_in_check = sorted(check_names - lsmod_names)
    only_in_lsmod = sorted(lsmod_names - check_names)
    both = sorted(check_names & lsmod_names)

    return {
        "loaded_modules": sorted(lsmod_names),
        "check_modules": sorted(check_names),
        "hidden_modules": only_in_check,
        "only_in_lsmod": only_in_lsmod,
        "both": both,
    }
```
