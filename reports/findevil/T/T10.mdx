# T10 도구 명세 구성

### T10.01 처리 함수에서 명세 생성

**구현.** 서버는 도구 함수 45개에 `@mcp.tool()`만 붙이고 이름, 설명, 입력 schema를 따로 적지 않는다 [1].
MCP Python SDK 1.27.2의 FastMCP는 함수 이름을 도구 이름으로, docstring 전체를 설명으로, 함수 서명을 입력 schema로 쓴다 [2].
그래서 docstring의 `Args:`·`Returns:` 단락은 설명 글에 그대로 실리고 입력 schema의 인자에는 설명이 없다 [3].
반환형이 모두 `str`이라 FastMCP는 모든 도구에 `result` 문자열 하나를 담는 출력 schema를 붙인다 [3][4].
도구 annotation은 없고 `tools/list_changed`도 알리지 않는다 [3].
서버는 리소스와 프롬프트를 두지 않고 도구를 쓰는 절차는 FastMCP를 만들 때 준 서버 지침 `instructions`로 초기화 응답에 싣는다 [3][5].
실행 설정이나 클라이언트에 따라 명세를 바꾸는 코드는 없다 [1].

**한계.** 도구 15개는 설명이 알리는 동작과 처리 함수의 동작이 다르다.
`analyze_sshd_config`의 설명은 약한 `Ciphers`·`MACs`·`HostKeyAlgorithms` 설정을 표시한다고 적지만 처리 함수가 검사하는 지시어는 `PermitRootLogin` 등 6개이고 이 세 지시어는 없다 [6][7].

`analyze_package_logs`의 설명은 `/var/log/apt/term.log`를 읽고 인기 패키지와 비슷한 이름(typosquat)의 npm 패키지를 표시한다고 적는다 [8].
처리 함수는 `term.log`를 읽지 않고 npm 기록도 읽지 않으며 npm 이름 목록 `_NPM_TYPOSQUATS`는 정의만 있고 쓰이지 않는다 [9][10].

`build_timeline`의 설명은 `auth.log`, `access.log`, `.bash_history`를 증거 폴더 아래 어디에 있든 찾는다고 적는다 [11].
처리 함수는 `auth.log`·`journal.jsonl`·`access.log`를 `evidence_root` 바로 아래에서만, `.bash_history`를 `fs/root`와 `fs/home/*` 아래에서만 찾는다 [12].

`assess_coverage`의 설명은 아직 어느 관련 도구도 실행되지 않은 아티팩트를 공백으로 알린다고 적는다 [13].
처리 함수는 관련 도구의 이름이 `audit.json`에 한 번이라도 있으면 그 아티팩트를 살펴본 것으로 정하고 그 호출이 어느 경로를 대상으로 했는지는 보지 않는다 [14].
같은 설명은 `bulk_ioc_lookup`에 넣지 않은 IOC를 공백으로 알린다고 적지만 처리 함수는 `bulk_ioc_lookup`이 기록에 한 번이라도 있는지만 보고 IOC마다 조회했는지는 보지 않는다 [13][15].

`get_audit_trail`의 설명은 이 세션의 모든 도구 호출 기록을 돌려준다고 적는다 [16].
처리 함수가 읽는 `audit.json`은 서버를 다시 실행해도 앞선 실행의 항목을 그대로 두고 뒤에 이어 쓴다 [17][18].
경로 검사에서 거부된 호출처럼 결과 요약을 남기기 전에 돌아가는 호출과 `get_audit_trail` 자신의 호출은 이 파일에 항목이 없다 [19][20].

`analyze_memory_network`·`analyze_memory_summary`·`analyze_memory_malfind`의 설명은 `linux.netstat`이나 `linux.malfind`를 실행한다고 적지만 처리 함수는 `linux.sockstat.Sockstat`과 `linux.malware.malfind.Malfind`를 먼저 실행한다 [21][22][23].

`correlate_memory_and_disk`의 설명은 `find_persistence`의 커널 모듈 검사와 컨테이너 검사를 함께 실행한다고 적지만 처리 함수는 커널 모듈 검사 `scan_kernel_modules`만 부른다 [24].

`auth_failed_logins`의 설명은 한 계정을 여러 IP가 노리는 password spraying을 드러낸다고 적지만 처리 함수는 실패 시도를 IP별로만 묶는다 [25].

`analyze_systemd_unit`의 설명은 `[Unit]`·`[Service]`·`[Install]` 절을 해석하고 드문 install target을 표시한다고 적지만 처리 함수는 `ExecStart` 줄과 `User` 값만 본다 [26].

`analyze_journal`의 설명은 pam 사건과 서비스 제어를 분류한다고 적지만 처리 함수에는 pam 분류가 없고 서비스는 시작 메시지만 센다 [27].
서비스 중지 메시지를 읽는 정규식 `_SYSTEMD_STOPPED`는 정의만 있고 쓰이지 않는다 [27].

`find_ai_signatures`의 설명은 `~/.config/claude`를 에이전트 실행 흔적으로 찾는다고 적지만 처리 함수는 홈 폴더 바로 아래의 `.claude`·`.anthropic`·`.openai`만 본다 [28].

`analyze_container_artifacts`의 설명은 TLS 없는 daemon TCP 수신을 표시한다고 적지만 처리 함수는 TLS 설정과 관계없이 루프백이 아닌 TCP 수신 주소를 모두 표시한다 [29].

`bulk_ioc_lookup`의 설명은 IOC마다 category·tags·confidence·source를 싣는다고 적지만 도메인 줄에는 source가 없고 해시 줄에는 confidence와 source가 없다 [30].

### T10.03 묶음 도구의 연산별 인자를 schema가 구분하지 않음

**구현.** `verify_finding`은 확인할 주장 유형 `claim_type`과 그 유형의 인자를 담은 JSON 글 `params`를 받는다 [31].
서버는 `claim_type`으로 확인 함수 8개 가운데 하나를 골라 `params`를 넘긴다 [31].
입력 schema는 두 인자를 모두 문자열로만 알리고 유형마다 다른 인자(`log_path`·`ip`·`fs_root`·`category` 등)는 설명 글에만 있다 [3][32].
`finalize_report`도 주장 목록을 JSON 글 `claims_json` 하나로 받고 주장마다 `type`으로 같은 확인 함수를 골라 그 주장의 필드를 넘긴다 [33].
이 도구의 입력 schema도 `claims_json`을 문자열로만 알린다 [3].
