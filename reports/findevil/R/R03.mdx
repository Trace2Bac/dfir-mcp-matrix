# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 도구 함수가 처리하지 않은 예외에만 적용된다.
MCP Python SDK 1.27.2의 FastMCP는 도구 함수의 예외를 `ToolError`로 바꾸고 하위 서버의 처리기는 이 예외를 `isError`가 참인 결과로 돌려준다 [1].
`_run_tool`은 `subprocess.run`이 내는 시간 초과 `TimeoutExpired`와 실행 파일이 없을 때의 `FileNotFoundError`를 처리하지 않으므로 이 두 경우는 `isError` 결과가 된다 [2].
auth 도구는 증거 파일을 읽을 때 `FileNotFoundError`와 `ValueError`만 처리하므로 권한 오류 같은 다른 `OSError`가 `isError` 결과가 된다 [3].
`verify_finding`은 `params`가 JSON 객체가 아닌 목록이면 검증 함수가 `dict` 메서드를 부르다 예외가 나 `isError` 결과가 된다 [4].
`_run_tool`은 명령 출력을 `text=True`로 받고 디코딩 오류 처리 방식을 정하지 않는다 [2].
그래서 명령 출력에 UTF-8로 읽히지 않는 바이트가 있으면 `UnicodeDecodeError`가 나 `isError` 결과가 된다 [5].
`log_search`가 고른 기록 줄, `strings_extract`의 8비트 문자열, `list_evidence`·`file_info`가 출력하는 파일 이름이 이런 바이트를 담을 수 있다 [5].
이 결과의 글은 `Error executing tool <도구>:` 뒤에 예외 문장을 붙인 것이고 실패 종류를 가르는 값은 없다 [1].

서버 코드가 스스로 판단한 실패와 찾지 못함은 `isError`가 거짓인 보통 응답의 문장으로 알린다 [6].
일치 0건은 `No failed login attempts found in the log.` 같은 문장으로만 알린다 [7].
Volatility가 시간 제한 600초를 넘기면 서버는 종료 코드 124와 `timed out` 문장을 만들어 실패 문장으로 돌려주고 시간 초과를 가르는 필드는 없다 [8].
`analyze_memory_summary`처럼 여러 플러그인을 차례로 실행하는 도구도 플러그인마다 성공과 실패를 싣지 않는다 [9].
도구 함수는 FastMCP 요청 문맥을 받지 않고 진행 알림을 보내지 않는다 [10].

**한계.** 서버가 처리한 실패는 모두 `isError`가 거짓인 응답으로 나간다 [6].
증거 폴더 밖 경로의 `Error: Access denied`, `File not found`, `Not a directory`, `INVALID params JSON`, Volatility의 `vol failed (rc=N)`과 기호 표가 없다는 안내가 그런 응답이다 [6][8].
이 응답과 성공 응답은 글의 문장으로만 갈린다.

`_run_tool`은 명령의 종료 코드를 응답 값으로 싣지 않고 0이 아니면 표준 출력 뒤에 `[STDERR]:`와 표준 오류를 붙일 뿐이다 [2].
`log_search`는 이렇게 만든 글이 공백뿐일 때만 `No matches found` 문장을 돌려준다 [11].
`grep`은 일치하는 줄이 없으면 종료 코드 1로 끝나므로 `_run_tool`의 글은 `[STDERR]:` 한 줄이 된다 [2][12].
그래서 일치가 없는 검색의 응답은 찾지 못했다는 문장이 아니라 빈 `[STDERR]:` 한 줄이다 [11][12].
`log_search`는 `grep`에 `-a`를 넘기지 않으므로 NUL 바이트가 든 파일은 `grep`이 이진 파일로 판정한다 [11].
이 경우 `grep`은 일치하는 줄을 표준 출력에 싣지 않고 종료 코드 0으로 끝나 서버는 `No matches found` 문장을 돌려준다 [13].
그래서 일치하는 줄이 있는 기록에 대해 찾지 못했다는 응답이 나간다 [13].

`analyze_memory_summary`는 플러그인이 실패하면 그 플러그인의 결과를 빈 목록으로 두고 실패를 응답에 싣지 않는다 [9].
Volatility 실행 파일이 없으면 모든 플러그인이 종료 코드 127로 실패하고 기호 표 실패로 보지 않는다 [14].
이때 응답은 프로세스·소켓·모듈·malfind 영역을 모두 0으로 적고 덤프가 내부적으로 일관되며 메모리 침해 지표가 없다는 판정 문장을 싣는다 [9][15].
`_run_vol_plugin`은 Volatility가 종료 코드 0으로 끝났는데 출력을 JSON으로 읽지 못하면 행을 빈 목록으로 둔다 [16].
이 경우 각 메모리 도구는 행이 없는 성공 응답을 돌려준다 [16].

증거 파일을 읽지 못한 실패를 결과 없음이나 정상 판정으로 돌려주는 경로가 여러 도구에 있다.
`_read_safe`는 파일을 읽지 못하면 `[unreadable: …]` 문자열을 파일 내용처럼 돌려준다 [17].
그래서 `analyze_authorized_keys`는 이 문자열을 해석하지 못한 키 1개로 싣고 `analyze_sudoers`는 규칙이 없다는 응답을, `analyze_sshd_config`는 위험한 설정이 없다는 응답을 돌려준다 [17][18].
`analyze_bash_history`는 읽기 실패를 변조 징후 목록에 적고 기록 파일이 비었다는 문장을 붙인다 [19].
`verify_package_integrity`는 MD5를 계산하지 못한 파일을 비교한 파일 수에 넣고 결과에서 빼며 읽지 못한 `.md5sums` 파일은 알리지 않고 건너뛴다 [20].
이 경우에도 다른 불일치가 없으면 패키지 파일 변조를 배제한다는 판정 문장을 싣는다 [20].
`find_webshells`·`find_ai_signatures`와 컨테이너 설정 검사는 읽지 못한 파일을 발견사항이 없는 파일과 같게 다룬다 [21].
`baseline_diff`는 지금 읽지 못한 파일을 현재 상태에서 빼므로 기준선에 있던 그 파일을 없어진 파일로 싣는다 [22].
그 파일이 `critical` 경로이면 응답의 판정은 `LIKELY COMPROMISE`가 된다 [22].

환경변수 `FINDEVIL_FAULT_RATE`가 0보다 크면 `_run_tool`은 그 비율로 명령을 실행하지 않고 시간 초과를 흉내 낸 `[STDERR]:` 문장을 돌려준다 [23].
이 응답도 `isError`가 거짓인 보통 응답이다 [23].

def _read_safe(path: Path, max_bytes: int = 65536) -> str:
    """Read a file with size cap and error tolerance."""
    try:
        with path.open("rb") as f:
            data = f.read(max_bytes)
