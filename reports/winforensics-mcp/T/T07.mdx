# T07 도구 부재 처리

### T07.01 실행 전 도구·참조 자료 가용성 검사

**구현.** 이 방식은 선택 의존성 라이브러리, Detect It Easy 실행 파일 `diec`, SIDR 실행 파일, Windows API 정의 DB, 저장소에 들어 있는 YARA 규칙을 쓰는 도구에 적용된다 [1][2][3][4][5].
파서 모듈은 불러올 때 `pefile`·`yara`·`vt`·`scapy`·`pyscca`·`pyesedb`·`mft`·`pylnk3`·`winrm`을 `import`로 시험하고 결과를 `*_AVAILABLE` 플래그에 둔다 [1].
`list_tools`는 플래그가 거짓인 라이브러리를 쓰는 도구를 목록에 올리지 않는다 [6].
`_execute_tool`은 그 도구가 불리면 플래그를 다시 보고 실행하지 않는다 [7].
`diec`는 모듈을 불러올 때 `PATH`와 정해 둔 설치 경로 6곳에서 찾고 찾지 못하면 `DIE_AVAILABLE`을 거짓으로 둔다 [2].
`windows_search_parse`는 SIDR 후보 경로마다 실행 권한이 있는 파일인지 확인한다 [3].
고른 실행 파일은 `--version`으로 시험 실행하고 종료 코드가 0이 아니거나 출력에 `0.9.2`가 없으면 분석을 실행하지 않는다 [8].
`api_lookup`·`api_search_category`는 API 정의 DB 파일 `data/api_definitions.db`가 있는지 먼저 확인한다 [4].
`yara_scan_file`·`yara_scan_directory`는 규칙 경로를 받지 않으면 패키지의 `rules` 폴더에 `.yar` 파일이 있는지 확인한다 [5].

**한계.** `diec` 확인은 모듈을 불러올 때 한 번만 한다 [2].
서버가 실행되는 중에 `diec`가 지워지면 `die_analyze_file`은 실행 파일을 찾지 못한 예외를 `Failed to run diec` 문구로 돌려준다 [9].

### T07.02 대체 없는 실패 처리·도구 부재 알림

**구현.** 이 방식은 선택 의존성이 필요한 도구, `diec`를 쓰는 도구, SIDR을 명시하거나 대체 라이브러리도 없는 `windows_search_parse`, API 정의 DB를 쓰는 도구에 적용된다 [7][10][11][4].
라이브러리가 없으면 `_execute_tool`은 다른 경로로 바꾸지 않고 `pefile library not installed. Install with: pip install pefile`처럼 라이브러리 이름과 설치 명령을 적은 `error`를 돌려준다 [7].
`diec`가 없으면 `diec (Detect It Easy CLI) not found`와 내려받을 주소를 적은 `error`를 돌려준다 [10].
실행 확인에서 `diec`가 없는 환경으로 `die_analyze_file`을 부르면 목록에 없는 도구인데도 이 문구가 응답으로 왔다 [12].
`windows_search_parse`는 사용자가 `sidr_path`를 주었는데 그 파일이 없거나, 찾은 SIDR이 없고 `pyesedb`도 없으면 분석하지 않는다 [11].
이때 응답의 `error`는 확인한 경로, `scripts/build_sidr.sh`로 빌드하거나 `WINFORENSICS_SIDR_PATH`를 정하라는 안내, `No backend was run` 문장을 싣는다 [11][12].
SIDR 버전이 다르면 `SIDR 0.9.2 is required; observed …` 문구로 실패를 알린다 [8][12].
`api_lookup`·`api_search_category`는 DB 파일이 없으면 그 경로와 DB를 먼저 만들라는 안내를 `error`로 돌려준다 [4].
`investigate_execution`·`hunt_ioc`·`investigate_user_activity`는 라이브러리가 없는 출처를 `available: false`와 `libscca-python not installed` 같은 `error`로 응답의 출처 목록에 싣는다 [13].

**한계.** 이 알림들은 MCP 오류 결과가 아니라 `isError`가 거짓인 정상 응답 글이다 [12].
EVTX 라이브러리가 없을 때의 문구는 `python-evtx library not installed. Install with: pip install evtx`이다 [14].
서버가 먼저 쓰는 라이브러리는 `evtx`이고 `python-evtx`는 그 라이브러리가 없을 때 쓰는 다른 라이브러리이므로 문구의 이름과 설치 명령이 가리키는 라이브러리가 다르다 [14].

### T07.03 알림 없는 대체 실행

**구현.** 이 방식은 EVTX를 읽는 모든 도구에 적용된다 [14].
EVTX 파서 모듈은 불러올 때 Rust로 만든 `evtx` 라이브러리를 먼저 시험하고 없으면 순수 Python 라이브러리 `python-evtx`의 `Evtx`를 시험한다 [14].
레코드를 읽을 때 `evtx`가 있으면 그 라이브러리의 JSON 출력을, 없으면 `Evtx`의 XML 출력을 사건으로 바꾼다 [15].
EVTX 도구의 응답과 사건에는 어느 라이브러리로 읽었는지 적는 필드가 없다 [15].
`pyproject.toml`의 필수 의존성에는 `evtx`가 있고 `python-evtx`는 없다 [16].
그래서 이 대체는 `evtx`가 설치되지 않고 `python-evtx`가 따로 설치된 환경에서만 일어난다 [14][16].

**한계.** 두 라이브러리 경로는 같은 레코드를 다른 꼴의 사건으로 만든다 [15].
`python-evtx` 경로는 이름 없는 `Data` 요소를 `Data_0` 같은 키로 만들고 `evtx` 경로에는 이 처리가 없다 [17][18].
`evtx` 경로는 `EventData`의 문자열이 아닌 값을 문자열로 바꾼다 [18].
캐시에 두는 레코드 원문도 한쪽은 JSON이고 다른 쪽은 XML이어서 원문 문자열에 대조하는 `contains`의 결과가 달라질 수 있다 [15][19].
대체 경로는 실행하지 않았고 이 차이는 코드로만 확인했다.

### T07.04 실행 환경별 경로 분기

**구현.** 이 방식은 `windows_search_parse`의 SIDR 선택과 DiE 도구의 `diec` 선택에 적용된다 [3][2].
`windows_search_parse`는 `sidr_path`를 받으면 그 경로만 본다 [3].
받지 않으면 환경변수 `WINFORENSICS_SIDR_PATH`, 저장소의 `.tools/sidr`(ARM64)나 `.tools/sidr_x86`(x86_64), `PATH`의 `sidr` 차례로 보고 실행 권한이 있는 첫 파일을 쓴다 [3].
저장소의 실행 파일은 `platform.machine()`이 `aarch64`·`arm64`이면 `sidr`, `x86_64`·`amd64`이면 `sidr_x86`을 고르고 그 밖의 아키텍처에서는 후보에서 빠진다 [3].
응답은 확인한 경로 목록을 `checked_sidr_locations`에, 실행한 파일의 경로와 SHA-256을 `backend_metadata`에 싣는다 [11][20].
실행 확인에서 x86_64 WSL로 경로를 주지 않고 부르면 `.tools/sidr_x86`이 골라지고 그 경로가 두 필드에 실렸다 [12].
`diec`는 `PATH`를 먼저 보고 없으면 `/usr/bin/diec`, `/usr/local/bin/diec`, `/opt/die/diec`, `/opt/detect-it-easy/diec`, `~/.local/bin/diec`, `~/DIE/diec` 차례로 실행 파일을 찾는다 [2].
DiE 도구의 응답에는 고른 `diec`의 경로가 없다 [21].

### T07.05 대체 사실을 응답·기록에 표시

**구현.** 이 방식은 `windows_search_parse`에 적용된다 [11].
`sidr_path`를 받지 않았고 SIDR 후보 경로에 실행 파일이 없으며 `pyesedb`가 있으면 서버는 `pyesedb`로 `PropertyStore` 표를 직접 읽는다 [11][22].
이때 응답의 `backend`는 `pyesedb`이고 SIDR로 읽으면 `sidr`이다 [22][20].
`checked_sidr_locations`에는 SIDR을 찾으려고 확인한 경로가 남는다 [11].
도구 설명도 SIDR이 없으면 부분 대체 경로를 쓴다고 적는다 [23].

**한계.** 실행 확인에서 대체 경로가 ESE 형식이 아닌 파일을 읽으면 응답의 `error`에 여는 단계의 오류가 아니라 `pyesedb_file_close: unable to close file` 문구가 실렸다 [12].
`_fallback_rows`는 `open`이 실패해도 `finally`에서 `close`를 부르고 `close`가 낸 예외가 앞선 예외를 대신한다 [22].

### T07.06 대체에 따른 검증·입력 범위 변화 표시

**구현.** 이 방식은 `windows_search_parse`의 `pyesedb` 대체 경로에 적용된다 [22].
대체 경로는 시작할 때 `complete`와 `content_filter_complete`를 거짓으로 둔다 [22].
진단 목록 `diagnostics`의 첫 줄에 긴 값과 압축된 검색 내용을 읽지 못하고 일치 0건이 결론이 되지 않는다는 문장을 싣는다 [22].
읽지 못한 긴 값의 수는 `unsupported_long_values`에 센다 [22].
`System_Search_AutoSummary` 열은 압축되어 있을 수 있어 대체 경로가 읽지 않는다 [22].
실행 확인에서 대체 경로로 실행하면 `complete`와 `content_filter_complete`가 모두 거짓이었고 위 문장이 진단 첫 줄에 실렸다 [12].

### T07.08 일부 제외 후 계속 실행

**구현.** 이 방식은 YARA 규칙을 모으는 단계, 여러 출처를 읽는 상관 분석 도구와 `build_timeline`, `hunt_ioc_pack`의 PCAP 검사, `api_analyze_imports`의 보강 단계, `ioc_pack_list`에 적용된다 [24][13][25][26][27][28].

`yara_scan_file`·`yara_scan_directory`와 `hunt_ioc`의 YARA 검사는 규칙 파일을 모을 때 정해 둔 이름의 파일을 뺀다 [24][29].
서버는 규칙 파일 이름 15개를 `EXTERNAL_VAR_FILES`에 정해 둔다 [30].
코드 주석은 이 파일들이 `filename`·`filepath`·`extension` 같은 외부 변수를 써서 THOR나 LOKI 없이는 쓸 수 없다고 적는다 [30].
`compile_rules`는 이름이 이 목록에 있는 파일을 컴파일 목록에서 빼고 나머지를 `yara.compile`에 넘긴다 [24].
규칙 내용이 외부 변수를 쓰는지는 보지 않고 파일 이름만 대조한다 [30].
남은 파일이 하나도 없을 때만 `No valid YARA rules found` 오류를 낸다 [24].
저장소의 규칙 파일 732개 가운데 14개의 이름이 이 목록에 들어 있다 [31].
그래서 기본 규칙으로 검사하면 718개만 쓰인다 [31].
`yara_list_rules`는 파일마다 `skipped`를 싣고 뺀 파일에는 `skip_reason`을 붙이며 쓸 수 있는 파일 수를 `usable_files`에 싣는다 [32].
규칙 폴더의 README도 뺀 파일 이름과 이유를 적는다 [33].

`investigate_execution`·`hunt_ioc`·`investigate_user_activity`는 아티팩트 출처마다 그 출처를 읽는 라이브러리의 플래그를 보고 플래그가 거짓이면 그 출처만 읽지 않고 나머지 출처로 판정한다 [13].
이 도구들은 읽지 않은 출처를 `available: false`와 오류 문구로 응답의 출처 목록에 싣는다 [13].
`build_timeline`은 `mft`, `pyscca`, `evtx` 라이브러리가 없으면 그 출처에서 사건을 만들지 않고 나머지 출처의 사건으로 응답한다 [25].
`hunt_ioc_pack`은 `scapy`가 없으면 `scan_pcap`이 참이어도 PCAP 검사를 건너뛰고 나머지 검사 결과로 응답한다 [26].
`api_analyze_imports`는 `enrich_from_db`가 참이어도 DB 파일이 없으면 보강 단계를 빼고 나머지 분석 결과를 돌려준다 [27].
`ioc_pack_list`는 `extra_paths`로 받은 묶음 파일이 없으면 그 경로를 빼고 나머지 묶음을 나열한다 [28].

**한계.** 다음 경로는 빼거나 건너뛴 사실을 그 실행의 응답에 싣지 않는다.

- `yara_scan_file`·`yara_scan_directory`의 응답에는 뺀 규칙 파일의 이름이나 수가 없고 도구 설명도 이 동작을 적지 않는다 [34][35].
- `build_timeline`은 라이브러리가 없어 사건을 만들지 못한 출처의 상태를 `processed`로 둔다 [25].
- `hunt_ioc_pack`은 건너뛴 PCAP 검사의 결과를 빈 목록으로 둔다 [26].
- `api_analyze_imports`는 보강을 뺀 응답에 `enrichment` 필드를 두지 않는다 [27].
- `ioc_pack_list`는 없던 경로를 응답에 싣지 않는다 [28].

이름이 `EXTERNAL_VAR_FILES`에 있으면 외부 변수를 쓰지 않는 규칙 파일도 빠진다 [30][36].
외부 변수를 쓰는 규칙이 목록에 없는 이름의 파일에 있으면 전체 컴파일이 실패하고 검사는 `error`로 끝난다 [36].
`yara_list_rules`는 폴더에서 `.yar` 파일만 나열하므로 검사에 쓰이는 `.yara` 파일은 목록에 나오지 않는다 [32][24][36].
`yara_list_rules`는 namespace가 같은 규칙 파일도 모두 `skipped`가 거짓인 항목으로 싣고 `usable_files`에 센다 [32].
`compile_rules`는 namespace를 키로 규칙 파일을 모으므로 namespace가 같은 파일 가운데 하나만 컴파일한다 [24].
그래서 `usable_files`는 실제로 컴파일되는 파일 수보다 클 수 있다 [32][24].

```python
def _find_diec() -> Optional[str]:
    """Find diec executable in PATH or common locations."""
    # Check PATH first
    diec_path = shutil.which("diec")
    if diec_path:
        return diec_path

    # Check common installation locations
    common_paths = [
        "/usr/bin/diec",
        "/usr/local/bin/diec",
        "/opt/die/diec",
        "/opt/detect-it-easy/diec",
        os.path.expanduser("~/.local/bin/diec"),
        os.path.expanduser("~/DIE/diec"),
    ]

    for path in common_paths:
        if os.path.isfile(path) and os.access(path, os.X_OK):
            return path

    return None


# Check if diec is available
_DIEC_PATH = _find_diec()
DIE_AVAILABLE = _DIEC_PATH is not None
```

```python
    machine = platform.machine().casefold()
```
