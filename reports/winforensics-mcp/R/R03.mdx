# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 서버 호출 처리기 `call_tool`과 MCP Python SDK 1.25.0의 입력 검사에 적용된다 [1][2].
`call_tool`은 EVTX·NTDS·보안 설명자 도구 12개에서 예외가 나면 `evtx_error_response`로 `isError`가 참인 결과를 돌려준다 [1][3].
이 결과의 글은 예외 문구를 800자 안에서 줄인 것이다 [3].
EVTX 질의의 `where`에 크기 비교를 주면 고른 사건 가운데 그 필드 값이 숫자 꼴이 아닌 사건이 하나라도 있을 때 질의 전체가 이 `isError` 결과로 끝난다 [1][4].
나머지 도구에서 예외가 나면 `call_tool`은 `{"error": "<예외 문구>"}` 글 블록 하나를 돌려준다 [1].
SDK는 목록에 오른 도구의 인자를 `inputSchema`로 검사하고 맞지 않으면 도구를 부르지 않고 `isError`가 참인 결과를 돌려준다 [2].
SDK는 서버 처리기가 돌려준 `CallToolResult`는 그대로, 글 블록 목록은 `isError`가 거짓인 결과로 내보낸다 [2].

여러 파서와 처리 분기도 실패를 결과 `dict`의 `error` 필드에 싣는다 [5].
선택 라이브러리가 없을 때, `diec`가 60초 안에 끝나지 않을 때, VirusTotal 조회가 실패할 때가 그런 경우다 [5].
NTDS 도구는 결과의 상태를 `status` 필드에 싣는다 [6].
보안 설명자 두 도구는 해석 상태를 `parse_status`에 `complete`·`partial`·`invalid`·`source_placeholder` 가운데 하나로 싣는다 [7].

**한계.** `isError`는 EVTX·NTDS·보안 설명자 도구 12개의 예외와 SDK 입력 검사 실패에만 쓰인다 [1][2].
나머지 62개 도구의 실패는 `isError`가 거짓인 결과로 나가고 `error` 필드로만 성공과 갈린다 [1][8].
목록에 없는 도구 이름도 SDK가 검사하지 않고 처리기로 넘기며 처리기는 `{"error": "Unknown tool: …"}`를 `isError`가 거짓인 결과로 돌려준다 [2][8][9].
`error` 필드는 문구만 담고 실패 종류를 가르는 값은 없다 [1][5].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 NTDS 도구, EVTX 질의, 오케스트레이터의 원천별 결과에 적용된다.
NTDS 계정 조회는 `status`를 `found`·`not_found`·`ambiguous`·`incomplete` 가운데 하나로, 도메인 조회는 `found`·`not_found`·`incomplete` 가운데 하나로 싣는다 [6][10].
읽기가 끝까지 되지 않았거나 스키마·데이터베이스 상태를 확인하지 못하면 찾지 못했더라도 `not_found`가 아니라 `incomplete`가 된다 [6][11].
EVTX 질의는 일치가 없으면 `events`가 빈 정상 결과를 돌려주고 파일을 읽지 못하면 `isError`가 참인 결과를 돌려준다 [1][12].
`hunt_ioc`는 원천마다 쓸 수 없음(`available` 거짓), 검색하지 않음(`searched` 거짓), 일치 없음(`found` 거짓), 예외(`error`)를 필드로 나눠 싣는다 [13].
`windows_search_parse`는 일치 0건을 `matched_records` 0으로, 실패를 `error`와 `complete` 거짓으로 싣는다 [14].
`disk_parse_mft`는 `entry_number`의 항목을 찾지 못하면 `error` 필드에 그 사실을 적은 결과를 돌려준다 [15].

이 구분이 없는 도구도 있다.
`registry_get_network`·`registry_get_usb_history`·`registry_get_system_info`는 키를 열거나 읽다가 예외가 나면 그때까지 모은 결과를 오류 표시 없이 돌려준다 [16][17].
SAM 하이브를 넘기자 `registry_get_usb_history`와 `registry_get_network`는 빈 목록을, `registry_get_system_info`는 모든 필드가 `None`인 결과를 오류 없이 돌려줬다 [18].
`browser_get_history`는 Firefox DB에 다운로드 주석 표가 없으면 오류 표시 없이 빈 다운로드 목록을 돌려준다 [19].
`disk_parse_usn_journal`은 `reason_filter`의 모르는 reason 이름을 무시하므로 모르는 이름만 주면 오류 없이 0건을 돌려준다 [20].
`disk_parse_amcache`는 항목을 읽거나 거르다 난 예외를 알리지 않고 그 항목을 건너뛴다 [21].
시간 조건에 `Z`나 오프셋이 붙으면 시간대 없는 키 시각과의 비교가 예외를 내므로 키 시각이 있는 항목이 모두 이렇게 빠지고 응답은 0건의 정상 결과가 된다 [21].
`time_range_start`를 `2000-01-01T00:00:00Z`로 주자 `disk_parse_amcache`는 247개를 읽고 0건을 오류 없이 돌려줬고 시간대 없이 주자 30건을 돌려줬다 [22].

**한계.** `hunt_ioc`의 요약 목록과 요약 문장은 예외가 난 원천을 일치가 없는 원천과 같이 다룬다 [23].
예외 결과도 `searched`가 참이고 `found`가 거짓이므로 `sources_searched_no_match`에 들어간다 [13][23].
`investigate_execution`의 요약 문장도 예외가 난 원천을 "증거를 찾지 못한" 원천으로 적는다 [24].
손상된 `Amcache.hve`로 두 도구를 부르자 원천 항목에는 `error`가 실렸지만 요약은 `hunt_ioc`가 "not found in any of the 1 sources searched", `investigate_execution`이 "No execution evidence found … in Amcache"였다 [25].
`hunt_ioc`의 EVTX 원천은 파일을 읽다가 예외가 나면 그 파일을 건너뛰고 오류를 싣지 않는다 [26].
그래서 EVTX 파일을 모두 읽지 못한 경우도 일치 없음과 같은 결과가 된다 [26].
`build_timeline`의 EVTX 원천은 늘 사건을 0건 만들고 상태를 `processed`로 적으므로 일치 없음과 처리 실패가 갈리지 않는다 [27][28].
`investigate_user_activity`의 브라우저 단계는 파서 결과에서 `visits`를 읽지만 브라우저 파서가 돌려주는 키는 `history`다 [29].
그래서 방문 기록이 있어도 다운로드 기록이 없으면 브라우저 원천의 `found`가 거짓이 된다 [29].
RecentDocs 단계는 레지스트리 값의 `data`가 `bytes`일 때만 파일 이름을 꺼내지만 레지스트리 파서는 `bytes` 값을 문자열로 바꿔 싣는다 [30].
그래서 RecentDocs 원천은 값이 있어도 `found`가 거짓으로 남는다 [30].
방문 기록 3건만 있는 Chrome 형식 DB로 부르자 브라우저 원천은 `found`가 거짓이었고 요약은 `No user activity found in Browser`였다 [31].
RecentDocs 값이 11개 있는 테스트 하이브에서 RecentDocs 단계는 오류 없이 `found` 거짓을 돌려줬다 [31].

### R03.03 입력별 성공·실패·생략 목록

**구현.** 이 방식은 여러 원천이나 입력을 한 번에 처리하는 도구에 적용된다.
`hunt_ioc`는 원천마다 결과 항목을 싣고 일치가 있는 원천·검색했지만 일치가 없는 원천·쓸 수 없는 원천을 이름 목록으로 나눠 싣는다 [13][23].
검색하지 않은 원천(YARA를 켜지 않은 경우, 그 원천이 지원하지 않는 IOC 종류)은 `searched` 거짓과 `note`로 표시한다 [13].
`investigate_execution`은 Prefetch·Amcache·SRUM마다 `available`·`found`·`error`를 싣는다 [24].
`build_timeline`은 원천마다 `processed`·`not found`·`error: …` 상태를 `sources_info`에 싣는다 [27].
`remote_collect_artifacts`는 수집한 아티팩트마다 `success`·`local_path`·`size_bytes`·`error`를 싣는다 [32].
`disk_parse_prefetch`의 폴더 결과는 파싱하지 못한 파일마다 경로와 오류를 `errors`에 싣는다 [33].
`user_parse_lnk_files`의 폴더 결과도 읽지 못한 파일마다 경로와 오류를 `errors`에 싣는다 [34].
`disk_parse_srum`은 `table`이 `all`이면 한 표를 읽다 난 예외를 그 표의 `error`에 싣고 다른 표의 결과는 함께 돌려준다 [35].
`registry_get_persistence`는 하이브마다 읽지 못하면 `software_error`·`winlogon_error`·`ntuser_error`·`system_error`를 따로 싣고 읽은 하이브의 결과는 함께 돌려준다 [36].

**한계.** `build_timeline`은 원천의 사건 생성기가 예외를 스스로 처리해 아무것도 내지 않아도 상태를 `processed`로 둔다 [27][28].
`yara_scan_directory`는 파일별 오류를 앞 10개만 싣고 오류의 전체 수는 싣지 않는다 [37].
`user_parse_lnk_files`의 `recent_only` 경로는 읽지 못한 LNK 파일을 알리지 않고 건너뛴다 [38].

### R03.04 시간 초과·부분 완료 표시

**구현.** 이 방식은 읽기 상한이 있는 EVTX·NTDS 도구, `evtx_export`, `windows_search_parse`, `pcap_get_stats`, `disk_parse_srum`, `registry_query`, 보안 설명자 도구에 적용된다 [11][12][14][39][40][41][42][7].
EVTX 질의는 파일 끝까지 읽었는지 `scan_complete`, 읽기 상한에 닿았는지 `scan_limit_hit`, 파싱하지 못한 레코드 수 `parse_errors`를 싣는다 [12].
`evtx_export`는 읽기 상한, 행 상한 `max_rows`, 파싱 오류, 시간 조건 오류가 없을 때만 `export_complete`를 참으로 둔다 [39].
NTDS 도구는 `scan_complete`·`schema_complete`·`database_clean`이 모두 참이고 파싱 오류가 없을 때만 `results_complete`를 참으로 둔다 [11].
`windows_search_parse`는 SIDR 실행이 시간 제한 `timeout`을 넘거나 실패하면 `error`를 싣고 `complete`를 거짓으로 둔다 [14].
SIDR 기록에 오류나 경고가 있거나, 데이터베이스가 정상 종료되지 않은 상태이거나, 대체 파서를 썼을 때도 `complete`를 거짓으로 둔다 [14][43].
`pcap_get_stats`는 패킷 수가 `max_packets`를 넘으면 `truncated`를 참으로 두고 분석한 패킷 수를 싣는다 [40].
`evtx_ntlm_operational_summary`는 시각을 읽지 못한 사건 수를 `timestamp_errors`에 싣고 그런 사건이 있거나 읽기가 끝까지 가지 못하면 `time_bounds_complete`를 거짓으로 둔다 [44].
`windows_search_parse`는 시간 조건이 있을 때 기준 시각을 읽지 못해 뺀 행의 수를 `time_filter_unreadable`에 싣는다 [45].
`disk_parse_srum`은 표를 끝까지 읽었는지 `scan_complete`에 싣고 집계에 읽기 오류, 시각 오류, 값 없는 행이 없을 때만 `aggregation.complete`를 참으로 둔다 [41].
`registry_query`는 읽지 못한 키와 값의 수를 `read_errors`에 싣는다 [42].
보안 설명자 두 도구는 ACE 상한으로 일부를 뺐거나 해석하지 않는 ACE가 있으면 `parse_status`를 `partial`로, `parse_complete`를 거짓으로 둔다 [7].

읽지 못한 부분을 알리지 않는 도구도 있다.
`registry_search`와 `registry_get_key`는 읽지 못한 키와 값을 알리지 않고 건너뛴다 [46].
`registry_query`가 읽기 오류 4,537건을 실은 Windows 10 SYSTEM 하이브 표본에서 두 도구의 응답에는 읽기 오류 표시가 없었다 [47].
`disk_parse_usn_journal`은 길이가 맞지 않거나 풀지 못한 레코드를 건너뛰고 그 수를 싣지 않는다 [48].

**한계.** 같은 `MAX_SCAN_EVENTS`(100,000개) 읽기 상한을 쓰는 `evtx_get_stats`·`evtx_attack_summary`·`hunt_ioc`·`build_timeline`의 EVTX 경로는 상한에 닿았는지 싣지 않는다 [49].
이 경로들은 파싱하지 못한 레코드 수도 싣지 않으므로 `evtx_get_stats`의 `total_events`는 파싱에 성공한 사건만 센 값이다 [49][50].
`die_analyze_file`·`die_scan_directory`의 `diec` 시간 초과는 `error` 문구로만 알린다 [5].
