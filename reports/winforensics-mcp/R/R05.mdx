# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 이 방식은 EVTX 질의 도구, NTDS 도구, `windows_search_parse`, YARA 도구, 오케스트레이터와 `hunt_ioc_pack`에 적용된다 [1][2][3][4][5].
`evtx_search`·`evtx_security_search`·`evtx_correlate_logon_id`·`evtx_ntlm_operational_summary`는 응답 머리에 읽은 파일의 실제 경로, 크기, 수정 시각을 `source`로 싣는다 [1].
NTDS 도구 4개는 `source`에 NTDS 파일의 실제 경로, 크기, 수정 시각과 이 세 값 등으로 만든 해시 `source_ref`를 싣는다 [2].
`windows_search_parse`는 `source`에 모델이 준 EDB 경로를 싣는다 [3].
`yara_scan_file`은 결과에 검사한 파일의 경로 `file`을 싣고 `yara_scan_directory`는 일치한 파일마다 이 결과를 싣는다 [4].
`investigate_execution`과 `hunt_ioc`는 출처마다 읽은 Prefetch 폴더나 아티팩트 파일의 경로를 `path`에 싣는다 [5].
`build_timeline`은 출처마다 읽은 파일이나 폴더의 경로를 `sources_info`에 싣는다 [6].
`hunt_ioc_pack`은 일치 항목마다 모델이 준 폴더 기준의 상대 경로를 `path`에 싣는다 [7].

레지스트리 도구는 하이브 안의 키 경로만 싣고 하이브 파일의 경로를 싣지 않는다 [8].
`evtx_attack_summary`는 사건마다 시각과 고른 칸만 TSV 한 줄로 싣고 파일 경로와 레코드 번호를 싣지 않는다 [9].

### R05.03 레코드 키·번호

**구현.** 이 방식은 EVTX, NTDS, MFT, USN, 레지스트리, Windows Search, PCAP 검색 도구에 적용된다.
EVTX 질의 도구는 행마다 이벤트 레코드 번호 `EventRecordID`를 싣는다 [10].
`compact`로 기본 필드를 고를 때도 `EventRecordID`가 포함된다 [10].
같은 행에 서버가 만든 `event_ref`도 붙는다 [11].
`event_ref`는 원본 파일의 경로·크기·시각 등으로 만든 해시와 파일 안 레코드 차례 번호를 담은 값이다 [11].
`evtx_get_event`는 이 값의 해시가 지금 파일과 같을 때만 그 차례의 레코드를 다시 읽는다 [12].
NTDS 도구는 계정과 신뢰 항목마다 datatable의 행 키 `dnt`를 싣는다 [13].
`disk_parse_mft`는 항목마다 MFT 번호 `entry_id`와 순번 `sequence`를 싣고 `disk_parse_usn_journal`은 레코드마다 `usn`과 파일 참조 번호를 싣는다 [14].
레지스트리 도구는 값마다 그 값이 있는 키 경로 `key_path`를 싣는다 [8].
`registry_get_usb_history`는 USBSTOR 장치마다 장치 instance 경로 `device_instance_path`를, 그 장치에 이은 WPD 항목마다 하이브 안의 키 경로 `key_path`를 싣는다 [15].
`windows_search_parse`는 SIDR나 대체 경로가 만든 행을 그대로 실으므로 Windows Search DB의 행 번호 `WorkId`가 전달된다 [3].
`pcap_search`는 일치한 패킷마다 패킷 번호 `packet_number`를 싣는다 [16].

**한계.** EVTX 질의에 `fields`를 주면 고른 필드만 실린다 [11].
그래서 `EventRecordID`를 고르지 않은 행에는 레코드 번호가 없고 `event_ref`만 남는다 [11].
`windows_search_parse`도 `fields`를 주면 고른 필드만 실으므로 `WorkId`를 고르지 않으면 행 번호가 빠진다 [3].
`ntds_get_object_by_sam`과 `registry_query`도 `fields`로 고른 필드만 실으므로 `dnt`나 `key_path`를 고르지 않으면 레코드 키가 빠진다 [17][8].
`evtx_ntlm_operational_summary`가 사건을 묶은 행에는 `EventRecordID`가 없고 `event_ref`는 묶음에서 파일 차례로 첫 사건 하나만 가리킨다 [18].
묶음의 나머지 사건은 `count`에만 반영된다 [18].

### R05.04 바이트·섹터·행 오프셋

**구현.** 이 방식은 YARA 도구와 `pcap_search`에 적용된다 [4][16].
`yara_scan_file`과 `yara_scan_directory`는 일치한 문자열 식별자마다 검사한 파일 안의 바이트 오프셋 `offset`을 싣는다 [4].
`pcap_search`는 패킷 번호와 함께 그 패킷 페이로드 안에서 일치한 위치 `match_offset`을 싣는다 [16].
`hunt_ioc_pack`의 파일 내용 일치 항목은 경로와 일치한 글, 앞뒤 글만 싣고 파일 안의 위치를 싣지 않는다 [7].

**한계.** YARA 결과는 문자열 식별자마다 첫 번째 일치의 오프셋만 싣고 식별자는 10개까지만 싣는다 [4].
그래서 같은 문자열이 파일에 여러 번 나오거나 일치한 식별자가 10개를 넘으면 나머지 위치는 응답에 없다 [4].

### R05.05 참조 지식 원문 출처

**구현.** 이 방식은 API 패턴 탐지, IoC 묶음 사냥, YARA 검사의 결과에 적용된다.
`api_detect_patterns`·`api_analyze_imports`는 탐지한 패턴마다 서버 코드의 패턴 표에서 고른 ATT&CK 기법 ID `mitre_id`를 싣는다 [19].
`apmx_detect_patterns`도 같은 표의 `mitre_id`를 패턴마다 싣는다 [20].
`hunt_ioc_pack`은 일치한 규칙마다 묶음 파일에 적힌 원문 주소 `reference`를 싣고 응답의 `pack`에 묶음의 원본 저장소 주소 `upstream`을 싣는다 [21].
YARA 도구는 일치한 규칙의 `meta`를 바꾸지 않고 싣는다 [4].
저장소에 함께 들어 있는 규칙 파일 대부분은 `meta`에 원문 주소나 출처 설명을 담은 `reference`를 둔다 [22].

다른 참조 지식 도구는 원문 위치를 싣지 않는다.
`evtx_explain_event_id`·`forensics_list_important_events`·`forensics_list_registry_keys`는 서버 설정 표의 설명만 싣는다 [23].
`die_get_packer_info`는 서버 코드에 적은 패커 설명을, `api_lookup`·`api_search_category`는 함께 들어 있는 API 정의 DB의 행을 싣는다 [23].
VirusTotal 조회 도구는 판정과 엔진 수를 싣고 VirusTotal 원문 주소를 싣지 않는다 [24].
참조 지식은 `mitre_id`·`reference`·`meta`처럼 증거 값과 다른 필드에 실리지만 코드와 도구 설명은 그 필드가 증거가 아니라고 밝히지 않는다 [4][19][21].
