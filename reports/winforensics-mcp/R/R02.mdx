# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 이 방식은 모든 도구의 응답에 적용된다.
서버는 응답 처리기 세 갈래에서 응답의 글자 수를 제한하고 도구마다 항목 수 상한을 둔다.
EVTX·NTDS·보안 설명자 도구 12개를 뺀 도구는 공통 처리기 `json_response`로 응답을 만든다 [1].
`json_response`는 직렬화한 JSON이 `MAX_RESPONSE_CHARS`(40,000자)를 넘으면 `_smart_truncate`로 줄인다 [1][2].
`_smart_truncate`는 `events`·`entries`·`results` 같은 정해 둔 배열 키 18개만 줄인다 [2].
먼저 각 항목 안의 `loaded_files`·`volumes`·`files`·`references` 배열을 20개로 줄이고 그래도 넘으면 최상위 배열의 뒤쪽 항목을 뺀다 [2].
최상위 배열은 앞에서부터 `TRUNCATE_KEEP_ITEMS`(10개) 이상을 남긴다 [2][3].

EVTX 질의·NTDS·보안 설명자 도구는 모델이 1,024~40,000 사이로 정하는 `max_chars`를 글자 상한으로 쓴다 [4].
기본값은 `compact` 질의와 상관·내보내기·NTLM 요약·NTDS·보안 설명자 도구가 12,000자, 나머지 EVTX 질의가 40,000자다 [4][5].
이 상한은 `CallToolResult` 전체를 JSON으로 바꾼 글자 수로 재고 행 단위로만 줄인다 [6].
`registry_query`는 40,000자를 넘으면 마지막 행부터 하나씩 뺀다 [7].
`windows_search_parse`는 한 페이지에 싣는 행의 JSON을 24,000자(`PAGE_BYTES`)까지만 담는다 [8].

항목 수 상한은 도구마다 `limit` 인자의 기본값으로 정한다 [3].
EVTX 질의 도구와 `registry_query`·`windows_search_parse`는 `limit`의 최댓값을 1,000으로 둔다 [4][9].
`evtx_attack_summary`·`registry_search`·`disk_parse_amcache`·`disk_parse_mft`·`build_timeline`을 비롯한 다른 도구는 `limit`에 최댓값을 두지 않는다 [9].
`disk_parse_amcache`·`disk_parse_mft`·`disk_parse_usn_journal`은 파일 차례로 읽다가 조건에 맞는 항목이 `limit`개가 되면 읽기를 멈추고 모은 항목을 시각 내림차순으로 정렬한다 [10].
오케스트레이터는 원천마다 상한을 따로 둔다.
`hunt_ioc`는 원천마다 일치 항목을 10개나 15개까지 싣고 EVTX는 파일마다 10건까지만 찾는다 [11].
`build_timeline`은 원천마다 `limit`을 원천 수로 나눈 값과 100 가운데 큰 값까지 사건을 모으고 EVTX 파일은 5개까지 읽는다 [12].

**한계.** `json_response`는 결과가 `dict`가 아니면 자르지 못하고 경고를 만들어도 응답에 붙이지 않는다 [1][2].
`evtx_list_files`처럼 `list`를 돌려주는 도구는 40,000자를 넘어도 그대로 나간다 [13].
EVTX 파일 400개가 있는 폴더에서 `evtx_list_files` 응답은 118,800자였다 [14].
정해 둔 배열 키가 없는 `dict`도 자르지 못하고 잘림 정보도 붙지 않는다 [2].
`evtx_attack_summary`는 TSV 글을 문자열 하나로 싣으므로 `limit`을 키우면 상한 없이 길어진다 [15].
2,000줄을 요청한 `evtx_attack_summary` 응답은 333,032자였고 `_truncation`이 없었다 [14].
최상위 배열을 10개까지 줄여도 40,000자를 넘으면 그 길이로 나간다 [2].

### R02.02 전체·반환 건수 표시

**구현.** 이 방식은 페이지를 나누는 도구의 응답과 공통 처리기가 배열을 줄인 응답에 적용된다.
EVTX 질의는 일치 수 `total_matched`, 반환 수 `returned`, 시작 위치 `offset`, 일치 수가 정확한지를 뜻하는 `total_matched_exact`를 싣는다 [16].
일치 수가 정확하지 않은 경우는 읽기 상한 `max_scan`에 닿았거나(`scan_limit_hit`), 파싱 오류가 있었거나, 시각을 읽지 못해 시간 조건에서 뺀 사건이 있을 때다 [16].
구조화 응답의 첫 글 블록은 반환한 수를 적고 일치 수가 정확하지 않으면 그 수가 하한이라고 적는다 [17].
예산으로 행을 줄인 응답은 `payload_clipped`를 참으로 두고 줄이기 전과 뒤의 글자 수를 `serialized_chars`·`returned_chars`에 싣는다 [6].
`registry_query`는 `total_matched`·`returned`와, 읽기 오류가 없었는지를 뜻하는 `total_matched_complete`를 싣는다 [18].
`disk_parse_prefetch`는 폴더의 파일 수, 일치 수, 반환 수를 싣는다 [19].
`windows_search_parse`는 읽은 행 수, 일치 수, 반환 수, 보고서 종류별 건수를 싣는다 [8].
`evtx_export`는 파일로 내보낸 행 수 `exported_rows`와 응답에 실은 미리 보기 행 수 `preview_returned`를 따로 싣는다 [20].
`ntds_get_object_by_sam`은 일치 수 `matched_count`와 반환 수를 싣고 후보를 10개로 자르면 `candidates_truncated`를 참으로 둔다 [21].
`json_response`가 배열을 줄이면 `_truncation.truncated_arrays`에 배열마다 원래 개수와 남긴 개수를 싣는다 [1][2].

**한계.** `_truncation`의 경고 문구는 오래된 자료를 남겼고 최신 자료가 빠졌을 수 있다고 적는다 [1].
`_smart_truncate`는 배열의 앞쪽을 남길 뿐 시각을 보지 않는다 [2].
`disk_parse_mft`·`disk_parse_usn_journal`·`build_timeline`처럼 시각 내림차순으로 정렬한 배열에서는 최신 항목이 남고 오래된 항목이 빠진다 [10][12].
시각 내림차순 배열 400개를 줄인 실행에서 남은 117개는 가장 최근 항목이었고 경고 문구는 위와 같았다 [14].
`_truncation.hint`는 `offset`으로 나머지를 읽으라고 적지만 `build_timeline`·`hunt_ioc`·`disk_parse_mft`처럼 `offset` 인자가 없는 도구에도 같은 문구가 붙는다 [1][9].

`disk_parse_amcache`·`disk_parse_mft`·`disk_parse_usn_journal`은 전체 일치 수를 싣지 않는다 [10].
대신 싣는 `total_entries`·`total_scanned`는 상한에 닿아 멈출 때까지 읽은 레코드 수다 [10].
`hunt_ioc`의 원천별 `match_count`는 상한으로 자른 수다 [11].
Amcache는 `parse_amcache`가 30개에서 멈춘 수이고 EVTX는 파일마다 10건으로 자른 수의 합이다 [11].
응답에는 이 수가 상한에 닿았는지 표시가 없다 [11].

### R02.03 페이지·커서 조회

**구현.** 이 방식은 EVTX 질의 4개, `ntds_get_trusts`, `registry_query`, Prefetch 폴더를 읽는 `disk_parse_prefetch`, `windows_search_parse`, APMX 호출 목록 도구에 적용된다 [7][8][16][19][22][23].
EVTX 질의 도구(`evtx_search`·`evtx_security_search`·`evtx_correlate_logon_id`·`evtx_ntlm_operational_summary`)는 남은 일치가 있으면 `next_offset`과 `next_cursor`를 싣는다 [16].
`next_cursor`는 질의 조건과 파일의 경로·크기·시각에서 만든 `query_ref`와 다음 위치를 담는다 [24].
서버는 다른 질의나 바뀐 파일에 쓴 커서를 거부한다 [24].
예산으로 행을 줄인 응답은 마지막으로 실은 행 다음 위치로 `next_cursor`를 다시 만든다 [6].
`ntds_get_trusts`도 같은 방식의 커서를 쓴다 [22].
`registry_query`는 행을 빼서 예산에 맞추면 `next_offset`을 그만큼 앞당긴다 [7].
`disk_parse_prefetch`와 `windows_search_parse`는 `offset` 인자를 받고 남은 결과가 있으면 `next_offset`을 싣는다 [8][19].
`apmx_get_calls`·`apmx_get_call_details`는 `offset` 인자를 받고 전체 호출 수를 함께 싣는다 [23].

**한계.** EVTX 질의가 `max_scan`에 닿으면 이어 읽기는 이미 읽은 범위 안에서만 된다 [16].
그 범위의 일치를 모두 돌려준 뒤에는 `next_cursor`가 없고 나머지 레코드는 `max_scan`을 키운 새 질의로만 읽는다 [16].
`disk_parse_amcache`·`disk_parse_mft`·`disk_parse_usn_journal`·`build_timeline`·`hunt_ioc`는 `offset`이나 커서 인자가 없어 상한 뒤의 항목을 이어 읽는 길이 없다 [9].

### R02.05 상한 초과 시 거부

**구현.** 이 방식은 줄일 수 없는 결과를 돌려주는 EVTX·NTDS·보안 설명자 도구와 `registry_query`에 적용된다 [7][25][22][26].
`evtx_get_event`는 사건 하나와 메타데이터가 `max_chars`를 넘으면 자르지 않고 오류를 낸다 [25].
보안 설명자 두 도구는 해석 결과가 `max_chars`를 넘으면 오류를 내고 `max_aces`를 줄이라고 적는다 [26].
`ntds_get_object_by_sam`·`ntds_get_object_sid`·`ntds_get_domain_info`는 결과가 `max_chars`를 넘으면 오류를 낸다 [22].
EVTX 질의와 `ntds_get_trusts`는 첫 행 하나와 메타데이터만으로 `max_chars`를 넘으면 오류를 낸다 [6][22].
`registry_query`는 한 행만 남겨도 40,000자를 넘으면 오류를 내고 `fields`로 필드를 줄이라고 적는다 [7].
EVTX·NTDS·보안 설명자 도구의 이 오류는 `isError`가 참인 MCP 결과로, `registry_query`의 오류는 `{"error": …}` 글로 나간다 [27].

### R02.06 값 단위 잘림

**구현.** 이 방식은 `windows_search_parse`, `evtx_attack_summary`, `vt_lookup_behavior`의 값에 적용된다 [28][15][29].
`windows_search_parse`는 문자열 값을 2,048자(`MAX_VALUE`)에서 자르고 끝에 `…`를 붙인다 [28].
같은 함수는 `list`와 `dict`를 64개 항목까지, 깊이 3단계까지만 싣고 더 깊은 값은 `[nested value omitted]`로 바꾼다 [28].
자른 값의 수는 `values_truncated`에 센다 [28].
`evtx_attack_summary`는 예약 작업 사건의 `TaskContent`를 120자에서 표시 없이 자른다 [15].
`vt_lookup_behavior`는 행위 보고서의 도메인과 하위 항목 값을 512자, URL을 1,024자에서 표시 없이 자르고 항목마다 키를 8개까지 싣는다 [29].

### R02.07 건수 없는 잘림 표시

**구현.** 이 방식은 `evtx_attack_summary`, `yara_scan_directory`, `windows_search_parse`에 적용된다 [15][30][8].
`evtx_attack_summary`는 `limit`보다 많은 사건이 있으면 `truncated`를 참으로 두지만 `total_events`에는 반환한 줄 수(`limit`)를 싣는다 [15].
사건 수가 `limit`과 같으면 `truncated`는 거짓이다 [15].
`yara_scan_directory`는 검사한 파일 수가 `limit`에 닿으면 `truncated`를 참으로 두고 검사하지 않은 파일 수는 싣지 않는다 [30].
`windows_search_parse`는 한 행이 24,000자를 넘으면 그 행을 `report_type`·`WorkId`와 `_truncated` 문구만 남긴 행으로 바꾼다 [8].

### R02.09 항목 참조값으로 전체 내용 재조회

**구현.** 이 방식은 EVTX 질의와 APMX 호출 목록에 적용된다 [31][32].
EVTX 질의 도구는 `compact`나 `fields`로 필드를 줄인 행에도 `event_ref`를 싣는다 [31].
`event_ref`를 `evtx_get_event`에 주면 서버는 그 EVTX 파일의 식별값이 `event_ref`와 같은지 확인하고 그 레코드의 사건 전체를 돌려준다 [33].
서버는 질의 결과를 따로 보관하지 않는다.
메모리에 남은 파싱 결과에 그 레코드가 없으면 원본 파일을 그 레코드까지 다시 읽는다 [33].
`evtx_get_event`는 사건을 줄이지 않고 상한을 넘으면 오류를 낸다 [25].
`apmx_get_calls`는 호출마다 레코드 번호 `call_index`와 API 이름, 안쪽 호출 수만 싣는다 [32].
`apmx_get_call_details`에 `call_indices`로 그 번호를 주면 캡처 파일에서 그 레코드를 다시 읽어 분석한 결과를 돌려준다 [34].

**한계.** `evtx_get_event`는 파일의 앞 1,000,000개 레코드 안에 있는 사건만 다시 읽는다 [33].
원본 파일의 식별값이 바뀌면 앞서 받은 `event_ref`는 거부된다 [33].

### 근거

[1] 공통 처리기 `json_response`는 상한을 넘으면 `_smart_truncate`를 부르고 결과가 `dict`일 때만 `_truncation`을 붙인다.

```python
def json_response(data: Any, max_chars: int = MAX_RESPONSE_CHARS) -> str:
    """Convert data to compact JSON string for response, with smart truncation if too large."""

    # Serialize compact (no indent) — saves ~40% size
    result = json.dumps(data, default=str)

    if len(result) <= max_chars:
        return result

    # Apply smart truncation
    truncated_data, truncation_info = _smart_truncate(data, max_chars)

    # Add truncation metadata to response
    if isinstance(truncated_data, dict) and truncation_info:
        truncated_data["_truncation"] = {
            "warning": "Response was truncated to fit context limits. IMPORTANT: Oldest data was kept, newest may be missing!",
            "original_chars": len(result),
            "max_chars": max_chars,
            "truncated_arrays": truncation_info,
            "hint": "Use time_range_start/end to focus on incident window, or use offset parameter to paginate through all results"
        }

    return json.dumps(truncated_data, default=str)
```

```python
def registry_query_response(data: dict[str, Any], max_chars: int = MAX_RESPONSE_CHARS) -> str:
    """Fit whole query rows to the response budget without invalidating pagination."""
    page = {**data, "results": list(data["results"])}
    while True:
        encoded = json.dumps(page, default=str)
        if len(encoded) <= max_chars:
            return encoded
        if len(page["results"]) <= 1:
            raise ValueError(
                "A registry query row exceeds the response size limit; "
                "use fields to project smaller values (for example name and key_path)"
            )
```
