# I02 분석 도구 통신 차단

### 미구현

**판단.** 서버는 외부 분석 도구 두 개를 자식 프로세스로 실행하고 통신을 끊거나 끄는 옵션이나 장치를 두지 않는다.
`die_analyze_file`·`die_scan_directory`는 Detect It Easy CLI `diec`를 `-j`와 선택 인자 `-d`, 파일 경로만으로 실행한다 [1].
`die_scan_directory`는 파일마다 `analyze_file`을 불러 같은 명령을 실행한다 [2].
`windows_search_parse`는 SIDR 실행 파일을 `--version`과 `-f json -r to-file -o <출력 폴더> <입력 폴더>`로 실행한다 [3].
두 실행 모두 `subprocess.run`에 `env`를 넘기지 않아 서버 프로세스의 환경변수를 그대로 물려준다 [1][3].
자식 프로세스의 네트워크를 끊는 컨테이너 구성이나 network namespace는 저장소에 없다.

SIDR는 저장소에 들어 있는 0.9.2 실행 파일이 기준이다 [4].
그 소스 커밋 `strozfriedberg/sidr@c7d3744`의 `Cargo.toml` 의존성에는 HTTP·네트워크 라이브러리가 없다 [5].
Detect It Easy 3.21이 스스로 통신하는지는 소스로 확인하지 않았다.

나머지 분석은 서버 프로세스 안에서 파이썬 라이브러리로 한다.
`evtx`·`python-registry`·`pefile`·`libscca-python`·`libesedb-python`·`mft`·`pylnk3`·`libfwsi-python`·`yara-python`·`scapy`가 그 라이브러리다 [6].
서버는 이 라이브러리의 통신을 끄는 설정을 두지 않는다.
`scapy`는 pcap 파일을 읽는 함수와 계층 클래스만 불러와 쓴다 [7].
YARA 규칙과 IoC 묶음은 저장소에 들어 있는 파일이나 호출 인자로 준 로컬 경로에서 읽는다 [8].
이 라이브러리들이 스스로 통신하는지는 소스로 확인하지 않았다.
