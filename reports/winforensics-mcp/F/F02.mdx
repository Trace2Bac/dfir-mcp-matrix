# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 여러 아티팩트를 묶어 판정하는 오케스트레이터 4개(`investigate_execution`, `hunt_ioc`, `investigate_user_activity`, `hunt_ioc_pack`)와, 파서 결과에 정해 둔 규칙을 대어 의심 항목을 고르는 도구들에 적용된다 [1][2][3][4].

오케스트레이터는 대상 이름이나 해시를 공유 키로 출처마다 찾고 찾은 출처를 묶어 판정한다.

- `investigate_execution`은 대상을 Prefetch, Amcache, SRUM에서 찾고 한 출처라도 찾으면 `execution_confirmed`를 참으로 둔다 [1].
- `investigate_execution`은 대상이 SHA1이면 Amcache를 해시로, 아니면 `.exe`를 뺀 이름을 이름 필터로 찾는다 [5].
- `hunt_ioc`는 값의 모양으로 IOC 종류를 정한다 [6].
- 32·40·64자리 16진수는 해시로, 점으로 나뉜 숫자 넷은 IP로, 정해 둔 최상위 도메인 26개로 끝나는 값은 도메인으로, 나머지는 파일 이름으로 본다 [6].
- `hunt_ioc`는 그 종류로 출처 7곳과 요청하면 YARA까지 찾고 하나라도 일치하면 `found`를 참으로 두며 일치한 출처와 일치하지 않은 출처를 나눠 싣는다 [2].
- `investigate_user_activity`는 브라우저 기록, ShellBags, LNK, RecentDocs에서 활동을 찾고 LNK 대상을 확장자로 실행 파일, 문서, 기타로 나눈다 [3].
- `hunt_ioc_pack`은 IoC 묶음의 규칙마다 파일 경로 정규식, 텍스트 파일 내용 정규식, PCAP payload 정규식을 맞춰 일치한 규칙을 싣는다 [4].

파서 도구는 결과 항목 하나에 정해 둔 규칙을 대어 의심 표시를 붙인다.

- `disk_parse_mft`는 항목마다 `$STANDARD_INFORMATION`과 `$FILE_NAME`의 생성 시각을 비교한다 [7].
- SI 생성 시각이 FN보다 이르거나, 365일 넘게 이르거나, 시·분·초·마이크로초가 모두 0이면 timestomping의 `detected`를 참으로 둔다 [7].
- `pcap_find_suspicious`는 정해 둔 TCP 포트 24개, User-Agent 정규식 7개, 40자를 넘는 DNS 레이블, 대상별 송신량 1MB 초과로 의심 항목을 고른다 [8].
- `file_analyze_pe`는 section마다 엔트로피 7.0 초과, 실행·쓰기 동시 허용, 원본 크기 0, packer section 이름을 표시한다 [9].
- `file_analyze_pe`는 packer section 이름, API 범주별 import, 버전 정보 없음, 2000년 이전이나 현재보다 뒤인 컴파일 시각을 `suspicious_indicators`에 싣는다 [10][11].
- `api_detect_patterns`·`api_analyze_imports`는 PE import를, `apmx_detect_patterns`는 API Monitor 캡처에서 실제로 불린 API를 같은 패턴 표 17개에 맞춘다 [12][13].
- 패턴마다 필수 API 가운데 `min_match`개 이상이 있으면 그 패턴을 싣는다 [12].
- `apmx_correlate_handles`는 핸들을 만드는 API의 반환값을 키로, 그 값을 앞 세 인자에 가진 API 호출을 이어 핸들 연결을 만든다 [14].
- `apmx_injection_info`는 그 가운데 `OpenProcess`에서 시작해 원격 메모리 할당이나 쓰기 API로 이어진 연결만 주입 연결로 고른다 [15].
- `user_parse_shellbags`는 `suspicious_only`가 참이면 네트워크 공유, 압축 파일 내부, C가 아닌 드라이브, 정해 둔 경로 문자열 19개에 해당하는 폴더를 `reason`과 함께 고른다 [16].
- `evtx_security_search`는 `lateral_movement`를 이벤트 ID 4624·4648·4778·4779로, `credential_access`를 4768·4769·4771·4776으로 정해 둔다 [17].
- `lateral_movement`는 로그온 유형을 가리지 않고 모든 4624 이벤트를 포함한다 [17].
- `registry_get_persistence`는 `include_microsoft_services`가 거짓이면 이미지 경로로 Microsoft 서비스를 가려 뺀다 [18].
- 이미지 경로에 `microsoft`가 있거나 앞 두 경로 요소에 `windows`가 있으면서 `system32`가 포함된 서비스가 빠지고 뺀 수는 응답에 싣지 않는다 [18].

패턴 표와 의심 표시 규칙에는 서명이나 알려진 정상 파일을 빼는 조건이 없다 [12][10].
Windows 11의 `taskmgr.exe`는 `credential_dumping`·`keylogging`을 포함한 8개 패턴과 `risk_level` `high`로, `notepad.exe`는 4개 패턴과 `medium`으로 나온다 [19].

**한계.** `investigate_execution`은 Amcache 항목만 찾아도 `execution_confirmed`를 참으로 두고 요약에 "confirmed"로 적는다 [1][20].
같은 응답의 시간선은 그 Amcache 항목을 실행 또는 설치 기록으로 적는다 [21].
`hunt_ioc`는 `time_range_start`·`time_range_end`를 받지만 어느 출처 검색에도 넘기지 않는다 [22].
그래서 시간 범위를 주어도 일치 여부와 등급은 전체 기간으로 정해진다 [23].
`hunt_ioc`의 EVTX 검색은 우선 로그 4개 가운데 하나라도 있으면 그 로그만, 없으면 폴더의 `.evtx` 파일 5개까지만 찾는다 [24].
파일마다 일치 이벤트를 10건까지만 가져온다 [24].
읽지 못한 EVTX 파일은 알리지 않고 건너뛴다 [24].
`disk_parse_mft`는 `detect_timestomping`을 받지만 판정에 쓰지 않아 거짓으로 주어도 timestomping 판정이 실린다 [25].
그 인자의 설명은 SI 시각이 FN보다 이른 파일을 표시한다고 적지만 코드는 365일 차이와 0시 조건으로도 표시한다 [25][7].
`file_analyze_pe`의 API 범주 검사는 DLL마다 앞 20개 함수만 본다 [26].
`apmx_correlate_handles`는 같은 핸들 값이 다시 만들어지면 뒤의 생성 호출로 앞의 것을 덮어쓰고 사용 호출을 시각 차례와 관계없이 그 값에 잇는다 [27][14].
`pcap_find_suspicious`는 출발지 주소가 `10.`·`192.168.`·`172.`로 시작하면 내부 주소로 보아 송신량을 센다 [8].
`172.16.0.0/12` 밖의 `172.` 주소도 내부 주소로 세어진다 [8].
`user_parse_shellbags`의 `suspicious_only`는 `limit`의 10배까지 읽은 폴더만 판정하고 `ntuser_path`를 쓰지 않는다 [28][16].
`hunt_ioc_pack`은 규칙마다 파일을 `max_files`개까지만 보고 `max_file_size`를 넘는 파일을 알리지 않고 건너뛴다 [29].
텍스트 내용 규칙은 정해 둔 확장자의 파일에만 적용된다 [29].

### F02.02 시각·위치 근접 연결

**구현.** 이 방식은 API Monitor 캡처의 레코드 번호를 위치로 쓰는 두 판정에 적용된다.
`apmx_detect_patterns`는 TLS 콜백 패턴을 FLS·TLS API가 캡처의 처음 200개 레코드 안에서 처음 나오고 원격 메모리 할당·쓰기 API가 캡처에 있을 때만 싣는다 [30].
`apmx_injection_info`는 `Process32` 호출 인자에서 `szExeFile`을 가진 구조를 읽지 못하면 `Process32` 호출 레코드 범위의 앞 5건부터 뒤 10건까지를 본다 [31].
그 레코드들의 인자 문자열 가운데 `.exe`로 끝나는 것을 세어 가장 많이 나온 이름을 `target_process`로 둔다 [31][32].

**한계.** `target_process`의 대체 이름은 주입 연결의 대상 PID와 대조하지 않고 모든 주입 연결에 같은 이름으로 붙으며 추정 값이라는 표시가 없다 [32].
`api_detect_patterns`·`api_analyze_imports`는 같은 TLS 콜백 패턴을 레코드 위치 조건 없이 PE import에 맞춘다 [33][12].
Bandizip의 `Arkview.x64.exe`는 이 경로에서 `tls_callback_execution`을 포함한 7개 패턴과 `risk_level` `high`로 나온다 [34].

### F02.03 통계·점수 산정

**구현.** 이 방식은 오케스트레이터 4개의 확신 등급, NTLM 요약의 빈도, PCAP beaconing 판정, 패턴 탐지의 전체 위험도에 적용된다.
`investigate_execution`은 찾은 출처가 3곳이면 `HIGH`, 2곳이면 `MEDIUM`, 1곳이면 `LOW`, 없으면 `NONE`으로 정한다 [35].
`hunt_ioc`와 `investigate_user_activity`는 찾은 출처가 4곳 이상이면 `HIGH`, 2곳 이상이면 `MEDIUM`, 1곳이면 `LOW`로 정한다 [35].
세 도구는 출처 안의 일치 건수나 내용을 등급에 쓰지 않는다 [35].
`hunt_ioc_pack`은 일치한 규칙마다 묶음 자료의 `weight`에 일치 수(최대 3)를 곱해 더한다 [36].
합계가 8 이상이면 `HIGH`, 4 이상이면 `MEDIUM`, 1 이상이면 `LOW`로 정하고 일치한 규칙을 `weight`와 일치 수 차례로 정렬한다 [36][37].
`weight`가 4인 규칙 하나가 파일 2개에서 일치하면 합계 8로 `HIGH`가 된다 [38].
`evtx_ntlm_operational_summary`는 걸러 낸 이벤트에서 (Computer, domain, process, user) 조합의 빈도를 세어 `pair_frequency`로 싣는다 [39].
`rare_first` 차례면 빈도가 낮은 조합부터 정렬하고 `unusual_only`가 참이면 빈도가 `rarity_threshold` 이하인 것만 남긴다 [39][40].
`pcap_find_suspicious`는 출발지·목적지·목적지 포트마다 패킷 시각 간격의 평균과 분산을 계산한다 [41].
평균이 1초를 넘고 분산이 평균의 0.3배를 제곱한 값보다 작으면 `potential_beaconing`에 싣는다 [41].
패턴 탐지는 탐지한 패턴의 `risk` 가운데 가장 높은 값을 전체 `risk_level`로 싣는다 [12].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 판정을 내는 도구의 응답에 적용된다.
실행·IOC·사용자 활동 오케스트레이터는 출처마다 읽은 파일이나 폴더의 `path`와 출처별 검색 여부 `artifacts_searched`를 싣는다 [42][2].
`hunt_ioc`는 EVTX 출처에 실제로 읽은 로그 이름 `logs_searched`를, YARA 출처에 검사한 파일 `file_scanned`를 싣는다 [24][43].
`pcap_find_suspicious`와 `user_parse_shellbags`는 고른 항목마다 적용한 규칙을 `reason` 문장으로 싣는다 [8][16].
`disk_parse_mft`는 맞은 조건을 `indicators`에 적고 비교한 두 생성 시각과 차이 일수를 함께 싣는다 [7].
패턴 탐지는 패턴마다 일치한 필수 API, 빠진 필수 API, 문턱 `min_required`를 싣는다 [12].
`apmx_detect_patterns`는 일치한 API마다 처음 나온 레코드 번호를 싣는다 [13][44].
`hunt_ioc_pack`은 규칙의 `id`와 출처 `reference`, 일치마다 파일 경로, 탐지기 이름, 정규식, 앞뒤 글을 싣는다 [4][45].
`evtx_ntlm_operational_summary`는 빈도 기준을 `rarity_basis`로 적고 행마다 원래 이벤트를 다시 여는 `event_ref`를 싣는다 [46].

**한계.** 오케스트레이터 4개는 확신 등급을 정한 문턱을 응답에 싣지 않는다 [35][37].
`hunt_ioc`의 EVTX 일치 항목은 `event_id`·`timestamp`·`provider` 키를 읽지만 EVTX 파서가 돌려주는 사건의 키는 `EventID`·`TimeCreated`·`Provider`다 [47][48].
그래서 일치 항목에는 로그 파일 이름만 값이 있고 사건 ID, 시각, 제공자는 `None`으로 실린다 [47][48].
`investigate_execution`의 Amcache 출처는 일치 항목 수 `match_count`만 싣고 해시와 경로는 첫 항목의 값만 싣는다 [49].

### F02.06 규칙 기반 공격 단계 분류·흐름 서술

**구현.** 이 방식은 API Monitor 캡처의 호출을 레코드 차례로 늘어놓는 `apmx_detect_patterns`와 `apmx_injection_info`에 적용된다 [44][50].
`apmx_detect_patterns`는 탐지한 패턴의 API를 캡처에서 처음 나온 레코드 차례로 늘어놓은 `suspicious_call_timeline`을 싣는다 [44].
`apmx_injection_info`는 주입 연결마다 `OpenProcess`부터 이어진 API 호출을 레코드 번호와 함께 `chain`으로 싣는다 [50].
같은 도구는 캡처에서 탐지한 패턴으로 `injection_technique`를 정한다 [50].
`Thread Local Storage (TLS Callback)`, `Classic Process Injection`, `APC Queue Injection`, `Process Hollowing` 차례로 고르고 해당하는 것이 없으면 `Unknown`으로 둔다 [50].
패턴 표는 패턴 17개마다 ATT&CK 기법 ID를 정해 두고 탐지한 패턴에 `mitre_id`를 싣는다 [51][12].
기법 ID를 tactic이나 킬체인 단계로 묶거나 흐름 문장을 만드는 코드는 없다 [51].
PE import를 패턴 표에 맞추는 `api_detect_patterns`·`api_analyze_imports`는 기법 ID만 싣고 호출 차례 표를 싣지 않는다 [12].

**한계.** `injection_technique`는 연결마다가 아니라 캡처 전체의 패턴 결과로 정해서 한 캡처의 모든 주입 연결이 같은 기법 이름을 받는다 [52][50].

### F02.08 확신 수준·추정 범위 표시

**구현.** 이 방식은 오케스트레이터 4개의 `confidence`와 `evtx_ntlm_operational_summary`의 상태 값·빈도 정확도 표시에 적용된다 [42][2][37][53].
오케스트레이터 4개는 판정에 `HIGH`·`MEDIUM`·`LOW`·`NONE` 가운데 하나를 `confidence`로 싣는다 [42][2][37].
`hunt_ioc_pack`은 일치한 규칙마다 묶음 자료가 정한 `confidence`도 함께 옮긴다 [45].
`evtx_ntlm_operational_summary`는 상태 코드가 0이면 `success`, `0xC000006D`이면 `failure`로 두고 그 밖의 값은 `unknown`으로 둔다 [53].
스캔이 상한에 닿는 등으로 걸러 낸 이벤트 수가 정확하지 않으면 `rarity_exact`를 거짓으로 둔다 [46].
그때 응답 요약은 일치 수가 정확하지 않으니 스캔 진단을 보라고 적는다 [54].

**한계.** 오케스트레이터의 출처 검색이 오류로 끝나면 그 출처는 `found`가 거짓인 채 검색한 출처로 남는다 [55][23].
일치한 출처가 없으면 등급은 `NONE`이 되고 요약은 오류 난 출처까지 포함해 찾지 못했다고 적으며 판단 보류로 표시하지 않는다 [20][2][23].

### F02.09 판정 제외 조건의 공개

**구현.** 이 방식은 `evtx_ntlm_operational_summary`의 `unusual_only`에 적용된다 [46].
응답은 드문 조합만 남기기 전의 이벤트 수 `matched_events`와 남긴 뒤의 행 수 `total_matched`, 문턱 `rarity_threshold`, 빈도 기준 `rarity_basis`를 함께 싣는다 [46].
개요 `overview`는 드문 조합을 고르기 전의 이벤트를 범위로 하고 드문 조합 예시마다 `unusual` 여부를 싣는다 [56].

다른 판정 도구는 뺀 항목의 수나 기준을 싣지 않는다.
`registry_get_persistence`는 Microsoft 서비스로 보아 뺀 서비스 수를 싣지 않는다 [18].
`user_parse_shellbags`의 `suspicious_only`는 고른 폴더 수 `total_suspicious`만 싣고 판정한 전체 폴더 수는 싣지 않는다 [16].

### 근거

[1] `investigate_execution`은 한 출처라도 찾으면 실행을 참으로 두고 등급을 계산한다.

```python
    # Determine if execution was confirmed
    execution_confirmed = any(r.get("found") for r in evidence_results)

    # Calculate confidence
```

```python
def _status_outcome(raw):
    """Interpret only verified values; other NTSTATUS/HRESULT values stay unknown.

    MS-ERREF lists 0 as STATUS_SUCCESS and 0xc000006d as STATUS_LOGON_FAILURE:
    https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55
    """
    if type(raw) is int:
        number = raw
    elif isinstance(raw, str):
        value = raw.strip()
        if re.fullmatch(r"0[xX][0-9a-fA-F]{1,8}", value):
            number = int(value, 16)
        elif re.fullmatch(r"[0-9]{1,10}", value, flags=re.ASCII):
            number = int(value, 10)
        else:
            return "unknown"
    else:
        return "unknown"
    return {0: "success", 0xC000006D: "failure"}.get(number, "unknown")
```
