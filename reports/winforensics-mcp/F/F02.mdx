# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 여러 아티팩트를 묶어 판정하는 오케스트레이터 4개(`investigate_execution`, `hunt_ioc`, `investigate_user_activity`, `hunt_ioc_pack`)와, 파서 결과에 정해 둔 규칙을 대어 의심 항목을 고르는 도구들, 공유 키로 결과 항목을 잇거나 문턱으로 판정 값을 정하는 도구들에 적용된다 [1][2][3][4][5][6].

오케스트레이터는 대상 이름이나 해시를 공유 키로 출처마다 찾고 찾은 출처를 묶어 판정한다.

- `investigate_execution`은 대상을 Prefetch, Amcache, SRUM에서 찾고 한 출처라도 찾으면 `execution_confirmed`를 참으로 둔다 [1].
- `investigate_execution`은 대상이 SHA1이면 Amcache를 해시로, 아니면 `.exe`를 뺀 이름을 이름 필터로 찾는다 [7].
- `hunt_ioc`는 값의 모양으로 IOC 종류를 정한다 [8].
- 32·40·64자리 16진수는 해시로, 점으로 나뉜 숫자 넷은 IP로, 정해 둔 최상위 도메인 26개로 끝나는 값은 도메인으로, 나머지는 파일 이름으로 본다 [8].
- `hunt_ioc`는 그 종류로 출처 7곳과 요청하면 YARA까지 찾고 하나라도 일치하면 `found`를 참으로 두며 일치한 출처와 일치하지 않은 출처를 나눠 싣는다 [2].
- `hunt_ioc`는 IOC 종류에 따라 검색할 출처를 정한다 [9].
- Prefetch, SRUM, MFT, USN, YARA는 파일 이름일 때만, 브라우저 기록은 도메인·IP·파일 이름일 때만 검색하고 EVTX는 모든 종류를 글로 검색한다 [9].
- Amcache는 SHA1이면 해시로, 파일 이름·MD5·SHA256이면 값을 항목 이름의 부분 문자열로 검색한다 [10].
- `investigate_user_activity`는 브라우저 기록, ShellBags, LNK, RecentDocs에서 활동을 찾고 LNK 대상을 확장자로 실행 파일, 문서, 기타로 나눈다 [3].
- `investigate_user_activity`는 ShellBags 경로가 `\\`로 시작하면 `network_shares`에 싣고 드라이브 문자로 시작하는 경로가 있으면 `has_removable_access`를 참으로 둔다 [11].
- `hunt_ioc_pack`은 IoC 묶음의 규칙마다 파일 경로 정규식, 텍스트 파일 내용 정규식, PCAP payload 정규식을 맞춰 일치한 규칙을 싣는다 [4].

파서 도구는 결과 항목 하나에 정해 둔 규칙을 대어 의심 표시를 붙인다.

- `disk_parse_mft`는 항목마다 `$STANDARD_INFORMATION`과 `$FILE_NAME`의 생성 시각을 비교한다 [12].
- SI 생성 시각이 FN보다 이르거나, 365일 넘게 이르거나, 시·분·초·마이크로초가 모두 0이면 timestomping의 `detected`를 참으로 둔다 [12].
- `pcap_find_suspicious`는 정해 둔 TCP 포트 24개, User-Agent 정규식 7개, 40자를 넘는 DNS 레이블, 대상별 송신량 1MB 초과로 의심 항목을 고른다 [13].
- 의심 포트는 출발 포트와 목적지 포트를 모두 대조하고 해당하는 패킷마다 항목을 하나씩 싣는다 [13].
- User-Agent 규칙은 목적지 포트가 80·8080·8081이고 `GET`이나 `POST`로 시작하는 TCP payload에만 적용된다 [14].
- `file_analyze_pe`는 section마다 엔트로피 7.0 초과, 실행·쓰기 동시 허용, 원본 크기 0, packer section 이름을 표시한다 [15].
- `file_analyze_pe`는 packer section 이름, API 범주별 import, 버전 정보 없음, 2000년 이전이나 현재보다 뒤인 컴파일 시각을 `suspicious_indicators`에 싣는다 [16][17].
- `api_detect_patterns`·`api_analyze_imports`는 PE import를, `apmx_detect_patterns`는 API Monitor 캡처에서 실제로 불린 API를 같은 패턴 표 17개에 맞춘다 [18][19].
- 패턴마다 필수 API 가운데 `min_match`개 이상이 있으면 그 패턴을 싣는다 [18].
- `apmx_correlate_handles`는 핸들을 만드는 API의 반환값을 키로, 그 값을 앞 세 인자에 가진 API 호출을 이어 핸들 연결을 만든다 [20].
- `apmx_injection_info`는 그 가운데 `OpenProcess`에서 시작해 원격 메모리 할당이나 쓰기 API로 이어진 연결만 주입 연결로 고른다 [21].
- `user_parse_shellbags`는 `suspicious_only`가 참이면 네트워크 공유, 압축 파일 내부, C가 아닌 드라이브, 정해 둔 경로 문자열 19개에 해당하는 폴더를 `reason`과 함께 고른다 [22].
- `evtx_security_search`는 `lateral_movement`를 이벤트 ID 4624·4648·4778·4779로, `credential_access`를 4768·4769·4771·4776으로 정해 둔다 [23].
- `lateral_movement`는 로그온 유형을 가리지 않고 모든 4624 이벤트를 포함한다 [23].
- `registry_get_persistence`는 SOFTWARE 하이브의 Winlogon 키에서 `Userinit`·`Shell`·`AppSetup`·`Taskman`을 읽어 정해 둔 기대값과 대조하고 하나라도 다르면 `suspicious`를 참으로 둔다 [24].
- `Userinit`은 파일 이름이 `userinit.exe`인 항목 하나가 아니면, `Shell`은 파일 이름이 `explorer.exe`가 아니면, `AppSetup`·`Taskman`은 값이 있으면 편차로 본다 [24].

파서와 조회 도구는 정해 둔 키로 결과 항목을 잇거나 정해 둔 문턱과 목록으로 판정 값을 붙이기도 한다.

- `registry_get_usb_history`는 USBSTOR 장치마다 `SWD\WPDBUSENUM` 아래 WPD 항목을 instance 경로의 조각과 ContainerID로 대조해 잇는다 [5].
- instance 경로는 WPD 키 이름을 `\`와 `#`으로 나눈 조각에서 `usbstor` 다음 두 조각이 장치 클래스와 instance ID와 같을 때만 일치로 본다 [5].
- 이은 WPD 항목의 이름을 `device_name`으로 싣고 USBSTOR의 제조사·장치 설명이 없거나 `@`로 시작하면 instance 경로로 이은 WPD 값으로 바꾼다 [25].
- `ntds_get_domain_info`는 `domainDNS` 객체를 `Partitions` 아래 `crossRef`의 `nCName`으로 이어 DNS 이름과 NetBIOS 이름을 붙인다 [26].
- 로컬 도메인은 `hiddentable`의 DSA 객체에서 `msDS-HasDomainNCs` 링크를 따라가 정하고 forest 루트는 `configuration` 객체의 부모 도메인으로 정한다 [27][28].
- forest 루트는 모든 도메인의 `crossRef`가 `trustParent`·`rootTrust`를 따라 그 루트에 닿을 때만 정한다 [28].
- `evtx_correlate_logon_id`는 받은 로그온 ID를 16진 문자열로 맞춘 뒤 사건마다 `SubjectLogonId`와 `TargetLogonId`를 같은 방식으로 맞춰 대조한다 [29].
- 일치한 쪽에 따라 행의 `role`을 `subject`나 `target`으로 정하고 한 사건에서 두 필드가 모두 일치하면 역할마다 한 행을 만든다 [29].
- `evtx_ntlm_operational_summary`는 제공자 `Microsoft-Windows-NTLM`, 채널 `Microsoft-Windows-NTLM/Operational`, 이벤트 ID 4021·4022·4023을 모두 만족하는 사건만 센다 [30].
- VirusTotal 조회 도구는 VirusTotal이 준 엔진별 판정 수를 서버 코드의 문턱과 대조해 `verdict`를 정한다 [6][31].
- 해시 조회는 `malicious`가 5 이상이면 `malicious`, 1 이상이거나 `suspicious`가 3 이상이면 `suspicious`, 엔진 수가 1 이상이면 `clean`, 0이면 `unknown`으로 둔다 [6].
- IP·도메인 조회는 `malicious`가 3 이상이면 `malicious`, 1 이상이거나 `suspicious`가 2 이상이면 `suspicious`, 그 밖은 `clean`으로 둔다 [31].
- `die_analyze_file`은 `diec`가 판별한 항목의 종류가 `packer`·`protector`·`cryptor`이면 `is_packed`를 참으로 두고 같은 방식으로 `is_dotnet`·`is_installer`를 정한다 [32].

패턴 표와 의심 표시 규칙에는 서명이나 알려진 정상 파일을 빼는 조건이 없다 [18][16].
Windows 11의 `taskmgr.exe`는 `credential_dumping`·`keylogging`을 포함한 8개 패턴과 `risk_level` `high`로, `notepad.exe`는 4개 패턴과 `medium`으로 나온다 [33].

**한계.** `investigate_execution`은 Amcache 항목만 찾아도 `execution_confirmed`를 참으로 두고 요약에 "confirmed"로 적는다 [1][34].
같은 응답의 시간선은 그 Amcache 항목을 실행 또는 설치 기록으로 적는다 [35].
`hunt_ioc`는 `time_range_start`·`time_range_end`를 받지만 어느 출처 검색에도 넘기지 않는다 [36].
그래서 시간 범위를 주어도 일치 여부와 등급은 전체 기간으로 정해진다 [37].
`hunt_ioc`의 EVTX 검색은 우선 로그 4개 가운데 하나라도 있으면 그 로그만, 없으면 폴더의 `.evtx` 파일 5개까지만 찾는다 [38].
파일마다 일치 이벤트를 10건까지만 가져온다 [38].
읽지 못한 EVTX 파일은 알리지 않고 건너뛴다 [38].
`disk_parse_mft`는 `detect_timestomping`을 받지만 판정에 쓰지 않아 거짓으로 주어도 timestomping 판정이 실린다 [39].
그 인자의 설명은 SI 시각이 FN보다 이른 파일을 표시한다고 적지만 코드는 365일 차이와 0시 조건으로도 표시한다 [39][12].
`file_analyze_pe`의 API 범주 검사는 DLL마다 앞 20개 함수만 본다 [40].
`apmx_correlate_handles`는 같은 핸들 값이 다시 만들어지면 뒤의 생성 호출로 앞의 것을 덮어쓰고 사용 호출을 시각 차례와 관계없이 그 값에 잇는다 [41][20].
`pcap_find_suspicious`는 출발지 주소가 `10.`·`192.168.`·`172.`로 시작하면 내부 주소로 보아 송신량을 센다 [13].
`172.16.0.0/12` 밖의 `172.` 주소도 내부 주소로 세어진다 [13].
`user_parse_shellbags`의 `suspicious_only`는 `limit`의 10배까지 읽은 폴더만 판정하고 `ntuser_path`를 쓰지 않는다 [42][22].
`hunt_ioc_pack`은 규칙마다 파일을 `max_files`개까지만 보고 `max_file_size`를 넘는 파일을 알리지 않고 건너뛴다 [43].
텍스트 내용 규칙은 정해 둔 확장자의 파일에만 적용된다 [43].
`investigate_execution`과 `hunt_ioc`의 Prefetch 검색은 `.pf` 파일 이름이 대상 이름에서 `.exe`를 뺀 문자열로 시작하면 일치로 본다 [44].
그래서 `cmd.exe`를 찾으면 `CMDKEY.EXE`의 Prefetch 파일도 일치하고 그 실행 횟수가 `total_run_count`에 더해진다 [44].
이 검색은 파싱하지 못한 `.pf` 파일을 알리지 않고 건너뛴다 [44].
`investigate_execution`은 SHA256 대상을 `target_type` `sha256`으로 적지만 해시로 대조하지 않고 세 출처에서 실행 파일 이름으로 찾는다 [45].
Amcache 이름 필터는 `name_filter`를 항목 이름의 부분 문자열로 대조한다 [46].
`investigate_execution`은 SRUM 네트워크 사용 조회에 시간 범위를 넘기지 않아 시간 범위를 주어도 송수신 합계는 전체 기간의 값이다 [47].
`hunt_ioc`에서 MD5나 SHA256 값은 어느 출처에서도 해시로 대조되지 않는다 [9][10].
이때 Amcache 출처는 검색했지만 일치가 없는 출처로 실리고 요약의 검색한 출처 수에 포함된다 [10][2].
`hunt_ioc`는 USN 저널을 늘 `interesting_only`를 켠 채 검색한다 [48].
그래서 정해 둔 reason 10종이 없는 레코드에서는 IOC가 일치해도 USN 출처의 `found`가 참이 되지 않고 응답에는 이 조건이 실리지 않는다 [48].
`investigate_user_activity`의 브라우저 단계는 파서 결과에서 `visits`·`total_visits`를 읽지만 `parse_browser_history`가 돌려주는 키는 `history`·`history_total`이다 [49].
그래서 방문 기록은 판정에 쓰이지 않고 다운로드 기록이 있을 때만 브라우저 출처의 `found`가 참이 된다 [49].
방문 기록 3건만 있는 Chrome 형식 DB로 부르자 브라우저 출처는 `found`가 거짓이었고 요약은 `No user activity found in Browser`였다 [50].
RecentDocs 단계는 레지스트리 값의 `data`가 `bytes`일 때만 파일 이름을 꺼내지만 `parse_registry_value`는 `bytes` 값을 문자열로 바꿔 싣는다 [51].
그래서 RecentDocs 출처는 값이 있어도 `found`가 거짓으로 남는다 [51].
RecentDocs 값이 11개 있는 테스트 하이브로 부르자 그 출처는 오류 없이 `found`가 거짓이었다 [52].
`investigate_user_activity`는 `time_range_start`·`time_range_end`를 브라우저 단계에만 넘기고 `keyword`를 함께 주면 브라우저 단계에서도 쓰지 않는다 [53].
ShellBags, LNK, RecentDocs 단계를 부르는 곳에는 시간 범위 인자가 없다 [54].
`has_removable_access`는 드라이브 문자를 가리지 않아 `C:\`로 시작하는 경로가 있어도 참이 된다 [11][55].
`evtx_security_search`와 `evtx_attack_summary`는 사건 종류를 이벤트 ID로만 고르고 채널과 제공자를 대조하지 않는다 [56].
그래서 다른 채널의 로그 파일에서도 번호가 같은 사건은 그 종류로 실린다 [56].
`log_cleared`의 104와 `service_installed`의 7045는 서버의 채널별 이벤트 표에서 System 채널의 ID다 [23][57].
`evtx_correlate_logon_id`가 대조하는 필드는 `SubjectLogonId`와 `TargetLogonId` 둘뿐이다 [29].
로그온 ID를 다른 이름의 필드에 싣는 사건은 같은 값이어도 일치하지 않는다 [29].
`disk_parse_mft`의 timestomping 판정은 항목의 첫 `$FILE_NAME` 속성과 `$STANDARD_INFORMATION`의 생성 시각만 비교하고 수정·접근 시각은 보지 않는다 [58].
`pcap_find_suspicious`는 IPv4 계층이 있는 패킷만 판정하고 응답에는 IPv6 패킷을 분석하지 않았다는 표시가 없다 [59].
목적지 포트가 4444인 IPv6 TCP 패킷 3개를 넣은 PCAP에서 의심 포트 항목은 없었다 [60].
`pcap_find_suspicious`의 송신량은 출발지가 내부 주소이면 목적지를 가리지 않고 더해서 내부 주소끼리의 전송도 `large_outbound_transfers`에 실린다 [14][13].
IP·도메인 VirusTotal 조회는 판정한 엔진이 하나도 없어도 `verdict`를 `clean`으로 둔다 [31][61].
`registry_get_persistence`의 Winlogon 판정은 `Userinit`과 `Shell`의 경로를 뺀 파일 이름만 대조하므로 다른 폴더의 `userinit.exe`·`explorer.exe`를 가리키는 값은 편차로 보지 않는다 [24].
`registry_get_usb_history`는 ContainerID만 같은 WPD 항목도 잇고 값이 모두 0인 ContainerID는 대조에서 뺀다 [5].
`ntds_get_domain_info`는 `Enabled`가 거짓이거나 `systemFlags`의 아래 두 비트가 서지 않은 `crossRef`와, `crossRef`도 SID도 없는 `domainDNS`를 판정 대상에서 빼고 뺀 수를 싣지 않는다 [26].

### F02.02 시각·위치 근접 연결

**구현.** 이 방식은 API Monitor 캡처의 레코드 번호를 위치로 쓰는 두 판정에 적용된다.
`apmx_detect_patterns`는 TLS 콜백 패턴을 FLS·TLS API가 캡처의 처음 200개 레코드 안에서 처음 나오고 원격 메모리 할당·쓰기 API가 캡처에 있을 때만 싣는다 [62].
`apmx_injection_info`는 `Process32` 호출 인자에서 `szExeFile`을 가진 구조를 읽지 못하면 `Process32` 호출 레코드 범위의 앞 5건부터 뒤 10건까지를 본다 [63].
그 레코드들의 인자 문자열 가운데 `.exe`로 끝나는 것을 세어 가장 많이 나온 이름을 `target_process`로 둔다 [63][64].

**한계.** `target_process`의 대체 이름은 주입 연결의 대상 PID와 대조하지 않고 모든 주입 연결에 같은 이름으로 붙으며 추정 값이라는 표시가 없다 [64].
`api_detect_patterns`·`api_analyze_imports`는 같은 TLS 콜백 패턴을 레코드 위치 조건 없이 PE import에 맞춘다 [65][18].
Bandizip의 `Arkview.x64.exe`는 이 경로에서 `tls_callback_execution`을 포함한 7개 패턴과 `risk_level` `high`로 나온다 [66].

### F02.03 통계·점수 산정

**구현.** 이 방식은 오케스트레이터 4개의 확신 등급, NTLM 요약의 빈도, PCAP beaconing 판정, 패턴 탐지의 전체 위험도에 적용된다.
`investigate_execution`은 찾은 출처가 3곳이면 `HIGH`, 2곳이면 `MEDIUM`, 1곳이면 `LOW`, 없으면 `NONE`으로 정한다 [67].
`hunt_ioc`와 `investigate_user_activity`는 찾은 출처가 4곳 이상이면 `HIGH`, 2곳 이상이면 `MEDIUM`, 1곳이면 `LOW`로 정한다 [67].
세 도구는 출처 안의 일치 건수나 내용을 등급에 쓰지 않는다 [67].
`hunt_ioc_pack`은 일치한 규칙마다 묶음 자료의 `weight`에 일치 수(최대 3)를 곱해 더한다 [68].
합계가 8 이상이면 `HIGH`, 4 이상이면 `MEDIUM`, 1 이상이면 `LOW`로 정하고 일치한 규칙을 `weight`와 일치 수 차례로 정렬한다 [68][69].
`weight`가 4인 규칙 하나가 파일 2개에서 일치하면 합계 8로 `HIGH`가 된다 [70].
`evtx_ntlm_operational_summary`는 걸러 낸 이벤트에서 (Computer, domain, process, user) 조합의 빈도를 세어 `pair_frequency`로 싣는다 [71].
`rare_first` 차례면 빈도가 낮은 조합부터 정렬하고 `unusual_only`가 참이면 빈도가 `rarity_threshold` 이하인 것만 남긴다 [71][72].
`pcap_find_suspicious`는 출발지·목적지·목적지 포트마다 패킷 시각 간격의 평균과 분산을 계산한다 [73].
같은 출발지·목적지·목적지 포트의 TCP 패킷이 5개 이상일 때만 판정하고 `connection_count`에는 패킷 수를 싣는다 [73][14].
평균이 1초를 넘고 분산이 평균의 0.3배를 제곱한 값보다 작으면 `potential_beaconing`에 싣는다 [73].
패턴 탐지는 탐지한 패턴의 `risk` 가운데 가장 높은 값을 전체 `risk_level`로 싣는다 [18].

**한계.** `investigate_user_activity`는 출처가 4곳이고 RecentDocs 출처가 늘 거짓이므로 `HIGH`에 닿지 못한다 [67][51].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 판정을 내는 도구의 응답에 적용된다.
실행·IOC·사용자 활동 오케스트레이터는 출처마다 읽은 파일이나 폴더의 `path`와 출처별 검색 여부 `artifacts_searched`를 싣는다 [74][2].
`hunt_ioc`는 EVTX 출처에 실제로 읽은 로그 이름 `logs_searched`를, YARA 출처에 검사한 파일 `file_scanned`를 싣는다 [38][75].
`pcap_find_suspicious`와 `user_parse_shellbags`는 고른 항목마다 적용한 규칙을 `reason` 문장으로 싣는다 [13][22].
`disk_parse_mft`는 맞은 조건을 `indicators`에 적고 비교한 두 생성 시각과 차이 일수를 함께 싣는다 [12].
패턴 탐지는 패턴마다 일치한 필수 API, 빠진 필수 API, 문턱 `min_required`를 싣는다 [18].
`apmx_detect_patterns`는 일치한 API마다 처음 나온 레코드 번호를 싣는다 [19][76].
`hunt_ioc_pack`은 규칙의 `id`와 출처 `reference`, 일치마다 파일 경로, 탐지기 이름, 정규식, 앞뒤 글을 싣는다 [4][77].
`evtx_ntlm_operational_summary`는 빈도 기준을 `rarity_basis`로 적고 행마다 원래 이벤트를 다시 여는 `event_ref`를 싣는다 [78].
`registry_get_usb_history`는 이은 WPD 항목마다 일치 근거를 `match_sources`(`instance_path`·`container_id`)로 싣고 바꾸기 전의 USBSTOR 값을 `usb_stor_manufacturer`·`usb_stor_device_desc`에 남긴다 [5][25].
`registry_get_persistence`는 Winlogon 편차마다 값 이름, 값, 사유를 `deviations`에 싣고 기대값 표를 `expected_defaults`에 싣는다 [24][79].
`ntds_get_domain_info`의 `forest_root`와 `local_domain`은 판정에 쓴 연결을 `evidence`에 종류(`configuration_parent`·`domain_crossref`·`trust_sid_corroboration`·`hidden_dsa_domain_link`)와 객체 `dnt`로 싣는다 [80][27].
`evtx_correlate_logon_id`는 행마다 일치한 역할 `role`, 사건에 적힌 원래 값 `logon_id`, 대조에 쓴 값 `normalized_logon_id`, 그 사건을 다시 여는 `event_ref`를 싣는다 [29].
VirusTotal 해시 조회는 `verdict`와 함께 엔진별 판정 수와 `detection_ratio`를 싣는다 [81].

**한계.** 오케스트레이터 4개는 확신 등급을 정한 문턱을 응답에 싣지 않는다 [67][69].
`hunt_ioc`의 EVTX 일치 항목은 `event_id`·`timestamp`·`provider` 키를 읽지만 EVTX 파서가 돌려주는 사건의 키는 `EventID`·`TimeCreated`·`Provider`다 [82][83].
그래서 일치 항목에는 로그 파일 이름만 값이 있고 사건 ID, 시각, 제공자는 `None`으로 실린다 [82][83].
`investigate_execution`의 Amcache 출처는 일치 항목 수 `match_count`만 싣고 해시와 경로는 첫 항목의 값만 싣는다 [84].
VirusTotal 해시 조회는 `verdict`를 정한 문턱을 응답에 싣지 않는다 [81].
`file_analyze_pe`의 컴파일 시각 지표는 컴파일 시각만 싣고 비교에 쓴 호출 시점의 현재 시각은 싣지 않는다 [16].
`evtx_ntlm_operational_summary`가 사건을 묶으면 행의 `event_ref`는 묶음에서 파일 차례로 첫 사건 하나만 가리킨다 [85].
묶음의 나머지 사건은 `count`에만 반영되고 참조값이 실리지 않는다 [85].
`hunt_ioc`의 브라우저 방문 일치 항목은 `visit_time`을 읽지만 파서의 키는 `last_visit_time`이어서 시각이 `None`으로 실린다 [86].

### F02.06 규칙 기반 공격 단계 분류·흐름 서술

**구현.** 이 방식은 API Monitor 캡처의 호출을 레코드 차례로 늘어놓는 `apmx_detect_patterns`와 `apmx_injection_info`에 적용된다 [76][87].
`apmx_detect_patterns`는 탐지한 패턴의 API를 캡처에서 처음 나온 레코드 차례로 늘어놓은 `suspicious_call_timeline`을 싣는다 [76].
`apmx_injection_info`는 주입 연결마다 `OpenProcess`부터 이어진 API 호출을 레코드 번호와 함께 `chain`으로 싣는다 [87].
같은 도구는 캡처에서 탐지한 패턴으로 `injection_technique`를 정한다 [87].
`Thread Local Storage (TLS Callback)`, `Classic Process Injection`, `APC Queue Injection`, `Process Hollowing` 차례로 고르고 해당하는 것이 없으면 `Unknown`으로 둔다 [87].
패턴 표는 패턴 17개마다 ATT&CK 기법 ID를 정해 두고 탐지한 패턴에 `mitre_id`를 싣는다 [88][18].
기법 ID를 tactic이나 킬체인 단계로 묶거나 흐름 문장을 만드는 코드는 없다 [88].
PE import를 패턴 표에 맞추는 `api_detect_patterns`·`api_analyze_imports`는 기법 ID만 싣고 호출 차례 표를 싣지 않는다 [18].

**한계.** `injection_technique`는 연결마다가 아니라 캡처 전체의 패턴 결과로 정해서 한 캡처의 모든 주입 연결이 같은 기법 이름을 받는다 [89][87].

### F02.08 확신 수준·추정 범위 표시

**구현.** 이 방식은 오케스트레이터 4개의 `confidence`와 `evtx_ntlm_operational_summary`의 상태 값·빈도 정확도 표시, `ntds_get_domain_info`의 판정 상태 값, VirusTotal 해시 조회의 `verdict`에 적용된다 [74][2][69][90][27][6].
오케스트레이터 4개는 판정에 `HIGH`·`MEDIUM`·`LOW`·`NONE` 가운데 하나를 `confidence`로 싣는다 [74][2][69].
`hunt_ioc_pack`은 일치한 규칙마다 묶음 자료가 정한 `confidence`도 함께 옮긴다 [77].
`evtx_ntlm_operational_summary`는 상태 코드가 0이면 `success`, `0xC000006D`이면 `failure`로 두고 그 밖의 값은 `unknown`으로 둔다 [90].
스캔이 상한에 닿는 등으로 걸러 낸 이벤트 수가 정확하지 않으면 `rarity_exact`를 거짓으로 둔다 [78].
그때 응답 요약은 일치 수가 정확하지 않으니 스캔 진단을 보라고 적는다 [91].
`ntds_get_domain_info`는 `local_domain.status`를 `found`·`candidate`·`unknown`, `forest_root.status`를 `found`·`unknown` 가운데 하나로 싣는다 [27][28].
링크가 활성인지나 읽기가 끝났는지 확인하지 못하면 `local_domain`을 `candidate`로 두고 `reason`을 싣는다 [27].
읽기가 끝나지 않았거나 `crossRef`가 둘 이상이거나 연결이 끊기거나 순환하거나 신뢰 객체의 SID가 루트 SID와 다르면 `forest_root`를 `unknown`으로 두고 `reason`을 싣는다 [28][80].
VirusTotal 해시 조회는 판정한 엔진이 없으면 `verdict`를 `unknown`으로 둔다 [6].

**한계.** 오케스트레이터의 출처 검색이 오류로 끝나면 그 출처는 `found`가 거짓인 채 검색한 출처로 남는다 [92][37].
일치한 출처가 없으면 등급은 `NONE`이 되고 요약은 오류 난 출처까지 포함해 찾지 못했다고 적으며 판단 보류로 표시하지 않는다 [34][2][37].

### F02.09 판정 제외 조건의 공개

**구현.** 이 방식은 `evtx_ntlm_operational_summary`의 `unusual_only`에 적용된다 [78].
응답은 드문 조합만 남기기 전의 이벤트 수 `matched_events`와 남긴 뒤의 행 수 `total_matched`, 문턱 `rarity_threshold`, 빈도 기준 `rarity_basis`를 함께 싣는다 [78].
개요 `overview`는 드문 조합을 고르기 전의 이벤트를 범위로 하고 드문 조합 예시마다 `unusual` 여부를 싣는다 [93].

다른 판정 도구는 뺀 항목의 수나 기준을 싣지 않는다.
`user_parse_shellbags`의 `suspicious_only`는 고른 폴더 수 `total_suspicious`만 싣고 판정한 전체 폴더 수는 싣지 않는다 [22].

def _status_outcome(raw):
    """Interpret only verified values; other NTSTATUS/HRESULT values stay unknown.

    MS-ERREF lists 0 as STATUS_SUCCESS and 0xc000006d as STATUS_LOGON_FAILURE:
    https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55
    """
    if type(raw) is int:
        number = raw
    elif isinstance(raw, str):
        value = raw.strip()
        if re.fullmatch(r"0[xX][0-9a-fA-F]{1,8}", value):
            number = int(value, 16)
        elif re.fullmatch(r"[0-9]{1,10}", value, flags=re.ASCII):
            number = int(value, 10)
        else:
            return "unknown"
    else:
        return "unknown"
    return {0: "success", 0xC000006D: "failure"}.get(number, "unknown")
