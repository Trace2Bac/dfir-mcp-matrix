# winforensics-mcp 원고

이 파일은 서버 개요다. 셀마다 이 폴더 아래 축 폴더의 `<축>/<셀ID>.mdx`에 쓴다.
셀과 상세 항목의 정의는 `matrix/cells/<축>/<셀ID>.mdx`를 따른다.
상세 항목마다 **구현**을 쓰고 그 방식이 적용되지 않는 경로나 조건이 있으면 **한계**를 따로 쓴다.
본문의 [번호]는 그 파일 끝 **근거**의 같은 번호를 가리킨다.

**기준 커밋.** [`cce7f36`](https://github.com/x746b/winforensics-mcp/tree/cce7f360873fc9ae564296017cbffe2a603d83dd)(2026-09-29).
줄 번호는 모두 이 커밋 기준이다.
이 커밋의 패키지 버전은 1.5.0(`pyproject.toml`, `winforensics_mcp/__init__.py`)이고 릴리스 태그 `v1.5.0`은 한 커밋 앞의 `78c0194`다.
`78c0194`에서 이 커밋까지 바뀐 파일은 `README.md`뿐이다.

**범위.** `winforensics_mcp/` 패키지를 서버로 본다.
서버는 stdio MCP 서버 하나다.
`server.py`의 `main`이 MCP Python SDK의 저수준 `Server`로 서버를 시작하고, `list_tools`가 도구 정의를, `_execute_tool`이 도구 이름별 처리를 맡는다.
도구는 74개다.
38개는 늘 목록에 오르고, 36개는 선택 의존성이나 외부 실행 파일이 있을 때만 목록에 오른다.
조건부 도구와 그 조건은 [기능 목록](coverage.mdx) 머리말에 있다.
서버는 MCP 리소스와 프롬프트를 두지 않는다.

저장소에 함께 들어 있는 다음 자료는 서버가 실행 중에 읽는 자료로 본다.

- YARA 규칙 `winforensics_mcp/rules/*.yar`
- IoC 묶음 `winforensics_mcp/ioc_packs/impacket-iocs/`
- Windows API 정의 DB `winforensics_mcp/data/api_definitions.db`
- Windows Search 분석에 쓰는 SIDR 실행 파일 `.tools/sidr`(ARM64)·`.tools/sidr_x86`(x86_64)과 각 manifest

`tests/`와 `scripts/build_sidr.sh`(SIDR 실행 파일을 다시 빌드하는 사용자 스크립트)는 서버 구현으로 세지 않는다.
저장소에는 MCP 클라이언트 설정 파일이나 훅이 없고, README가 클라이언트 등록 예시만 적는다.

**확인 방법.** 코드는 기준 커밋을 `git show`로 읽었다.
외부 라이브러리와 실행 파일의 동작은 아래 버전 기준의 태그 소스로 확인했다.
근거의 "실행 확인"은 WSL Ubuntu에서 기준 커밋을 `git archive`로 푼 소스를 Python 3.12.15와 `uv.lock`이 고정한 의존성(`uv export --frozen --all-extras`)으로 실행해 본 결과다.
이 환경에서 저장소 테스트는 910개가 통과하고 52개를 건너뛰었으며 1개가 실패했다.
실패한 테스트는 x86_64 환경에서 SIDR 실행 파일 탐색 순서를 확인하는 `test_discovery_precedence`다.

저장소에는 증거 표본 파일이 없어 다음 표본과 가짜 입력을 썼다.

- 공개 표본: `omerbenamram/evtx` 저장소의 `samples/security.evtx`, regipy 저장소의 테스트 하이브(SAM·SECURITY·SYSTEM·SOFTWARE·Amcache), Wireshark-MCP 저장소의 `plaintext_credentials.pcap`
- Windows 11의 `C:\Windows\System32`와 `C:\Program Files` 아래 실행 파일
- 가짜 입력: 합성 EVTX 레코드(EVTX 파서를 바꿔 넣음), 가짜 SIDR·`diec` 실행 파일, 가짜 `vt.Client`, 가짜 `winrm.Session`과 원격 응답을 흉내 낸 `WinRMCollector`

VirusTotal과 WinRM 대상 단말에는 접속하지 않았다.
확인한 것은 다음과 같다.

- MCP Python SDK 클라이언트 세션으로 서버를 실행해 도구 목록, 잘못된 enum·범위·추가 속성 인자의 거부, 목록에 없는 도구 호출, 일반 도구와 EVTX 도구의 `isError` 값을 확인했다.
- `diec`가 없는 환경에서 도구 목록이 71개인지 확인했다.
- 같은 세션에서 서버 표준 오류를 받아 실패 호출과 성공 호출에 남는 기록 줄을 보고, 표준 오류를 `/dev/full`에 연결해 기록 쓰기가 실패해도 결과가 돌아오는지 확인했다.
- `evtx_search`의 커서와 `event_ref`를 원본 파일의 수정 시각이나 내용 1바이트를 바꾼 뒤 다시 넘겨 거부되는지, 다른 질의의 커서와 7일을 넘는 상관 범위가 거부되는지 확인했다.
- `max_chars`를 줄인 `compact` 질의, 큰 `json_response` 응답, 10만 건을 넘는 `evtx_get_stats`에서 자르기 표시와 건수를 확인했다.
- `evtx_export`를 같은 폴더에 두 번 부르고, 출력 폴더 자리에 파일을 두거나 `os.link` 실패를 흉내 내 파일 권한·해시·남는 파일을 확인했다.
- 저장소의 `.tools/sidr_x86`과 가짜 SIDR로 버전 확인, 버전 불일치, 시간 제한, 종료 코드, 경고 줄, `sidr_path` 지정, `pyesedb` 대체를 확인했다.
- 가짜 `diec`로 종료 코드와 JSON 출력이 없을 때의 결과를 확인했다.
- WAL 모드 Chrome 형식 DB로 `browser_get_history`를 불러 원본 폴더 `-shm`의 변화와 WAL 행 반영을 확인했다.
- 오케스트레이터를 정해 둔 폴더 구조와 손상된 `Amcache.hve`로 불러 원천별 상태, 요약 문장, 확신 등급, `hunt_ioc`가 시간 범위 인자를 쓰지 않는지 확인했다.
- 합성 EVTX 레코드로 `hunt_ioc`·`build_timeline`의 EVTX 결과를 확인했다.
- 표본 하이브로 레지스트리 도구를 불러 이진 값, 시각 필드, SAM `V` 값과 SECURITY `Policy\Secrets` 값이 응답에 실리는지 확인했다.
- 표본 PCAP으로 `pcap_get_http`·`pcap_search`를, 시스템 실행 파일로 `api_detect_patterns`의 패턴과 `risk_level`을 확인했다.
- 가짜 VirusTotal 클라이언트로 보내는 값, 요청 간격, 키를 읽는 곳, `triage_dir` 덮어쓰기를 확인했다.
- 가짜 WinRM 세션으로 접속 주소, 인증 값, 수집 파일 덮어쓰기, 항목별 실패 표시를 확인했다.
- 표본 하이브로 `registry_get_persistence`의 서비스 제외 수, `registry_get_users`의 계정 이름, ShellBags `resolved_path`, Amcache 시간 조건에 시간대를 붙였을 때의 건수를 확인했다.
- 합성 USN 저널과 브라우저 DB로 `interesting_only`, `reason_filter`, `dangerous_only`, 시간대 없는 시각 인자의 동작을 확인했다.
- 표본 EVTX로 `contains`가 일치하는 범위와 `_raw_xml` 필드의 내용을 확인했다.
- 방문 기록이 든 브라우저 DB와 RecentDocs 값이 든 하이브로 `investigate_user_activity`의 출처별 결과와 시간표를 확인했다.
- 합성 PCAP으로 IPv6 패킷, 트랜잭션 ID가 같은 DNS 질의, `pcap_search`의 건수 필드를 확인했다.
- 시스템 실행 파일로 `file_analyze_pe`의 `extract_strings`와 `imports_count`를, 규칙 파일을 바꿔 가며 YARA 컴파일 캐시와 `yara_list_rules`의 응답 크기를, API 정의 DB로 `api_lookup`의 행 수를 확인했다.

실제 `diec` 실행, 실제 `Windows.edb`·NTDS·SRUM·Prefetch·MFT·APMX 증거, WinRM 원격 실행(섀도 복사본 경로), YARA 시간 초과는 실행으로 확인하지 않았다.
원고에서 이 부분은 정적 분석 결과다.

**외부 도구 버전 기준.** 파이썬 라이브러리는 `uv.lock`이 고정한 버전을 기준으로 한다.

- Python: `pyproject.toml`은 3.10 이상만 정한다. 실행 확인 환경인 CPython 3.12.15(태그 `v3.12.15`, `e848e4b`)를 기준으로 한다.
- MCP Python SDK: `mcp` 1.25.0(태그 `v1.25.0`, `ef96a31`)이다. `pyproject.toml`은 `mcp>=1.25.0`을 적는다.
- 증거 파서: `evtx` 0.11.0, `python-registry` 1.3.1, `pefile` 2024.8.26, `libscca-python` 20250915, `libesedb-python` 20240420, `mft` 0.7.0, `pylnk3` 0.4.3, `libfwsi-python` 20260522다.
- 선택 의존성: `yara-python` 4.5.4, `vt-py` 0.22.0, `scapy` 2.7.0, `pywinrm` 0.5.0, `paramiko` 4.0.0, `smbprotocol` 1.15.0이다.
- 입력·출력 스키마 검사: `jsonschema` 4.26.0이다. `pyproject.toml`에는 없고 `mcp`가 의존성으로 설치한다.
- SIDR: 저장소에 들어 있는 실행 파일이 기준이다. manifest가 SIDR 0.9.2, 소스 커밋 `strozfriedberg/sidr@c7d3744`, 실행 파일의 SHA-256을 적는다.
- Detect It Easy(`diec`): 저장소는 버전을 정하지 않고 `PATH`나 정해 둔 설치 경로에서 찾는다. 기준 커밋 날짜에 나와 있던 최신 정식 릴리스 3.21(`horsicq/DIE-engine` 태그 `3.21`, 2026-04-21)을 기준으로 한다.

**바뀔 수 있는 것.** 범위와 외부 도구 버전 기준은 조사하며 맞지 않는 곳이 나오면 검토를 거쳐 바꾼다.
