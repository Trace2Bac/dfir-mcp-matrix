# T06 실행 환경정보 표시

### T06.01 응답 메타데이터에 버전 표시

**구현.** 이 방식은 `sift-mcp`의 `run_command`가 카탈로그에 있는 도구를 실행한 응답과 `opencti-mcp`의 `lookup_ioc` 응답에 적용된다 [1][2].
`run_command`는 명령의 첫 인자가 카탈로그 도구이면 실행하기 전에 `tool_version.probe`로 그 실행 파일에 버전을 묻는다 [1].
`probe`는 카탈로그의 `version_argv`, `--version`, `-V` 차례로 실행해 출력에서 처음 찾은 버전 문자열을 `installed_version`으로, 실제로 실행되는 경로를 `resolved_path`로 돌려준다 [3].
버전을 읽지 못하면 `installed_version`은 `unknown`이고 출력 첫 줄을 `version_output`에 둔다 [3].
`run_command`는 이 값을 저장해 두지 않고 호출마다 다시 묻는다 [1].
`build_response`는 두 값을 응답 최상위의 `tool_version`과 `resolved_path`에 싣는다 [4].
실행이 시간 제한이나 오류로 끝난 응답에도 같은 두 필드를 싣는다 [5].
실행 확인에서 Sleuth Kit 4.11.1의 `fls`를 실행하자 응답의 `tool_version`은 `4.11.1`, `resolved_path`는 `/usr/bin/fls`였다 [6].

`lookup_ioc`는 위협 정보 플랫폼마다 답을 `providers.<이름>`에 싣고 그 답에 플랫폼 버전 `version`을 둔다 [2].
OpenCTI 어댑터는 조회 질의에 `about { version }`을 함께 묻고 받은 값을 `version`에 싣는다 [7].
MISP 어댑터는 `/servers/getVersion`으로 읽은 값을 `version`에 싣는다 [8].
실행 확인에서 OpenCTI 설정 없이 `lookup_ioc`를 부르자 `providers.opencti.version`은 `null`이었다 [9].

다른 결과에는 버전이 없다.

- `run_command`로 카탈로그에 없는 프로그램을 실행한 응답에는 `tool_version`과 `resolved_path`가 없다 [1].
- `run_command` 응답에 붙는 `forensic-knowledge`의 해석 자료(`caveats`, `advisories`, `field_meanings`)에는 그 자료의 버전을 싣지 않는다 [4][10].
- `windows-triage-mcp`의 `check_*` 응답에는 정상 기준 DB의 버전이나 갱신 시각이 없고 DB 통계도 항목 수만 센다 [11][12].
- `rag-mcp`의 `search_knowledge` 결과 항목에는 색인과 임베딩 모델의 식별값이 없다 [13].
- `opencti-mcp`의 `lookup_ioc` 밖 도구 7개는 OpenCTI 버전을 응답에 싣지 않는다 [14].
- `report-mcp`의 `generate_report` 결과와 `run_command`가 사건 폴더에 저장한 출력 파일에는 버전을 적은 manifest나 메타데이터가 없다 [15][16].

**한계.** MISP 어댑터는 플랫폼 정보를 1분 동안 다시 읽지 않고 앞서 읽은 값을 싣는다 [8].
남은 시간이 1초보다 적거나 다른 조회가 그 정보를 읽는 중이어도 앞서 읽은 값을 싣는다 [8].
OpenCTI 어댑터는 질의가 실패해 답을 받지 못하면 `version`을 `null`로 둔다 [7].

### T06.02 호출 기록 메타데이터에 버전 표시

**구현.** 이 방식은 `sift-mcp`의 `run_command` 호출 기록과 `opencti-mcp`의 `lookup_ioc` 호출 기록에 적용된다 [17][18].
`run_command`는 사건 폴더 `audit/sift-mcp.jsonl`에 남기는 항목의 `result_summary`에 `tool_version`과 `resolved_path`를 싣는다 [17].
실행이 시간 제한이나 오류로 끝난 항목에도 싣는다 [5].
실행 확인에서 `fls`를 실행한 항목의 `result_summary`에 `tool_version` `4.11.1`과 `resolved_path` `/usr/bin/fls`가 있었다 [6].
`opencti-mcp`는 오류가 아닌 응답 전체를 `result_summary`에 남기므로 `lookup_ioc` 항목에는 플랫폼마다 `version`이 남는다 [18].
실행 확인에서 `audit/opencti-mcp.jsonl`의 `lookup_ioc` 항목에 `providers.opencti.version` 키가 있었다 [9].
`get_tool_help`의 호출 기록에도 `installed_version`과 `resolved_path`가 남지만 이 도구는 버전과 도움말을 묻는 도구다 [19].

### T06.04 환경 조회 도구에서만 반환

**구현.** 이 방식은 `rag-mcp`의 `get_knowledge_stats`에 적용된다 [20].
`get_knowledge_stats`는 검색에 쓰는 임베딩 모델 이름 `model`과 사용자 문서 저장소를 만든 모델 이름 `user_model`을 돌려준다 [20].
임베딩 모델 이름은 환경변수 `RAG_MODEL_NAME`의 값이고 없으면 `BAAI/bge-base-en-v1.5`다 [21].
`search_knowledge` 결과에는 이 이름이 없다 [13].

`sift-mcp`의 `check_tools`와 `get_tool_help`도 카탈로그 도구마다 `installed_version`과 `resolved_path`를 돌려준다 [22][19].
`sift-mcp`는 같은 값을 `run_command`의 응답과 호출 기록에도 싣는다 [1][17].

### T06.05 서버 자신의 버전 표시

**구현.** 이 방식은 게이트웨이가 남기는 참조 조회 기록에 적용된다 [23].
게이트웨이는 `lookup_ioc`와 `windows-triage-mcp`의 `check_*` 응답을 사건 폴더 `extractions/<audit_id>/response.json`에 저장하고 게이트웨이 호출 기록에 `reference` 항목을 남긴다 [23][24].
`reference.source_version`에는 백엔드가 초기화 응답의 `serverInfo.version`으로 알린 값을 싣는다 [23][25].
코드 주석은 이 값이 백엔드 자신의 버전이고 자료의 버전이 아니라고 적는다 [24].
다른 응답, 호출 기록, 보고서에는 서버의 패키지 버전, git 커밋, 코드 해시를 싣지 않는다 [4][15][26].

**한계.** 백엔드 7개는 MCP Python SDK의 `FastMCP`나 `Server`를 만들 때 버전을 주지 않는다 [27].
MCP Python SDK 1.30.0의 `create_initialization_options`는 버전을 받지 않은 서버의 `serverInfo.version`에 `mcp` 패키지의 버전을 싣는다 [28].
그래서 `source_version`에 남는 값은 백엔드 패키지의 버전 `0.6.5.1`이 아니라 MCP Python SDK의 버전이다 [26][28].
실행 확인에서 게이트웨이를 거친 `lookup_ioc`의 `reference.source_version`은 `1.30.0`이었다 [9].
같은 실행 확인에서 시작한 백엔드 5개의 `serverInfo.version`도 모두 `1.30.0`이었다 [9].
