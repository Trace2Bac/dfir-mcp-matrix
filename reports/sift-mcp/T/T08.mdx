# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 `sift-mcp`의 `run_command`가 마운트 도구(`ewfmount`, `mount`, `qemu-nbd`, `xmount`, `losetup`)를 실행했을 때 마운트를 기록하는 단계에 적용된다 [1][2].
`run_command`는 마운트 도구가 종료 코드 0으로 끝났을 때만 호출 기록에 `mount` 항목을 남긴다 [1].

다른 실행에서는 종료 코드로 성공과 실패를 정하지 않는다 [1][3].
`run_command` 응답의 `success`는 서버가 실행을 멈추지 않았으면 참이고 종료 코드는 `metadata.exit_code`에 그대로 싣는다 [1][3].
코드 주석은 종료 코드의 뜻이 도구와 버전마다 달라 바꾸지 않고 실행 결과는 모델이 출력과 파일로 판단한다고 적는다 [3].
실행 확인에서 Sleuth Kit 4.11.1의 `fls`가 종료 코드 1과 `Cannot determine file system type`으로 끝나자 응답의 `success`는 참, `metadata.exit_code`는 1이었다 [4].
`get_tool_help`도 도움말 실행의 종료 코드를 `help_exit_code`로 싣기만 한다 [5].

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 `sift-mcp`의 실행기와 버전·도움말 실행, 게이트웨이의 백엔드 호출, `opencti-mcp`의 플랫폼 조회에 적용된다 [6][7][8][9].
`sift-mcp`의 실행기는 호출 인자 `timeout`이 없으면 설정의 `default_timeout`(기본 600초, 환경변수 `SIFT_TIMEOUT`)을 쓴다 [6][10].
제한 시각이 지나면 프로세스를 끝내고 `ExecutionTimeoutError`를 낸다 [6].
`run_command`는 이 예외를 응답과 호출 기록의 `stopped` 값 `timeout`으로 구별하고 응답의 `success`를 거짓으로 둔다 [11].
실행 확인에서 `sleep 5`를 `timeout` 1로 실행하자 응답의 `stopped`는 `timeout`, `error`는 `Command timed out after 1s: /usr/bin/sleep 5`였다 [4].

실행기는 표준 출력과 표준 오류를 합쳐 `max_output_bytes`(기본 50MB, 환경변수 `SIFT_MAX_OUTPUT`)까지 읽고 그 양에 이르면 프로세스를 끝낸다 [6][10].
프로세스의 종료 코드가 `-SIGKILL`이면 서버가 멈춘 것으로 보고 `stopped`를 `output limit`으로 둔다 [6].
`run_command`는 이때 `success`를 거짓으로 두고 종료 코드가 도구의 것이 아니라는 문구를 `error`에 싣는다 [1].
실행 확인에서 `SIFT_MAX_OUTPUT`을 2000으로 두고 `yes`를 실행하자 `stopped`는 `output limit`, `metadata.exit_code`는 -9, `output_sha256_scope`는 `prefix`였다 [4].

버전과 도움말을 묻는 실행은 한 번에 10초와 64KiB까지만 기다리고 읽는다 [7].
도움말 실행이 10초 안에 끝나지 않으면 그때까지 나온 출력을 싣고 멈췄다는 사실을 `help_note`에 적는다 [7].

게이트웨이는 백엔드 호출의 응답을 300초까지 기다린다 [8][12].
묶음 끝점은 300초가 지나면 `Tool call <도구> timed out after 300s` 오류를 돌려준다 [8].
게이트웨이는 기다리기만 끊고 백엔드에 취소를 보내지 않는다 [8][13].
실행 확인에서 게이트웨이를 거쳐 `run_command`로 `sleep 330`을 `timeout` 400으로 실행하자 300.2초 뒤 오류가 왔다 [14].
같은 실행의 `sift-mcp` 호출 기록에는 330.5초 걸려 종료 코드 0으로 끝난 항목이 남았다 [14].

`opencti-mcp`의 `lookup_ioc`는 플랫폼마다 설정한 시간 제한과 12초 가운데 작은 값을 쓴다 [9].
그 시간에 1초를 더해도 답이 없으면 그 플랫폼을 `UNAVAILABLE`과 `timed out after <초>s`로 둔다 [9].
코드 주석은 이때 대기열에 있던 조회만 버린다고 적는다 [9].
OpenCTI 어댑터는 남은 시간을 HTTP 요청의 시간 제한으로 주고 시간이 다 되면 관계 조회를 하지 않는다 [15].

`windows-triage-mcp`와 `rag-mcp`는 서버 프로세스 안에서 대조와 검색을 하고 시간 제한을 두지 않는다 [16][17].

**한계.** 카탈로그는 도구마다 `timeout_seconds`(60초에서 7200초)를 적고 `get_tool_help`가 이 값을 보여 주지만 실행기는 이 값을 쓰지 않는다 [18][6].
실행 확인에서 카탈로그의 `timeout_seconds`는 60, 120, 300, 600, 1200, 1800, 3600, 7200초였고 `hayabusa`의 `get_tool_help`는 1800을 보였지만 실행기의 기본값은 600초였다 [4].
시간 제한으로 끊긴 실행은 그때까지 읽은 출력을 응답에도 사건 폴더에도 남기지 않는다 [6][11].
게이트웨이의 300초 대기는 `sift-mcp`의 기본 시간 제한 600초보다 짧고 호출 인자 `timeout`에는 상한이 없다 [8][10].
그래서 게이트웨이를 거친 실행이 300초를 넘으면 모델은 시간 초과 오류를 받고 백엔드의 실행과 호출 기록은 그대로 이어진다 [14].
백엔드별 끝점은 게이트웨이의 300초 대기를 거치지 않고 백엔드 연결의 300초 대기만 쓴다 [12][19].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 `opencti-mcp`의 `lookup_ioc`, `sift-mcp`의 출력 상한 처리, `rag-mcp`의 출처 필터, 게이트웨이의 백엔드 응답 처리에 적용된다 [20][21][22][23].
OpenCTI 어댑터는 다음 경우에 그 플랫폼을 `UNAVAILABLE`로 둔다 [20].

- HTTP 상태가 200이 아니다 [20].
- 답이 JSON이 아니다 [20].
- 답에 `errors`가 있거나 `data`가 없다 [20].

`errors`의 코드가 `AUTH_REQUIRED`·`FORBIDDEN_ACCESS`면 토큰 거부로, `DATABASE_ERROR`면 저장소 오류로 사유를 나눈다 [24].
답의 지표 가운데 IOC와 같은 값이 없으면 `NO_MATCH`이다 [25].
후보가 100개를 넘는데 읽은 100개 안에 같은 값이 없으면 없다고 보지 않고 `UNAVAILABLE`로 둔다 [25].
일치가 있는데 관계 조회가 실패하거나 시간이 모자라면 관계 목록을 비우고 `relationships_unavailable`에 목록이 불완전하다고 적는다 [15].
MISP 어댑터도 경고 목록 확인이 실패하면 `warninglists_unavailable`을 싣는다 [26].
어댑터의 답이 정해 둔 모양이 아니면 `UNAVAILABLE`로 바꾼다 [27].
`lookup_ioc`의 `found`는 `UNAVAILABLE`이면 `null`이다 [28].

`sift-mcp`의 실행기는 읽은 양이 출력 상한에 이르면 `truncated`를 참으로, 출력 해시의 범위 `output_sha256_scope`를 `prefix`로 둔다 [21].
`rag-mcp`는 출처 필터에 맞는 출처가 없으면 결과가 빈 까닭을 `warning`에 적는다 [22].
게이트웨이는 백엔드 응답의 MCP `isError`가 참이면 오류 응답으로 넘기고 참조 조회 기록을 남기지 않는다 [23][29].

`sift-mcp`는 출력 내용으로 실패를 정하지 않는다 [1][3].
큰 출력은 카탈로그의 `output_format`으로 파싱하고 JSON으로 읽히지 않으면 JSONL로 다시 읽으며 읽히지 않는 줄은 `_raw`로 싣는다 [30][31].

**한계.** `windows-triage-mcp`, `rag-mcp`, `opencti-mcp`는 오류를 응답 본문의 `error`로만 알리고 MCP `isError`를 쓰지 않는다 [16][17][32].
게이트웨이는 `isError`만 보므로 `windows-triage-mcp`의 `check_*`나 `lookup_ioc`가 오류 본문을 돌려줘도 참조 응답으로 저장하고 기록한다 [23][29].
실행 확인에서 OpenCTI 설정 없이 게이트웨이를 거쳐 부른 `get_entity`와 `search_threat_intel`은 본문의 `error`가 `opencti_not_configured`였고 `isError`는 거짓이었다 [33].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 `windows-triage-mcp`의 도구 13개, `rag-mcp`의 도구 3개, `opencti-mcp`의 `lookup_ioc` 어댑터에 적용된다 [16][17][27].
`windows-triage-mcp`의 처리기는 입력 검사 오류를 `validation_error`, DB 오류를 `database_error`, 서버 오류를 `server_error`, 그 밖의 예외를 `internal_error`로 나눠 돌려준다 [16].
네 경우 모두 호출 기록에 `error` 값과 호출 기록 ID를 남긴다 [16][34].
`rag-mcp`의 처리기는 `ValueError`를 `validation_error`로, 그 밖의 예외를 `internal_error`와 예외 문구로 돌려준다 [17].
`lookup_ioc`는 플랫폼 어댑터가 예외를 내면 그 플랫폼을 `UNAVAILABLE`과 예외 종류 이름으로 둔다 [27].
`sift-mcp`의 응답에 `forensic-knowledge` 해석 자료를 붙이다 예외가 나면 해석 자료 없이 응답을 만든다 [35].

**한계.** `windows-triage-mcp`의 `database_error`와 `internal_error`, `opencti-mcp`의 `internal_error`는 예외 내용 없이 서버 로그를 보라는 문구만 돌려준다 [16][32].

```python
    """{help, help_exit_code, help_cut, help_note} from the installed tool, or
    {error}. The help is what the tool printed, stdout then stderr under
    STDERR_LABEL, with its exit code: nothing here judges whether it is help
    (TSK's usage comes after "invalid option", exit 1; Hayabusa 3.9.0 answers
    dfir-timeline with "unrecognized subcommand", exit 2). The next way of
    asking is tried only when the tool printed nothing at all and answered
    in time."""
    if subcommand and (why := subcommand_error(td, subcommand)):
        return {"error": why}
    found = launch(td)
    if not found:
        return {"error": f"{td.binary} isn't installed"}
    prefix, _ = found
    if subcommand:
        tries = [[a.replace("{subcommand}", subcommand) for a in td.subcommand_help]]
    else:
        tries = [td.help_argv] if td.help_argv else [["--help"], ["-h"]]
    for argv in tries:

            return {"error": f"{td.binary} couldn't be run: {err}"}

        if late:
```

```python
    a stuck provider holds only its own threads."""
    start = time.monotonic()
    answers: dict[str, dict] = {}
    running: dict[str, tuple[float, Future]] = {}
    for name, adapter in adapters.items():
        if isinstance(adapter, Unavailable):
            answers[name] = adapter.lookup(ioc, ioc_type)  # nothing to wait for
            continue
        limit = budget(getattr(adapter, "timeout", LOOKUP_BUDGET_SECONDS))
        running[name] = (limit, _pool_for(adapter).submit(_ask, adapter, ioc, ioc_type))
    for name, (limit, future) in running.items():
        # A second's grace: the adapter's own deadline passes first.
        wait = max(0.0, start + limit + GRACE_SECONDS - time.monotonic())
        try:
            answers[name] = future.result(timeout=wait)
        except FutureTimeout:
            future.cancel()  # dropped if it was still queued
            answers[name] = unavailable(f"timed out after {limit:g}s")
    return {name: answers[name] for name in adapters}
```
