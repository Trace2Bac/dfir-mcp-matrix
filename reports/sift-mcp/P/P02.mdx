# P02 다음 작업 결정

### P02.01 고정 문서·프로필 반환

**구현.** 이 방식은 `forensic-mcp`의 분석 규율 자료와 절차 도구, 백엔드마다 보내는 초기화 지침, `sift-mcp`의 `get_tool_help`에 적용된다 [1][2][3][4].
`forensic-mcp`는 `forensic-knowledge`의 조사 틀, 규칙, 단계별 확인 사항, 조사 playbook, 아티팩트별 수집 점검표, 도구 해석 안내를 기본으로 MCP 리소스 8개와 리소스 템플릿 6개로 내놓는다 [1].
시작 인자 `--deferred-tools`를 주면 같은 자료를 `list_playbooks`, `get_playbook`, `get_collection_checklist` 같은 도구 14개로 내놓고 게이트웨이 설정 예시는 이 인자로 `forensic-mcp`를 실행한다 [1][5].
리소스 방식으로 만든 서버는 도구가 10개였고 `--deferred-tools` 방식으로 만든 서버는 도구가 24개였다 [6].
`get_procedure`는 저장소 `skills/`의 `MANIFEST`에 적힌 파일만 골라 절차 이름과 설명, 절차의 `SKILL.md`와 딸린 파일을 돌려준다 [2].
`forensic-mcp`의 초기화 지침 `instructions`는 사건을 만들거나 연 뒤 맥락 묻기, 증거 살피기, 색인, 범위 정하기, 도구 목록 확인, 분류 우선순위, 그때그때 기록하기의 차례를 적는다 [3].
게이트웨이는 백엔드별 끝점 `/mcp/<백엔드>`에서 그 백엔드의 지침을 보내고 모아 둔 끝점 `/mcp`에서는 도구 이름별 쓰임만 적은 짧은 안내 `GATEWAY`를 보낸다 [7].
`get_tool_help`는 설치된 분석 도구의 버전에 맞는 사용 예시와 `forensic-knowledge`의 주의 사항, 조사 순서 `investigation_sequence`를 함께 돌려준다 [4].

**한계.** `get_procedure`는 설치 파일 위치에서 네 단계 위의 저장소 폴더에 `skills/`가 있어야 동작한다 [2].
패키지로만 설치한 서버에서는 `procedures aren't installed with this forensic-mcp` 오류만 돌아왔다 [6].
`list_playbooks`는 playbook의 표시 이름만 돌려주고 `get_playbook`은 파일 이름으로 된 식별자를 받는다 [8].
목록의 표시 이름으로 `get_playbook`을 부르자 오류와 함께 받을 수 있는 식별자 목록이 돌아왔다 [6].

### P02.02 규칙·조사 상태로 추천

**구현.** 이 방식은 `sift-mcp`의 `suggest_tools`와 `run_command` 응답, `case-mcp`의 `case_init`, `case_activate`, `case_status` 응답에 적용된다 [9][10][11][12].
`suggest_tools`는 아티팩트마다 `forensic-knowledge`에 적힌 관련 도구를 골라 도구마다 이 시스템에 설치되었는지를 `available`에 싣는다 [9].
`~/.vhir/gateway.yaml`에 `wintools-mcp`가 없으면 `srum`, `prefetch`, `registry`, `digital_signatures`에 Windows 쪽 도구를 쓰라는 안내를 더한다 [13].
`prefetch`를 묻자 PECmd를 쓰는 `wintools-mcp`를 준비하라는 안내가 첫 항목으로 돌아왔다 [6].
`run_command` 응답은 실행한 도구와 판별한 아티팩트에 따라 교차 확인할 아티팩트, 다른 백엔드에서 할 확인, 이어서 쓸 다른 백엔드의 도구를 싣는다 [10].
`case_init`은 조사 동기 묻기와 증거 살피기 같은 정해 둔 다음 작업 목록을 싣고 사건에 호스트 목록이 없으면 그 목록을 먼저 올리라는 안내 `host_list_hint`를 더한다 [11].
`case_activate`는 `opensearch_mcp`가 설치되어 있으면 색인 상태를 보라는 안내를 더한다 [11].
`case_status`는 설치된 패키지와 게이트웨이 설정에서 찾은 백엔드로 쓸 수 있는 조사 수단 목록과 `suggest_tools`를 부르라는 안내를 만든다 [12].

다음 작업을 묶음으로 실행하는 도구나 서버 안에서 모델을 불러 계획을 만드는 코드는 없다.
`log_reasoning`의 설명은 기록하지 않은 추론은 문맥 압축 때 사라진다고 적지만 압축 뒤 저장한 상태를 다시 읽으라는 안내는 없다 [14].

**한계.** `run_command` 응답의 교차 확인 안내와 다른 백엔드 도구 안내는 도구마다 처음 3번과 그 뒤 10번째마다만 실린다 [10].
이 횟수는 사건이나 세션과 상관없이 프로세스 하나에 하나뿐이어서 사건을 바꾼 뒤에도 앞 사건에서 센 횟수가 이어진다 [10].
`case_status`의 조사 수단 목록은 패키지가 설치되었는지와 설정에 이름이 있는지만 보고 그 백엔드에 연결해 보지 않는다 [12].

1. ASK FOR CONTEXT — Before touching evidence, ask the examiner: What triggered this investigation? What time window is relevant? Which hosts/users are involved? What evidence has been collected? 2. SURVEY EVIDENCE — List what's available (ls evidence/). Identify artifact types: KAPE triage packages, disk images, memory dumps, logs, packet captures. Report to examiner: "I see X hosts of KAPE triage, Y memory images, Z log files."

4. 5. TRIAGE PRIORITIES — Standard DFIR sequence: authentication anomalies (4624/4625/4648), lateral movement (type 3/10 logons across hosts), persistence mechanisms (services, scheduled tasks, Run keys), execution artifacts (process creation, script blocks), data staging/exfiltration indicators.
