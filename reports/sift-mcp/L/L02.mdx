# L02 기록 구성

### L02.01 MCP 요청 기록

**구현.** 이 방식은 공통 기록기 `AuditWriter`로 쓰는 게이트웨이와 백엔드 7개의 항목에 적용된다 [1].
항목은 `tool` 필드에 도구 이름을, `params` 필드에 인자를 담는다 [1].
`windows-triage-mcp`·`rag-mcp`·`opencti-mcp`는 SDK가 넘긴 `arguments`를 고치지 않고 `params`에 넣는다 [2][3].
`rag-mcp`가 `top_k`를 1~50으로 바꾸는 처리도 `params`에는 바꾸기 전 값으로 남는다 [2][4].
게이트웨이 항목은 인자 값을 문자열로 바꿔 1000자가 넘으면 앞 1000자에 `...`를 붙여 남긴다 [5].
`sift-mcp`의 `run_command`는 모델이 준 `command` 목록과 `purpose`를 `params`에 넣는다 [6].
`run_command`로 `echo`를 실행하자 `params.command`에는 준 그대로의 `echo`가 남았다 [7].

**한계.** FastMCP 백엔드 4개는 도구마다 고른 인자만 `params`에 넣는다 [6][8].
`run_command`는 `timeout`·`save_output`·`input_files`·`preview_lines`·`skip_enrichment`를 남기지 않는다 [6].
`record_finding`은 `finding`만 남기고 `supporting_commands`·`artifacts`·`analyst_override`는 남기지 않는다 [8].
`update_todo`·`complete_todo`는 `todo_id`만 남긴다 [8].
`prepare_host_list`는 받은 글 대신 그 바이트 수를 남긴다 [9].

### L02.02 서버가 변환한 연산·인자 기록

**구현.** 이 방식은 게이트웨이의 HTTP 백엔드 항목과 `report-mcp`의 `save_report` 항목에 적용된다 [10][11].
게이트웨이는 두 백엔드에 같은 도구 이름이 있으면 `<백엔드>__<도구>`로 내놓고 호출을 받을 때 앞의 백엔드 이름을 떼어 낸다 [12].
항목의 `tool`에는 떼어 낸 뒤 실제로 백엔드에 보낸 이름이 들어가고 `backend`에 백엔드 이름이 들어간다 [10].
`save_report`는 받은 파일 이름에서 영문자·숫자·`.`·`_`·`-`가 아닌 글자를 `_`로 바꾼 값을 `params.filename`에 넣는다 [11].
본문 대신 그 글자 수를 `characters`로 넣는다 [11].

**한계.** 게이트웨이가 `analyst_override`를 바꿔 넣는 도구는 설정 예시에서 모두 stdio 백엔드인 `forensic-mcp`·`case-mcp`의 도구라 게이트웨이 항목에 그 값이 남지 않는다 [13][10].
`rag-mcp`의 `top_k` 조정처럼 백엔드가 인자 값을 바꾼 결과는 항목에 남지 않는다 [2][4].

### L02.03 외부 실행 명령 기록

**구현.** 이 방식은 `sift-mcp`의 `run_command`에 적용된다 [6].
`run_command`는 인자 배열을 셸 없이 그대로 실행하고 항목의 `params.command`에 그 배열을 목록으로 남긴다 [6][14].
첫 원소 말고는 실행한 인자와 남긴 인자가 같다 [14].
분석 도구 목록에 있는 도구면 실행 전에 찾은 실행 파일 경로와 버전을 `result_summary`의 `resolved_path`·`tool_version`에 넣는다 [15][6].

**한계.** 서버는 실행 전에 첫 원소의 경로 부분을 떼고 그 이름을 `PATH`와 정해 둔 폴더 4곳에서 찾은 절대 경로로 바꾸며 Zimmerman 도구는 `dotnet <도구>.dll`로 바꿔 실행한다 [14][16].
모델이 첫 원소에 경로를 주어도 실행되는 것은 그 이름으로 찾은 실행 파일이고 항목의 `params.command`에는 모델이 준 경로가 남는다 [16][6].
항목에는 이렇게 바꾼 실제 실행 배열이 남지 않는다 [6].
`echo`를 실행하자 응답의 `command`는 `/usr/bin/echo`였고 항목의 `params.command`는 `echo`였다 [7].
`forensic-mcp`의 `supporting_command` 항목과 `case-mcp`의 `log_external_action` 항목은 모델이 적은 명령 문자열이고 서버가 실행한 명령이 아니다 [17][18].

### L02.05 결과 상태·실행 시점 기록

**구현.** 이 방식은 공통 기록기 `AuditWriter`로 쓰는 모든 항목에 적용된다 [1].
항목의 `ts`는 항목을 쓰는 때의 UTC 시각이고 모든 경로에서 처리를 마친 뒤 쓴다 [1][19].
`run_command`는 실행이 끝나면 `exit_code`를, 서버가 출력 상한에서 멈췄으면 `stopped`를 함께 `result_summary`에 넣는다 [6][20].
시간 제한이면 `error`와 `stopped`를, 거부나 실행 오류면 `error`를 넣는다 [6].
`run_command`와 저수준 백엔드 3개는 걸린 시간을 `elapsed_ms`로 남긴다 [6][2].
저수준 백엔드 3개는 오류면 `result_summary`를 `{"error": <오류 코드>}`로 두고 아니면 결과 `dict` 전체를 둔다 [2].
게이트웨이는 HTTP 백엔드 응답의 `exit_code`·`success`·`error`·`truncated`·`found`만 골라 넣고 시간 제한은 `timeout after 300s`, 거부는 `refused, not sent:` 문구로 남긴다 [21][22][23].
`mkfs`를 부르자 항목의 `result_summary`에는 `exit_code` 없이 `error`만 남았다 [7].

**한계.** 시작 시각은 남지 않고 `get_tool_help`·`add_todo` 같은 FastMCP 도구 항목에는 `elapsed_ms`도 없다 [1][8].
FastMCP 도구는 결과 `dict`를 그대로 `result_summary`에 넣으므로 성공과 실패를 가르는 필드가 도구마다 다르다 [8][24].

### L02.06 결과 참조·요약값 기록

**구현.** 이 방식은 `sift-mcp`의 `run_command`와 게이트웨이의 참조 조회 항목에 적용된다 [6][25].
`run_command` 항목은 표준 출력 원래 바이트의 SHA-256 `output_sha256`, 그 해시가 전체인지 앞부분인지를 적은 `output_sha256_scope`, 보관 파일 경로 `output_file`, 바이트 수 `stdout_bytes`를 남긴다 [6][20].
표준 출력 앞 500자는 `stdout_head`로 함께 남긴다 [6].
입력과 출력 파일은 `inputs`·`outputs`에 경로와 해시를 담는다 [6].
게이트웨이는 `lookup_ioc`·`check_*` 응답의 내용을 사건 폴더 `extractions/<항목 ID>/response.json`에 쓰고 항목의 `reference.response`에 그 경로와 SHA-256을 남긴다 [25].
`lookup_ioc`를 부르자 게이트웨이 항목에 `response.json` 경로와 해시가 남았다 [26].
`get_tool_help`는 도움말 대신 바이트 수 `help_bytes`를 남기고 `export_bundle`은 발견사항과 타임라인 건수를 남긴다 [27][28].

**한계.** `output_sha256`은 표준 출력만의 해시이고 표준 오류의 해시는 항목에 없다 [6][20].
게이트웨이 참조 항목의 `reference.source_version`은 백엔드가 초기화 응답에 적은 서버 버전을 남긴다 [25][29].
`opencti-mcp`와 `windows-triage-mcp`는 저수준 `Server`를 만들 때 버전을 주지 않아 MCP Python SDK 1.30.0이 SDK 패키지 버전을 서버 버전으로 보낸다 [30][31].
그래서 이 필드에는 백엔드 버전 대신 `1.30.0`이 남았다 [26].

### L02.07 호출 ID로 항목 연결

**구현.** 이 방식은 게이트웨이 항목과 `run_command`의 백그라운드 해시 항목에 적용된다 [10][32].
게이트웨이 항목은 백엔드 응답에 들어 있는 백엔드의 `audit_id`를 `backend_audit_id`에 넣는다 [10][33].
`lookup_ioc`를 부르자 게이트웨이 항목의 `backend_audit_id`가 `opencti-mcp.jsonl` 항목의 `audit_id`와 같았다 [26].
`run_command`가 인라인 한도를 넘는 입력 파일을 백그라운드로 해시하면 항목의 입력 기록에 작업 ID `job_id`를 남기고 그 작업이 끝날 때 쓰는 `hash_complete` 항목에도 같은 `job_id`를 넣는다 [32][34].
`run_command`의 `audit_id`는 그 실행의 출력 폴더 `extractions/<audit_id>/` 이름으로도 쓴다 [6].

    """Truncate large param values for audit storage."""
    truncated = {}
    for k, v in params.items():

        truncated[k] = s[:max_len] + "..." if len(s) > max_len else v
    return truncated

def find_binary(name: str, extra_paths: list[str] | None = None) -> str | None:
    """Find a binary on PATH or in common forensic tool locations."""
    # shutil.which checks PATH
    found = shutil.which(name)
    if found:
        return found

    # Check extra paths
    search_paths = extra_paths or [
        "/usr/local/bin",
        "/opt/zimmerman",
        "/opt/volatility3",
        "/opt/hayabusa",
    ]
    for d in search_paths:
        candidate = Path(d) / name
        if candidate.is_file() and os.access(candidate, os.X_OK):
            return str(candidate)

    return None
