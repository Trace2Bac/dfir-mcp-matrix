# L01 기록 방식

### L01.01 공통 요청 처리 단계에서 기록

**구현.** 이 방식은 저수준 `Server`로 만든 `windows-triage-mcp`·`rag-mcp`·`opencti-mcp`의 모든 도구와 게이트웨이의 도구 호출 경로에 적용된다 [1][2][3][4].
세 백엔드의 `call_tool` 처리기는 도구를 고르기 전에 호출 ID를 만들고 처리가 끝나면 성공과 오류를 가리지 않고 `_wrap_response`를 부른다 [1][2][3].
`_wrap_response`는 공통 기록기 `AuditWriter.log`로 사건 폴더 `audit/`의 백엔드별 JSONL 파일에 항목 하나를 쓴다 [1][5].
등록되지 않은 도구 이름으로 부른 호출도 오류 결과로 이 자리를 지난다 [2][3].
`lookup_ioc`를 두 번 부르자 `opencti-mcp.jsonl`에 호출마다 항목이 하나씩 남았다 [6].

게이트웨이는 모아서 내놓는 끝점(`/mcp`, REST `/api/v1/tools/{name}`)의 `Gateway.call_tool`과 백엔드별 끝점(`/mcp/<백엔드>`)의 `_call_tool` 두 곳에서 항목을 쓴다 [4][7].
두 곳 모두 HTTP 백엔드로 보낸 호출에만 `source`가 `gateway_proxy`인 항목을 쓰고 stdio 백엔드는 백엔드가 스스로 쓴다고 보고 쓰지 않는다 [4][7].
`wintools-mcp`의 상태 조회 도구 `get_windows_run`은 HTTP 백엔드여도 항목을 쓰지 않는다 [8].
보내기 전에 거부한 호출(인자에 UTF-8로 보낼 수 없는 문자가 있는 경우)은 백엔드 종류와 관계없이 `audit_refusal`로 항목을 쓴다 [9].
`opencti-mcp`의 `lookup_ioc`와 `windows-triage-mcp`의 `check_*` 도구는 오류가 아닌 응답이면 stdio 백엔드여도 게이트웨이가 참조 조회 항목을 따로 쓴다 [10].
게이트웨이에 `sift-mcp`와 위협 정보 백엔드를 stdio로 붙여 `run_command`와 `lookup_ioc`를 부르자 `sift-gateway.jsonl`에는 `lookup_ioc` 두 건만 남았다 [6].
게이트웨이는 호출마다 운영 로그에 도구 이름, 백엔드, 검토자 이름을 적고 인자는 적지 않는다 [4][6].

**한계.** 사건 폴더를 찾지 못하면 `AuditWriter.log`는 항목을 쓰지 않고 `None`을 돌려준다 [5].
게이트웨이의 `Gateway.call_tool`은 시간 제한 말고 백엔드 호출이 예외로 끝나면 항목을 쓰기 전에 예외를 올린다 [4].
백엔드별 끝점은 백엔드 시작 실패와 백엔드 호출 예외를 항목 없이 오류로 돌려준다 [7].
그래서 HTTP 백엔드 호출이 연결 오류로 끝나면 게이트웨이 항목이 남지 않는다.
stdio 백엔드 호출이 300초 시간 제한에 닿으면 게이트웨이는 항목을 쓰지 않고 백엔드 쪽 항목은 백엔드가 처리를 마친 뒤에야 쓴다 [4][1].

### L01.02 도구별 기록 호출

**구현.** 이 방식은 FastMCP로 만든 `forensic-mcp`·`sift-mcp`·`case-mcp`·`report-mcp`의 도구에 적용된다 [11][12][13][14].
네 백엔드에는 모든 호출이 지나는 기록 단계가 없고 도구 본문이 처리를 마친 뒤 `audit.log`를 직접 부른다 [11][12][13][14].
`run_command`·`add_todo`·`case_init`·`log_reasoning`을 부르자 백엔드별 JSONL 파일에 호출마다 항목이 하나씩 남았다 [15].
`forensic-mcp`의 `record_finding`은 도구 항목 말고도 `supporting_commands`의 셸 명령마다 `supporting_command` 항목을 쓴다 [16].
`sift-mcp`의 `run_command`와 `case-mcp`의 `log_external_action`이 입력 파일 해시를 백그라운드로 계산하면 그 작업이 끝날 때 `file-identity.jsonl`에 `hash_complete` 항목을 더 쓴다 [17].

다음 도구는 사건 기록에 항목을 쓰지 않는다.
- `forensic-mcp`의 `get_findings`·`get_timeline`·`get_actions`·`list_todos` [18].
- `case-mcp`의 `case_list`·`case_status`·`evidence_list`·`evidence_verify`·`audit_summary` [19].
- `report-mcp`의 `get_case_metadata`·`list_profiles`·`list_reports` [20].
- `sift-mcp`의 `list_available_tools`·`check_tools`와 `forensic-mcp`의 `get_procedure`, `--deferred-tools`로 내놓는 규율 자료 도구 가운데 `get_investigation_framework`를 뺀 13개 [12][21].

마지막 줄의 도구는 사건 밖 파일 `~/.vhir/logs/lookups.jsonl`에 `log_lookup`으로 한 줄을 쓴다 [21][22].
이 줄에는 시각, 백엔드, 도구 이름, 사건 이름과 문자열·정수·참·거짓 값의 인자만 들어가고 문자열은 120자에서 자른다 [22].
`check_tools`를 `tool_names` 목록과 함께 부르자 `args`가 빈 줄이 남았다 [15].

같은 저장소의 Claude Code 훅 `forensic-audit.sh`는 클라이언트의 Bash 명령과 그 출력 해시를 사건 폴더의 `claude-code.jsonl`에 남긴다 [23].
이 훅은 MCP 도구 호출을 기록하지 않고 MCP 도구에 대응하는 Bash 명령에 `mcp_route` 표시만 붙인다 [23].
Codex용 훅 설정도 `Bash`와 `apply_patch`에만 이 훅을 등록한다 [24].

**한계.** 사건 폴더를 찾지 못하면 항목을 쓰지 않는다 [5].
사건이 없을 때 `run_command`를 부르자 명령은 실행되었고 응답의 `audit_id`는 `null`이었다 [15].
`report-mcp`는 `AuditWriter`에 사건 폴더 확인 함수를 넘기지 않아 `generate_report`가 `case_id`로 다른 사건을 고르면 항목은 지금 활성 사건의 `audit/`에 들어간다 [14][25].

        self,
        tool_name: str,
        arguments: dict,
