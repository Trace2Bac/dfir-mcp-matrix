# R01 결과 가공

### R01.01 가공 없이 전달

**구현.** 이 방식은 `sift-mcp`의 `run_command`에서 표준 출력이 응답 예산 이하인 경우와 `get_tool_help`의 도움말에 적용된다 [1][2].
`run_command`는 표준 출력이 `response_byte_budget`(기본 10,240바이트) 이하이면 실행 결과 `dict`를 파싱하지 않고 응답의 `data`에 싣는다 [1].
이 `data`에는 도구가 쓴 표준 출력 `stdout`과 표준 오류 `stderr`, 실행한 명령 `command`, 종료 코드가 들어간다 [1][3].
(실행 확인) 사건 안에서 `echo hello`를 실행하자 `data.stdout`은 `hello\n` 그대로였고 `data.command`에는 실제 경로로 바꾼 실행 파일과 인자가 실렸다 [3].
`get_tool_help`는 설치된 도구가 출력한 도움말을 표준 출력, 구분 줄, 표준 오류 차례로 이어 `help`에 싣는다 [2].
`opencti-mcp`의 `lookup_ioc`는 플랫폼마다 `providers.<이름>` 아래 플랫폼이 돌려준 레코드를 플랫폼의 필드 이름 그대로 싣는다 [4].
OpenCTI 레코드는 서버가 정한 GraphQL 필드 목록 `SELECTION`으로 읽은 값이다 [4].

### R01.02 구조화 파싱·필드 선택

**구현.** 이 방식은 `sift-mcp`의 `run_command`에서 표준 출력이 응답 예산을 넘는 경우, `sift-mcp`의 버전 확인, `opencti-mcp`의 검색 도구와 `lookup_ioc`의 MISP 레코드, `rag-mcp`의 `search_knowledge`에 적용된다 [5][6][7][8][9].
`run_command`는 표준 출력이 응답 예산을 넘으면 도구 목록 `catalog`에 적힌 출력 형식으로 표준 출력을 파싱한다 [5].
CSV는 열 이름을 키로 한 행 `dict`의 목록 `rows`로, JSON은 배열 항목이나 JSONL 줄의 객체로, 그 밖의 글은 줄 목록 `lines`로 바꾼다 [5].
이때 응답의 `data`에는 파싱한 미리보기만 들어가고 실행 결과의 `stdout`·`stderr`·`command`는 들어가지 않는다 [1][5].
(실행 확인) CSV를 출력하는 `EvtxECmd` 시험용 실행 파일로 400행을 내자 `data`에는 `columns`·`rows`·`total_rows`·`preview_rows`·`preview_bytes`·`truncated`만 있었고 표준 오류는 응답에 없었다 [10].
`get_tool_help`·`check_tools`와 `run_command`는 도구의 버전 출력에서 정해 둔 정규식으로 버전 문자열만 골라 `installed_version`·`tool_version`에 싣는다 [6].
`get_tool_help`·`check_tools`는 버전을 고르지 못하면 `installed_version`을 `unknown`으로 두고 출력의 첫 줄을 200자까지 `version_output`에 싣는다 [6].
`opencti-mcp`의 검색 도구는 OpenCTI 객체에서 유형마다 정한 필드만 골라 결과 항목을 만든다 [7].
예를 들어 지표 항목은 이름, 패턴, 패턴 유형, 설명, 신뢰도, 생성 시각, 레이블만 싣는다 [7].
`lookup_ioc`의 MISP 레코드는 속성의 `uuid`·`type`·`value`·`to_ids`·`decay_score`와 이벤트의 정해 둔 필드만 싣는다 [8].
`rag-mcp`의 `search_knowledge`는 색인 레코드의 메타데이터에서 `source`·`mitre_techniques`·`platform`·`title`을 골라 순위, 점수, 본문과 함께 싣는다 [9].

### R01.03 형식 변환·건수 집계

**구현.** 이 방식은 `sift-mcp`의 `run_command`에서 표준 출력이 응답 예산을 넘는 경우, `opencti-mcp`의 `lookup_ioc`, `windows-triage-mcp`의 `check_registry`·`check_hijackable_dll`, `case-mcp`의 `evidence_verify`·`audit_summary`에 적용된다 [5][11][12][13][14][15][16].
`run_command`는 CSV 출력을 JSON 객체 목록으로 바꾸고 전체 행 수와 미리보기 행 수를 센다 [5].
`lookup_ioc`는 OpenCTI 레코드 가운데 철회되지 않은 일치 레코드에서 신뢰도의 최댓값, 레이블의 합집합, 가장 이른 생성 시각을 계산해 최상위 `confidence`·`labels`·`created`에 싣는다 [11].
같은 레코드에 걸린 관계를 따라 위협 행위자, 악성코드, ATT&CK 기법 이름을 모아 `related_threat_actors`·`related_malware`·`mitre_techniques`에 싣는다 [11].
최상위 `outcome`은 플랫폼 하나라도 일치하면 `MATCH`, 그렇지 않고 하나라도 묻지 못했으면 `UNAVAILABLE`, 나머지는 `NO_MATCH`로 묶은 값이다 [12].
`check_registry`는 기준 DB의 일치 행에서 OS 버전 수 `os_version_count`, 일치 수 `match_count`, 값 수 `value_count`를 센다 [13].
`check_hijackable_dll`은 DLL hijacking 사례를 hijack 유형별로 묶고 사례 수를 `total_scenarios`에 싣는다 [14].
`evidence_verify`는 증거 파일마다 대조한 결과를 상태별로 세어 `verified`·`modified`·`missing`·`errors`에 싣는다 [15].
`audit_summary`는 사건의 호출 기록을 서버별·도구별로 세어 돌려준다 [16].

### R01.04 가공 사실·대상 표시

**구현.** 이 방식은 `sift-mcp`의 `run_command` 응답에 적용된다 [17].
응답의 `output_format`은 파싱하지 않은 출력이면 도구 목록의 형식(`text`·`csv`·`json`)이고 미리보기로 파싱한 출력이면 `parsed_text`·`parsed_csv`·`parsed_json`이다 [5][17].
응답에는 도구 목록에 있는 도구를 실행했을 때만 그 버전 `tool_version`과 실제로 실행한 경로 `resolved_path`가 실린다 [17][6].
사건 안에서 실행한 `run_command`는 남긴 원래 표준 출력의 경로 `full_output_path`, 해시 `full_output_sha256`, 바이트 수 `full_output_bytes`를 싣는다 [18][19].
(실행 확인) 사건 안에서 20,000줄을 출력하자 `output_format`은 `parsed_text`였고 `full_output_path`에 사건 폴더 `extractions/` 아래 표준 출력 파일 경로가 실렸다 [20].
`lookup_ioc`의 최상위 요약 필드에는 요약한 플랫폼을 `source`에 `opencti`로 적는다 [11].

**한계.** 응답을 만드는 `build_response`는 실행한 명령을 인자 `command`로 받지만 응답에 넣지 않는다 [17].
그래서 표준 출력이 응답 예산을 넘어 파싱한 응답에는 실행한 명령과 입력 경로가 없다 [1][17].
도구 목록에 없는 실행 파일의 파싱한 응답에는 어느 프로그램의 출력인지 가리키는 값이 없다 [17][6].
사건 없이 실행하면 `save_output`을 주어도 원래 출력을 남기지 않으므로 파싱한 응답에 `full_output_path`가 없다 [19][21].
(실행 확인) 사건 없이 20,000줄을 출력하자 응답에는 `parsed_text` 미리보기만 있었고 `full_output_path`·`output_files`가 없었다 [21].
(실행 확인) 사건 없이 `save_output`을 참으로 주고 `seq 1 20000`을 실행해도 `full_output_path`·`output_files`가 없었다 [22].

### R01.06 응답 항목 선별

**구현.** 이 방식은 `opencti-mcp`의 `lookup_ioc`·`search_threat_intel`·`search_entity`와 `rag-mcp`의 `search_knowledge`에 적용된다 [23][24][25][26].
`lookup_ioc`는 플랫폼이 돌려준 레코드 가운데 값이 IOC와 정확히 같은 것만 `matches`에 싣는다 [23][24].
같은지는 IP 주소면 주소 값으로, SSDEEP·TLSH 해시면 대소문자까지, 그 밖에는 대소문자를 무시하고 판단한다 [23].
OpenCTI는 이름이 IOC와 같은 지표를 질의하고 서버가 위 규칙으로 다시 고른다 [23].
MISP는 값으로 속성을 찾고 서버가 값이나 복합 속성(`domain|ip` 등)의 두 값 가운데 하나가 IOC와 같은 속성만 고른다 [24].
(실행 확인) OpenCTI 응답 대신 `Evil.COM`과 `evil.com.example` 지표를 돌려주는 시험용 전송 함수로 `evil.com`을 조회하자 `matches`에는 `Evil.COM`만 실렸다 [27].
`search_threat_intel`과 `search_entity`의 위협 행위자 검색은 OpenCTI의 intrusion set과 threat actor group 결과를 합친 뒤 ID가 같은 항목을 하나만 남긴다 [25].
`search_knowledge`는 배포 색인과 사용자 색인에서 가까운 레코드를 모은 뒤 ID와 본문이 모두 같은 레코드를 하나만 남긴다 [26].
남긴 항목의 값은 바꾸지 않는다.

### R01.07 응답 선별 사실·건수 표시

**구현.** 이 방식은 `lookup_ioc`가 정확히 같은 레코드를 하나도 고르지 못하고 후보가 읽은 한도를 넘은 경우에 적용된다 [28].
이 경우 그 플랫폼의 결과를 `UNAVAILABLE`로 두고 `reason`에 후보 수와 읽은 후보 가운데 정확히 같은 값이 없다는 사실을 적는다 [28].
OpenCTI는 이름이 IOC와 같은 지표를 묻는 질의의 전체 수 `globalCount`와 읽은 수를, MISP는 100건을 넘는 속성이 있었다는 사실을 적는다 [28].
(실행 확인) MISP 응답 대신 IOC를 포함한 다른 도메인 속성 101건을 돌려주자 MISP 결과는 `UNAVAILABLE`이고 `reason`은 "too many candidate matches: more than 100 attributes match evil.com, and none of those read is exactly it"였다 [29].

**한계.** 정확히 같은 레코드가 하나라도 있거나 후보가 한도 안이면 `lookup_ioc` 응답에는 걸러 낸 레코드의 수나 거른 규칙이 없다 [23][24].
걸러 낸 규칙은 도구 설명에만 있다 [30].
위협 행위자 검색과 `search_knowledge`의 응답에도 중복으로 뺀 항목의 수가 없다 [25][26].

def _is_the_ioc(attribute: dict, ioc: str) -> bool:
    value = attribute.get("value")
    if not isinstance(value, str):
