# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 이 방식은 `sift-mcp`의 `run_command`에서 표준 출력이 응답 예산 이하인 경우와 `case-mcp`의 `evidence_verify`에 적용된다 [1][2].
`run_command`는 이때 실행 결과를 그대로 `data`에 싣고 그 `command`에는 모델이 넘긴 증거 경로 인자가 들어 있다 [1].
(실행 확인) `yara -s`로 시험 파일을 검사한 응답의 `data.command`에 규칙 파일과 검사한 파일의 경로가 실렸다 [3].
`evidence_verify`는 결과 항목마다 대조한 증거 파일의 경로를 `path`에 싣는다 [2].
`run_command` 응답의 `audit_id`는 호출 기록 항목의 ID이고 그 항목에는 명령이 읽은 파일의 경로, 해시, 등록 증거와의 연결이 남는다 [4].
호출 기록 항목을 ID로 돌려주는 MCP 도구는 찾지 못했고 `case-mcp`의 `audit_summary`는 항목 수만 센다 [5].

**한계.** 표준 출력이 응답 예산을 넘어 파싱한 `run_command` 응답에는 실행한 명령이 없으므로 증거 경로도 없다 [6].
(실행 확인) 사건 안에서 큰 출력을 낸 `seq`와 `EvtxECmd` 시험용 실행의 응답 최상위와 `data`에는 `command` 키가 없었다 [7].
실행 전 거부로 끝난 응답은 `data`를 비우므로 실행한 명령이 없다 [8].
시간 제한으로 끝난 응답은 `data`를 비우고 `error` 문구에만 실행 명령을 공백으로 이어 싣는다 [8][9].

### R05.02 증거 내부 경로

**구현.** 이 방식은 `run_command`가 실행한 분석 도구의 출력에 적용된다 [1][10].
`run_command`는 Sleuth Kit `fls`처럼 증거 안 경로를 적는 출력을 그대로 싣고 CSV 출력은 행으로 파싱해도 열 값을 바꾸지 않는다 [1][10].
(실행 확인) 직접 만든 ext2 이미지를 `fls -r`로 나열하자 응답의 `stdout`에 이미지 안 파일 이름 `note.txt`, `docs`, `b.txt`가 그대로 실렸다 [11].
이 출력에서 하위 폴더의 파일은 폴더 단계 표시 `+`와 이름만 적히므로 증거 안 전체 경로는 앞선 폴더 줄을 따라가 맞춰야 한다 [11].

### R05.03 레코드 키·번호

**구현.** 이 방식은 `run_command`가 실행한 분석 도구의 출력에 적용된다 [1][10].
`fls` 출력의 메타데이터 주소(inode)나 CSV 출력의 레코드 번호 열 같은 값은 응답에 그대로 남는다 [1][10].
(실행 확인) 위 `fls` 응답의 줄마다 `11`·`12`·`13`·`14` 같은 inode 번호가 실렸다 [11].
(실행 확인) `EventRecordId` 열을 가진 CSV를 출력하는 `EvtxECmd` 시험용 실행 파일의 응답에서 행마다 `EventRecordId` 값이 그대로 실렸다 [12].

### R05.04 바이트·섹터·행 오프셋

**구현.** 이 방식은 `run_command`가 실행한 분석 도구의 출력에 적용된다 [1].
YARA를 `-s`로 실행하면 일치한 문자열마다 파일 안 바이트 오프셋이 출력되고 `run_command`는 그 출력을 그대로 싣는다 [1][13].
(실행 확인) 문자열 `MARKER`가 두 번 들어간 시험 파일에 `yara -s`를 실행하자 `stdout`에 `0xa:$a: MARKER`와 `0x14:$a: MARKER`가 실렸다 [3].

### R05.05 참조 지식 원문 출처

**구현.** 이 방식은 `opencti-mcp`의 `lookup_ioc`·`get_entity`와 검색 도구 일부에 적용된다 [14][15][16].
`lookup_ioc`는 OpenCTI 레코드마다 OpenCTI ID `id`를, MISP 레코드마다 속성의 `uuid`와 이벤트의 `uuid`를 싣는다 [14].
`get_entity`는 객체의 외부 참조에서 출처 이름과 URL을 `external_references`에 싣는다 [15].
campaign, tool, infrastructure 같은 유형의 검색 결과 항목은 OpenCTI ID를 싣고 공격 기법 항목은 ATT&CK ID를 `mitre_id`에 싣는다 [16].

`rag-mcp`의 `search_knowledge`는 결과 항목마다 지식 원천의 이름 `source`와 레코드 제목 `title`을 싣고 원문 주소나 레코드 ID는 싣지 않는다 [17].
`windows-triage-mcp`의 `check_lolbin`은 기준 DB의 LOLBin 행에 원문 주소 `source_url`이 있어도 응답에는 이름, 설명, 기능, ATT&CK 기법, 탐지 안내만 싣는다 [18].
`check_pipe`도 기준 DB 행의 `microsoft_doc_url`을 응답에 싣지 않는다 [19].
`check_hash`는 취약 드라이버 표의 행을 `vulnerable_driver`에 그대로 싣고 이 행에는 CVE 번호 `cve`가 있지만 원문 주소나 원문 항목 ID 열은 없다 [20].
`run_command`·`suggest_tools`가 싣는 FK 지식에는 출처가 없다 [21][22].

**한계.** 지표, 위협 행위자, 악성코드, 취약점, 보고서 검색 결과 항목에는 OpenCTI ID와 외부 참조가 없다 [23].
`get_entity`는 외부 참조를 5개까지 싣는다 [15].

### R05.06 참조 지식과 증거 결과 구분

**구현.** 이 방식은 `rag-mcp`의 `search_knowledge`에 적용된다 [24].
`search_knowledge`의 응답은 검색 결과만 `results`에 싣고 `caveats`에 결과가 사건 증거가 아니라 참조 지식이라고 적는다 [24].
사용자가 넣은 문서 색인이 함께 열려 있으면 결과마다 `origin`에 배포 색인(`shipped`)인지 사용자 색인(`user`)인지 싣는다 [25].
`caveats`는 색인 상태와 관계없이 `user` 결과가 공개 참조 자료가 아니라 사용자의 자료라는 문장도 싣는다 [24].

`sift-mcp`의 `run_command`는 FK 지식을 `data`와 다른 최상위 키(`caveats`·`advisories`·`corroboration` 등)에 싣지만 이 값이 증거가 아니라는 문구는 없다 [21].
같은 응답의 `data_provenance` 값 `tool_output_may_contain_untrusted_evidence`는 도구 출력에 대한 표시이고 FK 키를 가리키지 않는다 [21].
`suggest_tools`의 응답도 FK 지식을 `suggestions`·`advisories`·`corroboration`에 싣고 이 값이 증거가 아니라는 문구는 없다 [22].
`opencti-mcp`의 응답은 위협 정보를 결과 필드에 싣고 `caveats`는 플랫폼 기록을 바꾸지 않고 전달하며 판정을 계산하지 않는다고만 적는다 [26].
`opencti-mcp`의 서버 지침은 위협 정보와의 상관을 "supporting evidence, not proof"라고 적는다 [27].
`windows-triage-mcp`의 LOLBin·취약 드라이버·파이프 조회 결과는 판정과 같은 응답에 실리고 `caveats`와 서버 지침은 이 값이 증거가 아닌 참조 지식이라고 밝히지 않는다 [28].
