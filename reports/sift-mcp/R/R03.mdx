# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 게이트웨이와 백엔드 7개의 모든 도구 응답에 적용된다 [1][2][3][4][5].
`sift-mcp`의 `run_command` 응답은 성공 여부 `success`를 싣고 실패하면 `error`에 문구를 싣는다 [1].
`run_command`의 `success`는 서버가 실행을 멈추었거나 실행 전에 거부했거나 실행 파일을 실행하지 못했을 때 거짓이다 [1][6][7].
도구의 종료 코드는 판단하지 않고 `metadata.exit_code`에 싣는다 [1][6].
(실행 확인) `false`를 실행하자 `success`는 참이었고 `metadata.exit_code`는 1이었다 [8].
`forensic-mcp`·`case-mcp`·`report-mcp`의 도구는 예외가 나면 `error` 키 하나에 예외 문구를 담은 `dict`를 돌려준다 [2].
`forensic-mcp`의 `record_finding`은 결과를 `status`(`STAGED`·`VALIDATION_FAILED`·`REJECTED`·`WITHDRAWN`)로 나누고 검사 실패는 `errors` 목록에 싣는다 [9].
`windows-triage-mcp`·`rag-mcp`·`opencti-mcp`는 실패하면 오류 종류 코드를 `error`에, 문구를 `message`에 싣는다 [3][4].
오류 종류는 `validation_error`·`database_error`·`rate_limit_exceeded`·`configuration_error`·`internal_error` 등이다 [3][4].
게이트웨이는 알 수 없는 도구, 백엔드 연결 실패, 백엔드 호출 시간 제한 같은 자기 쪽 실패를 MCP 오류 결과 `isError`로 돌려준다 [5].
백엔드가 `isError`로 돌려준 결과는 게이트웨이도 `isError`로 돌려준다 [5][10].

**한계.** `opencti-mcp`는 응답 캐시를 켜 두면 지표 검색의 OpenCTI 요청이 실패하거나 `_circuit_breaker`가 요청을 막을 때 캐시에 남은 결과를 만료된 것까지 돌려준다 [11][12].
응답 캐시는 기능 설정 `response_caching`(환경변수 `FF_RESPONSE_CACHING`)으로 켜고 기본으로 꺼져 있어 기본 설정에서는 캐시에 결과가 쌓이지 않는다 [13].
이때 클라이언트 객체는 결과가 캐시에서 왔다는 값을 내부에 두지만 서버는 그 값을 읽지 않아 응답에는 실패나 캐시 결과라는 표시가 없다 [11][14].
이 지표 검색은 `search_threat_intel`의 `indicators`를 만든다 [14].
이 경로는 코드로만 확인했다.
`forensic-mcp`의 `get_actions`·`list_todos`와 규율 자료 도구 일부는 실패하면 `error`를 담은 `dict` 하나를 목록에 넣어 돌려주므로 성공 응답과 모양이 같다 [2].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 `windows-triage-mcp`의 대조 도구, `opencti-mcp`의 `lookup_ioc`·`get_entity`, `case-mcp`의 `evidence_verify`, `forensic-mcp`의 `update_todo`·`complete_todo`에 적용된다 [15][16][17][18][19].
`windows-triage-mcp`는 기준 DB에 없는 대상을 판정 `UNKNOWN`과 "not in baseline" 이유로 돌려준다 [15].
입력이 모자라거나 선택 DB가 없으면 판정 대신 `error`를 싣고 `verdict`를 비우며 `lookup_performed`를 거짓으로 둔다 [15].
`lookup_ioc`는 플랫폼마다 일치하면 `MATCH`, 일치가 없으면 `NO_MATCH`, 묻지 못했으면 `UNAVAILABLE`로 나눈다 [16].
최상위 `found`는 `MATCH`면 참, `NO_MATCH`면 거짓, `UNAVAILABLE`이면 `null`이다 [16].
정확히 같은 레코드를 고르지 못했는데 읽지 않은 후보가 남았으면 `NO_MATCH`가 아니라 `UNAVAILABLE`로 둔다 [20].
`get_entity`는 ID로 객체를 찾지 못하면 `found`를 거짓으로 돌려준다 [17].
`evidence_verify`는 증거 파일이 없으면 `MISSING`, 읽지 못하면 `ERROR`로 나눈다 [18].
`update_todo`와 이를 부르는 `complete_todo`는 없는 할 일 ID를 받으면 `status`를 `not_found`로 돌려준다 [19].

### R03.03 입력별 성공·실패·생략 목록

**구현.** 이 방식은 `opencti-mcp`의 `lookup_ioc`와 `case-mcp`의 `evidence_verify`에 적용된다 [16][18].
`lookup_ioc`는 설정한 플랫폼마다 `providers.<이름>`에 결과 `outcome`과 질의 시각 `queried_at`을 싣고 `UNAVAILABLE`이면 `reason`을 싣는다 [16][21].
최상위 `reason`에는 묻지 못한 플랫폼의 이름과 이유를 이어 적는다 [16].
(실행 확인) OpenCTI와 MISP를 시험용 전송 함수로 설정하고 `lookup_ioc`를 부르자 `providers`에 두 플랫폼의 `outcome`이 따로 실렸다 [22].
`evidence_verify`는 등록한 증거 파일마다 경로, 상태(`OK`·`MODIFIED`·`MISSING`·`ERROR`·`PENDING`), 기대 해시와 실제 해시를 `results`에 싣는다 [18].
(실행 확인) 등록한 두 파일 가운데 하나를 고치고 하나를 지운 뒤 `evidence_verify`를 부르자 `results`에 `MODIFIED`와 `MISSING`이 경로와 함께 실렸다 [23].

### R03.04 시간 초과·부분 완료 표시

**구현.** 이 방식은 `sift-mcp`의 `run_command`, `opencti-mcp`의 `lookup_ioc`, `case-mcp`의 `evidence_register`·`evidence_verify`에 적용된다 [1][24][25][18].
`run_command`는 시간 제한(기본 600초, 환경변수 `SIFT_TIMEOUT`)이 지나면 프로세스를 끝내고 `success`를 거짓, `stopped`를 `timeout`으로 싣는다 [26][1].
캡처 상한에서 프로세스를 끝냈으면 `stopped`를 `output limit`으로 싣고 `error`에 종료 코드가 도구의 것이 아니라고 적는다 [1][6].
(실행 확인) `SIFT_TIMEOUT`을 2로 두고 `sleep 5`를 실행하자 `success`는 거짓, `stopped`는 `timeout`이었다 [27].
시간 제한으로 끝낸 실행은 그때까지 읽은 출력을 응답에 싣지 않고 `data`를 비운다 [26][27].
`lookup_ioc`는 플랫폼마다 정한 시간 안에 답하지 않으면 그 플랫폼을 `UNAVAILABLE`과 "timed out after N s"로 둔다 [24].
OpenCTI 관계를 읽을 시간이 남지 않았거나 그 질의가 실패하면 `relationships`를 비우고 `relationships_unavailable`에 관계 목록이 불완전하다고 적는다 [25].
MISP의 warninglist 확인이 시간 안에 끝나지 않으면 `warninglist_hits`를 `null`로, `warninglists_unavailable`에 이유를 싣는다 [25].
`evidence_register`는 폴더를 등록할 때 파일 크기의 합이 호출 안에서 해싱하는 한도 `INLINE_LIMIT`(1,000,000,000바이트)를 넘으면 나머지 파일을 백그라운드 작업으로 넘기고 `status`를 `hashing`과 작업 ID `job_id`로 돌려주며 등록하지 않는다 [28][29].
`evidence_verify`는 해싱 중인 파일을 `PENDING`과 `job_id`로 싣고 그 수를 `pending`에 싣는다 [18].

**한계.** 게이트웨이는 백엔드 호출을 300초에서 끊는다 [30].
`run_command`의 기본 시간 제한 600초보다 짧으므로 게이트웨이를 거친 실행이 300초를 넘으면 모델은 `stopped`와 `audit_id`가 담긴 `sift-mcp` 응답 대신 게이트웨이의 `isError` 오류 문구를 받는다 [30][5][26].
이 경로는 코드로만 확인했다.

```python
    def _get_fallback(self, cache: TTLCache[Any], key: str) -> tuple[bool, Any, bool]:
        """Get cached response for graceful degradation.

        Only used when service is unavailable (circuit open or request failed).
        Uses get_stale() to return expired entries that regular get() would
        discard — stale data is better than no data during an outage.

        Returns:
            (found, value, is_degraded) tuple
        """
        if not self._feature_flags.graceful_degradation:
            return (False, None, False)

        found, value = cache.get_stale(key)
        if found and value is not NOT_FOUND:
            logger.info(
                f"Graceful degradation: using cached response for {key[:16]}..."
            )
            return (True, value, True)

        return (False, None, False)
```
