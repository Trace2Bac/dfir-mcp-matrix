# F06 보고 산출물 구성

### F06.01 증거·환경 manifest 포함

**구현.** 이 방식은 `report-mcp`의 `generate_report`가 돌려주는 보고 자료와 `save_report`가 저장하는 보고서 파일에 적용된다 [1][2].
보고서 본문은 클라이언트 모델이 보고 자료를 보고 써서 `save_report`에 넘기고 서버는 그 끝에 검증 블록과 출처 블록을 붙인다 [2].
같은 저장소의 사용자 CLI `vhir report`도 같은 두 블록을 붙인 보고서를 만들고 사용자가 실행해야 만들어진다 [3].
`generate_report`의 `full` 프로필은 보고 자료 `evidence`에 등록한 증거마다 경로, SHA-256, 크기, 등록한 사람과 시각, 등록 경로 `registered_via`를 싣는다 [4][5].
`full` 말고 다른 프로필에는 증거 목록이 없다 [4].
출처 블록은 승인한 발견사항마다 근거 사슬이 이른 등록 증거의 경로, SHA-256 앞 16자, AI가 등록했는지 검토자가 등록했는지를 싣는다 [6].
`sift-mcp`가 호출 기록에 남긴 분석 도구 버전과 서버 버전은 보고 자료와 두 블록에 실리지 않는다 [1][2].
시험 사건의 `full` 보고 자료에는 등록한 증거 파일 하나가 경로, SHA-256, `registered_via`와 함께 실렸다 [7].

### F06.03 발견사항과 근거 링크 포함

**구현.** 이 방식은 `generate_report`의 보고 자료, `save_report`가 붙이는 출처 블록, 사용자 CLI `vhir report --findings`에 적용된다 [1][2][8].
보고 자료의 승인한 발견사항은 인용 원문 `artifacts`를 그대로 싣고 항목마다 근거 호출 `audit_id`, 출처 등급, 출처 사슬 `provenance_chain`이 들어 있다 [9][7].
출처 사슬의 단계마다 방법, 호출 ID, 그 호출의 입력 파일과 출력 파일의 경로와 SHA-256이 들어 있다 [7].
출처 블록은 승인한 발견사항마다 ID와 제목, 출처 등급을 적고 인용 원문마다 사슬 단계를 한 줄씩 싣는다 [6].
`vhir report --findings`는 발견사항마다 근거 호출 ID 목록을 `Evidence`로 싣는다 [8].
승인한 발견사항 하나를 저장한 보고서의 출처 블록에는 `grep` 실행의 호출 ID와 그 출력 파일 경로가 실렸다 [7].

보고 자료의 승인 발견사항에는 대안 설명 `alternatives`가 상태 `open`·`ruled_out`과 함께 남는다 [9][7].
대안 설명은 발견사항 안에 실리고 열린 대안만 따로 모은 절은 없다 [1][9].
`save_report`가 붙이는 블록에는 대안 설명이 없다 [6][10].
보고 자료는 반론 결과 `challenged`를 뺀다 [9].
그래서 반론 결과가 `contested`인 채로 승인한 발견사항도 보고 자료에는 그 반론이 실리지 않는다 [9].

**한계.** 보고 자료는 발견사항의 `audit_ids` 필드를 뺀다 [9].
그래서 인용 원문 없이 근거 호출 ID나 셸 명령만 준 발견사항은 보고 자료에 근거 호출 ID가 실리지 않는다 [9][11].

### F06.04 검증·한계 포함

**구현.** 이 방식은 `generate_report`의 `verification`·`integrity_warning`과 `save_report`·`vhir report`가 붙이는 검증 블록에 적용된다 [12][2][3].
검증 결과는 보고 자료를 만들 때와 보고서를 저장할 때마다 `vhir-cli`의 `approved_view`가 서명 원장을 다시 검증해 얻는다 [13][14].
검증 블록은 승인으로 싣는 항목 수, 승인 확인 검사에 실패해 사유를 적고 승인한 항목과 그 사유, 서명이 검증되지 않아 승인으로 싣지 않는 항목의 ID와 상태를 싣는다 [10].
사건 단위 실패, 서명 키 지문과 원장 줄 범위, 원장 끝 값도 함께 싣는다 [10].
`generate_report`는 같은 결과를 `verification`에 싣고 검증되지 않은 승인 항목이 있으면 그 항목을 보고 자료에서 뺐다는 `integrity_warning`을 싣는다 [12].
보고 자료에는 아직 열린 할 일 목록 `todos`도 실린다 [15].
서명 없이 상태만 `APPROVED`로 바꾼 발견사항은 보고 자료에서 빠지고 검증 블록에 `APPROVED_NO_LINE`과 사건 단위 실패 `LEDGER_MISSING`이 실렸다 [16].
승인한 뒤 내용을 바꾼 발견사항은 보고 자료에서 빠지고 `ALTERED_AFTER_APPROVAL`로 실렸다 [7].
검토자가 채울 절을 적은 `human_review_required`는 조사와 관계없이 늘 같은 목록이다 [17].

### F06.05 내보내기

**구현.** 이 방식은 `report-mcp`의 `save_report`와 사용자 CLI `vhir report --save`에 적용된다 [2][18].
`save_report`는 사건 폴더의 `reports/`에 보고서 파일을 쓰고 그 경로와 붙인 블록을 응답으로 돌려준다 [19][20].
파일 이름은 `..`, `/`, `\`가 있으면 거부하고 영문자, 숫자, `.`·`_`·`-` 밖의 문자를 `_`로 바꾼다 [21].
같은 이름의 파일이 있으면 `_v2`처럼 번호를 붙여 새 파일로 쓴다 [21].
본문은 10MB까지 받고 쓰기 전에 본문과 블록에 나오는 사건의 도메인·URL·IPv4 IOC를 `hxxp`·`[.]` 표기로 바꾼다 [21][2].
`vhir report --save`는 사건 폴더 안의 경로에만 보고서를 쓴다 [18].
`case-mcp`의 `export_bundle`은 발견사항과 타임라인을 응답으로 돌려주고 묶음을 파일로 쓰지 않는다 [22][23].
`save_report`가 `reports/test-report.md`를 쓰고 그 끝에 두 블록이 붙었다 [16].

### F06.07 판단의 확정 상태 표시

**구현.** 이 방식은 `generate_report`의 보고 자료, `save_report`의 검증 블록, 사용자 CLI `vhir report`에 적용된다 [1][2][3].
보고 자료와 출처 블록에는 서명 검증을 통과한 승인 발견사항과 타임라인 사건만 싣는다 [13][6].
DRAFT·REJECTED 발견사항은 싣지 않고 `summary`에 전체 수와 승인 수만 싣는다 [24].
보고 자료의 `generation_constraints`는 모델에게 승인하지 않은 항목을 보고서에 언급하지 말라고 적는다 [25].
검증 블록은 승인으로 싣는 항목 수와 승인 상태지만 검증되지 않은 항목을 나눠 싣는다 [10].
서명 원장이 붙인 표시가 있는 승인 항목은 보고 자료의 `verification` 필드에 그 표시를 싣는다 [26].
표시는 서명 전 버전의 승인, 연결된 발견사항을 따라 함께 승인된 항목, 승인 확인 검사 실패 뒤 사유를 적은 승인 같은 것이다 [14].
발견사항의 확신도 `confidence`와 확신도 근거는 보고 자료에서 뺀다 [9].
`vhir report --findings`는 요청한 발견사항마다 상태와 검증 결과를 싣고 `vhir report --full`은 상태별 수를 싣는다 [8][27].
발견사항 하나를 승인하자 함께 승인된 타임라인 사건에 그 발견사항을 따라 승인되었다는 표시가 실렸다 [7].
