# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 `windows-triage-mcp`의 `check_*` 도구, `forensic-mcp`의 `record_finding`, `report-mcp`의 `generate_report`에 적용된다 [1][2][3][4].
`windows-triage-mcp`는 파일, 프로세스, 서비스, 해시를 정상 기준 DB와 대조한 결과에 정한 차례의 규칙을 대어 SUSPICIOUS·EXPECTED_LOLBIN·EXPECTED·UNKNOWN 가운데 하나로 판정한다 [1].
파일 판정은 이름에 심각한 문제가 있거나 알려진 도구 이름이면 SUSPICIOUS로 정하고 경로가 기준에 있으면 EXPECTED, 그 파일이 LOLBin이면 EXPECTED_LOLBIN으로 정한다 [5].
이름만 기준에 있고 폴더가 다르면 코드에 정한 위장 대상 이름 목록 `_MASQUERADE_TARGETS`에 있을 때만 SUSPICIOUS로 정하고 그 밖에는 UNKNOWN으로 정한다 [6].
프로세스 판정은 기대한 부모, 경로, 사용자와 어긋나면 SUSPICIOUS로 정한다 [7].
`check_scheduled_task`는 기준에 없는 작업 경로에 `\temp\`·`\appdata\` 같은 문자열이 있으면 SUSPICIOUS로 정한다 [8].
기준에 있는 작업 경로는 작업의 명령과 인자를 보지 않고 EXPECTED로 정하고 그 사실을 사유에 적는다 [8].
`forensic-mcp`의 `record_finding`은 발견사항의 `iocs` 값마다 값 모양 규칙으로 유형을 정하고 정규화한 값을 키로 사건의 IOC 기록에 잇는다 [2][9].
같은 키의 IOC 기록이 있으면 새 기록을 만들지 않고 그 기록의 `source_findings`와 `sightings`에 이번 발견사항과 호스트를 더한다 [2].
이때 IOC 기록의 확신도는 잇는 발견사항 가운데 더 높은 확신도로 바뀐다 [2].
`record_finding`은 새 발견사항이 인용한 호출의 명령을 앞서 반론으로 철회되었거나 `contested`로 남은 발견사항이 인용한 명령과 대조한다 [10].
같은 명령이 있으면 그 앞 기록의 ID와 반대 근거를 새 발견사항의 `prior_challenge`에 잇고 앞 기록 뒤에 새로 실행한 명령을 `new_since`에 남긴다 [10][11].
`report-mcp`의 `generate_report`는 승인한 발견사항의 `iocs`와 관찰·해석 글에서 정규식으로 IOC를 뽑아 값마다 그 값을 적은 발견사항 ID를 잇는다 [4][12].
사건의 IOC 기록에 없는 값은 "Found in text, not recorded" 묶음으로 따로 싣는다 [4].
`svchost.exe`라는 이름만 기준에 있고 폴더가 다르며 보호 프로세스 이름인 경우를 판정 함수에 넣자 SUSPICIOUS가 나왔다 [13].
위장 대상이 아닌 `setup.exe`를 같은 조건으로 넣자 UNKNOWN과 위장 대상이 아니라는 사유가 나왔다 [13].
한 발견사항은 `10.0.0.5`를, 다른 발견사항은 표기를 바꾸고 포트를 붙인 `10.0.0[.]5:443`을 `iocs`에 넣자 IOC 기록은 하나만 생기고 두 발견사항과 두 호스트가 그 기록에 이어졌다 [14].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 `windows-triage-mcp`의 `check_*` 결과, `forensic-mcp`의 IOC 기록, 게이트웨이의 참조 조회 호출 기록에 적용된다 [5][2][15].
`windows-triage-mcp`의 판정 결과에는 판정 값과 함께 어느 규칙이 판정을 정했는지 적은 `reasons`가 실린다 [16][5].
`check_file` 결과에는 경로와 이름이 기준에 있었는지 `path_in_baseline`·`filename_in_baseline`와 해시를 대조했는지 `hash_compared`가 함께 실린다 [17].
해시 없이 경로만 맞아 EXPECTED가 되면 내용은 확인하지 않았다는 사유가 더해진다 [18].
`forensic-mcp`의 IOC 기록은 그 값을 적은 발견사항 ID를 `source_findings`에, 발견사항마다의 호스트를 `sightings`에 남긴다 [2].
게이트웨이는 `windows-triage-mcp`의 `check_*`와 `opencti-mcp`의 `lookup_ioc` 호출마다 응답 원문을 사건 폴더에 저장한다 [15].
그 호출의 호출 기록 `reference`에는 출처 백엔드 이름, 백엔드가 알린 버전, 저장한 응답의 경로와 SHA-256이 남는다 [15].

**한계.** 호출 기록의 `source_version`은 백엔드 프로그램이 알린 버전이고 기준 DB 자료의 버전이 아니다 [19].

### F02.06 규칙 기반 공격 단계 분류·흐름 서술

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`이 함께 만드는 타임라인 사건에 적용된다 [20].
종류가 `finding`이고 사건 시각 `event_timestamp`가 있는 발견사항을 저장하면 같은 시각과 같은 근거 호출 ID를 가진 DRAFT 타임라인 사건을 함께 만든다 [20][21].
이 사건의 `event_type`은 발견사항이 준 값을 쓰고 값이 없으면 코드에 정한 ATT&CK 기법 대응표 `_MITRE_EVENT_TYPE`으로 정한다 [21][22].
대응표는 기법 ID 전체가 맞는 항목을 먼저 찾고 없으면 앞 세 글자로 찾는다 [23].
분류 값은 `execution`·`persistence`·`lateral`·`auth`·`network`·`other` 가운데 하나이고 맞는 항목이 없으면 `other`가 된다 [22][21].
`report-mcp`의 `generate_report`는 승인한 타임라인 사건을 시각 차례로 정렬해 보고 자료에 싣는다 [24].
`mitre_ids`가 `T1021`인 발견사항에서 함께 만든 타임라인 사건의 `event_type`은 `lateral`이었다 [25].

**한계.** 앞 세 글자로 찾기 때문에 대응표에 따로 없는 `T10`으로 시작하는 기법 ID는 모두 `execution`이 되고 `T11`·`T13`으로 시작하는 기법 ID는 모두 `persistence`가 된다 [22][23].

### F02.08 확신 수준·추정 범위 표시

**구현.** 이 방식은 `windows-triage-mcp`의 판정 결과에 적용된다 [16].
판정 결과마다 확신 수준 `confidence`를 `high`·`medium`·`low` 가운데 하나로 싣는다 [16].
값은 판정 함수의 규칙마다 코드에 정해 두었고 기준에 없어 UNKNOWN이 된 판정은 `low`다 [5][6].
판정 함수에 넣은 세 경우에서 위장 의심은 `high`, 기준에 없는 이름과 위장 대상이 아닌 이름은 `low`가 나왔다 [13].
규칙이 정한 값은 두 경우에 낮춘다 [26].
8.3 짧은 이름이 들어간 경로라서 경로만으로 낸 판정이면 `high`를 `medium`으로 낮춘다 [26].
프로세스 계정을 판단하지 못한 `EXPECTED` 판정은 `medium`으로 둔다 [26].

```python
Verdict Categories (in priority order):

    SUSPICIOUS - Anomalies or suspicious patterns detected
        - Hash mismatch on known path (trojanized binary)
        - Protected process name in wrong location (svchost.exe in C:\\Temp)
        - Unicode evasion (RLO attacks, homoglyphs)
        - Double extensions (invoice.pdf.exe)
        - Unexpected process parent (Word spawning cmd.exe)
        - Known tool patterns (mimikatz.exe)
        - LOLBin in non-standard location
        - Vulnerable driver detected

    EXPECTED_LOLBIN - Matches baseline AND is a LOLBin
        - LOLBin in expected location (certutil.exe in System32)
        - Legitimate Windows tool that can be abused for malicious purposes

    EXPECTED - Matches Windows baseline, no risk factors
        - Path and/or filename found in VanillaWindowsReference
        - No LOLBin, no suspicious patterns

    UNKNOWN - Not in any database (NEUTRAL, not suspicious)
        - Our baseline cannot cover all legitimate software
        - Third-party apps, enterprise tools, or newer Windows components
        - Only flag as suspicious if actual indicators present
```

```python
def _what_ran(entry: dict) -> str:
    """What an audit entry ran: its command, whitespace-normalised, or its
    tool and parameters. A re-run of the same thing has a new id, not a new
    key."""
    params = entry.get("params") if isinstance(entry.get("params"), dict) else {}
    cmd = params.get("command")
    if isinstance(cmd, list):
        cmd = " ".join(map(str, cmd))
    if isinstance(cmd, str) and cmd.strip():
        return " ".join(cmd.split())
    args = json.dumps(params, sort_keys=True, default=str)
```

```python
def _infer_event_type(sanitized: dict) -> str:
    """Best-effort event_type from MITRE technique IDs."""
    mitre_ids = sanitized.get("mitre_ids", [])
    if isinstance(mitre_ids, str):
        mitre_ids = [mitre_ids]
    for mid in mitre_ids:
        mid = mid.strip().upper()
        # Try exact match first (T1021), then prefix (T10)
        if mid in _MITRE_EVENT_TYPE:
            return _MITRE_EVENT_TYPE[mid]
        prefix = mid[:3]  # T10, T11, etc.
        if prefix in _MITRE_EVENT_TYPE:
            return _MITRE_EVENT_TYPE[prefix]
    return ""
```
