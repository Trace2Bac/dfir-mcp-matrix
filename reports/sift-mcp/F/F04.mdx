# F04 발견사항·결론 기록 관리

### F04.01 자유 노트

**구현.** 이 방식은 `case-mcp`의 `log_reasoning`에 적용된다 [1].
`log_reasoning`은 판정 필드 없는 글 하나를 받아 승인 없이 `case-mcp`의 호출 기록에 남긴다 [1].
도구 설명은 조사 방향을 고를 때, 가설을 세우거나 고칠 때, 무언가를 배제할 때 부르라고 안내한다 [1].
글은 1만 자까지 받고 호출 기록 항목의 `params.text`에 그대로 남으며 항목의 `source`는 `orchestrator`다 [1][2].
가설과 배제를 적은 글을 `log_reasoning`으로 보내자 `case-mcp.jsonl`에 그 글이 들어간 항목이 생겼다 [2].
같은 서버의 `record_action`은 발견사항이 아닌 작업 메모를 `actions.jsonl`에 남긴다 [3].

### F04.02 발견사항 필드 구분 저장

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`과 `record_timeline_event`에 적용된다 [4][5].
`record_finding`은 발견사항을 `dict` 하나로 받고 서버가 허용한 필드만 골라 저장한다 [4][6].
허용한 필드는 제목, 관찰, 해석, 확신도, 확신도 근거, 종류, 근거 호출 ID, ATT&CK ID, IOC, 사건 종류, 아티팩트 참조, 관련 발견사항, 호스트, 사건 시각, 관련 계정이다 [6].
대안 설명 `alternatives`, 반론 결과 `challenged`, 작성 클라이언트 `produced_by`는 서버가 따로 검사해 저장한다 [7].
인용 원문 `artifacts`는 항목마다 출처, 추출 방법, 원문, 근거 호출 ID를 받아 저장하고 서버가 계산한 출처 등급과 출처 사슬을 더한다 [8][9].
서버는 ID, 상태 `DRAFT`, 저장 시각, 작성자, 출처 등급, 내용 해시를 붙인다 [10].
`record_timeline_event`는 시각과 설명을 받고 ID, 상태, 시각, 작성자 같은 보호 필드를 입력에서 지운 뒤 나머지 필드를 그대로 저장한다 [5][11].

**한계.** 허용 목록에 없는 필드는 알리지 않고 버린다 [6].
`severity`와 `status`를 넣은 발견사항은 필드를 버렸다는 경고 없이 저장되었고 저장한 기록에는 `severity`가 없고 상태는 `DRAFT`였다 [12].
`host`와 `affected_account`는 200자에서 알리지 않고 자른다 [13][12].

### F04.03 근거 증거·호출 참조

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`과 `record_timeline_event`에 적용된다 [4][5].
발견사항의 `audit_ids`에는 모델이 준 호출 ID, 셸 명령을 적은 `supporting_commands`마다 서버가 만든 `shell-` ID, 인용 원문마다의 `audit_id`가 순서를 지키며 한 번씩 합쳐진다 [14][15].
`supporting_commands`는 다섯 개까지 명령, 목적, 출력 발췌를 저장하고 명령마다 `forensic-mcp`의 호출 기록에 `shell_self_report` 항목을 남긴다 [14].
인용 원문의 출처 사슬이 등록 증거에 이르면 그 경로를 `source_evidence`로 남긴다 [9][16].
`record_finding`이 함께 만드는 타임라인 사건은 발견사항의 근거 호출 ID와 발견사항 ID를 `audit_ids`·`related_findings`로 남긴다 [17].
`record_timeline_event`는 관련 발견사항 ID `related_findings`를 받은 값 그대로 저장한다 [5].

**한계.** `record_timeline_event`는 `related_findings`의 ID가 사건에 있는지 보지 않는다 [5].
없는 발견사항 ID를 `related_findings`에 넣은 타임라인 사건은 그 ID를 그대로 담아 저장되었다 [12].

### F04.04 사건 시각과 작성 시각 분리

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`과 `record_timeline_event`에 적용된다 [4][5].
발견사항은 사건이 일어난 시각 `event_timestamp`와 서버가 넣는 저장 시각 `staged`·수정 시각 `modified_at`을 따로 둔다 [10][18].
`event_timestamp`는 ISO 8601이나 날짜만 받고 형식이 다르면 거부한다 [18].
종류가 `finding`인데 `event_timestamp`가 없으면 거부하지 않고 경고만 붙인다 [18].
타임라인 사건도 사건 시각 `timestamp`와 저장 시각 `staged`를 따로 두고 `timestamp`가 없거나 형식이 다르면 거부한다 [5][19].
`timestamp`를 `yesterday`로 준 타임라인 사건은 `VALIDATION_FAILED`로 거부되었다 [20].

### F04.05 수정·철회 이력

**구현.** 이 방식은 게이트웨이가 함께 실행하는 검토 포털의 서명 커밋과 `forensic-mcp`의 `record_finding` 호출 기록에 적용된다 [21][22].
`forensic-mcp`에는 저장한 발견사항을 고치거나 철회하는 도구가 없고 고치기, 승인, 반려는 검토 포털이나 사용자 CLI `vhir approve`에서 검토자가 한다 [23][24].
검토 포털은 검토자가 고친 필드마다 원래 값, 새 값, 고친 사람, 시각을 발견사항의 `examiner_modifications`에 남기고 메모는 `examiner_notes`에 덧붙인다 [21].
고칠 수 있는 필드는 제목, 관찰, 해석, 확신도, 확신도 근거, ATT&CK ID, 대안 설명 같은 정해 둔 목록이다 [25].
고치기, 승인, 반려는 결정마다 서명 원장에 한 줄씩 남고 그 줄에는 결정한 기록의 내용 `content_snapshot`이 들어간다 [26].
반려한 발견사항은 지우지 않고 상태 `REJECTED`, 반려한 사람과 시각, 반려 사유를 붙여 남긴다 [27].
반론으로 철회된 제출은 발견사항으로 저장하지 않고 그 `record_finding` 호출의 호출 기록 항목에 제목, 관찰, 반대 근거가 남는다 [22][28].
검토 포털은 이 호출 기록 항목을 찾아 철회된 제출 목록을 검토자에게 보여 준다 [29].
반려 사유를 주고 반려한 발견사항은 `REJECTED` 상태와 반려 사유를 담아 남았고 원장에는 결정 다섯 줄이 남았다 [30].

**한계.** 같은 필드를 다시 고치면 `examiner_modifications`의 그 필드 항목을 새 항목으로 덮어쓴다 [21].
`case-mcp`의 `import_bundle`은 다른 사건에서 가져온 DRAFT 발견사항을 같은 ID의 더 새 사본으로 바꿀 때 앞 사본을 남기지 않는다 [31].

### F04.06 파일·DB에 저장

**구현.** 이 방식은 `forensic-mcp`의 발견사항, 타임라인, IOC 기록에 적용된다 [32].
발견사항은 사건 폴더의 `findings.json`, 타임라인은 `timeline.json`, IOC 기록은 `iocs.json`에 쓴다 [32].
세 파일은 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로 다시 쓰고 쓴 뒤 읽기 전용 권한 `0o444`로 바꾼다 [33].
발견사항을 읽고 쓰는 동안 사건 잠금을 획득해 그사이 서명된 결정을 덮어쓰지 않는다 [34].

### F04.08 가설 상태 관리

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`이 받는 대안 설명 `alternatives`에 적용된다 [7].
대안 설명은 발견사항마다 10개까지 받고 항목마다 설명, 상태, 근거 글, 근거 호출 ID를 둔다 [35].
상태는 아직 가능한 `open`과 배제한 `ruled_out` 두 가지다 [35].
서버는 `ruled_out`을 근거 글과, 증거 백엔드의 호출 기록에 있는 근거 호출 ID가 함께 있을 때만 받고 그 밖에는 `open`으로 바꿔 저장하고 경고를 붙인다 [35][36].
근거 호출 ID 가운데 증거 백엔드의 도구 출력이 아닌 것은 빼고 뺀 ID를 경고에 적는다 [35][37].
근거 없이 `ruled_out`으로 낸 대안 설명은 `open`으로 저장되고 그 사유가 경고로 실렸다 [38].
검토 포털에서 검토자가 대안 설명을 고칠 수 있다 [25].

**한계.** 상태 규칙은 `record_finding`이 발견사항을 저장할 때만 적용되고 뒤에 근거가 생겨도 서버가 상태를 다시 계산하지 않는다 [7].
검토 포털에서 검토자가 고친 대안 설명은 받은 값 그대로 저장되어 이 규칙이 적용되지 않는다 [21].

### F04.09 판정·분류 값 기준 대조

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`과 `record_timeline_event`에 적용된다 [39][5].
종류 `type`은 코드에 정한 `finding`·`conclusion`·`attribution`·`exclusion` 가운데 하나여야 한다 [39].
확신도 `confidence`는 서버가 읽는 참조 표 `forensic-knowledge`의 `confidence.yaml`에 있는 HIGH·MEDIUM·LOW·SPECULATIVE 가운데 하나여야 한다 [39][40].
두 값이 목록에 없으면 `VALIDATION_FAILED`로 거부한다 [39].
확신도 값으로 `CERTAIN`을 준 발견사항은 `VALIDATION_FAILED`로 거부되었다 [20].

**한계.** ATT&CK ID `mitre_ids`와 사건 종류 `event_type`은 값 목록과 대조하지 않는다 [39][6].
`record_timeline_event`는 `event_type`을 포함해 시각 말고는 어떤 값도 대조하지 않는다 [5].

### F04.10 근거·확신도 필드 필수 입력

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`에 적용된다 [4].
입력 schema는 발견사항을 필드 정의 없는 `object` 하나 `finding`으로만 받고 필드마다의 필수 여부는 도구 설명에 적는다 [12][41].
서버 코드는 확신도 `confidence`와 확신도 근거 `confidence_justification`이 비어 있으면 `VALIDATION_FAILED`로 거부한다 [39].
반론 결과 `challenged`가 없으면 `REJECTED`로 거부한다 [42].
인용 원문 `artifacts`의 항목은 출처, 추출 방법, 원문이 있으면 근거 호출 `audit_id`가 비었을 때 `REJECTED`로 거부한다 [43].
`confidence_justification`이 빠진 발견사항과 `challenged`가 빠진 발견사항은 거부되었다 [20].

**한계.** `audit_ids`는 `list`이기만 하면 빈 목록도 이 검사를 통과한다 [39].
출처, 추출 방법, 원문 가운데 하나가 빈 `artifacts` 항목은 거부하지 않고 버린 뒤 버린 수를 경고로 알린다 [8][44].

### F04.11 관련 없음·배제 처분 기록

**구현.** 이 방식은 `forensic-mcp`의 `record_finding`에서 종류 `type`을 `exclusion`으로 준 기록에 적용된다 [39].
`exclusion`은 발견사항의 네 종류 가운데 하나이고 다른 발견사항과 같은 필드, 검사, DRAFT 상태로 저장된다 [39][10].
배제한 대상과 사유는 제목, 관찰, 해석에 글로 적고 대상과 사유를 나눈 필드는 없다 [6].
서버 지침은 정상이라는 증거를 갖춘 배제를 기록할 발견사항의 예로 적는다 [45].
`exclusion` 기록을 저장하면 응답에 확증 편향 안내와 배제 확인 지점 안내를 붙인다 [46].
호스트를 배제한 `exclusion` 기록은 DRAFT로 저장되었고 응답에 두 안내가 실렸다 [12].

```python
def _protected_write(path: Path, content: str) -> None:
    """Write to a chmod-444-protected case data file.

    Uses atomic write (tempfile + rename), then locks (0o444).
    The temp file is created writable, so we only need to unlock the
    existing file for _atomic_write's rename to succeed on the same inode.
    """
    try:
        if path.exists():
            os.chmod(path, 0o644)
    except OSError:
        pass  # May already be writable or on non-POSIX fs
    try:
        _atomic_write(path, content)
    finally:
        # Always re-lock, even if the write failed partway
        try:
            if path.exists():
                os.chmod(path, 0o444)
        except OSError:
            pass  # Non-POSIX filesystem
```

```python
def _cited_ids(raw: Any, limit: int, tool_ids: set[str]) -> tuple[list[str], list]:
    """The ids in raw that are tool output in the trail, and the ones that aren't."""
    if isinstance(raw, str):
        raw = [raw]
    if not isinstance(raw, list):
        return [], []
    kept: list[str] = []
    removed: list = []
    for aid in raw[:limit]:
        if isinstance(aid, str) and aid in tool_ids:
            if aid not in kept:
                kept.append(aid)
        else:
            removed.append(aid)
    return kept, removed
```
