# D02 파생물 추적

### D02.01 ID·경로 참조

**구현.** 이 방식은 `sift-mcp`의 `run_command`, `case-mcp`의 `log_external_action`, 게이트웨이의 참조 조회 기록, `forensic-mcp`의 `record_finding`, `report-mcp`의 `save_report`에 적용된다 [1][2][3][4][5].
`run_command`는 출력을 둔 폴더의 이름을 그 호출의 호출 기록 항목 ID로 짓고 응답에도 같은 `audit_id`를 싣는다 [1][6].
호출 기록 항목에는 보관한 표준 출력의 경로 `output_file`, 명령이 읽은 파일·폴더의 `inputs`, 출력 파일의 `outputs`가 들어간다 [1].
`inputs`의 각 항목은 받은 경로, 실제 경로, 장치 번호 `st_dev`, 마운트 ID `mnt_id`를 담는다 [7].
등록 증거는 `input_registered`에 등록 경로로 따로 적는다 [7].
입력은 호출자가 준 목록이 아니라 명령 인자에서 찾고 있는 파일이나 폴더를 가리키는 인자만 입력으로 본다 [8].
명령에 나오지 않는 파일을 `input_files`로 주면 그 파일은 `found: declared` 표시를 붙여 따로 적는다 [9].
`outputs`는 작업 폴더의 모든 파일과 출력 인자 경로에서 실행 전후 inode·크기·수정 시각이 달라진 파일이다 [10].
`log_external_action`은 모델이 알린 입력·출력 파일의 경로를 같은 필드에 적고 항목에 `declared: true`를 붙인다 [2].

게이트웨이의 참조 조회 항목은 응답 사본의 경로를 `reference.response.path`에, 백엔드 응답에 들어 있던 호출 ID를 `backend_audit_id`에 적는다 [3].
`record_finding`은 인용 `artifacts`마다 `audit_id`를 요구하고 호출 기록에 없는 ID면 발견사항을 거부한다 [4].
받은 ID에서 시작해 그 호출의 보관 출력과 입력을 따라 등록 증거까지 이은 연결 목록을 `provenance_chain`에, 도달한 등록 증거를 `provenance_root`와 `source_evidence`에 저장한다 [4].
백엔드가 돌려준 호출 ID로 인용하면 그 ID를 `backend_audit_id`로 가진 게이트웨이 참조 항목 하나로 잇는다 [11].
`save_report`는 승인되고 서명 검증을 통과한 발견사항마다 저장된 연결 목록(호출 ID, 경로, 해시)을 보고서 끝의 출처 목록으로 덧붙인다 [5].
등록한 시험 증거를 읽은 `run_command`의 출력을 인용해 발견사항을 기록하자 `registered-path`와 `recorded-id` 두 연결이 저장되었다 [12].

**한계.** 명령 인자에 나오지 않고 읽은 파일은 `input_files`로 알리지 않으면 입력으로 남지 않는다 [8][9].
출력 플래그로 정해 둔 인자가 아닌 방식(위치 인자로 받는 목적지, `bash -c` 안의 경로 등)으로 작업 폴더 밖에 쓴 파일은 `outputs`에 오르지 않는다 [10][13].
도구 설명은 두 호출이 같은 출력 폴더를 쓰면 그 폴더의 새 파일이 두 호출 모두의 출력으로 기록된다고 적는다 [13].
활성 사건이 없으면 호출 기록 항목이 없어 `run_command`의 출력은 어떤 호출 ID와도 이어지지 않는다 [14].
`artifacts` 없이 `audit_ids`나 `supporting_commands`만 준 발견사항은 ID만 남고 연결 목록을 만들지 않는다 [4][15].
`save_report`의 호출 기록 항목에는 파일 이름과 글자 수만 있고 보고서에 실은 발견사항 ID는 없다 [16].

### D02.02 입출력 해시 연결

**구현.** 이 방식은 `run_command`와 `log_external_action`의 호출 기록 항목에 적용된다 [1][2].
등록 증거가 아닌 입력 파일은 `inputs`의 `sha256`에, 출력 파일은 `outputs`의 `sha256`에 같은 항목 안에서 함께 남는다 [7][17].
등록 증거 입력은 다시 읽지 않고 등록부의 SHA-256을 `input_registered`에 적는다 [7].
보관한 표준 출력의 해시는 `result_summary`의 `output_sha256`이다 [1].
입력 폴더는 사건 폴더나 등록 폴더 안에 있고 조건을 만족하면 파일마다의 해시를 묶은 `folder` digest를 남긴다 [18].
한 호출이 해시할 파일 크기의 합이 1 GB를 넘으면 나머지는 백그라운드 작업이 해시하고 항목에는 `pending:<job>`을 적는다 [17][19].
작업이 끝나면 `audit/file-identity.jsonl`에 `hash_complete` 항목을 쓰고 추적은 그 값으로 바꿔 읽는다 [19][20].
등록 시험 증거를 읽은 `run_command` 항목에 등록부 해시와 출력 파일의 SHA-256이 함께 기록되었다 [12].

**한계.** 입력 폴더는 링크나 특수 파일이 없고 다른 파일 시스템을 지나지 않으며 파일 10,000개·2 GB 이하일 때만 digest를 남긴다 [18][21].
그 밖의 폴더 입력은 경로만 남는다 [7].
활성 사건이 없으면 1 GB를 넘는 파일은 해시하지 않는다 [19].
`log_external_action`은 모델이 알린 파일을 기록할 때 해시하므로 실제 실행 때의 내용과 대조하지 않는다 [2].

### D02.03 파생물 측 manifest

**구현.** 이 방식은 `case-mcp`의 `backup_case`가 만드는 백업 폴더에 적용된다 [22].
백업 폴더에는 `backup-manifest.json`이 함께 생긴다 [23].
manifest에는 원래 사건 폴더의 경로 `source`와 실제 경로 `source_realpath`, 만든 시각 `timestamp`, 검토자 `examiner`, 이유 `purpose`가 들어간다 [23].
파일마다 사건 폴더 기준 상대 경로, SHA-256, 크기도 적는다 [23].
같은 사건을 백업하자 manifest에 이 값들과 18개 파일의 해시가 들어 있었다 [24].
manifest에는 백업을 만든 호출의 호출 기록 ID가 없다 [23].
그 호출의 기록 항목에는 응답 전체가 `result_summary`로 들어가 백업 폴더 경로 `backup_path`가 남는다 [22].
다른 파생물 곁에는 manifest 파일이 없고 `save_report`는 출처 목록을 보고서 파일 안에 덧붙인다 [5].

### D02.04 여러 단계 파생 관계 기록

**구현.** 이 방식은 `record_finding`이 인용한 호출의 출처를 따라가는 `trace_artifact`에 적용된다 [4][25].
입력이 등록 증거가 아니면 그 입력을 읽은 호출보다 먼저 기록된 호출 가운데 같은 실제 경로에 같은 SHA-256의 출력을 남긴 호출을 찾는다 [25].
찾은 호출의 입력을 같은 방식으로 다시 따라가 등록 증거에 이를 때까지 잇는다 [26].
연결마다 방법(`hash+place`, `recorded-id`, `recorded-mount`, `folder-digest` 등), 호출 ID, 호출 기록 줄의 SHA-256 `entry_sha256`, 앞뒤 파일의 경로와 해시를 `provenance_chain`에 남긴다 [27].
같은 경로와 해시를 출력으로 남긴 호출이 둘 이상이면 하나를 고르지 않고 `AMBIGUOUS`로 후보를 모두 적는다 [25].
마운트 아래 파일은 기록된 마운트의 장치 번호와 마운트 기간이 맞을 때만 그 마운트로 잇는다 [28].
앞 호출이 `-o`로 쓴 중간 파일을 다음 호출이 읽게 하고 다음 호출을 인용하자 등록 증거, 앞 호출, `hash+place`, 다음 호출로 이어진 `FULL` 연결이 저장되었다 [29].

**한계.** 이 관계는 발견사항을 기록할 때 계산해 발견사항에만 저장하고 중간 파일을 읽은 호출의 기록 항목에는 부모 호출 ID를 적지 않는다 [7][4].
앞 호출의 출력으로 기록되지 않은 중간 파일은 잇지 못하고 `no-recorded-origin`으로 끊긴다 [25].
중간 파일을 기록 밖에서 바꾼 뒤 다음 호출이 읽게 하자 그 호출을 인용한 발견사항은 `BROKEN`으로 저장되었다 [29].
해시 작업이 끝나지 않은 파일은 `hash-pending`으로 끊긴다 [20].
읽지 못한 호출 기록 파일이 있으면 추적 결과는 `AMBIGUOUS`보다 나을 수 없다 [30].

### D02.05 선언 연결 구분

**구현.** 이 방식은 `run_command`와 `log_external_action`이 남기는 입력 기록과 `trace_artifact`의 출처 추적에 적용된다 [9][2][25][31].
`run_command`는 명령 인자에서 찾은 입력과 명령에 나오지 않는 `input_files`를 나누어 뒤의 것에만 `found: declared`를 붙인다 [8][9].
`log_external_action`은 모델이 알린 실행의 항목에 `declared: true`를 붙인다 [2].
이 도구의 응답 `note`는 알린 대로 기록했고 실행한 것과 대조하지 않았다고 적는다 [32].
추적은 `log_external_action` 항목을 잇는 연결의 방법을 `declared`로 적고 그 출처 등급을 `DECLARED`로 정한다 [31].
`found: declared`가 붙은 입력은 그 입력의 추적이 `FULL`이어도 연결 방법 `declared`를 더하고 등급을 `DECLARED`로 낮춘다 [33].
`save_report`가 덧붙이는 출처 목록은 발견사항과 인용 원문마다 이 등급을 적는다 [5].

[7] 입력 기록은 경로·실제 경로·장치·마운트 ID이고 등록 증거는 등록부 해시로, 다른 파일은 해시로, 폴더는 조건이 맞을 때 digest로 남긴다.

```python
def input_record(
    case_dir, path, requested_by: str = "", folder: bool = False, known=None
) -> tuple[dict, dict | None]:
    """``(input, registered)`` for a file or folder a call reads: registered
    evidence links by its path to the registry's hash and isn't read; a
    folder isn't hashed, but with ``folder`` an eligible one gets its digest
    (``folder_record``, with ``known``); any other file is hashed for the call."""
    rec = place(path)
    real = rec.get("realpath")
    if "st_dev" not in rec:
        return rec, None  # gone, or never there
    reg = fi.registered_hash(case_dir, real) if case_dir else None
    if reg:
        return rec, {"path": real, "sha256": reg}
    if not os.path.isdir(real):
        h = _hash(real, case_dir, requested_by)
        if h is not None:
            rec["sha256"] = h if isinstance(h, str) else h.sha256
    elif folder and case_dir and (digest := folder_record(case_dir, rec, known)):
        rec["folder"] = digest
    return rec, None
```

```python
    path, *, case_dir, requested_by: str = "", inline_limit: int = INLINE_LIMIT
) -> HashResult | Pending | None:
    """A hash for a tool call that must answer in time: a file of up to
    `inline_limit` bytes is hashed in the call; a larger one by a thread of
    this process, whose result goes to the case's `audit/file-identity.jsonl`.
    Callers asking for the same file while its thread runs share its job.
    Without a case there's nowhere to record that result: None, and nothing
    starts."""
    st = os.stat(path)
    if not stat.S_ISREG(st.st_mode):
        raise NotRegularFile(f"{path} is not a regular file")
    if st.st_size <= inline_limit:
        return hash_file(path)
    if not case_dir:
        return None
    # the job hashes the file only while it is still as it is now
    key = (os.path.realpath(path), *_stat_key(st))
    return Pending(str(path), _start(key, str(path), str(case_dir), requested_by))
```

```python
    why = (f"couldn't read {', '.join(case.skipped)}: an entry there could "
           f"change {audit_id}'s trace")  # fmt: skip
    reason = (
        f"{t.reason}; {why}" if t.reason else why
    )  # a DECLARED's own reason stays first
    if t.grade in ("FULL", "DECLARED"):
        fix = "make each log a readable regular file, then record the finding again"
        return Trace("AMBIGUOUS", t.root, t.roots, t.links, t.candidates,
                     {"kind": "audit-unreadable", "detail": why, "fix": fix}, reason)  # fmt: skip
    t.reason = reason
    return t
```
