# E02 증거 무결성 검증

### E02.01 등록 시 기준값 자동 계산

**구현.** 이 방식은 증거 파일 하나를 받아 읽는 기본 도구와 파일을 받는 외부 도구 래퍼에 적용된다 [1][2][3].
서버 코드의 `_sha256`은 파일을 1 MiB씩 끝까지 읽어 내용 전체의 SHA-256을 계산한다 [1].
기본 도구는 모델이 요청하지 않아도 이 값을 계산해 응답의 `source`에 읽은 파일의 경로와 함께 싣는다 [2].
외부 도구 래퍼 대부분은 도구를 실행하기 전에 입력 파일의 SHA-256을 계산해 `metadata`의 `image_sha256`·`mft_sha256`·`hive_sha256`·`amcache_sha256` 같은 필드에 싣는다 [3].
해시 범위는 받은 파일 하나의 바이트이고 메모리 이미지나 디스크 이미지도 그 파일 자체를 해시한다 [1][3].
서버는 이 값을 저장하지 않고 어느 도구도 이 값을 다시 읽어 지금 증거와 대조하지 않는다.
모델이 해시를 따로 요청하는 도구와 기준값을 대조하는 도구는 없다 [4].
같은 저장소의 클라이언트 `dfir_agent`의 결정적 모드는 호출 기록에 응답 JSON 전체의 SHA-256만 남기므로 증거 해시 값은 기록에 그대로 남지 않는다 [5].

부속 CSV를 읽는 도구는 받은 증거 파일의 해시를 싣고 실제로 읽은 부속 CSV는 해시하지 않는다 [6].
`analyze_downloads`, 폴더를 받는 기본 도구 5개, `sift_yara_scan_dir`, `detect_persistence`, `match_sigma_rules`는 입력의 해시를 싣지 않는다 [7].
`detect_defense_evasion`과 `detect_credential_access`도 받은 사건 파일을 해시하지 않는다 [7].
EvtxECmd·PECmd·RECmd 래퍼와 `sift_plaso_log2timeline`은 폴더를 받으면 해시 필드를 `null`로 둔다 [8].
`scan_pth_files_for_supply_chain_iocs`는 표시가 붙은 파일만 해시하고 `parse_linux_cron_jobs`와 `list_scheduled_tasks`는 읽은 파일마다 해시한다 [9].

**한계.** 기준값은 도구를 부를 때마다 그 시점의 파일에서 새로 계산한다 [1][2].
그래서 서버가 읽기 전에 바뀐 증거는 바뀐 상태가 그 응답의 기준값이 된다.
같은 파일을 두 번 읽는 사이에 내용을 바꾸자 두 응답의 SHA-256이 달랐고 응답에 다르다는 표시는 없었다 [10].
기본 도구 대부분은 파일을 읽은 뒤 응답을 만들 때 파일을 다시 열어 해시하므로 두 읽기 사이에 파일이 바뀌면 응답의 내용과 해시가 서로 다른 상태를 가리킨다 [2].
부속 CSV를 읽는 도구에서 응답의 해시는 읽은 내용을 대표하지 않는다 [6].
`Amcache.csv`의 행을 바꾸고 `get_amcache`를 다시 부르자 `source.sha256`은 같았고 `items`는 바뀌었다 [10].

### 근거

[1] `_sha256`은 파일 전체를 1 MiB씩 읽어 해시한다.

```python
def _sha256(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()
```
