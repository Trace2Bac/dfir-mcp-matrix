# T10 도구 명세 구성

### T10.02 처리기와 따로 둔 명세

**구현.** 이 방식은 서버의 도구 73개 모두에 적용된다 [1][2].
도구 함수마다 `@tool` 데코레이터에 도구 이름, 설명 문자열, 손으로 쓴 입력 schema `dict`를 적는다 [1].
데코레이터는 이 세 값과 처리 함수를 `ToolSpec`으로 묶어 모듈 수준의 등록부 `_REGISTRY`에 이름을 키로 넣는다 [1].
입력 schema는 처리 함수의 서명에서 만들지 않고 설명도 docstring에서 가져오지 않는다 [1].
`list_tools`는 등록부에 들어간 차례대로 이름, 설명, `inputSchema` 세 필드를 돌려준다 [1].
실행 확인에서 도구 73개 모두 등록 이름과 함수 이름이 같았고 입력 schema의 속성 이름과 처리 함수의 인자 이름도 같았다 [2].
같은 실행 확인에서 기본값을 schema와 처리 함수 양쪽에 둔 인자의 두 기본값도 모두 같았다 [2].
도구 38개는 입력 schema의 어느 속성에도 `description`이 없고 `list_scheduled_tasks`, `detect_persistence`, `parse_linux_cron_jobs`의 schema에는 `required`가 없다 [2].

등록부는 모듈을 불러올 때 데코레이터가 실행되며 채워진다.
`__init__.py`는 끝에서 `_load_extension`으로 `_v04_expansion`, `sift_adapters`, `_v05_supply_chain`, `_v06_macos_linux`, `_v07_sigma`를 차례로 불러온다 [3].
`_load_extension`은 그 모듈과 하위 모듈을 `sys.modules`에서 먼저 지운 뒤 불러오므로 `dfir_mcp`를 다시 불러와도 확장 모듈의 데코레이터가 다시 실행된다 [3].
기준 커밋의 메시지는 이 변경 전에는 `dfir_mcp`만 다시 불러오면 확장 모듈이 캐시에 남아 등록부가 `__init__.py`의 34개로 줄었다고 적는다 [4].
실행 확인에서 등록부의 도구는 `__init__.py` 34개, `_v04_expansion` 4개, `sift_adapters` 25개, `_v05_supply_chain` 6개, `_v06_macos_linux` 3개, `_v07_sigma` 1개였다 [2].
`sys.modules`에서 `dfir_mcp`만 지우고 다시 불러온 뒤에도 도구는 73개였다 [2].

두 진입점은 같은 `list_tools`로 명세를 내보낸다 [5][6].
`server.py`는 `tools/list`에 `list_tools`의 결과를 그대로 싣고 초기화 응답의 `capabilities`에 빈 `tools`만 싣는다 [5].
`server_stdio.py`는 결과마다 MCP Python SDK의 `Tool`을 이름, 설명, `inputSchema`만 주어 만든다 [6].
그래서 도구 명세에는 annotation, 제목, 출력 schema가 없다 [6].
MCP Python SDK 1.29.1은 목록 변경 알림 설정이 없으면 `tools.listChanged`를 거짓으로 선언한다 [7].
`server.py`는 `tools/list`의 `cursor`를 읽지 않고 모든 도구를 한 번에 돌려준다 [5].
서버는 MCP 리소스와 프롬프트를 두지 않고 `server.py`는 `resources/list`에 -32601 오류를 돌려준다 [5].
실행 확인에서 두 진입점 모두 도구 73개를 돌려주었고 SDK 클라이언트로 받은 목록에 annotation, 제목, 출력 schema가 있는 도구는 없었다 [8].
`server_stdio`의 `capabilities`는 `tools.listChanged`가 거짓이었고 `server.py`의 `capabilities`는 `{"tools": {}}`였다 [8].
실행 설정이나 클라이언트에 따라 명세를 바꾸는 코드는 없다 [1].

**한계.** 다음 도구는 설명이나 입력 schema가 알리는 처리와 처리 함수의 동작이 다르다.

`analyze_web_access_log`의 `log_format`은 `combined`, `common`, `iis_w3c`, `auto` 가운데 하나를 받지만 처리 함수는 이 값을 쓰지 않고 줄 모양으로 형식을 고른다 [9].
실행 확인에서 같은 접근 기록을 `auto`와 `iis_w3c`로 부르면 응답이 같았다 [8].

`parse_browser_history`의 `browser`는 `chrome`, `edge`, `firefox`, `safari`, `auto` 가운데 하나를 받는다 [10].
처리 함수는 SQLite 파일을 읽을 때 이 값과 관계없이 테이블 이름으로 브라우저를 고르고 부속 CSV를 읽을 때는 받은 값을 `browser`에 그대로 싣는다 [10].
실행 확인에서 Chromium 형식의 파일을 `browser` 값 `firefox`로 부르면 응답의 `browser`가 `chromium`이었다 [8].

`detect_dns_tunneling`의 `volume_window_seconds`는 질의량을 세는 시간 창으로 설명되지만 처리 함수는 이 값을 쓰지 않고 기록 전체에서 상위 도메인마다 질의 수를 센다 [11].
실행 확인에서 같은 상위 도메인의 질의 61건을 8시간에 걸쳐 적은 기록으로 `volume_window_seconds`를 300과 1로 부르면 두 응답 모두 `high_volume_domains`에 이 도메인의 질의 수 61을 실었다 [8].

`parse_linux_cron_jobs`의 `evidence_root`는 설명과 schema가 기본값 `/`를 적는다 [12].
처리 함수는 이 값을 `_safe_resolve`로 검사하고 `_safe_resolve`는 `DFIR_EVIDENCE_ROOT`가 `/`가 아니면 `/`를 증거 폴더 밖 경로로 거부한다 [12][13].
실행 확인에서 `server_stdio`로 인자 없이 부르면 `PathTraversalAttempt` 오류 글이 돌아왔다 [8].

`sift_yara_scan_dir`는 `max_file_size`(기본값 52428800)를 `--max-file-size` 옵션으로 YARA에 넘긴다 [14].
기준으로 삼은 YARA 4.5.8에는 이 옵션이 없고 같은 일을 하는 옵션은 `--skip-larger`(`-z`)다 [15].
YARA 4.5.8은 모르는 옵션을 받으면 `unknown option`을 출력하고 종료 코드 1로 끝난다 [16].
그래서 이 도구는 `max_file_size`를 0 이하로 주지 않으면 빈 `matches`와 `metadata.error`를 돌려준다 [14][16].

`sift_plaso_psort`의 설명은 `output_format`으로 `l2tcsv`, `json_line`, `dynamic`을 적지만 처리 함수는 `l2tcsv`의 출력만 읽고 다른 형식이면 빈 `events`를 돌려준다 [17].

`sift_recmd_run_batch`의 `batch_name` 속성 설명은 `ASEPs`, `kroll`, `USB`, `All`을 적지만 schema에 `enum`이 없다 [18].
처리 함수는 목록에 없는 이름을 오류 없이 `ASEPs`의 배치 파일로 바꾼다 [18].
실행 확인에서 `nosuch`로 부르면 응답의 `batch_name`은 `nosuch`, `batch_file`은 `RECmd_Batch_MC.reb`였다 [8].

`analyze_downloads`의 설명은 Firefox `moz_annos`와 Safari `Downloads.plist`를 읽는다고 적지만 처리 함수는 Chromium의 `downloads` 테이블만 읽는다 [19].
같은 설명은 macOS quarantine xattr로도 MOTW를 확인한다고 적지만 처리 함수는 `*.Zone.Identifier` 파일만 읽는다 [19].

`analyze_kerberos_events`의 설명은 Golden Ticket 후보를 찾는다고 적지만 처리 함수에 그 검사가 없다 [20].
같은 설명이 적는 드문 호스트의 TGT 요청 검사는 처리 함수의 주석이 미뤘다고 적고 결과에 싣지 않는다 [20].

`parse_unified_log`의 설명은 predicate로 거른다고 적지만 입력 schema에 predicate 인자가 없다 [21].

`sift_vol3_windows_runkey`의 설명은 Run과 RunOnce 키를 읽는다고 적지만 처리 함수는 `key` 인자의 키 하나만 읽고 기본값은 `Run` 키다 [22].

`detect_ransomware_behavior`의 설명은 랜섬웨어 확장자로 바뀐 파일을 센다고 적지만 처리 함수는 `Renamed` 표시가 있는 사건을 확장자와 관계없이 센다 [23].

[1] `@tool`은 이름, 설명, schema를 처리 함수와 함께 등록부에 넣고 `list_tools`는 등록부를 그대로 돌려준다.

```python
@dataclass
class ToolSpec:
    name: str
    description: str
    schema: dict
    handler: Callable[..., dict]


_REGISTRY: dict[str, ToolSpec] = {}


def tool(name, description, schema):
    def wrap(fn):
        _REGISTRY[name] = ToolSpec(name=name, description=description,
                                   schema=schema, handler=fn)
        return fn
    return wrap


def list_tools():
    return [{"name": t.name, "description": t.description,
             "inputSchema": t.schema} for t in _REGISTRY.values()]
```

```python
def _safe_resolve(path_str: str) -> Path:
    if not isinstance(path_str, str) or not path_str:
        raise PathTraversalAttempt(f"invalid path: {path_str!r}")
    if "\x00" in path_str:
        raise PathTraversalAttempt("null byte in path")
    if len(path_str) > 1024:
        raise PathTraversalAttempt(f"path too long: {len(path_str)} chars (max 1024)")
    root = EVIDENCE_ROOT.resolve()
    try:
        requested = (EVIDENCE_ROOT / path_str).resolve()
    except OSError as e:
        # File-name-too-long, no-such-process, etc. — treat as path attack
        raise PathTraversalAttempt(f"path resolution failed: {e}") from e
    try:
        requested.relative_to(root)
    except ValueError as e:
        raise PathTraversalAttempt(
            f"path escapes evidence root: {path_str!r} -> {requested}"
        ) from e
    return requested
```
