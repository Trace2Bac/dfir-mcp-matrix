# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 외부 도구 래퍼 25개가 공통으로 쓰는 실행기 `run_tool`에 적용된다 [1].
`run_tool`은 `subprocess.run`을 `check=False`로 부르고 종료 코드가 0이 아니면 `SiftToolFailedError`를 낸다 [1].
이 예외의 문구는 실행 파일 경로, 종료 코드, 표준 오류의 앞 200자를 담고 표준 오류가 비었으면 `(no stderr)`를 담는다 [1].
YARA 래퍼를 뺀 래퍼는 이 예외를 처리하지 않으므로 두 진입점이 예외 종류 이름과 문구를 오류 응답으로 돌려준다 [2][3].
YARA 래퍼 2개는 이 예외를 처리해 `matches`를 빈 목록으로 두고 문구를 `metadata.error`에 싣는다 [4].
실행 확인에서 Volatility 3 2.28.0이 있는 환경으로 0으로 채운 이미지를 `sift_vol3_windows_pslist`에 주면 종료 코드 1과 `Unable to validate the plugin requirements` 문구를 담은 `SiftToolFailedError`가 났다 [5].
YARA 자리에 0이 아닌 종료 코드로 끝나는 시험용 실행 파일을 두고 `sift_yara_scan_dir`를 부르면 빈 `matches`와 종료 코드 문구를 담은 `metadata.error`가 돌아왔다 [5].

**한계.** RECmd 기준 날짜 커밋 `bcd0ac3`의 `Main`은 명령 처리 함수의 결과를 종료 코드로 돌려주지 않는다 [6].
그래서 배치 파일이 없어 RECmd가 처리를 끝내도 `run_tool`의 종료 코드 검사로는 실패가 드러나지 않는다 [6][1].
다른 Zimmerman 도구가 실패할 때 0이 아닌 종료 코드를 내는지는 확인하지 못했다.

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 외부 도구 래퍼 25개의 실행에 적용된다 [1].
`run_tool`의 기본 시간 제한은 600초이고 래퍼마다 다른 값을 준다 [7].
Volatility는 1200초, MFTECmd·EvtxECmd·YARA는 1800초, RECmd는 900초, PECmd·AmcacheParser는 600초, psort는 3600초다 [7].
`sift_plaso_log2timeline`은 인자 `timeout_seconds`로 시간 제한을 받고 기본값은 21600초다 [8].
제한을 넘으면 Python의 `subprocess.run`이 실행한 프로세스를 끝내고 `TimeoutExpired`를 낸다 [9].
`run_tool`은 이 예외를 `SIFT tool timed out after <초>s: <실행 파일>` 문구의 `SiftToolFailedError`로 바꾼다 [1].
`TimeoutExpired`에 담긴 끊기 전 출력은 버리고 같은 명령을 다시 실행하지 않는다 [1].
실행 확인에서 log2timeline 자리에 10초 동안 멈추는 시험용 실행 파일을 두고 `timeout_seconds` 2로 부르면 2초 뒤에 이 문구의 예외가 났다 [5].

시간 초과와 0이 아닌 종료 코드는 같은 `SiftToolFailedError`이고 두 경우는 문구로만 구별된다 [1].
외부 프로그램을 실행하지 않는 도구 48개에는 시간 제한이 없다.
`server.py`는 `notifications/cancelled`를 받아도 아무것도 하지 않는다 [10].
`server_stdio.py`의 처리기는 동기 함수 `call_tool`을 이벤트 루프에서 바로 부르므로 취소 알림이 실행 중인 외부 도구를 끝내는지는 확인하지 못했다 [11].

**한계.** `sift_plaso_log2timeline`이 시간 제한에 걸리면 log2timeline이 그때까지 쓴 저장 파일이 `DFIR_DERIVED_ROOT` 아래에 남는다 [8].
이 도구는 이미 있는 저장 파일 경로를 받으면 `FileExistsError`를 내므로 같은 경로로 다시 실행할 수 없다 [8].
실행 확인에서 저장 파일을 먼저 만들고 멈추는 시험용 실행 파일로 시간 제한에 걸리게 하면 그 파일이 남았고 같은 경로로 다시 부르면 `FileExistsError`가 났다 [5].
`subprocess.run`은 직접 실행한 프로세스만 끝낸다 [9].
log2timeline이 만든 작업자 프로세스가 시간 초과 뒤에도 남는지는 확인하지 못했다.
`timeout_seconds`의 입력 schema에는 최솟값과 최댓값이 없다 [12].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 외부 도구 래퍼의 출력 처리에 적용된다 [13][14][15][16].
Volatility 래퍼는 표준 출력이 비어 있지 않으면 CSV로 읽고 CSV로 읽히지 않으면 줄마다 `line` 하나를 담은 행으로 돌려준다 [13].
표준 출력이 비면 행 0개를 돌려준다 [13].
`sift_mftecmd_parse`는 MFTECmd가 CSV를 만들지 않으면 `error` 값 `no CSV produced`와 표준 오류의 끝 500자를 `metadata`에 싣는다 [14].
YARA 래퍼는 표준 출력에서 `warning:`이나 `error:`로 시작하는 줄을 빼고 나머지 줄을 규칙 이름과 경로로 읽는다 [15].
`sift_plaso_psort`는 psort가 쓴 출력 파일을 `output_format`이 `l2tcsv`일 때만 CSV로 읽는다 [16].
`sift_plaso_log2timeline`은 표준 오류의 끝 500자와 저장 파일의 해시를 응답에 싣고 저장 파일의 내용은 읽지 않는다 [8].
`sift_recmd_query_key`는 RECmd의 표준 출력을 읽지 않고 `raw_output`에 그대로 싣는다 [17].

**한계.** EvtxECmd, PECmd, RECmd 배치, AmcacheParser 래퍼는 CSV가 만들어지지 않아도 오류 없이 빈 결과를 돌려준다 [18][19][20][21].
EvtxECmd와 PECmd의 내부 함수는 이때 표준 오류의 끝 500자를 남기지만 공개 도구가 응답에 옮기지 않는다 [18][19].
`sift_mftecmd_timestomp`는 `sift_mftecmd_parse`의 결과에서 행만 읽으므로 CSV가 없을 때 `error` 없이 발견사항 0건을 돌려준다 [22].
실행 확인에서 CSV를 만들지 않고 종료 코드 0으로 끝나는 시험용 실행 파일로 부르면 `sift_mftecmd_parse`만 `no CSV produced`를 싣고 나머지 다섯 도구는 빈 결과를 돌려주었다 [5].
`sift_plaso_psort`는 `output_format`이 `l2tcsv`가 아니면 psort가 출력 파일을 써도 사건 0개를 오류 없이 돌려준다 [16].
실행 확인에서 `json_line`으로 부르면 시험용 실행 파일이 출력 파일을 썼는데도 `events`가 빈 목록이었다 [5].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 두 진입점이 받는 모든 도구 호출에 적용된다 [2][3].
`server.py`는 도구 처리 중 난 예외를 처리해 JSON-RPC 오류 코드 -32000과 `<예외 종류>: <문구>`를 돌려주고 표준 오류에 traceback을 남긴다 [2].
`server_stdio.py`는 같은 예외를 처리해 `{"error": <예외 종류>, "detail": <문구 앞 500자>}` 글을 돌려준다 [3].
이 글은 MCP Python SDK 1.29.1이 `isError`를 거짓으로 둔 결과로 보낸다 [3][23].
실행 확인에서 읽기 권한이 없는 파일로 `analyze_event_logs`를 부르면 처리되지 않은 `PermissionError`가 도구 밖으로 나왔다 [5].
같은 실행 확인에서 경로 검사 예외와 래퍼의 예외는 `server.py`에서 -32000 오류가, `server_stdio`에서 `isError`가 거짓인 `error` 글이 되었다 [5].

일부 도구는 분석 중 난 예외를 도구 안에서 처리해 실패를 결과에 싣는다.
`parse_registry_hive`는 python-registry가 하이브를 열지 못하면 `hive_open_failed`를, 키를 열지 못하면 `key_open_failed`를 예외 종류와 함께 돌려준다 [24].
값 하나를 읽지 못하면 그 값의 항목에 `error`를 싣고 나머지 값을 계속 읽는다 [25].
`parse_knowledgec`, `parse_browser_history`, `analyze_downloads`는 SQLite를 읽다 예외가 나면 `sqlite_read_failed`를 돌려준다 [26].
`parse_launchd_plist`는 `plistlib`이 낸 예외를 `plist_parse_failed`로, `parse_macos_quarantine`은 `sqlite3.Error`를 `error`로 돌려준다 [27].
`parse_linux_text_log`, `parse_linux_shell_history`, `grep_shell_history_for_c2`, `detect_dns_tunneling`, `match_sigma_rules`는 증거 파일을 읽다 난 예외를 `error`로 돌려준다 [28].
`parse_linux_cron_jobs`는 읽지 못한 cron 파일을 `error`가 든 항목으로 작업 목록에 넣고 다른 파일을 계속 읽는다 [29].
`detect_credential_access`는 Sysmon 사건 파일을 읽다 난 예외를 `error`가 든 발견사항 항목으로 넣는다 [30].
실행 확인에서 형식이 맞지 않는 하이브로 `parse_registry_hive`를 부르면 `hive_open_failed`와 `ParseException`이, 읽기 권한이 없는 파일로 `parse_linux_text_log`를 부르면 `read_failed`가 돌아왔다 [5].

**한계.** 다음 경로에서는 분석 중 난 예외나 읽지 못한 항목이 실패로 표시되지 않는다.
`detect_defense_evasion`은 MFT CSV를 읽다 예외가 나면 그때까지 찾은 불일치만 싣고 예외를 알리지 않는다 [31].
`detect_webshell`은 파일 내용을 읽다 예외가 나면 내용 검사만 건너뛰고 그 파일을 검사한 파일 수에 센다 [32].
`analyze_downloads`는 `Zone.Identifier` 파일을 읽지 못하면 알리지 않고 건너뛴다 [33].
`scan_pth_files_for_supply_chain_iocs`와 `detect_nodejs_install_hooks`는 읽지 못한 파일을 검사한 파일 수에 세고 건너뛴다 [34].
`analyze_event_logs`와 `parse_unified_log`는 규칙을 적용하다 예외가 나면 그 규칙을 건너뛴다 [35].
사건 JSON을 줄 단위로 읽는 도구는 JSON으로 읽히지 않는 줄을 건너뛰고 건너뛴 줄의 수를 싣지 않는다 [36].
두 진입점은 도구 처리 중 난 `KeyError`를 도구 이름을 찾지 못한 경우와 같은 응답으로 돌려준다 [2][3].
`server.py`는 이 경우 JSON-RPC 오류 코드 -32601을, `server_stdio.py`는 `ToolNotFound`를 돌려준다 [2][3].
기준 커밋의 도구 처리 코드에서 `KeyError`가 나는 경로는 찾지 못했다 [2][3].

@app.call_tool()
async def handle_call_tool(name: str, arguments: dict) -> list[TextContent]:
    """Execute a registered function. Any attempt to call something not in
    _REGISTRY raises the same KeyError the in-process path would raise."""
    try:
        result = call_tool(name, arguments or {})
        return [TextContent(
            type="text",
            text=json.dumps(result, default=str, indent=2),
        )]
    except KeyError as e:
        # Surface the ToolNotFound error as a structured result so the
        # agent can reason about it rather than crashing.
        return [TextContent(
            type="text",
            text=json.dumps({"error": "ToolNotFound", "detail": str(e)}),
        )]
    except Exception as e:
        return [TextContent(
            type="text",
            text=json.dumps({"error": type(e).__name__, "detail": str(e)[:500]}),
        )]
