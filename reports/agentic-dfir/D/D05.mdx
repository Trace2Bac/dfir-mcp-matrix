# D05 파생물 저장 실패 처리

### D05.01 오류·부분 완료 표시

**구현.** 이 방식은 `sift_plaso_log2timeline`이 Plaso 저장 파일을 만드는 경로에 적용된다 [1].
`log2timeline.py`가 0이 아닌 코드로 끝나거나 시간 제한을 넘으면 공통 실행 함수 `run_tool`이 `SiftToolFailedError`를 일으킨다 [2].
실행 파일을 찾지 못하면 `_which`가 `SiftToolNotFoundError`를 일으킨다 [3].
`sift_plaso_log2timeline`은 이 예외와 상위 폴더를 만들다 난 예외를 처리하지 않고 호출한 쪽으로 넘긴다 [1].
`server_stdio`의 처리기는 예외를 `{"error": <예외 이름>, "detail": …}` 글로 바꿔 돌려준다 [4].
처리기가 글 목록을 돌려주면 MCP Python SDK 1.29.1은 `isError`를 거짓으로 둔 결과를 만든다 [5].
`server`는 같은 예외를 코드 `-32000`의 JSON-RPC 오류 응답으로 돌려준다 [6].
그래서 저장이 실패한 호출에는 저장 파일 경로와 해시를 담은 응답이 나가지 않는다 [1][4][6].
가짜 실행 파일이 1로 끝나게 하면 `server_stdio`는 `isError`가 거짓인 `{"error": "SiftToolFailedError", …}` 글을, `server`는 `-32000` 오류 응답을 돌려주었다 [7].

Zimmerman 도구 래퍼와 `sift_plaso_psort`의 CSV는 호출 안에서 지우는 임시 폴더에 쓰는 중간 파일이고 보관하는 파생물이 아니다 [8].

같은 저장소의 클라이언트와 사용자 CLI가 쓰는 파일은 서버 구현으로 보지 않고 사실로 적는다.
`dfir_agent`의 결정적 모드는 `report.json`을, `analyze.py`는 `report.json`·`findings.json`·`summary.json`을 쓸 때 예외를 처리하지 않으므로 쓰기가 실패하면 명령이 오류로 끝난다 [9].

**한계.** 실패한 호출이 쓰다 만 저장 파일은 지우지 않는다 [1][2].
가짜 실행 파일이 저장 파일에 몇 글자를 쓴 뒤 1로 끝나거나 시간 제한을 넘긴 경우 모두 그 파일이 `DFIR_DERIVED_ROOT` 아래에 남았다 [7].
그 경로로 다시 `sift_plaso_log2timeline`을 부르면 이미 있는 파일이라 거부된다 [1].
`sift_plaso_psort`는 저장 파일이 끝까지 만들어졌는지 보지 않고 `psort.py`에 넘긴다 [10].
`log2timeline.py`가 0으로 끝났는데 저장 파일이 없으면 서버는 오류 없이 `storage_sha256`이 `null`인 응답을 돌려준다 [2][11].
이 응답의 `output_storage_path`는 없는 파일을 가리킨다 [11].

async def handle_call_tool(name: str, arguments: dict) -> list[TextContent]:
    """Execute a registered function. Any attempt to call something not in
    _REGISTRY raises the same KeyError the in-process path would raise."""
    try:
        result = call_tool(name, arguments or {})
        return [TextContent(
            type="text",
            text=json.dumps(result, default=str, indent=2),
        )]
    except KeyError as e:

        )]

            type="text",

        )]
