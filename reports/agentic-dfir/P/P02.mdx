# P02 다음 작업 결정

### P02.02 규칙·조사 상태로 추천

**구현.** 이 방식은 부속 CSV, 입력 파일, 파서 라이브러리, 외부 도구 실행 파일이 없을 때의 응답과 `parse_prefetch`가 파일 이름만 읽은 응답에 적용된다 [1][2][3][4][5][6][7].
`get_amcache`는 부속 CSV가 없으면 `amcache_csv_missing` 오류에 AmcacheParser를 실행해 그 CSV를 하이브 옆에 같은 이름으로 두라는 `hint`를 싣는다 [1].
`parse_shimcache`·`parse_shellbags`·`extract_mft_timeline`은 부속 CSV가 없으면 `AppCompatCacheParser.exe`·`SBECmd.exe`·`MFTECmd.exe`를 실행하라는 `hint`를 싣는다 [2].
`parse_unified_log`·`parse_fsevents`·`parse_systemd_journal`은 입력 파일이 없으면 그 입력을 만드는 `log show`·`FSEParser.py`·`journalctl` 명령을 `hint`로 싣는다 [3].
`parse_auditd_log`와 `parse_bash_history`는 입력 파일이 없으면 흔한 파일 위치를 `hint`로 싣는다 [3].
`parse_knowledgec`와 `parse_browser_history`는 SQLite DB를 읽지 못하거나 브라우저 표를 찾지 못하면 부속 CSV를 만들라는 `hint`를 싣는다 [4].
`parse_registry_hive`는 `python-registry`가 없으면 `pip install python-registry`를 `hint`로 싣는다 [5].
키를 찾지 못하면 키 경로를 하이브 루트 기준으로 주라는 `hint`와 하이브 루트 키 이름 `root_key_in_hive`를 싣는다 [5].
`parse_prefetch`는 부속 JSON이 없어 파일 이름만 읽으면 실행 횟수와 불러온 모듈은 PECmd로 얻으라는 `note`를 붙인다 [6].
외부 도구 래퍼는 실행 파일을 찾지 못하면 환경변수로 경로를 주거나 `scripts/install.sh`를 실행하라는 문구로 `SiftToolNotFoundError`를 낸다 [7].
`server_stdio`는 이 예외를 오류 이름과 문구를 담은 JSON 글로 돌려준다 [8].
이 문구들은 오류마다 정해 둔 글이고 서버는 다음 호출을 대신 고르거나 실행하지 않는다 [1][2][3].
부속 CSV가 없다는 `hint`는 같은 자료를 읽는 래퍼 `sift_amcacheparser_parse`·`sift_mftecmd_parse`를 가리키지 않는다 [1][2].

그 밖의 응답은 다음에 할 작업을 싣지 않는다.
`correlate_events`는 IP-KVM 장치 삽입 뒤 정한 시간 안에 로그온이 있으면 `status`가 `UNRESOLVED`인 항목을 `contradictions`에 싣고 다음 할 일은 적지 않는다 [9].
`correlate_timeline`은 `dfir_corr`가 만든 `contradictions`를 응답에 옮기지 않는다 [10].
같은 행위자의 서로 다른 사건 두 개를 주자 `dfir_corr`를 직접 부른 결과에는 `UNRESOLVED` 항목이 하나 있었고 `correlate_timeline` 응답에는 `contradictions` 필드가 없었다 [11].
`dfir_corr`의 `correlate_download_to_execution`은 대응하는 내려받기가 없는 실행이 있으면 `revision_required`를 참으로 둔다 [12].
같은 이름의 MCP 도구는 이 함수를 부르지 않고 `dfir_mcp` 안의 다른 구현을 쓰므로 응답에 `revision_required`가 없다 [12].
서버는 절차서나 조사 프로필을 돌려주는 도구를 두지 않고 MCP 리소스, 프롬프트, 서버 지침도 두지 않는다 [13].
MCP SDK 클라이언트로 `server_stdio`를 초기화하자 응답의 `instructions`는 비어 있었다 [14].

같은 저장소의 클라이언트 `dfir_agent`는 조사 절차를 클라이언트 쪽에 둔다 [15][16].
live 모드는 `dfir_playbook/`에서 이름 차례로 마지막인 `senior-analyst-v*.yaml`을 읽어 `sequence`의 단계 이름, 설명 앞부분, `mcp_calls`를 시스템 지침에 넣는다 [15].
플레이북의 `exit_criteria`, `next_call_decisions`, `stop_conditions`는 이 코드가 읽지 않는다 [15][17].
결정적 모드는 플레이북을 읽지 않고 코드에 적은 네 단계를 차례로 실행한다 [16].
이 절차는 클라이언트가 정하므로 다른 MCP 클라이언트로 붙으면 적용되지 않고 서버 응답에도 실리지 않는다.

**한계.** `get_amcache`의 `hint`는 CSV를 하이브 옆에 두라고 적으므로 이를 따르려면 증거 폴더에 파일을 써야 한다 [1].
AmcacheParser는 이름 앞에 시각이 붙은 CSV 여러 개를 쓰고 `hint`가 가리키는 `Amcache.csv` 하나를 만들지 않는다 [18].

### P02.04 서버 코드에 고정한 분석 절차

**구현.** 이 방식은 `detect_persistence`, `sift_mftecmd_timestomp`와 검사 여러 개를 정한 차례로 실행해 합치는 탐지 도구 4개에 적용된다 [19][20][21][22][23][24].
`detect_persistence`는 `NTUSER.DAT`·`SOFTWARE`의 Run 키 CSV, `SYSTEM`의 서비스 CSV, `list_scheduled_tasks`의 예약 작업을 차례로 읽는다 [19].
세 결과는 `items` 하나로 합치고 `high_severity`와 `by_mechanism`으로 나눠 센다 [19].
`sift_mftecmd_timestomp`는 `sift_mftecmd_parse`를 행 상한 1,000,000으로 부른 뒤 행마다 `$SI`·`$FN` 시각 비교 두 가지를 적용한다 [20].
`detect_exfiltration`은 보관 파일 생성, 알려진 업로드 도메인과 큰 송신, 1시간 안의 생성 뒤 업로드, 업로드 서비스 방문을 차례로 검사하고 가장 높은 등급을 `max_severity`로 낸다 [21].
`detect_ransomware_behavior`는 복구 방해 명령, 짧은 시간 안의 서비스 중지, 몸값 안내문 생성, 랜섬웨어 확장자로의 대량 이름 변경을 차례로 검사한다 [22].
`detect_defense_evasion`은 `events_json`의 로그 삭제 사건, 명령줄의 로그 삭제·시각 변조 명령, `mft_csv`의 `$SI`·`$FN` 불일치를 차례로 검사한다 [23].
`detect_credential_access`는 덤프 도구 이름과 명령줄, `sysmon_events_json`의 LSASS 접근, 민감 경로 접근을 차례로 검사한다 [24].
`detect_exfiltration`과 `detect_ransomware_behavior`는 증거를 읽지 않고 모델이 앞선 도구의 결과로 넘긴 목록에 검사를 적용한다 [21][22].
모델은 이 도구와 인자만 고르고 그 안의 단계는 서버 코드가 정한다.
서버 안에서 모델을 불러 계획을 세우는 경로는 없다.

**한계.** `detect_persistence`는 정해 둔 CSV가 없는 단계를 건너뛰고 `sources_examined`에는 읽은 Run 키·서비스 CSV만 적는다 [19].
예약 작업 파일은 읽어도 `sources_examined`에 적지 않는다 [25].
`list_scheduled_tasks`가 Tasks 폴더를 찾지 못해 붙이는 `note`는 `detect_persistence` 응답으로 옮겨지지 않는다 [25].
빈 증거 폴더에서 `detect_persistence`는 `sources_examined`가 빈 목록이고 `total_mechanisms`가 0인 응답을 돌려주었다 [26].
같은 폴더에서 `list_scheduled_tasks`를 따로 부르면 `no Tasks directory in evidence tree`가 실렸다 [26].
`detect_defense_evasion`은 `events_json`이나 `mft_csv`가 가리키는 파일이 없으면 그 단계를 건너뛰고 응답에 알리지 않는다 [23].
MFT 단계는 예외가 나면 그 줄에서 멈추고 그때까지 모은 불일치만 싣고 멈춘 사실은 알리지 않는다 [23].
`sift_mftecmd_timestomp`는 파싱 단계가 `no CSV produced`를 돌려주어도 그 오류를 옮기지 않고 `findings`가 빈 응답을 돌려준다 [27].
파싱 단계의 행 상한 1,000,000에 닿았는지도 응답에 싣지 않는다 [27].
없는 파일 이름 두 개와 로그 삭제 명령 하나를 주자 `finding_count`가 1인 응답이 돌아왔고 두 파일을 읽지 못했다는 표시는 없었다 [26].
