# F01 판단 지침

### F01.04 공통 확인 절차 안내

**구현.** 이 방식은 `match_sigma_rules`의 도구 설명에 적용된다 [1].
설명은 이 도구로 발견사항을 알려진 탐지 패턴과 교차 확인(corroborate)하라고 적는다 [1].
예로 HID 키보드 USB 장치 삽입이나 의심스러운 예약 작업을 이 도구로 확인하라고 적고 규칙은 일반 패턴이지 사건의 답이 아니라고 덧붙인다 [1].
이 문구는 발견사항의 내용과 관계없이 늘 같다 [1].
모델이 이 안내를 따르는지는 서버가 보지 않는다.

서버에는 서버 지침, MCP 리소스, MCP 프롬프트가 없다.
`server_stdio.py`는 MCP SDK의 저수준 `Server`를 이름만으로 만들고 `list_tools`와 `call_tool` 처리기만 등록한다 [2].
SDK 없이 JSON-RPC를 처리하는 `server.py`의 `initialize` 응답에도 `instructions`가 없다 [3].
MCP SDK 클라이언트로 받은 `initialize` 응답의 `instructions`는 `None`이었고 `resources/list`와 `prompts/list`는 오류로 끝났다 [4].

조사 전체에 걸치는 해석 원칙과 결론 서술 방식은 도구 설명과 응답 어디에도 없다 [4].
부재가 무죄를 뜻하지 않는다는 원칙이나 근접이 인과가 아니라는 원칙, 확정하지 못한 결론을 후보로 적으라는 안내가 그 예다.
도구 설명과 응답의 다른 해석 문구는 그 도구 결과 하나의 뜻이나 다음에 확인할 것을 적는다.

- `sift_vol3_windows_psscan`의 설명은 psscan에 있고 pslist에 없는 프로세스를 rootkit 신호로 본다고 적는다 [5].
- `sift_vol3_windows_netscan`의 설명은 외부 주소를 위협 정보와 대조하라고 적는다 [5].
- `detect_credential_file_access`의 설명은 의심 패키지를 설치한 직후의 자격증명 파일 접근을 유출 신호로 본다고 적는다 [5].
- `analyze_event_logs`는 규칙 `scheduled_task_create`의 설명 "review for legitimacy"를 그 규칙의 경보마다 싣는다 [6].

같은 저장소의 클라이언트 `dfir_agent`는 live 모드에서 모델에게 주는 시스템 지시문에 판단 지침을 넣는다 [7].
지시문은 `dfir_playbook/`에서 이름 차례로 마지막인 playbook YAML의 `sequence`와 `classification_guidance`를 옮긴 글이다 [7].
지시문은 모든 단계에서 서로 다른 가설을 세우고 다른 출처로 교차 확인하며 모순을 숨기지 말고 모든 발견사항이 도구 호출을 하나 이상 가리키게 하라고 적는다 [8].
`analyze.py`가 모델에게 주는 첫 요청도 가설을 여러 출처로 교차 확인하고 증거가 뒷받침하는 것만 보고하라고 적는다 [9].
이 지시는 클라이언트 구성이어서 다른 MCP 클라이언트로 서버에 붙으면 모델에게 전달되지 않는다.
