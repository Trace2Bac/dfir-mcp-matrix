# F06 보고 산출물 구성

### F06.01 증거·환경 manifest 포함

**구현.** 이 방식은 사용자가 같은 저장소의 CLI `analyze.py`를 실행해야 만들어지는 `summary.json`에 적용된다 [1].
MCP 도구에는 보고 산출물을 만드는 도구가 없고 다른 MCP 클라이언트로 서버에 붙으면 이 파일은 만들어지지 않는다 [2].
`analyze.py`는 `ANTHROPIC_API_KEY`가 있어야 실행되고 사례마다 `dfir_agent`를 live 모드로 실행한 뒤 출력 폴더에 `summary.json`을 쓴다 [3][4].
`summary.json`에는 `--model`로 준 모델 이름, 실행한 컴퓨터의 사용자·호스트 이름, 운영체제와 릴리스, Python 버전, 증거 폴더 경로, 발견사항 수, 반복 수, 토큰 사용량이 실린다 [1].
증거 파일 목록과 해시, 서버와 외부 도구의 버전은 실리지 않는다 [1].
`analyze.py`는 증거 폴더의 파일 목록을 200개까지 모델에게 주는 첫 요청에 넣지만 이 목록을 파일로 남기지 않는다 [5][1].
`dfir_agent`를 직접 실행하면 결정적 모드와 live 모드 모두 증거나 환경 목록을 쓰지 않는다 [6][7].
`summary.json`은 API 키가 필요해 코드로만 확인했다 [1].

### F06.03 발견사항과 근거 링크 포함

**구현.** 이 방식은 사용자가 `dfir_agent`를 결정적 모드로 실행할 때 쓰이는 `report.json`에 적용된다 [6].
`report.json`의 발견사항마다 `finding_id`, 설명, 근거 호출의 `audit_ids`가 실린다 [8][9].
`audit_ids`는 같은 폴더 `audit.jsonl` 항목의 `audit_id`이고 클라이언트는 호출할 때 그 항목의 `finding_ids`에 앞으로 낼 발견사항 ID를 적는다 [10].
사용자 CLI `dfir_audit`의 `lookup`은 `audit_id`로 항목 하나를, `trace`는 발견사항 ID가 적힌 항목 전체를 찾아 표준 출력에 낸다 [11].
찾은 항목에는 도구 이름, 인자, 출력의 SHA-256이 있고 출력 자체는 없다 [12].
결정적 실행의 `report.json`에서 `F-001`의 `audit_ids` 1개를 `dfir_audit trace F-001`로 찾자 `get_amcache` 항목 1건이 나왔다 [13].
live 모드의 발견사항은 모델이 `REPORT:`에 적은 글이고 그 안의 `tool_calls`도 모델이 적은 값이다 [14].
dry-run에서는 클라이언트 코드가 `F-013` 하나를 만들고 그때까지 부른 도구 이름 전체를 `tool_calls`로 싣는다 [15].

**한계.** 결정적 모드는 `analyze_usb_history` 호출을 IP-KVM 사건이 나왔는지 보기 전에 `F-013`으로 표시한다 [16].
빈 증거 폴더로 실행하자 `report.json`에는 `F-013`이 없었고 `dfir_audit trace F-013`은 그 `analyze_usb_history` 항목을 돌려줬다 [17].
`F-001`은 근거 호출의 응답이 오류여도 그 호출을 근거로 싣는다 [9][13].
호출 기록에는 출력이 없어 산출물만으로는 근거 응답의 내용을 볼 수 없다 [12].
dry-run의 `tool_calls`에는 `amcache_csv_missing`으로 끝난 `get_amcache`도 들어 있다 [18].

### F06.04 검증·한계 포함

**구현.** 이 방식은 사용자가 `dfir_agent`를 결정적 모드로 실행할 때 쓰이는 `progress.jsonl`에 적용된다 [19].
`--max-iterations`에 닿아 남은 단계를 건너뛰면 `progress.jsonl` 마지막 줄의 `phase`가 `forced_exit`이 되고 `unresolved`에 보고서가 일부라는 문장이 실린다 [19][20].
`--max-iterations` 1로 실행하자 이 줄이 실렸다 [21].
결정적 모드는 끝에 호출 기록의 해시 체인을 검증하고 결과를 표준 출력과 종료 코드로만 알린다 [22].
`dfir_audit summary`도 체인 검증 결과를 표준 출력에만 낸다 [11].
출력 폴더의 파일에는 체인 검증 결과와 증거 해시 재대조 결과가 실리지 않는다 [6][7].
live 모드는 반복 한도에 닿으면 모델에게 지금까지 모은 증거로 보고서를 쓰라고 요청하지만 그 사실을 `live_summary.json`에 싣지 않는다 [23][7].

**한계.** 일부만 실행한 경우에도 `report.json`에는 보고서가 일부라는 표시가 없다 [6][19].
`--max-iterations` 1로 실행한 `report.json`은 `unresolved`가 빈 목록이었다 [21].
`report.json`의 `iterations`는 호출이 없는 단계도 센 값이어서 결정적 실행의 `iterations` 5는 호출 3건과 다르다 [24][13].

### F06.05 내보내기

**구현.** 이 방식은 사용자가 `dfir_agent`나 `analyze.py`를 실행할 때 쓰이는 파일에 적용된다 [22][7][1].

- 결정적 모드는 `--out` 폴더에 `report.json`, `audit.jsonl`, `progress.jsonl`을 쓰고 그 폴더 경로를 표준 출력에 낸다 [22].
- live 모드는 같은 폴더에 `live_transcript.txt`, `live_tool_calls.jsonl`, `live_summary.json`을 쓴다 [7].
- `analyze.py`는 `out/<tier>/<case-id>/<시각>/` 폴더를 만들어 live 모드를 실행하고 `live_summary.json`을 `report.json`으로 옮겨 쓴 뒤 `findings.json`과 `summary.json`을 더 쓴다 [4][1].
- `analyze.py`는 새 실행 폴더를 만들기 전에 같은 사례의 실행 폴더를 최근 10개만 남기고 지운다 [25].
- `analyze.py`는 발견사항이 0개이면 한 번 더 실행하고 두 실행 폴더를 모두 남긴다 [26].
- `examples/demo-run.sh`는 `examples/out/demo` 폴더를 지운 뒤 그 폴더에 결정적 모드를 실행하고 체인을 검증한다 [27].

결정적 모드와 live 모드의 dry-run으로 실행하자 출력 폴더에 각 모드의 파일 3개가 쓰였다 [13][18].
호출 기록 파일은 클라이언트가 호출마다 한 줄씩 쓰고 보고서에는 호출 목록이 실리지 않는다 [12][28][6].

**한계.** 결정적 모드는 `--out` 폴더에 `audit.jsonl`이 있으면 그 끝에 이어 쓰고 `progress.jsonl`에도 덧붙인다 [29][30].
`report.json`만 새로 쓰므로 같은 폴더로 다시 실행하면 앞 실행의 호출과 단계가 새 보고서의 기록에 섞인다 [22].
`analyze.py`의 설명은 출력 폴더에 `audit.jsonl`과 `progress.jsonl`이 생긴다고 적지만 `analyze.py`가 실행하는 live 모드는 두 파일을 쓰지 않는다 [31][7].
같은 `--out`으로 두 번 실행하자 `audit.jsonl`은 6줄, `progress.jsonl`은 8줄이었고 `report.json`의 발견사항은 2개였다 [32].

### F06.06 미해결 반론·열린 가설 포함

**구현.** 이 방식은 사용자가 `dfir_agent`를 결정적 모드로 실행할 때 쓰이는 `report.json`과 `progress.jsonl`에 적용된다 [6][30].
`report.json`은 주 가설과 대안 가설을 따로 싣고 가설마다 문장, 확신도, 지지·반박 발견사항 ID를 싣는다 [33][6].
`unresolved`에는 USB 기록이 로그온 기록과 맞지 않는다는 모순 문장이 실린다 [34].
`progress.jsonl`은 단계마다 그때의 두 가설과 미해결 목록을 싣는다 [33][30].
가설의 문장과 확신도는 코드에 정해 둔 값이다 [35][34].
live 모드의 `live_summary.json`에는 가설과 미해결 항목을 싣는 칸이 없다 [7].

**한계.** 결정적 모드는 IP-KVM 사건을 찾으면 모순 문장을 `unresolved`에 넣고 다시 호출한 뒤 그 모순이 풀렸다고 보고 가설을 바꾼다 [34].
그 단계의 `progress.jsonl` 줄은 `unresolved`를 비우고 `notes`에 넓힌 시간 범위로 모순이 풀렸다고 적지만 `report.json`의 `unresolved`에는 같은 문장이 남는다 [34][6].
저장소에 커밋된 참조 실행 `examples/out/ref-01`의 두 파일도 이렇게 적혀 있다 [36].
대안 가설에는 닫혔는지 열렸는지 적는 상태 값이 없고 확신도 0.05만 실린다 [34].

### F06.07 판단의 확정 상태 표시

**구현.** 이 방식은 사용자가 `dfir_agent`를 결정적 모드로 실행할 때 쓰이는 `report.json`에 적용된다 [6].
발견사항마다 `status`가 실리고 자료형의 주석은 그 값으로 `confirmed`·`unresolved`·`false_positive`를 적는다 [8].
live 모드의 발견사항은 모델이 적은 `confidence`를 그대로 싣고 클라이언트가 상태를 정하지 않는다 [14][7].
dry-run의 `F-013`은 `confidence` 0.82를 코드에 정해 둔 값으로 싣는다 [15].

**한계.** 결정적 모드는 `Finding`을 만들 때 `status`를 넘기지 않아 모든 발견사항이 기본값 `confirmed`로 실린다 [8][9][34].
`unresolved`나 `false_positive`를 넣는 코드는 없다 [8].
`get_amcache`가 오류를 돌려주거나 증거 폴더가 비어 있어도 `F-001`은 `confirmed`로 실렸다 [13][17].

    def _call(self, tool_name: str, inputs: dict, *,
              output_tokens: int = 500,
              finding_ids: list | None = None) -> tuple[dict, str]:
        """Invoke an MCP tool AND log it. Returns (output, audit_id).

        finding_ids forward-declares which findings this call will support
        so the audit chain is queryable via `dfir-audit trace <fid>`.
        """
        output = call_tool(tool_name, inputs)
        aid = self.audit.log(
            tool_name=tool_name,
            inputs=inputs,
            output=output,
            iteration=self.iteration,
            token_count_in=len(json.dumps(inputs)) // 4,   # rough proxy
            token_count_out=output_tokens,
            finding_ids=finding_ids or [],
        )
        return output, aid

        # playbook schedules additional phases. Exit path writes a closeout
        # report so an early exit is still analyst-readable.
        phases = [
            self._phase_timeline,

            self._phase_finalize,

```python
def _rotate_out_dirs(case_out_root: Path, keep: int = 10) -> None:
    """Keep only the most recent `keep` timestamped run dirs for one case.

    Every analyze run writes out/<tier>/<case-id>/<timestamp>/ with a transcript,
    tool-call log, findings, etc. Left unchecked this grows without bound — basic
    housekeeping says rotate it. We keep the newest `keep` runs per case (by the
    timestamp dir name, which sorts chronologically) and delete the rest. Only
    timestamp-shaped dirs are touched; anything else is left alone. Best-effort:
    a cleanup failure never blocks the run.
    """
    try:
        if not case_out_root.is_dir():
            return
        runs = sorted(
            (p for p in case_out_root.iterdir()
             if p.is_dir() and p.name.isdigit() is False
             and len(p.name) == 15 and "T" in p.name),
            key=lambda p: p.name,
        )
        for old in runs[:-keep] if len(runs) > keep else []:
            shutil.rmtree(old, ignore_errors=True)
    except Exception:  # noqa: BLE001 — housekeeping must not break the run
        pass
```
