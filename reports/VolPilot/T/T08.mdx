# T08 실행 종료 판별

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 `windows_crashinfo`와 `detect_service_tampering`에 적용된다 [1][2].
`run_crashinfo`는 Volatility가 낸 `RuntimeError`의 문구에 `No active exception to reraise`가 있으면 빈 `results`를 돌려준다 [1].
코드 주석은 이 문구를 크래시 덤프가 아닌 이미지에서 Volatility의 `crashinfo`가 내는 오류로 설명한다 [1].
문구가 다른 `RuntimeError`는 다시 내보내므로 FastMCP가 오류 응답으로 돌려준다 [1][3].
`detect_service_tampering`은 `svclist` 결과가 비었는지 보고 비었으면 `os_compatible`을 거짓으로 둔다 [2].
`run_crashinfo`의 `run_plugin`을 바꿔 두 문구의 `RuntimeError`를 내게 하자 `No active exception to reraise`는 빈 `results`가 되고 다른 문구는 그대로 예외로 나왔다 [4].

서버는 Volatility가 기록한 경고나 오류를 읽지 않는다 [5].
FastMCP가 이 기록을 서버의 표준 오류로 보낸다 [6].
플러그인이 예외 없이 오류를 기록하고 행 없이 끝나면 서버는 빈 `results`를 성공 응답으로 돌려준다 [5].
Volatility 2.28.0의 `pedump`는 `pid`와 `kernel_module`이 함께 있거나 함께 없을 때, `svclist`는 지원하지 않는 OS일 때 이렇게 끝난다 [7][8].
`windows_pe_symbols`의 설명도 `symbols`와 `addresses`가 모두 비면 플러그인이 오류를 기록하고 행 없이 끝난다고 적는다 [9].

**한계.** `windows_crashinfo`의 빈 `results`에는 크래시 덤프가 아니어서 비었다는 사실이 실리지 않는다 [1].
`detect_service_tampering`은 `svclist` 결과가 빈 이유를 가리지 않는다 [2].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 `windows_strings`에 적용된다 [10].
`run_strings`는 Volatility가 플러그인을 만들 때 낸 `PluginRequirementException`을 처리해 빈 `results`와 예외 문구를 담은 `error`를 돌려준다 [10].
이 응답은 `isError`가 거짓인 일반 결과다 [11].
없는 `strings_file`로 부르자 `error`에 `The plugin configuration failed to validate`가 실린 응답이 돌아왔다 [11].

다른 도구는 서버 코드가 분석 예외를 처리하지 않는다 [12].
MCP Python SDK 1.27.0의 FastMCP는 도구 함수에서 난 예외를 `Error executing tool <도구>: <문구>` 오류로 바꾸고 응답의 `isError`를 참으로 둔다 [3].
무작위 바이트 이미지로 부른 플러그인 도구와 교차 분석 도구는 모두 이 꼴의 오류를 돌려주었다 [11].
여러 플러그인을 부르는 교차 분석 도구는 `malware.svcdiff`를 뺀 플러그인 하나에서 예외가 나면 호출 전체가 이 오류로 끝나고 앞선 플러그인의 결과는 응답에 싣지 않는다 [13].
실패한 플러그인 실행은 결과 캐시에 넣지 않으므로 같은 인자로 다시 부르면 다시 실행한다 [14].
이미지 폴더에 쓸 수 없으면 플러그인의 `run()`까지 처음 실행된 호출이 설정 파일을 쓰다 난 `PermissionError`로 끝나고 다음 호출부터는 설정 파일을 쓰지 않는다 [15].
서버는 플러그인 실행에 시간 제한을 두지 않는다 [12][14].

**한계.** 다음 경로에서는 분석 중 난 예외가 실패로 표시되지 않고 빈 값이나 빈 결과가 된다.

- `windows_virtmap`은 `SymbolError`가 나면 빈 `results`를 돌려준다 [16].
- `windows_crashinfo`는 Volatility가 낸 `RuntimeError`의 문구가 `No active exception to reraise`이면 빈 `results`를 돌려준다 [1].
- `detect_service_tampering`은 `malware.svcdiff`에서 어떤 예외가 나도 `svcdiff_results`를 빈 `list`로 두고 오류를 싣지 않는다 [2].
- 결과 값을 바꾸는 `_serialize_layerdata`는 이미지 계층을 읽다 예외가 나면 `None`을 돌려주므로 그 필드는 값이 없는 필드와 같은 `null`이 된다 [17].

`run_virtmap`의 `run_plugin`을 `SymbolError`를 내게 바꾸자 빈 `results`가 돌아왔다 [18].

[1] `run_crashinfo`는 오류 문구로 크래시 덤프가 아닌 경우를 가린다.

```python
def run_crashinfo(session: Session) -> dict:
    """Run windows.crashinfo and return crash dump header information.

    Only produces data when the image is an actual Windows crash dump
    (.dmp), not a raw/VM memory snapshot. volatility3's own plugin has a
    bug on that path: it logs "This plugin requires a Windows crash
    dump" and then executes a bare ``raise`` outside any except block,
    which Python turns into ``RuntimeError("No active exception to
    reraise")`` instead of returning cleanly. Caught here and translated
    into an empty result, matching how sibling tools (svclist, consoles,
    truecrypt, ...) report "not applicable to this image" without
    crashing the MCP call.
    """
    try:
        treegrid = run_plugin(session, crashinfo.Crashinfo)
    except RuntimeError as e:
        if "No active exception to reraise" in str(e):
            return {"plugin": "crashinfo", "results": []}
        raise
    return {"plugin": "crashinfo", "results": parse_treegrid(treegrid)}
```
