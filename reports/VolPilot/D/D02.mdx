# D02 파생물 추적

### D02.01 ID·경로 참조

**구현.** 이 방식은 덤프 파일의 이름과 설정 파일의 이름에 적용된다 [1][2][3].
덤프 파일 이름은 서버 코드가 아니라 Volatility 3 2.28.0의 플러그인이 정한다 [1][2].
`dumpfiles`는 `file.<FILE_OBJECT 주소>.<캐시 객체 주소>.<캐시 종류>.<이미지 안 파일 이름>.<확장자>` 이름을 짓는다 [1].
`pedump`는 `PE.<프로세스 객체 주소>.<PID>.<기준 주소>.dmp` 이름을 짓고 커널 모듈이면 프로세스 객체 주소 자리에 0, PID 자리에 4를 넣는다 [2].
이 이름의 주소와 PID는 그 파일을 꺼낸 이미지 안 객체를 가리킨다 [1][2].
덤프 도구의 응답은 행마다 `FileObject`·`FileName`·`Result`(`windows_dumpfiles`)나 `PID`·`Process`·`File output`(`windows_pedump`)을 싣고 `Result`·`File output`에는 파일 이름이 들어간다 [4][5].
설정 파일 이름은 이미지 경로 뒤에 `.vol3cfg.json`을 붙인 것이라 어느 이미지의 설정인지 경로로 가리킨다 [3].

파생물을 만든 호출을 가리키는 값은 없다.
서버는 MCP 도구 호출에 ID를 매기지 않고 호출 기록을 파일이나 DB에 쓰지 않는다 [6].
덤프 파일 이름과 내용에는 이미지 경로나 해시가 들어가지 않는다 [1][2][7].
덤프 파일 곁에 manifest를 두지 않고 입력과 출력의 해시를 남기지 않는다 [7].
덤프 파일을 다른 도구의 입력으로 다시 읽는 도구는 없다.

**한계.** 응답의 `Result`와 `File output`은 실제로 쓴 이름이 아니라 플러그인이 처음 정한 이름이다 [1][7].
서버의 `DumpFileHandler`는 같은 이름의 파일이 있으면 `-1`, `-2`를 붙인 새 이름으로 쓰지만 그 이름을 핸들러의 `preferred_filename`에 되돌려 놓지 않는다 [7].
같은 이름의 파일을 두 번 쓰자 두 번째 내용은 `…exe-1.img`에 들어갔고 `preferred_filename`은 두 번 모두 `…exe.img`였다 [8].
두 번째 호출의 응답 `Result`도 `-1`이 없는 첫 파일 이름이었다 [9].
도구 설명은 이 열에 디스크에 쓴 최종 경로가 들어간다고 적는다 [4][5].
이 값은 `VOL_DUMP_DIR`을 붙이지 않은 파일 이름이다 [1][2][7].
`VOL_DUMP_DIR`는 이미지마다 나뉘지 않으므로 다른 이미지로 다시 시작한 서버가 같은 폴더에 쓴 덤프 파일은 이름만으로 어느 이미지에서 나왔는지 가릴 수 없다 [7][10].

```python
        def close(self):
            if self.closed:
                return None
            self.seek(0)

            output_path = os.path.join(output_dir, self.preferred_filename)
            base, ext = os.path.splitext(output_path)
            counter = 1
            while os.path.exists(_long_path_safe(output_path)):
                output_path = f"{base}-{counter}{ext}"
                counter += 1

            with open(_long_path_safe(output_path), "wb") as fp:
                fp.write(self.read())

            super().close()
```
