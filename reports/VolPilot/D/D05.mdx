# D05 파생물 저장 실패 처리

### D05.01 오류·부분 완료 표시

**구현.** 이 방식은 덤프 도구 `windows_dumpfiles`·`windows_pedump`의 파일 쓰기, `windows_dumpfiles`의 덤프 실패 행, 설정 파일 쓰기에 적용된다 [1][2][3].
서버의 `DumpFileHandler.close`는 파일을 열거나 쓰다가 난 예외를 처리하지 않는다 [1].
이 예외는 Volatility 3 플러그인과 `parse_treegrid`를 거쳐 도구 함수 밖으로 나가고 MCP SDK가 그 호출을 오류 응답으로 돌려준다 [1][4].
읽기 전용 폴더에 묶은 핸들러로 파일을 닫자 `PermissionError`가 났고 파일은 생기지 않았다 [5].
`windows_dumpfiles`에서 예외가 난 MCP 호출의 응답은 `isError` 참과 `Error executing tool` 문장이었다 [6].

Volatility 3 2.28.0의 `dumpfiles`는 캐시 객체 하나의 페이지를 읽지 못하거나 읽은 바이트가 없으면 그 행의 `Result`를 `Error dumping file`로 싣는다 [7].
그래서 `windows_dumpfiles`의 응답은 꺼내지 못한 캐시 객체를 행마다 알린다 [7][2].

설정 파일 `<이미지 경로>.vol3cfg.json`을 쓰지 못하면 그 호출도 오류로 끝난다 [3][8].
`save_config`는 쓰기 전에 설정을 세션에 넣고 파일 쓰기 예외를 처리하지 않는다 [3].
공통 실행 함수는 플러그인의 `run()`을 부른 뒤 결과 행을 만들기 전에 설정을 저장하므로 저장이 실패하면 결과 행 없이 오류가 난다 [8].
이미지 폴더를 읽기 전용으로 둔 시험에서 첫 호출은 `PermissionError`로 끝났고 덤프 폴더에는 파일이 생기지 않았다 [9].

**한계.** 한 호출에서 파일 몇 개를 쓴 뒤 다음 파일 쓰기가 실패하면 앞서 쓴 파일은 폴더에 남고 오류 응답에는 그 파일의 이름이 실리지 않는다 [1][4].
파일 하나를 쓴 뒤 `OSError`를 내도록 한 시험에서 호출은 `OSError`로 끝났고 앞서 쓴 파일은 남았다 [10].
`Error dumping file`로 실린 캐시 객체도 덤프 폴더에 파일이 남을 수 있다 [7][11].
`dump_file_producer`는 실패하면 열어 둔 핸들러를 닫지 않고 `None`을 돌려준다 [7].
페이지 읽기가 중간에 실패한 경우와 읽은 바이트가 없는 경우 모두 함수가 `None`을 돌려준 뒤 덤프 폴더에 그 이름의 파일이 생겼고 크기는 4바이트와 0바이트였다 [11].
설정 파일 저장이 실패한 뒤 세션은 설정이 있는 것으로 처리해 다시 쓰지 않는다 [3].
같은 시험에서 두 번째 호출은 성공 응답을 돌려주었고 설정 파일은 끝까지 생기지 않았으며 이를 알리는 값은 없었다 [9].

### D05.03 알림 없이 계속

**구현.** 이 방식은 `windows_pedump`가 PE를 다시 짜 맞추지 못한 경우에 적용된다 [12].
Volatility 3 2.28.0의 `pedump`는 PE 재구성 중 `OSError`, `VolatilityException`, `OverflowError`, `ValueError`가 나면 `debug` 수준 로그만 남기고 `None`을 돌려준다 [12].
`None`을 받은 프로세스는 결과 행에 들어가지 않으므로 응답은 실패한 대상을 싣지 않은 성공 응답이다 [12].
재구성은 `with` 블록 안에서 하므로 실패해도 블록을 나갈 때 핸들러가 닫히고 서버의 `DumpFileHandler.close`가 그때까지 모은 바이트를 파일로 쓴다 [12][1].
재구성이 예외를 내도록 한 시험에서 `dump_pe`는 `None`을 돌려주었고 덤프 폴더에 0바이트 `PE.0x1.4.0x2.dmp`가 생겼다 [11].
MCP 서버 안에서 Volatility 3의 로그는 `FastMCP`가 붙인 `INFO` 수준 처리기로 표준 오류에 나가므로 `debug` 로그는 어디에도 남지 않는다 [13].
