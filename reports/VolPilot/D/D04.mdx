# D04 출력 경로 제한

### D04.01 서버가 출력 위치 결정

**구현.** 이 방식은 덤프 도구 `windows_dumpfiles`·`windows_pedump`가 쓰는 파일과 서버가 쓰는 설정 파일에 적용된다 [1][2].
덤프 파일의 폴더는 호출 인자가 아니라 서버를 시작할 때 환경변수 `VOL_DUMP_DIR`로 정한 값이다 [3].
`Session`은 만들어질 때 `make_file_handler`로 이 폴더를 `os.makedirs`로 만들고 그 폴더에 묶은 핸들러 클래스를 둔다 [4][1].
파일 이름은 Volatility 3 2.28.0의 `dumpfiles`·`pedump`가 객체 주소, 캐시 종류, 이미지 안 파일 이름, PID, 기준 주소로 짓는다 [5][6].
서버의 `DumpFileHandler`는 폴더와 그 이름을 `os.path.join`으로 이어 쓴다 [1].
`windows_dumpfiles`의 인자 `pid`·`filter`·`filter_ignore_case`·`virtaddr`·`physaddr`와 `windows_pedump`의 `base`·`pid`·`kernel_module`은 무엇을 꺼낼지만 정한다 [7][8].
`windows_pedump`의 `pid`와 `base`는 숫자로 바뀌어 이름에 들어간다 [6].
설정 파일 경로는 `VOL_IMAGE_PATH`의 이미지 경로 뒤에 `.vol3cfg.json`을 붙인 것이라 이미지와 같은 폴더에 생긴다 [2].
Windows에서는 덤프 파일을 쓸 때 절대 경로 앞에 `\\?\`를 붙여 경로 길이 제한 없이 연다 [9].
저장된 파생물을 고치거나 지우는 도구는 없다.

`VOL_DUMP_DIR`이 비어 있으면 덤프 도구는 플러그인을 실행하기 전에 오류로 끝난다 [10].
`VOL_DUMP_DIR` 없이 시작한 서버에 `windows_dumpfiles`와 `windows_pedump`를 부르자 두 응답 모두 `isError` 참과 `VOL_DUMP_DIR is not configured` 문장이었다 [11].
서버는 `VOL_DUMP_DIR` 값이 절대 경로인지 검사하지 않는다 [3][4].
README는 이 값에 절대 경로를 적으라고 적는다 [12].

### D04.04 이름·확장자·충돌 검사

**구현.** 이 방식은 서버 코드가 아니라 덤프 도구가 쓰는 Volatility 3 2.28.0의 파일 핸들러 기반 클래스에 적용된다 [13].
`FileHandlerInterface`의 `preferred_filename`은 이름에 `os.path.sep`이 있으면 `ValueError`로 거부한다 [13].
서버의 `DumpFileHandler`는 이 클래스를 이어받아 생성자에서 그 검사를 거친다 [1].
경로 구분자가 들어간 이름으로 핸들러를 만들자 `ValueError: FileHandler filenames cannot contain path separators`가 났다 [14].
`dumpfiles`는 이미지 안 파일 경로를 `ntpath.basename`으로 마지막 조각만 남겨 이름에 넣으므로 `\`와 `/`는 이 검사 전에 빠진다 [5].
확장자, `:`, Windows 예약 이름은 검사하지 않는다 [13][1].
같은 이름이 이미 있으면 거부하지 않고 번호를 붙인 새 이름으로 쓴다 [1].

**한계.** Windows에서 `:`나 예약 이름이 들어간 덤프 파일 이름을 `\\?\` 경로로 열 때의 동작은 실행으로 확인하지 않았다 [9].

def make_file_handler(output_dir: str):
    """Return a FileHandlerInterface subclass that writes into ``output_dir``.

    The directory is created on first use. Every handler instance buffers
    writes in an ``io.BytesIO`` and flushes to
    ``<output_dir>/<preferred_filename>`` in ``close()``. Collisions are
    resolved by inserting ``-N`` before the extension.
    """
    os.makedirs(output_dir, exist_ok=True)

    class DumpFileHandler(io.BytesIO, plugins.FileHandlerInterface):
        def __init__(self, filename: str):
            io.BytesIO.__init__(self)
            plugins.FileHandlerInterface.__init__(self, filename)

```python
def _long_path_safe(path: str) -> str:
    """Return a path Windows' file APIs will accept regardless of length.

    Windows' classic MAX_PATH (260-character) limit applies unless the
    path is absolute and prefixed with ``\\\\?\\``, which Windows treats
    as an escape into the unrestricted-length API and which is a no-op
    everywhere else. Forensic artifact names routinely exceed this once
    joined with an output directory -- e.g. a Windows Event Log channel
    name like ``Microsoft-Windows-Windows Firewall With Advanced
    Security%4Firewall.evtx`` combined with dumpfiles' own
    ``file.<offset>.<offset>.<type>.`` prefix -- so this is applied to
    every dump write rather than only ones measured as "too long".
    """
    if os.name != "nt":
        return path
    abs_path = os.path.abspath(path)
    if abs_path.startswith("\\\\?\\"):
        return abs_path
    if abs_path.startswith("\\\\"):
        return "\\\\?\\UNC\\" + abs_path.lstrip("\\")
    return "\\\\?\\" + abs_path
```

    def file_handler(self):
