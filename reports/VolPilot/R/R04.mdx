# R04 도구 결과 해석 주의

### R04.01 도구별 정적 주의

**구현.** 이 방식은 도구 설명에 적용된다 [1].
도구 96개의 설명은 모두 `Forensic context` 항목을 두고 그 아래에 결과를 읽는 방법을 적는다 [1].
교차 분석 도구와 일부 플러그인 도구의 설명은 이 항목에 결과가 곧바로 침해를 뜻하지 않는 경우를 적는다 [2][3][4][5][6][7].
`detect_process_anomalies`의 설명은 `singleton_violation`이 끝난 프로세스가 남은 것처럼 무해한 원인일 수 있다고 적는다 [2].
`detect_dll_injection`의 설명은 `unlinked_dll` 하나만 있으면 실행 중 모듈 해제 같은 무해한 원인일 수 있다고 적는다 [3].
`detect_hidden_processes`의 설명은 끝난 프로세스도 `psscan`에만 나타날 수 있다고 적는다 [4].
`windows_registry_hashdump`의 설명은 도메인에 가입한 컴퓨터에서 결과가 비거나 적은 것은 실패가 아니라고 적는다 [5].
`windows_suspended_threads`의 설명은 정상 코드도 스레드를 멈춘 상태로 만들었다가 다시 실행한다고 적는다 [6].
`windows_mutantscan`의 설명은 이름 없는 뮤텍스가 흔하고 대개 무해하다고 적는다 [7].
이 문구는 결과와 관계없이 설명에 고정되어 있고 도구 응답에는 해석 주의를 싣지 않는다 [8].

### R04.03 추가 확인 도구·증거 추천

**구현.** 이 방식은 도구 설명에 적용된다 [1].
교차 분석 도구의 설명은 결과를 확인할 다음 도구를 적는다 [2][3][4][9].
`detect_hidden_processes`와 `detect_process_anomalies`의 설명은 찾은 PID마다 `triage_process`를 부르라고 적는다 [4][2].
같은 두 설명은 끝난 프로세스인지 `ExitTime`으로 확인하라고 적는다 [4][2].
`detect_dll_injection`의 설명은 `triage_process`로 명령 줄, 핸들, 네트워크 연결을 더 보라고 적는다 [3].
`detect_service_tampering`의 설명은 숨은 서비스의 `Binary` 필드를 `windows_filescan`이나 `windows_dumpfiles`와 대조하라고 적는다 [9].
`windows_suspended_threads`의 설명은 `windows_malware_malfind`로 확인하라고 적는다 [6].
서버 지침은 처음에 `windows_info`, 다음에 `windows_pslist`와 교차 분석 도구, 보고서를 만들기 전에 `verify_image_integrity`를 부르는 호출 순서만 적는다 [10].
도구 응답에는 확인할 도구를 싣지 않는다 [8].

**한계.** `detect_hidden_processes`가 권하는 `triage_process`는 `pslist`에 PID가 있는지 먼저 보고 없으면 찾지 못했다는 응답만 돌려준다 [11].
`detect_hidden_processes`가 찾는 프로세스는 `psscan`에 있고 `pslist`에 없는 프로세스다 [12].
그래서 이 도구가 찾은 PID로 `triage_process`를 부르면 명령 줄, DLL, 핸들, 네트워크 연결을 받지 못한다 [11][12].

[6] `windows_suspended_threads`의 설명이다.

```python
    Forensic context:
    - Legitimate code routinely creates threads suspended then resumes them;
      this plugin surfaces only threads still suspended at acquisition time,
      which is unusual and correlates strongly with hollowing / evasion
    - Suspended threads whose StartFile or Win32StartFile is None (start
      address outside any mapped module) indicate code running from an
      injected memory region — pair with windows_malware_malfind to confirm
    - The process hollowing pattern pairs a suspended main thread with an
      overwritten image base; correlate this plugin with windows_pslist
      and windows_dlllist to see whether the process's backing image has
      been swapped
    - If the suspended thread's PID also appears in windows_malware_malfind or its
      Win32StartAddress points into a VAD with RWX protection, escalate —
      this is a classic hollowing signature
    - `WorkFoldersShell.dll` is filtered out by the plugin as a known false
      positive, so any result here is after de-noising
```

    """Run windows.pslist and return structured process list."""
