# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 외부 도구 출력이나 서버가 만든 결과를 사건 DB에 적재하는 도구와 그 적재 자료를 읽는 조회 도구가 이 방식을 쓴다.
적재 함수 `extract_and_index`는 적재 자료(`source`)마다 행을 만들고 `source_path`에 호출 인자로 받은 증거 경로를 적는다 [1].
적재 단위인 `window`마다 `source_id`가 있다 [2].
`search`와 공통 함수 `windowed_response`를 쓰는 조회 도구는 결과 항목에 `window`의 `source_id`와 적재 자료 이름을 싣는다 [3].
적재 도구의 응답 공통 함수 `tool_response`는 적재 자료 이름 `source`를 싣는다 [4].
`list_sources`는 적재 자료마다 `source_id`·이름·`source_path`를 돌려주므로 결과의 `source_id`로 증거 경로를 찾을 수 있다 [5].
적재하지 않고 증거 파일을 바로 읽는 `read_evidence_file`은 응답에 출처 값을 따로 싣지 않는다 [6].

**예외.** 서버는 같은 이름의 적재 자료가 있어도 새 행을 만든다 [7].
`get_raw_output`은 이름이나 접두어가 맞는 적재 자료를 모두 이어 붙여 `source_id` 없이 돌려준다 [8].
그래서 같은 도구를 여러 증거에 돌린 사건에서는 이 응답의 본문이 어느 증거에서 나왔는지 가를 수 없다 [8].
복합 도구는 결과 항목에서 `source_window`를 지운다 [9].
`find_lateral_movement_indicators`는 결과 항목의 `source`를 `evtx.security` 같은 상수로 적는다 [10].
EZ Tools 보안 로그를 읽었거나 요청한 자료가 없어 모든 적재 자료를 검색했을 때도 같은 이름을 붙인다 [11].
복합 분석·상관 분석·IOC 조회 결과를 적재한 자료의 `source_path`는 증거 경로가 아니라 `composite_analysis` 같은 고정 문자열이다 [12].

### R05.02 증거 내부 경로

**구현.** 디스크 이미지의 파일 목록을 적재하는 TSK 도구가 이 방식을 쓴다.
`run_fls`가 적재하는 파일 목록(`tsk.filelist`)은 `fls -r -p` 출력이고 서버는 줄마다 inode와 이미지 안 경로가 있는 형식으로 읽는다 [13].
`search`와 `get_raw_output`은 이 줄을 `raw_text`에 그대로 돌려준다 [3][8].
`run_evtx_parser`는 이미지에서 꺼낸 EVTX 파일의 이름을 이미지 안 경로의 `/`를 `_`로 바꿔 만든다 [14].
서버는 이미지 안 경로를 결과 항목의 필드로 따로 붙이지 않는다.

**예외.** `search`와 `windowed_response`는 `window`의 `raw_text`를 300자에서 자르고 `full_text_available`만 붙인다 [15].
`window` 하나에는 최대 4096자까지 여러 줄이 들어가므로 일치한 줄의 경로가 응답에서 빠질 수 있다 [16].

### R05.03 레코드 키·번호

**구현.** 디스크 이미지의 파일 목록과 inode로 파일을 읽는 도구가 이 방식을 쓴다.
`tsk.filelist`의 줄마다 경로 앞에 inode가 있다 [13].
`extract_file_by_inode`는 결과에 `inode` 필드를 싣고 텍스트 파일이면 적재 자료 이름을 `tsk.extracted.<inode>`로 붙인다 [17].
`window_id`는 사건 DB가 적재 단위에 매긴 번호이고 증거 안 레코드 키가 아니다 [2].

**예외.** 파일 목록을 `search`나 `windowed_response`로 받으면 `raw_text`가 300자에서 잘리므로 일치한 줄의 inode가 응답에서 빠질 수 있다 [15][16].

### R05.04 바이트·섹터·행 오프셋

**구현.** 파티션 표를 돌려주는 `list_partitions`가 이 방식을 쓴다 [18].
이 도구가 돌려주는 `tsk.partitions`는 `mmls` 출력이고 서버는 그 행에서 시작 섹터와 길이를 읽는다 [19].
`window`의 `line_start`·`line_end`는 적재한 출력 본문 안의 줄 번호라 증거 안 위치가 아니다 [20].
`run_strings`는 `strings`를 오프셋 옵션 없이 돌린다 [21].
다른 결과에는 서버가 증거 안 오프셋을 따로 붙이지 않는다.

**예외.** `list_partitions`도 `windowed_response`로 응답해 `raw_text`를 300자에서 자르므로 `mmls` 출력이 그보다 길면 뒤 행의 시작 섹터가 응답에서 빠진다 [15][18].

def truncate_raw_text(d: dict[str, Any], cap: int = _DEFAULT_TEXT_CAP) -> None:
    """Truncate ``raw_text`` in a window dict in-place if it exceeds *cap*."""
    raw = d.get("raw_text", "")

    The description is stripped and lower-cased so callers can match it
    against the filesystem indicator tuples directly.
    """
    return [
        (int(m.group(1)), int(m.group(2)), m.group(3).strip().lower())
        for m in MMLS_ROW_RE.finditer(mmls_text)
    ]
