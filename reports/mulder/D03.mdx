# D03 파생물 무결성 검증

### D03.01 기준값 자동 계산

**구현.** 도구 출력을 사건 DB에 넣는 `extract_and_index`는 출력 텍스트 전체의 BLAKE2b를 `sources.source_hash`에 넣는다 [1].
출력이 비면 해시 대신 `blake2b:empty`를 넣는다 [1].
`insert_windows`는 `window`를 넣을 때마다 그 `source`의 `window` 본문을 처음부터 이어 BLAKE2b를 다시 계산해 `sources.windows_hash`에 넣는다 [2].
`windows_hash`는 `window`의 본문만 덮고 `line_start`·`line_end`·`event_time` 열과 `sources` 행의 경로·이름은 덮지 않는다 [2][3].
`extract_optical_file`은 꺼낸 파일을 다 쓴 뒤 그 파일 전체를 읽어 SHA-256을 계산한다 [4].

두 DB 해시는 사건 DB의 `sources` 행에 남고 `list_sources`가 `source`마다 돌려준다 [5].
`extract_optical_file`의 응답에는 꺼낸 파일의 `sha256`과 `size_bytes`가 실린다 [4].
출력을 적재한 도구의 응답에는 줄 수와 `window` 수만 있고 해시는 없다 [6].

다른 파생물에는 해시가 없다.
`finalize_report`의 보고서, `run_plaso`의 저장 파일, `carve_sqlite_from_raw`의 SQLite 파일, `extract_archive`가 푼 파일은 해시하지 않는다 [7].
발견사항과 북마크 행에도 해시 열이 없다 [3].
호출 기록의 `output_hash`는 적재 요약 `dict`나 응답 결과의 해시이고 보관한 출력의 해시가 아니다 [8].

### D03.11 도구를 요청해 검증

**구현.** 이 방식은 인자 없이 부르는 MCP 도구 `verify_evidence_integrity`에 적용되고 대조 함수를 부르는 곳은 이 도구뿐이다 [9].
대조 함수는 사건 DB의 `window` 본문을 `source`마다 다시 해시해 `windows_hash`와 대조하고 같으면 `verified`, 다르면 `modified`로 적는다 [10].
기준값 `windows_hash`는 대조 대상인 `window`와 같은 사건 DB 파일의 `sources` 행에 있다 [2][3].
그래서 둘을 함께 고치면 대조로 드러나지 않는다.
`source_hash`는 다시 대조하지 않고 파일로 남는 파생물과 발견사항은 대조 대상이 아니다 [10].
응답에 `source`마다 기준값·계산값·`window` 수·상태를 싣고 전체 집계와 상태를 붙인 뒤 호출 기록에 남긴다 [9].
검색·원문 조회·보고서 작성은 대조를 거치지 않고 불일치가 있어도 다른 도구를 막지 않으므로 D03.09·D03.10에는 연결하지 않는다 [9].

**예외.** `windows_hash`가 빈 `source`는 대조하지 않고 `no_hash_recorded`로 세지만 전체 상태는 `modified`가 없으면 `all_verified`다 [10][9].
`windows_hash` 열이 생기기 전에 만든 사건 DB를 열면 열만 빈 값으로 더하므로 그때까지 넣은 `source`는 모두 이 대조에서 빠진다 [11].

    """Add the windows_hash column to sources if it doesn't exist."""
    try:

    except Exception as exc:
        if "duplicate column" not in str(exc).lower():
