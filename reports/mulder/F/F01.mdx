# F01 판단 지침

### F01.02 결론 서술 방식 안내

**구현.** 이 방식은 `submit_finding`과 `submit_narrative`의 도구 설명, 발견사항 응답의 시각 경고 문구에 있다 [1][2][3].
서버는 서버 지침(`instructions`)을 넘기지 않고 만들어지며 MCP 리소스와 프롬프트도 등록하지 않는다 [4].
`submit_finding`의 설명은 확신도를 출처 2개 이상으로 뒷받침된 `confirmed`와 `inference` 둘 가운데 하나로 적으라고 한다 [1].
같은 설명은 출력을 직접 검토한 호출만 근거로 인용하고 사건 시각은 도구 출력에서 그대로 옮기며 모르면 null로 두라고 적는다 [1].
시각이 없는 발견사항에 붙는 경고 문구는 배제한 가설을 기록하는 발견사항이면 제목 앞에 `[NEGATIVE]`를 붙이고 시각을 지어내지 말라고 적는다 [3].
`submit_narrative`의 설명은 보고서 서술을 배경·사건 시간선·주요 발견사항·영향 평가·권고·결론 절로 나누고 목록 대신 문단으로 쓰라고 적는다 [2].

같은 저장소의 `mulder investigate` 오케스트레이터는 분석 역할의 모델에게 주는 프롬프트에 확신도 규칙을 더 자세히 적는다 [5].
도구 하나의 탐지는 많아야 `inference`이고 "consistent with"나 "likely" 같은 표현을 쓴 발견사항은 `inference`로 두라는 규칙이 그 예다 [5].
이 프롬프트는 서버를 쓰는 클라이언트의 지시라서 이 서버의 구현으로 세지 않는다.

### F01.03 발견사항별 보완 안내

**구현.** 이 방식은 `submit_finding`·`update_finding`의 응답과 보고서 마감 조건의 결과 문구에 있다 [6][3][7][8].
`submit_finding`은 `confidence`가 `confirmed`인데 근거 호출이 2개 미만이면 출처 2개 이상을 권하고 `inference`가 맞는지 다시 보라는 `hint`를 응답에 붙인다 [6].
두 도구는 제목이 `[NEGATIVE]`로 시작하지 않고 등급이 `info`가 아닌 발견사항에 `event_time_start`가 없으면 `timestamp_warnings`에 경고를 싣는다 [3][7].
이 경고는 도구 출력에서 옮긴 시각을 `update_finding`으로 더하거나, 상태를 적은 발견사항이면 등급을 `info`로 두거나, 배제한 가설이면 `[NEGATIVE]`를 붙이라고 권한다 [3].
사건 시각이 자정 정각으로 끝나거나 ISO-8601이 아니어서 서버가 그 값을 비우면 그 사실도 같은 목록에 싣는다 [9].
보고서 마감 조건의 근거 인용 범위 결과는 조건을 통과했어도 인용한 증거 `source`의 비율이 25% 미만이면 인용하지 않은 `source`를 다시 보되 비율을 올리려고 발견사항을 만들지 말라는 문구를 단다 [10].
인용한 증거 `source`가 3개 미만이면 발견사항이 실제로 기대는 `source`를 인용하라는 문구를 단다 [10].
이 결과는 `check_finalize_readiness`가 돌려주는 마감 조건 목록에 실린다 [8].

**한계.** `update_finding`은 근거 수 `hint`를 붙이지 않는다 [7].
그래서 `update_finding`으로 확신도를 `confirmed`로 바꾸거나 근거 호출을 하나로 줄이면 이 안내가 붙지 않는다 [7].

```python
def _timestamp_gap(title: str, severity: str, event_time_start: str | None) -> str | None:
    """Return the timestamp_coverage gate's complaint for this finding, or None.

    Mirrors the gate's exemptions exactly so the model hears about a missing
    ``event_time_start`` when it submits the finding, not from the phase gate
    several sessions later. A warning rather than a rejection: submitting
    first and timestamping via ``update_finding`` is how existing runs work,
    and a hard reject would push a weaker model to fabricate a timestamp.
    """
    if event_time_start or title.startswith(_NEGATIVE_PREFIX):
        return None
    if severity in _TS_EXEMPT_SEVERITIES:
        return None
    return (
        "This finding has no event_time_start and will block finalize_report "
        "(timestamp_coverage gate). Either call update_finding with a precise "
        "ISO-8601 event_time_start copied from tool output, set severity to "
        "'info' if it describes a state rather than a timed event, or prefix "
        f"the title with '{_NEGATIVE_PREFIX}' if it records a hypothesis you "
        "ruled out. Do not fabricate a timestamp."
    )
```

```python
def _sanitize_event_time(ts: str | None) -> tuple[str | None, str | None]:
    """Validate an event timestamp and nullify day-precision placeholders.

    Returns ``(cleaned_value, warning_message)``.  If the timestamp ends
    in ``T00:00:00Z`` it is almost certainly a fabricated day-level
    placeholder and is replaced with ``None``.
    """
    if not ts:
        return None, None
    if _MIDNIGHT_RE.search(ts):
        return None, (
            f"Timestamp '{ts}' looks like a day-precision placeholder "
            f"(T00:00:00). Nullified; omit timestamps you don't have "
            f"precise values for."
        )
    try:
        datetime.fromisoformat(ts.replace("Z", "+00:00"))
    except ValueError:
        return None, f"Timestamp '{ts}' is not valid ISO-8601. Nullified."
    return ts, None
```
