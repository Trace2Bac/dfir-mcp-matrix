# F06 보고 산출물 구성

### F06.01 증거·환경 manifest 포함

**구현.** 이 방식은 `finalize_report`가 쓰는 마크다운·HTML 보고서에 있다 [1].
사용자가 CLI 명령 `mulder report`를 실행하면 서버 없이 사건 DB와 호출 기록을 읽어 같은 두 보고서를 다시 쓴다 [2].
보고서는 사건 DB의 `evidence_registry`를 읽어 증거 파일마다 SHA-256과 크기를 싣는다 [1][3].
증거 표의 파일 칸에는 전체 경로가 아니라 파일 이름만 나온다 [3].
보고서 머리에는 사건 ID, 생성 시각, 증거 루트가 실린다 [4].
분석 환경으로는 모델별 토큰 사용량만 싣고 이 값도 오케스트레이터가 남긴 `<case_id>.model_usage.json`이 있을 때만 나온다 [5].
외부 도구와 룰의 버전은 싣지 않는다 [6].
사건 메타데이터의 `extractor_versions`는 사건을 만들 때 빈 값으로 채워지고 저장소 안에서 그 값을 갱신하는 `update_extractor_versions`를 부르는 곳이 없다 [6].

**한계.** 두 보고서의 "Forensic Soundness and Evidence Integrity" 문단은 읽기 전용 MCP 서버, 읽기 전용 볼륨으로 붙인 원본 증거, 셸 없는 도구 호출, 호출 기록과 대조한 발견사항을 고정 문장으로 단언한다 [7].
렌더러가 받는 값에는 증거를 어떻게 붙였는지와 `verify_evidence_integrity` 결과가 없어 이 문장은 조사마다 같다 [8].
증거를 읽기 전용으로 붙이는지는 서버를 실행하는 환경이 정하고 서버는 그 사실을 확인하지 않는다 [8].
`evidence_registry`에 행이 하나라도 있으면 마크다운 요약은 "SHA-256 hashes recorded for all evidence"를, HTML 요약은 자물쇠 표시를 싣는다 [9].
해시를 계산하지 못한 증거 파일은 `evidence_registry`에 들어가지 않으므로 그런 파일이 있어도 모든 증거에 해시가 있다고 적힌다 [9][10].

### F06.02 수행·누락 범위 포함

**구현.** 이 방식은 같은 두 보고서에 있다 [11].
마크다운 보고서는 전체 호출 수, 많이 부른 도구 5개와 호출 수, 적재한 `source` 목록(추출기·줄 수), 호출 기록 파일 경로를 싣는다 [11].
HTML 보고서는 `run_parallel`을 뺀 호출 기록 항목 전체를 도구 이름·소요 시간·시각과 함께 싣는다 [12].
호출 기록 항목에는 성공·실패 상태가 없어 오류로 끝난 호출도 다른 호출과 같게 나온다 [13].
점검 도구 `audit_tool_coverage`·`audit_evidence_coverage`의 결과와 인용되지 않은 `source` 비율은 렌더러에 넘기지 않아 보고서에 없다 [14].
HTML 보고서의 `source` 목록은 이름·추출기·줄 수에 해시 앞 16자와 그 자료를 인용한 발견사항 수를 더해 싣는다 [15].
두 보고서의 `source` 목록에는 그 자료를 만든 증거 경로 `source_path`가 없다 [11][15].
두 보고서에는 호출이나 `source`를 증거 항목별로 묶은 절이 없다 [14].
HTML 보고서는 호출 항목마다 호출 기록의 인자 `params`를 함께 넣어 두고 항목을 고르면 보여 준다 [16].

### F06.03 발견사항과 근거 링크 포함

**구현.** 이 방식은 같은 두 보고서에 있다 [17].
발견사항마다 등급·확신도·사건 시각·`sources`·`evidence_refs`·ATT&CK ID가 실린다 [17].
마크다운 보고서의 연결은 근거 호출 ID와 호출 기록 파일 경로까지다 [11][17].
HTML 보고서는 `evidence_refs`의 ID마다 호출 기록 항목을 찾아 도구 이름·인자·`output_hash`를 잇고 "Evidence Chain"으로 싣는다 [18][19].
호출 기록에 없는 ID는 도구 이름이 `unknown`인 항목으로 남는다 [18].
HTML의 `sources` 표시는 "Evidence Browser"의 그 `source` 원문으로 이어진다 [19].
"Evidence Browser"는 `source`마다 앞 `window` 50개의 원문과 전체 수, 잘림 여부를 싣는다 [20].
HTML의 "Evidence strength" 막대는 근거 호출 수에 20%를 곱한 길이이고 근거의 내용과는 관계가 없다 [19].

### F06.05 내보내기

**구현.** `finalize_report`는 사건 DB 옆에 `<case_id>.report.md`와 `<case_id>.report.html`을 쓰고 두 경로를 응답에 싣는다 [21].
서버는 PDF를 만들지 않는다 [21].
HTML을 만들지 못하면 마크다운만 쓰고 응답에 `html_warning`을 싣는다 [21].
보고서 부록에는 렌더러가 발견사항 설명에서 IP·포트·경로·해시·전자우편 주소를 정규식으로 뽑아 만든 IOC 표가 실린다 [22][23].
`finalize_report`는 IOC 평판 조회 결과를 적재한 `enrichment.iocs`를 렌더러에 넘기고 렌더러는 IOC 표의 값마다 평판 요약을 붙인다 [24].
두 보고서에는 모델이 `submit_narrative`로 낸 보고서 서술이 "Investigation Report" 절로 실린다 [25].
렌더러는 그 서술을 sandbox 환경의 Jinja2 템플릿으로 읽어 `finding_count` 같은 템플릿 변수 자리에 보고서가 계산한 값을 넣는다 [26].
템플릿으로 읽지 못하면 받은 서술을 그대로 싣는다 [26].
`mulder report`는 같은 렌더러로 같은 이름의 두 파일을 사건 DB 폴더에 쓰므로 `finalize_report`가 쓴 보고서를 덮어쓴다 [2][27].
이 명령은 `finalize_report`가 보고서를 쓰기 전에 하는 batch 확인과 마감 조건 대조를 거치지 않는다 [28].
`mulder report`는 HTML을 만들지 못하면 표준 오류에 문구를 출력하고 마크다운만 쓴다 [27].
IOC와 ATT&CK 기법의 내보내기 파일은 사용자가 CLI 명령 `mulder export-iocs`·`mulder export-navigator`를 실행해야 만들어진다 [29].
두 명령은 사건 DB의 발견사항 전체를 읽고 기본으로 사건 DB 폴더에 파일을 쓴 뒤 그 경로를 출력한다 [29].
`mulder export-iocs`는 발견사항 설명에서 IP·포트·경로·해시·이메일을 뽑아 `<case_id>.iocs.csv`와 STIX 2.1 묶음 `<case_id>.iocs.stix.json`을 쓴다 [22].
`stix2` 라이브러리가 없으면 STIX 묶음을 라이브러리 검사 없이 사전 구조로 직접 만든다 [22].
`mulder export-navigator`는 발견사항의 ATT&CK ID마다 그 ID를 단 발견사항 중 가장 높은 등급으로 점수와 색을 정해 Navigator 층 `<case_id>.navigator.json`을 쓴다 [30].
ATT&CK ID가 하나도 없으면 층 파일을 만들지 않고 그렇다고 출력한다 [29].

**한계.** `mulder export-iocs`는 보고서의 IOC 부록과 달리 `[NEGATIVE]` 발견사항과 등급이 낮거나 오탐을 밝힌 발견사항을 빼지 않고 발견사항 전체에서 IOC를 뽑는다 [23][29][22].
STIX 묶음은 그렇게 뽑은 지표 모두에 `malicious-activity` 표지를 붙인다 [31].
그래서 배제한 가설이나 오탐으로 밝힌 발견사항에 적힌 IP·해시도 악성 지표로 내보낸다 [22][23][31].
`mulder export-navigator`도 `[NEGATIVE]` 발견사항의 ATT&CK ID를 빼지 않아 배제한 가설의 기법이 "Techniques observed" 층에 실린다 [30].
`mulder report`는 `enrichment.iocs`를 렌더러에 넘기지 않아 이 명령으로 다시 쓴 보고서의 IOC 표에는 평판 값이 빠진다 [27][24].

### F06.07 판단의 확정 상태 표시

**구현.** 이 방식은 `finalize_report`와 `mulder report`가 쓰는 마크다운·HTML 보고서에 있다 [21][2].
렌더러는 제목이 `[NEGATIVE]`로 시작하는 발견사항을 나머지 발견사항과 나누고 확신도별 수는 나머지 발견사항에서만 센다 [32].
마크다운 보고서는 `[NEGATIVE]` 발견사항을 "Hypotheses Ruled Out" 절에 따로 싣고 "explicitly tested and no supporting evidence was found" 문장을 붙인다 [33].
HTML 보고서도 같은 발견사항을 "Ruled Out (Negative Findings)" 카드에 같은 문장과 함께 싣는다 [34].
나머지 발견사항은 확신도 `confirmed`·`inference`를 마크다운 부록의 `Confidence` 칸과 HTML 발견사항 카드의 배지에 싣는다 [17][35].
마크다운 요약 표는 두 확신도별 발견사항 수와 배제한 가설 수를 싣는다 [36].
HTML 보고서는 확신도별 수를 요약 칸에 싣고 확신도로 발견사항을 고르는 버튼을 둔다 [35].
두 보고서는 `confirmed`와 `inference`를 나누는 기준을 적지 않는다 [17][35].

**한계.** 부재 주장 절의 문장은 서버가 그 주장이 어떤 자료를 확인했는지 대조하지 않은 채 붙는다 [33].
마크다운 보고서는 `inference` 발견사항도 "Appendix A: Verified Forensic Findings" 제목 아래 싣는다 [37][32].

```python
def _filter_ioc_eligible(findings: list[Finding]) -> list[Finding]:
    """Exclude findings that should not contribute IOCs to the appendix.

    Filters out findings at LOW/INFO severity and findings whose title or
    description explicitly documents a false positive, since their artifacts
    are not actionable indicators of compromise.

    Args:
        findings: All positive findings from the case.

    Returns:
        Subset of findings eligible for IOC extraction.
    """
    eligible: list[Finding] = []
    for f in findings:
        if f.severity in _IOC_EXCLUDED_SEVERITIES:
            continue
        if _FALSE_POSITIVE_RE.search(f.title) or _FALSE_POSITIVE_RE.search(f.description):
            continue
        eligible.append(f)
    return eligible
```
