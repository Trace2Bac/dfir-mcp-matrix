# F04 발견사항·결론 기록 관리

### F04.01 자유 노트

**구현.** `bookmark_window`는 `window_id` 하나에 자유 글 `note`와 선택 인자 `source_name`을 붙여 북마크로 남긴다 [1].
도구 설명은 발견사항으로 올리기 전의 단서를 표시하는 용도라고 적는다 [1].
북마크 행에는 서버가 작성 시각 `created_at`을 넣고 `window_id`는 외래 키로 `windows` 행을 가리킨다 [2].
`get_bookmarks`는 메모와 함께 그 `window` 본문 앞부분과 사건 시각을 돌려준다 [3].
`submit_narrative`는 판정 필드나 근거 참조 없이 조사 서술 한 편을 자유 글로 받아 남긴다 [4].
도구 설명은 이 서술을 결론 절이 있는 공식 사건 보고서로 쓰라고 적는다 [4].
같은 설명은 이 서술이 최종 산출물의 보고서 페이지가 된다고 적는다 [4].

### F04.02 발견사항 필드 구분 저장

**구현.** `submit_finding`은 제목·설명·심각도·확신도·근거 호출·근거 `source`·ATT&CK ID·사건 시각을 따로 받는다 [5].
배제한 가설은 따로 두지 않고 제목 앞에 `[NEGATIVE]`를 붙인 발견사항으로 남긴다 [6].
이 접두어가 붙은 발견사항은 보고서 마감 게이트의 개수와 사건 시각 요구에서 빠진다 [6].
가설의 상태나 지지·반박 근거를 따로 두는 필드는 없다 [7].

### F04.03 근거 증거·호출 참조

**구현.** 발견사항은 근거 호출 ID 목록 `evidence_refs`와 근거 `source` 이름 목록 `sources`를 필드로 가진다 [7].
`sources`는 `source` 행의 ID가 아니라 이름 목록이다 [7].

### F04.04 사건 시각과 작성 시각 분리

**구현.** 발견사항은 사건 시각 `event_time_start`·`event_time_end`와 작성 시각 `submitted_at`을 다른 필드로 가진다 [7].
`submitted_at`은 `submit_finding`이 UTC 현재 시각으로 넣고 `update_finding`은 이 필드를 받지 않는다 [8].
사건 시각은 모델이 넣는 선택 값이고 서버는 ISO-8601이 아니거나 자정 정각으로 끝나는 값을 비우고 경고를 돌려준다 [9].

### F04.05 수정·철회 이력

**구현.** `update_finding`은 DB의 발견사항 행을 그 자리에서 고치고 호출 기록에 바꾼 필드의 새 값과 시각을 남긴다 [10][11].
`delete_finding`은 행을 지우고 호출 기록에 `finding_id`만 남긴다 [12].
`deduplicate_findings`로 합치면 흡수한 발견사항의 제목·ID·심각도·확신도·설명은 남기는 발견사항의 설명에 글로 남고 합친 사실은 호출 기록의 흡수한 ID 대응으로 남는다 [13][14].
DB 행에는 수정 시각이나 이전 값 열이 없다 [15].

**한계.** `submit_finding`의 호출 기록에는 `description`과 사건 시각이 빠지므로 제출한 뒤 이 둘을 고치면 처음 값은 어디에도 남지 않는다 [16].
`delete_finding`으로 지운 발견사항의 내용은 호출 기록에도 남지 않는다 [12].
`update_finding`이 다시 읽는 단계에서 예외로 끝나면 DB만 바뀌고 호출 기록에는 그 수정이 남지 않는다 [10][11].
`submit_narrative`를 다시 부르면 앞 서술을 새 서술로 바꾸고 호출 기록에는 서술의 길이만 남으므로 앞 서술은 어디에도 남지 않는다 [4][17][18].
`deduplicate_findings`로 합치면 남기는 발견사항의 심각도·확신도·`sources`·`evidence_refs`·ATT&CK ID·사건 시각은 무리 전체를 합친 값으로 바뀐다 [19][13].
이 필드들의 발견사항별 앞 값은 DB에도 호출 기록에도 남지 않는다 [15][14].

### F04.06 파일·DB에 저장

**구현.** 발견사항은 사건마다 하나인 SQLite 파일 `<case_id>.db`의 `findings` 테이블에 쓴다 [15][20].
쓰기는 DB 쓰기 대기열을 거쳐 트랜잭션으로 끝난다 [20].
북마크도 같은 파일의 `bookmarks` 테이블에 남는다 [2].
`submit_narrative`로 받은 서술은 같은 파일의 `case_metadata` 테이블 `narrative` 열에 같은 쓰기 대기열로 쓴다 [18].
호출 기록 파일에는 제출마다 `finding_id`와 근거 호출을 담은 `finding` 항목이 따로 남는다 [21].

### F04.09 판정·분류 값 기준 대조

**구현.** `submit_finding`은 `Finding` 자료 모델을 만들며 `severity`가 다섯 값 가운데 하나인지, `confidence`가 `confirmed`·`inference` 가운데 하나인지 검사하고 어긋나면 `validation` 오류로 거부한다 [5][7].

**한계.** `update_finding`은 받은 값을 자료 모델 검사 없이 DB에 쓴 뒤 그 행을 다시 읽는다 [10].
`severity`에 정해진 값 밖의 문자열을 넘기면 DB에는 그 값이 저장되고 다시 읽는 단계의 자료 모델 검사에서 예외로 끝난다 [10][22].
그 뒤에는 같은 행을 읽는 `get_findings`와 `finalize_report`도 같은 검사에서 예외로 끝난다 [22].

### F04.10 근거·확신도 필드 필수 입력

**구현.** 이 방식은 발견사항을 받는 `submit_finding`에 적용된다 [23].
`submit_finding`의 입력 schema는 근거 호출 `evidence_refs`, 근거 `source` 목록 `sources`, 확신도 `confidence`를 기본값 없는 필수 인자로 둔다 [23].
`Finding` 자료 모델은 `evidence_refs`가 빈 목록이면 만들어지지 않으므로 `submit_finding`은 그 제출을 `validation` 오류로 거부한다 [7][5].
`confidence`는 `confirmed`·`inference` 가운데 하나여야 하므로 빈 문자열도 같은 검사에서 거부된다 [7][5].

**한계.** `sources`는 필수 인자이지만 자료 모델이 빈 목록을 받는다 [7].
`update_finding`에 빈 `evidence_refs` 목록을 넘기면 자료 모델 검사 없이 DB에 빈 목록이 저장되고 다시 읽는 단계에서 예외로 끝난다 [10][22].

### F04.13 저장한 발견사항 병합

**구현.** 이 방식은 모델이 부르는 `deduplicate_findings`에 적용된다 [24].
이 도구는 사건의 발견사항을 모두 읽어 두 발견사항마다 유사도 점수를 계산하고 무리로 묶는다 [25].
점수는 제목 낱말, ATT&CK ID, 설명 속 IOC, `evidence_refs`, `sources`의 Jaccard 계수와 사건 시각 범위가 겹치는지(1 또는 0)에 0.20·0.15·0.15·0.25·0.15·0.10을 곱해 더한 값이다 [26].
무리의 어느 한 발견사항과 점수가 `similarity_threshold` 이상인 발견사항을 그 무리에 넣는다 [27].
`similarity_threshold`의 기본값은 0.4이고 `dry_run`이 참이면 묶은 무리만 돌려주고 발견사항을 고치지 않는다 [24][13].
`dry_run`이 거짓이면 기준이 0.4보다 낮거나 합칠 발견사항 수가 전체 발견사항의 25%를 넘을 때 `invalid_params`로 거부한다 [24][28][25].
무리마다 설명이 가장 긴 발견사항을 남기고 무리의 `sources`·`evidence_refs`·ATT&CK ID를 합친다 [19].
심각도는 무리에서 가장 높은 값으로 바꾸고 확신도는 무리에 `confirmed`가 하나라도 있으면 `confirmed`로 바꾼다 [19].
사건 시각은 무리의 가장 이른 시작과 가장 늦은 끝으로 바뀐다 [19].
흡수한 발견사항의 제목·ID·심각도·확신도·설명은 남기는 발견사항의 설명 끝 `Merged findings` 아래에 붙고 흡수한 행은 지워진다 [19][13].
호출 기록에는 인자와 함께 남긴 발견사항과 흡수한 ID의 대응을 `absorbed`로 남긴다 [14].
응답에는 무리마다 남긴 발견사항의 ID, 흡수한 ID와 제목이 실리고 합친 수 `merged_count`와 남은 수 `kept_count`가 실린다 [29].

**한계.** 무리에 넣을 때 무리의 한 발견사항과만 점수를 비교하므로 같은 무리의 두 발견사항끼리 점수가 기준보다 낮아도 하나로 합친다 [27].

    }

```python
def _sanitize_event_time(ts: str | None) -> tuple[str | None, str | None]:
    """Validate an event timestamp and nullify day-precision placeholders.

    Returns ``(cleaned_value, warning_message)``.  If the timestamp ends
    in ``T00:00:00Z`` it is almost certainly a fabricated day-level
    placeholder and is replaced with ``None``.
    """
    if not ts:
        return None, None
    if _MIDNIGHT_RE.search(ts):
        return None, (
            f"Timestamp '{ts}' looks like a day-precision placeholder "
            f"(T00:00:00). Nullified; omit timestamps you don't have "
            f"precise values for."
        )
    try:
        datetime.fromisoformat(ts.replace("Z", "+00:00"))
    except ValueError:
        return None, f"Timestamp '{ts}' is not valid ISO-8601. Nullified."
    return ts, None
```
