# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 종료 코드를 보는 도구는 세 가지 조건 가운데 하나를 쓴다.
`run_chainsaw`와 `run_bulk_extractor`는 종료 코드가 0이 아니면 실패로 본다 [1][2].
Chainsaw 쪽 주석은 실패한 실행도 빈 출력 파일을 남기므로 종료 코드만이 실패를 알려 준다고 적는다 [1].
Volatility 도구의 별도 프로세스 실행은 종료 코드가 0이 아니거나 출력이 비면 실패로 본다 [2].
공통 실행 함수 `run_cli_tool`을 거치는 5개 도구(`strings`·`hashdeep`·`exiftool`·`ssdeep`·`pasco`)와 capa·YARA·Hayabusa·MVT 도구는 종료 코드가 0이 아니고 출력도 없을 때만 실패로 본다 [3][4].

다른 도구는 본 실행의 종료 코드를 보지 않는다.
`run_clamav`·`run_regripper`·`run_foremost`와 EZ Tools 공통 실행 함수가 그 예다 [5].
이 도구들은 출력이 비거나 결과 파일이 없을 때의 처리로만 실패를 가른다.

**한계.** 종료 코드가 0이 아니고 출력이 있으면 그 결과를 아무 표시 없이 성공으로 적재한다 [3][6].
Hayabusa 쪽 주석은 읽지 못한 EVTX가 있어도 나머지 탐지는 남기려고 이렇게 했다고 적는다 [6].
그런데 응답에는 종료 코드도 부분 결과라는 표시도 없다 [6].
tshark를 부르는 PCAP 도구는 출력이 있으면 종료 코드를 보지 않고 그 출력을 적재한다 [7].
`run_plaso`는 `log2timeline`이 0이 아닌 코드로 끝나도 저장 파일이 있으면 다음 단계로 간다 [8].

### T08.02 시간 제한·종료 신호 처리

**구현.** 외부 실행은 `subprocess.run`의 `timeout`으로 시간 제한을 건다 [9].
공통 실행 함수 `run_subprocess`는 `TimeoutExpired`가 나면 시간 초과 문구를 돌려준다 [9].
공통 기본값은 600초이고 파일 크기에 맞추는 계산은 4 GiB를 넘는 1 GiB마다 120초를 더하되 8시간을 넘지 않게 한다 [9].
Volatility 도구는 시간 초과 전에 나온 표준 출력이 두 줄을 넘으면 그 부분을 적재하고 상태를 `partial`로 둔다 [10].
`run_bulk_extractor`는 시간 초과 뒤에도 그때까지 쓴 특징 파일을 적재하고 결과에 `partial`과 경고를 붙인다 [11].
`run_zeek_analysis`는 시간 초과 뒤 남은 로그를 `zeek.partial`로 적재하고 결과에 `timed_out`을 붙인다 [12].
Volatility 라이브러리 경로는 플러그인마다 스레드 하나에서 실행하고 정한 시간이 지나면 시간 초과 오류로 정리한다 [13].

비동기 일괄 실행의 작업이 시간 초과로 끝나면 같은 배치의 다른 작업이 실행 중이거나 CPU 사용률이 70%를 넘을 때 그 작업을 `deferred`로 둔다 [14].
배치의 다른 작업이 모두 끝나면 미룬 작업을 하나씩 다시 실행하고 다시 실패하면 `failed`로 정한다 [14].
미룬 작업은 배경 작업 풀 밖에서 새로 만든 스레드 하나가 차례로 다시 실행하고 작업마다 자원 대기를 다시 거친다 [15].
CPU 사용률을 읽지 못하면 부하가 없다고 보므로 같은 배치에 실행 중인 다른 작업이 없으면 시간 초과 작업은 바로 `failed`가 된다 [16].
그래서 같은 작업의 최종 상태는 시간 초과 때의 부하와 같은 배치의 다른 작업 유무에 따라 달라진다 [14].
이 동작은 코드로만 확인했고 실행하지 않았다.

**한계.** `detect_masquerading`이 파일 앞부분을 읽으려고 실행하는 `icat`에는 시간 제한이 없다 [17].
`icat`이 정한 바이트를 내기 전에 멈추면 읽기가 끝나지 않는다 [17].
Volatility 라이브러리 경로는 시간 초과를 돌려준 뒤에도 플러그인 스레드를 멈추지 않는다 [13].
그 스레드가 늦게 끝나면 출력을 사건 DB에 적재한다 [18].
tshark를 부르는 PCAP 도구는 시간 초과가 나면 그때까지 나온 출력 끝에 `[TRUNCATED: … timed out]` 문구만 붙인다 [19].
이 글은 성공한 출력과 같은 경로로 적재된다 [7][19].

### T08.03 오류·출력 내용 판독

**구현.** Volatility 도구는 출력이 비면 `no_output`, 열 이름 한 줄뿐이면 `header_only`로 가른다 [20].
표준 오류에 `unsupported`·`not found` 같은 문구가 있으면 `plugin_unsupported`로 가른다 [20].
`run_capa`는 출력이 JSON이 아니거나 JSON 객체가 아니면 오류로 본다 [21].
EZ Tools 공통 실행 함수는 CSV 파일이 하나도 없으면 오류로 본다 [22].
오피스 매크로 분석은 `olevba` 출력이 JSON이 아니고 종료 코드도 0이 아니면 오류로 본다 [23].
Hayabusa 도구는 출력 파일을 미리 만들어 두므로 파일이 있는지가 아니라 내용이 있는지로 판단한다 [6].

**한계.** EZ Tools 공통 실행 함수는 종료 코드를 보지 않고 CSV 파일이 있는지만 본다 [22].
도구가 중간에 실패해 CSV 일부만 남겨도 그 CSV를 성공 결과로 적재한다 [22].

### T08.04 입력별 부분 완료 집계

**구현.** `run_volatility_batch`는 플러그인마다 상태를 두고 요청·성공·헤더만·실패 수를 센다 [24].
`run_registry_parser`는 하이브마다 적재 요약이나 실패 상태를 `per_hive`에 담는다 [25].
`start_extraction_batch`는 제출한 작업, 이미 적재돼 건너뛴 작업, 인자가 틀려 거부한 작업을 나눠 돌려준다 [26].
`run_parallel`은 작업마다 결과를 담지만 성공·실패 수를 따로 세지 않는다 [27].

**한계.** `run_volatility_batch`는 상태가 `error`·`empty`·`header_only`가 아니면 모두 성공으로 센다 [24].
그래서 시간 초과로 일부 출력만 적재한 `partial` 플러그인도 `plugins_succeeded`에 들어간다 [10][24].
`run_registry_parser`의 `hives_parsed`는 실패한 하이브까지 센 수다 [25].

### T08.05 비동기 최종 상태 조회

**구현.** `start_extraction_batch`가 맡긴 작업은 서버 프로세스 안 스레드에서 실행되고 작업마다 `pending`·`running`·`completed`·`failed`·`deferred` 상태를 둔다 [28].
`check_extraction_status`는 배치의 상태별 작업 수와 실행 중·실패·미룬 작업을 돌려주고 남은 작업이 없으면 `all_done`을 참으로 둔다 [29].
`wait_all`은 배치가 모두 끝날 때까지 기다리고 30분이 지나면 `timeout`과 끝나지 않은 배치를 돌려준다 [30].
작업이 끝나면 결과의 `status`·`error`·`error_message`로 완료와 실패를 정한다 [31].
작업 목록은 서버 프로세스 메모리에만 있어서 서버가 다시 시작하면 앞선 배치는 `Unknown batch` 오류로 답한다 [32].
어느 도구를 배경 작업으로 실행할지는 모델이 고른다 [33].
모델이 `start_extraction_batch`에 넘긴 작업만 배경 작업이 되고 같은 도구를 직접 부르면 일반 호출로 실행된다 [33].
배경 작업은 일반 호출의 공유 실행 제한을 나눠 쓰지 않고 `JobStore`의 별도 스레드 풀에서 실행된다 [34].

**한계.** 완료·실패 판정은 결과의 최상위 필드만 본다 [31].
사건 DB에 적재하는 도구의 응답은 `tool_response`가 최상위 `status`를 `success`로 두고 도구 결과는 `preview` 글에만 담는다 [35].
`run_volatility`는 플러그인 오류·시간 초과 결과도 이 경로로 돌려주므로 그 작업은 `completed`가 된다 [36].
`get_completed_results`가 작업마다 돌려주는 `status`는 작업 기록에 없는 키를 읽어 늘 `unknown`이다 [37].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** `run_volatility_batch`는 Volatility 3를 서버 프로세스 안에서 라이브러리로 부르고 플러그인마다 라이브러리가 낸 예외를 처리한다 [38].
예외가 나면 그 플러그인의 `status`를 `error`, `error_type`을 `exception`으로 정하고 다음 플러그인을 실행한다 [38].
`netscan`이 지원되지 않는다는 예외면 `connscan`·`sockscan`으로 다시 실행하고 그것도 실패하면 `error_type`을 `plugin_unsupported`로 정한다 [38].
`run_optical_listing`과 `extract_optical_file`은 서버 자체 코드로 광학 디스크의 UDF·ISO 9660 구조를 읽고 이 코드가 낸 `OpticalError`·`OSError`를 처리해 호출을 오류로 끝낸다 [39].
`run_pcap_analysis`는 분석 방식마다 예외를 처리해 그 방식의 `status`를 `error`로 정하고 다음 방식을 실행한다 [40].
이 방식 가운데 `beaconing`은 tshark가 낸 시각과 목적지를 서버 코드로 모아 접속 간격을 계산한다 [41].
`analyze_disk_pcaps`는 PCAP 파일마다 분석 중 난 예외를 처리해 그 파일을 사유와 함께 `pcaps_failed`에 넣고 다음 파일을 분석한다 [42].
`carve_sqlite_from_raw`는 이미지에서 SQLite 머리글을 찾아 잘라 내는 서버 코드가 `OSError`를 내면 `error_type`을 `io_error`로 정한 오류를 돌려준다 [43].
`query_sqlite_from_image`는 `sqlite3`가 질의 중 낸 예외를 처리해 호출을 오류로 끝낸다 [44].

**한계.** python-evtx로 EVTX를 읽는 `_parse_evtx_file`은 파일을 읽다 예외가 나면 서버 로그에 경고만 남기고 빈 글을 돌려준다 [45].
레코드 하나를 읽다 예외가 나면 debug 로그만 남기고 그 레코드를 건너뛴다 [45].
폴더를 파싱하는 경로는 빈 글이 나온 파일을 표시 없이 결과에서 뺀다 [46].
`index_evtx_file`은 파싱 실패와 `event_ids`에 맞는 이벤트가 없는 경우를 같은 `No events parsed` 오류로 돌려준다 [47].
UDF 파서는 파일 항목의 위치를 풀다 예외가 나면 그 항목을 크기 0, 빈 시각으로 목록에 넣고 실패 표시를 붙이지 않는다 [48].
그 항목이 폴더이면 그 아래 항목은 읽지 않는다 [48].
기록 세션 하나를 읽다 `OpticalError`가 나면 debug 로그만 남기고 그 세션을 목록에서 뺀다 [49].
`parse_browser_history`와 `parse_plist`는 `sqlite3`·`plistlib`가 낸 예외를 debug 로그로만 남기고 그 파일을 건너뛴다 [50].
모든 파일에서 예외가 나면 읽을 파일이 없을 때와 같은 `no_results`를 돌려준다 [50].

```python
def adaptive_timeout(
    file_path: str | Path,
    base: int = 600,
    per_gib: int = 120,
    cap: int = 28800,
) -> int:
    """Compute a timeout that scales with file size.

    For files under 4 GiB, returns the base timeout. For larger files,
    adds *per_gib* seconds for each GiB above 4, capped at *cap* seconds.
    Returns the base timeout if the file doesn't exist or can't be stat'd.

    Args:
        file_path: Path to the evidence file being processed.
        base: Minimum timeout in seconds (default 600 = 10 min).
        per_gib: Additional seconds per GiB above 4 GiB (default 120 = 2 min/GiB).
        cap: Maximum timeout in seconds (default 28800 = 8 hours).

    Returns:
        Timeout in seconds, between *base* and *cap*.
    """
    try:
        size_bytes = Path(file_path).stat().st_size
    except OSError:
        return base
    gib = size_bytes / (1024**3)
    return min(base + int(max(0, gib - _GIB_THRESHOLD) * per_gib), cap)
```
