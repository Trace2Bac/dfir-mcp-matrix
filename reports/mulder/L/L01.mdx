# L01 기록 방식

### L01.02 도구별 기록 호출

**구현.** 실행기를 쓰는 도구 5개를 뺀 mulder의 MCP 도구는 모두 도구 본문에서 기록을 불러 호출 기록을 남긴다.
호출 기록은 사건마다 하나인 `<case_id>.audit.jsonl` 파일이고 `AuditLog._append`가 항목마다 JSON 한 줄을 덧붙인다 [1].
모든 도구 호출이 지나는 등록 래퍼 `_concurrent_tool`과 동기 도구를 스레드로 넘기는 `_wrap_sync_tool`은 기록하지 않는다 [2].
그래서 기록을 남길지와 언제 남길지는 도구 본문이 정한다.

도구 본문이 부르는 기록 장치는 여럿이다.
응답을 만드는 `tool_response`와 `error_response`는 사건이 열려 있으면 응답을 만들기 전에 `log_tool_call`을 부른다 [3].
창 목록을 돌려주는 `windowed_response`도 같다 [4].
`audited_tool` 데코레이터는 도구 함수가 끝난 뒤 항목을 쓰고 도구 함수가 예외를 내면 항목을 쓴 뒤 예외를 다시 올린다 [5].
이 데코레이터를 붙인 도구는 `list_sources`·`get_source_stats`·`get_raw_output`·`bookmark_window`·`remove_bookmark` 5개다 [6].
나머지 여러 도구는 본문에서 `ctx.audit.log_tool_call`을 직접 부르고 복합 분석 도구는 `finalize_composite_result`로 기록한다 [7].
`submit_finding`은 자기 `tool_call` 항목과 따로 `log_finding_submission`으로 `finding` 항목을 쓴다 [8].
`run_parallel`은 하위 도구를 등록 표 `_tool_dispatch`에서 꺼내 직접 부르므로 하위 도구는 자기 본문에서 항목을 쓰고 `run_parallel`은 모두 끝난 뒤 자기 항목을 쓴다 [9].

**한계.** `get_tool_guide`는 어느 반환 경로에서도 기록을 부르지 않는다 [10].
`wait`도 기록을 부르지 않고 `job_id`를 받으면 끝난 백그라운드 작업의 결과 전체를 기록 없이 돌려준다 [11].

기록을 부르기 전에 응답을 돌려주는 `return` 문이 여러 도구에 있다 [12].
`finalize_report`의 게이트 거부, `list_directory`·`read_evidence_file`의 경로 정책 거부, `query_sqlite_from_image`의 SQL 인자 거부와 추출·질의 실패, `search`·`decode_payload`의 인자 오류가 그렇다 [12].
이 응답에는 `tool_call_id`가 붙지만 그 ID의 항목은 호출 기록에 없다 [12].

도구 본문이 기록을 부르기 전에 예외가 나면 대신 기록하는 공통 처리가 없다 [2].
`list_directory`에 `recursive` 없이 파일 경로를 주면 `iterdir()`가 예외를 내고 항목이 남지 않는다 [13].
`run_parallel`은 `tool` 키가 없는 작업이 섞이면 하위 작업을 모두 실행한 뒤 자기 항목의 인자를 만드는 줄에서 `KeyError`로 끝나 자기 항목을 남기지 않는다 [14][9].
`decode_payload`가 base64를 푼 글을 한 겹 더 풀려고 자기 이름을 다시 부르는 경로는 기록을 부르기 전에 예외로 끝나 항목을 남기지 않는다 [15].
백그라운드 작업에서 난 예외는 작업 상태와 서버 로그에만 남는다 [16].

응답 함수와 `list_cases`는 사건이 열려 있을 때만 기록한다 [3][17].
그래서 사건을 열기 전의 `list_cases` 호출과 `scan_evidence`가 사건을 만들기 전에 낸 오류 응답은 남지 않는다 [17].
`start_extraction_batch`·`check_extraction_status` 같은 작업 관리 도구는 사건이 없으면 기록을 건너뛰고 서버 로그에 경고만 남긴다 [18].

### L01.03 공통 실행 함수에서 기록

**구현.** `run_strings`·`run_hashdeep`·`run_exiftool`·`run_ssdeep`·`run_pasco` 5개는 명령 줄을 실행기 `run_cli_tool`에 넘긴다 [19].
`run_cli_tool`은 명령을 실행하고 출력을 적재한 뒤 `tool_response`로 항목을 쓴다 [20].
실행 파일이 없거나 대상 파일이 없거나 시간 초과·실패로 끝나도 `error_response`로 항목을 쓴다 [21][20].
다른 외부 명령 도구는 기록하지 않는 `run_subprocess`나 `subprocess.run`을 직접 부르고 자기 본문에서 기록한다 [22].

**한계.** 사건을 열기 전에 부르면 실행기가 끝에 부르는 응답 함수도 기록하지 않는다 [3].

### L01.04 클라이언트의 MCP 호출 기록

**구현.** 이 방식은 같은 저장소의 MCP 클라이언트인 `mulder investigate` 오케스트레이터로 조사할 때만 적용된다 [23].
오케스트레이터는 서버가 호출 기록을 쓰는 폴더에 자기 기록을 남긴다 [23].
오케스트레이터는 `--db-dir` 폴더를 `MULDER_DB_DIR`로 모델 세션에 넘기므로 세션이 실행하는 서버도 그 폴더에 호출 기록을 쓴다 [23].
오케스트레이터는 같은 폴더의 `orchestrator.log`에 자기 로거 출력을 덧붙여 쓴다 [23].
이 파일 이름에는 사건 ID가 없어서 같은 폴더에서 실행한 조사의 기록이 한 파일에 이어진다 [23].

`orchestrator.log`에는 서버를 거치지 않는 모델 호출과 모델의 글이 남는다 [24][25].
모델 세션을 시작할 때 모델 이름과 최대 차례 수를 쓰고 끝날 때 차례 수와 입력·출력 토큰 수를 쓴다 [24].
모델이 낸 글은 줄마다 한 줄씩 쓰되 JSON 객체 하나로 된 긴 글은 요약 한 줄로 바꿔 쓴다 [25][26].
앞뒤 공백을 뺀 글이 `{`로 시작해 `}`로 끝나고 100자를 넘는 글이 그 대상이다 [26].
요약은 JSON에 `tasks`가 있으면 작업 수와 앞 5개 작업의 도구 이름이고 `results`가 있으면 성공한 수와 실패한 수다 [26].
둘 다 없거나 JSON으로 읽지 못하면 `[JSON output]`만 쓴다 [26].
모델이 부른 도구는 `mcp__mulder__`를 뗀 이름만 쓰고 `submit_finding`이면 발견사항의 심각도와 제목을 쓴다 [27][25].
그 밖에 도구 인자와 결과는 이 파일에 남지 않는다 [27].
모델별 입력·출력 토큰 합계는 따로 `<case_id>.model_usage.json`에 쓴다 [28].

MCP를 거치지 않고 부른 도구 함수의 항목은 서버 기록에 남는다.

다른 MCP 클라이언트로 서버에 붙으면 이 기록은 남지 않는다.
MCP 도구 이름을 남기는 기록이 이 상세의 근거이며 함께 담기는 모델 대화와 토큰 합계는 근거가 아니다.

**한계.** 오케스트레이터가 `execute_utility`로 여는 보조 모델 세션은 MCP 도구 호출을 `orchestrator.log`에 쓰지 않는다 [29].
이 세션은 모델에게 `open_case`와 `wait_all`을 부르게 해 추출 배치가 끝나기를 기다린다 [30].
보조 세션의 토큰 수는 `<case_id>.model_usage.json`의 모델별 합계에 더해진다 [29][28].

    async def _run_one(idx: int, tool_name: str, arguments: dict[str, Any]) -> None:
        """Execute a single task and store its result at *idx*."""
        token = current_batch_id.set(batch_id)
        try:
            fn = _tool_dispatch.get(tool_name)
            if fn is None:
                results[idx] = {"error": f"Unknown tool: {tool_name}"}
                return
            arguments = fill_case_id(fn, arguments, open_case_id)
            problem = validate_tool_args(fn, arguments)
            if problem is not None:
                results[idx] = {"error": f"{tool_name}: {problem}"}
                return
            try:
                results[idx] = await fn(**arguments)
            except Exception as exc:
                logger.exception("run_parallel: %s failed", tool_name)
                results[idx] = {"error": f"{tool_name} failed: {exc}"}
        finally:
            current_batch_id.reset(token)

    except OSError as exc:
