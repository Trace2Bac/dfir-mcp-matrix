# L01 기록 방식

### L01.08 도구별 기록 호출

**구현.** 실행기를 쓰는 도구 5개(L01.09)를 뺀 mulder의 MCP 도구는 모두 도구 본문에서 기록을 불러 호출 기록을 남긴다.
호출 기록은 사건마다 하나인 `<case_id>.audit.jsonl` 파일이고 `AuditLog._append`가 항목마다 JSON 한 줄을 덧붙인다 [1].
모든 도구 호출이 지나는 등록 래퍼 `_concurrent_tool`과 동기 도구를 스레드로 넘기는 `_wrap_sync_tool`은 기록하지 않는다 [2].
그래서 기록을 남길지와 언제 남길지는 도구 본문이 정한다.

도구 본문이 부르는 기록 장치는 여럿이다.
응답을 만드는 `tool_response`와 `error_response`는 사건이 열려 있으면 응답을 만들기 전에 `log_tool_call`을 부른다 [3].
창 목록을 돌려주는 `windowed_response`도 같다 [4].
`audited_tool` 데코레이터는 도구 함수가 끝난 뒤 항목을 쓰고 도구 함수가 예외를 내면 항목을 쓴 뒤 예외를 다시 올린다 [5].
이 데코레이터를 붙인 도구는 `list_sources`·`get_source_stats`·`get_raw_output`·`bookmark_window`·`remove_bookmark` 5개다 [6].
나머지 여러 도구는 본문에서 `ctx.audit.log_tool_call`을 직접 부르고 복합 분석 도구는 `finalize_composite_result`로 기록한다 [7].
`submit_finding`은 자기 `tool_call` 항목과 따로 `log_finding_submission`으로 `finding` 항목을 쓴다 [8].
`run_parallel`은 하위 도구를 등록 표 `_tool_dispatch`에서 꺼내 직접 부르므로 하위 도구는 자기 본문에서 항목을 쓰고 `run_parallel`은 모두 끝난 뒤 자기 항목을 쓴다 [9].

서버 밖의 `mulder investigate` 오케스트레이터도 같은 파일에 항목을 남긴다 [10].
오케스트레이터는 자기 프로세스에서 사건을 열고 `_tool_dispatch_sync`로 `check_finalize_readiness` 같은 도구 함수를 MCP 없이 직접 부른다 [10].
그 도구 본문이 기록을 부르므로 이 호출도 같은 호출 기록 파일에 항목으로 남는다 [10].
항목에는 쓴 프로세스를 가르는 필드가 없다 [11].

**예외.** `get_tool_guide`는 어느 반환 경로에서도 기록을 부르지 않는다 [12].
`wait`도 기록을 부르지 않고 `job_id`를 받으면 끝난 백그라운드 작업의 결과 전체를 기록 없이 돌려준다 [13].

기록을 부르기 전에 응답을 돌려주는 반환 지점이 여러 도구에 있다 [14].
`finalize_report`의 게이트 거부, `list_directory`·`read_evidence_file`의 경로 정책 거부, `query_sqlite_from_image`의 SQL 인자 거부와 추출·질의 실패, `search`·`decode_payload`의 인자 오류가 그렇다 [14].
이 응답에는 `tool_call_id`가 붙지만 그 ID의 항목은 호출 기록에 없다 [14].

도구 본문이 기록을 부르기 전에 예외가 나면 대신 기록하는 공통 처리가 없다 [2].
`list_directory`에 `recursive` 없이 파일 경로를 주면 `iterdir()`가 예외를 내고 항목이 남지 않는다 [15].
`run_parallel`은 `tool` 키가 없는 작업이 섞이면 하위 작업을 모두 실행한 뒤 자기 항목의 인자를 만드는 줄에서 `KeyError`로 끝나 자기 항목을 남기지 않는다 [16][9].
백그라운드 작업에서 난 예외는 작업 상태와 서버 로그에만 남는다 [17].

응답 함수와 `list_cases`는 사건이 열려 있을 때만 기록한다 [3][18].
그래서 사건을 열기 전의 `list_cases` 호출과 `scan_evidence`가 사건을 만들기 전에 낸 오류 응답은 남지 않는다 [18].
`start_extraction_batch`·`check_extraction_status` 같은 작업 관리 도구는 사건이 없으면 기록을 건너뛰고 서버 로그에 경고만 남긴다 [19].

### L01.09 실행기 안 기록

**구현.** `run_strings`·`run_hashdeep`·`run_exiftool`·`run_ssdeep`·`run_pasco` 5개는 명령 줄을 실행기 `run_cli_tool`에 넘긴다 [20].
`run_cli_tool`은 명령을 실행하고 출력을 적재한 뒤 `tool_response`로 항목을 쓴다 [21].
실행 파일이 없거나 대상 파일이 없거나 시간 초과·실패로 끝나도 `error_response`로 항목을 쓴다 [22][21].
다른 외부 명령 도구는 기록하지 않는 `run_subprocess`나 `subprocess.run`을 직접 부르고 자기 본문에서 기록하므로 L01.08에 든다 [23].

**예외.** 사건을 열기 전에 부르면 실행기가 끝에 부르는 응답 함수도 기록하지 않는다 [3].

    async def _run_one(idx: int, tool_name: str, arguments: dict[str, Any]) -> None:
        """Execute a single task and store its result at *idx*."""
        token = current_batch_id.set(batch_id)
        try:
            fn = _tool_dispatch.get(tool_name)
            if fn is None:
                results[idx] = {"error": f"Unknown tool: {tool_name}"}
                return
            arguments = fill_case_id(fn, arguments, open_case_id)
            problem = validate_tool_args(fn, arguments)
            if problem is not None:
                results[idx] = {"error": f"{tool_name}: {problem}"}
                return
            try:
                results[idx] = await fn(**arguments)
            except Exception as exc:
                logger.exception("run_parallel: %s failed", tool_name)
                results[idx] = {"error": f"{tool_name} failed: {exc}"}
        finally:
            current_batch_id.reset(token)

```python
def run_subprocess(
    cmd: list[str],
    *,
    timeout: int = TOOL_TIMEOUT,
    text: bool = True,
) -> subprocess.CompletedProcess[str] | str:
    """Run a subprocess with standardized timeout handling.

    Returns the CompletedProcess on success, or an error message string
    on timeout/OS failure. Callers check ``isinstance(result, str)`` to
    detect failures.
    """
    try:
        return subprocess.run(cmd, capture_output=True, text=text, timeout=timeout, check=False)
    except subprocess.TimeoutExpired:
        return f"{cmd[0]} timed out after {timeout}s"
    except OSError as exc:
        return f"Failed to run {cmd[0]}: {exc}"
```
