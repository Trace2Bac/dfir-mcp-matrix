# P02 다음 작업 결정

### P02.01 고정 문서·프로필 반환

**구현.** `get_tool_guide`는 저장소의 `tool_guide.json`을 모듈을 읽을 때 한 번 읽어 두고 분류별 도구 안내를 그대로 돌려준다 [1].
안내 항목은 도구 이름, 설명, 입력, 관련 도구(`related`)로 되어 있고 분류 15개에 도구 103개가 들어 있다 [2].
docstring은 증거 유형에 맞춰 다음에 실행할 도구를 정할 때 부르라고 적는다 [1].
안내는 증거 유형이 아니라 도구 분류로 나뉘고 사건 상태와 관계없이 같은 내용이다 [1][2].

### P02.02 규칙·조사 상태로 추천

**구현.** 상태 조회 도구 `get_investigation_summary`는 사건 DB와 호출 기록을 보고 남은 일 목록 `remaining_work`를 만든다 [3].
시각이 없는 발견사항, 제출하지 않은 `narrative`, 아직 부르지 않은 점검 도구 2개가 항목이 된다 [3].
`check_finalize_readiness`는 마감 조건 가운데 통과하지 못한 것의 이름을 `action`에 넣어 먼저 고치라고 알린다 [4].
점검 도구 `audit_tool_coverage`는 증거 유형별로 정해 둔 도구 가운데 호출 기록에 없는 것을 `tools_not_run`에 싣고 실행하거나 건너뛴 이유를 적으라고 안내한다 [5].

`scan_evidence`는 압축 파일이 있으면 `extract_archive`를 쓰라고 하고 광학 매체로 판별한 이미지에는 `run_optical_listing`을 쓰라는 `note`를 붙인다 [6].
이미 있는 사건을 `scan_evidence`로 다시 열면 적재한 자료가 있는지에 따라 분석 도구를 바로 쓰라거나 추출 도구를 실행하라고 알린다 [7].
`start_extraction_batch`는 작업을 백그라운드로 넘긴 뒤 기다리지 말고 검색·상관 분석·발견사항 제출을 이어 하라고 알린다 [8].
복합 도구는 필요한 `source`가 적재되지 않았으면 그 이름과 먼저 실행할 도구 호출 문자열을 `suggestion`으로 묶어 `missing_sources`에 싣는다 [9].
예를 들어 `find_persistence_mechanisms`는 `registry.system`이 없으면 `run_registry_parser('<image_path>', hive='SYSTEM')`을 권한다 [9].
`scan_hidden_processes`·`scan_kernel_modules`는 대조할 두 Volatility 자료가 모두 없으면 `run_volatility_batch`로 두 플러그인을 먼저 실행하라는 `hint`를 돌려준다 [10].
`detect_timestomping`은 MFT 자료가 없으면 오류 응답의 `suggestion`에 먼저 실행할 도구 호출을 싣는다 [11].
이 권고들은 응답의 문구와 목록이고 서버가 다음 호출을 대신 고르지는 않는다.

`mulder investigate` 오케스트레이터는 단계마다 계획 역할의 모델에게 도구 실행 계획을 세우게 한다 [12].
오케스트레이터는 이 서버를 쓰는 MCP 클라이언트라서 P02.03에 연결하지 않는다.

**한계.** 적재한 `source`가 하나라도 있는 사건을 다시 열면 `scan_evidence`는 카탈로그 단계가 압축을 이미 풀었으니 다시 풀지 말라는 고정 문구를 돌려준다 [7].
서버는 압축을 실제로 풀었는지 보지 않는다 [7].
`audit_tool_coverage`의 권고는 확장자로 정한 유형을 따르므로 확장자가 `.raw`·`.001`인 디스크 이미지에는 메모리 분석 도구를 권한다 [5].
같은 유형에 정한 도구가 사건 안 어느 증거에서든 한 번 불렸으면 다른 증거 항목의 권고에서도 빠진다 [5].
`detect_timestomping`과 `find_file_staging`은 MFT 자료가 없으면 서버에 등록되지 않은 도구 `run_ez_tool`을 권한다 [11].
`assess_recovery`는 `ez.usnjrnl`이 없으면 `parse_usn_journal('<image_path>')`를 권한다 [13].
`parse_usn_journal`은 이미지 경로가 아니라 시각 범위를 받아 이미 적재한 자료를 읽는 조회 도구라서 이 권고대로는 `ez.usnjrnl`을 만들 수 없다 [13].

### P02.04 서버 코드에 고정한 분석 절차

**구현.** 이 방식은 응답을 `finalize_composite_result`로 만드는 복합 도구 11개에 적용된다 [14].
복합 도구는 조사 목적마다 코드에 정해 둔 하위 조회를 차례로 실행하고 그 결과를 한 목록으로 합친다 [15].
예를 들어 `find_persistence_mechanisms`는 인자 없이 레지스트리, 서비스, 이벤트 로그, 시작 폴더, EZ Tools 실행 흔적, 예약 작업, 시작 파일을 찾는 수집 함수 7개를 정해진 차례로 실행한다 [15].
`finalize_composite_result`는 하위 조회의 호출 ID를 복합 도구의 호출 기록 항목에 함께 남긴다 [16].
모델은 어느 복합 도구를 부를지만 고르고 그 안의 단계는 서버 코드가 정한다.

**한계.** 하위 조회가 쓰는 `_keyword_sub_query`는 요청한 `source`가 사건 DB에 없으면 모든 `source`를 검색한다 [17].
그 결과로 만든 항목에는 다른 `source`에서 찾았다는 표시가 없다 [18].
예를 들어 `find_persistence_mechanisms`의 서비스 설치 항목은 어느 `source`에서 찾았든 `source`에 요청한 이름 `evtx.system`을 적는다 [18].
모든 `source`를 검색했다는 사실은 하위 조회의 호출 기록 이름(`._search(all)`)에만 남는다 [17].

```python
def _check_missing_sources(
    required: list[tuple[str, str]],
) -> list[dict[str, str]]:
    """Return a list of missing sources with suggested extraction commands.

    *required* is a list of ``(source_name, suggested_command)`` pairs.
    Only returns entries for sources not yet indexed.  Uses prefix
    matching so ``volatility.netscan.host1`` satisfies ``volatility.netscan``.

    Network sources (netscan/connscan/sockscan) are treated as
    interchangeable; having any one satisfies the requirement.
    """
    missing = []
    for src, cmd in required:
        if src in _NETWORK_SOURCE_ALTERNATIVES:
            if not any(_source_exists(alt) for alt in _NETWORK_SOURCE_ALTERNATIVES):
                missing.append({"source": src, "suggestion": cmd})
        elif not _source_exists(src):
            missing.append({"source": src, "suggestion": cmd})
    return missing
```
