# P03 조사 진척 판단

### P03.01 기준 작업 목록 대조

**구현.** 점검 도구 `audit_tool_coverage`는 사건의 증거 루트를 분류기로 다시 분류하고 증거 유형마다 적용할 도구 목록 `_EVIDENCE_TOOL_MAP`을 찾는다 [1].
목록은 유형 9개에 도구를 정해 두는데 메모리 덤프에는 Volatility·YARA 도구를, 디스크 이미지에는 `run_fls`·`run_mmls`·`run_plaso` 등을 둔다 [2].
호출 기록에 남은 도구 이름 집합과 목록을 맞춰 증거 항목마다 `tools_run`과 `tools_not_run`을 싣고 빠진 도구 수 `total_gaps`를 센다 [1].
마감 조건은 이 도구를 불렀는지만 보고 `total_gaps`는 보지 않는다 [3].

**예외.** 대조는 사건 전체의 도구 이름으로 하고 호출 인자의 증거 경로는 보지 않아 한 증거에 실행한 도구가 같은 유형의 다른 증거에서도 `tools_run`에 든다 [1].
호출 기록 항목에는 성공·실패 상태가 없고 오류 응답도 같은 도구 이름으로 기록되므로 실패한 호출도 실행한 것으로 센다 [4].
목록에 없는 유형(`log_file`·`log_directory`·`browser_history`·`autoruns_csv`·`yara_rules`)의 증거 항목은 결과에서 빠진다 [1][2].
P01.01의 확장자 판별이 디스크 이미지를 메모리 덤프로 정하면 그 이미지는 메모리 도구 목록과 대조한다.

### P03.03 단계 상태·완료 조건 대조

**구현.** 서버에는 조사 단계 상태가 없고 보고서 마감 조건 5개가 완료 판단을 맡는다 [5].
조건은 부정이 아닌 발견사항 3개 이상, 그 발견사항 가운데 심각도가 `info`가 아닌 것의 시작 시각, `narrative` 제출, 점검 도구 2개(`audit_evidence_coverage`·`audit_tool_coverage`) 호출, 인용한 증거 `source` 3개 이상(증거 `source`가 그보다 적으면 그 수)이다 [5].
`check_finalize_readiness`와 `get_investigation_summary`는 같은 함수로 조건마다 통과 여부와 사유를 돌려준다 [6].
`finalize_report`는 조건을 보기 전에 job store의 batch가 모두 끝났는지 본다 [7].
조건을 채우지 못했을 때 보고서 작성을 막는 동작은 T03에서 본다.
조사 단계는 서버 밖의 오케스트레이터가 두고 서버만 실행해 쓰는 클라이언트에는 단계 판단이 없다.

**예외.** 점검 도구 조건은 호출 기록의 도구별 호출 횟수만 보고 점검 결과의 `total_gaps`나 인용되지 않은 `source` 수는 보지 않는다 [3].
batch 상태는 프로세스 메모리에만 있어 서버를 다시 시작하면 앞 프로세스에서 끝나지 않은 추출이 있어도 batch 조건을 통과한다 [8].
증거 `source`가 하나도 없으면 인용 조건은 통과로 처리한다 [9].

### P03.04 미조사 범위·생략 사유 보고

**구현.** 점검 도구 `audit_evidence_coverage`는 적재한 `source` 가운데 어느 발견사항도 인용하지 않은 것을 추출기별로 묶어 앞 3개 `window`의 본문 표본과 함께 돌려준다 [10].
인용 비율이 50% 아래이면 경고 문구를 붙인다 [10].
`audit_tool_coverage`의 `tools_not_run`은 증거 항목마다 실행하지 않은 도구를 알린다 [1].
추출 도구와 `start_extraction_batch`는 같은 증거에서 만든 `source`가 이미 있으면 작업을 건너뛰고 `reason`과 `existing_sources`를 싣는다 [11].
`start_extraction_batch`는 인자가 도구 서명과 맞지 않는 작업을 `tasks_rejected`에 오류와 함께 싣는다 [12].
모델이 도구를 건너뛴 사유는 점검 도구가 적으라고 안내만 하고 그 사유를 받는 곳은 P03.05의 `notes`뿐이다 [1][13].

**예외.** 건너뛰기 판단은 도구별 `source` 이름 앞부분과 증거 경로만 보므로 요청한 내용이 달라도 건너뛴다 [14].
`run_volatility_batch`는 같은 메모리 덤프에서 플러그인 하나라도 적재돼 있으면 요청한 다른 플러그인도 실행하지 않고 `run_registry_parser`·`run_chainsaw`도 다른 `hive`·`mode`를 요청해도 건너뛴다 [14].
`parse_autoruns`는 증거 경로를 보지 않아 다른 CSV에서 만든 `autoruns.` `source`가 있어도 건너뛴다 [15].
`run_volatility_batch`·`run_registry_parser`·`run_chainsaw`가 건너뛴 응답은 `status`가 `success`인 적재 응답 모양이라 생략 사실과 사유는 앞 500자 `preview` 안에만 들고 `hint`는 결과를 적재했다고 적는다 [16].
건너뛴 호출도 그 도구 이름으로 호출 기록에 남아 `audit_tool_coverage`가 실행한 것으로 센다 [16][4].

### P03.05 모델이 적은 진행 기록 보관

**구현.** `track_progress`는 시스템 이름, 마쳤다고 적은 도구, 다룬 조사 질문, 메모를 받아 사건 DB의 `progress` 표에 넣는다 [13].
응답은 지금까지의 진행 기록을 합친 시스템·질문·도구 목록과 `status: accepted`다 [13][17].
서버는 적은 도구가 호출 기록에 있는지 대조하지 않는다 [13].
이 표를 읽는 곳은 같은 도구의 응답뿐이고 점검 도구와 마감 조건은 이 표 대신 호출 기록을 본다 [17][1][5].
docstring은 진행 기록이 DB에 남아 문맥 압축 뒤에도 남는다고 적는다 [13].

    def get_progress_summary(self) -> ProgressSummary:
        """Return aggregated progress across all recorded entries.

        Collects unique systems analyzed, questions addressed, and tools
        used from all progress records.
        """
        records = self.get_all_progress()
        systems: set[str] = set()
        questions_covered: set[str] = set()
        all_tools: set[str] = set()
        for r in records:
            systems.add(r["system_name"])
            for q in r["questions_addressed"]:
                questions_covered.add(q)
            for t in r["tools_completed"]:
                all_tools.add(t)
        return ProgressSummary(
            systems_analyzed=sorted(systems),
            questions_covered=sorted(questions_covered),
            tools_used=sorted(all_tools),
            total_progress_records=len(records),
        )
