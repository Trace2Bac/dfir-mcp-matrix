# D06 결론 도출

### D06.01 규칙·키 기반 상관

**구현.** 이 방식은 `composite` 모듈의 복합 도구 11개, 탐지 도구 `detect_timestomping`·`detect_masquerading`·`detect_steganography`, 문서 분석 도구 `analyze_office_document`·`analyze_pdf`, `finalize_report`가 부르는 보고서 렌더러에 적용된다 [1][2][3][4][5][6].
복합 도구는 사건 DB에 적재된 `source`를 하위 조회로 다시 읽어 정한 규칙과 공유 키로 결과 항목을 만든다 [1].
`find_suspicious_processes`는 Volatility 플러그인 결과마다 PID 색인을 만들고 같은 PID의 흔적을 한 항목에 모은다 [7].
`reconstruct_execution_chains`는 `pstree`의 부모 PID로 자식 목록을 만들고 시스템 프로세스를 부모로 둔 비시스템 프로세스에서 사슬을 시작한다 [8].
사슬은 자식이 있거나 `malfind`·네트워크 연결·DLL 이상이 붙은 것만 남는다 [8].
`find_execution_evidence`는 prefetch·amcache·shimcache·jump list·LNK·`pstree`의 `window`를 실행 파일 이름으로 묶고 그 이름이 나온 자료 종류를 `sources`에 싣는다 [9].
`correlate_pcap_with_host`는 패킷 결과에서 뽑은 IP 집합과 `netscan` 줄의 IP가 겹치면 그 줄의 PID·프로세스 이름을 붙인 항목을 만든다 [10].
`find_lateral_movement_indicators`는 키워드 검색으로 가져온 `window`를 본문의 이벤트 ID·낱말로 로그온·실패 로그온·명시적 자격 증명·WinRM 지표로 나눈다 [11].
같은 도구는 `netscan`과 패킷 대화 목록을 측면 이동 포트 목록(445·3389·5985·5986·135)으로 거른다 [11].
보고서 렌더러는 같은 `evidence_refs`를 인용한 발견사항끼리 관련 발견사항으로 잇는다 [12].
`detect_timestomping`은 적재된 MFTECmd 결과 `ez.mft`의 행마다 $SI 생성 시각, $FN 생성 시각, $SI 수정 시각을 비교한다 [2].
$SI 생성 시각이 $FN 생성 시각보다 10초 넘게 이르거나 $SI 수정 시각보다 늦으면 그 파일을 timestomping 지표로 분류하고 맞은 규칙을 `reasons`에 적는다 [2].
Windows Update·servicing·installer 폴더처럼 정한 경로 아래의 파일은 비교에서 뺀다 [2].
지표 파일마다 경로·두 생성 시각·이유를 한 줄로 만들어 `forensic.timestomping` `source`로 사건 DB에 적재하고 응답에는 적재 요약과 지표 수 `result_count`를 싣는다 [13].
`detect_masquerading`은 `fls`로 나열한 일반 파일 가운데 확장자 표에 있는 파일의 앞부분을 `icat`으로 읽어 매직 바이트로 내용 종류를 정한다 [3].
그 종류가 확장자 표가 허용한 종류에 없으면 불일치로 분류하고 표에 없는 확장자나 알아보지 못한 내용은 불일치로 보지 않는다 [3].
표본은 `max_files`(기본 5000)개나 300초에 닿으면 멈추고 응답에 `truncated`를 붙인다 [3].
불일치 파일마다 경로·확장자·탐지한 종류·크기·삭제 여부·시각을 `tsk.masquerade` `source`로 적재하고 응답에는 불일치 25건까지와 파티션별 건수, 표본 수 `files_sampled`를 싣는다 [14].
`detect_steganography`는 JPEG에는 stegdetect를, PNG에는 zsteg를 실행하고 stegdetect 출력은 `negative`가 없을 때만, zsteg 출력은 비어 있지 않을 때 탐지 문구로 남긴다 [15].
서버 코드의 기본 검사는 JPEG·PNG 파일 끝 8192바이트에서 마지막 JPEG EOI 표지나 PNG `IEND` 청크를 찾고 그 뒤 데이터가 10바이트를 넘으면 덧붙은 데이터로 분류한다 [16].
덧붙은 데이터가 8192바이트보다 길면 원래 표지가 읽은 범위 밖이 되어 이 검사로 찾지 못할 수 있다 [16].
stegdetect는 JPEG 앞 200개, zsteg는 PNG 앞 100개, 기본 검사는 JPEG·PNG를 합친 앞 200개 파일만 보고 실행 오류·시간 초과·읽기 오류가 난 파일은 건너뛴다 [15][16].
HEIC·HEIF 파일은 `heif-convert`로 앞 100개를 JPEG로 바꿔 JPEG 목록에 더한다 [17].
탐지 문구가 하나라도 있으면 그 문구를 `steg.detection` `source`로 사건 DB에 적재한다 [18].

`analyze_office_document`는 olevba가 매크로마다 낸 자동 실행 여부와 의심 낱말의 존재 조합으로 `risk_level`을 정한다 [5].
VBA가 없으면 `clean`, 자동 실행과 함께 실행 낱말이나 내려받기 낱말이 있으면 `malicious`, 자동 실행만 있으면 `high`, 의심 낱말이 있으면 `medium`, VBA만 있으면 `low`다 [5].
이 판정은 가중치나 건수를 쓰지 않고 난독화 낱말(`Chr(`·`ChrW(`·`CallByName`)은 `reasons`와 `obfuscation_detected`에만 실린다 [5].
`analyze_pdf`는 pdfid가 센 구조 낱말과 pdf-parser로 꺼낸 JavaScript로 `risk_level`을 정한다 [6].
`/Launch`가 있거나 JavaScript 낱말·자동 실행 낱말·난독화된 JavaScript 객체가 함께 있으면 `malicious`, JavaScript나 자동 실행 낱말이 있으면 `medium`, 내장 파일 낱말만 있으면 `low`다 [6].
건수로 등급을 정하는 규칙은 D06.03에서 본다.

**예외.** `find_lateral_movement_indicators` 설명은 4624 Type 3·10 네트워크 로그온과 WinRM 이벤트 91·168·169를 찾는다고 적는다 [19].
코드는 `4624`나 `logon`이 든 `window`를 모두 `network_logon`으로 싣고 `type 3`·`type 10`이 없으면 `logon_type`만 `other`로 둔다 [11].
WinRM 지표는 `window` 본문 어디에든 `91`·`168`·`169`가 있으면 붙으므로 `192.168.`처럼 IP 주소에 `168`이 든 `window`도 WinRM 연결 지표가 된다 [11].
`detect_timestomping` 설명은 `ez.mft`의 파일 항목마다 $SI와 $FN 시각을 비교한다고 적는다 [20].
코드는 `window`마다 첫 줄을 CSV 머리글로 읽고 그 줄에 $SI·$FN 생성 시각 열 이름이 없으면 그 `window`를 건너뛴다 [21].
`run_mft_parser`는 MFTECmd CSV 전체를 `extract_and_index`로 줄을 자르지 않는 최대 4096자 `window`로 나눠 적재하므로 머리글 줄은 첫 `window`에만 있다 [22][23].
그래서 이 도구는 첫 `window`에 든 행만 비교하고 나머지 `window`의 행은 비교하지 않는다 [21][22].
지표가 없을 때의 문구와 `total_mft_windows_analyzed`는 가져온 `window` 전체의 수를 분석한 수로 적는다 [13].
`detect_masquerading`이 파일 앞부분을 읽는 함수는 `icat`을 실행하지 못하면 빈 값을 돌려주고 `icat`의 종료 코드는 보지 않는다 [24].
읽지 못한 파일은 알아보지 못한 내용으로 처리되어 불일치에 들지 않지만 `files_sampled`에는 표본으로 세어진다 [3].
`detect_steganography`는 `files_scanned`와 결과 없음 문구 "No steganographic content detected in N files"의 N에 모은 JPEG·PNG 파일 전체 수를 쓴다 [18].
그래서 이 수에는 상한 밖에서 검사하지 않은 파일과 오류가 나 건너뛴 파일이 들어간다 [15][16][18].
도구 설명은 HEIC·HEIF 파일을 JPEG로 바꿔 검사한다고 적지만 `heif-convert`가 없으면 그 파일을 알림 없이 뺀다 [4][17].
폴더를 받으면 POSIX 경로에서 대소문자를 가리는 `*.jpg`·`*.jpeg`·`*.png`·`*.heic`·`*.HEIC`·`*.heif` 패턴으로 파일을 모은다 [4].
그래서 `.JPG`·`.PNG`처럼 확장자가 대문자인 JPEG·PNG 파일은 검사하지 않는다 [4].
`analyze_office_document`는 실행 낱말이 있는지를 `write_to_filesystem` 필드에 싣는다 [5].
이 필드 이름은 파일 쓰기를 뜻하지만 값은 `Shell`·`Execute`·`PowerShell` 같은 명령 실행 낱말에서 나온다 [5].
`analyze_pdf`를 `extract_javascript=False`로 부르면 JavaScript를 꺼내지 않고 빈 목록으로 등급을 계산한다 [25].
그래서 JavaScript·자동 실행·난독화 조합의 `malicious` 규칙이 적용되지 않는다 [6][25].

### D06.02 시간·공간 근접성 연결

**구현.** 이 방식은 `find_lateral_movement_indicators`, `correlate_across_sources`, `deduplicate_findings`에 있다 [26].
`find_lateral_movement_indicators`는 로그온 지표와 측면 이동 포트 연결 지표의 `event_time` 차이가 30초 이하이면 `temporal_correlation` 항목을 만든다 [26].
이 항목에는 두 시각과 로그온 종류·포트·시각 차이만 실리고 호스트·주소·계정은 대조하지 않는다 [26].
`correlate_across_sources`는 모델이 준 시작·끝 시각 사이에 `event_time`이 든 `window`를 `source` 이름별로 묶는다 [27].
이 도구는 `source`마다 `window` 20개까지 돌려주고 넘으면 `truncated`를 붙인다 [27].
`deduplicate_findings`는 두 발견사항의 사건 시각 범위가 겹치는지를 유사도 점수의 한 항목으로 쓴다 [28].

**예외.** `find_lateral_movement_indicators` 설명은 이벤트를 30초 창으로 잇는다고 적지만 비교하는 시각은 `window`마다 하나다 [19].
`window`는 줄을 모은 최대 4096자 묶음이고 `event_time`은 그 안에서 처음 찾은 시각이다 [23].
이 시각은 초 단위까지만 읽고 시간대 표기를 버린다 [23].
그래서 한 `window`의 뒤쪽 이벤트 시각은 비교하지 않고 출력마다 시간대가 달라도 적힌 숫자를 그대로 비교한다 [23].
`correlate_pcap_with_host` 설명은 패킷 시각을 이벤트 로그·prefetch와 대조한다고 적지만 코드는 시각을 비교하지 않는다 [29].
`t_start`는 이벤트 로그 키워드 검색어에 문자열로 들어가고 `t_end`는 함께 주어졌는지만 본다 [29].
이 도구는 prefetch를 조회하지 않는다 [29].

### D06.03 통계·점수 산정

**구현.** 이 방식은 `find_suspicious_processes`, `triage_binary`, `analyze_pdf`, `enrich_iocs`, `deduplicate_findings`, `find_execution_evidence`에 적용된다 [30][6].
`find_suspicious_processes`는 의심 이유마다 정한 가중치를 더해 `anomaly_score`를 싣고 점수순으로 정렬하도록 짜여 있다 [30].
가중치 표는 코드 주입 10, 숨은 프로세스 9, 의심 네트워크 8 같은 값을 두고 표에 없는 이유는 3으로 센다 [30].
`triage_binary`는 패킹 지표 하나에 2, 고위험 범주 API 하나에 3, 그 밖의 의심 API 하나에 1, 불가능한 컴파일 시각에 5, 의심스러운 시각에 2, RWX 섹션에 4를 더한다 [31].
합이 10 이상이면 `malicious_indicators`, 4 이상이면 `suspicious_indicators`로 분류하고 분석 단계가 실패했으면 `benign_indicators`를 `inconclusive`로 바꾼다 [31].
`analyze_pdf`는 `malicious` 규칙에 들지 않은 문서에서 위험도가 `high`인 pdfid 낱말(`/JS`·`/JavaScript`·`/OpenAction`·`/AA`·`/Launch`)이 두 종류 이상 나오거나 JBIG2 낱말이 있으면 `high`로 둔다 [6][32].
JavaScript 객체의 난독화 여부는 escape 수, `eval`과 `unescape`·`fromCharCode`의 조합, `+` 수, 짧은 변수 선언 수로 만든 지표 5개 가운데 2개 이상이 맞는지로 정한다 [33].
`enrich_iocs`는 외부 조회 서비스가 준 `reputation_score`의 평균을 0~100으로 잘라 `aggregate_score`로 싣고 서비스별 결과는 같은 항목의 `sources`에 남긴다 [34].
`deduplicate_findings`는 제목 낱말·ATT&CK ID·설명 속 IOC·`evidence_refs`·`sources`의 Jaccard 계수와 시각 겹침에 0.20·0.15·0.15·0.25·0.15·0.10을 곱해 더한다 [35].
유사도가 기준값(기본 0.4) 이상인 발견사항은 한 무리가 되고 설명이 가장 긴 것 하나에 나머지가 합쳐진다 [36].
합친 발견사항은 무리 안에서 가장 높은 `severity`를 받고 하나라도 `confirmed`이면 `confirmed`가 된다 [36].
실제로 합치는 호출은 기준값이 0.4 미만이거나 사건 발견사항의 25%를 넘게 흡수하면 거부된다 [37].
`find_execution_evidence`는 실행 파일마다 그 이름이 나온 자료 종류의 수로 결과를 정렬한다 [38].

**예외.** `find_suspicious_processes`의 점수 함수는 항목의 `reasons`를 읽지만 이 도구가 만드는 항목은 이유를 `suspicion_reasons`에 담는다 [39].
그래서 모든 항목의 `anomaly_score`가 0이 되고 정렬은 PID 차례를 바꾸지 않는다 [39].
가중치 표의 이유 이름 4개(`suspicious_network`·`suspicious_cmdline`·`unusual_parent`·`suspicious_dll_path`)도 이 도구가 붙이는 이름(`external_network_connection`·`encoded_powershell`·`suspicious_parent`·`unusual_dll_path`)과 다르다 [39].

### D06.05 사용 근거·변환 기록

**구현.** 이 방식은 복합 도구 11개가 함께 쓰는 마무리 함수 `finalize_composite_result`와 `correlate_across_sources`, `deduplicate_findings`, 점수 도구의 응답에 있다 [40].
복합 도구의 하위 조회는 저마다 `tool_call_id`를 받아 호출 기록에 조회한 `source`·검색어·일치한 `source` 목록을 남긴다 [41].
하위 조회 항목의 `output_hash`는 가져온 `window` 수만 해시한 값이다 [41].
복합 호출의 항목은 하위 조회 ID를 `sub_calls`로 모으고 결과 전체의 해시를 남긴다 [40].
응답에는 조회한 `source` 이름 목록과 아직 적재되지 않은 필요 `source`(`missing_sources`)가 실린다 [42].
결과는 `composite.*` 이름의 `source`로 사건 DB에 다시 적재되고 `source_path`는 `composite_analysis`로 고정된다 [40].
응답과 다시 적재하는 결과에서는 각 항목이 가리키던 `window`(`source_window`·`source_windows`)를 지운다 [43].
그래서 어느 하위 조회가 결과를 만들었는지는 되짚을 수 있지만 어느 `window`가 그 항목이 됐는지는 남지 않는다 [43].

`correlate_across_sources`는 하위 조회 없이 시간 범위와 `source` 인자를 호출 기록에 남기고 결과를 `composite.correlation`으로 적재한다 [44].
`deduplicate_findings`는 실제로 합칠 때 대표 발견사항과 흡수한 ID의 대응을 호출 기록 인자 `absorbed`에 남긴다 [45].
흡수한 발견사항의 제목·ID·등급·본문은 대표 발견사항 설명 끝에 붙는다 [45].
`triage_binary`와 `analyze_office_document`는 점수를 올린 이유를 `reasons`에 함께 싣는다 [31][5].
`analyze_pdf`는 JavaScript·자동 실행·`/Launch`·내장 파일 낱말과 난독화된 객체 수를 `reasons`에, JBIG2 낱말을 `exploit_indicators`에 싣는다 [6].
high 낱말이 두 종류 이상이라 `high`가 된 경우 그 건수 규칙은 `reasons`에 남지 않는다 [6].
보고서 렌더러가 계산하는 관련 발견사항·킬체인 단계·tactic 묶음은 결과만 보고서에 싣고 쓴 규칙은 보고서나 호출 기록에 남기지 않는다 [46].

**예외.** 측면 이동 도구는 로그온 지표의 `source`를 `evtx.security`로, WinRM 지표의 `source`를 `evtx.system`으로 고정해 싣는다 [47].

대응 자료 파일이 없으면 tactic으로 묶지 않고 기법 목록만 싣는다 [53].
보고서가 싣는 단계와 시간선은 모델이 적은 제목·시각에 따라 정해지고 서버는 그 값을 증거와 대조하지 않는다 [48].

def _build_related_findings(
    findings: Sequence[Finding],
) -> dict[str, list[str]]:
    """Map each finding_id to IDs of findings sharing evidence refs."""
    ref_to_fids: dict[str, set[str]] = defaultdict(set)

        for ref in f.evidence_refs:

def _aggregate_score(results: list[EnrichmentResult]) -> int:
    """Compute 0-100 aggregate threat score from multi-source results.

    Args:
        results: List of enrichment results from various sources.

    Returns:
        Aggregate threat score between 0 and 100.
    """
    if not results:
        return 0
    scores = [r.reputation_score for r in results if r.reputation_score is not None]
    if not scores:
        return 0
    return min(100, max(0, round(sum(scores) / len(scores))))
