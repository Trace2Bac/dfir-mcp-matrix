# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 응답을 만드는 공통 함수가 상한을 건다.
`windowed_response`는 `window`를 20개까지 싣고 `raw_text`를 300자에서 자른다 [1].
`tool_response`는 사건 DB에 적재한 도구의 결과 `dict`를 JSON으로 바꿔 앞 500자만 싣는다 [2].
조회 도구는 인자 기본값으로 건수를 묶는다.
`search`는 50건, `get_raw_output`은 `window` 50개, `get_timeline`은 50건이 기본값이다 [3].
`read_evidence_file`은 기본으로 1 MiB까지 읽는다 [4].
`correlate_across_sources`는 source마다 `window` 20개와 본문 200자까지 싣는다 [5].
`lookup_attack_technique`는 기본으로 기법을 `max_results` 5개까지 싣는다 [6].

여러 도구를 한 번에 부르는 `run_parallel`은 하위 도구의 결과를 응답에 실을 때 한 번 더 줄인다 [7].
최상위 `raw_text`는 500자, 목록인 `results`는 5개까지 남긴다 [7].
`results`가 `dict`이면 그 안에 바로 든 문자열 값을 500자로 자른다 [7].
이 축약은 얕아서 다른 최상위 키와 중첩된 값은 줄이지 않는다 [7].

도구 안에서 결과의 목록을 따로 자르는 곳도 있다.
`triage_binary`의 관심 문자열은 100개, `run_suricata`의 경보는 200개, `run_zeek_analysis`의 DNS 질의·HTTP 요청 같은 목록은 50개에서 끊긴다 [8].
`parse_plist`는 일치한 plist 파일 가운데 앞 50개만 처리하고 `parse_browser_history`는 브라우저 DB마다 500행만 조회한다 [9].
`detect_masquerading`은 결과 `dict`의 `hits`에 불일치를 25건까지 넣는다 [10].
이 `dict`도 `tool_response`의 500자 `preview`로 응답에 실리므로 `hits`는 500자 안에 들어가는 만큼만 응답에 남는다 [10][2].

**한계.** `search`의 `max_results`, `get_raw_output`과 `get_timeline`의 `limit`, `read_evidence_file`의 `max_bytes`에는 최댓값이 없어 모델이 호출 인자로 올린다 [3][4].
`lookup_attack_technique`의 `max_results`에도 최댓값이 없다 [6].
`read_evidence_file`은 `max_bytes`를 그대로 `read()`에 넘기므로 음수를 주면 파일 전체를 읽는다 [4].
`list_processes_from_memory`·`parse_prefetch`·`get_amcache`의 설명은 결과를 줄이지 않고 전부 돌려준다고 적지만 이 도구들도 `windowed_response`의 20개 상한을 거친다 [11].

### R02.02 전체·반환 건수 표시

**구현.** `windowed_response`는 반환한 `window` 수 `result_count`와 전체 수 `total_windows`를 함께 싣는다 [1].
상한을 넘으면 `truncated`와 몇 개 중 몇 개를 보였는지 적은 `hint`를 붙인다 [1].
`search`는 전체 일치 수 `total_matches`, 반환 수 `returned`, 남은 수 `remaining`과 `has_more`를 싣는다 [12].
`get_raw_output`은 `total_windows`·`returned_windows`·`has_more`를, `get_timeline`은 `total_events`·`has_more`를 싣는다 [13].
`read_evidence_file`은 파일 크기 `file_size`와 `truncated`를 싣는다 [4].
`correlate_across_sources`는 source마다 `total_windows`와 `truncated`를 싣는다 [5].
결과 `dict` 안의 목록을 자르는 `triage_binary`·`run_zeek_analysis`·`parse_plist`는 잘랐다는 표시도 전체 수도 싣지 않는다 [8][9].
`detect_masquerading`은 `hits`를 자르기 전의 불일치 수를 `mismatches`에 싣는다 [10].
EZ Tools 결과를 요약하는 도구 7개는 `window` 앞 10개를 200자로 자른 표본과 전체 `window` 수 `total_windows`, 표본 수 `sample_count`를 싣는다 [14].

**한계.** `get_raw_output`의 `has_more`는 이번 쪽의 `window` 수가 `limit`와 같은지로 정한다 [13].
그래서 남은 `window`가 정확히 `limit`개인 마지막 쪽에서도 `has_more`가 참이다 [13].
`read_evidence_file`에 음수 `max_bytes`를 주면 파일 전체를 읽고도 `truncated`가 참으로 나간다 [4].
`run_parallel`은 목록을 5개로 줄이면 줄이기 전 목록의 길이를 `results_total`에 싣는다 [7].
하위 도구가 이미 자른 목록이면 이 값은 전체 수가 아니며 `windowed_response`의 결과에서는 많아야 20이다 [7][1].
하위 결과에 들어 있는 `result_count`·`returned`·`remaining`·`returned_windows`는 줄이기 전 값이 그대로 남아 실제로 실린 항목 수와 맞지 않는다 [7][1][12][13].
EZ Tools 요약 도구의 `hint`는 표본 수와 전체 수를 "Showing N of M entries" 꼴로 적지만 M은 항목 수가 아니라 `window` 수다 [14].

### R02.03 페이지·커서 조회

**구현.** `get_raw_output`은 `after_id`를 커서로 받아 그 뒤의 `window`를 `limit`개 돌려주고 다음 커서 `next_after_id`를 싣는다 [13].
DB는 `window_id`가 `after_id`보다 큰 행을 `window_id` 순으로 읽는다 [15].
`windowed_response`의 `hint`는 전체를 보려면 `get_raw_output`을 부르라고 적는다 [1].
`search`와 `get_timeline`에는 다음 쪽을 읽는 인자가 없고 `hint`는 `max_results`나 `limit`를 늘리거나 범위를 좁히라고 적는다 [12][13].
`search`의 `hint`는 `get_raw_output(source_name, offset, limit)`라고 적지만 `get_raw_output`에는 `offset` 인자가 없다 [12][13].

**한계.** `run_parallel`로 `get_raw_output`을 부르면 응답에서 `raw_text`를 500자로 자르지만 `next_after_id`와 `returned_windows`는 자르기 전 값으로 남는다 [7][13].
그래서 그 커서로 이어 읽으면 잘려 나간 `window`를 건너뛴다 [7][13].
`raw_text_truncated` 표시는 붙지만 커서가 실제로 전달된 위치와 어긋났다는 안내는 없다 [7].
같은 `after_id`로 `get_raw_output`을 따로 부르면 그 부분을 다시 읽을 수 있다 [13].

### R02.04 파일·리소스로 전체 결과 조회

**구현.** 추출 도구는 외부 도구 출력을 사건 DB에 적재하고 응답의 `hint`에 그 source 이름과 `get_raw_output`을 적는다 [2].
`get_raw_output`을 커서로 이어 부르면 그 source의 `window`를 끝까지 읽는다 [13][15].

**한계.** 출력의 일부만 적재하고도 같은 안내를 붙이는 도구가 있다.
`run_zeek_analysis`는 Zeek 로그 파일마다 앞 50,000자만 적재한다 [16].
`run_bulk_extractor`는 256 MiB를 넘는 특징 파일의 앞부분만 읽고 서버 로그에만 경고를 남긴다 [17].
`run_suricata`는 경보 목록을 적재하지 않고 경보 수와 상위 서명 10개를 적은 글만 적재한다 [18].
`run_volatility`는 플러그인이 실패하거나 머리글만 낸 결과에도 `source_name`을 넣어 응답 `hint`가 전체 출력을 적재했다고 적는다 [19].
그 호출은 아무것도 적재하지 않는다 [19].
`run_hayabusa`는 Hayabusa CSV가 비면, `run_plaso`는 시간선과 통계가 모두 비면, `run_mft_parser`는 파일 시스템이 NTFS가 아니어서 건너뛰면 아무것도 적재하지 않는다 [20].
세 경우 모두 `source`를 준 `tool_response`로 응답하므로 `hint`는 전체 출력을 적재했다고 적는다 [20][2].

### R02.06 값 단위 잘림

**구현.** `window`를 싣는 응답은 `raw_text`를 300자에서 자르고 끝에 `...`와 `full_text_available`을 붙인다 [1].
`get_timeline`은 `raw_text`를 500자에서 자르고 `...`만 붙인다 [21].
`tool_response`의 `preview`는 500자에서 잘리면 끝에 `...`가 붙는다 [2].
`triage_binary`의 판정 `triage_verdict`는 결과 `dict`의 끝쪽 키라서 앞 키들이 500자를 채우면 응답 `preview`에 실리지 않는다 [22].
코드 주석도 미리보기에는 판정이 닿지 않아 적재 본문의 맨 앞에 둔다고 적는다 [22].
이때 모델은 `search`나 `get_raw_output`으로 적재 본문을 읽어야 판정을 본다 [22].
복합 도구는 지표마다 `window` 본문을 500자로 자른 `evidence_text`를 싣고 잘렸다는 표시는 없다 [23].
`read_evidence_file`은 이진 파일이면 앞 2000자만 싣고 그렇다는 문장을 덧붙인다 [4].
`run_parallel`은 하위 결과의 `raw_text`를 500자에서 자르면 `raw_text_truncated`를 붙이고 `results` `dict`의 문자열 값을 자르면 그 키 이름을 `truncated_fields`에 싣는다 [7].
`lookup_attack_technique`는 기법의 `description`과 `detection`이 500자를 넘으면 497자로 자르고 끝에 `...`를 붙인다 [24].
`decode_payload`는 `decoded`를 50,000자에서 자르고 끝에 줄을 바꿔 `... [truncated at 50000 chars]`를 붙인다 [25].
같은 응답의 `layers`에 싣는 단계별 `preview`는 200자나 500자에서 표시 없이 자른다 [26].

### R02.07 건수 없는 잘림 표시

**구현.** 적재 도구 응답의 `preview`는 끝의 `...`로만 잘렸다는 것을 알린다 [2].
결과 `dict`에서 몇 개의 키와 항목이 빠졌는지는 싣지 않는다 [2].
`window`의 `full_text_available`도 원래 본문 길이를 싣지 않는다 [1].
`run_parallel`의 `raw_text_truncated`와 `truncated_fields`는 잘린 사실과 키 이름만 알리고 원래 길이는 싣지 않는다 [7].
`lookup_attack_technique`도 끝의 `...`로만 잘렸다는 것을 알리고 원래 길이는 싣지 않는다 [24].
`decode_payload`는 `decoded` 끝의 표시 문구로만 잘렸다는 것을 알린다 [25].
같은 응답의 `decoded_length`는 자른 뒤 표시 문구까지 더한 길이라 원래 길이가 아니다 [25].

### R02.08 보관한 출력의 일부 재조회

**구현.** `search`는 적재한 source의 `window`를 FTS 질의나 정규식으로 찾고 `source`·시간 범위·제외할 source로 범위를 좁힌다 [27].
결과 항목마다 `window`와 source 이름을 싣는다 [27].
`regex=True`에 `source`를 주지 않으면 일치가 있어도 0건이 나온다 [27].

    db: Any,
    terms: list[str],
    source: str | None,
    exclude_sources: list[str] | None,
    t_start: str | None,
    t_end: str | None,
    max_results: int,
) -> tuple[list[dict[str, object]], int]:
    """Full-text search path using the database FTS index.

    Returns ``(results, total_matches)``.
    """
    combined_fts = " OR ".join(terms)
    total_matches = db.count_search_windows(
        combined_fts,
        source_name=source,
        time_start=t_start,
        time_end=t_end,
        exclude_source_names=exclude_sources,
    )
    raw_matches = db.search_windows(
        combined_fts,
        source_name=source,
        max_results=max_results,
        time_start=t_start,
        time_end=t_end,
        exclude_source_names=exclude_sources,
    )
    results = [{"window": _truncated_window(w), "source_name": sname} for w, sname in raw_matches]
    return results, total_matches
