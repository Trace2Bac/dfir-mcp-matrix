# R04 해석 한계 안내

### R04.01 도구별 정적 주의

**구현.** YARA 도구 3개(`yara_scan_files`·`yara_scan_memory`·`yara_scan_with_volatility`)는 공통 함수 `_run_yara_scan`으로 성공 응답을 만든다 [1].
이 응답에는 탐지 건수와 관계없이 규칙 이름만으로 악성을 확정할 수 없으니 일치한 문자열·바이트를 보라는 `caveat`가 늘 붙는다 [1].
`yara_scan_files`의 도구 설명도 규칙 이름만으로 악성을 확정할 수 없다고 적는다 [2].
`yara_scan_memory`의 도구 설명은 일반 문자열에 걸린 규칙 하나는 오탐일 가능성이 크고 규칙 이름은 귀속을 증명하지 않는다고 적는다 [2].
서버 코드에서 `caveat` 키를 넣는 곳은 YARA 응답과 malfind 결과 두 곳이다 [1][3].
서버 지침(`instructions`)은 쓰지 않는다 [4].

### R04.02 결과 조건별 주의

**구현.** YARA 결과에서 규칙 계열이 4개 이상이면 `hit_metadata`에 공개 규칙 세트의 과다 일치일 가능성을 알리는 `noise_warning`을 붙인다 [5].
`run_volatility`는 malfind 플러그인 결과에만 RWX 메모리가 백신·JIT 컴파일러·.NET CLR에서도 나온다는 `caveat`를 붙인다 [3].
Volatility 플러그인이 머리글만 내면 결과의 `message`에 ISF 심볼이 없거나 메모리 형식을 다 지원하지 않는 경우가 많다고 적는다 [6].
`detect_timestomping`은 지표가 0건이면 MFTECmd 출력에 SI·FN 열이 없을 때는 이 결과가 timestomping이 없다는 것을 보장하지 않는다고 적는다 [7].

**예외.** `run_volatility_batch`가 Volatility 라이브러리로 플러그인을 돌리는 기본 경로는 malfind 결과에 `caveat`를 붙이지 않는다 [8].
`caveat`를 붙이는 함수는 단일 실행 `run_volatility`와 배치의 하위 프로세스 대체 경로만 쓴다 [3][8].
`run_volatility_batch`의 도구 설명은 이 도구를 메모리 추출의 기본 도구로 소개한다 [8].

### R04.03 추가 확인 도구·증거 추천

**구현.** YARA 응답의 `caveat`는 결론을 내리기 전에 일치한 문자열·바이트를 직접 보라고 권한다 [1].
`noise_warning`은 특정 위협 행위자로 귀속하기 전에 행위 증거로 교차 확인하라고 권한다 [5].
malfind `caveat`는 주입이라고 결론 내리기 전에 hex dump 내용을 확인하라고 권한다 [3].

**예외.** R04.02의 예외와 같이 `run_volatility_batch`의 기본 경로에서는 malfind 결과에 이 권고가 붙지 않는다 [8].

### R04.04 불확실성·추정 범위 표시

**구현.** `triage_binary`는 패킹 지표·의심 import·컴파일 시각·RWX section에 점수를 매겨 판정 `classification`과 확신 수준 `confidence`를 정한다 [9].
분석 단계가 실패하면 그 사실을 `reasons`에 더하고 지표가 없던 판정은 `inconclusive`와 `confidence: none`으로 바꾼다 [9].
적재하는 본문의 첫 줄에도 판정과 확신 수준을 적는다 [10].

**예외.** 판정 `triage_verdict`는 결과 `dict`의 끝쪽 키라서 앞 키들이 500자를 채우면 응답 `preview`에 실리지 않는다 [11].
코드 주석도 미리보기에는 판정이 닿지 않아 적재 본문의 맨 앞에 둔다고 적는다 [11].
이때 모델은 `search`나 `get_raw_output`으로 적재 본문을 읽어야 판정을 본다 [11].
