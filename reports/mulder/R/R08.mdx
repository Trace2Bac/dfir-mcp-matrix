# R08 시간값 처리

### R08.01 시간 변환 전 값 유지

**구현.** 외부 도구 출력을 적재하는 경로는 시각 문자열을 바꾸지 않고 `raw_text`에 그대로 둔다 [1].
`get_raw_output`은 이 `raw_text`를 돌려주므로 외부 도구가 낸 시각 표기가 그대로 모델에게 간다 [2].

서버가 출력을 다시 만드는 도구는 다르다.
`parse_browser_history`는 Chrome·Firefox·Safari의 시각 정수를 SQLite `datetime`으로 바꾼 값만 적재하고 원래 정수는 버린다 [3].
`parse_ios_artifacts`도 iOS 앱 DB의 시각을 같은 방식으로 바꾼 값만 적재한다 [4].

### R08.02 정규화 시간과 변환 전 값 병기

**구현.** 적재 함수는 `window`마다 본문에서 찾은 시각 하나를 ISO 형식으로 바꿔 `event_time`에 넣고 본문 `raw_text`는 그대로 둔다 [1][5].
`search`·`get_timeline`과 `windowed_response`를 쓰는 조회 도구는 `window`의 `event_time`과 `raw_text`를 한 항목에 함께 싣는다 [6].
`query_registry_value`는 8바이트 이진 값이 1980년부터 2100년 사이의 FILETIME으로 풀리면 원래 hex 값 `data` 옆에 풀어 쓴 시각 `decoded`를 둔다 [7][8].

정규화 값은 원래 값보다 정보가 적다.
ISO 형식 정규식은 초 단위까지만 읽어 소수 초와 시간대 표기를 버린다 [5].
연도가 없는 syslog 시각에는 정규화하는 시점의 현재 연도를 채운다 [5].
`window` 하나는 레코드 여러 개를 담지만 `event_time`은 하나뿐이다 [1][5].
응답은 `event_time`이 서버가 정규화하거나 연도를 가정한 값이라는 것을 알리지 않아 R08.04에는 연결하지 않는다 [6].

**한계.** 조회 응답은 `raw_text`를 잘라 싣는다 [6].
`search`와 `windowed_response`는 300자, `get_timeline`은 500자, `correlate_across_sources`는 200자에서 자른다 [6].
`event_time`은 4096자 `window` 전체에서 찾은 값이라 그 시각이 든 줄이 잘린 뒤쪽에 있으면 응답에는 정규화 값만 남는다 [6][5].

### R08.03 시간대·단위·정밀도 표시

**구현.** `query_registry_value`가 FILETIME을 풀어 쓴 `decoded`는 UTC 시간대가 붙은 시각이라 값 끝에 `+00:00`이 붙는다 [8].
`window`의 `event_time`과 `parse_browser_history`가 바꾼 시각에는 시간대 표기가 없다 [3][5].

**한계.** 같은 응답의 키 수정 시각 `last_written`은 python-registry가 돌려준 값을 `isoformat()`으로 바꾼 것이다 [9].
`uv.lock`은 python-registry를 1.3.1로 고정하지만 그 소스를 확인하지 못했다 [10].
그래서 이 값에 시간대가 붙는지는 확인하지 못했다 [9].
