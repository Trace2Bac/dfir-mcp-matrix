# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 외부 도구 출력이나 서버가 만든 결과를 사건 DB에 적재하는 도구와 그 적재 자료를 읽는 조회 도구가 이 방식을 쓴다.
적재 함수 `extract_and_index`는 적재 자료(`source`)마다 행을 만들고 `source_path`에 호출 인자로 받은 증거 경로를 적는다 [1].
적재 단위인 `window`마다 `source_id`가 있다 [2].
`search`와 공통 함수 `windowed_response`를 쓰는 조회 도구는 결과 항목에 `window`의 `source_id`와 적재 자료 이름을 싣는다 [3].
적재 도구의 응답 공통 함수 `tool_response`는 적재 자료 이름 `source`를 싣는다 [4].
`list_sources`는 적재 자료마다 `source_id`·이름·`source_path`를 돌려주므로 결과의 `source_id`로 증거 경로를 찾을 수 있다 [5].
적재하지 않고 증거 파일을 바로 읽는 `read_evidence_file`은 응답에 출처 값을 따로 싣지 않는다 [6].
`decode_payload`는 푼 결과를 사건 DB에 적재하지 않는다 [7].
source에서 문자열을 뽑았으면 응답의 `extraction`에 적재 자료 이름 `extracted_from_source`와 그 `window`가 적재 자료에서 시작하는 줄 번호 `window_line_start`를 싣고 `source_id`는 싣지 않는다 [8].

**한계.** 서버는 같은 이름의 적재 자료가 있어도 새 행을 만든다 [9].
`get_raw_output`은 이름이나 접두어가 맞는 적재 자료를 모두 이어 붙여 `source_id` 없이 돌려준다 [10].
그래서 같은 도구를 여러 증거에 실행한 사건에서는 이 응답의 본문이 어느 증거에서 나왔는지 가를 수 없다 [10].
복합 도구는 결과 항목에서 `source_window`를 지운다 [11].
`find_lateral_movement_indicators`는 결과 항목의 `source`를 `evtx.security` 같은 상수로 적는다 [12].
EZ Tools 보안 로그를 읽었거나 요청한 자료가 없어 모든 적재 자료를 검색했을 때도 같은 이름을 붙인다 [13].
복합 분석·상관 분석·IOC 조회 결과를 적재한 자료의 `source_path`는 증거 경로가 아니라 `composite_analysis` 같은 고정 문자열이다 [14].
`run_chkrootkit`을 `target_path` 없이 실행한 결과의 `source_path`는 증거 경로가 아니라 서버가 실행되는 시스템의 `/`다 [15].
`find_defense_evasion`의 timestomping 지표는 `source` 필드에 자료 이름 대신 `window` 본문의 앞 20자를 싣는다 [16].

### R05.02 증거 내부 경로

**구현.** 디스크 이미지의 파일 목록을 적재하는 TSK 도구가 이 방식을 쓴다.
`run_fls`가 적재하는 파일 목록(`tsk.filelist`)은 `fls -r -p` 출력이고 서버는 줄마다 inode와 이미지 안 경로가 있는 형식으로 읽는다 [17].
`search`와 `get_raw_output`은 이 줄을 `raw_text`에 그대로 돌려준다 [3][10].
`run_evtx_parser`는 이미지에서 꺼낸 EVTX 파일의 이름을 이미지 안 경로의 `/`를 `_`로 바꿔 만든다 [18].
`extract_optical_file`은 광학 디스크 이미지에서 꺼낸 파일의 디스크 안 경로를 응답의 `disc_path` 필드에 싣는다 [19].
이 필드는 꺼낸 사본의 위치 `extracted_to`와 따로 있다 [19].
`detect_masquerading`은 확장자와 내용이 맞지 않는 파일마다 이미지 안 경로를 적재 자료 `tsk.masquerade`의 줄에 적는다 [20].
이 두 도구 밖에서는 서버가 이미지 안 경로를 결과에 따로 붙이지 않는다.

**한계.** `search`와 `windowed_response`는 `window`의 `raw_text`를 300자에서 자르고 `full_text_available`만 붙인다 [21].
`window` 하나에는 최대 4096자까지 여러 줄이 들어가므로 일치한 줄의 경로가 응답에서 빠질 수 있다 [22].

### R05.03 레코드 키·번호

**구현.** 디스크 이미지의 파일 목록과 inode로 파일을 읽는 도구가 이 방식을 쓴다.
`tsk.filelist`의 줄마다 경로 앞에 inode가 있다 [17].
`extract_file_by_inode`는 결과에 `inode` 필드를 싣고 텍스트 파일이면 적재 자료 이름을 `tsk.extracted.<inode>`로 붙인다 [23].
`window_id`는 사건 DB가 적재 단위에 매긴 번호이고 증거 안 레코드 키가 아니다 [2].

**한계.** 파일 목록을 `search`나 `windowed_response`로 받으면 `raw_text`가 300자에서 잘리므로 일치한 줄의 inode가 응답에서 빠질 수 있다 [21][22].

### R05.04 바이트·섹터·행 오프셋

**구현.** 파티션 표를 돌려주는 `list_partitions`가 이 방식을 쓴다 [24].
이 도구가 돌려주는 `tsk.partitions`는 `mmls` 출력이고 서버는 그 행에서 시작 섹터와 길이를 읽는다 [25].
`window`의 `line_start`·`line_end`는 적재한 출력 본문 안의 줄 번호라 증거 안 위치가 아니다 [26].
`run_strings`는 `strings`를 오프셋 옵션 없이 실행한다 [27].
`yara_scan_files`·`yara_scan_memory`는 `yara`를 `-s`로 실행하고 일치한 문자열마다 16진 오프셋으로 시작하는 줄이 들어 있는 출력을 그대로 적재한다 [28].
`yara_scan_memory`는 메모리 이미지 파일을 그대로 검사하므로 이 오프셋은 파일 안 위치이고 이미지 형식에 따라 물리 주소와 다를 수 있다 [28].
`detect_masquerading`이 적재하는 줄에는 그 파일이 있는 파티션의 시작 섹터가 `offset=`으로 함께 적힌다 [20].
이 밖의 결과에는 서버가 증거 안 오프셋을 따로 붙이지 않는다.

**한계.** `list_partitions`도 `windowed_response`로 응답해 `raw_text`를 300자에서 자르므로 `mmls` 출력이 그보다 길면 뒤 행의 시작 섹터가 응답에서 빠진다 [21][24].
YARA 적재 자료를 `search`로 받으면 `raw_text`가 300자에서 잘려 오프셋 줄이 응답에서 빠질 수 있다 [21][28].

### R05.05 참조 지식 원문 출처

**구현.** 이 방식은 ATT&CK 기법을 조회하는 `lookup_attack_technique`에 적용된다 [29].
이 도구는 STIX 자료의 기법마다 `external_references`에서 `mitre-attack`이나 `mitre-ics-attack` 항목을 골라 기법 ID를 정하고 그 항목의 `url`을 결과 항목의 `url`에 싣는다 [29].
그 항목에 주소가 없으면 기법 ID로 `https://attack.mitre.org/techniques/` 아래 주소를 만들어 싣는다 [29].
응답은 증거 도구와 같은 `tool_response`로 만들고 `source`를 `None`으로 둔다 [30].
`tool_response`의 설명은 `None`을 사건 DB에 적재하지 않는 읽기·참조 도구의 결과에 쓴다고 적고 응답에 참조 지식이라는 표시는 따로 없다 [30].
그래서 R05.06에는 연결하지 않는다.

외부 위협 정보를 조회하는 `enrich_iocs`는 서비스별 결과에 서비스 이름 `source`를 싣지만 조회한 원문 위치는 싣지 않는다 [31].
이 도구는 조회 결과를 출처 이름 `enrichment.iocs`로 사건 색인에 적재해 증거에서 뽑은 출력과 같은 색인에 둔다 [32].
