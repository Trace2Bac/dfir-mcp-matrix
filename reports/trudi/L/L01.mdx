# L01 기록 방식

### L01.01 공통 요청 처리 단계에서 기록

**구현.** 이 방식은 서버가 받는 모든 MCP 도구 호출에 적용된다.
`server.py`는 최상위 FastMCP 서버에 `NarrationMiddleware`를 붙이고 `tools/`의 모듈 25개를 namespace로 그 아래에 mount한다 [1].
FastMCP 3.4.7은 도구 호출마다 최상위 서버의 미들웨어 묶음을 먼저 지나게 하고 mount한 서버의 도구는 그 안에서 하위 서버로 넘긴다 [2].
없는 도구 이름으로 온 호출도 이 묶음 안에서 `NotFoundError`로 거부된다 [2].

미들웨어 `on_call_tool`은 도구를 실행한 뒤 그사이 메모리의 기록 목록에 `call_initiated`가 아닌 항목이 늘었는지 본다 [3].
늘지 않았으면 도구가 스스로 기록하지 않았다고 보고 `<py>:<도구 이름>` 항목을 쓴다 [3].
스스로 기록하는 도구는 외부 명령을 실행기로 실행하는 도구와 본문에서 기록 함수를 부르는 도구다.
모델을 부르는 `reason.*`·`dair.assess`는 `record_reason_call`·`record_dair_call`로, `hash.file`은 `record_tool_call`로 항목을 쓴다 [4].
미들웨어는 게이트가 막은 호출을 `tool_blocked`로, 클라이언트가 취소한 호출을 `call_abandoned`로, `ToolError`가 아닌 예외를 실패한 `tool_call`로 쓴다 [5][6].
`_note` 인자로 온 모델의 서술은 `agent_message` 항목으로 쓴다 [5].

모든 기록 함수는 모듈 객체 `log` 하나를 거쳐 사건의 trace JSON 파일에 쓴다 [7].
trace는 `misc.start_execution_log`가 연다 [7].
trace를 열기 전에 기록 함수가 불리면 `_auto_recover`가 `session.json`이 가리키는 trace를 열고 그것이 없으면 작업 폴더의 `analysis/*_trace.json`을 연다 [8].
그래서 사건을 열지 않은 호출은 마지막으로 연 사건의 trace에 이어 쓰일 수 있다 [8].
실시간 감시 도구는 조사마다 `analysis/<case>_<inv>_trace.json`을 따로 열고 조사를 닫으면 사건 전체 trace로 돌아간다 [9].

**한계.** 도구 본문에서 난 예외는 항목 없이 끝난다 [6][10].
FastMCP 3.4.7은 도구 함수가 낸 예외를 하위 서버의 실행 단계에서 `ToolError`로 바꿔 올린다 [10].
미들웨어는 `ToolError`를 항목 없이 그대로 넘긴다 [6].
그래서 `_trace_exception`은 인자 검사 오류와 없는 도구 이름처럼 FastMCP가 `ToolError`로 바꾸지 않는 예외에만 항목을 쓴다 [6][10].
`@output_safe`가 출력 경로를 거부하며 내는 `ValueError`도 이 경로로 가서 거부된 호출이 trace에 남지 않는다 [11].
`requirements.txt`의 하한인 FastMCP 3.2.0도 도구 예외를 같은 단계에서 `ToolError`로 바꾼다 [10].

trace가 열려 있지 않고 `_auto_recover`도 열 trace를 찾지 못하면 기록 함수는 `RuntimeError`를 낸다 [12].
미들웨어의 기본 항목 쓰기는 이 예외를 처리해 표준 오류에 경고만 출력하고 도구 결과를 그대로 돌려준다 [3].
게이트 거부의 `tool_blocked` 쓰기는 이 예외를 받고 아무것도 남기지 않는다 [5].

미들웨어는 호출하는 동안 늘어난 항목이 다른 호출의 것이어도 도구가 스스로 기록했다고 보고 기본 항목을 쓰지 않는다 [3].
서버 안 백그라운드 작업은 다른 호출과 동시에 진행되며 끝날 때 항목을 쓰고 FastMCP 3.4.7은 동기 도구 함수를 스레드 풀에서 실행한다 [13][14].
그래서 스스로 기록하지 않는 도구를 부른 동안 백그라운드 작업이 끝나 항목을 쓰면 그 도구 호출의 항목이 빠진다 [3][13].
미들웨어는 백그라운드 작업에서만 결과의 호출 ID로 이 경우를 가린다 [13].
동시에 호출해 이 동작을 확인하지는 않았다.

백그라운드 작업으로 실행되는 도구가 기다리는 시간 안에 끝나지 않으면 미들웨어는 작업 핸들만 돌려주고 항목은 작업이 끝날 때 쓴다 [13].
서버 안 작업은 서버를 다시 시작하면 사라지므로 그 전에 서버가 끝나면 그 호출의 항목은 남지 않는다 [15].

### L01.03 공통 실행 함수에서 기록

**구현.** 이 방식은 외부 명령을 실행기 함수로 실행하는 도구에 적용된다.
외부 도구 실행기 `run`·`run_with_progress`·`run_with_output_file`은 명령이 끝나거나 시간 초과·실행 파일 없음·실행 오류로 끝난 뒤 `_log_tool`로 `tool_call` 항목을 쓴다 [16].
`run_dotnet`은 `run`을 부른다 [16].
SSH 실행기 `ssh_run`·`ssh_run_write`와 Velociraptor 실행기 `_velo_run`도 인자 오류와 설정 파일 없음까지 포함해 실행마다 `record_tool_call`로 항목을 쓴다 [17][18].
`misc.evtx_filter`와 `strings.grep`은 출력을 줄 단위로 읽으려고 `subprocess.Popen`을 직접 부르지만 끝난 뒤 실행기의 `_log_tool`로 같은 항목을 쓴다 [19].
`misc.batch_run`은 모델이 준 명령마다 `run`을 불러 명령마다 항목이 남는다 [20].

`net.tcpxtract_streams`는 `start_job`으로 carve 명령을 별도 프로세스로 실행하고 바로 돌아오며 `start_job`은 기록하지 않는다 [21].
명령의 항목은 `misc.job_status`가 끝난 작업을 처음 조회할 때 `_log_tool`로 한 번 쓴다 [21].
그래서 끝난 작업을 조회하지 않으면 trace에는 시작 호출의 기본 항목만 남는다.
`monitor.start_watcher`가 시작하는 감시 프로세스는 탐지기마다 Velociraptor 감시 질의를 자식 프로세스로 계속 실행하지만 trace에는 쓰지 않고 경보 파일과 자기 로그만 쓴다 [22].

**한계.** trace가 열려 있지 않고 `_auto_recover`도 열 trace를 찾지 못하면 실행기는 명령을 실행한 뒤 `_log_tool`에서 `RuntimeError`로 끝난다 [12][16].
이 예외는 항목 없이 오류 응답이 되므로 실행한 명령이 trace에 남지 않는다 [10].
SSH와 Velociraptor 실행기는 같은 상태에서 표준 오류에 경고만 남기고 결과를 돌려주며 항목은 남지 않는다 [17][18].
