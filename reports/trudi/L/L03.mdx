# L03 기록 실패 처리

### L03.02 실행 후 응답 차단

**구현.** 이 방식은 외부 도구 실행기 `run`·`run_with_progress`·`run_with_output_file`로 명령을 돌리는 도구에 적용된다 [1].
`misc.evtx_filter`·`strings.grep`처럼 명령을 직접 띄운 뒤 실행기의 `_log_tool`을 감싸지 않고 부르는 도구와 `hash.file`도 같다 [2][3].
모든 기록 함수는 항목을 메모리 목록에 넣은 뒤 `_flush`로 trace 파일 전체를 임시 파일에 써서 바꿔 놓는다 [4].
`_flush`는 쓰기가 실패하면 표준 오류에 경고를 찍고 예외를 다시 올린다 [4].
`_log_tool`은 명령이 끝난 뒤 불리고 이 예외를 표준 오류 경고와 함께 다시 올린다 [1].
`hash.file`은 해시를 계산한 뒤 `record_tool_call`과 `annotate_tool_call`을 감싸지 않고 부른다 [3].

이 예외는 도구 본문 밖으로 나간다.
FastMCP 3.4.7은 이 예외를 `ToolError`로 바꾸고 클라이언트에는 `isError` 결과로 오류 문구를 돌려준다 [5].
미들웨어는 `ToolError`를 항목 없이 그대로 넘긴다 [6].
그래서 기록 쓰기가 실패한 호출은 명령 결과를 돌려주지 않고 오류로 끝난다.
서버 안 백그라운드 작업으로 돈 도구도 작업이 이 예외로 끝나 `misc.job_status`가 결과 대신 오류를 돌려준다 [7].
`misc.batch_run`은 명령 하나의 기록이 실패하면 다른 명령이 모두 끝날 때까지 기다린 뒤 전체 호출이 오류로 끝나 이미 끝난 명령의 결과도 돌려주지 않는다 [8].

명령이 남긴 부수 효과는 되돌리지 않는다.
`run_with_output_file`이 출력 파일에 쓴 내용과 sudo로 실행한 명령의 결과는 기록 없이 남는다 [9].
쓰지 못한 항목이 어떻게 되는지는 L03.05에서 본다.

### L03.03 경고 후 계속

**구현.** 이 방식은 SSH 실행기, Velociraptor 실행기, 미들웨어의 기본 항목, 모델 호출 기록, 분리 실행 carve 수집, 게이트 거부 기록에 적용된다.
SSH 실행기의 `_log_ssh_tool`과 Velociraptor 실행기의 `_log_velo_tool`은 쓰기 예외를 잡아 표준 오류에 경고를 찍고 `_trudi_call_id`를 0으로 둔 결과를 돌려준다 [10][11].
`live.*`, `respond.execute_action`, `velo.*`가 이 실행기를 쓴다 [12].
`respond.execute_action`은 원격 단말에 격리 조치를 실행한 뒤 기록하므로 기록이 실패해도 조치는 이미 실행되었고 결과를 그대로 돌려준다 [12][13].

스스로 기록하지 않는 도구의 기본 항목은 미들웨어가 쓰고 쓰기 예외는 표준 오류 경고로 끝난다 [14].
이때 결과에는 호출 ID가 붙지 않는다 [14].
`reason.*`와 `dair.assess`의 기록 함수와 모델 호출 전의 `call_initiated` 쓰기도 예외를 잡아 표준 오류에 경고만 찍는다 [15][16].
`misc.job_status`는 끝난 carve 작업을 거둘 때 `_log_tool`이 올린 예외를 잡아 `_trudi_call_id`를 비운 결과를 돌려준다 [17].
`_log_tool`이 그 전에 표준 오류에 경고를 찍는다 [1].

게이트 거부를 쓰는 `record_tool_blocked`의 예외는 아무것도 하지 않고 넘기고 거부 응답을 그대로 올린다 [18].
쓰기 실패가 파일 쓰기 오류이면 `_flush`가 예외를 올리기 전에 표준 오류에 경고를 찍는다 [4].

어느 경우에도 응답에는 기록 실패를 알리는 필드가 없다 [10][11][14].
실패 사실은 서버의 표준 오류에만 남는다.
쓰지 못한 항목이 어떻게 되는지는 L03.05에서 본다.

`misc.start_execution_log`는 trace를 열며 파일을 처음 쓰고 `run_profile` 항목을 써 본 뒤 그 쓰기가 실패하면 `success: false`를 돌려준다 [19].
이 검사는 사건을 열 때 한 번이고 그 뒤 호출의 기록 실패를 막지 않는다.

### L03.05 재시도·별도 저장

**구현.** 이 방식은 기록 함수가 항목을 메모리 목록에 넣은 뒤 trace 파일 전체를 다시 쓰는 구조에서 생기고 L03.02·L03.03의 모든 경로에 적용된다 [4].
쓰기가 실패해도 항목은 메모리 목록에 남고 다음 기록의 `_flush`가 성공하면 파일 전체를 다시 쓸 때 함께 들어간다 [4].
쓰지 못한 항목이 남아 있다는 표시도, 그 항목만 다시 쓰려는 코드도 없다 [4].
그래서 다음 기록이 성공하기 전에 서버 프로세스가 끝나면 그 항목은 사라진다 [4].
L03.02의 경로에서는 그 항목의 호출 ID가 모델에게 돌아가지 않았다 [1].
