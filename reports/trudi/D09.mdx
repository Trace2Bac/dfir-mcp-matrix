# D09 파생물 저장 실패 처리

### D09.01 오류·부분 완료 표시

**구현.** 이 방식은 표준 출력을 파일로 받는 외부 도구 실행, 오래 걸리는 카빙 작업, 서버 코드가 파생물이나 보고 산출물을 직접 쓰는 도구에 있다 [1][2][3][4][5][6][7].
`run_with_output_file`은 출력 파일을 열거나 도구를 실행하다 난 예외를 잡아 `success`를 거짓으로 두고 그 내용을 표준 오류 칸에 담아 호출 기록에 남긴 뒤 돌려준다 [1].
시간 제한에 걸리면 `timed_out`을 참으로 두지만 그때까지 쓴 파일은 `output_path`에 남고 결과와 호출 기록 항목에도 그 경로가 남는다 [1][8].
카빙 작업은 셸이 도구의 종료 코드를 `exit` 파일에 쓰고 `misc.job_status`는 그 값이 0이 아니면 `success`를 거짓으로 두어 호출 기록에 남긴다 [2].
종료 코드가 124(시간 제한)이면 결과에 `timed_out`과 그때까지 만든 파일 수를 알리는 `partial_output`을 싣는다 [9].
`misc.write_final_report`는 보고서 파일을 `w` 모드로 열어 쓰고 쓰기 예외를 잡지 않는다 [3].
도구 함수가 잡지 않은 예외는 FastMCP 3.4.7이 `ToolError`로 바꾸고 미들웨어는 그 `ToolError`를 호출 기록 없이 넘긴다 [10][11].
FastMCP 3.4.7에서 도구 호출 중 난 `ToolError`는 `isError`가 참인 도구 결과가 된다 [12].
그래서 보고서 파일을 쓰지 못하면 `misc.write_final_report` 호출은 오류로 끝나고 경로를 담은 성공 응답은 나가지 않는다 [3][11][12].
이 실패가 호출 기록에 남지 않는 것은 L01에서 본다.
`accuracy.export_report`는 쓰기 `OSError`를 잡아 `success`가 거짓인 결과와 오류 문구를 돌려준다 [4].
`misc.chat_db_export`와 `misc.cs_beacon_config`는 CSV·JSON 쓰기 `OSError`를 잡아 응답에 경고를 싣는다 [5].
`misc.cs_beacon_config`는 그때 응답의 `output_path`를 비운다 [5].
`misc.capa_analyze`는 쓰기 실패를 응답의 `write_error`에 싣고 `success`는 바꾸지 않는다 [6].
`hash.hashdeep_compute`·`hash.md5deep_scan`·`net.http_session_inventory`·`net.pcap_identity_timeline`·`misc.knowns_pattern_generate`와 PECmd 대신 libscca로 프리페치를 읽는 경로는 `misc.write_final_report`처럼 파일 쓰기 예외를 잡지 않아 호출이 오류로 끝난다 [7][11][12].

### D09.03 저장 확인·검증

**구현.** 이 방식은 호출 기록의 저장 출력 파일과 카빙 작업의 완료 표시에 있다 [13][14].
호출 기록은 도구의 전체 표준 출력을 임시 파일에 다 쓴 뒤 `<호출 ID>.txt`로 이름을 바꾸고 이름 바꾸기까지 끝난 경우에만 항목에 `stdout_path`를 남긴다 [13][15].
출력이 상한(기본 8MB)을 넘어 앞부분만 썼으면 항목에 `stdout_partial`을 남긴다 [15][16].
검토 모델에게 보내는 근거 묶음은 `stdout_partial`이 있는 출력을 `retained_output_complete`가 거짓인 출처로 싣는다 [17].
카빙 작업은 셸이 도구가 끝난 뒤에 `exit` 파일을 쓰고 `misc.job_status`는 그 파일이 생기기 전까지 `running`으로 답하며 결과를 호출 기록에 올리지 않는다 [2][14].
결과를 올린 작업은 상태 파일에 `collected`를 남겨 같은 결과를 한 번만 호출 기록에 올린다 [18].

### D09.04 알림 없이 계속

**구현.** 이 방식은 `misc.export_execution_log`, 호출 기록의 저장 출력 쓰기, `misc.device_install_inventory`의 CSV 쓰기에 있다 [19][13][20].
`ExecutionLog.export`는 JSON과 markdown 파일 쓰기의 `OSError`를 잡아 표준 오류에 경고만 쓰고 `json_wrote`·`md_wrote`를 거짓으로 돌려준다 [19].
`misc.export_execution_log`는 이 두 값을 보지 않고 `success`를 참으로 두어 두 파일 경로를 응답에 싣는다 [21].
저장 출력 쓰기가 실패하면 호출 기록 항목에 `stdout_sidecar_error`만 남기고 항목을 그대로 쓴다 [13].
외부 도구 실행기는 이 항목의 호출 ID만 결과에 넣으므로 도구 응답에는 저장 실패가 실리지 않는다 [22].
`misc.device_install_inventory`는 전체 목록 CSV를 쓰다 난 `OSError`를 잡은 뒤 알리지 않고 응답에 요청한 `output_path`를 그대로 싣는다 [20].

        """Persist the complete stdout for `cid`. Called from record_tool_call
        between _next_id() and _append_entry() — no lock is held across the

    def _write_sidecar_text(self, name: str, text: str) -> tuple[str | None, bool, str]:
        """Atomically write `text` to `.tool_output/<name>` (capped at
        STDOUT_SIDECAR_CAP). Returns (path, partial, error); never raises."""
        try:
            from core.paths import STDOUT_SIDECAR_CAP
            d = self.stdout_sidecar_dir()
            if not d:
                return None, False, ""
            os.makedirs(d, exist_ok=True)
            partial = len(text) > STDOUT_SIDECAR_CAP
            body = text[:STDOUT_SIDECAR_CAP]
            import tempfile
            stem = os.path.splitext(name)[0]
            fd, tmp = tempfile.mkstemp(prefix=f".{stem}-", suffix=".tmp", dir=d)
            try:
                with os.fdopen(fd, "w", encoding="utf-8", errors="replace") as fh:
                    fh.write(body)
                final = os.path.join(d, name)
                os.replace(tmp, final)
            except Exception:
                try:
                    os.unlink(tmp)
                except OSError:
                    pass
                raise
            return final, partial, ""
        except Exception as e:
            return None, False, str(e)[:200]
