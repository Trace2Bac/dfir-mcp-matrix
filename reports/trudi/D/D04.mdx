# D04 출력 경로 관리

### D04.01 서버가 출력 위치 결정

**구현.** 이 방식은 호출마다 남기는 출력 텍스트 파일, 검토 모델의 추가 행 요청 결과, 작업 폴더, live monitoring 파일, 조사별 호출 기록과 보고서에 적용된다.
`.tool_output` 폴더는 서버가 호출 기록 파일 옆으로 정하고 파일 이름은 호출 ID다 [1].
검토 모델이 더 요청한 행은 같은 폴더의 `fetch-<호출 ID>-<n>.txt`에 쓴다 [2].
`net.tcpxtract_streams` 작업은 서버 캐시 폴더의 `jobs/<작업 ID>.d/` 아래 `stdout`·`stderr`·`exit` 파일에 출력을 쓴다 [3].
live monitoring 도구는 `TRUDI_CASES_ROOT/<case_id>/monitoring/` 아래에 baseline·watcher·alert 파일을 둔다 [4].
`monitor.start_investigation`과 `monitor.end_investigation`은 조사 호출 기록을 `analysis/<case_id>_<investigation_id>_trace.json`으로, 보고서를 `reports/<case_id>_<investigation_id>`에 `.json`·`.md`를 붙인 이름으로 정한다 [5].
`misc.chat_db_export`는 `output_dir`을 주지 않으면 `./exports/chat`에 쓴다 [6].

그 밖의 도구는 모델이 준 `output_path`·`output_dir`·`output_file`·`storage_file` 등을 출력 위치로 그대로 쓴다 [7].
`@output_safe`와 `assert_output_safe`는 실제 경로가 `/cases/`·`/mnt/`·`/media/` 아래이거나 경로에 `evidence` 폴더가 있는지만 보고 그 밖의 경로는 받는다 [7].
서버 지시문은 출력 경로를 analysis·exports·reports 안에 두라고 적지만 코드는 그 폴더와 대조하지 않는다 [8][7].
증거 위치를 거부하는 이 검사는 E03에서 보고 허용 폴더와 대조하는 코드가 없어 D04.02에는 연결하지 않았다.
`ez.*`는 `output_dir`과 `output_file`을 따로 외부 도구에 넘기고 검사는 두 값을 서버 작업 폴더 기준으로 따로 풀어 본다 [9][7].
두 값을 합친 경로는 검사하지 않아 `output_file`에 `..`가 들어가도 거부하지 않는다 [9][7].
`misc.batch_run`은 모델이 준 명령을 출력 경로 검사 없이 실행한다 [10].
`misc.clear_case_run`은 모델이 준 `case_dir` 아래 analysis·exports·reports를 검사 없이 지우고 그 삭제는 P05에서 본다 [11].
마운트 도구 `ewf.mount`·`ewf.mount_ntfs`·`ewf.mount_full_image`·`img.vshadow_mount`·`img.bde_mount`·`img.xmount_image`는 모델이 준 마운트 지점에 서버 계정으로 폴더를 만든 뒤 sudo로 그 위에 마운트한다 [12].
`@output_safe`가 보는 인자 이름에는 마운트 지점 인자가 없고 `ewf.*` 마운트 도구에는 `@output_safe`도 붙지 않는다 [13][12].
그래서 마운트 지점은 출력 경로 검사를 받지 않는다 [13][12].
해제 도구 `ewf.umount`·`ewf.umount_filesystem`·`img.vshadow_umount`·`img.losetup_detach`는 모델이 준 경로나 장치를 검사 없이 sudo로 실행하는 `umount`·`losetup -d`에 넘긴다 [14].

**한계.** 서버가 정한 위치가 모델 인자를 따라가는 경로가 있다.
`.tool_output` 폴더는 `misc.start_execution_log`의 `output_path`로 정한 호출 기록 파일의 위치를 따라가고 그 경로는 증거 위치 검사만 받는다 [15][1].
조사 호출 기록과 보고서 이름에 들어가는 `investigation_id`는 접두어만 검사해서 `/`·`..`가 든 값을 주면 사건 폴더 밖에 쓴다 [16][5].
이 경로는 코드로만 따라갔고 실행하지 않았다.

### D04.03 파생물 ID로만 수정·삭제

**구현.** 이 방식은 발견사항의 수정과 철회에 적용된다.
`misc.record_finding`과 `misc.submit_finding`은 `supersedes`로 서버가 매긴 발견사항 호출 ID를 받아 고칠 대상을 고른다 [17].
대상이 지금 버전이 아니거나 수정이 갈라지거나 명제 필드가 다르면 거부한다 [17].
`misc.retract_finding`은 지금 유효한 발견사항의 호출 ID와 사유, 호출 기록에 있는 근거 호출 ID를 받아야 철회 항목을 더한다 [18].
두 경로 모두 앞 항목을 지우지 않고 새 항목을 더한다 [18][19].
출력 파일을 지우는 모델 도구는 ID가 아니라 모델이 준 폴더 경로로 대상을 고른다 [11].

### D04.04 이름·확장자·충돌 검사

**구현.** 이 방식은 live monitoring과 조사 도구가 경로에 넣는 식별자와 작업 ID에 적용된다.
live monitoring 경로의 `case_id`는 비었거나 `/`·`..`가 들어 있으면 거부한다 [4].
실제 경로로 변환하지 않는 문자열 검사다 [4].
`investigation_id`는 `INV-`로 시작하는지 보고 `client_id`는 `C.`로 시작하는지 본다 [16][20].
두 값 모두 접두어 뒤는 검사하지 않는다 [16][20].
작업 ID는 도구 이름의 `/`·`.`을 `_`로 바꾼 뒤 난수를 붙여 만든다 [3].

**한계.** `investigation_id`는 접두어 뒤를 검사하지 않아 D04.01의 한계처럼 사건 폴더 밖 경로를 만들 수 있다 [16][5].
`monitor.baseline_capture`도 `client_id`의 접두어 뒤를 검사하지 않고 baseline 파일 이름에 넣는다 [20].
baseline 파일은 Velociraptor 수집이 끝난 뒤에 쓰므로 그런 값이 수집 단계를 지나는지는 확인하지 못했다 [20].

### D04.05 실행 ID별 위치

**구현.** 이 방식은 출력 텍스트 파일, 검토 모델의 추가 행 요청 결과, 작업 폴더, 조사 호출 기록과 보고서에 적용된다.
출력 텍스트 파일은 `<호출 ID>.txt`, 추가 행 요청 결과는 `fetch-<호출 ID>-<n>.txt`로 호출마다 이름이 다르다 [1][2].
호출 ID는 서버와 Claude 훅이 함께 쓰는 기계 전체 카운터로 매기고 지금 호출 기록 파일의 최댓값보다 늘 크다 [21].
작업 폴더 이름은 도구 이름 뒤에 6바이트 난수의 16진수를 붙인 작업 ID다 [3].
조사 호출 기록과 보고서는 사건별 카운터로 매긴 `INV-NNN`으로 나눈다 [22][5].
모델이 출력 경로를 주는 도구는 실행 ID로 나누지 않는다.
`net.tcpxtract_streams`도 작업 ID와 관계없이 모델이 준 `output_dir`에 쓴다 [23].

**한계.** 출력 텍스트 파일은 같은 이름이 있는지 보지 않고 바꾸어 쓴다 [24].
사용자 CLI `tools/trudi_reset.py`를 `--purge-outputs` 없이 실행하면 호출 기록 파일만 옮기고 카운터를 1로 되돌린다 [25].
같은 사건 폴더에서 다시 시작한 호출은 앞 사건이 쓴 번호를 다시 받아 그 출력 텍스트 파일을 바꾸어 쓰고 옮긴 호출 기록의 `stdout_path`는 새 출력을 가리킨다 [25][24].
`misc.clear_case_run`은 다시 쓰는 호출 ID로 앞 출력을 읽지 않도록 `.tool_output`까지 지운다고 설명에 적는다 [11].
`monitor.start_investigation`은 `investigation_id`를 인자로 받아 이미 쓴 번호를 주면 그 조사의 호출 기록을 이어 쓴다 [16][5].
`monitor.end_investigation`은 그 번호의 보고서 파일을 쓰기 모드로 다시 쓴다 [26].

### D04.07 버전·이력 보존

**구현.** 이 방식은 발견사항에 적용된다.
발견사항을 고치면 같은 `finding_id`에 `revision`을 하나 올린 새 항목을 더하고 앞 항목에는 `superseded_by`만 붙여 남긴다 [27][19].
보고서는 `active_findings`로 지금 버전만 읽는다 [28][29].
갈라진 수정이나 대상이 없는 연결은 `anomalies`로 따로 모으고 그런 대상의 수정은 거부한다 [28][17].
보고서의 발견사항 절은 앞 버전이 호출 기록에 남아 있다고 적는다 [29].
출력 파일에는 이런 버전 보존이 없고 D04.08의 구현 단락에 적는다.

### D04.08 덮어쓰기 선택·충돌 감지

**구현.** 이 방식은 발견사항 제출, 작업 결과 수집, 호출 기록 파일 열기에 적용된다.
`misc.submit_finding`은 `idempotency_key`로 같은 요청이 이미 있었는지 본다 [30].
같은 키와 같은 요청이면 앞 결과를 돌려주고 다시 기록하지 않으며 같은 키로 다른 요청을 보내면 거부한다 [30].
`misc.job_status`는 끝난 작업을 한 번만 기록하고 그 뒤에는 저장한 결과를 돌려준다 [31].
`misc.start_execution_log`는 같은 경로에 같은 `case_id`의 호출 기록이 있으면 새로 만들지 않고 이어 쓴다 [32].

모델이 경로를 주는 출력 파일은 이미 있는지 보지 않고 쓰기 모드로 열어 알리지 않고 덮어쓴다 [33].

**한계.** `misc.start_execution_log`는 같은 경로에 다른 `case_id`의 호출 기록이 있으면 표준 오류에 경고만 남기고 새 사건으로 연다 [34].
경고 문구는 덮어쓴다고 적지만 저장 함수는 디스크에 있던 앞 사건의 항목을 호출 ID로 합쳐 다시 쓴다 [35].
그래서 앞 사건의 항목이 새 사건의 호출 기록 파일에 남는다(코드로만 따라갔다).
호출 기록 파일이 JSON으로 읽히지 않으면 표준 오류 경고만 남기고 빈 기록으로 그 파일을 바꾸어 쓴다 [34][35].

```python
def output_safe(func):
    """Decorator that validates any output_* / storage_file kwarg against the
    evidence read-only policy before calling the wrapped function.

    Apply BELOW @mcp.tool() so MCP introspects the original signature:

        @mcp.tool()
        @output_safe
        def my_tool(image: str, output_dir: str) -> dict: ...
    """
    sig = inspect.signature(func)
    relevant = tuple(n for n in _OUTPUT_PARAM_NAMES if n in sig.parameters)
    if not relevant:
        return func

    @wraps(func)
    def wrapper(*args, **kwargs):
        try:
            bound = sig.bind_partial(*args, **kwargs)
        except TypeError:
            # Signature mismatch — let the wrapped function raise its own error.
            return func(*args, **kwargs)
        for name in relevant:
            value = bound.arguments.get(name)
            if value:
                assert_output_safe(value)
        return func(*args, **kwargs)

    return wrapper
```

```python
    """Atomically increment and return the next shared call_id.

    Both the MCP server (this module) and the PostToolUse hook
    (~/.claude/hooks/log_narration.py) call this so call_ids form a single
    dense monotonic sequence across both writers.

    Returns `max(counter_file, trace_max+1, in_memory_seq+1)` — so even if the
    counter file is stale (hand-edited, race-reset between writers, lost) the
    returned cid is provably greater than any cid present in the trace OR in

    impossible by construction; the counter file becomes a fast-path *cache*,
    not a source of truth.

        # trace scan is the cross-process safety net (e.g. for the hook).
        trace_max = _scan_trace_max_cid(trace_path) if trace_path else 0
```

```python
def _next_inv_seq(case_id: str) -> int:
    """fcntl-locked atomic increment of the per-case INV counter."""
    import fcntl
    seq_path = _inv_seq_path(case_id)
    seq_path.parent.mkdir(parents=True, exist_ok=True)
    lock_path = seq_path.with_suffix(".lock")
    with open(lock_path, "w") as lock:
        fcntl.flock(lock.fileno(), fcntl.LOCK_EX)
        try:
            try:
                cur = int(seq_path.read_text().strip() or "0")
            except (OSError, ValueError):
                cur = 0
            cur += 1
            seq_path.write_text(str(cur))
            return cur
        finally:
            fcntl.flock(lock.fileno(), fcntl.LOCK_UN)
```
