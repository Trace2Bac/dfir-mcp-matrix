# D05 발견사항 기록 관리

### D05.01 자유 노트

**구현.** `misc.record_agent_message`와 도구 호출의 `_note` 인자는 모델이 쓴 해석 글을 `investigation_narration` 항목으로 남긴다 [1][2].
항목에는 글과 서버가 채운 시각, 모델이 준 `input_call_ids`가 들어가고 판정 필드는 없다 [1].
`input_call_ids`가 호출 기록에 있는지는 검사하지 않는다 [1].
사실 주장은 같은 도구의 `findings` 인자로 따로 받아 `misc.record_finding`과 같은 게이트를 거친다 [3].

`misc.record_curiosity_probe`는 모델이 작업 지시 밖에서 고른 탐색의 이유를 `curiosity_probe` 항목으로 남긴다 [4].
항목에는 근거 문장 `probe_rationale`, 그 탐색을 이끈 가설 ID `seeded_by`, 서버가 채운 시각이 들어가고 판정 필드는 없다 [4].
`input_call_ids`를 주지 않으면 마지막 `dair.assess` 호출 ID로 채우고 실제로 돌린 읽기 도구 호출과는 묶지 않는다 [4].
기록 전에 최근 30개 항목 가운데 마지막 `dair_call`이 준 `curiosity_budget`을 읽고 그 뒤의 `curiosity_probe` 항목 수가 이 값 이상이면 거부한다 [4][5].
근거 문장이 비어 있어도 거부한다 [6].
이 검사는 `misc.record_curiosity_probe`만 부르므로 기록 수만 제한하고 분석 도구 실행은 제한하지 않는다 [6].
`misc.record_self_correction`은 `trigger`·`prior_belief`·`new_belief`·`evidence`·`linked_call_id`를 `self_correction` 항목으로 남긴다 [7].
`trigger`가 `dair_max_pass_cap`일 때만 따로 검사하고 다른 값은 목록과 대조하지 않는다 [7].
이 항목은 모델이 쓴 글이며 발견사항이나 가설의 앞 값을 서버가 남기는 D05.05의 이력과 다르다 [7].

**예외.** `investigation_narration` 항목의 글은 앞 2,000자만 남고 잘렸다는 표시는 항목에도 응답에도 없다 [1][8].

### D05.02 발견사항 필드 구분 저장

**구현.** 발견사항은 `misc.record_finding`, `misc.record_agent_message`의 `findings`, `misc.submit_finding`으로 받는다 [3][9].
항목은 `description`, 판정 등급 `confidence`, 결과를 낸 도구 이름 `source`, 근거 글 `supporting_evidence`, 형식을 정한 주장 `claim`을 나누어 담는다 [10].
`claim`은 주장 종류·범주·행위·행위자·주체·대상·기법 등을 따로 담는다 [11].
`claim`의 열거 필드는 정해 둔 값인지 늘 검사하고 CONFIRMED·LIKELY·UNCONFIRMED에서는 종류·범주·행위를 요구한다 [12].
판정 등급 검사는 D05.10에서 본다.

**예외.** `supporting_evidence`는 2,000자에서 잘려 저장되고 응답에 그 사실이 없다 [10].
환경변수 `TRUDI_REQUIRE_TYPED_CLAIMS`를 `0`으로 두면 `claim`의 필수 필드 요구가 꺼진다 [12].

### D05.03 근거 증거·호출 참조

**구현.** 발견사항 항목은 근거 호출 `input_call_ids`와 결과를 낸 호출 `linked_call_id`를 필드로 남긴다 [10].
`claim`은 세션 연결·전송·수신 근거와 배제한 대안의 근거를 호출 ID 목록으로 따로 담는다 [11].
게이트가 맞춘 검토 호출의 ID도 `gated_by_*_call_id` 필드로 들어간다 [13].
`input_call_ids`와 `linked_call_id`는 호출 기록에 있는 ID여야 받고 CONFIRMED는 `linked_call_id`가 있어야 받는다 [14][15].
`misc.submit_finding`은 인용 호출 ID가 모두 양의 정수이고 호출 기록에 있어야 받는다 [16].
`misc.record_agent_message`의 `findings`는 `input_call_ids`를 주지 않으면 메시지의 `input_call_ids`를 물려받는다 [3].
증거 파일을 직접 가리키는 필드는 없고 근거 호출의 명령과 출력으로 이어지는 연결은 D02에서 본다.

**예외.** `input_call_ids`를 주지 않으면 서버가 최근 30개 항목 가운데 도구·검토 호출 5개로 채우고 `lineage_inferred`만 적는다 [17].
그 5개가 실제 근거인지는 보지 않는다 [17].
호출 기록 항목이 5개보다 적으면 근거 호출 없이도 받는다 [14].

### D05.04 사건 시각과 작성 시각 분리

**구현.** 작성 시각은 서버가 항목의 `ts`에 UTC로 넣고 모델이 넘기는 인자에는 작성 시각이 없다 [10][18].
사건 시각은 `claim.window`의 `start`·`end`로 따로 받는다 [11].
`window`는 부정 주장 가운데 범주가 `logon_auth`·`device_initial_access`인 것에서만 필수다 [19].

**예외.** 서버는 `window`의 날짜 형식을 검사하지 않고 받은 `dict`를 그대로 복사한다 [11].
`TRUDI_REQUIRE_TYPED_CLAIMS`를 `0`으로 두면 `window` 필수 검사도 꺼진다 [12][19].

### D05.05 수정·철회 이력

**구현.** `supersedes`로 발견사항을 고치면 같은 `finding_id`에 `revision`을 하나 올린 새 항목을 더하고 앞 항목에는 `superseded_by`만 붙여 남긴다 [10][20].
고칠 대상이 지금 버전이 아니거나 수정이 갈라지거나 명제 필드가 다르면 거부한다 [21].
`misc.retract_finding`은 대상 호출 ID, 사유, 근거 호출 ID, 시각을 담은 `finding_retracted` 항목을 더하고 앞 항목을 지우지 않는다 [22].
게이트가 거부한 기록 시도도 `finding_refused` 항목으로 남는다 [23].
항목마다 서버가 채운 시각이 있어 바뀐 차례를 다시 볼 수 있고 `finding_view`가 지금 버전과 이력을 나눈다 [24].
호출 기록 파일을 통째로 지우는 일은 P05에서 본다.

### D05.06 파일·DB에 저장

**구현.** 발견사항, 철회, 제출 기록은 `misc.start_execution_log`가 연 호출 기록 JSON 파일에 항목으로 남는다 [10][25].
저장은 임시 파일에 쓴 뒤 이름을 바꾸고 환경변수로 끄지 않으면 매번 fsync한다 [25].
호출 기록 파일이 열리지 않은 상태에서는 발견사항 기록이 오류로 끝난다 [26].
서버를 다시 띄우면 세션 파일이나 작업 폴더의 호출 기록 파일에서 항목을 다시 읽는다 [27].

**예외.** 호출 기록 파일이 JSON으로 읽히지 않으면 표준 오류에 경고만 남기고 빈 기록으로 그 파일을 바꾸어 써서 앞 발견사항이 사라진다 [28][29].
같은 경로를 다른 `case_id`로 열면 저장 함수가 앞 사건의 항목을 새 사건의 호출 기록 파일에 합쳐 쓴다 [28][29].
`misc.record_finding`처럼 디스크 항목을 다시 읽는 도구를 부른 뒤에는 앞 사건의 발견사항이 지금 사건의 발견사항으로 읽힌다 [30].
이 두 번째 경로는 코드로만 따라갔고 실행하지 않았다.

### D05.07 가설 지지·반박 근거 연결

**구현.** `reason.hypothesize`는 가설을 발견사항과 따로 모델 호출 항목으로 남기고 서버가 `H0001` 형식의 `hypothesis_id`를 매긴다 [31][32].
가설 항목에는 근거 호출 `input_call_ids`, 가설 종류 `hypothesis_kind`, 다투는 주체 `contested_principals`가 들어간다 [32].
발견사항은 `tested_hypothesis_id`로 가설을 가리키고 `claim.resolves`의 `confirmed`·`refuted`로 지지와 반박을 적는다 [10][11].
`misc.record_disposition`은 가설을 대상으로 `refuted`·`excluded`·`evidence_unavailable` 사유와 근거 호출 ID를 담은 처분을 남긴다 [33].
가설이 닫혔는지는 D05.08에서 본다.

**예외.** `tested_hypothesis_id`가 실제 가설 ID인지는 검사하지 않는다 [34].
비어 있지 않은 아무 문자열이면 가설 게이트를 지나 그대로 저장된다 [34][10].

### D05.08 가설 상태 관리

**구현.** 이 방식은 `reason.pre_report_check`의 가설 점검에 있다 [35].
이 점검은 D05.07의 발견사항 연결과 처분으로 가설마다 닫혔는지를 서버 규칙으로 계산한다 [35].
다투는 주체가 판정되지 않았거나 `distinct_principal` 가설이 닫히지 않았으면 보고를 막고 그 밖의 열린 가설은 경고로 남긴다 [35].
가설의 상태는 따로 저장하지 않고 점검할 때마다 다시 계산하므로 상태가 바뀐 시각은 남지 않는다 [35].

### D05.09 미해결 반론을 보고에 전달

**구현.** `misc.write_final_report`는 마지막 `reason.pre_report_check`에 남은 미해결 검토 반론을 보고서 끝의 "Reviewer limitations and unresolved objections" 절로 붙인다 [36][37].
검토가 정해 둔 횟수를 넘긴 뒤에도 열린 반론과 한계로 판정된 반론이 이 목록에 들어간다 [38].
이 절은 모델이 쓴 본문과 관계없이 늘 붙는다 [37].
다투는 주체 가운데 판정되지 않은 것은 점검 결과의 인벤토리에 `open`이나 `inventory` 상태로 남고 보고서의 "Evidence registry inventory" 절에 실린다 [39][40].
닫히지 않은 일반 가설은 점검 경고에만 있고 보고서에는 싣지 않는다 [35][36].

**예외.** 인벤토리 절은 모델이 쓴 본문에 "registry inventory"라는 말이 있으면 붙이지 않는다 [40].

### D05.10 판정·분류 값 기준 대조

**구현.** `misc.submit_finding`은 `confidence`가 CONFIRMED·LIKELY·SUSPECTED·UNCONFIRMED 가운데 하나가 아니면 거부한다 [41].
`reason.hypothesize`의 `hypothesis_kind`도 정해 둔 값이 아니면 거부한다 [42].
이 두 검사의 기준은 코드에 정한 값 목록이다 [41][42].

분류 값인 ATT&CK 기법 ID는 서버가 읽는 MITRE 기법 표와 대조한다 [43][44].
`misc.record_finding`의 게이트 `evidence_strength`와 `misc.submit_finding`의 사전 점검은 둘 다 `mitre_technique_validation` 검사를 부른다 [45].
이 검사는 발견사항 설명에서 기법 ID 모양의 값을 모두 뽑고 claim의 `techniques`와 합친다 [43].
`techniques`에 기법 ID 모양이 아닌 값이 있으면 거부한다 [43].
모은 ID는 `correlate.mitre_validate`로 표에서 찾고 표에 없는 ID가 있으면 거부한다 [44].
`misc.record_ioc`도 지표의 `techniques`를 같은 표에서 찾고 없으면 거부한다 [46].
기준 표는 환경변수 `TRUDI_MITRE_TABLE`이 가리키는 파일이고 값이 없으면 `~/cases/.common/mitre_techniques.json`이다 [47].
이 표의 고정과 버전 확인은 T05에서 본다.

**예외.** `misc.record_finding`과 `misc.record_agent_message`의 `findings`는 `confidence`를 대문자로 바꿔 게이트에 넘길 뿐 네 값과 대조하지 않는다 [48].
등급을 보는 게이트는 등급이 CONFIRMED·LIKELY·UNCONFIRMED 가운데 하나일 때만 돌아서 빈 값이나 목록 밖 값은 받은 그대로 저장된다 [49][10].

`mitre_technique_validation`은 표의 기법 수가 600개보다 적으면 표에 없는 ID를 거부하지 않는다 [50].
그 ID는 `unvalidated` 표시와 함께 `validated_techniques`에 넣고 기록을 진행한다 [50].
저장소의 기법 표 `cases/.common/mitre_techniques.json`에는 기법이 486개 있고 `install.sh`는 `~/cases/.common/`에 표가 없으면 이 파일을 복사한다 [51].
그래서 이 표를 쓰는 설치에서는 발견사항 경로가 표에 없는 기법 ID를 거부하지 않는다 [50][51].
표 파일이 없거나 JSON으로 읽히지 않으면 기법 수가 0이 되어 같은 조건으로 통과한다 [52][50].
`correlate.mitre_validate`를 불러오지 못하면 검사 없이 통과한다 [53].
`misc.record_ioc`에는 표 크기 조건이 없어 발견사항 경로가 `unvalidated`로 통과시킨 ID를 지표 기록에서는 거부한다 [46][50].

    """Return (budget_granted, dair_cid) from the most recent dair_call in the
