# D02 파생물 추적

### D02.01 ID·경로 참조

**구현.** 이 방식은 호출마다 남기는 출력 텍스트 파일, 실행기 항목에 경로가 적힌 출력 파일, 발견사항, 최종 보고서에 적용된다.
`.tool_output` 파일 이름은 그 출력을 만든 호출 ID이고 호출 기록 항목의 `stdout_path`에 그 경로가 들어간다 [1].
같은 항목의 `cmd`에는 실행한 명령이 들어가 외부 도구가 읽은 증거와 입력 파일의 경로가 명령 인자로 남는다 [2].
`run_with_output_file`과 작업 수집은 항목의 `output_path`에 출력 파일이나 폴더의 경로를 넣는다 [3].
다른 도구가 `output_dir`로 받은 폴더에 쓴 파일은 항목의 `cmd` 인자로만 가리킨다 [2].

실행기 항목의 `input_call_ids`에는 마지막 `dair_assess` 호출 ID 하나만 들어간다 [4].
서버 안 파이썬 도구가 스스로 호출 기록을 남기지 않으면 미들웨어가 `<py>:<tool_name>` 항목을 만들고 그 `input_call_ids`에도 같은 값을 넣는다 [5].
어느 항목에도 그 도구가 입력으로 읽은 앞 파생물의 호출 ID는 들어가지 않는다 [4][5].
`read.output`도 읽은 파일을 `cmd`의 경로로만 가리킨다 [6].

발견사항이 근거 호출 ID를 필드로 남기는 방식은 D05.03에서 본다.
발견사항의 `input_call_ids`와 `linked_call_id`는 호출 기록에 있는 ID여야 받으므로 그 ID로 호출 기록 항목을 찾을 수 있다 [7].
검토 도구와 evidence packet을 만드는 코드는 인용한 호출 ID의 항목에서 `output_path`, `cmd`에 적힌 출력 경로, `stdout_path`의 파일을 차례로 찾아 읽는다 [8][9].
그런 파일이 없으면 항목에 남은 표준 출력 발췌를 읽는다 [8].
그래서 발견사항의 근거 호출 ID에서 보관한 출력 파일까지 서버 코드가 이어 간다.
수정한 발견사항은 `supersedes`로 앞 항목을 가리키고 앞 항목에는 `superseded_by`가 붙는다 [10].

`misc.write_final_report`는 현재 발견사항마다 `finding_id`와 호출 ID를 보고서 본문에 적는다 [11].
보고서를 쓴 호출의 항목은 `cmd`에 보고서 경로만 넣고 `output_path`와 `input_call_ids`는 넣지 않는다 [12].

발견사항에서 근거 호출로 가는 ID는 있지만 호출에서 그것을 근거로 삼은 발견사항을 찾는 모델 도구는 찾지 못해 D02.04에는 연결하지 않았다.
파일 파생물 곁에 manifest를 두지 않아 D02.03에도 연결하지 않았다.

**한계.** 참조가 다른 대상을 가리키게 되는 경로가 있다.
사용자 CLI `tools/trudi_reset.py`를 `--purge-outputs` 없이 실행하면 호출 기록 파일만 백업 폴더로 옮기고 호출 ID 카운터를 1로 되돌린다 [13].
같은 사건 폴더에서 다시 시작한 호출은 같은 ID를 다시 받아 `.tool_output/<호출 ID>.txt`를 바꾸어 쓰므로 옮긴 호출 기록의 `stdout_path`가 새 출력을 가리킨다 [13][1].
같은 `output_path`로 `run_with_output_file`을 다시 부르면 앞 항목의 `output_path`도 새 파일을 가리킨다 [3].
`net.http_session_inventory`·`net.pcap_identity_timeline`의 tcpdump 항목은 읽은 뒤 지운 `/tmp` 파일을 `output_path`로 가리킨다 [14].

### D02.02 입출력 해시 연결

**구현.** 이 방식은 검토를 거쳐 기록하는 CONFIRMED·LIKELY 발견사항에 적용된다.
`reason.evaluate_finding`과 `misc.submit_finding`은 인용한 호출의 출력을 읽어 그 바이트의 SHA-256을 evidence packet의 `output_sha256`에 넣는다 [9].
출력이 64 MiB를 넘으면 앞부분만 읽어 해시하고 `scan_truncated`를 적는다 [9].
검토가 성공하면 발견사항의 설명·claim·인용 호출 ID를 묶은 해시 `binding`과 packet ID를 검토를 통과했다는 기록 `review_receipt`에 담아 검토 항목에 남긴다 [15][16].
CONFIRMED·LIKELY 발견사항은 기록하려는 내용의 `binding`이 `review_receipt`의 값과 같아야 기록되고 항목에 그 검토의 호출 ID가 들어간다 [17][18].
`misc.submit_finding`으로 기록하면 발견사항 항목에 `evidence_packet_id`와 요청 해시 `submission_request_hash`도 들어간다 [18].
SUSPECTED·UNCONFIRMED 발견사항, 보고서, 출력 파일에는 이런 해시 연결이 없다.

**한계.** 검토 항목에 `receipt_required`와 `review_receipt`가 둘 다 없으면 판정이 SUPPORTED라는 것만으로 CONFIRMED·LIKELY 발견사항이 기록되어 해시 연결이 생기지 않는다 [19].
이 서버의 `reason.evaluate_finding`은 모든 검토 항목에 `receipt_required`를 붙이므로 이런 항목은 다른 코드가 쓴 호출 기록 파일을 이어 쓸 때 생긴다 [16].

### D02.05 여러 단계 파생 관계 기록

**구현.** 이 방식은 검토 호출이 앞 도구의 출력을 입력으로 쓸 때 적용된다.
D02.02와 같은 evidence packet이며 이 상세는 인용 호출 ID(부모)와 그 출력의 `output_sha256`·파일 버전(중간 입력의 버전)을 근거로 삼는다 [9][20].
`reason.evaluate_finding`과 `misc.submit_finding`이 만드는 evidence packet은 인용한 호출마다 호출 ID, 읽은 파일 경로, `output_sha256`을 담는다 [9].
읽은 파일과 출력 폴더의 버전(장치·inode·크기·수정 시각·변경 시각)과 인용한 항목의 내용 digest도 함께 담는다 [20][21].
발견사항은 `gated_by_evaluate_call_id`로 그 검토 항목을 가리키므로 발견사항에서 검토를 거쳐 인용 출력의 버전까지 이어진다 [18].
검토가 아닌 도구 호출은 앞 파생물을 읽어도 그 호출 ID나 해시를 남기지 않는다 [4][6].
`net.http_session_inventory`·`net.pcap_identity_timeline`의 가공 항목만 `input_call_ids`에 원래 tcpdump 호출 ID를 넣는다 [14].

**한계.** D02.02의 한계와 같이 `receipt_required`와 `review_receipt`가 없는 검토 항목으로 기록한 발견사항에는 인용 출력의 버전이 남지 않는다 [19].

def receipt_matches(ctx, review):
    if review.get('success') is not True or review.get('review_pending'):
        return False
    packet, receipt = review.get('evidence_packet'), review.get('review_receipt')
    if not packet or not receipt or review.get('verdict') != 'SUPPORTED':
        return False
    ids = cited_ids({'input_call_ids': ctx.input_call_ids, 'linked_call_id': ctx.linked_call_id,
                     'claim': ctx.claim})
    # Context/review call IDs may appear in legacy lineage, but cannot stand in
    # for evidence IDs in the exact binding.
    ids = [cid for cid in ids if (ctx.idx.by_call_id.get(cid) or {}).get('type') == 'tool_call']
    binding = material_binding(ctx.description, ctx.claim, ids, getattr(ctx, 'supersedes', 0))
    return binding == receipt.get('binding') and packet_current(ctx.log, packet)
