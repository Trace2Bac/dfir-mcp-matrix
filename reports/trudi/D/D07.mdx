# D07 발견사항 근거 검증

### D07.01 근거 참조 존재 확인

**구현.** 이 방식은 발견사항을 기록하는 `misc.record_finding`·`misc.submit_finding`, 발견사항을 거두는 `misc.retract_finding`, 단서를 발견사항 없이 정리하는 `misc.record_disposition`에 있다 [1][2][3][4].
네 도구는 인용한 호출 ID가 모두 호출 기록에 있어야 받는다 [1][2][3][4].
`misc.record_finding`의 `lineage_required` 게이트가 대조하는 ID 집합은 호출 기록의 모든 항목이라서 실패한 호출, 모델 호출, 다른 발견사항의 ID도 받는다 [1].
CONFIRMED 발견사항은 `linked_call_id`를 0으로 둘 수 없다 [5].
`agent_authored_source` 게이트는 인용한 호출이 Write·Edit 항목이거나 모델이 쓴 파일을 읽은 호출이면 등급과 관계없이 거부한다 [6].
`misc.submit_finding`은 근거 묶음을 만들 때 인용한 `tool_call`이 성공하지 않았으면 거부한다 [2].
`misc.record_disposition`은 증거에 관한 사실을 주장하는 이유에는 성공한 증거 도구 호출 ID를 요구하고 그 밖의 이유에는 인용한 ID가 기록에 있는지만 본다 [4][7].
증거 도구 호출인지는 `is_evidence_tool_call`이 정하고 성공한 호출 가운데 명령 문자열이 `<py>:misc_`·`<py>:reason_`·`<py>:dair_`·`<py>:accuracy_`·`<py>:monitor_`·`<py>:coverage_`·`<py>:attribution_`으로 시작하는 기록만 뺀다 [8].
서버 프로세스 안에서 실행되는 도구가 성공하면 미들웨어가 그 호출을 명령 문자열 `<py>:<도구 이름>`으로 기록한다 [9].
그래서 참조 지식을 조회하는 `correlate.mitre_validate`와 외부 위협 정보를 조회하는 `enrich.vt_lookup_hash`·`enrich.vt_lookup_ip`·`enrich.vt_lookup_domain`의 호출도 증거 도구 호출로 세어진다 [8][9].
`misc.knowns_pattern_generate`는 모델이 준 이름·호스트·해시 목록으로 검색 패턴만 만들고 증거를 읽지 않는다 [10].
그런데 이 도구는 `<py>:` 접두어가 없는 명령 문자열 `misc.knowns_pattern_generate <유형> n=<개수>`로 성공 항목을 스스로 남기므로 이 호출도 증거 도구 호출로 세어진다 [10][8].
`misc.record_ioc`는 `evidence_call_ids`가 모두 증거 도구 호출이어야 지표를 받으므로 증거를 읽지 않는 이런 호출만 인용해도 지표가 기록된다 [11].
이 경로는 코드로만 확인했고 실행하지 않았다.

**한계.** `misc.record_finding`에서 `input_call_ids`를 비우면 서버가 최근 30개 항목 가운데 마지막 `tool_call`·`reason_call` 5개의 ID로 채우고 발견사항에 `lineage_inferred`만 표시한다 [12][13].
이렇게 채운 ID는 늘 기록에 있으므로 존재 대조를 통과하지만 모델이 인용한 근거가 아니다 [1][12].
호출 기록 항목이 5개보다 적으면 `input_call_ids`가 비어도 `lineage_required`를 통과한다 [14].

### D07.02 도구 출력과 내용 대조

**구현.** 이 방식은 `misc.submit_finding`의 사전 점검과 `misc.record_finding`이 응답에 붙이는 `lineage_content_note`에 있다 [15][16].
`misc.submit_finding`은 인용한 호출의 저장된 출력에서 발견사항 글과 claim의 낱말이 든 행을 골라 근거 묶음을 만든다 [15].
그 묶음에서 고른 행만 이은 글을 근거 글로 넘겨 CONFIRMED·LIKELY 발견사항의 결정적 인용 검사를 다시 실행한다 [17].
인용 검사는 발견사항 글에서 IPv4 주소·해시·ATT&CK 기법 ID·절대 경로·레지스트리 키를 정규식으로 뽑고 하나라도 근거 글에 없으면 거부한다 [18][19].
이 검사에 걸리면 `misc.submit_finding`은 `needs-evidence` 상태와 빠진 값을 돌려주고 모델 검토를 하지 않는다 [17].
산문과 숫자는 대조하지 않는다 [18].
`misc.record_finding`에 모델이 `supporting_evidence`를 직접 주면 같은 인용 검사를 그 글에 대므로 도구 출력과 대조하지 않는다 [19].
`misc.record_finding`은 기록한 뒤 발견사항 글의 같은 종류 값이 인용한 호출의 명령·출력 요약·저장 출력 앞 64KB에 하나도 없으면 `lineage_content_note`를 응답에 싣는다 [16][20].
이 알림은 기록을 막지 않고 발견사항 항목에도 남지 않는다 [21].

**한계.** `lineage_content_note`가 읽는 근거 글에는 모델이 쓴 `supporting_evidence`도 들어간다 [20].
그래서 인용한 호출의 출력에는 없고 모델이 쓴 글에만 있는 값도 맞은 것으로 세어 알림이 나가지 않는다 [16][20].

### D07.03 출처 수·범주로 등급 산정

**구현.** 이 방식은 `misc.record_finding`의 `tier_contract`·`attribution`·`transfer` 게이트와 `tier_contract`와 같은 계산을 미리 돌려주는 `reason.confidence_score`에 있다 [22][23][24].
게이트는 CONFIRMED·LIKELY 긍정 발견사항이 인용한 호출(`input_call_ids`·`linked_call_id`·claim의 전송·수신·세션 호출 ID와 `rule_outs`의 호출 ID)을 모은다 [22].
인용한 호출마다 명령·MCP 도구 이름·출력 글·서버가 붙인 표시로 아티팩트 범주를 정하고 `read.*` 호출에는 그 파일을 만든 앞선 호출의 범주를 더한다 [25][26].
`data/fk/tiering.yaml`은 `act`마다 등급별로 필요한 범주 묶음과 개수를 정한다 [27].
같은 호출 하나가 두 범주를 채우면 독립된 근거로 세지 않는다 [28].
요청한 등급이 범주로 닿는 등급보다 높으면 거부하고 빠진 범주와 그 범주를 만드는 도구를 알린다 [29].
낮게 요청하면 받고 닿는 등급을 응답의 `tier_headroom`으로 알린다 [30].
닿는 등급과 범주, 규칙 이름은 발견사항 항목에 남는다 [31].
`reason.confidence_score`는 모델을 부르지 않고 같은 계산 결과와 다음 등급에 필요한 범주를 돌려준다 [24].
부재 발견사항과 SUSPECTED·UNCONFIRMED 발견사항은 등급 계산을 거치지 않는다 [32].
`misc.record_finding` 설명과 게이트 설명은 이 계산을 CONFIRMED·LIKELY 발견사항이 요청한 등급의 요건으로 적고 게이트 설명은 부재 claim을 계산하지 않는다고 적는다 [33].
`misc.record_finding`에 `supporting_evidence`를 주지 않으면 `confidence_and_citation` 게이트는 같은 설명을 담은 `reason.confidence_score` 호출을 요구하고 그 호출이 매긴 `tier`보다 높은 등급을 거부한다 [34].

`attribution`·`transfer` 게이트는 주장 종류에 맞는 근거 종류를 CONFIRMED·LIKELY의 요건으로 두고 없으면 SUSPECTED로 낮추라고 거부한다 [23].
`principal_attribution_grounding`은 claim이 계정을 사람에게 묶을 때 로그온·세션 근거를 요구한다 [35].
`named_actor_attribution_grounding`은 claim이 계정 없이 핵심 행위의 주체를 사람으로 적을 때 같은 근거를 요구한다 [36].
세션 근거로 먼저 인정하는 것은 `session_binding_call_ids`가 가리키는 항목 가운데 서버가 `session_artifact` 표시를 붙이고 실패하지 않은 호출이다 [37].
그 항목의 명령이 로그온 열거 도구 정규식에 맞아도 인정한다 [37].
인용 근거 글에 `logon`·`rdp` 같은 낱말이 있어도 인정한다 [37][20].
`exfil_channel_grounding`은 `act`가 `egress`이면 `transfer_call_ids`를 요구한다 [38].
`offhost_delivery_grounding`은 `act`가 `delivery`·`possession`이면 `receipt_call_ids`를 요구한다 [39].
두 게이트는 그 ID가 모두 성공한 증거 도구 호출이면 통과시키고 그 호출이 전송·수신 기록인지는 보지 않는다 [38][39][40].
ID가 없거나 증거 도구 호출이 아닌 ID가 있으면 인용 근거 글에서 전송·수신 표시 낱말을 찾는다 [38][39].
`tier_contract`는 이 두 게이트보다 먼저 실행되고 `egress`·`delivery`·`possession`의 CONFIRMED·LIKELY에 `transfer`·`receipt` 범주를 요구한다 [23][17][41].
그래서 무관한 성공 호출만 인용한 전송·수신 주장은 `tier_contract`에서 거부된다 [22][41].

**한계.** typed claim의 `act` 값에는 `privilege_escalation`이 있지만 `data/fk/tiering.yaml`에는 그 `act`의 규칙이 없다 [42][43].
규칙이 없으면 게이트는 등급을 정하지 않고 통과시키므로 `act`가 `privilege_escalation`인 발견사항은 인용한 범주와 관계없이 이 게이트를 지난다 [44].
환경변수 `TRUDI_REQUIRE_TYPED_CLAIMS`를 `0`으로 두면 claim 없이 CONFIRMED·LIKELY를 기록할 수 있고 그때는 `act`가 비어 이 게이트가 등급을 계산하지 않는다 [45][32].
세션 근거의 글 검사는 인용한 호출의 명령·출력과 함께 모델이 `misc.record_finding`에 준 `supporting_evidence`도 읽는다 [20][46].
그래서 모델이 쓴 근거 글에 `logon`·`rdp` 같은 낱말이 있으면 세션 근거를 인용하지 않아도 두 사람 귀속 게이트를 지난다 [37].
명령 정규식 경로는 인용한 호출이 성공했는지 보지 않는다 [37].
`tier_contract`가 세션 범주를 요구하는 `act`는 `attribution`·`logon`뿐이다 [47].
그 밖의 행위의 주체를 사람으로 적은 발견사항은 모델 검토(D07.05) 말고 세션 근거를 따로 요구하는 서버 검사를 거치지 않는다 [47][36].
이 경로들은 코드로만 확인했고 실행하지는 않았다.

### D07.04 교차 확인·반론 검토

**구현.** 이 방식은 `misc.record_finding`의 `interactive_injection_grounding`·`hypothesize_required` 게이트와 `reason.pre_report_check`의 보강 출처·검증 과제 점검에 있다 [48][49][50][51].
`interactive_injection_grounding`은 이동식 매체를 다룬 호출이 기록에 있을 때, 콘솔 세션의 계정 생성이나 지속성 설치를 사람·계정의 행위로 적은 CONFIRMED·LIKELY 발견사항에 키 입력 주입 장치라는 대안을 따진다 [48].
기간을 덮는 장치 설치 목록이 없으면 거부하고 목록이 주입 장치를 표시했으면 그 장치를 증거로 배제해야 받는다 [48][52].
배제는 claim의 `rule_outs`에 증거 도구 호출을 적거나 기간을 덮는 장치 배제 처분을 남기는 것이고 어느 경우든 예약 작업 열거가 먼저 있어야 한다 [52].
`hypothesize_required`는 범주가 있는 CONFIRMED·LIKELY 발견사항에 `tested_hypothesis_id`가 없으면 조사 전체에 `reason.hypothesize` 호출이 하나라도 있어야 받는다 [49].
`reason.pre_report_check`는 CONFIRMED·LIKELY 발견사항의 근거 아티팩트가 혼자서 그 주장을 증명하지 못한다고 지식 자료에 적혀 있으면, 그 자료가 정한 보강 도구의 호출이 호출 기록에 하나도 없으면 보고서를 막는다 [50].
막힌 상태는 보강 도구를 실행하거나 그 발견사항을 SUSPECTED로 낮춰야 풀린다 [50].
`dair.assess`가 낸 검증 과제가 `verified: null`로 남고 그 방법의 도구를 호출한 기록이 없으면 보고서 전 점검이 막는다 [51].
`misc.write_final_report`는 가장 최근 보고서 전 점검이 통과했고 그 뒤 상태가 바뀌지 않았을 때만 보고서를 쓴다 [53].

**한계.** 보강 점검은 호출 기록의 모든 `tool_call` 명령에서 보강 도구의 명령 서명을 찾고 그 호출이 성공했는지 보지 않는다 [54].
그래서 실패한 보강 도구 호출도 보강으로 센다 [54].
`interactive_injection_grounding`은 `rule_outs`에 적은 호출이 모두 증거 도구 호출이면 주입 장치를 배제한 것으로 보고 그 호출이 장치를 다뤘는지는 보지 않는다 [52].
증거 도구 호출 판정(D07.01)으로는 증거를 읽지 않는 `misc.knowns_pattern_generate`나 참조 지식 조회 호출도 이 조건을 채운다 [52][8].
보강 점검과 검증 과제 점검은 예외가 나면 표준 오류에 경고만 쓰고 보고서를 막지 않는다 [50][51].

### D07.05 모델 검토

**구현.** 이 방식은 CONFIRMED·LIKELY 발견사항을 기록하는 `misc.record_finding`, 모든 등급을 받는 `misc.submit_finding`, 보고서를 쓰기 전에 `reason.synthesize`의 검토 결과를 보는 `reason.pre_report_check`에 있다 [55][56][57].
`reason.evaluate_finding`은 서버 안에서 검토 모델을 불러 발견사항의 사실이 인용한 출력 행에 있는지 보고 `SUPPORTED`·`CONTRADICTED`·`UNVERIFIABLE` 가운데 하나로 답하게 한다 [58].
서버는 이 답을 `SUPPORTED`·`CHALLENGED`·`UNCERTAIN`으로 바꿔 기록한다 [59].
근거 묶음이 있으면 판정에 묶음 ID와, 발견사항 글·claim·근거 호출 ID·`supersedes`를 묶은 값을 담은 검토 통과 기록 `review_receipt`를 붙인다 [60].
`confirmed_requires_supported_evaluate` 게이트는 아직 쓰지 않은 `SUPPORTED` 판정의 `review_receipt`가 기록할 글·claim·근거 호출 ID와 맞아야 CONFIRMED·LIKELY를 통과시킨다 [55].
`review_receipt`가 맞지 않거나 판정이 `SUPPORTED`가 아니면 거부한다 [61].
판정 항목은 만들 때부터 `receipt_required`로 표시되므로 모델 호출이 실패한 판정이나 근거 묶음 없이 낸 판정은 기록을 허락하지 못한다 [62][61].
`review_receipt`를 만든 뒤 인용한 호출 항목이나 출력 파일이 바뀌면 `review_receipt`가 맞지 않는다 [63].
`challenge_sticky` 게이트는 같은 발견사항의 앞선 판정이 `CHALLENGED`·`UNCERTAIN`이면, 그 뒤 증거 도구 호출이 없는 한 다시 받은 `SUPPORTED`로도 기록을 받지 않는다 [64].
저장된 출력이 일부만 남아 행을 찾지 못한 판정(`verdict_basis: partial_source`)은 고정하지 않는다 [65].
`misc.submit_finding`은 등급과 관계없이 검토를 부르고 `SUPPORTED`일 때만 `misc.record_finding`으로 기록한다 [56].
`misc.record_finding`으로 SUSPECTED·UNCONFIRMED 발견사항을 기록하면 모델 검토를 거치지 않는다 [55].
`misc.record_finding` 설명은 `SUPPORTED` 판정을 CONFIRMED·LIKELY 발견사항의 요건으로 적는다 [66].

`misc.record_finding`에 `supporting_evidence`를 주지 않은 CONFIRMED·LIKELY 발견사항은 `confidence_and_citation` 게이트의 이전 경로를 거친다 [67].
이 경로는 최근 호출 기록 30개에서 사용자 메시지에 발견사항 설명의 앞 60자가 든 `reason.cite_check` 호출을 찾는다 [68][46].
설명은 소문자로 바꾸고 공백을 하나로 줄여 비교하며 같은 설명의 앞선 발견사항보다 뒤에 있는 호출만 센다 [68].
`reason.cite_check`는 검토 모델을 불러 발견사항의 구체적인 값마다 근거 글에 인용이 있는지 보게 하고 `ALL_CITED`·`UNCITED_CLAIMS_PRESENT`·`INSUFFICIENT_EVIDENCE` 가운데 하나로 답하게 한다 [69].
서버는 이 답을 호출 기록 항목의 `cite_verdict`에 남긴다 [69].
게이트는 판정이 `UNCITED_CLAIMS_PRESENT`나 `INSUFFICIENT_EVIDENCE`이면 거부하고 통과하면 그 호출 ID를 발견사항의 `gated_by_cite_check_call_id`에 남긴다 [70][71].
`supporting_evidence`를 주면 이 경로 대신 결정적 인용 검사(D07.02)를 쓴다 [19].
`misc.submit_finding`은 서버가 만든 근거 묶음 글을 `supporting_evidence`로 넘기므로 묶음에 고른 행이 있으면 이 경로를 거치지 않는다 [17][15].

발견사항 글과 근거 글은 `FINDING:`·`SUPPORTING EVIDENCE:` 제목 아래 머리말 없이 들어간다 [74].

`reason.synthesize`는 서버 안 검토 모델이 현재 발견사항을 함께 읽고 낸 답을 typed issue로 바꿔 호출 기록에 저장한다 [75].

코드 주석은 끝내 만족하지 않는 검토 모델이 보고서를 막지 않도록 회차를 제한한다고 적는다 [57].

**한계.** `TRUDI_SYNTH_ROUND_CAP`을 `0`으로 두면 회차 수를 상한과 비교하는 `rounds >= SYNTH_ROUND_CAP`이 늘 참이 된다 [76][57].

def deterministic_cite_check(finding: str, supporting_evidence: str) -> dict:
    """Verify every citable artifact value in `finding` appears in
    `supporting_evidence`. Mirrors reason.cite_check's verdict vocabulary."""
    evidence = (supporting_evidence or "").lower()
    claims = extract_claims(finding)

    if not claims:
        # No concrete artifact claims to verify (prose-only finding).
        return {"verdict": "ALL_CITED", "cited_claims": [], "uncited_claims": []}

    if not evidence.strip():
        return {
            "verdict": "INSUFFICIENT_EVIDENCE",
            "cited_claims": [],
            "uncited_claims": [v for _, v in claims],
        }

    cited, uncited = [], []
    for _kind, value in claims:
        if value.lower() in evidence:
            cited.append(value)
        else:
            uncited.append(value)

    verdict = "UNCITED_CLAIMS_PRESENT" if uncited else "ALL_CITED"
    return {"verdict": verdict, "cited_claims": cited, "uncited_claims": uncited}

    """Concatenated evidence text a grounding gate may inspect for a required
    marker: the agent-supplied ``supporting_evidence`` plus the ``cmd`` and
    ``stdout_excerpt`` of every entry referenced by ``linked_call_id`` and
    ``input_call_ids``. Used by grounding gates (principal_attribution_grounding,
    exfil_channel_grounding) that demand the *evidence* — not merely the
    description prose — carry a specific artifact marker."""

    cids = list(ctx.input_call_ids or [])
    if ctx.linked_call_id:
        cids.append(ctx.linked_call_id)

        # past the 600-char excerpt still grounds the finding.

        if sp:
            try:
                with open(sp, "r", errors="replace") as fh:
                    parts.append(fh.read(_SIDECAR_READ_CHARS))
            except OSError:
                pass
    return " \n ".join(p for p in parts if p)

def _independent(chosen: list[str], origins: dict) -> bool:
    """True when every chosen class can be assigned its OWN origin call
    (distinct representatives) — one tool run backing two classes is one
    artifact, not two. Classes with no origin info count as independent."""
    if not origins:
        return True
    match: dict[int, str] = {}                         # origin -> class

    def _try(cls: str, seen: set) -> bool:
        for o in origins.get(cls) or {f"free:{cls}"}:
            if o in seen:
                continue

def tasks_examined(entries, idx=None) -> bool:
    """True when the trace shows a scheduled-task enumeration ran, OR a typed

    for e in _tool_calls(entries):
