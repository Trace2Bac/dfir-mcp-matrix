# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 외부 프로그램을 실행하는 공통 실행기 `run`, `run_with_progress`, `run_with_output_file`은 종료 코드를 도구별 정책에 대어 성공을 정한다 [1].
기본 정책은 0만 성공이다 [1].
`clamscan`, `ngrep`, `grep`, `mraptor`는 결과를 뜻하는 0이 아닌 코드도 성공으로 두고 그 뜻을 `exit_meaning`으로 붙인다 [2].
SSH로 단말 명령을 실행하는 `ssh_run`, 대응 조치를 실행하는 `ssh_run_write`, Velociraptor CLI를 실행하는 `_velo_run`도 종료 코드가 0일 때만 성공으로 정한다 [3].
분리 실행 작업은 셸이 파일에 남긴 종료 코드가 0일 때만 성공이다 [4].

**예외.** `misc.evtx_filter`는 `evtx_dump.py`의 종료 코드를 성공 판단에 쓰지 않고 이벤트를 하나라도 읽었으면 성공으로 정한다 [5].
도중에 비정상 종료한 실행도 읽은 이벤트가 있으면 성공이고 응답에는 종료 코드가 없다 [5][6].
`live.process_details`는 원격 셸 명령을 `echo`로 끝내고 `cat`의 오류를 버리므로 없는 PID를 주어도 종료 코드가 0이다 [7].
`live.users`처럼 여러 명령을 `sh -c`로 이은 도구는 마지막 명령의 종료 코드로만 성공을 정한다 [8].

### T08.02 시간 제한·종료 신호 처리

**구현.** 외부 실행의 시간 제한은 환경변수로 정하고 기본값은 일반 300초, Volatility 600초, Plaso 21,600초다 [9].
`run`과 `run_with_output_file`은 `subprocess.run`의 시간 제한을 넘으면 `timed_out`을 참으로 두고 실패를 돌려준다 [10].
`run_with_progress`는 시간 제한을 넘으면 프로세스를 끊고 그때까지 받은 진행 줄만 남긴 실패를 돌려준다 [11].
실행기는 시간 초과된 실행을 다시 실행하지 않는다 [12].
분리 실행 작업은 coreutils `timeout`으로 감싸 종료 코드 124를 시간 초과로 정하고 그때까지 만든 파일 수를 `partial_output`으로 싣는다 [4][13].
SSH 실행과 Velociraptor 실행도 시간 제한을 넘으면 `timed_out`을 참으로 둔다 [14].
`hash.file`과 `reason.*` 도구처럼 서버 안에서 오래 도는 도구는 감시 스레드로 시간 제한을 둔다 [15].
`misc.batch_run`, `velo.collect_artifact`, `misc.evtx_filter`, `strings.grep`은 모델이 시간 제한 값을 인자로 준다 [16].

**예외.** `misc.evtx_filter`는 `evtx_dump.py`의 출력 줄을 받을 때마다 마감 시각을 보므로 출력 없이 멈춘 프로세스는 끊지 못한다 [17].
`strings.grep`는 출력 16,384줄마다 마감 시각을 보므로 같은 경우에 끊지 못한다 [18].
감시 스레드 시간 제한은 시간이 지나면 실패를 돌려주지만 작업 스레드는 멈추지 않고 계속 돈다 [15].

### T08.03 오류·출력 내용 판독

**구현.** `ewf.verify`는 `ewfverify`의 출력에서 판정 줄과 `Verify completed`를 찾아 검증을 마쳤는지 정한다 [19].
판정이 있으면 종료 코드와 관계없이 실행을 성공으로 두고 `verified`와 `status`로 일치와 불일치를 가른다 [19].
판정 줄이 없으면 `verified`를 비우고 `status: error`를 붙인다 [19].
EZ Tools 실행은 종료 코드가 0이어도 출력에 .NET의 처리되지 않은 예외 문구가 있으면 실패로 바꾼다 [20].
`misc.srum_export`는 `esedbexport`가 성공해도 표를 하나도 쓰지 못했으면 실패로 바꾼다 [21].
`ez.pecmd`는 PECmd 출력의 플랫폼 거부 문구를 읽어 대체 파서로 넘어간다(T07.06) [22].
`read.mail`은 메일 저장소에서 메시지를 하나도 읽지 못하면 한 번 더 읽고 그래도 없으면 응답에 `warning`을 붙인다 [23].
Volatility, Plaso, Sleuth Kit, 카빙 도구의 실행은 출력을 해석하지 않고 종료 코드만 본다.

### T08.04 입력별 부분 완료 집계

**구현.** `ez.recmd_batch`는 기본값 `per_hive=True`에서 하이브마다 RECmd를 따로 실행하고 하이브별 성공 여부와 `hives_ok`·`hives_failed` 수를 싣는다 [24].
`ez.pecmd`의 대체 파서는 Prefetch 파일마다 성공과 실패를 가르고 `files_seen`, `files_parsed`, `parse_failures`를 싣는다 [25].
`yara.scan_directory`는 파일마다 검사하고 검사한 파일 수 `scanned`, 일치한 파일 수 `hits`, 파일별 오류 `errors`를 싣는다 [26].
`misc.batch_run`은 명령마다 결과를 담지만 개수는 세지 않고 모두 성공했는지만 정한다 [27].

**예외.** `ez.recmd_batch`는 하이브 하나라도 성공하면 `success`를 참으로 둔다 [24].
그래서 일부 하이브가 실패해도 전체 상태는 성공이고 실패한 하이브 수는 `hives_failed`에만 실린다 [24].
`per_hive`를 거짓으로 주면 RECmd를 `-d`로 한 번 실행하고 하이브별 성공과 실패를 세지 않는다 [28].
`yara.scan_directory`는 오류 목록을 50개까지만 싣고 전체 오류 수는 싣지 않는다 [26].
`max_files`를 넘는 파일은 검사하지 않고 응답에 그 수를 적지 않는다 [26].
모든 파일에서 오류가 나도 `success`는 참이다 [26].

### T08.05 비동기 최종 상태 조회

**구현.** 미들웨어는 오래 걸리는 도구를 서버 안 배경 작업으로 돌리고 정해 둔 시간 안에 끝나지 않으면 작업 ID와 `queued` 또는 `running` 상태를 돌려준다 [29].
배경 작업으로 돌릴 도구는 `BACKGROUND_ALWAYS`·`BACKGROUND_IF_SLOW` 목록과 `vol_` 이름으로 정한다 [30].
`misc.job_status`는 서버 안 작업이면 진행 중, 취소, 예외, 완료 상태를 돌려주고 완료면 도구 결과의 `success`를 그대로 싣는다 [31].
서버를 다시 띄우면 서버 안 작업은 사라지고 `misc.job_status`는 그 작업 ID를 `unknown`으로 답한다 [31][32].
`net.tcpxtract_streams`는 tcpxtract를 셸로 분리 실행하고 `misc.job_status`는 종료 코드 파일이 생길 때까지 `running`과 지금까지 만든 파일 수를 돌려준다 [32][33].
종료 코드 파일이 생기면 결과를 한 번만 모아 호출 기록에 남긴다 [4].

**예외.** 분리 실행 작업의 상태는 종료 코드 파일로만 정하고 저장한 프로세스 번호로 살아 있는지 보지 않는다 [32][34].
셸이 종료 코드를 쓰기 전에 끝나면 `misc.job_status`는 그 작업을 계속 `running`으로 돌려준다 [32].
`install.sh`는 `requirements.txt`로 Python 의존성을 설치하고 `requirements.txt`는 FastMCP를 `fastmcp>=3.2.0`으로만 적는다 [35].
그래서 FastMCP 4.0.0이 나온 2026-08-31 뒤에 새로 설치하면 4.x가 설치된다 [35].
미들웨어는 작업을 등록한 뒤 작업 ID를 담은 응답을 만들려고 `fastmcp.tools.tool`에서 `ToolResult`를 불러온다 [36].
FastMCP 3.4.7은 이 옛 모듈 이름을 남겨 두지만 4.0.0부터는 남겨 두지 않으므로 4.x에서는 이 불러오기가 실패한다 [36].
이때 작업은 등록되어 계속 돌지만 호출은 작업 ID를 돌려주지 못하고 오류로 끝난다 [36].

### T08.07 수집 작업의 시작·종료·취소 상태 추적

**구현.** 이 방식은 Velociraptor 수집(flow)에 있다 [37].
`velo.collect_artifact`는 단말에 아티팩트 수집을 시작하고 flow ID를 돌려준다 [37].
`velo.wait_for_flow`는 정해 둔 간격으로 Velociraptor의 `flows()`를 조회해 상태가 `FINISHED`나 `ERROR`가 되면 그 상태를 `final_state`로 돌려준다 [38].
기다리는 시간을 넘으면 마지막으로 본 상태를 담은 실패를 돌려준다 [38].
`monitor.baseline_capture`는 `final_state`가 `FINISHED`가 아니면 기준선 만들기를 멈춘다 [39].
수집을 취소하는 도구는 없다.

**예외.** `velo.wait_for_flow`는 flow가 `ERROR`로 끝나도 조회가 성공했으면 `success`를 참으로 둔다 [38].
`velo.get_collection_results`는 flow 상태를 보지 않고 결과를 읽으므로 진행 중이거나 실패한 flow의 일부 결과도 성공으로 돌려준다 [40].
`monitor.baseline_capture`는 `velo.get_collection_results`가 실패해도 빈 결과로 기준선을 만든다 [39].

### T08.08 라이브러리 예외를 실패로 구별

**구현.** 미들웨어는 도구가 잡지 못한 예외를 받아 호출 기록에 실패 항목과 예외 문구를 남기고 `ToolError`로 바꿔 돌려준다 [41][42].
`yara.*` 도구는 yara-python이 낸 예외를 잡아 `success: false`와 예외 문구를 돌려준다 [43].
`yara.scan_directory`와 `ez.pecmd`의 대체 파서는 파일마다 예외를 잡아 그 파일을 실패 목록에 넣는다 [25][26].

**예외.** `read.mail`이 쓰는 메일 저장소 읽기는 `.eml` 파일이나 mbox 파일을 읽다가 예외가 나면 그 파일을 건너뛰고 건너뛴 수를 세지 않는다 [44].
메일 저장소가 mbox 파일 하나이면 예외가 난 곳에서 읽기를 끝낸다 [44].
pffexport 항목 폴더를 메시지로 바꾸지 못하면 그 항목도 표시 없이 빠진다 [45].

def _apply_exit_policy(result: dict, returncode: int,
                       success_codes, exit_meanings) -> None:
    """Map a returncode to success per the wrapper's declared policy
    (default: only 0 succeeds) and stamp the tool-specific meaning."""
    result["exit_code"] = returncode
    codes = success_codes if success_codes is not None else frozenset({0})
    result["success"] = returncode in codes
    meaning = (exit_meanings or {}).get(returncode)
    if meaning:
        result["exit_meaning"] = meaning

    without a native SQLite.Interop on Linux): the run parsed nothing, so it

async def _run_as_job(jobs, mode: str, tool_name: str, args: dict, invoke):
    """Run a long tool as an in-process background task. Returns ("done",
    result) when it finishes within the inline wait (a short run stays a
    normal call), else a job handle. The task is created while this call's
    context (tool identity) is set, so it logs exactly as a synchronous run."""
    started = {"flag": False}
    job_id = {"id": None}

    async def body():
        async with jobs.slots():
            started["flag"] = True
            if job_id["id"]:
                jobs.mark_state(job_id["id"], "running")
            return await invoke(True)

    task = asyncio.create_task(body())
    wait = 0 if mode == "always" else jobs.INLINE_WAIT
    if wait > 0:
        await asyncio.wait({task}, timeout=wait)
    if task.done():
        return ("done", task.result())          # re-raises a ToolError as before
    jid = jobs.register_task(tool_name, task, _arg_shapes(args))
    job_id["id"] = jid
    status = "running" if started["flag"] else "queued"
    jobs.mark_state(jid, status)
    handle = {"success": True, "status": status, "job_id": jid, "tool": tool_name,
              "hint": (f"BACKGROUND JOB {jid} ({status}): {tool_name} is still running and "
                       f"no longer blocks this turn. Continue with other work and poll "
                       f"misc.job_status(job_id='{jid}'); the finished result carries the "
                       f"citable _trudi_call_id. Up to {jobs.MAX_CONCURRENT} jobs run at once.")}

@output_safe
def get_collection_results(
    client_id: str,
    flow_id: str,
    artifact: str,
) -> dict:
    """Fetch rows produced by a completed flow's artifact source.

    Call after `wait_for_flow` returns FINISHED. The artifact name must
    match what was collected (e.g. "Linux.Sys.Pslist").
    """
    if not flow_id.startswith("F."):
        return {"success": False, "error": f"flow_id must look like 'F.xxx', got {flow_id!r}"}
    res = _velo_query(
        f"SELECT * FROM source("
        f"client_id={json.dumps(client_id)}, "
        f"flow_id={json.dumps(flow_id)}, "
        f"artifact={json.dumps(artifact)}"
        f")",
    )
    if res["success"]:
        res["rows"] = _parse_jsonl(res["stdout"])
    return res

def _trace_exception(tool_name: str, exc: Exception, elapsed: float,
                     args: dict | None = None) -> None:
    tb = traceback.format_exc()
    # The exception MESSAGE first (a traceback head tells the auditor nothing
    # about WHICH field failed), then arg names/types, then the traceback tail.
    msg = f"{type(exc).__name__}: {str(exc)[:700]}"
    shapes = _arg_shapes(args)
    head = (f"Unhandled {msg} in {tool_name}"
            + (f" | args: {shapes}" if shapes else "")
            + f"\n--- traceback tail ---\n{tb[-1500:]}")
    try:
        from core.execution_log import log
        log.record_tool_call(
            cmd=f"<py>:{tool_name}",
            success=False,
            truncated=False,
            retries=0,
            exit_code=-1,
            stderr=head[:4096],
            elapsed_seconds=elapsed,
            input_call_ids=_parent_cids(),
            gate="input_validation" if _is_input_validation(exc) else "",
        )
