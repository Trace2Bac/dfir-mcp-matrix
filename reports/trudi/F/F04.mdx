# F04 발견사항·결론 기록 관리

### F04.01 자유 노트

**구현.** `misc.record_agent_message`와 도구 호출의 `_note` 인자는 모델이 쓴 해석 글을 `investigation_narration` 항목으로 남긴다 [1][2].
항목에는 글과 서버가 채운 시각, 모델이 준 `input_call_ids`가 들어가고 판정 필드는 없다 [1].
`input_call_ids`가 호출 기록에 있는지는 검사하지 않는다 [1].
사실 주장은 같은 도구의 `findings` 인자로 따로 받아 `misc.record_finding`과 같은 게이트를 거친다 [3].

`misc.record_curiosity_probe`는 모델이 작업 지시 밖에서 고른 탐색의 이유를 `curiosity_probe` 항목으로 남긴다 [4].
항목에는 근거 문장 `probe_rationale`, 그 탐색을 이끈 가설 ID `seeded_by`, 서버가 채운 시각이 들어가고 판정 필드는 없다 [4].
`input_call_ids`를 주지 않으면 마지막 `dair.assess` 호출 ID로 채우고 실제로 실행한 읽기 도구 호출과는 묶지 않는다 [4].
기록 전에 최근 30개 항목 가운데 마지막 `dair_call`이 준 `curiosity_budget`을 읽고 그 뒤의 `curiosity_probe` 항목 수가 이 값 이상이면 거부한다 [4][5].
근거 문장이 비어 있어도 거부한다 [6].
이 검사는 `misc.record_curiosity_probe`만 부르므로 기록 수만 제한하고 분석 도구 실행은 제한하지 않는다 [6].
`misc.record_self_correction`은 `trigger`·`prior_belief`·`new_belief`·`evidence`·`linked_call_id`를 `self_correction` 항목으로 남긴다 [7].
`trigger`가 `dair_max_pass_cap`일 때만 따로 검사하고 다른 값은 목록과 대조하지 않는다 [7].
이 항목은 모델이 쓴 글이며 발견사항이나 가설의 앞 값을 서버가 남기는 이력과 다르다 [7].
모델이 `reason.synthesize`의 `findings`로 넘기는 조사 서술은 따로 항목이 되지 않는다 [8].
이 서술은 검토 모델에게 보낸 사용자 메시지의 일부로 그 모델 호출 항목의 `inputs.user_message`에만 남는다 [8][9].

**한계.** `investigation_narration` 항목의 글은 앞 2,000자만 남고 잘렸다는 표시는 항목에도 응답에도 없다 [1][10].

### F04.02 발견사항 필드 구분 저장

**구현.** 발견사항은 `misc.record_finding`, `misc.record_agent_message`의 `findings`, `misc.submit_finding`으로 받는다 [3][11].
항목은 `description`, 판정 등급 `confidence`, 결과를 낸 도구 이름 `source`, 근거 글 `supporting_evidence`, 형식을 정한 주장 `claim`을 나누어 담는다 [12].
`claim`은 주장 종류·범주·행위·행위자·주체·대상·기법 등을 따로 담는다 [13].
`claim`의 `answers_case_question`은 그 발견사항이 사건 질문에 답하는 결론이라는 표시다 [13].
`claim`의 열거 필드는 정해 둔 값인지 늘 검사하고 CONFIRMED·LIKELY·UNCONFIRMED에서는 종류·범주·행위를 요구한다 [14].

**한계.** `supporting_evidence`는 2,000자에서 잘려 저장되고 응답에 그 사실이 없다 [12].
환경변수 `TRUDI_REQUIRE_TYPED_CLAIMS`를 `0`으로 두면 `claim`의 필수 필드 요구가 꺼진다 [14].

### F04.03 근거 증거·호출 참조

**구현.** 발견사항 항목은 근거 호출 `input_call_ids`와 결과를 낸 호출 `linked_call_id`를 필드로 남긴다 [12].
`claim`은 세션 연결·전송·수신 근거와 배제한 대안의 근거를 호출 ID 목록으로 따로 담는다 [13].
게이트가 맞춘 검토 호출의 ID도 `gated_by_*_call_id` 필드로 들어간다 [15].
`input_call_ids`와 `linked_call_id`는 호출 기록에 있는 ID여야 받고 CONFIRMED는 `linked_call_id`가 있어야 받는다 [16][17].
`misc.submit_finding`은 인용 호출 ID가 모두 양의 정수이고 호출 기록에 있어야 받는다 [18].
`misc.record_agent_message`의 `findings`는 `input_call_ids`를 주지 않으면 메시지의 `input_call_ids`를 물려받는다 [3].
증거 파일을 직접 가리키는 필드는 없다.

**한계.** `input_call_ids`를 주지 않으면 서버가 최근 30개 항목 가운데 도구·검토 호출 5개로 채우고 `lineage_inferred`만 적는다 [19].
그 5개가 실제 근거인지는 보지 않는다 [19].
호출 기록 항목이 5개보다 적으면 근거 호출 없이도 받는다 [16].

### F04.04 사건 시각과 작성 시각 분리

**구현.** 작성 시각은 서버가 항목의 `ts`에 UTC로 넣고 모델이 넘기는 인자에는 작성 시각이 없다 [12][20].
사건 시각은 `claim.window`의 `start`·`end`로 따로 받는다 [13].
`window`는 부정 주장 가운데 범주가 `logon_auth`·`device_initial_access`인 것에서만 필수다 [21].

**한계.** 서버는 `window`의 날짜 형식을 검사하지 않고 받은 `dict`를 그대로 복사한다 [13].
`TRUDI_REQUIRE_TYPED_CLAIMS`를 `0`으로 두면 `window` 필수 검사도 꺼진다 [14][21].

### F04.05 수정·철회 이력

**구현.** `supersedes`로 발견사항을 고치면 같은 `finding_id`에 `revision`을 하나 올린 새 항목을 더하고 앞 항목에는 `superseded_by`만 붙여 남긴다 [12][22].
고칠 대상이 지금 버전이 아니거나 수정이 갈라지거나 명제 필드가 다르면 거부한다 [23].
`misc.retract_finding`은 대상 호출 ID, 사유, 근거 호출 ID, 시각을 담은 `finding_retracted` 항목을 더하고 앞 항목을 지우지 않는다 [24].
게이트가 거부한 기록 시도도 `finding_refused` 항목으로 남는다 [25].
항목마다 서버가 채운 시각이 있어 바뀐 차례를 다시 볼 수 있고 `finding_view`가 지금 버전과 이력을 나눈다 [26].

### F04.06 파일·DB에 저장

**구현.** 발견사항, 철회, 제출 기록은 `misc.start_execution_log`가 연 호출 기록 JSON 파일에 항목으로 남는다 [12][27].
저장은 임시 파일에 쓴 뒤 이름을 바꾸고 환경변수로 끄지 않으면 매번 fsync한다 [27].
호출 기록 파일이 열리지 않은 상태에서는 발견사항 기록이 오류로 끝난다 [28].
서버를 다시 시작하면 세션 파일이나 작업 폴더의 호출 기록 파일에서 항목을 다시 읽는다 [29].

**한계.** 호출 기록 파일이 JSON으로 읽히지 않으면 표준 오류에 경고만 남기고 빈 기록으로 그 파일을 바꾸어 써서 앞 발견사항이 사라진다 [30][31].
같은 경로를 다른 `case_id`로 열면 저장 함수가 앞 사건의 항목을 새 사건의 호출 기록 파일에 합쳐 쓴다 [30][31].
`misc.record_finding`처럼 디스크 항목을 다시 읽는 도구를 부른 뒤에는 앞 사건의 발견사항이 지금 사건의 발견사항으로 읽힌다 [32].
이 두 번째 경로는 코드로만 따라갔고 실행하지 않았다.

### F04.07 가설 지지·반박 근거 연결

**구현.** `reason.hypothesize`는 가설을 발견사항과 따로 모델 호출 항목으로 남기고 서버가 `H0001` 형식의 `hypothesis_id`를 매긴다 [33][34].
가설 항목에는 근거 호출 `input_call_ids`, 가설 종류 `hypothesis_kind`, 다투는 주체 `contested_principals`가 들어간다 [34].
발견사항은 `tested_hypothesis_id`로 가설을 가리키고 `claim.resolves`의 `confirmed`·`refuted`로 지지와 반박을 적는다 [12][13].
`misc.record_disposition`은 가설을 대상으로 `refuted`·`excluded`·`evidence_unavailable` 사유와 근거 호출 ID를 담은 처분을 남긴다 [35].

**한계.** `tested_hypothesis_id`가 실제 가설 ID인지는 검사하지 않는다 [36].
비어 있지 않은 아무 문자열이면 가설 게이트를 지나 그대로 저장된다 [36][12].

### F04.08 가설 상태 관리

**구현.** 이 방식은 `reason.pre_report_check`의 가설 점검에 있다 [37].
이 점검은 발견사항 연결과 처분으로 가설마다 닫혔는지를 서버 규칙으로 계산한다 [37].
다투는 주체가 판정되지 않았거나 `distinct_principal` 가설이 닫히지 않았으면 보고를 막고 그 밖의 열린 가설은 경고로 남긴다 [37].
가설의 상태는 따로 저장하지 않고 점검할 때마다 다시 계산하므로 상태가 바뀐 시각은 남지 않는다 [37].

### F04.09 판정·분류 값 기준 대조

**구현.** `misc.submit_finding`은 `confidence`가 CONFIRMED·LIKELY·SUSPECTED·UNCONFIRMED 가운데 하나가 아니면 거부한다 [38].
`reason.hypothesize`의 `hypothesis_kind`도 정해 둔 값이 아니면 거부한다 [39].
이 두 검사의 기준은 코드에 정한 값 목록이다 [38][39].

분류 값인 ATT&CK 기법 ID는 서버가 읽는 MITRE 기법 표와 대조한다 [40][41].
`misc.record_finding`의 게이트 `evidence_strength`와 `misc.submit_finding`의 사전 점검은 둘 다 `mitre_technique_validation` 검사를 부른다 [42].
이 검사는 발견사항 설명에서 기법 ID 모양의 값을 모두 뽑고 claim의 `techniques`와 합친다 [40].
`techniques`에 기법 ID 모양이 아닌 값이 있으면 거부한다 [40].
모은 ID는 `correlate.mitre_validate`로 표에서 찾고 표에 없는 ID가 있으면 거부한다 [41].
`misc.record_ioc`도 지표의 `techniques`를 같은 표에서 찾고 없으면 거부한다 [43].
기준 표는 환경변수 `TRUDI_MITRE_TABLE`이 가리키는 파일이고 값이 없으면 `~/cases/.common/mitre_techniques.json`이다 [44].

**한계.** `misc.record_finding`과 `misc.record_agent_message`의 `findings`는 `confidence`를 대문자로 바꿔 게이트에 넘길 뿐 네 값과 대조하지 않는다 [45].
등급을 보는 게이트는 등급이 CONFIRMED·LIKELY·UNCONFIRMED 가운데 하나일 때만 검사하므로 빈 값이나 목록 밖 값은 받은 그대로 저장된다 [46][12].

`mitre_technique_validation`은 표의 기법 수가 600개보다 적으면 표에 없는 ID를 거부하지 않는다 [47].
그 ID는 `unvalidated` 표시와 함께 `validated_techniques`에 넣고 기록을 진행한다 [47].
저장소의 기법 표 `cases/.common/mitre_techniques.json`에는 기법이 486개 있고 `install.sh`는 `~/cases/.common/`에 표가 없으면 이 파일을 복사한다 [48].
그래서 이 표를 쓰는 설치에서는 발견사항 경로가 표에 없는 기법 ID를 거부하지 않는다 [47][48].
표 파일이 없거나 JSON으로 읽히지 않으면 기법 수가 0이 되어 같은 조건으로 통과한다 [49][47].
`correlate.mitre_validate`를 불러오지 못하면 검사 없이 통과한다 [50].
`misc.record_ioc`에는 표 크기 조건이 없어 발견사항 경로가 `unvalidated`로 통과시킨 ID를 지표 기록에서는 거부한다 [43][47].

### F04.10 근거·확신도 필드 필수 입력

**구현.** 이 방식은 `misc.submit_finding`과 `misc.retract_finding`에 있다 [51][52].
`misc.submit_finding`은 `description`·`confidence`·`input_call_ids`·`claim`·`idempotency_key`를 기본값 없는 인자로 둔다 [51].
서버는 설명이 비었거나 `confidence`가 CONFIRMED·LIKELY·SUSPECTED·UNCONFIRMED 가운데 하나가 아니면 `invalid`로 거부한다 [51][53].
이 도구가 근거로 보는 호출 ID는 `input_call_ids`, `linked_call_id`, claim의 전송·수신·세션·배제 호출 ID를 합친 값이다 [54].
이 값이 비면 사전 점검의 `lineage_required`가 거부한다 [54][16].
`misc.retract_finding`은 사유 `reason`과 근거 호출 ID `input_call_ids`를 기본값 없는 인자로 두고 사유가 비었거나 근거 호출 ID가 없으면 거부한다 [52].
`misc.record_finding`은 `description`과 `confidence`만 기본값 없는 인자로 두고 `input_call_ids`를 비우면 서버가 채운다 [55].
이 도구는 빈 `confidence`도 받아 저장한다 [45][46].

**한계.** 호출 기록 항목이 5개보다 적으면 `lineage_required`는 근거 호출 ID가 비어도 통과시킨다 [16].

### F04.11 관련 없음·배제 처분 기록

**구현.** 이 방식은 `misc.record_disposition`에 있다 [56].
대상 종류는 출처, 도구, 검증 과제, 주체, 상대방, 장치, 가설, 호스트, 파괴 범위, 탐지 범위 행 열 가지다 [56].
사유는 `out_of_scope`·`noise`·`excluded`·`ruled_out`·`absent_from_evidence` 같은 열거 값이고 대상 종류마다 받는 사유가 정해져 있다 [56].
서버는 대상 종류나 사유가 목록에 없거나 그 조합이 정해진 것이 아니거나 대상 ID가 비었으면 거부한다 [57].
받은 처분은 대상 종류, 대상 ID, 서버가 정규화한 대상 키, 사유, 시각을 담은 `disposition` 항목으로 호출 기록에 남는다 [58].
근거 호출 ID, 메모, 기간, `input_call_ids`를 주면 함께 남긴다 [58].
`input_call_ids`를 주지 않으면 마지막 `dair.assess` 호출 ID로 채운다 [58].

**한계.** 대상 ID는 200자, 메모는 500자에서 잘려 저장되고 응답에는 잘렸다는 표시가 없다 [58][59].

    if not supersedes:
        return None

    def transaction(self):

def validate(target_kind: str, target_id: str, reason: str) -> str:
    """'' when valid, else a message naming the field and its enum."""
    tk = (target_kind or "").strip().lower()
    rs = (reason or "").strip().lower()
    if tk not in TARGET_KINDS:
        return (f"target_kind={target_kind!r} is not valid — one of: "
                f"{', '.join(TARGET_KINDS)}")
    if not str(target_id or "").strip():
        return "target_id is required (the manifest source id, tool name, "\
               "`<dair_call_id>:<challenge claim>`, account/identity, address, host, "\
               "device id, hypothesis id, or finding call_id for destruction_scope)"
    if rs not in REASONS:
        return f"reason={reason!r} is not valid — one of: {', '.join(REASONS)}"
    if rs not in ALLOWED[tk]:
        return (f"reason={rs!r} does not apply to target_kind={tk!r} — allowed: "
                f"{', '.join(sorted(ALLOWED[tk]))}")
    return ""
