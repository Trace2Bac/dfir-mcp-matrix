# F01 판단 지침

### F01.01 조사 전체 해석 원칙

**구현.** 서버 지침(`instructions`)은 도구가 증거에 대해 읽기 전용이라는 것, 출력 경로의 범위, 시각이 늘 UTC라는 것만 적고 해석 원칙은 적지 않는다 [1].
조사 전체에 걸치는 해석 원칙은 증거 도구 응답의 `_metadata.discipline_reminder`로 간다 [2].
문구는 다섯 가지이고 호출마다 하나씩 돌아가며 붙는다 [2].
다섯 가지 가운데에는 증거가 가설과 어긋나면 가설을 고치라는 것, 증거가 없다는 것이 없었다는 증거가 아니라는 것, ShimCache·Amcache는 존재만 증명하고 실행을 증명하지 않는다는 것이 있다 [2].
`reason.*`·`dair.*`·`correlate.*` 같은 제어 도구의 응답에는 이 문구가 붙지 않는다 [3].
이 원칙은 서버 지침이나 MCP 리소스·프롬프트가 아니라 도구 응답에 실린다 [1][2].
모델이 이 문구를 읽고 따르는지는 서버가 정하지 않는다.
저장소의 `claude/CLAUDE.md`도 부재 주장은 그 범주의 출처를 모두 검색해야 한다는 원칙을 적지만 이것은 클라이언트 구성이고 서버가 보내는 글이 아니다 [4].

### F01.03 발견사항별 보완 안내

**구현.** 이 방식은 `misc.record_finding`이 기록에 성공한 응답에 붙이는 알림 세 가지에 있다 [5][6][7].
기록한 등급이 인용한 호출의 아티팩트 범주로 닿는 등급보다 낮으면 응답의 `tier_headroom`에 닿는 등급과 규칙을 적는다 [5].
이 문구는 닿는 등급으로 다시 기록하거나 이유를 남기라고 권하고 결론을 강하게 하라는 지시가 아니라고 적는다 [5].
CONFIRMED·LIKELY 발견사항의 `source`가 지식 시트의 아티팩트에 대응하고 claim의 `act`가 실행·존재·시간 가운데 하나이면 서버는 그 시트가 정한 보강 도구가 호출 기록에 있는지 본다 [6][8].
시트의 `does_not_prove`가 그 아티팩트만으로 그 행위를 증명하지 못한다고 적고 보강 도구가 하나도 실행되지 않았으면 응답의 `completeness_note`에 그 도구 이름을 적는다 [8].
이 문구는 그 도구로 보강하거나 SUSPECTED로 낮추라고 권한다 [8].
CONFIRMED·LIKELY 발견사항의 설명에 ATT&CK 기법 ID가 둘 이상 있거나 접속어와 함께 행위 동사가 둘 이상 있으면 `atomicity_note`로 주장마다 발견사항을 나누라고 권한다 [7].
세 알림은 기록을 막지 않는다 [5][6].
`completeness_note`와 `atomicity_note`는 만들다 예외가 나면 그 알림 없이 응답한다 [6].

**한계.** `completeness_note`는 보강 도구가 실행됐는지를 호출 기록의 `tool_call` 명령 문자열에 도구별 정규식을 대어 보고 그 호출이 성공했는지 보지 않는다 [9].
`ez_pecmd`의 정규식은 `prefetch`라는 글자에도 맞으므로 Prefetch 폴더 경로를 인자로 받은 다른 도구의 호출도 보강 도구 실행으로 처리한다 [9].

def atomicity_note(description: str) -> Optional[str]:
    d = description or ""
    tids = set(m.upper() for m in _TID_RE.findall(d))
    verbs = {v.lower() for v in _CLAIM_VERB_RE.findall(d)}

    reason = None
    if len(tids) >= 2:
        reason = f"{len(tids)} ATT&CK techniques ({', '.join(sorted(tids))})"
    elif _CONNECTOR_RE.search(d) and len(verbs) >= 2:
        reason = f"multiple actions ({', '.join(sorted(verbs))})"

    if not reason:
        return None

    return (
        f"This finding's description appears to bundle multiple claims — {reason}. "
        f"For audit traceability, prefer one finding per claim so each links to its "
        f"own evidence (linked_call_id) and is tiered on its own merits. Consider "
        f"splitting it into separate record_finding calls."
    )
```

def note_for_finding(*, tier: str, description: str, source: str, idx,
                     claim=None) -> Optional[str]:
    """warn-early: a non-blocking completeness note for a just-recorded
    CONFIRMED/LIKELY finding, or None. `idx` is the ExecutionLog LogIndex."""
    if (tier or "").upper() not in {"CONFIRMED", "LIKELY"}:
        return None
    by_type = getattr(idx, "by_type", {}) or {}
    gap = corroboration_gap(source, claim, _ran_cmds(by_type.get("tool_call", [])))
    if not gap:
        return None
    return (f"Finding {gap['message']} Corroborate with one of "
            f"{', '.join(gap['expected'])}, or downgrade to SUSPECTED.")
```
