# T04 실행 방식

### T04.01 서버 프로세스 안 분석

**구현.** 서버 프로세스 안에서 파이썬 코드나 라이브러리로 분석하는 도구가 있다 [1][2][3][4].
`yara.*`는 yara-python으로 룰을 컴파일하고 파일을 서버 프로세스 안에서 검사한다 [1].
`hash.file`·`hash.directory`는 서버 프로세스가 파일을 읽어 `hashlib`로 해시를 계산한다 [2].
`misc.cs_beacon_config`는 저장소의 `core/cs_beacon.py`로 메모리 덤프에서 Cobalt Strike 설정을 찾는다 [3].
`read.*`와 `af.timestomp_drift`·`af.sysmon_evasion`·`af.usn_gaps`는 앞선 도구가 쓴 CSV·JSON·메일 파일을 서버 프로세스에서 파싱한다 [4].
`correlate.process_to_file`·`correlate.network_to_process`·`af.event_log_clear`·`af.prefetch_deletion`·`coverage.report`는 호출 기록의 항목을 서버 프로세스에서 읽어 잇는다 [4].
`misc.evtx_filter`·`strings.grep`은 외부 도구의 출력을 서버 프로세스에서 한 줄씩 읽어 거른다 [5].

### T04.02 같은 권한의 별도 프로세스

**구현.** 외부 도구는 대부분 실행기 `core/executor.py`의 `run`·`run_with_progress`·`run_with_output_file`로 실행한다 [6].
실행기는 인자 목록을 `subprocess.run`이나 `asyncio.create_subprocess_exec`에 넘겨 셸 없이 자식 프로세스로 실행한다 [6].
문자열 명령을 받으면 `shlex.split`으로 나눠 같은 방식으로 실행한다 [6].
`misc.evtx_filter`·`strings.grep`은 출력을 스트림으로 읽으려고 `subprocess.Popen`에 인자 목록을 직접 넘긴다 [5].
`velo.*`는 `velociraptor` 실행 파일을, `live.*`와 대응 조치 실행은 `ssh` 실행 파일을 같은 방식으로 실행한다 [7].
`monitor.start_watcher`는 감시 스크립트 `bin/trudi-velo-watcher.py`를 서버와 같은 파이썬으로 새 세션에서 실행한다 [8].
`misc.batch_run`은 모델이 준 인자 목록을 같은 실행기로 실행한다 [9].

`sudo`를 붙이지 않은 자식 프로세스는 서버의 계정과 환경변수를 그대로 물려받아 서버와 같은 파일·네트워크 권한으로 실행된다 [6].
작업 위치(`cwd`)를 주는 도구는 `misc.hindsight_chrome` 하나이고 모델이 준 `output_dir`를 작업 위치로 쓴다 [10].
나머지 도구는 서버 프로세스의 작업 위치에서 실행되고 호출마다 새 작업 폴더를 만드는 곳은 없다 [6].
백그라운드 작업은 작업마다 `~/.cache/trudi/jobs/<job_id>.d` 폴더를 만들지만 표준 출력·표준 오류·종료 코드 파일만 두고 작업 위치로 쓰지 않는다 [11].
컨테이너, namespace, seccomp로 외부 도구를 서버와 나누는 코드는 없다.

### T04.03 셸 명령 문자열 실행

**구현.** 이 방식은 `net.tcpxtract_streams`의 백그라운드 작업과 SSH로 보내는 원격 명령에 있다 [11][12].
백그라운드 작업 함수 `start_job`은 명령 토큰을 `shlex.quote`로 감싸 이은 뒤 출력 방향 바꾸기와 종료 코드 기록을 더한 문자열을 `sh -c`로 실행한다 [11].
`net.tcpxtract_streams`의 모델 값 `pcap_file`·`output_dir`가 따옴표 처리를 거쳐 그 문자열에 들어간다 [13].

Ubuntu 22.04의 OpenSSH 8.9p1에서 `ssh`는 원격 명령 인자를 공백으로 이어 한 문자열로 보내고 `sshd`는 그 문자열을 접속 계정의 셸에 `-c`로 넘긴다 [14].
그래서 `live.*`와 대응 조치 실행의 원격 명령은 모두 원격 셸이 해석한다 [12][14].
서버는 원격 명령 토큰마다 `shlex.quote`를 붙여 토큰 하나가 원격 셸에서 인자 하나로 읽히게 한다 [12].
`live.process_details`·`live.users`·`live.recent_logins`·`live.scheduled_tasks`·`live.persistence_audit`는 `sh -c` 스크립트를 토큰으로 보내고 스크립트에 들어가는 모델 값은 정수 인자 `pid`·`hours`뿐이다 [15].
대응 조치 4종(`quarantine_image`·`restore_quarantined_image`·`remove_cron_entry`·`restore_cron_entry`)은 `/bin/sh -c` 문자열을 만들고 정규식 검사를 통과한 경로를 `shlex.quote`로 감싸 넣는다 [16].

`misc.batch_run`은 모델이 `sh -c`가 든 인자 목록을 주면 그대로 셸을 실행한다 [9].
실행기는 셸을 거치지 않고 서버 코드에서 `shell=True`나 `os.system`으로 실행하는 곳은 찾지 못했다 [6].

### T04.04 권한을 나눈 실행

**구현.** 이 방식은 실행기를 부를 때 `needs_sudo=True`를 넘기는 도구와 `net.tcpxtract_streams`의 백그라운드 작업에 있다 [17][11].
실행기는 `needs_sudo`가 참이면 인자 목록 앞에 `sudo`를 붙여 외부 도구를 root 권한으로 실행한다 [6].
백그라운드 작업은 `sudo timeout`으로 명령을 감싸 같은 일을 한다 [11].
이 도구들에서 `sudo`를 붙일지는 도구 코드가 정하고 사용자 설정이나 호출 인자로 바꾸지 못한다 [17].
Sleuth Kit 도구 `tsk.*`의 다수, tcpdump·ngrep·tcpxtract를 쓰는 `net.*`, 이미지·볼륨 마운트 도구 `img.*`·`ewf.*`의 다수, 카빙 도구 `carve.*`가 이렇게 root 권한으로 실행된다 [17].
권한을 높이는 방향만 있고 권한을 낮추거나 다른 일반 계정으로 바꾸는 코드는 없다.
`install.sh`는 설치 계정이 암호 없이 `sudo`를 쓸 수 없으면 그 계정에 `NOPASSWD: ALL`을 준다 [18].
그래서 `misc.batch_run`에 모델이 `sudo`로 시작하는 인자 목록을 주면 그 명령도 root 권한으로 실행된다 [9][18].
`sudo`를 붙이지 않은 도구는 서버와 같은 권한으로 실행된다 [6].

### T04.06 원격 API 작업 요청

**구현.** 이 방식은 `velo.*`와 이를 부르는 `monitor.baseline_capture`·`monitor.start_watcher`에 있다 [19][20].
서버는 `velociraptor` 실행 파일을 API 설정 파일과 함께 실행해 VQL을 Velociraptor 서버에 보내고 결과 행을 JSON 줄로 받는다 [19].
`velo.collect_artifact`는 대상 단말의 아티팩트 수집을 Velociraptor 서버에 흐름(flow)으로 맡기고 흐름 ID를 받아 바로 돌아온다 [21].
서버는 `velo.wait_for_flow`로 흐름 상태를 되묻고 `velo.get_collection_results`로 결과 행을 가져온다 [21].
`monitor.start_watcher`는 감시 아티팩트를 Velociraptor의 전역 클라이언트 감시 표에 넣는다 [20].
`velociraptor` 실행 파일 자체는 서버와 같은 권한의 자식 프로세스다 [7].

`reason.*`·`dair.assess`는 모델 API에 발견사항 검토와 다음 작업 계획을 묻는다 [22].
이 호출은 파싱·검색·도구 실행을 원격에 맡기는 요청이 아니다 [22].

### T04.07 SSH 원격 호스트 명령 실행

**구현.** 이 방식은 `live.*`와 대응 조치 실행 `respond.execute_action`·`respond.revert_action`에 있다 [12][23].
접속 대상의 주소·포트·계정·인증 키는 사용자 설정 파일 `live_hosts.json`에서 오고 모델은 그 키 이름만 고른다 [23].
서버는 `ssh` 실행 파일로 그 호스트에 접속해 원격 명령을 실행하고 표준 출력을 받는다 [12][23].
원격 명령은 설정에 적힌 접속 계정 권한으로 실행된다 [23].
`live.scheduled_tasks`는 원격에서 `sudo -n crontab`으로 사용자마다 crontab을 읽는다 [15].
접속하는 호스트는 분석 도구를 둔 별도 분석 호스트가 아니라 조사 대상인 살아 있는 단말이다 [24].
분석 명령은 그 단말 위에서 단말의 계정으로 실행되고 단말 안에서 계정이나 파일을 나누는 장치는 없다 [23].

def _compile_rules(rules_path: str):
    import yara
    if os.path.isdir(rules_path):
        rule_files = {
            os.path.basename(f): f
            for f in glob.glob(os.path.join(rules_path, "**/*.yar"), recursive=True)

        }
        if not rule_files:
            raise ValueError(f"No .yar/.yara files found in {rules_path}")
        return yara.compile(filepaths=rule_files)
    else:
        return yara.compile(filepath=rules_path)

```python
def _build_ssh_argv(resolved: dict, cmd_argv: list[str]) -> list[str]:
    """Construct the full local argv: ssh + opts + user@host + -- + remote argv.

    The `--` separator tells SSH that everything after is the remote command
    as discrete argv tokens, not a single shell string. SSH still concatenates
    them, but each token is properly shell-quoted by ssh's own quoting layer,
    so an operand like `'; rm -rf /'` is passed as a literal filename, not
    parsed as a separator.
    """
    argv = ["ssh"] + _SSH_OPTS + [
        "-i", resolved["identity"],
        "-p", str(resolved["port"]),
        f"{resolved['user']}@{resolved['host']}",
        "--",
    ]
    # Quote each operand so the remote shell sees one token per item even
    # though SSH joins them into a single command-line string.
    quoted_remote = [shlex.quote(a) for a in cmd_argv]
    argv.extend(quoted_remote)
    return argv
```
