# T03 실행 조건 확인

### T03.01 선행 결과 대조

**구현.** 대응 조치를 제안하는 `respond.suggest_containment`와 원격 호스트에 쓰기 명령을 보내는 `ssh_run_write`는 사건 폴더의 `monitoring/baselines/`에 기준선 파일이 있어야 진행한다 [1].
기준선 파일은 앞선 `monitor.baseline_capture` 호출이 쓴다 [1].
`respond.suggest_containment`는 기록된 발견사항이 없어도 모델이 `detector`와 `evidence`를 주면 제안을 만들어 이 도구에는 선행 발견사항 조건이 없다 [2].
이때 조치 대상 값은 모델이 준 `evidence`에서 온다 [2].
발견사항이 인용한 호출 ID를 호출 기록과 대조하는 `misc.record_finding`의 게이트는 인자 값 검사이므로 T01.06과 D07.01에서 본다 [3].

### T03.02 조사 단계 검사

**구현.** 서버는 DAIR 단계를 호출 기록의 `dair_call` 항목으로 정한다 [4].
`dair_required` 게이트는 `dair_call`이 없으면 발견사항 기록을 거부한다 [5].
모델이 `reason.plan`을 불러 분류 단계를 마쳤는데 DAIR 단계가 아직 없으면 허용 목록 밖의 도구를 거부하고 `dair.assess`를 먼저 부르라고 알린다 [6].
단계가 `Report`이면 새 발견사항 기록을 거부한다 [7].
`Report` 단계에서 증거 도구를 부르면 거부하지 않고 단계를 `Collect`로 되돌린다 [7].

**한계.** DAIR 참여 게이트와 단계 게이트는 판단하다 예외가 나면 호출을 통과시킨다 [8].
DAIR 참여 게이트는 환경변수 `TRUDI_DAIR_NUDGE`로 끈다 [9].
호출 기록을 열 때 `configure`는 `dair_call`이 없어도 단계 값을 `Triage`로 정한다 [10].
DAIR 참여 게이트는 단계 값이 비어 있지 않으면 바로 통과시키므로 호출 기록이 열린 뒤에는 `reason.plan` 다음의 거부가 적용되지 않는다 [6][10].
이름이 `live_`·`velo_`·`monitor_`·`respond_`로 시작하는 도구는 설정과 관계없이 DAIR 참여 게이트를 건너뛴다 [11].

### T03.03 앞선 점검·판정 결과 대조

**구현.** 보고서 도구 `misc.write_final_report`와 `misc.export_execution_log`는 호출 기록에서 가장 최근의 `reason.pre_report_check` 항목을 찾는다 [12].
그 항목이 없거나 `ready_to_report`가 참이 아니거나 그 뒤 호출 기록의 상태가 바뀌었으면 거부한다 [12].
CONFIRMED·LIKELY 발견사항에는 같은 주장에 검토 모델이 SUPPORTED를 준 `reason.evaluate_finding` 기록을 요구한다 [13].
SUPPORTED 판정은 서버 안에서 부른 검토 모델이 내고 그 판정을 심사하는 방식은 D07에서 본다 [13].

**한계.** 임의 명령을 실행하는 `misc.batch_run`으로 `reports/`에 파일을 쓰면 준비 점검 없이 보고서 파일이 생긴다 [14].
`monitor.end_investigation`은 `misc.export_execution_log`와 같은 호출 기록 내보내기를 보고 준비 점검 없이 한다 [15].
코드 주석은 조사별 호출 기록을 기준선이 있는 실시간 감시 사건으로 한정해 이 보고서 요건에서 빠지는 범위를 좁힌다고 적는다 [16].
그런데 `monitor.end_investigation`은 기준선이나 열린 조사를 확인하지 않는다 [17].
그래서 조사 호출 기록 파일이 없는 사건에서도 그때 열려 있는 호출 기록이 점검 없이 보고서 파일로 쓰인다 [15][17].

### T03.04 반복 호출 제한

**구현.** 미들웨어는 도구 이름과 인자로 만든 키마다 앞선 결과의 해시와 같은 결과가 되풀이된 횟수를 프로세스 메모리의 `_repeat_state`에 둔다 [18].
같은 인자로 같은 결과가 `TRUDI_REPEAT_BLOCK_AFTER`번(기본 4번) 되풀이된 뒤의 호출은 실행 전에 거부한다 [19].
거부 문구는 부재를 발견사항으로 한 번 기록하고 다른 질의를 하라고 안내한다 [19].
이 상태는 메모리에만 있어 서버를 다시 시작하면 비고 키가 512개를 넘으면 오래된 것부터 버린다 [18].
상태가 얼마나 남는지는 P04에서 본다.

**한계.** 환경변수 `TRUDI_REPEAT_GATE`나 `TRUDI_REPEAT_BLOCK_AFTER`로 이 게이트를 끈다 [9].
이름이 `live_`·`velo_`·`monitor_`·`respond_`로 시작하는 도구는 설정과 관계없이 이 게이트를 건너뛴다 [11].

### T03.06 승인 토큰·서명 대조

**구현.** 이 방식은 원격 호스트에 대응 조치를 실행하는 `respond.execute_action`과 실행한 조치를 되돌리는 `respond.revert_action`에 적용된다 [20].
두 도구는 사건 폴더의 조치 제안 파일(`suggestions/<action_id>.json`)을 읽은 뒤 `check_execution_permitted`로 실행을 허용할지 정한다 [20][21].
이 함수는 서버가 AUTO로 분류하지 않은 조치와 `auto_protect`가 꺼진 사건의 조치에 승인 기록을 요구한다 [21].
쓰기 SSH를 실행하는 `ssh_run_write`는 MCP 도구가 아니고 이 두 도구만 부른다 [22].

승인 기록은 `respond.approve_action`이 발급한다 [23].
`respond.approve_action`은 인자 `operator_text`에 `action_id`가 들어 있는지와 그 `action_id`의 제안 파일이 있는지를 먼저 본다 [24].
그다음 호출 기록의 마지막 30개 항목에서 내용이 `operator_text`와 같고 `type`·`source`·`role`이 사용자 입력을 나타내는 항목을 찾고 없으면 거부한다 [24].
이 사용자 입력 항목은 서버가 쓰지 않는다.
Claude Code의 UserPromptSubmit 훅과 OpenCode 플러그인이 사용자가 입력한 글을 `type`이 `user_message`이고 `role`이 `user`인 항목으로 호출 기록 파일에 덧붙인다 [25].
훅이나 플러그인이 없는 클라이언트로 붙으면 사용자 입력 항목이 생기지 않아 `respond.approve_action`은 항상 거부하고 승인 없이 실행되는 조치는 AUTO 조치뿐이다 [24][25].
모델이 글을 남기는 `misc.record_agent_message`는 `type`이 `investigation_narration`이고 `source`·`role`이 없는 항목을 써서 이 대조를 채우지 못한다 [26].
대조는 서버 메모리에 있는 호출 기록 목록을 읽는다 [27].
훅이 파일에 쓴 항목은 `transaction`을 여는 도구(`misc.record_finding`·`reason.readiness_status` 등)나 `configure`가 파일을 다시 읽어야 메모리 목록에 들어온다 [27][28].
그래서 사용자가 입력한 뒤 그런 호출 없이 `respond.approve_action`을 부르면 대조가 그 입력을 찾지 못한다 [27][28].
서버를 실행해 이 순서를 확인하지는 않았다.

대조를 통과하면 `issue_approval`이 사건 폴더의 `monitoring/response/approvals/<action_id>.json`에 무작위 hex 값 `approval_token`과 만료 시각을 쓴다 [23].
`check_approval`은 이 파일이 있고 읽히며 만료 시각이 지나지 않았는지만 보고 `approval_token` 값은 다른 값과 대조하지 않는다 [29].
`approval_token`은 실행 기록에 옮겨 적힌다 [29].

AUTO 분류는 `policy.classify`가 제안 파일의 `risk`가 `low`이고 `reversible`이 참일 때만 준다 [30].
`risk`와 `reversible`은 `respond.suggest_containment`가 `detector`로 고른 recipe에서 제안 파일로 옮겨 적는다 [31][32].
저장소의 recipe 4개에서 AUTO가 되는 조치는 `pause_pid`·`block_egress_to_endpoint`·`remove_cron_entry`·`disable_systemd_unit`·`quarantine_image`·`dump_process_memory`이고 승인이 필요한 조치는 `kill_pid`·`kill_owning_pid`다 [33].
`auto_protect`는 사건의 `monitoring/config.json`에서 읽고 파일이 없으면 켜진 것으로 본다 [34].
AUTO 조치의 대상 값(`pid`·`remote_ip` 등)은 `respond.suggest_containment`가 받은 `evidence`에서 온다 [32].
`detector`와 `evidence`를 인자로 주면 `finding_id`의 발견사항이 호출 기록에 없어도 제안 파일을 만든다 [32].
`respond.execute_action`의 `mode` 인자는 실행 기록에만 남고 허용 판단에 쓰이지 않는다 [21].
`monitor.set_awaiting_approval`·`monitor.clear_awaiting_approval`은 모델이 부르는 대기 표시이고 승인 기록을 보지 않으며 실행 허용 판단에 쓰이지 않는다 [35].

**한계.** `misc.batch_run`은 받은 argv를 그대로 실행하므로 모델이 이 도구로 `approvals/<action_id>.json`에 만료 전 기록을 쓰면 사용자 입력 없이 `check_approval`을 통과한다 [14][29].
같은 도구로 제안 파일의 `risk`를 `low`로, `reversible`을 참으로 바꾸면 그 조치는 AUTO로 분류되어 승인 없이 실행된다 [14][30].
같은 도구로 호출 기록 파일에 `type`이 `user_message`인 항목을 덧붙이면 메모리 목록을 다시 읽은 뒤 `respond.approve_action`이 그 항목을 사용자 입력으로 받아들인다 [14][24][28].
모듈 설명은 AUTO 분류를 디스크의 recipe 메타데이터로 정하므로 모델이 분류를 바꿀 수 없다고 적는다 [36].
그러나 `respond.suggest_containment`는 `detector` 인자를 검사하지 않고 recipe 경로를 `RECIPES_DIR / f"{detector}.yaml"`로 만든다 [31].
`detector`에 절대 경로나 `../`를 넣어 recipe 폴더 밖의 YAML 파일을 고르면 그 파일에 적힌 `risk`·`reversible`로 분류되므로 `kill_pid`도 AUTO가 될 수 있다 [31][30].
`load_config`는 `config.json`을 읽지 못하거나 JSON으로 풀지 못하면 `auto_protect`를 켜진 것으로 돌려준다 [34].
`auto_protect` 값이 객체가 아니면(예: `false`) 이것도 켜진 것으로 본다 [34].
그래서 사용자가 `auto_protect`를 끄려고 쓴 설정 파일을 JSON으로 풀지 못하거나 `auto_protect`를 객체가 아닌 값(예: `false`)으로 적으면 AUTO 조치가 승인 없이 실행된다 [34].
`dump_process_memory`는 recipe에 `reversible: true`로 적혀 AUTO로 분류되지만 서버의 되돌리기 표에는 되돌릴 명령이 없고 `respond.revert_action`은 이 조치를 되돌릴 수 없다고 거부한다 [37][20].

### T03.07 승인 내용과 요청 대조

**구현.** 이 방식은 T03.06과 같이 `respond.approve_action`이 발급하고 `respond.execute_action`·`respond.revert_action`이 확인하는 승인 기록에 적용된다 [23][20].
`respond.approve_action`은 사용자 입력과 같은 `operator_text`에 승인할 `action_id`가 글자 그대로 들어 있지 않으면 거부한다 [24].
승인 기록은 사건 폴더와 `action_id`로 정한 경로에 저장되고 실행 도구는 요청의 `case_id`·`action_id`로 같은 경로를 읽으므로 다른 조치의 승인으로는 실행되지 않는다 [23][29].
실행할 조치 종류(`action_template`)와 대상 값(`raw_evidence`)은 같은 `action_id`의 제안 파일에서 읽는다 [20].
승인 기록에는 `action_id`·`case_id`·`operator_text`·`approval_token`·시각만 있고 조치 종류, 대상 값, 대상 호스트는 없다 [23].
대상 호스트는 실행할 때 `config.json`의 `host`나 `live_hosts.json`에 하나뿐인 호스트로 정한다 [38].
그래서 승인한 뒤 이 설정이 바뀌면 승인할 때와 다른 호스트에서 실행된다 [38].

**한계.** `action_id` 대조는 부분 문자열 검사라 사용자가 `approve ACT-12`라고 입력했을 때 `ACT-1`의 승인도 통과한다 [24].
사용자 입력이 `action_id`를 담기만 하면 `do not approve ACT-3`처럼 거절하는 글도 승인으로 받아들인다 [24].

### T03.08 승인 만료·소모·재승인

**구현.** 이 방식은 T03.06의 승인 기록에 적용된다 [23].
승인 기록의 만료 시각은 발급한 때부터 600초 뒤(`APPROVAL_TTL_SECONDS`)이고 `check_approval`은 만료된 기록을 거부하며 다시 승인하라고 알린다 [39][29].
`respond.suggest_containment`는 제안마다 `_action_seq.txt`의 번호를 하나 올려 새 `action_id`를 주므로 새로 만든 제안에는 새 승인이 필요하다 [40].
승인 기록은 실행한 뒤에도 지우지 않아 만료 전에는 같은 `action_id`를 다시 실행하거나 되돌릴 수 있다 [20][29].
사용 횟수는 세지 않는다.

**한계.** 같은 사용자 입력 항목이 메모리 목록의 마지막 30개 안에 있는 동안 모델이 `respond.approve_action`을 다시 부르면 새 사용자 입력 없이 만료 시각이 새로 정해진다 [24][23].
제안 파일 내용은 승인 기록에 묶이지 않아 승인한 뒤 `misc.batch_run`으로 제안 파일의 `action_template`·`raw_evidence`를 바꾸면 다시 승인받지 않고 바뀐 조치가 실행된다 [14][20][23].
`_action_seq.txt`를 읽지 못하거나 숫자가 아니면 번호가 1부터 다시 매겨져 앞선 제안 파일을 덮어쓰고 그 번호에 남은 만료 전 승인 기록이 새 제안의 실행을 허용한다 [40][29].

### T03.12 동시 실행 수 제한

**구현.** 이 방식은 미들웨어가 서버 안 배경 작업으로 실행하는 도구에 적용된다 [41].
그 도구는 `BACKGROUND_ALWAYS`·`BACKGROUND_IF_SLOW` 목록에 있거나 이름이 `vol_`로 시작하는 도구다 [41].
미들웨어는 이 도구의 실행 본문을 `jobs.slots()`가 돌려주는 `asyncio.Semaphore` 안에서 실행한다 [41][42].
세마포어는 서버 프로세스에 하나 만들어지므로 이 제한은 프로세스 전체의 배경 작업에 적용된다 [41].
동시에 실행되는 작업 수는 사용자가 환경변수 `TRUDI_JOB_SLOTS`(기본 3)로 정하고 모델은 바꾸지 못한다 [41].
자리가 없으면 실행을 미룬다 [42].
`BACKGROUND_ALWAYS` 도구는 바로 작업 핸들을 돌려주고 나머지 도구는 `TRUDI_JOB_INLINE_WAIT`(기본 30초) 안에 끝나지 않으면 작업 핸들을 돌려준다 [41][42].
핸들의 상태는 그때까지 실행 본문이 자리를 얻었으면 `running`이고 아니면 `queued`다 [42].
이 제한은 메모리나 CPU 사용률을 읽지 않고 작업 수만 센다 [41].
목록에 없는 도구와 `net.tcpxtract_streams`가 `start_job`으로 분리 실행하는 명령은 이 제한을 거치지 않는다 [41][43].

**한계.** `misc.batch_run`은 모델이 준 argv 목록을 슬롯 밖의 `ThreadPoolExecutor`에서 함께 실행한다 [44].
동시에 실행되는 명령 수는 모델이 인자 `max_concurrent`(기본 4)로 정하고 서버는 1 미만만 1로 올릴 뿐 상한을 두지 않는다 [44].
그래서 모델은 배경 작업 도구가 실행하는 외부 프로그램을 이 도구로 슬롯 없이 여러 개 동시에 실행할 수 있다 [41][44].

    Composes the auto-protect policy with the existing approval gate:

        check_approval — which requires a non-expired operator-issued token.

def start_job(cmd: list[str], tool: str, timeout: int, output_dir: str,
              needs_sudo: bool = False) -> dict:
    """Spawn `cmd` detached under a hard `timeout` budget; return immediately
    with a running-job handle. Never blocks."""
    os.makedirs(JOBS_DIR, exist_ok=True)
    if output_dir:
        os.makedirs(output_dir, exist_ok=True)
    job_id = _new_job_id(tool)
    jdir = os.path.join(JOBS_DIR, f"{job_id}.d")
    os.makedirs(jdir, exist_ok=True)
    stdout_file = os.path.join(jdir, "stdout")
    stderr_file = os.path.join(jdir, "stderr")
    exit_file = os.path.join(jdir, "exit")

    import shlex
    # `timeout` (coreutils) enforces the budget and exits 124 on expiry; run it
    # under sudo so it can signal a root-owned carve child. The sentinel write
    # (`echo $? > exit`) is what job_status polls for completion.
    inner = " ".join(shlex.quote(c) for c in cmd)
    prefix = ("sudo timeout" if needs_sudo else "timeout") + f" {int(timeout)}"
    script = (f"{prefix} {inner} > {shlex.quote(stdout_file)} "
              f"2> {shlex.quote(stderr_file)}; echo $? > {shlex.quote(exit_file)}")
    proc = subprocess.Popen(
        ["sh", "-c", script], stdin=subprocess.DEVNULL,
        stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL,
        start_new_session=True)
