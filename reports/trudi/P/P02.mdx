# P02 다음 작업 결정

### P02.02 규칙·조사 상태로 추천

**구현.** 모든 도구 호출을 지나는 `NarrationMiddleware`가 단계와 호출 기록의 상태를 보고 응답에 다음 작업을 붙인다 [1][2].
단계 값이 비어 있고 `reason.hypothesize`도 `reason.plan`도 없으면 증거 도구 응답마다 `dair_notice`로 `reason.hypothesize`, `reason.plan`, `dair.assess`를 차례로 부르라고 적는다 [1].
`reason.hypothesize`만 있으면 남은 두 단계를 부르라고 적고 `reason.plan`까지 있으면 증거 도구를 막고 `dair.assess`를 부르라고 돌려준다 [1].
Analyze·Scan 단계에서 기록한 발견사항이 하나도 없으면 60초에 한 번 `finding_notice`로 `misc.record_finding`을 부르라고 적는다 [2].
같은 인자로 같은 결과가 되풀이되면 `repeat_notice`로 다른 질의나 `dair.assess`를 권한다 [3].
`misc.job_status`를 다른 일 없이 연달아 부르면 `poll_advisory`로 다른 분석을 먼저 하라고 적는다 [4].
Report 단계에서 증거 도구를 부르면 Collect로 옮기고 `phase_transition`으로 끝나면 `dair.assess`로 Report에 돌아가라고 적는다 [5].

`dair.assess`는 처방 모델의 답을 규칙으로 고친 뒤 작업 지시를 돌려준다 [6].
발견사항이 없는데 모델이 Report를 고르면 전이를 막고 `misc.record_finding`을 작업 지시 맨 앞에 넣는다 [6].
Collect·Analyze(후보 호스트가 있으면 Scan까지)를 거치지 않았는데 Report를 고르면 빠진 단계로 넣는다 [7].
Collect 단계의 작업 지시가 비면 공격 단계 다섯 가지 가운데 아직 보지 않은 단계의 수집 도구로 채운다 [8][9].
수집 도구로 채우는 목록은 Windows 디스크 산출물 도구이고 P01.04의 증거 종류 대조만 거친다 [8][9].
증거 종류에 OS가 없어 Linux 디스크 이미지 사건에도 `ez.recmd_hive`·`ez.pecmd` 같은 Windows 도구를 권한다 [8][9].
단계를 떠나려 할 때 그 단계에서 처방한 도구가 실행되지도 처분되지도 않았으면 전이를 막고 그 도구를 다시 작업 지시에 넣는다 [10].
이 고친 내용은 `server_override`로 응답과 호출 기록에 남는다 [6].
`reason.pre_report_check`는 보고를 막는 사유를 `blocking_issues`로 돌려주고 Report 단계에서 준비가 안 됐으면 Collect로 옮긴다 [11].
사유 문장은 실행해야 할 도구나 남겨야 할 처분을 적고 그 판단은 P03.03에서 본다.

고정 절차 문서를 돌려주는 경로는 없어 P02.01에는 연결하지 않는다.
서버 지침은 증거를 읽기만 한다는 것과 출력 폴더, 시각 기준만 적는다 [12].
조사 순서를 적은 `claude/CLAUDE.md`는 `install.sh`가 Claude Code 전역 지침으로 설치하는 클라이언트 구성이다 [13].
도구 응답의 `_metadata`에 붙는 교차 확인 도구는 R04에서 본다 [14].

**예외.** `dair_notice`와 `reason.plan` 뒤의 차단은 단계 값이 비어 있을 때만 적용된다 [1].
미들웨어 주석은 DAIR가 아직 시작되지 않은 Triage를 빈 단계 값으로 적는다 [15].
그러나 `misc.start_execution_log`가 부르는 `configure`는 새 호출 기록이든 다시 읽은 호출 기록이든 `dair_call`이 없으면 단계 값을 `Triage`로 정한다 [16].
그래서 호출 기록을 연 뒤에는 `dair.assess`를 한 번도 부르지 않아도 이 알림과 차단이 적용되지 않고 기록을 열기 전의 호출에만 적용된다 [1][16].
`TRUDI_DAIR_NUDGE`를 `0`·`off`·`false`·`none`으로 두면 `dair_notice`, `finding_notice`, 차단이 모두 꺼진다 [17].
알림 판단 중 예외가 나면 알림 없이 통과시킨다 [1][2].
`finding_notice`가 세는 발견사항 수는 프로세스 메모리의 `_ritual`이 호출 기록을 어디까지 읽었는지 기억해 이어 센 값이다 [18].
항목 수가 줄 때만 처음부터 다시 세므로 호출 기록을 항목이 더 많은 다른 사건의 기존 파일로 바꾸면 앞 사건의 발견사항 수가 남고 새 파일의 앞부분은 세지 않는다 [18].
그래서 새 사건에 기록한 발견사항이 없어도 `finding_notice`가 붙지 않을 수 있다 [2][18].

### P02.03 모델 계획 생성

**구현.** `dair.assess`는 서버 안에서 처방 모델을 불러 다음 작업 지시를 만든다 [19].
처방 모델은 `ANTHROPIC_API_KEY`가 있으면 Anthropic API로, `DAIR_URL`만 있으면 OpenAI 호환 API로 부르고 `DAIR_BACKEND`로 고를 수 있다 [19].
모델 입력에는 에이전트가 쓴 결과 요약, 서버가 가진 단계 스택과 현재 단계, 증거 종류, 아직 실행하지 않은 작업 지시, IOC 탐지 범위의 열린 항목이 들어간다 [20].
이 입력에는 결과 요약 안의 증거 글을 데이터로 표시하는 머리말이 없다 [20].
`dair.assess`가 한 번이라도 실행된 뒤에는 에이전트가 보낸 단계 스택 대신 서버가 기록한 스택을 보낸다 [21].
시스템 지시는 `priority_tools`를 빠짐없는 작업 지시로 정의하고 에이전트는 그 목록만 실행한다고 적는다 [22].
서버는 모델 답의 형식을 검사해 한 번 고쳐 달라고 다시 묻고 그래도 틀리면 `dair_schema`로 실패를 돌려준다 [23].
작업 지시에 도구 목록에 없는 이름이 있으면 `unknown_priority_tools`에 적기만 하고 빼지 않는다 [24].
작업 지시에는 모델이 정하는 탐색 할당량 `curiosity_budget`도 들어간다 [25].
시스템 지시는 Triage·Analyze 단계에 2~3, Collect·Scan 단계에 1~2, Report 단계에 0을 권한다 [25].
서버는 모델이 이 값을 주지 않으면 0으로 채우고 상한을 두지 않는다 [26][27].
이 값은 `misc.record_curiosity_probe`의 기록 수만 제한하고 분석 도구 실행은 제한하지 않는다(D05.01) [27].
그 뒤 P02.02의 규칙과 P01.04의 증거 종류 대조로 작업 지시를 고친다.

`reason.plan`은 에이전트가 준 사건 설명과 사전 조사 출력으로 모델에게 우선순위가 있는 조사 계획과 처음 실행할 도구 3~5개를 받는다 [28].
`reason.advise`는 분석가의 질문과 상황으로 모델의 조언과 `priority_tools`를 받는다 [29].
두 도구의 모델은 `REASON_BACKEND`·`ANTHROPIC_API_KEY`·`REASON_URL`로 정한다 [30].
`reason.plan`·`reason.advise`의 `priority_tools`는 증거 종류와 대조하지 않고 돌려준다 [28][29].
`reason.draft_command`는 분석가의 작업 문장을 도구 호출 후보로 바꾸기만 하고 실행하지 않는다 [31].
서버 밖 클라이언트 모델이 세우는 계획은 이 상세에 넣지 않는다.

**예외.** 서버를 다시 시작한 뒤 다른 기록 호출보다 먼저 부른 `dair.assess`는 호출 기록을 다시 읽기 전에 모델 입력을 만든다 [21][32].
그때는 에이전트가 보낸 단계 스택을 쓰고 증거 종류와 남은 작업 지시 없이 모델에게 계획을 받는다 [20][32].
P01.04에서 본 대로 증거 종류 판별이 일부만 훑었거나 다른 폴더를 봤으면 처방 모델은 그 종류 목록에 맞춰 작업을 권한다 [20].

def missing_report_phases(entries) -> list:
    """Phases a static investigation must have transited before Report:
    Collect AND Analyze always; Scan additionally when host candidate pivots
    exist (a lead to other hosts demands the sweep). [] when satisfied or when
    this is a live-monitoring investigation trace."""
    if _is_live_monitoring_trace(entries):
        return []
    entered = _phases_entered(entries)
    required = ["Collect", "Analyze"]
    if any(isinstance(pv, dict) and str(pv.get("kind") or "").lower() == "host"
           for e in (entries or []) if isinstance(e, dict) and e.get("type") == "dair_call"
           for pv in (e.get("candidate_pivots") or [])):
        required.append("Scan")
    return [ph for ph in required if ph not in entered]

def prescribe_for_gaps(entries) -> list:
    """Collection tools for the lifecycle phases still `not_examined`, deduped and
    filtered to those not already run (by binary signature). Empty when every
    phase is at least examined — the signal that the phase's work is done and the
    investigation can advance rather than backfill."""
    cov = coverage(entries)
    from tools._gates.work_order import _binary_sig
    succ = [(e.get("cmd") or "").lower() for e in (entries or [])
            if e.get("type") == "tool_call" and e.get("success") is not False and e.get("cmd")]
    out: list = []
    for pid in LIFECYCLE:
        if cov[pid]["status"] != "not_examined":
            continue
        for t in COLLECT_TOOLS.get(pid, []):
            if t in out:
                continue
            sig = _binary_sig(t)
            if sig and any(sig in c for c in succ):     # tool already ran anywhere
                continue
            out.append(t)
    return out
