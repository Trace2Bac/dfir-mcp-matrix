# P04 조사 단위 관리

### P04.01 사건 시작 시 ID 확정

**구현.** 조사 단위는 사건이고 사건 ID는 `misc.start_execution_log`가 받은 `case_id`다 [1].
이 도구는 `case_id`와 호출 기록 경로를 `log.configure`에 넘긴다 [1].
`configure`는 그 경로에 같은 `case_id`의 호출 기록이 있으면 다시 읽어 이어 쓰고 없으면 새 호출 기록을 시작한다 [2].
그 뒤 기록 함수는 모두 모듈 전역 객체 `log`에 설정된 호출 기록 하나에 쓰고 증거 도구는 사건 인자를 받지 않는다 [3].
`configure`는 `case_id`와 호출 기록의 절대 경로를 캐시 폴더의 `session.json`에 적는다 [4].

live-monitoring 도구는 같은 `configure`로 호출 기록을 바꾼다 [5][6].
`monitor.start_investigation`은 `<사건>/analysis/<사건>_<INV-NNN>_trace.json`으로, `monitor.end_investigation`은 사건 전체 호출 기록으로 `configure`를 다시 부른다 [5][6].
`monitor.*`·`respond.*` 도구는 호출마다 `case_id`를 받아 폴더를 정하지만 열린 호출 기록의 사건과 대조하지 않는다 [7][8].
사건 안의 조사 ID는 `monitor.extend_investigation`만 열린 조사와 대조한다 [9].

**한계.** 서버는 정적 사건의 `case_id` 값을 검사하지 않아 빈 문자열도 받는다 [1][2].
이미 있는 호출 기록 경로에 다른 `case_id`를 주면 `configure`는 경고만 쓰고 빈 목록으로 새로 시작한다 [2].
그러나 파일에 쓸 때 메모리에 없는 디스크 항목을 훅이 쓴 항목으로 보고 모두 합쳐 쓰므로 앞 사건의 항목이 새 `case_id` 아래에 남는다 [10].

### P04.02 호출마다 사건 ID 전달·검사

**구현.** 이 방식은 live-monitoring 사건 안의 조사 단위 `INV-NNN`에 적용되고 조사에 경보를 더하는 `monitor.extend_investigation`에 있다 [9].
`monitor.extend_investigation`은 인자 `investigation_id`를 사건의 열린 조사 기록 `monitoring/_open_investigation.json`에 적힌 `investigation_id`와 대조한다 [9].
값이 다르거나 열린 조사 기록이 없으면 경보를 더하지 않고 거부한다 [9].

**한계.** 조사를 닫는 `monitor.end_investigation`은 받은 `investigation_id`가 열린 조사 기록의 값과 다르거나 열린 조사 기록이 없어도 응답에 `warning`만 붙이고 닫기를 계속한다 [11].
받은 ID의 조사 호출 기록 파일이 없으면 그때 열려 있는 호출 기록을 그 ID 이름의 보고서로 내보낸다 [12].
그다음 열린 조사 기록 파일을 지우므로 다른 조사가 열려 있었다면 그 조사의 열린 조사 기록이 닫는 절차 없이 사라진다 [11].
조사를 여는 `monitor.start_investigation`은 다른 조사가 열려 있는지 확인하지 않고 열린 조사 기록을 새 값으로 덮어쓴다 [13].
이때 앞 기록의 `opened_at_utc`와 `extended_at_utc`를 새 기록에 그대로 옮겨 적는다 [13].

### P04.03 폴더·DB·manifest에 사건 ID 연결

**구현.** 호출 기록 JSON 파일의 머리에 `case_id`를 적는다 [14].
`misc.export_execution_log`가 쓰는 JSON 머리와 Markdown 제목에도 `case_id`가 들어간다 [15][16].
발견사항 검토에 쓰는 근거 묶음은 `case_id`와 호출 기록의 실제 경로를 사건 식별값으로 싣는다 [17].
live-monitoring 사건은 `<사건>_<INV-NNN>_trace.json`처럼 사건 ID를 호출 기록과 보고서 파일 이름에 넣는다 [6].

**한계.** 호출 기록 안의 `tool_call` 항목에는 사건 필드가 없고 그 파일 안에 있다는 사실로만 사건에 이어진다 [18].
원래 출력 사본은 `.tool_output/<call_id>.txt`라 이름에 사건 ID가 없다 [19].
백그라운드 작업 상태 파일과 해시 캐시 항목에도 사건 필드가 없다 [20][21].
도구 출력 파일과 최종 보고서는 모델이 준 경로와 내용으로 쓰고 서버가 사건 ID를 붙이지 않는다 [22].

### P04.04 사건별 폴더·DB 분리

**구현.** live-monitoring 도구는 `case_id`로 `TRUDI_CASES_ROOT/<case_id>` 폴더를 정하고 그 아래 `monitoring/`·`analysis/`·`reports/`에 상태와 호출 기록을 둔다 [7][6].
`case_id`에 `/`나 `..`가 있으면 거부한다 [7].
정적 사건은 사용자가 `case-template`을 `~/cases/<CASE_ID>`로 복사해 사건 폴더를 만든다 [23].
서버는 모델이 준 호출 기록 경로를 쓰고 원래 출력 사본은 그 호출 기록과 같은 폴더의 `.tool_output/`에 둔다 [19].
그래서 사건마다 다른 폴더의 호출 기록을 쓰면 원래 출력도 사건마다 나뉜다 [19].

**한계.** 캐시 폴더는 기계 전체에 하나이고 `session.json`, 호출 번호 카운터, 해시 캐시, 파일 기반 작업 상태가 모두 여기에 놓인다 [24].
호출 번호는 기계 전체에서 한 순서로 매겨 한 사건의 번호가 1부터 이어지지 않는다 [25].
해시 캐시는 경로, 크기, 시각, inode를 키로 써서 앞 사건에서 계산한 해시가 지금 사건의 호출 기록에 캐시 적중으로 들어간다 [21].
파일 기반 작업은 끝난 결과를 `misc.job_status`를 부른 때 설정된 호출 기록에 쓴다 [20].
사건 A에서 시작한 `net.tcpxtract_streams` 작업을 사건 B로 바꾼 뒤 조회하면 결과가 B의 호출 기록에 들어간다 [20][26].
같은 경로에 다른 사건 ID를 주면 두 사건의 항목이 한 파일에 합쳐진다 [10].
`monitor.end_investigation`이 조사 보고서에 붙이는 대응 조치 절은 사건 전체의 제안 파일 `suggestions/ACT-*.json`과 실행 기록 `executions/ACT-*.json`을 모두 읽으므로 같은 사건의 다른 조사 조치까지 싣는다 [27].

### P04.06 동시 작업의 사건 문맥 검사

**구현.** `misc.submit_finding`은 시작할 때 사건 식별값(`case_id`와 호출 기록 실제 경로)을 읽어 둔다 [28].
근거를 모은 뒤와 검토 모델의 답을 받은 뒤 이 값을 다시 비교하고 다르면 발견사항을 기록하지 않는다 [28][29].
같은 제출 키의 검토가 1시간 lease 안에 진행 중이면 다시 받지 않고 기록 직전에 lease 주인이 바뀌었으면 기록하지 않는다 [30].

**한계.** 백그라운드 작업은 시작한 사건을 기억하지 않는다.
서버 프로세스 안의 작업은 끝날 때 그때 설정된 호출 기록에 결과를 쓴다 [31].
파일 기반 작업도 `misc.job_status`를 부른 때의 호출 기록에 쓴다 [20].
그래서 작업 중에 사건을 바꾸면 결과가 바뀐 사건에 기록되고 이를 막는 검사는 없다 [20][31].

```python
async def _run_as_job(jobs, mode: str, tool_name: str, args: dict, invoke):
    """Run a long tool as an in-process background task. Returns ("done",
    result) when it finishes within the inline wait (a short run stays a
    normal call), else a job handle. The task is created while this call's
    context (tool identity) is set, so it logs exactly as a synchronous run."""
    started = {"flag": False}
    job_id = {"id": None}

    async def body():
        async with jobs.slots():
            started["flag"] = True
            if job_id["id"]:
                jobs.mark_state(job_id["id"], "running")
            return await invoke(True)

    task = asyncio.create_task(body())
    wait = 0 if mode == "always" else jobs.INLINE_WAIT
    if wait > 0:
        await asyncio.wait({task}, timeout=wait)
    if task.done():
        return ("done", task.result())          # re-raises a ToolError as before
    jid = jobs.register_task(tool_name, task, _arg_shapes(args))
    job_id["id"] = jid
    status = "running" if started["flag"] else "queued"
    jobs.mark_state(jid, status)
```
