# P04 조사 문맥 관리

### P04.01 사건 시작 시 ID 확정

**구현.** 조사 단위는 사건이고 사건 ID는 `misc.start_execution_log`가 받은 `case_id`다 [1].
이 도구는 `case_id`와 호출 기록 경로를 `log.configure`에 넘긴다 [1].
`configure`는 그 경로에 같은 `case_id`의 호출 기록이 있으면 다시 읽어 이어 쓰고 없으면 새 호출 기록을 시작한다 [2].
그 뒤 기록 함수는 모두 모듈 전역 객체 `log`에 설정된 호출 기록 하나에 쓰고 증거 도구는 사건 인자를 받지 않는다 [3].
`configure`는 `case_id`와 호출 기록의 절대 경로를 캐시 폴더의 `session.json`에 적는다 [4].

live-monitoring 도구는 같은 `configure`로 호출 기록을 바꾼다 [5][6].
`monitor.start_investigation`은 `<사건>/analysis/<사건>_<INV-NNN>_trace.json`으로, `monitor.end_investigation`은 사건 전체 호출 기록으로 `configure`를 다시 부른다 [5][6].
`monitor.*`·`respond.*` 도구는 호출마다 `case_id`를 받아 폴더를 정하지만 열린 호출 기록의 사건과 대조하지 않아 P04.02에는 연결하지 않는다 [7][8].

**예외.** 서버는 정적 사건의 `case_id` 값을 검사하지 않아 빈 문자열도 받는다 [1][2].
이미 있는 호출 기록 경로에 다른 `case_id`를 주면 `configure`는 경고만 쓰고 빈 목록으로 새로 시작한다 [2].
그러나 파일에 쓸 때 메모리에 없는 디스크 항목을 훅이 쓴 항목으로 보고 모두 합쳐 쓰므로 앞 사건의 항목이 새 `case_id` 아래에 남는다 [9].

### P04.03 폴더·DB·manifest에 사건 ID 연결

**구현.** 호출 기록 JSON 파일의 머리에 `case_id`를 적는다 [10].
`misc.export_execution_log`가 쓰는 JSON 머리와 Markdown 제목에도 `case_id`가 들어간다 [11][12].
발견사항 검토에 쓰는 근거 묶음은 `case_id`와 호출 기록의 실제 경로를 사건 식별값으로 싣는다 [13].
live-monitoring 사건은 `<사건>_<INV-NNN>_trace.json`처럼 사건 ID를 호출 기록과 보고서 파일 이름에 넣는다 [6].

**예외.** 호출 기록 안의 `tool_call` 항목에는 사건 필드가 없고 그 파일 안에 있다는 사실로만 사건에 이어진다 [14].
원래 출력 사본은 `.tool_output/<call_id>.txt`라 이름에 사건 ID가 없다 [15].
백그라운드 작업 상태 파일과 해시 캐시 항목에도 사건 필드가 없다 [16][17].
도구 출력 파일과 최종 보고서는 모델이 준 경로와 내용으로 쓰고 서버가 사건 ID를 붙이지 않는다 [18].

### P04.04 사건별 폴더·DB 분리

**구현.** live-monitoring 도구는 `case_id`로 `TRUDI_CASES_ROOT/<case_id>` 폴더를 정하고 그 아래 `monitoring/`·`analysis/`·`reports/`에 상태와 호출 기록을 둔다 [7][6].
`case_id`에 `/`나 `..`가 있으면 거부한다 [7].
정적 사건은 사용자가 `case-template`을 `~/cases/<CASE_ID>`로 복사해 사건 폴더를 만든다 [19].
서버는 모델이 준 호출 기록 경로를 쓰고 원래 출력 사본은 그 호출 기록과 같은 폴더의 `.tool_output/`에 둔다 [15].
그래서 사건마다 다른 폴더의 호출 기록을 쓰면 원래 출력도 사건마다 나뉜다 [15].

**예외.** 캐시 폴더는 기계 전체에 하나이고 `session.json`, 호출 번호 카운터, 해시 캐시, 파일 기반 작업 상태가 모두 여기에 놓인다 [20].
호출 번호는 기계 전체에서 한 순서로 매겨 한 사건의 번호가 1부터 이어지지 않는다 [21].
해시 캐시는 경로, 크기, 시각, inode를 키로 써서 앞 사건에서 계산한 해시가 지금 사건의 호출 기록에 캐시 적중으로 들어간다 [17].
파일 기반 작업은 끝난 결과를 `misc.job_status`를 부른 때 설정된 호출 기록에 쓴다 [16].
사건 A에서 시작한 `net.tcpxtract_streams` 작업을 사건 B로 바꾼 뒤 조회하면 결과가 B의 호출 기록에 들어간다 [16][22].
P04.01에서 본 대로 같은 경로에 다른 사건 ID를 주면 두 사건의 항목이 한 파일에 합쳐진다 [9].

### P04.06 동시 작업의 사건 문맥 검사

**구현.** `misc.submit_finding`은 시작할 때 사건 식별값(`case_id`와 호출 기록 실제 경로)을 읽어 둔다 [23].
근거를 모은 뒤와 검토 모델의 답을 받은 뒤 이 값을 다시 비교하고 다르면 발견사항을 기록하지 않는다 [23][24].
같은 제출 키의 검토가 1시간 lease 안에 진행 중이면 다시 받지 않고 기록 직전에 lease 주인이 바뀌었으면 기록하지 않는다 [25].

**예외.** 백그라운드 작업은 시작한 사건을 기억하지 않는다.
서버 프로세스 안의 작업은 끝날 때 그때 설정된 호출 기록에 결과를 쓴다 [26].
파일 기반 작업도 `misc.job_status`를 부른 때의 호출 기록에 쓴다 [16].
그래서 작업 중에 사건을 바꾸면 결과가 바뀐 사건에 기록되고 이를 막는 검사는 없다 [16][26].

### P04.08 프로세스 메모리에만 보관

**구현.** 다음 상태는 서버 프로세스 메모리에만 있고 프로세스가 끝나면 사라진다 [27].
알림 판단 상태 `_ritual`, 반복 호출 상태 `_repeat_state`, 작업 상태 연속 조회 수 `_poll_run`이 미들웨어에 있다 [27].
서버 프로세스 안에서 실행되는 백그라운드 작업 목록 `_TASK_JOBS`, 증거 종류 탐색 결과 캐시, 마지막 `dair_call` 번호 `_last_dair_cid`도 메모리에만 있다 [27].
호출 기록 항목과 단계 스택도 메모리의 `log`에 있지만 P04.09처럼 파일에도 쓴다 [3].
서버는 stdio로 클라이언트 하나와 연결하고 이 상태를 모듈 전역 객체에 두어 세션마다 나누지 않으므로 P04.05에는 연결하지 않는다 [3][28].

### P04.09 조사 상태를 파일·DB에 저장

**구현.** 호출 기록은 사건 ID, 항목 수, 모든 항목을 담은 JSON 파일이고 항목을 더할 때마다 임시 파일에 쓴 뒤 이름을 바꿔 덮어쓴다 [10][29].
`TRUDI_TRACE_FSYNC`가 `0`이 아니면 쓸 때마다 fsync한다 [29].
단계 전이는 `dair_call`과 `phase_transition` 항목으로 이 파일에 남는다 [30].
도구의 전체 표준 출력은 `.tool_output/<call_id>.txt`에 쓴다 [15].
캐시 폴더에는 마지막 사건을 가리키는 `session.json`, 호출 번호 카운터, 해시 캐시, 파일 기반 작업 상태가 남는다 [4][20].
live-monitoring 사건은 열린 조사 `_open_investigation.json`과 조사 번호 카운터를 `monitoring/`에 둔다 [31].
`reason.audit_findings`는 감사한 서술 ID, 서술별 digest, 발견사항과 모델 문맥의 digest, 후보 결과를 자기 `reason_call` 항목에 남긴다 [32].
다음 호출은 발견사항과 모델 문맥, 감사한 서술이 그대로이면 아직 감사하지 않은 서술만 모델에 보낸다 [32].
감사할 서술이 남지 않은 뒤 바뀐 것이 없으면 모델을 부르지 않고 저장된 결과를 돌려준다 [32].
발견사항 저장은 D05에서 본다.

### P04.10 재시작 뒤 자동 복구

**구현.** 서버를 다시 시작하면 메모리의 `log`는 비어 있다 [3].
기록 함수가 처음 불릴 때 `_auto_recover`가 `session.json`의 `case_id`와 경로로 `configure`를 불러 호출 기록을 다시 읽는다 [33].
`session.json`이 없으면 현재 폴더에 `CLAUDE.md`와 `analysis/*_trace.json`이 있을 때 그 호출 기록을 다시 읽는다 [34].
다시 읽을 때 항목을 메모리로 올리고 `dair_call`과 `phase_transition`을 차례로 다시 적용해 단계 스택을 되살리고 호출 번호 카운터를 맞춘다 [2][30][35].
`_last_dair_cid`, 반복 호출 상태, 서버 프로세스 안의 백그라운드 작업은 되살리지 않는다 [27].
파일 기반 작업은 상태 파일이 남아 서버를 다시 시작한 뒤에도 `misc.job_status`로 조회한다 [16].

**예외.** 다시 읽기는 기록 함수 안에서만 실행된다 [33].
도구를 부르기 전에 미들웨어가 하는 단계 검사와 `dair.assess`의 입력 구성은 메모리의 `log`를 바로 읽는다 [36][37].
그래서 서버를 다시 시작한 뒤 다른 기록 호출보다 먼저 온 증거 도구 호출은 Report 단계였어도 빈 호출 기록으로 보고 통과한다 [36].
같은 때 부른 `dair.assess`는 에이전트가 보낸 단계 스택으로 처방 모델을 부른다 [37].
`session.json`으로 되살릴 때 현재 폴더와 대조하지 않아 마지막으로 연 다른 사건의 호출 기록에 이어 쓴다 [33].
현재 폴더로 되살릴 때는 `analysis/*_trace.json` 가운데 이름순 첫 파일을 고르고 파일 이름에서 `_trace.json`을 뗀 값을 사건 ID로 쓴다 [34].
live-monitoring 사건에서는 `<사건>_INV-001_trace.json`이 `<사건>_trace.json`보다 앞에 와 `<사건>_INV-001`을 사건 ID로 쓴다 [6][34].
그 파일 머리의 `case_id`와 다르므로 `configure`는 새 호출 기록으로 시작하고 디스크 항목을 합쳐 쓴다 [2][9].

### P04.11 만료

**구현.** 반복 호출 상태는 키 512개를 넘으면 가장 오래된 키를 버린다 [38].
증거 종류 탐색 결과는 300초가 지나면 다시 탐색한다 [39].
`misc.submit_finding`의 검토 lease는 3,600초가 지나면 같은 제출 키로 다시 검토할 수 있다 [25].
호출 기록, 해시 캐시, 파일 기반 작업 상태에는 유효 시간이나 개수 한도가 없다 [10][17][16].

async def _run_as_job(jobs, mode: str, tool_name: str, args: dict, invoke):
    """Run a long tool as an in-process background task. Returns ("done",
    result) when it finishes within the inline wait (a short run stays a
    normal call), else a job handle. The task is created while this call's
    context (tool identity) is set, so it logs exactly as a synchronous run."""
    started = {"flag": False}
    job_id = {"id": None}

    async def body():
        async with jobs.slots():
            started["flag"] = True
            if job_id["id"]:
                jobs.mark_state(job_id["id"], "running")
            return await invoke(True)

    task = asyncio.create_task(body())
    wait = 0 if mode == "always" else jobs.INLINE_WAIT
    if wait > 0:
        await asyncio.wait({task}, timeout=wait)
    if task.done():
        return ("done", task.result())          # re-raises a ToolError as before
    jid = jobs.register_task(tool_name, task, _arg_shapes(args))
    job_id["id"] = jid
    status = "running" if started["flag"] else "queued"
    jobs.mark_state(jid, status)
