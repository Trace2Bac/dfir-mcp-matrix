# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 외부 도구를 실행기로 실행해 그 결과를 돌려주는 도구와, 서버가 파일을 직접 읽어 결과를 만드는 도구 일부가 이 방식을 쓴다.
실행기는 실행한 명령 줄을 결과의 `cmd`에 싣고 그 안에 증거 경로 인자가 들어 있다 [1].
예를 들어 Volatility 도구의 공통 함수 `_vol`은 메모리 이미지 경로를 `-f` 인자로 넘긴다 [2].
서버가 직접 읽는 도구 가운데 `hash.file`·`yara.scan_file`은 읽은 파일 경로를 `file`에 싣는다 [3].
`net.http_session_inventory`·`net.pcap_identity_timeline`은 패킷 캡처 경로를 `pcap`에 싣는다 [4].
`misc.cs_beacon_config`는 설정을 찾은 파일 경로를 결과 항목마다 `file`에 싣는다 [5].

이 밖의 도구에는 입력 경로가 응답에 없는 경우가 있다.
`misc.evtx_filter`는 입력 EVTX 경로를 호출 기록의 `cmd`에만 적고 응답에는 싣지 않는다 [6].
응답마다 붙는 `_trudi_call_id`는 호출 기록 항목의 번호이고 그 항목의 `cmd`에 증거 경로가 남는다 [7].
호출 기록 항목을 MCP 도구로 돌려주는 조회는 찾지 못했다.
마운트한 볼륨을 대상으로 실행되는 도구의 `cmd`에는 마운트 폴더 경로가 들어가고 원래 이미지 경로는 마운트한 호출의 `cmd`에만 있다 [1].

**한계.** `cmd`는 인자를 공백 하나로 이어 붙인 문자열이고 따옴표를 넣지 않는다 [1].
그래서 증거 경로에 공백이 있으면 `cmd`에서 그 경로와 다른 인자의 경계가 남지 않는다 [1].
서버의 출력 읽기 코드도 따옴표 없이 기록된 경로가 여러 조각으로 나뉜다고 적고 실제로 있는 경로가 될 때까지 조각을 이어 붙여 경로를 추정한다 [8].

### R05.02 증거 내부 경로

**구현.** 파일 시스템 목록을 돌려주는 `tsk.fls`, MFT 기록을 읽는 `af.timestomp_drift`, 예약 작업 폴더를 읽는 `misc.parse_scheduled_tasks`, 폴더를 훑는 `hash.directory`·`yara.scan_directory`가 이 방식을 쓴다 [9][10][11][12].
`tsk.fls`는 `fls` 출력을 실행기 결과의 `stdout`으로 그대로 돌려주고 `-p`를 주지 않는다 [9].
Sleuth Kit 4.11.1의 `fls`는 `-p`가 없으면 경로의 폴더 단계마다 `+`를 하나씩 출력하고 상위 폴더 경로 없이 이름만 적는다 [13].
그래서 항목의 증거 안 경로는 앞선 폴더 줄을 따라가 맞춰야 한다.
`af.timestomp_drift`는 MFTECmd CSV의 `ParentPath`와 `FileName`을 이어 결과 항목의 `path`에 싣는다 [10].
`misc.parse_scheduled_tasks`는 작업 파일 경로에서 `tasks_dir`를 뺀 값을 결과 항목의 `task`에 싣는다 [11].
`hash.directory`·`yara.scan_directory`의 항목 `file`은 호스트에서 읽은 경로이므로 마운트한 볼륨을 주면 마운트 폴더 뒤에 이미지 안 경로가 붙은 값이다 [12].

**한계.** `tsk.fls`에 `inode`를 주면 `fls`는 그 폴더부터 나열한다 [9].
응답에는 그 폴더의 증거 안 경로가 없고 `cmd`에 inode 번호만 남으므로 나열한 이름의 위치를 응답만으로 알 수 없다 [9].
`misc.parse_scheduled_tasks`의 응답에는 `tasks_dir`가 없어 `task`가 어느 폴더 기준의 경로인지 응답에 남지 않는다 [11].
같은 도구는 읽지 못한 작업의 `task`에는 `tasks_dir`를 뺀 값이 아니라 호스트 전체 경로를 적는다 [11].

### R05.03 레코드 키·번호

**구현.** `tsk.fls`, `-r json`으로 실행되는 Volatility 도구, `af.timestomp_drift`의 결과가 이 방식을 쓴다 [9][2][10].
`tsk.fls` 출력은 줄마다 이름 앞에 메타데이터 주소(inode)를 적는다 [13].
Volatility 도구는 플러그인을 `-r json`으로 실행한다 [2].
Volatility 3 2.28.2의 JSON 출력은 행마다 열 이름을 키로 한 객체를 만들고 `windows.pslist`의 열에는 `PID`가 있다 [14].
`af.timestomp_drift`는 MFTECmd CSV의 `EntryNumber`를 결과 항목의 `mft_record`에 싣는다 [10].
`net.pcap_identity_timeline`의 `order`는 포트로 거른 tcpdump 출력 안 패킷 블록의 차례로 서버가 매긴 번호라 패킷 캡처 안 패킷 번호가 아니다 [15].

**한계.** 실행기는 표준 출력을 150줄에서 자른다 [16].
Volatility 3 2.28.2는 이 JSON을 들여쓰기하고 키를 이름순으로 정렬해 쓰므로 객체 하나가 여러 줄에 걸치고 줄 상한에 걸리면 마지막 객체가 `PID` 줄 앞에서 끊길 수 있다 [14][16].
`af.timestomp_drift`는 `EntryNumber`와 `MftRecord`가 모두 비어 있으면 `mft_record`를 0으로 적는다 [10].
NTFS에서 레코드 번호 0은 MFT 자신의 레코드여서 이 값은 실제와 다른 레코드를 가리킨다.

### R05.04 바이트·섹터·행 오프셋

**구현.** 파티션 표를 돌려주는 `tsk.mmls`, YARA 검사 도구 `yara.scan_file`·`yara.scan_directory`, 비컨 설정을 찾는 `misc.cs_beacon_config`의 결과가 이 방식을 쓴다 [17][18][5].
`tsk.mmls`는 `mmls` 출력을 그대로 돌려준다 [17].
Sleuth Kit 4.11.1의 `mmls`는 파티션마다 시작 섹터, 끝 섹터, 길이를 섹터 단위로 적는다 [19].
`yara.scan_file`·`yara.scan_directory`는 일치한 규칙의 문자열마다 `offset`을 싣는다 [18].
`misc.cs_beacon_config`는 설정을 찾은 파일 안 바이트 위치를 `offset`·`offset_hex`에 싣는다 [5].
입력이 서버가 뽑은 덤프 파일이면 이 값은 그 덤프 안의 위치다.
Volatility 프로세스 객체의 `Offset(V)`는 가상 주소라 이미지 안 바이트 위치가 아니다 [14].
`strings.extract`는 `strings`를 오프셋 옵션 없이 실행해 문자열만 돌려준다 [20].

**한계.** YARA 결과의 `offset`은 문자열마다 `instances`의 첫 항목 하나에서만 가져온다 [18].
yara-python 4.5.4는 한 문자열이 맞은 위치마다 항목을 하나씩 `instances`에 넣으므로 같은 문자열의 두 번째 이후 위치는 응답에 없다 [21].

### R05.05 참조 지식 원문 출처

**구현.** 이 방식은 MITRE ATT&CK 표에서 후보를 고르는 `correlate.mitre_map`과 `attribution.attribute_actors`에 적용된다 [22][23].
`correlate.mitre_map`은 모델이 준 글을 기법마다 정한 `keywords`와 대조하고 맞은 기법마다 ATT&CK 기법 ID `technique_id`를 싣는다 [22].
`attribution.attribute_actors`는 호출 기록의 발견사항에서 모은 기법 ID와 겹치는 ATT&CK 그룹마다 그룹 ID `group_id`를 싣는다 [23].
두 표의 키는 표를 만드는 `build_mitre_cache`가 MITRE CTI STIX 객체의 `external_references` 가운데 `source_name`이 `mitre-attack`인 항목의 `external_id`로 정한다 [24].
그래서 두 값은 모델이 준 값을 되풀이한 것이 아니라 표에서 고른 ATT&CK 원문 ID다 [22][23][24].

### R05.06 참조 지식과 증거 결과 구분

**구현.** 이 방식은 미들웨어가 도구 응답에 덧붙이는 FK 지식 시트의 내용에 적용된다 [25].
`enrich`는 지식 시트의 `caveats`·`field_meanings`·`advisories`·`corroboration`과 종료 코드의 뜻을 결과의 최상위 키가 아니라 하위 객체 `_metadata`에 넣는다 [26][27].
코드 주석은 이 해석 정보가 증거가 아닌 메타데이터라서 `_metadata`에 두고 인용되는 도구 결과에는 증거만 남긴다고 적는다 [26].
반복 호출 판정은 `enrich`가 덧붙이기 전의 결과로 해시를 계산한다 [25].

지식 시트가 붙지 않는 응답도 있다.
`vol.*`와 `ez.*` 일부 도구는 백그라운드 작업으로 실행될 수 있고 그때 미들웨어는 `enrich`를 부르기 전에 작업 핸들을 돌려준다 [28].
그 결과는 `misc.job_status`로 받고 이때 `enrich`는 도구 이름 `misc_job_status`로 호출되어 연결된 지식 시트가 없으므로 원래 도구의 지식 시트가 붙지 않는다 [25][29].
`enrich`가 처리 중 예외를 내면 결과를 바꾸지 않고 돌려주므로 그 응답에도 지식 시트가 붙지 않는다 [30].

MITRE 표에서 참조 지식을 돌려주는 `correlate.mitre_validate`·`correlate.mitre_map`은 기법 이름과 tactic을 결과 본문에 싣고 이 구분을 쓰지 않는다 [22].
`correlate.mitre_validate`는 기법 설명도 결과 본문에 싣는다 [22].
두 도구는 이름이 `correlate_`로 시작해 제어 도구로 분류되므로 `_metadata`에 아무 표시도 붙지 않는다 [31].
`correlate.mitre_validate`의 `technique_id`는 모델이 준 값을 되풀이한 것이라 R05.05에서는 `correlate.mitre_map`만 본다 [22].
외부 위협 정보를 조회하는 `enrich.vt_lookup_hash`·`enrich.vt_lookup_ip`·`enrich.vt_lookup_domain`·`enrich.abuseipdb_check`·`enrich.machinae_lookup`도 VirusTotal·AbuseIPDB·machinae에서 받은 참조 지식을 결과 본문에 싣고 이 구분을 쓰지 않는다 [32].
이 도구들은 이름이 제어 도구 목록에 없어 증거 도구 출력과 같은 `data_provenance` 값 `tool_output_may_contain_untrusted_evidence`를 받는다 [31].
