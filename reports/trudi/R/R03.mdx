# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 외부 도구 실행기 `run`·`run_with_progress`·`run_with_output_file`의 결과는 `success`와 `exit_code`를 싣는다 [1].
종료 코드 정책을 둔 도구는 정책에 맞는 종료 코드를 성공으로 보고 그 코드의 뜻을 `exit_meaning`에 적는다 [1][2].
EZ Tools 실행은 출력에 처리되지 않은 .NET 예외가 있으면 종료 코드와 관계없이 `success`를 거짓으로 두고 `status`를 `error`나 `tool_unavailable`로 둔다 [3].
선택 설치 도구가 없으면 `status: tool_unavailable`과 `tool_unavailable: true`를 돌려준다 [4].
서버 프로세스 안에서 실행되는 `yara.scan_file`·`read.output` 같은 도구도 `success`와 `error`를 싣는다 [5][6].
도구 함수가 낸 예외는 FastMCP 3.4.7이 `ToolError`로 바꾸고 미들웨어는 인자 검사 오류처럼 `ToolError`가 아닌 예외만 `ToolError`로 바꾼다 [7][8].
미들웨어의 게이트도 호출을 거부할 때 `ToolError`를 낸다 [8].
FastMCP 3.4.7에서 `ToolError`는 MCP 오류 결과(`isError`)가 된다 [9].
게이트 이름은 오류 문구 안에만 있다 [8].

**한계.** `ewf.verify`는 검증 결과를 `status`에 `verified`·`verification_failed`·`error`로 적는다 [10].
이 도구는 늘 백그라운드 작업으로 실행되므로 호출은 작업 핸들을 돌려주고 결과는 `misc.job_status`로만 받는다 [11].
`misc.job_status`는 도구 결과 위에 `status: finished`를 덮어써서 해시가 맞지 않은 검증도 `status`로는 `finished`가 된다 [12].
이때 `verified`와 `exit_meaning`은 남는다 [10][12].
`strings.extract`는 UTF-16LE 문자열 추출이 실패해도 ASCII 문자열 추출 결과만으로 `success`를 정한다 [13].

### R03.02 찾지 못함과 실패 구분

**구현.** 종료 코드 정책을 둔 `ngrep`·`grep`·`clamscan`·`mraptor` 실행은 일치 없음을 성공으로 두고 `exit_meaning`에 `no frames matched`·`no matches` 같은 뜻을 적어 오류 종료 코드와 가른다 [2].
`strings.grep`은 파일이 없으면 `success: false`와 `error`를, 파일을 끝까지 훑었는데 일치가 없으면 `match_count: 0`과 `complete: true`를 돌려준다 [14][15].
`yara.scan_file`은 일치가 없으면 `success: true`와 `match_count: 0`을, 규칙 컴파일이나 검사에서 예외가 나면 `success: false`와 `error`를 돌려준다 [5].
`read.output`은 파일이 없으면 `success: false`와 `error`를, 일치하는 행이 없으면 빈 `body`의 성공 응답을 돌려준다 [6].

`misc.evtx_filter`는 둘을 가르지 않는다 [16].
이 도구는 이벤트를 하나도 읽지 못하면 `success: false`를 돌려주지만 오류 문구를 싣지 않아 빈 로그와 evtx_dump.py 실패가 같은 응답이 된다 [16].

`enrich.vt_lookup_hash`는 HTTP 상태 코드가 404이면 `found: false`를, 요청이나 본문 해석에서 예외가 나면 `success: false`와 `error`를 돌려준다 [17].
`enrich.vt_lookup_ip`·`enrich.vt_lookup_domain`·`enrich.abuseipdb_check`는 HTTP 상태 코드를 보지 않고 응답 본문을 결과로 읽는다 [18].
세 도구는 본문을 JSON으로 읽지 못할 때만 `success: false`를 돌려준다 [18].

**한계.** `read.output`이 파일을 읽다가 오류를 만나면 행 검색 함수가 빈 문자열을 돌려준다 [19].
`read.output`은 그것을 일치 없음과 같은 빈 `body`의 성공 응답으로 낸다 [6][19].
`enrich.vt_lookup_hash`는 404가 아닌 상태 코드를 보지 않는다 [17].
그래서 인증 실패나 요청 수 제한 응답의 본문이 JSON이면 `success: true`, `found: true`와 탐지 수 0을 싣는다 [17].

### R03.03 입력별 성공·실패·생략 목록

**구현.** 여러 입력을 처리하는 도구 일부가 입력마다 상태를 싣는다.
`hash.directory`는 읽지 못한 파일을 `errors`에 파일과 오류로, 크기 상한을 넘어 건너뛴 파일을 `skipped`에 파일·크기·이유로 싣는다 [20].
상한에 걸려 멈추면 `truncation_reason`과 다음 시작 경로 `next_start_path`를 싣는다 [21].
`ez.recmd_batch`는 하이브마다 `hive`·`success`·`error`·`_trudi_call_id`를 `hives`에 싣고 성공·실패 수를 센다 [22].
`yara.scan_directory`는 검사하지 못한 파일을 파일과 오류로 `errors`에 싣는다 [23].
`ez.pecmd`의 libscca 대체 파서는 파싱하지 못한 Prefetch 파일을 "파일 이름: 이유" 문자열로 `parse_failures`에 싣는다 [24].

외부 도구에 폴더를 넘기는 도구는 다르다.
`ez.mftecmd_dir`·`ez.evtxecmd`는 실행기 결과만 돌려주고 외부 도구가 처리하지 못한 파일을 서버가 따로 가려 싣지 않는다 [25].
`misc.cs_beacon_config`는 서버 안에서 폴더의 파일을 훑으며 읽지 못한 파일을 `errors`에 모은다 [26].
응답에는 `errors`를 싣지 않고 `summary`에 훑은 파일 수와 전체 파일 수만 적는다 [27].
`errors`는 `output_path`의 전체 결과 JSON과 호출 기록의 표준 출력 사본에만 남는다 [27].

**한계.** `yara.scan_directory`는 오류 목록을 50개까지만 싣고 전체 오류 수는 싣지 않는다 [23].
`max_files`를 넘는 파일은 검사하지 않고 그 수도 알리지 않는다 [23].
`ez.recmd_batch`는 하이브를 `max_hives`개 찾으면 찾기를 멈추고 `capped: true`만 싣는다 [22][28].
그 뒤에 남은 하이브는 목록에도 수에도 나오지 않는다 [28].

### R03.04 시간 초과·부분 완료 표시

**구현.** 외부 도구 실행기 세 함수는 시간 제한을 넘기면 `timed_out: true`를 실패 결과에 싣는다 [29].
SSH 원격 쓰기 실행기도 같은 값을 싣는다 [30].
서버 프로세스 안에서 실행되는 도구에 거는 시간 제한 래퍼 `with_tool_timeout`은 제한을 넘기면 `success: false`·`timed_out: true`·`killed_after_seconds`를 돌려준다 [31].
분리 실행하는 carve 작업은 `timeout` 명령의 종료 코드 124를 시간 초과로 보고 `misc.job_status` 결과에 `timed_out`과 이미 만든 파일 수를 적은 `partial_output`을 싣는다 [32].
`hash.directory`는 시간 상한에 걸리면 `truncation_reason: max_seconds`와 이어서 시작할 경로를 싣는다 [33][21].
`strings.grep`은 시간 제한에 걸리면 `complete: false`와 `error: scan incomplete (timed out)`을 싣는다 [15].
`misc.evtx_filter`는 시간 예산을 넘기면 `wall_clock_timed_out: true`를, 건수 상한에 이르면 `cap_hit: true`를 싣는다 [16].

`reason.*`는 모델 API 호출이 시간 제한을 넘기면 예외 문구만 `error`에 싣고 시간 초과를 가리키는 필드는 없다 [34].

**한계.** `respond.execute_action`은 SSH 쓰기 실행기가 적은 `timed_out`을 응답의 `execution`에 옮기지 않는다 [30][35].
이 도구에서 시간 초과는 `success: false`와 `stderr` 문구로만 드러난다 [35].

### R03.05 실행 중 경과·생존 알림

**구현.** `vol.pslist`(PID를 주지 않은 경우)·`vol.psscan`·`vol.netstat`·`vol.netscan`·`vol.filescan` 5개는 `run_with_progress`로 Volatility를 실행한다 [36].
`run_with_progress`는 Volatility의 표준 오류 줄을 읽을 때마다 FastMCP `Context.report_progress`를 부른다 [37].
진행 값은 실행을 시작한 뒤 흐른 초, 전체 값은 시간 제한 초, 문구는 그 표준 오류 줄의 앞 120자다 [37].
서버 코드 주석은 Volatility 3가 `Progress:` 줄을 표준 오류에 쓴다고 적으므로 분석 진행 정도는 문구 안에만 있고 진행 값은 경과 시간이다 [38][37].
FastMCP 3.4.7의 `report_progress`는 요청에 진행 토큰이 있으면 그 토큰으로 MCP 진행 알림을 보낸다 [39].
`vol.*` 도구는 30초 안에 끝나지 않으면 백그라운드 작업이 되고 호출은 작업 핸들을 돌려주며 끝난다 [40].
코드 주석은 그 뒤의 진행 보고가 실패한다고 적는다 [37].
코드는 첫 실패에서 진행 보고를 멈춘다 [37].
다른 도구는 진행 알림을 보내지 않는다.
백그라운드 작업의 실행 중 상태와 경과 시간은 `misc.job_status`를 불러야 보이며 이것은 T08에서 본다 [41].

def _apply_exit_policy(result: dict, returncode: int,
                       success_codes, exit_meanings) -> None:
    """Map a returncode to success per the wrapper's declared policy
    (default: only 0 succeeds) and stamp the tool-specific meaning."""
    result["exit_code"] = returncode
    codes = success_codes if success_codes is not None else frozenset({0})
    result["success"] = returncode in codes
    meaning = (exit_meanings or {}).get(returncode)
    if meaning:
        result["exit_meaning"] = meaning
