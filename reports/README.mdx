# reports/ — 서버별 원고

이 폴더에는 서버별 원고가 있습니다. 서버마다 폴더가 하나씩 있고, 그 안에 셀마다 파일이 하나씩 있습니다.
원고 파일 하나에는 다음 내용을 씁니다.

- 그 서버가 셀의 어느 상세 항목에 해당하는지
- 그 방식을 어떻게 구현했는지(**구현**)와, 적용 범위 안에서 그 방식이 적용되지 않는 경로나 조건(**한계**)
- 위 설명을 뒷받침하는 기준 커밋의 코드 근거

구현 단락에는 그 방식이 적용되는 도구와 경로, 동작, 판정에 영향을 준 조건을 씁니다.
셀 정의에는 판정 기준과 다른 셀과 차이점만 있으므로 셀마다 더 적을 내용은 아래 [셀별로 원고에 적을 것](#셀별로-원고에-적을-것)에서 봅니다.

셀, 상세, 한계 단락 같은 용어는 [용어 사전](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/docs/glossary/README.mdx)에서 설명합니다.

```
reports/
└─ trudi/
   ├─ index.mdx        서버 개요: 저장소, 기준 커밋, 확인 방법
   ├─ coverage.mdx     (선택) 기능→셀 대응표. 머리말 tools에 기능 목록을 두고 tools/coverage.py가 본문 표를 만든다
   ├─ E/               축 폴더. 셀 번호의 첫 글자
   │  └─ E03.mdx       셀 E03
   ├─ T/
   │  └─ T03.mdx
   └─ …
```

아직 조사하지 않은 셀은 파일을 만들지 않습니다. 파일이 없는 셀에서 그 서버는 미확인이고, 셀 화면의 조사한 서버 수에 포함되지 않습니다.

## index.mdx

`index.mdx`에는 서버 전체에 공통인 정보를 씁니다. 저장소, 원고가 기준으로 삼는 커밋, 코드를 확인한 방법이 여기에 들어갑니다.

```markdown
---
server: trudi                                       # 폴더 이름과 같게
repo: nebulae/trudi                                 # GitHub 저장소
commit: 88fbca78186b6a0ca40423cf5e37a9dc46ae051e    # 원고가 인용하는 기준 커밋(40자)
matrix_version: "2026-10-06"                        # 이 원고가 기준으로 삼은 매트릭스 정의 버전(날짜)
---

# trudi 시범 전환 원고

**기준 커밋.** [`88fbca7`](https://github.com/nebulae/trudi/tree/88fbca7…)(날짜).
줄 번호는 모두 이 커밋 기준이다.

**확인 방법.** 코드를 어떻게 읽고 무엇을 실행했는지.
```

## \<축\>/\<셀ID\>.mdx

셀 하나의 원고입니다. 머리말의 `details`에 서버가 해당하는 상세를 적고, 본문에 상세마다 소제목을 하나씩 둡니다.

```markdown
---
cell: E03
details:                  # 이 서버가 해당하는 상세. 차례대로 아래 ### 소제목과 맞춘다
- id: E03.01
- id: E03.02
---

# E03 원본 변경 방지

### E03.01 실행 환경의 읽기 전용 강제

**구현.** 그 방식이 어느 도구·경로에 있고 어떻게 동작하는지 쓴다 [1].
문장 하나를 한 줄에 쓴다 [2].

이어지는 단락은 머리말 없이 빈 줄 뒤에 쓴다.

**한계.** 구현에 적은 적용 범위 안에서 그 방식이 적용되지 않는 경로나 조건 [3]. 없으면 이 단락을 쓰지 않는다.

### E03.02 서버 코드의 원본 쓰기 제한

**구현.** … [4].

### 근거

[1] 확인할 동작을 한 문장으로 쓴다.

@발췌 src/server.py:120-128

[2] 코드 위치가 셋 이상이면 링크만 둔다: [`src/a.py:10-12`](…), [`src/b.py:40`](…), [`src/c.py:7-9`](…).
```

서버가 어느 상세에도 해당하지 않으면 다음과 같이 씁니다.

- 머리말을 `details: [{id: not_implemented}]`(비적용이면 `not_applicable`)로 합니다.
- 본문에 `### 미구현`과 `**판단.** 왜 그런지 [1].`을 씁니다.

## 원고 작성 규칙

### 문장

낱말과 문장은 [작성 규칙](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/docs/writing-rules/README.mdx)을 따릅니다. 원고에 특히 필요한 것은 다음과 같습니다.

- **문장 하나를 한 줄에 씁니다.** 빈 줄은 단락 사이에만 둡니다. 화면은 원고의 줄바꿈을 그대로 보여 줍니다.
- 원고 문장은 "~다"로 끝나는 평서문으로 씁니다.
- 코드 이름이 든 문장에는 근거 표지 `[번호]`를 답니다.
- 원고는 그 셀만 다룹니다. 다른 셀의 내용은 그 셀의 원고에 쓰고, 다른 셀과 차이점은 셀 정의의 `boundary`에 있습니다.
- 그래서 본문에는 셀·상세 번호를 쓰지 않습니다. 번호는 머리말 `details`와 소제목에만 씁니다. 어느 상세에 연결하지 않았는지는 따로 쓰지 않고 그 이유가 된 사실만 씁니다.
- `[번호]`는 파일마다 1부터 시작해, 본문에 처음 나온 차례대로 매깁니다. 문장의 위치를 옮겼으면 `python tools/pilot.py renumber <서버>`를 실행해 번호를 다시 매깁니다.

### 소제목과 한계 단락

- 상세마다 소제목을 `### <상세 번호> <상세 이름>` 형식으로 씁니다.
- 원고는 상세 번호로 셀 정의와 연결됩니다. 그래서 소제목의 상세 이름이 셀 정의의 이름과 달라도 오류가 아니라 경고로 처리됩니다.
- 한계 단락에 무엇을 쓰는지는 [CONTRIBUTING.md](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/CONTRIBUTING.md#판단-기준)에 있습니다.

### 셀별로 원고에 적을 것

셀 정의에는 판정 기준만 있으므로, 판정과 별개로 원고에 꼭 적어야 하는 사실을 셀마다 여기에 모아 둡니다.

| 셀·상세 | 원고에 적을 것 | 단락 |
|---|---|---|
| 클라이언트 쪽 방식을 묻는 상세(예: T02.01) | 다른 클라이언트로 붙으면 그 방식이 적용되지 않는다는 점 | 구현 |
| E02.01·E02.02·D03.01(기준값 계산) | 기준값의 종류(내용 해시와 그 범위, MAC·서명, 상태 값)와 기준값을 남기는 곳 | 구현 |
| E02·D03의 검증 상세 | 대조 방법과 기준값을 가져오는 곳 | 구현 |
| E02·D03의 검증 상세 | 상태 값만 대조하면 내용이 바뀌어도 상태 값이 같을 때 알아채지 못한다는 점 | 한계 |
| E03 | 원본을 지키는 장치가 없는 다른 실행 방식, 도구, 경로 | 구현 |
| E03.03 | 외부 도구가 원본을 읽기 모드로 여는지 서버 개요의 버전 기준으로 소스에서 확인한 결과. 확인하지 못했으면 "실제 보호 미확인" | 한계 |
| T01.01 | 서버가 실행할 때 읽는 기준(설치된 도구가 알린 값, 사용자 설정)을 읽지 못했을 때의 처리 | 구현이나 한계 |
| T01.05와 F05.01을 함께 연결할 때 | T01.05에는 어느 인자를 어느 목록과 대조하는지와 대조를 거치지 않는 경로, F05.01에는 그 대조가 발견사항을 받는 조건인지와 어떤 기록을 근거로 인정하는지 | 구현 |
| T03.09 | 정해 둔 시간을 기다린 뒤 실행하는 동작 | 구현 |
| T03.09 | 자원 상태를 읽지 못하면 통과시키는 경우, 이 확인을 설정으로 끌 수 있는 경우 | 한계 |
| R03.05 | 진행률이 아니라 경과 시간이나 살아 있다는 사실만 알리면 그 사실 | 구현 |
| R06.01 | 값을 가리는 처리를 응답, 기록, 보고서 가운데 어디에 적용하는지 | 구현 |
| L01.04 | 서버가 MCP 도구 호출을 직접 기록하지 않으면 그 사실 | 구현 |
| L02 | 해시를 남기면 원래 출력, 파싱 결과, 요약 가운데 무엇의 해시인지. 비동기 호출은 기록이 어느 단계의 상태인지 | 구현 |
| L04.01 | 해시 체인의 끝 값이나 항목 수를 기록 밖에 남기면 그 사실 | 구현 |
| F03.01 | 표시가 실제로 주입을 막는지 확인한 범위 | 한계 |
| F04.09 | 기준이 코드에 정한 값인지 서버가 읽는 참조 표인지 | 구현 |
| F05.01 | 인용이 비어 대조할 값이 없는데도 발견사항을 받아들이는 경로 | 한계 |
| F05.02 | 대조 방법과, 그 결과로 거부하는지, 등급을 바꾸는지, 응답에 표시만 하는지 | 구현 |
| F06 | 사용자가 CLI나 훅을 실행해야 산출물이 생기면 그 사실. 클라이언트 모델이 안내문에 따라 직접 쓰는 보고서 글은 연결하지 않고 사실로만 적습니다 | 구현 첫머리 |

### 근거와 발췌

- 코드 블록은 `### 근거` 안에만 둡니다.
- **발췌를 손으로 쓰지 않습니다.** 발췌할 자리에 `@발췌 경로:시작-끝` 한 줄을 두고 `python tools/pilot.py fill <서버>`로 채웁니다. `check`는 발췌가 기준 커밋의 원문과 글자 하나까지 같은지 대조합니다.
- 링크는 기준 커밋의 고정 링크(`/blob/<40자 커밋>/`)만 씁니다.

**근거에 발췌를 붙이는 기준**

근거가 가리키는 코드 위치가 한두 곳이고 범위가 각각 30줄 이하이면, 위치마다 `@발췌`를 둡니다.
발췌 없이 링크만 두어도 되는 근거는 다음 네 가지뿐입니다.

- **코드가 아닌 근거**: 실행 확인, 문서(`.mdx`·`.txt`), 예시 로그. 실행 확인이면 근거 첫 줄에 `(실행 확인)`을 붙이고, 무엇을 실행해 봤는지는 `index.mdx`의 확인 방법에 씁니다.
- **코드 위치가 세 곳 이상인 근거**: 흩어진 분기나 호출 지점을 한꺼번에 가리킬 때입니다.
- **30줄을 넘는 범위**: 함수 흐름 전체를 가리킬 때입니다. 판단에 필요한 부분이 따로 있으면 그 부분을 발췌합니다.
- **같은 셀 파일의 다른 근거에서 이미 발췌한 범위**

링크만 두는 근거도 첫 줄에는 무엇을 확인할지 씁니다.
이 기준에 어긋난 근거가 있으면 `check`가 경고로 알려 줍니다.
