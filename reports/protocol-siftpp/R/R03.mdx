# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 서버의 도구 11개 모두에 적용된다.
Volatility 도구 9개의 응답은 Volatility의 종료 코드를 `exit_code` 필드로 싣고 0이 아니면 표준 오류 끝부분을 `stderr`에 싣는다 [1].
종료 코드가 0이 아니어도 MCP 결과의 `isError`는 거짓이다 [1][2].
서버 코드가 Volatility 실행 전이나 실행 뒤에 예외를 내는 경우는 FastMCP가 `isError`가 참인 결과로 돌려준다 [3].
실행 전의 예는 `pid` 거부, 증거 미설정이나 증거 파일 부재, 증거 파일의 크기·수정 시각 변경, `vol` 실행 파일 부재, Volatility 실행 실패(`OSError`)다 [4][2].
실행 뒤의 예는 증거 파일의 크기·수정 시각 변경과 호출 기록 쓰기 실패다 [4][2].
등록하지 않은 도구 이름은 FastMCP가 `Unknown tool` 오류 결과로 돌려준다 [2].
`evidence_metadata`와 `verify_evidence_integrity`는 상태 필드 없이 값을 돌려주고 실패하면 예외로 `isError` 결과가 된다 [5][3].

**한계.** Volatility 도구 응답의 `integrity_ok`는 서버 코드에 적은 상수 `true`다 [1].
크기와 수정 시각을 그대로 두고 증거 내용을 바꾸면 `verify_evidence_integrity`가 `unchanged: false`를 낸 뒤에도 `integrity_ok: true`가 나간다 [2].

클라이언트 `siftpp-investigate`는 `exit_code`가 0이나 `null`이 아니면 모델에게 넘기는 도구 결과의 `is_error`를 참으로 둔다 [6].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 Volatility 도구 9개의 응답에 적용된다 [1].
서버가 쓰는 Volatility 3 2.28.0의 JSON 렌더러는 행을 모두 모은 뒤 목록 하나로 출력한다 [7].
플러그인이 찾은 행이 없으면 응답은 `exit_code` 0, 빈 목록 `result`, `row_count` 0이다 [8][1].
Volatility는 요구 조건을 채우지 못하거나 실행 중 예외가 나면 목록을 출력하지 않고 종료 코드 1로 끝난다 [9].
그래서 실패한 실행의 응답은 `exit_code`가 0이 아니고 `result`와 `row_count`가 `null`이다 [8][1].
찾지 못함만을 뜻하는 상태 값은 없고 두 경우는 이 필드 값으로 구별된다 [1].

### R03.04 시간 초과·부분 완료 표시

**구현.** Volatility 도구 9개의 응답은 시간 제한 900초를 넘겨 실행을 끊었는지를 `timed_out` 필드로 알린다 [1][10].
끊긴 실행은 `exit_code`가 -1이고 `stderr` 끝에 `[timed out]`이 붙는다 [10].
JSON 렌더러는 행을 모두 모은 뒤 목록을 마지막에 한 번 출력하므로 끊긴 실행의 응답에는 행이 없고 `result`는 `null`이다 [7][8][10].
이 동작은 코드로만 확인했고 시간 초과를 실제로 일으켜 보지는 않았다.
`timed_out`이 참이므로 행이 없는 까닭이 찾지 못함이 아니라 시간 초과임을 알 수 있다 [1].
시간 초과와 관계없이 결과를 자른 것은 `truncated`로 알린다 [1].
