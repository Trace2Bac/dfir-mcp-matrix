# L03 기록 실패 처리

### L03.02 실행 후 응답 차단

**구현.** Volatility 도구는 `vol`을 실행한 뒤 `tool_call` 항목을 쓰고 그다음에 응답을 만든다 [1].
기록 객체는 파일을 열거나 쓰다 난 예외를 처리하지 않으므로 쓰기가 실패하면 예외가 도구 함수 밖으로 나간다 [2].
FastMCP는 이 예외를 `isError` 응답으로 돌려주고 Volatility 출력은 모델에게 가지 않는다 [3][4].
`verify_evidence_integrity`도 해시를 다시 계산한 뒤 `evidence_integrity` 항목을 쓰고 그 쓰기가 실패하면 대조 결과 대신 `isError` 응답이 돌아온다 [5][3].
Volatility는 파일을 남기지 않으므로 실행이 남긴 부수 효과는 Volatility 자신의 캐시와 내려받은 심볼뿐이다.

처음 도구를 부를 때 `evidence_opened`를 쓰지 못하면 실행기를 만들지 못해 그 호출이 오류로 끝난다 [6].
실행기가 없으므로 다음 호출은 증거를 다시 열고 해시하며 같은 쓰기를 다시 시도한다 [6].

기록 객체는 파일에 쓰기 전에 메모리의 일련번호와 앞 해시를 먼저 바꾼다 [2].
그래서 쓰기가 한 번 실패하면 다음 항목의 `seq`는 빠진 번호를 건너뛰고 `prev_hash`는 파일에 없는 항목의 해시를 가리킨다 [2][4].
기록이 다시 써지기 시작해도 해시 체인 검증은 그 항목에서 실패한다 [4].

쓰기가 줄 중간에서 실패해 마지막 줄이 JSON으로 읽히지 않으면 같은 파일로 서버를 다시 시작할 때 `_resume`의 `json.loads`가 예외를 낸다 [7].
그러면 실행기를 만들지 못하므로 모든 도구 호출이 오류로 끝난다 [6].
이 동작은 코드로만 확인했다.

def _build_runner() -> VolatilityRunner:
    evidence = os.environ.get("SIFTPP_EVIDENCE")
    if not evidence:
        raise RuntimeError("Set SIFTPP_EVIDENCE to the path of the memory image")
    audit = AuditLogger(os.environ.get("SIFTPP_AUDIT_LOG", "analysis/audit.jsonl"))
    runner = VolatilityRunner(
        guard=EvidenceGuard.open(evidence),
        audit=audit,
        agent=os.environ.get("SIFTPP_AGENT", "investigator"),
        offline=os.environ.get("SIFTPP_VOL_OFFLINE") == "1",
    )
    runner.session_start()
    return runner


def get_runner() -> VolatilityRunner:
    global _runner
    if _runner is None:
        _runner = _build_runner()
    return _runner

    def _resume(self) -> None:
        """Continue an existing log's chain instead of restarting it."""
        last = None
        with self.path.open("r", encoding="utf-8") as fh:
            for line in fh:
                line = line.strip()
                if line:
                    last = line
        if last:
            rec = json.loads(last)
            self._seq = int(rec.get("seq", 0))
            self._prev_hash = rec.get("hash", _GENESIS)
