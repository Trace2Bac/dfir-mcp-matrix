# F04 발견사항·결론 기록 관리

### F04.02 발견사항 필드 구분 저장

**구현.** 이 방식은 분석 메모를 받는 `add_analyst_note`와 고치는 `update_analyst_note`에 적용된다 [1].
`add_analyst_note`는 `note` 인자 하나로 `AnalystNote`를 받는다 [1].
`AnalystNote`는 제목 `title`, 판정 `status`, 태그 `tags`, 본문 `description` 네 필드로 이루어진다 [2].
`status`는 `benign`·`malicious`·`unknown` 가운데 하나이고 `tags`는 문자열 목록이다 [2].
네 필드는 기본값이 없어 입력 schema에 모두 필수로 실린다 [2][3].
`AnalystNoteManager.add_note`는 `title`·`status`·`tags`를 `AnalystNoteSummary`로 묶어 목록 `note_list`에 넣고 `description`은 본문 파일에 따로 쓴다 [4].
`show_analyst_notes_summary`는 목록을 돌려주고 `show_analyst_note`는 `title`로 찾은 목록 항목에 본문 파일의 글을 붙여 돌려준다 [1][5].

서버는 `title`·`tags`·`description`의 내용을 검사하지 않는다 [2].
빈 `description`과 빈 `tags`를 넘긴 메모도 저장되었다 [3].
`AnalystNote`에는 근거가 된 명령 번호나 증거 경로를 담는 필드가 없다 [2].
입력 schema에 없는 `evidence_refs`와 `confidence`를 더해 넘기자 오류 없이 저장되었고 두 값은 목록 파일과 본문 파일 어디에도 남지 않았다 [3].
근거는 모델이 `description`에 적은 글로만 남는다 [2].
예시 사건 폴더의 보고서 메모는 본문 끝에 실행한 명령의 번호와 명령을 적은 표를 싣는다 [6].
메모에는 작성 시각이나 사건 시각을 담는 필드가 없다 [2].
메모의 종류를 가르는 필드가 없어 조사 결론과 보고서 글도 같은 `AnalystNote`로 받는다 [2].
예시 사건 폴더의 메모 7개 가운데 하나는 `status`가 `malicious`이고 `tags`에 `report`를 넣은 보고서 글이다 [6].
정상으로 본 발견사항은 `status`가 `benign`인 메모로 남는다 [2].
가설을 따로 받는 도구, 대상을 배제했다는 처분을 받는 도구, 메모를 지우는 도구는 없다 [7].

**한계.** `update_analyst_note`는 있는 제목으로 부르면 늘 오류로 끝난다 [8][3].
`AnalystNoteManager.update_note`는 목록을 차례로 읽는 반복 변수의 이름이 인자 `note`와 같아 목록에서 찾은 `AnalystNoteSummary`에 `summary()`를 부른다 [8].
`AnalystNoteSummary`에는 `summary` 메서드가 없다 [2].
있는 제목으로 부르자 `'AnalystNoteSummary' object has no attribute 'summary'` 오류가 왔고 목록과 본문 파일은 바뀌지 않았다 [3].
없는 제목으로 부르자 `No note with title` 오류가 왔다 [3].
그래서 저장한 메모의 판정이나 본문을 고치는 도구 경로는 동작하지 않는다 [8][3].

`add_note`는 같은 제목의 메모가 이미 있는지 확인하지 않는다 [4].
같은 제목으로 두 번 더하면 목록에는 항목이 둘 남고 본문 파일은 나중 글로 바뀐다 [4][3].
`get_note`는 목록에서 제목이 처음 맞는 항목을 쓰므로 `show_analyst_note`는 앞 메모의 `status`·`tags`에 나중 메모의 본문을 붙여 돌려준다 [5][3].

### F04.06 파일·DB에 저장

**구현.** 이 방식은 `add_analyst_note`로 받은 분석 메모에 적용된다 [1].
`AnalystNoteManager.dump`는 메모를 더할 때마다 목록 전체를 `analysis/analyst_notes.json`에 다시 쓰고 본문을 `analysis/analyst_notes/<title>.md`에 쓴다 [9][10].
목록 파일은 메모마다 `title`·`status`·`tags`를 담은 JSON 배열이고 본문 파일에는 `description`만 들어간다 [9][3].
서버를 시작할 때 `AnalystNoteManager`는 목록 파일이 있으면 읽어 `note_list`를 채운다 [11].
본문은 메모리에 두지 않고 `show_analyst_note`를 부를 때마다 파일에서 읽는다 [5].
서버를 끝내고 같은 사건 폴더로 다시 실행하자 앞 세션에서 더한 메모의 목록과 본문이 그대로 읽혔다 [3].
저장소의 예시 사건 폴더에 있는 목록 파일과 본문 파일을 새 사건 폴더에 복사해 서버를 실행하자 메모 7개가 읽혔다 [3][6].
같은 제목으로 다시 더하면 본문 파일을 쓰기 모드로 열어 앞 글을 덮어쓴다 [9].
앞 값이나 바뀐 시각을 따로 남기는 파일은 없다 [9].
`update_note`의 코드도 목록 항목을 새 요약으로 바꾸고 `dump`를 부르는 것이어서 앞 값을 남기는 단계가 없다 [8].

**한계.** `dump`는 목록 파일을 먼저 쓰고 본문 파일을 나중에 쓴다 [9].
본문 파일을 쓰지 못하면 호출은 오류로 끝나지만 그 메모의 항목은 목록과 목록 파일에 남는다 [9][3].
없는 하위 폴더를 가리키는 제목 `sub/inner`로 더하자 `No such file or directory` 오류가 왔고 그 제목은 `show_analyst_notes_summary`에 남았다 [3].
그 제목으로 `show_analyst_note`를 부르자 같은 오류가 왔다 [3].
같은 사건 폴더에 서버 프로세스 둘이 붙으면 프로세스마다 자기 목록으로 목록 파일 전체를 다시 쓴다 [9][11].
두 프로세스가 메모를 하나씩 더하자 목록 파일에는 나중에 쓴 프로세스의 메모만 남았고 본문 파일은 둘 다 남았다 [3].
`get_note`는 목록에 있는 제목만 찾으므로 목록 파일에서 빠진 메모는 다음에 시작한 서버에서 `show_analyst_note`로 읽을 수 없다 [5][11].
`dump`와 `get_note`는 본문 파일을 `newline` 인자 없이 text mode로 쓰고 읽으므로 Windows 호스트에서는 줄 끝 글자가 바뀐다 [9][5].
`description`이 `a\nb\r\nc\rd\n`인 메모를 더하자 본문 파일에는 `a\r\nb\r\r\nc\rd\r\n`이 저장되었고 `show_analyst_note`는 `a\nb\n\nc\nd\n`을 돌려주었다 [3].
Linux 호스트에서는 실행하지 않았다.

### F04.09 판정·분류 값 기준 대조

**구현.** 이 방식은 `add_analyst_note`와 `update_analyst_note`가 받는 `status`에 적용된다 [2].
기준은 코드에 정한 값 목록이고 `AnalystNote.status`의 자료형 `Literal["benign", "malicious", "unknown"]`이다 [2].
MCP Python SDK 1.27.0의 FastMCP는 도구 함수를 부르기 전에 인자를 함수 서명으로 만든 pydantic 모델로 검사한다 [12].
`status`에 `suspicious`를 넘기자 `add_analyst_note`는 `Input should be 'benign', 'malicious' or 'unknown'` 오류로 끝났고 메모는 저장되지 않았다 [3].
`update_analyst_note`도 세 값 밖의 `status`를 같은 오류로 거부했다 [3].
목록 파일을 읽을 때도 항목마다 `AnalystNoteSummary`로 같은 값을 검사한다 [11].
목록 파일의 `status` 하나를 `suspicious`로 고친 뒤 서버를 실행하자 `data_manager` 모듈을 불러오다 `ValidationError`로 끝나 서버가 시작되지 않았다 [3].
`tags`는 문자열 목록인지만 검사하고 값 목록을 정해 두지 않는다 [2].

```python
class AnalystNoteSummary(BaseModel):
    title: str = Field(examples=["Found WannaCry ransomware executable"])
    status: Literal["benign", "malicious", "unknown"] = Field(examples=["malicious"])
    tags: list[str] = Field(examples=[["malware", "ransomware", "executable"]])


class AnalystNote(BaseModel):
    title: str = Field(examples=["Found WannaCry ransomware executable"])
    status: Literal["benign", "malicious", "unknown"] = Field(examples=["malicious"])
    tags: list[str] = Field(examples=[["malware", "ransomware", "executable"]])
    description: str = Field(
        examples=[
            "# Found WannaCry ransomware executable\nFound WannaCry executable after running <COMMAND>, follow-on analysis needed"
        ]
    )

    def summary(self) -> AnalystNoteSummary:
        return AnalystNoteSummary(
            title=self.title,
            status=self.status,
            tags=self.tags,
        )
```

제목 `sub/inner`로 더한 호출은 `[Errno 2] No such file or directory` 오류로 끝났고 그 뒤 목록에 그 제목이 있었으며 `show_analyst_note`도 같은 오류로 끝났다.
서버를 끝내고 같은 사건 폴더로 다시 실행한 세션에서 `show_analyst_notes_summary`와 `show_analyst_note`가 앞 세션의 메모를 돌려주었다.

Windows 11 호스트에서 `description`이 `a\nb\r\nc\rd\n`인 메모를 더한 뒤 본문 파일의 바이트는 `a\r\nb\r\r\nc\rd\r\n`이었고 `show_analyst_note`가 돌려준 `description`은 `a\nb\n\nc\nd\n`이었다.
예시 사건 폴더의 `analysis`를 새 사건 폴더에 복사해 실행한 세션에서 `show_analyst_notes_summary`는 메모 7개를, `show_analyst_note`는 `Case 002 - Evidence Inventory`의 본문을 돌려주었다.
