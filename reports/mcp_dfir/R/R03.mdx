# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 서버의 도구 18개 모두에 적용된다 [1][2].
명령을 실행하는 도구의 응답 `CommandRecordSummary`는 명령의 종료 코드를 `exit_code`에 싣는다 [3][4].
실행기 `exec_stream`은 종료 코드를 0으로 두고 `DockerException`이 나면 예외의 `return_code`를, 그 값이 없으면 1을 넣는다 [3].
python-on-whales 0.81.0은 실행한 `docker exec`의 종료 코드가 0이 아니면 이 예외를 낸다 [5].
종료 코드가 0이 아니어도 도구 함수는 예외를 내지 않으므로 MCP 결과의 `isError`는 거짓이다 [3][6].
없는 파일에 `fls`를 실행하자 `exit_code`가 1이고 `isError`가 거짓인 응답이 왔다 [6].
그 명령의 표준 오류는 응답에 없고 `get_command_result`로 읽는 결과 본문의 예외 글 안에 있었다 [6].
컨테이너를 거치지 않는 심볼 도구가 남기는 명령 기록의 `exit_code`는 코드에 적힌 0이다 [7].
서버 코드가 예외를 내면 MCP Python SDK 1.27.0이 `Error executing tool`로 시작하는 글을 담은 `isError`가 참인 결과로 바꾼다 [2].
`-exec`를 준 `run_find`, 없는 번호나 틀린 정규식을 준 `get_command_result`, 없는 제목을 준 `show_analyst_note`, 허용 값이 아닌 `algorithm`을 준 `get_hash`가 이 결과를 돌려줬다 [8].
표준 출력이 UTF-8이 아닌 `img_cat` 실행과 일치가 있는 `search_linux_symbols`도 이 결과로 끝났다 [8].
등록되지 않은 도구 이름에는 `Unknown tool`로 시작하는 오류 결과가 왔다 [8].
`list_files`·`get_command_history`와 메모 도구는 상태 필드 없이 값을 돌려주고 실패하면 예외가 `isError` 결과가 된다 [9][8].

서버는 실행 중인 호출의 진행을 알리지 않는다 [3][10].
`exec_stream`과 심볼 도구는 `ctx.report_progress`에 문구 하나를 넘겨 부른다 [3][11].
SDK의 `report_progress`는 coroutine 함수인데 도구 함수는 동기 함수이고 `await` 없이 부르므로 알림을 보내는 코드가 실행되지 않는다 [10][3].
`progressToken`을 붙여 부른 Volatility 실행은 약 1분 뒤에 끝났고 그동안 진행 알림은 오지 않았으며 서버 표준 오류에 `coroutine 'Context.report_progress' was never awaited` 경고가 남았다 [12].
`exec_stream`과 심볼 내려받기에는 시간 제한이 없고 시간 초과를 알리는 상태 값도 없다 [3][11].

**한계.** `exit_code`는 도구가 낸 종료 코드와 `docker exec` 자체의 실패를 구분하지 않는다 [3][5].
세션 중에 컨테이너를 멈추고 `run_grep`을 부르자 `exit_code`가 1이고 `isError`가 거짓인 응답이 왔다 [13].
그 결과 본문의 표준 오류 자리에는 `Error response from daemon: container … is not running`이 있었다 [13].
`grep`이 일치하는 줄을 찾지 못한 응답도 `exit_code`가 1이다 [14].

종료 코드 0으로 끝난 명령이 표준 오류에 쓴 오류 문구는 응답과 결과 본문에 남지 않는다 [3].
읽기 전용으로 연결된 `/evidence` 아래를 대상 폴더로 준 `tsk_recover`의 응답은 `exit_code`가 0이었고 결과 본문은 `Files Recovered: 0` 한 줄이었다 [15].
같은 명령을 직접 실행했을 때 표준 오류에 나온 `Error making directory`는 응답과 결과 본문에 없었다 [15].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 결과가 없어도 종료 코드 0으로 끝나는 명령의 응답과 `get_command_result`에 적용된다 [3][16].
맞는 파일이 없는 `find`는 `exit_code`가 0이고 결과 본문이 빈 글이었다 [14].
없는 파일을 준 `fls`는 `exit_code`가 1이었다 [6].
응답에 찾지 못함만을 뜻하는 상태 값은 없고 두 경우는 `exit_code` 값으로 구별된다 [4].
`CommandRecordSummary`에는 결과 본문의 길이나 줄 수가 없어 모델은 `get_command_result`를 불러야 결과 본문이 비었는지 안다 [4].
`get_command_result`는 `regex`에 맞는 줄이 없으면 빈 글을 `isError`가 거짓인 결과로 돌려주고 정규식이 틀리면 `isError`가 참인 결과를 돌려준다 [16][14][8].
`search_linux_symbols`는 맞는 심볼이 없으면 `exit_code`가 0인 명령 기록과 결과 본문 `[]`를 남긴다 [17][14].

키로 하나를 찾는 조회에는 이 구분이 없다.
없는 번호를 준 `get_command_result`와 없는 제목을 준 `show_analyst_note`는 `KeyError`로 끝나 다른 실패와 같은 `isError` 결과가 된다 [18][8].

**한계.** `grep`은 일치하는 줄이 없으면 종료 코드 1로 끝난다 [14].
python-on-whales는 0이 아닌 종료 코드를 모두 예외로 내므로 이 명령 기록의 결과 본문은 빈 글이 아니라 예외 글이다 [5][14].
파일이 없어 실패한 `grep`의 `exit_code`는 2였고 두 결과 본문은 같은 모양의 예외 글이었다 [14].
서버는 명령마다 다른 종료 코드의 뜻을 응답에 설명하지 않는다 [3].
`search_linux_symbols`는 맞는 심볼이 하나라도 있으면 결과를 JSON 글로 만들다 예외가 나 `isError` 결과로 끝난다 [17][8].
그래서 이 도구의 정상 응답은 일치 0건일 때만 나온다 [8].

        if self.container is None:
            raise RuntimeError("No docker container is currently running")

        ctx.report_progress(f"Running command {' '.join(command_list)}")
        output = []
        exit_code = 0
