# P06 조사 상태 유지

### P06.03 조사 상태를 파일·DB에 저장

**구현.** 이 방식은 명령 기록, 분석 메모, Linux 심볼 맵에 적용된다 [1][2][3].
이 파일들의 경로는 모두 사건 폴더 아래다 [4].
서버는 명령을 하나 실행할 때마다 번호, 명령 문자열, 실행 시각, 종료 코드를 담은 목록 전체를 명령 기록 목록 `analysis/command_history.json`에 다시 쓴다 [1].
그 명령의 결과 본문은 결과 본문 파일 `analysis/command_history/<번호>.txt`에 쓴다 [1].
번호는 메모리에 둔 목록의 길이에 1을 더한 값이다 [5].
분석 메모는 제목, `status`, `tags`를 담은 목록 전체를 `analysis/analyst_notes.json`에 다시 쓰고 본문을 `analysis/analyst_notes/<제목>.md`에 쓴다 [2].
`search_linux_symbols`는 처음 부를 때 받은 Linux 심볼 맵을 `symbols/linux/symbol_map.json`에 두고 이 파일이 있으면 다시 받지 않는다 [3].
프로세스 메모리에는 두 JSON 파일과 같은 내용의 목록 `command_summary_list`와 `note_list`가 있다 [1][2].
파일에 쓰지 않고 프로세스 메모리에만 두는 조사 상태는 없다.
이 파일들에는 유효 시간이나 개수 한도가 없다 [1][2][3].

컨테이너도 서버 프로세스가 끝난 뒤에 남는다.
서버는 컨테이너를 `remove=False`로 만들고 끝날 때 멈추기만 한다 [6][7].
그래서 볼륨이 아니라 컨테이너 안에 쓴 파일도 다음 실행에 그대로 있다 [8].
Volatility 3가 실행 중에 만드는 캐시 `/tools/.cache/volatility3/identifier.cache`가 그런 파일이다 [8].

**한계.** 메모리의 목록은 서버를 시작할 때만 파일에서 읽고 그 뒤로는 파일을 다시 읽지 않는다 [9].
그래서 같은 사건 폴더에 서버 프로세스 둘이 붙으면 두 프로세스가 같은 번호를 매기고 서로의 파일을 덮어쓴다 [1][5][10].
두 프로세스에서 명령을 하나씩 실행하자 둘 다 번호 1을 받았고 `1.txt`에는 나중에 실행한 명령의 결과만 남았다 [10].
먼저 실행한 프로세스의 `get_command_result`는 번호 1에 다른 프로세스가 실행한 명령의 결과를 돌려주었다 [10].
`command_history.json`에는 마지막으로 쓴 프로세스의 목록만 남아 다른 프로세스가 실행한 명령은 파일에서 사라졌다 [10].
두 프로세스는 컨테이너 하나를 함께 쓰므로 한 프로세스가 끝나며 컨테이너를 멈추면 남은 프로세스의 명령은 컨테이너가 실행 중이 아니라는 오류로 끝난다 [7][10].
표준 출력이 UTF-8로 읽히지 않는 명령은 컨테이너에서 실행된 뒤 `exec_stream`이 예외로 끝나 명령 기록에 남지 않는다 [11][12].

### P06.04 재시작 뒤 자동 복구

**구현.** 이 방식은 명령 기록 목록, 분석 메모 목록, 컨테이너에 적용된다 [9][13].
`data_manager` 모듈은 불러올 때 `CommandHistoryManager`와 `AnalystNoteManager` 객체를 하나씩 만든다 [14].
두 객체는 만들어질 때 `command_history.json`과 `analyst_notes.json`이 있으면 읽어 메모리의 목록을 채운다 [9].
그래서 서버를 다시 시작하면 모델이 사건을 여는 도구를 부르지 않아도 `get_command_history`와 `show_analyst_notes_summary`가 앞 프로세스의 항목을 돌려준다 [15].
새 명령의 번호는 읽어 온 목록의 길이에 이어서 매긴다 [5][15].
결과 본문과 메모 본문은 시작할 때 읽지 않고 `get_command_result`와 `show_analyst_note`를 부를 때 파일에서 읽는다 [16].
서버는 시작할 때 사건 폴더 이름으로 만든 이름의 컨테이너를 찾아 실행 중이면 그대로 쓰고 멈춰 있으면 다시 시작한다 [13].
서버를 다시 시작한 실행에서 서버 로그에는 멈춰 있는 컨테이너를 다시 시작한다는 줄이 남았다 [15].

**한계.** `command_history.json`이 JSON으로 읽히지 않거나 항목에 필드가 빠져 있으면 서버는 MCP 세션을 열기 전에 예외로 끝난다 [9][17].
`analyst_notes.json`이 JSON으로 읽히지 않을 때도 서버는 같은 예외로 끝난다 [9][17].
이 예외가 났을 때 빈 목록으로 시작하거나 파일을 다른 이름으로 남겨 두는 코드는 없다 [9].
목록에는 있는데 `<번호>.txt`가 없으면 `get_command_result`는 `No such file or directory` 오류를 돌려준다 [16][17].
서버는 다시 쓰는 컨테이너가 이 사건 폴더에 연결되어 있는지 확인하지 않는다 [13].
