# T04 실행 방식

### T04.01 서버 프로세스 안 분석

**구현.** 이 방식은 `list_files`, `search_linux_symbols`, `get_command_result`와 심볼 도구가 내려받은 파일을 다루는 단계에 적용된다 [1][2][3][4].
`list_files`는 호스트의 사건 폴더 아래 `artifacts`·`symbols`·`evidence` 가운데 하나를 `Path.walk`로 훑어 파일마다 이름, 컨테이너 경로, 크기를 만든다 [1].
`search_linux_symbols`는 심볼 맵 `symbol_map.json`을 읽어 커널 배너 문자열을 `re.search`로 검색한다 [2].
이 도구는 일치하는 항목이 있으면 그 목록을 `json.dumps`로 바꾸는 줄에서 `TypeError`로 끝나고 일치하는 항목이 없을 때만 결과를 남긴다 [2][5].
`get_command_result`는 결과 본문을 줄 단위로 자르고 `regex`에 맞는 줄을 고른다 [3].
`download_windows_symbol`은 `pdbconv`가 만든 심볼 파일을 `lzma`로 풀어 `unknown.pdb` 바이트열을 `pdb_name`으로 바꾼 뒤 다시 압축해 쓴다 [4].
심볼 도구 3개의 내려받기 요청도 서버 프로세스가 `requests.get`으로 보낸다 [6].
이 코드는 서버 프로세스의 계정과 네트워크로 실행되고 사건 폴더의 네 폴더를 호스트 경로로 읽고 쓴다 [7].

### T04.04 권한을 나눈 실행

**구현.** 이 방식은 서버가 컨테이너에서 실행하는 모든 명령에 적용된다 [8][9].
서버 프로세스는 사용자가 호스트에서 서버를 실행한 계정으로 실행되고 컨테이너의 명령은 이미지가 정한 계정 `analyst`로 실행된다 [10][11][12].
`Dockerfile`은 `useradd`로 `analyst`를 만들고 `USER analyst`로 이미지의 기본 사용자로 정한다 [11].
서버는 컨테이너를 만드는 `docker.run`에 `user`·`privileged`·`cap_add`·`cap_drop`을 주지 않는다 [13].
`exec_stream`도 `docker.execute`에 `user`와 `privileged`를 주지 않아 명령은 컨테이너의 기본 사용자로 실행된다 [8][14].
그래서 명령의 계정을 정하는 것은 서버 코드의 인자가 아니라 이미지의 설정이다 [13][11].
서버 코드에는 `sudo`를 붙이거나 명령마다 사용자를 바꾸는 곳이 없다 [8].
서버가 만든 컨테이너에서 도구가 실행한 `grep` 프로세스는 uid와 gid가 1000이었고 유효 capability(`CapEff`)와 허용 capability(`CapPrm`)가 0이었다 [12].
이 프로세스의 capability 상한(`CapBnd`)은 `00000000a80425fb`였고 컨테이너 설정의 `CapDrop`은 비어 있었으며 `Privileged`는 거짓이었다 [12].
이미지에서 `/tools`와 그 아래 Volatility 소스 폴더는 `analyst` 소유라서 이 계정으로 실행된 명령이 분석 도구의 폴더에 파일을 만들고 지울 수 있다 [11][12][15].

**한계.** 서버는 같은 이름의 컨테이너가 이미 있으면 그 컨테이너의 사용자 설정을 확인하지 않고 다시 쓴다 [13].
같은 이미지를 `--user 0`으로 실행한 컨테이너를 같은 이름으로 미리 두고 서버를 시작하자 도구가 실행한 `grep` 프로세스는 uid가 0이고 `CapEff`가 `00000000a80425fb`였다 [16].

### T04.08 컨테이너·VM

**구현.** 이 방식은 컨테이너에서 명령을 실행하는 도구 8개와 `download_windows_symbol`의 `pdbconv` 실행에 적용된다 [8][9].
8개는 `run_strings`, `run_grep`, `run_find`, `unzip_file`, `untar_file`, `get_hash`, `run_volatility_command`, `run_sleuthkit_command`다 [9].
서버 프로세스는 컨테이너 밖 호스트에서 실행되고 시작할 때 `androsh7/forensics-docker` 이미지로 컨테이너 하나를 만들어 분석 도구를 그 안에서 실행한다 [13][7].
README는 서버를 `pip install mcp-dfir`로 설치해 `python -m mcp_dfir`로 실행하라고 적고 포렌식 도구를 격리된 Docker 컨테이너 안에서 실행한다고 설명한다 [10].
이미지를 만드는 `Dockerfile`은 분석 도구만 설치하고 서버 패키지는 설치하지 않으며 작업 폴더를 `/tools`, 진입점을 `sleep infinity`로 둔다 [11].
서버는 컨테이너를 네트워크 `none`으로 만들고 사건 폴더의 `evidence`와 `analysis`는 읽기 전용으로, `symbols`와 `artifacts`는 읽고 쓰게 연결한다 [13][7].
`exec_stream`은 명령 list를 python-on-whales의 `docker.execute`에 넘긴다 [8].
python-on-whales 0.81.0은 `docker exec <컨테이너> <명령>` 꼴의 인자 list를 만들어 `Popen`으로 `docker` CLI를 하위 프로세스로 실행하고 셸을 거치지 않는다 [14].
서버는 `docker.execute`에 `workdir`를 주지 않으므로 명령은 이미지의 작업 폴더에서 실행된다 [8][14].
그래서 분석 도구는 네트워크를 쓰지 못하고 연결한 네 폴더와 컨테이너 자체의 파일만 본다 [12].
시험 컨테이너의 설정은 `WorkingDir=/tools`, `NetworkMode=none`이었고 컨테이너 안의 네트워크 인터페이스는 `lo` 하나였다 [12].
컨테이너에서 `/evidence`와 `/analysis`에 쓰려는 명령은 `Read-only file system`으로 실패했다 [12].
`vol`과 `pdbconv`는 이미지 안의 bash 스크립트이고 받은 인자를 `"$@"`로 파이썬 스크립트에 넘긴다 [11].

서버는 호출마다 새 컨테이너나 새 작업 폴더를 만들지 않고 컨테이너 하나의 `/tools`에서 모든 명령을 실행한다 [8][13].
서버는 끝날 때 컨테이너를 멈추기만 하고 다음에 시작할 때 같은 이름의 컨테이너를 다시 시작해 쓴다 [13].
그래서 도구 호출이 컨테이너 안에 만든 파일은 서버를 다시 시작한 뒤에도 남는다 [15].
`run_find`의 `-fprintf`로 Volatility 플러그인 폴더에 만든 파일은 서버를 다시 시작한 뒤에도 남아 있었고 `run_volatility_command`가 그 파일을 플러그인으로 실행했다 [15].
서버가 컨테이너를 만들 때 메모리나 CPU 상한을 주는 인자는 없다 [13].

**한계.** 서버는 같은 이름의 컨테이너가 이미 있으면 그 컨테이너의 이미지, 네트워크, 연결한 폴더를 확인하지 않고 다시 쓴다 [13].
컨테이너 이름은 사건 폴더 이름의 공백을 `_`로 바꾸고 `-forensics`를 붙인 값이라서 위치가 다른 같은 이름의 사건 폴더도 같은 컨테이너 이름이 된다 [7].
폴더를 연결하지 않고 기본 네트워크로 만든 컨테이너를 같은 이름으로 미리 두고 서버를 시작하자 서버는 그 컨테이너에서 명령을 실행했다 [17].
이때 `get_hash`에 준 `/evidence/notes.txt`는 컨테이너에 없어 종료 코드 1이 기록되었고 컨테이너의 네트워크 설정은 `bridge` 그대로였다 [17].

```python
def list_files(path: Literal["artifacts", "symbols", "evidence"]) -> list[FileDetails]:
    valid_paths = [volume.name for volume in config.docker_volumes]

    # Select volume
    selected_volume = None
    for volume in config.docker_volumes:
        if volume.name == path:
            selected_volume = volume
            break
    if selected_volume is None:
        raise RuntimeError(f"Invalid path {path}, valid paths are {valid_paths}")

    out_list = []
    for dir_path, _, file_name_list in selected_volume.external_path.walk():
        for file_name in file_name_list:
            external_file_path = Path(dir_path / file_name)
            internal_file_path = (
                f"/{path}/{str(external_file_path.relative_to(selected_volume.external_path)).replace('\\', '/')}"
            )
            out_list.append(
                FileDetails(
                    name=file_name,
                    path=internal_file_path,
                    size=external_file_path.stat().st_size,
                )
            )
    return out_list
```

```python
        if self.container is None:

        ctx.report_progress(f"Running command {' '.join(command_list)}")
        output = []
        exit_code = 0
```

[12] (실행 확인) 서버가 만든 컨테이너를 `docker inspect`로 보고 그 안에서 명령을 실행했다.
`docker inspect`는 `User=analyst`, `WorkingDir=/tools`, `NetworkMode=none`, `Privileged=false`와 연결 4개(`/evidence`·`/analysis`는 `RW=false`, `/symbols`·`/artifacts`는 `RW=true`)를 보였다.
컨테이너 안의 `id`는 `uid=1000(analyst)`였고 `/sys/class/net`에는 `lo`만 있었으며 유효 capability(`CapEff`)는 0이었다.
`run_grep`으로 `/proc/self/status`를 읽으면 `Uid`와 `Gid`가 모두 1000, `CapPrm`과 `CapEff`가 `0000000000000000`, `CapBnd`가 `00000000a80425fb`였다.
`docker inspect`가 보인 `CapAdd`와 `CapDrop`은 비어 있었고 `Memory`와 `NanoCpus`는 0이었다.
`run_find`의 `-printf`로 본 `/tools`와 `/tools/volatility3`의 소유자는 `analyst`였다.
컨테이너 안에서 `https://example.com`을 여는 파이썬 한 줄은 이름을 찾지 못해 실패했다.
