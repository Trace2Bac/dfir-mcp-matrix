# E03 원본 변경 방지

### E03.01 실행 환경의 읽기 전용 강제

**구현.** 이 방식은 서버가 컨테이너에서 실행하는 모든 명령에 적용된다 [1][2].
서버는 사건 폴더의 `evidence`를 컨테이너의 `/evidence`에 `ro`로 연결하도록 설정한다 [1].
명령 기록과 분석 메모가 있는 `analysis`도 `ro`이고 `symbols`와 `artifacts`만 `rw`다 [1].
서버는 컨테이너가 없으면 이 연결 설정과 네트워크 `none`으로 컨테이너를 만든다 [3].
python-on-whales 0.81.0은 연결 설정의 세 값을 `:`로 이어 `docker run`의 `--volume` 인자로 넘긴다 [4].
서버가 만든 컨테이너의 연결 정보에서 `/evidence`와 `/analysis`는 쓰기가 꺼져 있다 [5].
Volatility 3, Sleuth Kit, `strings`, `grep`, `find`, 해시 명령, `tar`는 모두 `exec_stream`이 이 컨테이너에서 실행한다 [2].
그래서 모델이 어떤 인자를 주어도 이 명령들은 `/evidence` 아래 파일을 고치거나 지우지 못한다 [5].
`run_find`에 `/evidence`의 파일과 `-delete`를 주거나 `-fprint`로 `/evidence` 아래에 파일을 쓰게 하자 `find`가 `Read-only file system` 오류로 끝났다 [5].
`run_sleuthkit_command`로 `tsk_recover`의 출력 폴더를 `/evidence` 아래로 주자 꺼낸 파일이 0개였고 호스트의 `evidence` 폴더에는 새 파일이 없었다 [5].
이미지 옆에 DB 파일을 만드는 `tsk_loaddb`는 DB를 열 수 없다는 오류로 끝났다 [5].
이 실행들 뒤에 증거 파일의 SHA-256은 실행 전과 같았다 [5].
컨테이너의 명령은 이미지에 만든 일반 사용자 `analyst`로 실행된다 [6].

컨테이너 밖에서 실행되는 서버 코드에는 이 장치가 적용되지 않는다.
분석 메모와 내려받은 심볼은 서버 프로세스가 호스트의 사건 폴더에 직접 쓴다 [7][8].
`add_analyst_note`는 메모 제목을 검사하지 않고 `analysis/analyst_notes/<제목>.md` 경로에 본문을 쓴다 [7].
제목을 `../../evidence/pe_note`로 주자 호스트의 `evidence` 폴더에 `pe_note.md` 파일이 생겼다 [9].
파일 이름 끝에 늘 `.md`가 붙으므로 이 경로로 덮어쓸 수 있는 파일은 이름이 `.md`로 끝나는 파일이다 [7].
`download_windows_symbol`은 `pdb_name`을 검사하지 않고 `symbols/windows/<pdb_name>` 폴더를 먼저 만든 뒤 내려받는다 [8].
`pdb_name`을 `../../evidence/pe_dir`로 주자 내려받기는 404로 끝났고 호스트의 `evidence` 폴더에 `pe_dir` 폴더가 생겼다 [9].
`download_linux_symbol`은 `symbol_path`의 마지막 `/` 뒤 조각을 검사 없이 파일 이름으로 삼아 내려받은 내용을 `symbols/linux` 아래에 쓴다 [10].
Windows 호스트에서 `symbol_path`를 `README.md?x=/..\..\evidence\notes.txt`로 주자 내려받은 내용이 호스트의 `evidence/notes.txt`를 덮어썼다 [11].

사용자 CLI의 `--clear-case-dir`는 사용자가 `yes`를 입력하면 `evidence` 폴더를 하위 폴더까지 지운다 [12].
서버는 사건 폴더의 하위 폴더를 `mkdir(mode=500)`으로 만든다 [13].
500은 10진수라 8진수 764와 같고 소유자의 쓰기 권한이 켜진 값이다 [13].
호스트의 `evidence` 폴더나 그 안의 파일을 읽기 전용으로 바꾸는 코드는 없다 [13].

**한계.** 서버는 사건 폴더 이름으로 만든 이름의 컨테이너가 이미 있으면 실행 중이든 멈춰 있든 그 컨테이너를 다시 쓴다 [14].
이때 그 컨테이너의 연결 설정을 다시 적용하거나 지금 설정과 대조하지 않는다 [14].
`evidence`를 `rw`로 연결한 같은 이름의 컨테이너를 미리 만들어 두고 서버를 실행하자 `run_find`의 `-fprint`가 `/evidence` 아래에 파일을 썼다 [15].
이름이 같은 다른 사건 폴더로 만든 컨테이너를 다시 쓰면 읽기 전용으로 연결된 폴더는 그 다른 사건 폴더의 `evidence`다 [15].

### E03.02 서버 코드의 원본 쓰기 제한

**구현.** 이 방식은 `unzip_file`과 `untar_file`의 목적지 검사에 적용된다 [16].
두 도구는 `source_file`이나 `destination_dir`에 `..`이 있으면 거부한다 [16].
두 도구는 `destination_dir`이 `/artifacts/`로 시작하지 않아도 거부한다 [16].
그래서 두 도구에는 `/evidence`로 시작하는 경로를 풀 위치로 줄 수 없다 [16][17].
호스트의 파일 확인을 지나는 `source_file`과 함께 `/tmp/x`나 `/evidence/`를 목적지로 주자 `untar_file`은 `Destination directory must be in /artifacts` 오류를 돌려주었다 [17].

서버 코드에는 증거 파일의 내용을 읽으려고 여는 곳이 없다.
`list_files`는 호스트의 `evidence` 폴더를 훑어 파일 이름과 크기만 읽는다 [18].
증거의 내용은 컨테이너에서 실행되는 분석 도구만 읽는다 [2].

파일을 쓰는 다른 도구에는 목적지 검사가 없다.
`run_sleuthkit_command`와 `run_find`는 출력 경로를 포함한 인자를 받은 대로 넘긴다 [19].
분석 메모와 심볼 내려받기는 제목, `pdb_name`, `symbol_path`로 만든 호스트 경로가 `evidence` 폴더 안인지 확인하지 않는다 [7][8][10].

**한계.** 이 검사는 경로 문자열만 보고 링크를 해석한 실제 경로를 확인하지 않는다 [16].
`/artifacts/` 아래에 다른 폴더를 가리키는 심볼릭 링크가 있으면 그 링크를 지나는 `destination_dir`은 검사를 통과한다 [16][20].
`/symbols`를 가리키는 링크 `/artifacts/lnk`를 만들어 두고 `destination_dir`을 `/artifacts/lnk/`로 주자 푼 파일이 사건 폴더의 `symbols`에 생겼다 [20].
`/evidence`를 가리키는 링크로 같은 호출을 하자 검사는 통과했고 `tar`는 `Read-only file system` 오류로 끝나 `evidence` 폴더에 파일을 쓰지 못했다 [20].
