# E02 증거 무결성 검증

### E02.01 등록 시 기준값 자동 계산

**구현.** 이 방식은 `artifact-forensic`의 파일 분석 도구와 ZIP 항목 도구, `ir-collect`의 `analyze_triage_zip`에 적용된다 [1][2][3][4].
EZ Tools·capa·YARA 도구와 파일을 받은 Hayabusa 도구, `inspect_binary_file`은 분석 도구를 실행하기 전에 모델의 요청 없이 입력 파일 전체의 SHA-256을 계산한다 [1].
이 값은 응답의 `input.sha256_before`(`inspect_binary_file`은 `input.hashes`)와 `provenance.evidence_digest`에 실린다 [1].
`inspect_binary_file`은 같은 읽기에서 MD5와 SHA-1도 계산해 싣는다 [5].
ZIP 항목 도구는 ZIP 파일 전체의 SHA-256을 계산한 뒤 항목을 꺼내면서 꺼낸 바이트의 SHA-256을 계산한다 [2][6].
두 값은 `archive_sha256_before`와 `member_sha256_before`, `provenance`의 `archive_digest`와 `evidence_digest`에 실린다 [2].
`analyze_triage_zip`은 ZIP을 풀기 전에 ZIP 파일의 크기와 SHA-256을 `provenance`의 `source_zip_size_bytes`와 `source_zip_sha256_before`에 싣는다 [3][4].
기준값은 모두 내용의 SHA-256이고 서버는 이 값을 응답에만 싣고 따로 보관하지 않는다 [1][2][3].

`analyze_artifact_folder`, `correlate_hosts`, `expand_investigation_graph`는 받은 폴더의 해시를 계산하지 않는다 [7].
`analyze_artifact_folder`의 `provenance.evidence_digest`는 `IR_Collect.exe` 0.24.2가 받은 폴더의 파일 해시로 만든 묶음 해시를 옮긴 것이다 [8][9].
`correlate_hosts`는 같은 묶음 해시를 `hosts`의 호스트마다 `evidence_digest`로 옮긴다 [10].
`correlate_hosts`의 `provenance.evidence_digest`는 `IR_Collect.exe` 0.24.2의 결과에 최상위 값이 없어 `null`이다 [10].
`expand_investigation_graph`의 응답에는 묶음 해시가 실리지 않는다 [11].
기본값으로 `IR_Collect.exe`가 받는 폴더는 원본이 아니라 작업 폴더의 사본이다 [7].
`analyze_evtx_with_hayabusa`에 폴더를 주면 해시를 계산하지 않고 `sha256_before`가 `null`이다 [12].

**한계.** 기준값은 도구를 부를 때마다 그 시점의 파일에서 새로 계산한다 [1][2][3].
그래서 서버가 읽기 전에 바뀐 증거는 바뀐 상태가 기준값이 된다.

### E02.02 도구를 요청해 기준값 계산

**구현.** 이 방식은 `artifact-forensic`의 `inventory_evidence_path`와 `inventory_archive_members`에 적용된다 [13][14].
`inventory_evidence_path`는 `include_sha256`이 참(기본값)이면 받은 파일이나 폴더의 파일마다 SHA-256을 계산해 응답의 `files`에 싣는다 [13].
이미 해시한 바이트에 그 파일의 크기를 더한 값이 512MiB를 넘는 파일은 `sha256`을 `null`로 두고 경고를 싣는다 [13].
받은 경로가 파일이면 그 해시를 `provenance.evidence_digest`에도 싣는다 [13].
`inventory_archive_members`는 `include_sha256`이 참이면 ZIP 파일의 SHA-256을 계산해 `input.sha256_before`에 싣는다 [14].
두 값은 응답에만 실린다 [13][14].

`local-forensic`의 `get_file_metadata`는 `include_hashes`가 참이면 PowerShell의 `Get-FileHash`로 SHA-256·SHA-1·MD5를, `check_file_signatures`는 Sigcheck의 `-h`로 해시를 계산한다 [15][16].
두 도구의 대상은 서버를 실행한 호스트의 파일이고 서버는 그 값을 보관하거나 다시 대조하지 않는다 [15][16].

### E02.03 도구 호출 중 자동 검증

**구현.** 이 방식은 실행 전 기준값을 자동으로 계산하는 위의 도구들과 `inventory_archive_members`에 적용된다 [1][2][3][14].
파일 분석 도구는 분석 도구가 끝난 뒤 입력 파일의 SHA-256을 다시 계산해 실행 전 값과 대조하고 `input.sha256_after`에 싣는다 [1].
ZIP 항목 도구는 분석이 끝난 뒤 ZIP 파일과 꺼낸 주 항목 사본의 SHA-256을 다시 계산해 각각 실행 전 값과 대조한다 [2].
`analyze_triage_zip`은 `IR_Collect.exe`가 끝난 뒤 ZIP 파일을 다시 해시해 `source_zip_sha256_after`에 싣고 풀기 전 값과 대조한다 [3][4].
`inventory_archive_members`는 `include_sha256`이 참(기본값)이면 항목 목록을 읽기 전후의 ZIP 해시를 대조한다 [14][17].
대조는 내용의 해시로 하고 기준값은 같은 호출 안에서 계산한 값이다 [1][2][3].

**한계.** 대조는 한 호출 안의 실행 전후만 비교하고 앞선 호출의 값과 대조하지 않는다 [1][2][3].
파일 분석 도구는 결과 파일이 없거나 시간 제한·출력 한도에 닿거나 출력이 JSON이 아니면 실행 뒤 해시를 대조하지 않고 오류만 돌려준다 [18].
폴더를 받는 `analyze_artifact_folder`, `correlate_hosts`, `expand_investigation_graph`와 폴더를 받은 Hayabusa 도구는 대조하지 않는다 [7][12].
ZIP 항목 도구는 함께 꺼낸 `.LOG1`·`.LOG2` 사본의 SHA-256을 꺼낼 때만 계산하고 분석 뒤에는 다시 계산하지 않는다 [19][6].
응답 `companion_members`의 `member_sha256`은 꺼낼 때 계산한 값이다 [19].
해시 대조로 더하는 경고는 ZIP 파일이나 주 항목 사본의 전후 해시가 다를 때만 나온다 [2].
ZIP이 아닌 하이브를 받는 `parse_windows_artifact_with_eztools`는 `-f`로 넘기는 하이브 파일만 전후로 해시한다 [20][1].
RECmd·AmcacheParser가 dirty 하이브 옆에서 찾아 적용하는 `.LOG1`·`.LOG2`는 이 대조에 포함되지 않는다 [20][21].
시험용 실행 함수가 로그 사본이나 하이브 옆의 `SYSTEM.LOG1`만 바꾼 실행에서 응답 `status`는 `SUCCESS`였고 `warnings`는 빈 목록이었다 [22].
하이브 사본을 바꾼 실행에서는 `status`가 `DEGRADED`였다 [22].

### E02.04 도구를 요청해 검증

**구현.** 이 방식은 `artifact-forensic`의 `verify_sha256_manifest`에 적용된다 [23].
모델이 증거 폴더 아래의 해시 목록 파일을 주면 서버는 `<SHA-256> <대상>` 꼴의 줄마다 대상 파일의 SHA-256을 계산해 목록의 값과 대조한다 [23][24].
대상이 없는 줄은 목록 파일이 `.sha256`이면 그 확장자를 뗀 파일 하나를 대상으로 삼는다 [23].
상대 경로는 목록 파일의 폴더를 기준으로 하고 대상의 실제 경로가 증거 폴더 밖이면 `INVALID`, 파일이 없으면 `MISSING`으로 적는다 [23].
대조 결과는 줄마다 `MATCH`·`MISMATCH`·`MISSING`·`INVALID`·`SKIPPED`로 싣고 상태별 수를 `status_counts`에 싣는다 [23].
기준값은 모델이 고른 목록 파일에서 가져오고 응답의 `disclaimer`는 일치가 목록을 누가 만들었는지를 증명하지 않는다고 적는다 [25].
`deep-analysis` 워크플로 문서는 ZIP 옆에 `.sha256` 파일이 있으면 분석 전에 이 도구를 부르라고 적는다 [26].
맞는 해시, 다른 해시, 없는 파일, 형식이 틀린 줄을 담은 목록으로 부르자 `status_counts`는 `MATCH` 1, `MISMATCH` 1, `MISSING` 1이었다 [27].

**한계.** 이미 해시한 바이트에 대상 크기를 더한 값이 2GiB를 넘는 항목은 대조하지 않고 `SKIPPED`로 적는다 [23].
`max_entries`(최대 1,000)를 넘는 줄은 대조하지 않고 잘랐다는 경고만 싣는다 [23][28].

### E02.05 불일치 시 중단·경고

**구현.** 이 방식은 위의 두 대조가 어긋날 때 적용된다.
파일 분석 도구와 ZIP 항목 도구는 해시가 다르면 "The source artifact changed during analysis." 같은 경고를 `warnings`와 `note`에 더하고 응답 `status`를 `DEGRADED`로 둔다 [1][2].
ZIP 항목 도구는 꺼낸 주 항목 사본의 해시가 달라져도 "The internal member copy changed during analysis."를 더한다 [2].
`inventory_archive_members`도 전후 해시가 다르면 경고를 더하고 `status`를 `DEGRADED`로 둔다 [14][29].
`verify_sha256_manifest`는 `MISMATCH`·`MISSING`·`INVALID`·`SKIPPED`가 하나라도 있으면 상태별 수를 경고로 싣고 `status`를 `DEGRADED`로 둔다 [23].
공통 모듈은 이 `note`를 `evidence_v1` 응답의 `limitations`에 `TOOL_NOTE`로 옮기고 `status` `DEGRADED`를 그대로 쓴다 [30].
불일치가 있는 목록으로 부른 응답을 `evidence_v1`로 감싸자 `status`는 `DEGRADED`였고 `limitations`에 `TOOL_NOTE` 1개가 실렸다 [27].
서버는 분석 결과를 그대로 돌려주고 이후의 호출을 막지 않는다.
불일치를 기억하는 상태도 없다.

**한계.** `analyze_triage_zip`은 ZIP 해시가 달라지면 `load_warnings`에 문장을 더하기만 한다 [4].
공통 모듈은 `load_warnings`를 보지 않으므로 `evidence_v1` 응답의 `status`는 `SUCCESS`로 남는다 [4][30].
분석 중에 원본 ZIP 끝에 1바이트를 덧붙이는 시험용 `IR_Collect.exe`로 부르자 `load_warnings`에 문장이 실리고 해시 전후가 달랐지만 `status`는 `SUCCESS`, `errors`와 `limitations`는 빈 목록이었다 [31].
