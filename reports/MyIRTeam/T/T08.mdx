# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 `local-forensic`의 Sysinternals 도구와 PowerShell 실행, `artifact-forensic`의 EZ Tools·Hayabusa·capa·YARA·YARA-X 실행에 적용된다 [1][2][3][4][5][6].
`run_sysinternals_tool`은 종료 코드가 0이 아니면 `Error: <도구> exited with code <값>.` 뒤에 도구의 출력을 붙인 글을 돌려준다 [1].
`run_powershell_json`은 종료 코드가 0이 아니면 `PowerShell command failed.`와 표준 오류를 `error`·`details`로 돌려준다 [2].
`evidence_v1` 응답에서 Sysinternals 도구 하나의 결과를 그대로 돌려주는 도구와 PowerShell 결과를 그대로 돌려주는 `list_running_processes`·`list_loaded_dlls`·`list_services`·`list_scheduled_tasks`의 상태는 이때 `FAILED`다 [7].
PowerShell 결과를 `result`나 `host` 안에 담는 `get_forensic_context`·`get_file_metadata`·`collect_event_log_events`·`list_wmi_subscriptions`·`collect_defender_context`·`list_local_users_and_admins`·`collect_network_context`와 채널마다 결과를 담는 `collect_ir_event_bundle`의 상태는 `DEGRADED`다 [7][8].
실행 확인에서 종료 코드 1을 돌려주도록 바꾼 Sysinternals 실행으로 `collect_autoruns`를 부르면 상태가 `FAILED`였다 [9].

`artifact-forensic`의 EZ Tools와 Hayabusa 실행은 출력 파일이 없으면 종료 코드와 상관없이 실패로 정한다 [3][4].
이때 `details`에는 도구의 표준 오류나 표준 출력을 싣고 둘 다 비면 종료 코드를 싣는다 [3][4].
출력 파일이 있고 종료 코드가 0이 아니면 `<도구> returned exit code <값>.` 경고를 싣고 상태를 `DEGRADED`로 둔다 [3][4].
capa, YARA, YARA-X는 출력을 읽을 수 있으면 종료 코드가 0이 아닐 때 같은 경고와 `DEGRADED`를 싣는다 [5][6].
종료 코드는 `provenance.exit_code`에도 실린다 [3][4].
실행 확인에서 CSV를 쓰고 종료 코드 3으로 끝나는 시험용 실행 파일을 PECmd 자리에 두면 상태가 `DEGRADED`였고 `PECmd returned exit code 3.` 경고가 실렸다 [9].

`ir-collect`는 `IR_Collect.exe`의 종료 코드로 성공과 실패를 정하지 않는다 [10][11].
`analyze_artifact_folder`·`analyze_triage_zip`·`correlate_hosts`·`expand_investigation_graph`는 출력 JSON이 있으면 정상 결과로 돌려주고 종료 코드는 `provenance.exit_code`에만 싣는다 [10][12].
실행 확인에서 결과 JSON을 쓰고 종료 코드 5로 끝나는 시험용 실행 파일로 `analyze_artifact_folder`를 부르면 `evidence_v1` 응답 상태가 `SUCCESS`였고 `errors`가 비어 있었다 [9].
`collect_triage_package`는 ZIP이 있으면 정상 결과로 돌려주고 종료 코드는 `exit_code`에만 싣는다 [11].
`IR_Collect` 0.24.2의 `-c`는 실패한 수집 단계가 있으면 ZIP을 만든 뒤 종료 코드 2로 끝나고 수집 범위가 빠졌을 때는 종료 코드 0으로 끝난다 [13].
`IR_Collect` 0.24.2의 `-analyze`는 폴더를 읽지 못하거나 사실 추출이 실패하면 출력 JSON을 쓰지 않고 1로 끝난다 [14].

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 세 증거 서버가 실행하는 모든 외부 프로그램에 적용된다 [1][2][15][16][17].
`local-forensic`은 Sysinternals 도구를 기본 180초, `collect_autoruns`는 300초의 시간 제한으로 실행한다 [1][18].
PowerShell 실행의 시간 제한은 도구에 따라 120초, 180초, 300초다 [2][19].
시간 제한을 넘으면 `subprocess.run`이 실행을 끊고 서버는 `timed out after <초> seconds` 문구의 오류를 돌려준다 [1][2].
실행 확인에서 시간 제한 예외를 내도록 바꾼 Sysinternals 실행으로 `collect_autoruns`를 부르면 상태가 `FAILED`였고 `timed out after 300 seconds` 문구가 실렸다 [9].

`artifact-forensic`의 Hayabusa 실행은 `HAYABUSA_TIMEOUT`(기본 300초, 1~3600초)으로 끊고 `Hayabusa exceeded the configured timeout` 오류를 돌려준다 [16][4].
EZ Tools, capa, YARA·YARA-X는 `run_static_tool`이 0.05초마다 종료와 출력 크기를 보며 `STATIC_ANALYSIS_TIMEOUT`(기본 180초)을 넘으면 프로세스를 끝내고 `timed_out`을 참으로 둔다 [17].
capa와 YARA는 `timed_out`이 참이면 오류로 끝낸다 [5][6].
YARA와 YARA-X에는 도구 자신의 시간 제한 인자로 같은 값을 주고 프로세스 시간 제한은 그보다 10초 길게 둔다 [20].
EZ Tools는 끊기 전에 CSV가 나왔으면 그 행을 결과로 싣고 `Analysis exceeded the <초>-second timeout.` 경고와 `DEGRADED`를 싣는다 [3].
실행 확인에서 CSV를 쓴 뒤 6초 동안 멈추는 시험용 PECmd를 시간 제한 2초로 부르면 상태가 `DEGRADED`였고 CSV의 2행과 시간 제한 경고, 끝낸 프로세스의 종료 코드 1 경고가 함께 실렸다 [9].

`ir-collect`의 `run_ircollect`는 분석을 `IRCOLLECT_ANALYZE_TIMEOUT`(기본 300초), 수집을 `IRCOLLECT_COLLECT_TIMEOUT`(기본 1800초)으로 끊고 종료 코드 -1과 `IR_Collect timed out after <초>s.` 문구를 돌려준다 [15][21].
그 뒤 출력 파일이 없으면 그 문구를 `stderr`에 담은 오류로 끝낸다 [10].

`collect_ir_event_bundle`은 채널 8개를 차례로 묻고 채널마다 180초의 시간 제한을 두며 호출 전체의 시간 제한은 없다 [22][23].

**한계.** `ir-collect`는 시간 제한으로 끊긴 뒤에도 출력 JSON이나 ZIP이 있으면 정상 결과로 돌려주고 `exit_code`만 -1로 싣는다 [10][11].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 세 증거 서버의 결과 해석과 공통 응답 형식 `evidence_v1`의 상태 결정에 적용된다 [2][7][3][10].
`local-forensic`의 PowerShell 스크립트는 오류를 처리해 `status`나 `error`가 들어 있는 JSON을 출력하고 `run_powershell_json`은 JSON으로 읽지 못한 출력을 `PowerShell returned invalid JSON.`과 원문으로 돌려준다 [2][23].
`collect_event_log_events`의 스크립트는 일치하는 사건이 없다는 오류를 실패와 나누어 `count` 0과 `No matching events` 문구의 성공 결과로 돌려준다 [23].
`evidence_v1`은 결과를 읽어 상태를 정한다 [7].

- 결과에 `error`가 있거나 `status`가 `FAILED`·`ERROR`이면 `FAILED`다 [7].
- 결과 글이 `Error:`나 `File not found:`로 시작하면 `FAILED`다 [7].
- `status`가 `DEGRADED`·`PARTIAL`이거나 안쪽 결과 `result`에 오류가 있으면 `DEGRADED`다 [7].
- 항목 목록 `results`나 질의 목록 `queries`에 실패한 항목이 있으면 `DEGRADED`다 [7].

`artifact-forensic`는 EZ Tools가 CSV를 내지 않거나 Hayabusa가 JSONL을 내지 않으면 실패로 정한다 [3][4].
CSV를 읽지 못한 파일과 JSON으로 읽지 못한 JSONL 줄은 20개까지 `parse_errors`에 싣고 경고와 `DEGRADED`를 싣는다 [24][25][3][4].
capa는 출력이 JSON이 아니거나 객체가 아니거나 `rules`가 없으면 실패로 정하고 YARA-X는 출력이 JSON이 아니면 실패로 정한다 [5][26][6].
출력이 16MB를 넘어 실행을 끊으면 capa와 YARA는 실패로, EZ Tools는 경고와 `DEGRADED`로 정한다 [17][5][6][3].

`ir-collect`는 출력 JSON이 없거나 JSON으로 읽지 못하면 실패로 정한다 [10].
`analyze_artifact_folder`와 `analyze_triage_zip`은 사실 수가 0이면 출처별 건수를 `EMPTY_ANALYSIS`로, 건수가 없고 사실 수도 모르면 `UNAVAILABLE`로 두어 빈 결과와 빠진 값을 나눈다 [27].
실행 확인에서 `fact_count` 0인 결과 JSON을 쓰는 시험용 실행 파일로 부르면 `coverage_reporting`의 두 값이 `EMPTY_ANALYSIS`였다 [9].

**한계.** 다음 경로는 실패를 성공과 나누지 못한다.

- `run_powershell_json`은 표준 출력이 비면 빈 목록을 돌려주므로 `list_running_processes` 같은 도구는 0건의 성공 결과를 낸다 [2][28].
- `run_sysinternals_tool`은 종료 코드가 0이면 출력이 비어도 그대로 돌려준다 [1].
- `run_sysinternals_tool`이 실행 파일을 시작하지 못해 돌려준 `Error executing` 문구는 `Error:`로 시작하지 않아 `evidence_v1`이 실패로 읽지 않는다 [1][29].
- YARA-X의 표준 출력이 비면 서버는 일치 0건으로 두고 YARA의 표준 출력은 형식을 보지 않고 빈 줄이 아닌 줄마다 일치 하나로 세므로 두 백엔드에서 출력이 비거나 형식이 다른 실행은 종료 코드나 표준 오류가 있을 때만 경고와 `DEGRADED`로 드러난다 [6].
- `build_process_tree_snapshot`은 `list_running_processes`를 기본 응답 형식으로 불러 `evidence_v1` 응답을 받고 그 최상위에서 `error`와 `processes`를 찾는다 [30].

`evidence_v1` 응답에는 `error`와 `processes` 키가 최상위에 없으므로 `build_process_tree_snapshot`은 PowerShell이 실패해도 실패를 알아채지 못하고 프로세스 0개를 돌려준다 [30][31].
실행 확인에서 시험용 PowerShell 대체가 프로세스 2개를 돌려줄 때 `list_running_processes`는 2개를, `build_process_tree_snapshot`은 0개를 돌려주었다 [9].
대체가 PowerShell 실패를 돌려줄 때 `list_running_processes`의 상태는 `FAILED`였고 `build_process_tree_snapshot`의 상태는 `SUCCESS`였다 [9].
같은 실행 확인에서 종료 코드 0과 빈 출력을 돌려주는 Sysinternals 대체로 `collect_autoruns`를 부르면 빈 글이 `SUCCESS`로 왔고 `OSError`를 내는 대체로 부르면 `Error executing` 문구가 `SUCCESS`로 왔다 [9].

### T08.04 입력별 부분 완료 집계

**구현.** 이 방식은 `local-forensic`의 묶음 도구와 `artifact-forensic`의 해시 목록 검증·목록 작성 도구에 적용된다 [32][22][33].
`check_file_signatures_batch`는 경로마다 결과를 `results`에 싣고 `evidence_v1`은 실패 글이 들어 있는 행을 세어 `PARTIAL_RESULT_FAILURE`로 알린다 [32][34].
`collect_ir_event_bundle`은 채널 8개의 질의 결과를 `queries`에 싣고 `evidence_v1`은 실패한 질의를 세어 `PARTIAL_QUERY_FAILURE`로 알린다 [22][34].
`list_loaded_dlls`는 프로세스마다 모듈을 읽지 못한 오류를 `module_error`에 싣고 `evidence_v1`은 그 프로세스 수를 `PARTIAL_MODULE_ENUMERATION`으로 알린다 [35][34].
실행 확인에서 8개 채널 가운데 2개가 실패하게 바꾼 PowerShell 대체로 `collect_ir_event_bundle`을 부르면 상태가 `DEGRADED`였고 `2 bounded sub-query or channel request(s) failed.`가 실렸다 [36].

`verify_sha256_manifest`는 항목마다 `MATCH`, `MISMATCH`, `MISSING`, `INVALID`, `SKIPPED` 가운데 하나를 정하고 상태별 개수를 `status_counts`에 싣는다 [33].
`inventory_archive_members`는 경로가 안전하지 않거나 암호화되었거나 이름이 겹치거나 크기·압축 비율 상한을 넘은 항목을 종류별로 센다 [37].
`inventory_evidence_path`는 건너뛴 링크와 증거 폴더 밖으로 이어진 항목을 센다 [38].

`correlate_hosts`와 `expand_investigation_graph`는 `IR_Collect.exe`가 결과 JSON에 적은 `ready_hosts`·`skipped_hosts`나 호스트 수를 옮기기만 하고 서버가 호스트별 결과를 구분하지 않는다 [39].

**한계.** `check_file_signatures_batch`에서 실행 파일을 시작하지 못한 행의 `Error executing` 문구는 실패 행으로 세지 않는다 [34][29].
실행 확인에서 4개 경로 가운데 종료 코드 오류, 실행 실패, 없는 파일이 하나씩 있게 바꾸면 실패 행은 2개로 세어졌다 [36].
`inventory_evidence_path`는 파일 정보를 읽지 못한 파일을 세지 않고 건너뛴다 [38].
`evidence_v1`은 모든 행이나 질의가 실패해도 상태를 `FAILED`가 아니라 `DEGRADED`로 둔다 [34].
실행 확인에서 8개 채널이 모두 실패하게 바꾼 PowerShell 대체로 `collect_ir_event_bundle`을 부르면 상태가 `DEGRADED`였다 [8].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 `artifact-forensic`의 서버 안 분석 코드, `ir-collect`의 결과 JSON 읽기와 ZIP 풀기, `myirteam-core`의 자료 파일 읽기에 적용된다 [40][10][41].
`inspect_binary_file`은 파일을 읽거나 PE 구조를 해석하다 난 `OSError`, `struct.error`, `ValueError`를 처리해 `error`로 돌려준다 [40].
PE 머리가 맞지 않는 파일은 `parse_error`를 담은 결과로 두고 경고와 `DEGRADED`를 싣는다 [40][42].
실행 확인에서 PE 서명이 없는 MZ 파일로 부르면 상태가 `DEGRADED`였고 `missing PE signature` 경고가 실렸다 [9].
`verify_sha256_manifest`는 항목 하나의 경로를 해석하거나 해시를 계산하다 난 `OSError`를 그 항목의 `INVALID`로 정하고 나머지 항목을 계속 검증한다 [33].
ZIP 항목을 분석하는 도구는 항목 사본을 만들거나 분석하다 난 예외를 처리해 `could not safely analyze archive member` 오류로 돌려준다 [43].
`ir-collect`는 결과 JSON을 읽지 못하거나 ZIP을 풀지 못하면 `error`로 돌려준다 [10][44].
`myirteam-core`는 manifest, 워크플로, schema 파일을 읽지 못하면 오류 코드를 담은 `FAILED` 응답을 돌려준다 [41].

**한계.** `ir-collect`의 결과 정리 함수는 결과 JSON의 필드가 기대한 자료형이 아니면 예외를 처리하지 않는다 [27][45].
이 예외는 MCP Python SDK 1.28.1의 FastMCP가 `Error executing tool <도구>: ` 뒤에 붙여 `isError` 응답으로 돌려준다 [46].
실행 확인에서 `guided_hunt`가 목록인 `summary_v3` 보고서로 `ingest_analysis_report`를 부르면 `isError`가 참인 `Error executing tool ingest_analysis_report: 'list' object has no attribute 'get'` 응답이 왔다 [47].
`analyze_artifact_folder`·`analyze_triage_zip`·`correlate_hosts`·`expand_investigation_graph`는 `IR_Collect.exe`가 쓴 JSON이 객체가 아닐 때도 정리 함수를 그대로 부른다 [10][27][12].

def run_ircollect(cfg: Config, args: list[str], cwd: Path | None = None,
                  timeout: int | None = None) -> tuple[int, str, str]:
    """Run IR_Collect.exe with args. Returns (exit_code, stdout_text, stderr_text).
    stdout is unreliable for winexe — callers read the output FILE, not this."""
    cmd = [str(cfg.exe_path), *args]
    eff_timeout = timeout if timeout is not None else cfg.analyze_timeout
    try:

            cmd,
            capture_output=True,
            timeout=eff_timeout,
            check=False,
            creationflags=CREATE_NO_WINDOW,
            cwd=(str(cwd) if cwd else None),
        )
    except subprocess.TimeoutExpired:
        return (-1, "", f"IR_Collect timed out after {eff_timeout}s.")
    except OSError as exc:
        return (-1, "", f"failed to launch IR_Collect ({cfg.exe_path}): {exc}")
    return (result.returncode, decode_output(result.stdout), decode_output(result.stderr))

    try:
        p = validate_evidence_file(report_path, cfg)
    except ValueError as exc:
        return {"error": str(exc)}

    if not isinstance(data, dict):
        return {"error": "report is not a JSON object."}

    if shaper is None:
