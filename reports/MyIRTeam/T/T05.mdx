# T05 분석 도구 검증

### T05.01 저장소·의존성 고정

**구현.** 이 방식은 `External Tools/external_tools_manifest.json`이 적은 외부 분석 도구와 서버 코드가 해시를 적은 RECmd 프로필 파일에 적용된다 [1][2].
manifest는 도구 14개마다 놓을 상대 경로, 버전, 실행 파일의 SHA-256을 적는다 [1].
버전과 SHA-256이 모두 있는 도구는 Hayabusa 3.10.0, EvtxECmd·PECmd·AmcacheParser·RECmd·MFTECmd 2026.5.0, capa 7.1.0, YARA-X 1.19.0, `IR_Collect.exe` 0.24.2의 9개다 [1].
SrumECmd, YARA, KAPE, Volatility 3, WinPmem은 두 값이 비어 있다 [1].
`External Tools/README.md`는 사용자가 도구를 공식 배포처에서 따로 받아 manifest의 경로에 두고 버전과 SHA-256을 manifest와 대조하라고 적는다 [3].
저장소는 실행 파일을 담지 않고 `.gitignore`로 도구 폴더와 `*.exe`를 뺀다 [4].
설치를 맡는 스크립트는 저장소에 없다.

같은 SHA-256은 서버 코드에도 상수로 있다 [2][5].
`artifact-forensic`은 Hayabusa, capa, YARA, YARA-X, EZ Tools 5개의 SHA-256과 RECmd 프로필 파일 5개의 SHA-256을, `ir-collect`는 `IR_Collect.exe`의 SHA-256을 상수로 둔다 [2][5].
`portable_setup.py`는 이 값을 클라이언트 설정의 `*_EXPECTED_SHA256` 환경변수로 적는다 [6].
YARA 규칙 폴더 `yara-rules/`에는 README만 있고 규칙 파일은 저장소에 없다 [7].
Sysinternals 도구 4개는 manifest에 없고 저장소 어디에도 버전이나 해시가 없다 [1][8].
서버 실행용 라이브러리 `mcp`는 `requirements.txt`가 `mcp>=1.27,<2` 범위만 적고 이 방식으로 보지 않는다 [9].

**한계.** manifest의 YARA 항목은 버전과 SHA-256이 비어 있지만 서버 코드는 YARA 4.5.5와 SHA-256 상수를 둔다 [1][2].
`portable_setup.py`는 YARA의 기대 해시를 설정에 적지 않는다 [6].
RECmd 프로필 파일의 SHA-256은 서버 코드에만 있고 manifest에는 없다 [1][2].
도구를 설치할 때 버전과 해시를 대조하는 일은 사용자가 손으로 한다 [3].

### T05.02 설정·호출 인자로 지정

**구현.** 이 방식은 `ir-collect`·`artifact-forensic`이 실행하는 분석 도구의 위치와 기대 해시, YARA 규칙의 위치에 적용된다 [10][11].
`ir-collect`는 환경변수 `IRCOLLECT_EXE`로 `IR_Collect.exe`의 위치를, `IRCOLLECT_EXPECTED_SHA256`으로 기대 해시를 받는다 [10].
`artifact-forensic`은 `HAYABUSA_EXE`·`CAPA_EXE`·`YARA_EXE`·`YARAX_EXE`와 EZ Tools 5개의 `<도구>_EXE`로 위치를, 같은 이름의 `*_EXPECTED_SHA256`으로 기대 해시를 받는다 [11].
환경변수를 주지 않으면 프로젝트 폴더의 `External Tools` 아래 정해 둔 경로를 쓴다 [2][5].
YARA 규칙은 사용자가 `YARA_RULE_ROOTS`로 정한 폴더 안에서 모델이 `rules_path`로 파일이나 폴더를 고른다 [12][13].
Hayabusa 규칙과 EvtxECmd 맵은 서버가 위치를 따로 넘기지 않아 실행 파일 폴더의 것을 쓴다 [14][15][16].
Hayabusa 3.10.0은 `-r`이 없으면 실행 파일 폴더의 `encoded_rules.yml`이나 `rules` 폴더를 쓰고 EvtxECmd는 `--maps`가 없으면 실행 파일 폴더의 `Maps`를 쓴다 [15][16].
그래서 `HAYABUSA_EXE`·`EVTXECMD_EXE`로 실행 파일 위치를 바꾸면 규칙과 맵의 위치도 바뀐다 [14][15][16].
`local-forensic`의 Sysinternals 도구 위치는 프로젝트 폴더의 `Sysinternals Suite`로 정해져 있고 바꾸는 설정이 없다 [8].
PowerShell은 `PATH`에서 찾은 `pwsh.exe`나 `powershell.exe`를 쓴다 [17].

### T05.03 실행 시 버전 조회

**구현.** 이 방식은 세 증거 서버의 정보 도구와 `IR_Collect.exe`·capa의 분석 결과에 적용된다 [18][19][20][21].
`ir-collect`의 `get_ircollect_info`는 `IR_Collect.exe`의 PE 파일 버전을 Windows 버전 정보 API로 읽는다 [18].
`IR_Collect.exe`는 창 프로그램이라 표준 출력을 믿을 수 없어 실행하지 않고 파일에서 읽는다 [18].
분석 도구가 쓴 JSON의 `tool_name`·`tool_version`은 응답의 `provenance`에 옮긴다 [22].
`artifact-forensic`의 `get_artifact_forensic_info`는 해시 대조를 통과한 Hayabusa를 `help`로 실행해 출력의 `Hayabusa v<버전>`을 읽는다 [19].
Hayabusa 3.10.0의 도움말 첫 줄에는 `Hayabusa v3.10.0`이 있다 [23].
capa, YARA, YARA-X, EZ Tools는 해시 대조를 통과하면 `--version`으로 실행해 출력에서 처음 나오는 `숫자.숫자` 꼴의 값을 버전으로 읽는다 [20].
`analyze_file_with_capa`는 capa JSON의 `meta.version`을 응답의 `capa_result_meta`에 싣는다 [24].
`local-forensic`의 `get_forensic_context`는 PowerShell로 Sysinternals 도구 4개의 `FileVersion`·`ProductVersion`을 읽는다 [21].

**한계.** 읽은 버전은 manifest나 서버 코드의 버전과 대조하지 않는다 [20][18].
`--version` 출력에서 숫자 꼴만 고르므로 출력이 버전이 아니어도 숫자가 있으면 그 값이 버전이 된다 [20].
`fake 9.9.9`를 출력하는 시험용 실행 파일을 capa 자리에 두자 `version`이 `9.9.9`로 돌아왔다 [25].
도구마다 `--version`의 출력 모양은 확인하지 못했다 [20].

### T05.04 참조 자료 버전·식별값 조회

**구현.** 이 방식은 YARA 규칙 묶음에 적용된다 [26].
`scan_file_with_yara`는 고른 규칙 파일마다 경로와 SHA-256을 이어 붙여 다시 SHA-256을 계산하고 응답의 `rules.sha256`과 `provenance.rule_set_digest`에 싣는다 [26].
규칙 묶음의 버전이나 가져온 곳은 읽지 않는다 [26].
`get_artifact_forensic_info`는 Hayabusa 폴더의 `encoded_rules.yml`·`rules_config_files.txt`가 있는지만 적고 버전이나 해시는 읽지 않는다 [27].
EvtxECmd 맵의 버전이나 해시는 읽지 않는다.

### T05.05 사용 전 기대값 대조

**구현.** 이 방식은 `artifact-forensic`이 실행하는 Hayabusa, capa, YARA, YARA-X, EZ Tools와 RECmd 프로필 파일, `ir-collect`가 실행하는 `IR_Collect.exe`에 적용된다 [28][29][30].
`artifact-forensic`의 `executable_integrity`는 실행 직전에 실행 파일의 SHA-256을 계산해 기대 해시와 대조한다 [28].
실행 파일이 없거나 기대 해시가 없거나 값이 다르면 `FAILED`를 돌려주고 도구 함수는 분석 도구를 실행하지 않는다 [28][31].
기대 해시는 `*_EXPECTED_SHA256`이고 그 값이 없으면서 정해 둔 경로를 쓸 때만 서버 코드의 상수를 쓴다 [32].
YARA 도구의 `backend`가 `auto`이면 대조를 통과한 YARA-X를 먼저 고르고 YARA-X가 통과하지 못하면 대조를 통과한 YARA를 고른다 [33].
RECmd를 쓸 때는 고른 프로필 파일의 SHA-256을 서버 코드의 상수와 대조하고 다르면 실행하지 않는다 [29].
`ir-collect`의 `ircollect_integrity_status`는 `IR_Collect.exe`를 실행하는 도구마다 실행 전에 SHA-256을 계산해 기대 해시와 대조하고 다르면 실행하지 않는다 [30].
기대 해시가 다른 설정에서는 `SHA-256 does not match` 오류로 끝났다 [34].
PECmd 자리에 시험용 실행 파일을 두고 기대 해시를 주지 않자 `no expected SHA-256 is configured` 오류로 끝났다 [25].
기대 해시를 맞춘 시험용 실행 파일은 실행되었다 [25][34].

Hayabusa 규칙, EvtxECmd 맵, YARA 규칙 파일은 쓰기 전에 기대값과 대조하지 않는다 [27][26].
서버는 capa에 `-r`을 넘기지 않고 capa 7.1.0은 `-r`이 없으면 PyInstaller로 만든 실행 파일 안에 담긴 규칙을 쓴다 [35].
이 경우 capa 규칙은 실행 파일의 SHA-256 대조에 포함된다 [35].
manifest가 적은 capa 실행 파일이 PyInstaller로 만든 것인지는 배포 파일로 확인하지 못했다.
`local-forensic`은 Sysinternals 도구와 PowerShell의 해시를 실행 전에 대조하지 않는다 [36].
`get_external_tool_inventory`는 manifest의 SHA-256과 실제 파일의 SHA-256을 대조해 `sha256_matches_manifest`로 알리기만 하고 실행을 막지 않는다 [37].

**한계.** `ir-collect`는 기대 해시가 없으면 대조를 건너뛰고 실행한다 [30].
`IRCOLLECT_EXE`로 다른 위치를 정하고 `IRCOLLECT_EXPECTED_SHA256`을 주지 않으면 서버 코드의 상수도 쓰지 않는다 [10].
이 설정에서 시험용 실행 파일이 대조 없이 실행되었고 응답의 `verified`는 `null`이었다 [34].
`get_ircollect_info`는 이때 `integrity is unverified`를 적는다 [18].

def validate_rule_files(path_str: str, cfg: Config) -> list[Path]:
    if not path_str or not path_str.strip():
        raise ValueError("rules_path is empty.")
    path = _resolve(path_str)
    if not cfg.rule_roots:
        raise ValueError("no YARA rule roots configured (set YARA_RULE_ROOTS).")
    if not is_under_roots(path, cfg.rule_roots):
        raise ValueError(f"rules path is outside the configured YARA rule roots: {path}")
    if path.is_symlink():
        raise ValueError(f"symbolic-link rule paths are not accepted: {path}")
    if path.is_file():
        candidates = [path]
    elif path.is_dir():
        candidates = sorted(
            item.resolve()
            for item in path.rglob("*")
            if item.is_file() and not item.is_symlink() and item.suffix.lower() in {".yar", ".yara"}
        )
    else:
        raise ValueError(f"rules path does not exist: {path}")
    candidates = [item for item in candidates if item.suffix.lower() in {".yar", ".yara"}]
    if not candidates:
        raise ValueError(f"no .yar or .yara source files found: {path}")
    if len(candidates) > MAX_RULE_FILES:
        raise ValueError(f"rules path contains {len(candidates)} files; maximum is {MAX_RULE_FILES}.")
    if any(not is_under_roots(item, cfg.rule_roots) for item in candidates):
        raise ValueError("one or more resolved rule files escaped the configured rule roots.")
    return candidates
