# R01 결과 가공

### R01.01 가공 없이 전달

**구현.** 이 방식은 `local-forensic`의 `collect_autoruns`·`check_file_signatures`·`check_file_signatures_batch`·`list_network_connections`·`list_open_handles`, `artifact-forensic`의 Hayabusa 도구와 YARA 실행 파일 경로, `ir-collect`가 IR_Collect 보고서에서 옮기는 목록 항목에 적용된다 [1][2][3][4].
`local-forensic`의 공통 실행기 `run_sysinternals_tool`은 Sysinternals 도구의 표준 출력을 글자로 바꾼 뒤 그대로 돌려준다 [1].
`collect_autoruns`·`check_file_signatures`·`list_network_connections`·`list_open_handles`는 이 글을 바꾸지 않고 결과로 쓴다 [5].
`check_file_signatures_batch`는 경로마다 이 글을 `results`의 `result`에 그대로 싣는다 [5].
`artifact-forensic`의 Hayabusa 도구 두 개는 `json-timeline` 출력의 JSONL 줄을 `json.loads`로 읽은 객체를 그대로 `records`에 싣는다 [2].
값의 길이를 줄이지 않으므로 3,000자 값이 들어 있는 레코드가 바뀌지 않고 실렸다 [6].
YARA 실행 파일(`yara64.exe`)을 고르면 출력 한 줄을 `raw_match_line`에 그대로 싣는다 [3].
`ir-collect`는 Guided Hunt 일치의 `evidence` 줄, `shared_entities`·`temporal_correlations`·`nodes`·`edges`의 항목을 바꾸지 않고 싣는다 [4].

응답 형식은 이 동작을 바꾸지 않는다.
`legacy` 형식은 도구의 결과를 그대로 돌려주고 기본 형식 `evidence_v1`은 결과를 바꾸지 않고 `data`에 넣는다 [7].
그래서 `evidence_v1`에서는 Sysinternals 출력이 JSON 문자열 값 하나로 실린다 [7][8].

**한계.** `run_sysinternals_tool`은 표준 출력이 비어 있으면 표준 오류를 결과로 쓴다 [1].
종료 코드가 0이 아니면 `Error: <도구> exited with code N.` 문구 뒤에 도구 출력을 붙여 돌려준다 [1].
YARA 출력 줄은 8,000자에서 자르고 `...[TRUNCATED]`를 붙인다 [3][9].
Hayabusa 출력에서 2 MiB를 넘는 줄은 싣지 않고 `parse_errors`에 줄 번호만 남긴다 [10].

### R01.02 구조화 파싱·필드 선택

**구현.** 이 방식은 `local-forensic`의 PowerShell 도구, `ir-collect`의 보고서 정리 함수, `artifact-forensic`의 EZ Tools·capa·YARA-X 도구와 서버 안 파서에 적용된다 [11][12][13][14][15].
`local-forensic`은 고정 PowerShell 스크립트로 정해 둔 속성만 골라 `ConvertTo-Json`으로 출력하게 하고 그 글을 `json.loads`로 읽는다 [11][16].
예를 들어 `list_running_processes`는 `Win32_Process`에서 `ProcessId`·`ParentProcessId`·`Name`·`ExecutablePath`·`CommandLine`·`CreationDate`·`SessionId`만 고른다 [11].
`build_process_tree_snapshot`은 프로세스마다 부모 프로세스의 이름, 경로, 명령 줄을 이어 붙이도록 짜여 있다 [17].

`ir-collect`의 `shape_summary`·`shape_correlation`·`shape_graph`는 IR_Collect의 `summary_v3`·`correlation_v1`·`graph_v1` 보고서에서 필드를 골라 새 `dict`를 만든다 [12].
`shape_summary`는 Guided Hunt 일치마다 `id`·`title`·`severity`·ATT&CK 세 필드·`summary`·`evidence`·`suggested_hypothesis_id`만 옮긴다 [12].
가설 틀은 `id`·`title`·`question`·`why`만 옮긴다 [12].

`artifact-forensic`의 `read_csv_outputs`는 EZ Tools가 만든 CSV를 `csv.DictReader`로 읽어 행마다 열 이름을 키로 한 `dict`를 만든다 [13].
`shape_capa_document`는 capa 규칙마다 `meta`에서 이름, namespace, scope, 설명, 작성자, ATT&CK, MBC, 참고 주소, 라이브러리 여부를 고른다 [14].
`shape_yarax_document`는 YARA-X 일치마다 규칙 이름, namespace, 파일, 태그, 메타데이터를 고른다 [15].
`inspect_binary_file`은 서버 안에서 PE 머리와 섹션 표를 읽어 필드로 나눈다 [18].

**한계.** `build_process_tree_snapshot`은 `list_running_processes`를 `response_format` 없이 부르므로 그 결과는 기본 형식인 `evidence_v1` 응답이다 [17][19].
`evidence_v1` 응답에는 최상위 `processes` 키가 없어 이 도구는 프로세스를 하나도 읽지 못한다 [17][7].
같은 프로세스 행 3개를 돌려주도록 PowerShell 실행을 바꾸자 `list_running_processes`는 3개를 실었고 `build_process_tree_snapshot`은 두 형식 모두 `process_count` 0을 돌려줬다 [20].

`shape_summary`는 IR_Collect 요약에 있는 `fact_samples`, `collection_coverage`, Guided Hunt의 `explanation`·`fact_ids`·`notes`·`enabled`를 싣지 않는다 [12][21].
`evidence` 목록은 항목 수 `evidence_manifest_count`로만 남는다 [12].
capa 7.1.0의 JSON은 규칙 범위를 `scopes`에, 표본 해시를 `sample` 아래 `md5`·`sha1`·`sha256`에 둔다 [22].
서버는 `scope`와 `sample.hashes`를 읽으므로 `scope`는 늘 `null`, `sample_hashes`는 늘 빈 `dict`로 실린다 [14][23].
YARA-X 1.19.0의 JSON 일치 항목에는 namespace 필드가 없어 `namespace`는 늘 `null`이다 [15][24].
서버는 `yr.exe`에 `--print-namespace`를 넘기지만 YARA-X 1.19.0은 이 옵션을 `ndjson`과 텍스트 출력에만 반영한다 [25].
EZ Tools CSV에서 201번째부터의 열은 표시 없이 빠진다 [13].

### R01.03 형식 변환·건수 집계

**구현.** 이 방식은 세 증거 서버의 건수 필드, `artifact-forensic`의 해시·엔트로피 계산과 ZIP 항목 도구의 임시 경로 치환에 적용된다 [26][27][12][28].
`artifact-forensic`의 `inspect_binary_file`은 파일 전체의 MD5·SHA-1·SHA-256과 바이트 엔트로피, 섹션마다의 엔트로피를 계산한다 [27][18].
`inventory_evidence_path`는 확장자별 파일 수를, `inventory_archive_members`는 후보 아티팩트 유형별 수와 안전하지 않은 항목 수를 센다 [26][29].
`verify_sha256_manifest`는 상태별 항목 수 `status_counts`를 센다 [30].
`shape_capa_document`는 규칙마다 capa가 돌려준 일치 위치의 수를 `match_count`로 싣는다 [14].
`ir-collect`는 Guided Hunt 일치의 `fact_ids` 목록을 개수 `fact_id_count`로, 요약의 `evidence` 목록을 `evidence_manifest_count`로 바꾼다 [12].
`local-forensic`은 `matched_processes`·`service_count`·`task_count`처럼 돌려준 행의 수를 싣는다 [11].
ZIP 항목 도구는 결과의 모든 문자열 값에서 서버가 만든 임시 사본 경로를 `<ZIP 경로>::<항목 경로>`로, 작업 폴더 경로를 `[internal work directory]`로 바꾼다 [28].
EvtxECmd 출력의 `SourceFile` 값은 이 치환으로 `triage.zip::C/Windows/System32/winevt/Logs/Security.evtx` 꼴이 되었다 [31].

**한계.** `inventory_evidence_path`의 `extension_counts`와 `returned_total_bytes`는 `max_files`로 자른 뒤의 파일만 센 값이다 [26].
`_bounded_list`와 `_bounded_metadata`는 목록과 `dict` 안의 값을 `str()`로 바꾼다 [32].
그래서 capa의 ATT&CK·MBC 항목의 `parts` 목록은 `['Defense Evasion', ...]` 같은 Python 표기 문자열로 실린다 [23].
YARA-X 메타데이터의 정수 75와 참 값은 문자열 `"75"`와 `"True"`로 실렸다 [23].
임시 경로 치환은 문자열 값 전체에 적용되므로 증거 값 안에 같은 문자열이 있어도 바뀐다 [28].

### R01.04 가공 사실·대상 표시

**구현.** 이 방식은 `ir-collect`와 `artifact-forensic`의 `provenance`, `evidence_v1` 응답의 `tool`·`provenance`, EZ Tools 레코드의 `source_csv`에 적용된다 [12][33][7][13].
`artifact-forensic`의 분석 도구는 `provenance`에 분석 도구 이름, 버전, 실행 파일 SHA-256, 종료 코드, 출력 형식, 분석한 파일의 폴더를 싣는다 [33].
ZIP 항목 도구는 여기에 원본 ZIP 경로, 항목 경로, ZIP의 SHA-256, 사본을 분석했다는 `analyzed_copy`를 더한다 [28].
응답마다 `analysis_mode`에 분석 방식을 적는다 [33].
`ir-collect`는 IR_Collect가 보고서에 적은 도구 이름, 버전, schema, 생성 시각에 서버가 읽은 폴더, ZIP, 보고서 경로와 실행 파일 SHA-256을 더해 `provenance`에 싣는다 [12][34].
`read_csv_outputs`는 레코드마다 그 행을 읽은 CSV 파일 이름을 `source_csv`에 싣는다 [13].
`evidence_v1` 응답은 `tool`에 `<서버>/<도구>` 이름을 싣고 `provenance`에 `producer`와 결과의 `provenance`에서 고른 키 9개를 옮긴다 [7].

**한계.** `local-forensic`의 결과에는 `provenance`가 없다 [11].
그래서 `legacy` 형식의 `local-forensic` 응답에는 결과를 만든 도구를 적는 필드가 없고 `evidence_v1`에서도 `producer`만 있다 [7][35].
`evidence_v1` 응답이 옮기는 키에는 `analyzer_sha256`·`output_format`·`source_archive`·`source_member`가 없다 [7].
이 값은 `data` 안의 `provenance`에만 있다 [31].
Hayabusa 도구는 `tool_version`을 늘 `null`로 둔다 [2].
capa와 YARA 도구는 실행 파일 SHA-256이 서버에 적힌 값과 같을 때만 `tool_version`을 채운다 [33][3].

### R01.06 응답 항목 선별

**구현.** 이 방식은 `local-forensic`의 `collect_ir_event_bundle`, `ir-collect`의 건수 표, `artifact-forensic`의 Hayabusa 등급 기준과 RECmd 프로필, `inventory_evidence_path`에 적용된다 [36][37][38][39][26].
`collect_ir_event_bundle`은 채널 8개마다 서버가 정해 둔 사건 ID 목록으로만 사건을 읽는다 [36].
Security 채널은 4624·4625·4672·4688·4697·4698·4702·4720·4722·4728·4732·4756·1102를 읽는다 [36].
이 목록은 인자로 바꿀 수 없다 [36].
`ir-collect`의 `_nonzero`는 `fact_source_counts`와 `entity_type_counts`에서 값이 0인 항목을 뺀다 [37][12].
Hayabusa 도구는 `min_level`을 `-m`으로 넘기고 기본값은 `medium`이다 [38].
그래서 인자를 주지 않으면 `informational`·`low` 등급 규칙의 일치는 응답에 없다 [38].
`parse_windows_artifact_with_eztools`와 `parse_archive_member_with_eztools`는 레지스트리 하이브를 서버가 SHA-256으로 고정한 RECmd 배치 파일 5개 가운데 하나로 읽고 기본값은 `dfir`이다 [39].
배치 파일에 적힌 키만 결과에 실린다 [39][40].
`inventory_evidence_path`는 심볼릭 링크와 증거 루트 밖으로 이어지는 항목을 빼고 뺀 수를 경고 문구에 적는다 [26].

**한계.** `collect_ir_event_bundle`과 `_nonzero`가 뺀 항목의 수는 응답에 없다 [36][12].
RECmd 배치 파일은 저장소에 없고 서버는 SHA-256만 대조하므로 어떤 키를 고르는지는 배포된 파일에 달려 있다 [39].
RECmd 저장소 `bcd0ac3`의 `DFIRBatch.reb`와 배포된 파일이 같은지는 확인하지 못했다 [40].

    shared = data.get("shared_entities") if isinstance(data.get("shared_entities"), list) else []

    if value is None:

    rows = value if isinstance(value, list) else [value]
    bounded: list[Any] = []
    for row in rows[:limit]:
        if isinstance(row, (str, int, float, bool)) or row is None:
            bounded.append(_bounded_text(row))
        elif isinstance(row, dict):
