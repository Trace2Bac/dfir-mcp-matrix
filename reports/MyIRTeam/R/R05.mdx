# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 이 방식은 세 증거 서버의 `evidence_v1` 응답의 `target`과 `ir-collect`·`artifact-forensic` 결과의 `input`·`provenance`에 적용된다 [1][2][3].
`evidence_v1` 응답은 `target`에 대상의 종류 `type`과 식별자 `identifier`를 싣는다 [1].
`ir-collect`와 `artifact-forensic`은 모델이 준 폴더, ZIP, 파일, 보고서 경로를, ZIP 항목 도구는 `<ZIP 경로>::<항목 경로>`를 식별자로 쓴다 [2][4].
`ir-collect`의 `correlate_hosts`와 `expand_investigation_graph`는 폴더 수를 적은 문장을 식별자로 쓰고 폴더 경로는 결과의 `provenance.source_folders`에만 싣는다 [5].
`local-forensic`은 대상이 호스트이면 환경변수 `COMPUTERNAME`의 값을, 프로세스·사건 채널·파일이면 모델이 준 PID·이름·채널·경로를 식별자로 쓴다 [6].
`artifact-forensic`은 `input.path`에 분석한 파일의 실제 경로를, `provenance.evidence_digest`에 그 파일의 SHA-256을 싣는다 [3].
ZIP 항목 도구는 `provenance`에 ZIP 경로 `source_archive`와 항목 경로 `source_member`를 싣는다 [7].
`ir-collect`는 `provenance`에 읽은 폴더 `source_folder`·`source_folders`, ZIP `source_zip`, 보고서 `source_report`를 싣는다 [2].
EvtxECmd·MFTECmd 출력은 행마다 읽은 파일의 경로 `SourceFile`을, RECmd 출력은 `HivePath`를 가지며 서버는 이 열을 그대로 싣는다 [8][9].

`legacy` 형식에서는 `target`이 없고 결과 안의 `input`·`provenance`만 남는다 [1].
`legacy` 형식의 `local-forensic` 응답에서 대상 호스트를 가리키는 값은 `get_forensic_context`의 `hostname`과 사건 조회가 사건마다 싣는 `machine_name`뿐이다 [10][11].

**한계.** `COMPUTERNAME`이 없는 환경에서 `local-forensic`의 식별자는 `CURRENT_HOST`다 [6].
`COMPUTERNAME`을 주지 않고 실행한 서버의 `collect_autoruns` 응답에서 `target.identifier`는 `CURRENT_HOST`였다 [12].
`evidence_id`와 `snapshot_id`는 호출마다 새로 만든 무작위 값이고 이 값으로 결과나 증거를 다시 찾는 도구는 없다 [1].
Hayabusa 도구는 프로필 `standard`로 실행하고 Hayabusa 3.10.0의 `standard` 프로필에는 EVTX 파일 이름 필드 `EvtxFile`이 없다 [13][14].
그래서 폴더를 준 호출의 레코드에는 그 레코드가 나온 EVTX 파일이 없다 [13][14].
`ir-collect`는 IR_Collect 요약의 증거 파일 목록 `evidence`를 개수로만 싣는다 [15].

### R05.02 증거 내부 경로

**구현.** 이 방식은 `artifact-forensic`의 목록 도구와 EZ Tools 도구, `ir-collect`의 Guided Hunt 일치, `local-forensic`의 프로세스·모듈·파일 도구에 적용된다 [16][17][8][18][19].
`inventory_evidence_path`는 파일마다 입력 폴더 기준의 상대 경로 `relative_path`를, `inventory_archive_members`는 항목마다 ZIP 안 경로 `member_path`를 싣는다 [16][17].
EZ Tools 출력의 경로 열(MFTECmd의 `ParentPath`·`FileName` 등)은 그대로 실린다 [8].
ZIP 항목 도구에서는 서버가 임시 사본 경로를 `<ZIP 경로>::<항목 경로>`로 바꾸므로 `SourceFile`에 ZIP 안 경로가 실린다 [7][20].
IR_Collect의 Guided Hunt `evidence` 줄은 사실의 경로를 `path=` 뒤에 적고 서버는 이 줄을 그대로 싣는다 [18][15].
`local-forensic`은 프로세스의 `ExecutablePath`, 모듈의 `file_name`, 파일 메타데이터의 `path`처럼 대상 시스템 안 경로를 싣는다 [19].

### R05.03 레코드 키·번호

**구현.** 이 방식은 `local-forensic`의 사건 조회, `artifact-forensic`의 EZ Tools와 Hayabusa 도구에 적용된다 [11][8][13].
`collect_event_log_events`와 `collect_ir_event_bundle`의 PowerShell 스크립트는 사건마다 `record_id`를 싣는다 [11].
EvtxECmd 출력의 `RecordNumber`·`EventRecordId`, MFTECmd 출력의 `EntryNumber`·`SequenceNumber`·`UpdateSequenceNumber`, RECmd 출력의 `KeyPath`·`ValueName`은 그대로 실린다 [8][9][21].
Hayabusa 3.10.0의 `standard` 프로필은 `RecordID`를 출력하고 서버는 레코드를 바꾸지 않는다 [14][13].

**한계.** `ir-collect`는 Guided Hunt 일치의 사실 ID 목록 `fact_ids`를 개수 `fact_id_count`로 바꾼다 [15].
IR_Collect 요약의 사실 표본 `fact_samples`도 싣지 않는다 [15].

### R05.04 바이트·섹터·행 오프셋

**구현.** 이 방식은 `artifact-forensic`의 `inspect_binary_file`·`inspect_archive_member_binary`와 MFTECmd로 USN 저널을 읽은 결과에 적용된다 [22][21].
`parse_pe_structure`는 섹션마다 파일 안 위치 `raw_offset`과 크기 `raw_size`를, 마지막 섹션 뒤 자료가 있으면 그 위치 `overlay_offset`을 싣는다 [22].
시험용 PE 파일에서 `.text` 섹션의 `raw_offset`은 512, `overlay_offset`은 1024였다 [20].
MFTECmd의 USN 저널 출력은 레코드마다 `OffsetToData`를 가지며 서버는 이 열을 그대로 싣는다 [21][8].

**한계.** capa 7.1.0의 JSON은 규칙마다 일치한 주소를 `matches`에 싣지만 서버는 그 수만 `match_count`로 싣는다 [23][24].
YARA·YARA-X는 일치 문자열 출력 옵션 없이 실행하므로 일치 위치가 없다 [25].
추출한 문자열에도 파일 안 위치가 없다 [26].

### R05.05 참조 지식 원문 출처

**구현.** 이 방식은 `artifact-forensic`의 capa·YARA-X·Hayabusa 결과와 `ir-collect`의 Guided Hunt 일치에 적용된다 [27][28][14][18].
`shape_capa_document`는 규칙마다 capa 규칙 메타데이터의 ATT&CK 항목, MBC 항목, 참고 주소 `references`를 싣는다 [27].
ATT&CK·MBC 항목에는 기법 ID `id`가 들어 있다 [24][20].
`shape_yarax_document`는 규칙 메타데이터를 싣고 규칙이 `reference` 같은 메타데이터를 두면 그 값이 실린다 [28][20].
Hayabusa 레코드에는 규칙 ID `RuleID`가 있다 [14].
`ir-collect`는 Guided Hunt 일치마다 IR_Collect가 정한 ATT&CK 기법 ID `attack_technique_id`를 싣는다 [18].

이 값들은 증거 값과 다른 필드에 실리지만 코드와 도구 설명은 그 필드가 증거가 아니라고 밝히지 않는다 [27][18].

**한계.** YARA 실행 파일(`yara64.exe`) 경로는 출력 줄을 나누지 않으므로 메타데이터가 출력 줄 글 안에만 있다 [29].
capa ATT&CK 항목의 `parts`는 Python 목록 표기 문자열로 실린다 [20].
