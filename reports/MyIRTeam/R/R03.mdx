# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 네 서버의 모든 도구와 MCP Python SDK 1.28.1의 입력 검사에 적용된다 [1][2][3].
`myirteam-core`는 실패하면 `status`를 `FAILED`로, `error`를 `code`와 `message`를 가진 객체로 돌려준다 [1].
세 증거 서버는 기본 형식 `evidence_v1`에서 응답 최상위에 `status`를 `SUCCESS`·`DEGRADED`·`FAILED` 가운데 하나로 싣고 `errors`에 `code`와 `message`를 가진 항목을 싣는다 [2].
`status`는 공통 함수 `infer_status_and_messages`가 도구 결과를 보고 정한다 [2].
결과가 `error` 필드를 가지거나 결과의 `status`가 `FAILED`·`ERROR`이면 `FAILED`다 [2].
결과의 `status`가 `DEGRADED`·`PARTIAL`이거나 하위 결과에 실패가 있으면 `DEGRADED`다 [2].
결과가 문자열이면 `error:`나 `file not found:`로 시작할 때만 `FAILED`다 [4].

`legacy` 형식에서는 도구 결과의 필드가 상태를 알린다 [5].
`ir-collect`와 `artifact-forensic`은 실패하면 `error` 필드를 가진 `dict`를 돌려준다 [6][7].
`artifact-forensic`은 성공한 결과에도 `status`를 `SUCCESS`나 `DEGRADED`로 싣는다 [7].
SDK는 인자가 입력 schema에 맞지 않거나 도구 함수가 예외를 내면 `isError`가 참인 결과를 돌려준다 [3].
`max_events`에 정수가 아닌 값을 준 호출은 `isError`가 참이고 `Error executing tool …` 글을 받았다 [8].

**한계.** 도구가 실패를 결과로 돌려주면 `isError`는 거짓이다 [3][8].
`local-forensic`의 `collect_autoruns`·`check_file_signatures`·`list_network_connections`·`list_open_handles`는 결과가 문자열이라서 `legacy` 형식에서는 `Error:`로 시작하는 문장으로만 실패를 알린다 [9][10].
`run_sysinternals_tool`은 실행 파일을 시작하지 못하면 `Error executing <도구> …` 문장을 돌려준다 [9].
이 문장은 `error:`로 시작하지 않아 `evidence_v1`의 `status`가 `SUCCESS`가 된다 [9][4].
실행할 수 없는 파일을 `autorunsc.exe`로 둔 폴더에서 `collect_autoruns`를 부르자 `status`는 `SUCCESS`, `errors`는 빈 목록이었다 [11].
하위 결과의 실패는 `FAILED`가 아니라 `DEGRADED`가 된다 [2].
PowerShell 조회가 `Access is denied`로 실패한 `collect_event_log_events`의 `status`는 `DEGRADED`였다 [11].
`response_format`에 허용되지 않는 값을 주면 `status` 없이 `error`와 허용 값만 담은 `dict`를 돌려준다 [5][8].
`errors`의 `code`는 `TOOL_ERROR`처럼 결과의 위치만 가리키고 실패 종류는 문구에만 있다 [2].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 `local-forensic`의 사건 조회와 파일 메타데이터, `artifact-forensic`의 해시 목록 검증과 ZIP 항목 도구, `ir-collect`의 요약 정리에 적용된다 [12][13][14][15][16].
`collect_event_log_events`의 PowerShell 스크립트는 일치하는 사건이 없으면 `status` `SUCCESS`, `count` 0, `note`를 싣는다 [12].
조회 자체가 실패하면 `status` `FAILED`와 `error`를 싣는다 [12].
그래서 `evidence_v1`에서 사건이 없는 조회는 `SUCCESS`, 실패한 조회는 `DEGRADED`가 되었다 [11].
`get_file_metadata`는 파일이 없으면 오류가 아니라 `exists` 거짓을 싣는다 [13].
`verify_sha256_manifest`는 항목마다 `MATCH`·`MISMATCH`·`MISSING`·`INVALID`·`SKIPPED`를 나눠 싣는다 [14].
`inventory_archive_members`는 유형마다 이름이 맞는 항목이 없으면 `collection_status`를 `NOT_OBSERVED`로 둔다 [15].
ZIP 항목 도구는 `artifact_coverage`의 `parse_status`를 `PARSED`·`PARSED_WITH_LIMITATIONS`·`FAILED`로 나눈다 [15].
`shape_summary`는 IR_Collect가 사실 0건을 적었으면 `EMPTY_ANALYSIS`, 건수 표가 비었는데 사실이 0건이 아니면 `UNAVAILABLE`을 `coverage_reporting`에 싣는다 [16].
두 형식 모두 이 필드를 `data`나 결과에 그대로 둔다 [5].

**한계.** `list_loaded_dlls`는 프로세스를 찾지 못한 경우를 조회 실패와 같은 `error` 결과로 돌려준다 [17].
IR_Collect는 Guided Hunt가 꺼져 있거나 평가할 사실이 없으면 `notes`에 그 사실을 적고 일치 목록을 비운다 [18].
`shape_summary`는 `notes`를 옮기지 않으므로 이 경우와 일치가 없는 경우의 응답이 같다 [16][19].
`build_process_tree_snapshot`이 받는 `list_running_processes`의 결과는 `evidence_v1` 응답이라서 최상위에 `error`와 `processes` 키가 없다 [20].
그래서 프로세스 조회가 실패해도 오류 분기가 적용되지 않고 `process_count` 0을 정상 결과로 돌려준다 [20][21].

### R03.03 입력별 성공·실패·생략 목록

**구현.** 이 방식은 `local-forensic`의 `collect_ir_event_bundle`, `artifact-forensic`의 `verify_sha256_manifest`에 적용된다 [22][14].
`collect_ir_event_bundle`은 채널마다 조회 조건과 `result`를 `queries`에 싣는다 [22].
`verify_sha256_manifest`는 목록 항목마다 줄 번호, 대상, `status`, 실패 사유 `error`를 싣는다 [14].

`check_file_signatures_batch`는 경로마다 `requested_path`와 Sigcheck 결과 `result`를 싣지만 `result`는 Sigcheck 출력이나 오류 문장이라서 성공 여부를 나누는 필드가 없다 [23].
`evidence_v1`은 실패한 경로 행과 채널 조회의 수를 세어 `PARTIAL_RESULT_FAILURE`·`PARTIAL_QUERY_FAILURE` 항목을 `errors`에 더한다 [2].
없는 경로 두 개를 준 `check_file_signatures_batch`의 `errors`에는 `2 bounded result row(s) failed.`가 실렸다 [11].
`evidence_v1`은 `error:`나 `file not found:`로 시작하는 행만 실패로 센다 [4].
그래서 Sigcheck를 시작하지 못한 행의 `Error executing …` 문장은 실패로 세지 않는다 [9][4].
`errors` 항목은 실패한 행의 수만 적고 어느 경로인지는 적지 않는다 [2].

### R03.04 시간 초과·부분 완료 표시

**구현.** 이 방식은 `artifact-forensic`의 EZ Tools 도구와 해시 계산 상한이 있는 `verify_sha256_manifest`·`inventory_evidence_path`에 적용된다 [24][14][25].
EZ Tools 도구는 실행이 시간 제한을 넘거나 출력 상한에 닿으면 실행을 멈추고 그때까지 쓴 CSV를 읽는다 [24].
그 경우 `warnings`에 시간 제한이나 출력 상한 문구를 더하고 `status`를 `DEGRADED`로 둔다 [24].
`verify_sha256_manifest`는 해시 계산 상한 2 GiB를 넘는 항목을 `SKIPPED`로 둔다 [14].
`inventory_evidence_path`는 해시 상한 512 MiB에 닿으면 남은 파일의 `sha256`을 `null`로 두고 경고를 더한다 [25].
`evidence_v1`은 이 경고를 `limitations`에 옮기고 `status`를 `DEGRADED`로 둔다 [2][11].

**한계.** `DEGRADED`는 시간 초과, 목록 잘림, 원본 변경을 모두 가리키므로 원인은 `warnings` 문장으로만 알 수 있다 [24].
Hayabusa·capa·YARA 도구는 시간 제한을 넘으면 결과 없이 `error`만 돌려준다 [26].
`ir-collect`는 IR_Collect가 시간 제한을 넘어도 결과 JSON이 있으면 정상 결과로 정리하고 `provenance.exit_code`에 -1만 남긴다 [27].
IR_Collect가 0이 아닌 종료 코드로 끝나도 결과 JSON이 있으면 같은 방식으로 정상 결과가 되고 종료 코드는 `provenance.exit_code`에만 남는다 [27][28].
`local-forensic`은 시간 제한을 넘으면 `Error: … timed out` 문장이나 `error` 필드만 돌려준다 [9][29].
`collect_event_log_events`가 `max_events`에 닿아 읽기를 멈췄는지는 응답에 없다 [12].
