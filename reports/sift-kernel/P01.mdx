# P01 분석 방법 적합성 확인

### P01.01 이름·확장자 판별

**구현.** 증거 형식을 정하는 곳은 커널 도구 `mount_evidence` 하나다 [1].
`mount_evidence`는 받은 `image_path`에서 마지막 `.` 뒤의 글자를 소문자로 바꿔 확장자로 쓴다 [1].
확장자가 `raw`·`img`·`dmp`·`mem`·`vmem`·`lime`·`core`이고 경로에 `drive`·`disk`가 없으면 메모리 덤프 후보로 보고 P01.03의 내용 확인을 거친다 [1][2].
확장자가 `pcap`·`pcapng`·`cap`이면 내용을 보지 않고 네트워크 캡처로 정한다 [3].
그 밖의 확장자는 마운트 명령을 고르는 데 쓴다 [4].
`e01`·`s01`·`ex01`은 `ewfmount`, `vmdk`는 `qemu-nbd`, `aff4`는 `affuse`, 나머지는 `mount -o ro,loop`로 마운트한다 [4].
정한 종류는 조사 상태 `investigationState`의 `evidenceType`·`imageFormat`에 적고 응답의 `evidence_type`·`format`으로 돌려준다 [2][3][5].
분류 도구의 연산은 형식을 다시 판별하지 않고 조사 상태의 이미지 경로를 쓴다 [6].

**예외.** 서버를 시작 인자 `--evidence`로 띄우면 조사 상태의 이미지 경로가 처음부터 그 값이다 [6].
그 뒤 `mount_evidence`가 다른 이미지를 마운트 명령으로 마운트하면 이미지 경로가 비어 있지 않아 바꾸지 않는다 [5].
그때 분석 연산은 판별하고 마운트한 이미지가 아니라 `--evidence`로 준 이미지를 읽는다 [5][6].
`reset_investigation`도 조사 상태를 비우지 않으므로 초기화한 뒤 새 이미지를 마운트 명령으로 마운트하면 앞 이미지 경로가 남는다 [7].
마운트 명령이 실패해 `fls` 직접 접근으로 넘어가는 경로와 메모리·캡처 분기만 이미지 경로를 새 값으로 바꾼다 [2][3][8].

### P01.02 메타데이터 조회

**구현.** 디스크 이미지의 마운트 명령이 실패하면 `mount_evidence`는 `fls -o 0`으로 이미지를 직접 읽을 수 있는지 본다 [8].
읽히면 `mmls`가 낸 파티션 표에서 `NTFS`·`Win95`·`FAT`가 든 줄을 찾아 그 시작 섹터를 분석 연산의 파티션 오프셋으로 쓴다 [8].
맞는 줄이 없으면 오프셋은 0이다 [8].
이어서 그 오프셋으로 `fsstat`을 돌린다 [9].
출력에 `NTFS`·`FAT`가 있으면 `disk-windows`, `ext2`~`ext4`·`xfs`·`btrfs`가 있으면 `disk-linux`, `HFS`·`APFS`가 있으면 `disk-macos`로 정한다 [9].
어느 것에도 맞지 않으면 `disk-windows`로 두고 `filesystemType`을 `unknown`으로 적는다 [9].
정한 종류와 파일 시스템은 성공 응답의 `evidence_type`·`filesystem_type`에 싣고 방법론 상태 기계에 넘긴다 [5].
분류 도구의 `list_partitions`·`get_filesystem_info` 연산도 `mmls`·`fsstat`을 돌리지만 그 결과로 조사 상태의 오프셋이나 종류를 바꾸지 않는다 [10].

**예외.** 이 조회는 마운트 명령이 실패한 경로에만 있다 [8].
마운트 명령이 성공하면 `mmls`·`fsstat`을 돌리지 않아 오프셋은 0이고 `evidenceType`은 앞의 값으로 남는다 [5][8].
처음 마운트라면 그 값은 `unknown`이고 방법론 상태 기계는 Windows 기준 목록을 쓰며 Linux 연산이 요구하는 `linux_accessible` 능력도 생기지 않는다 [5][9][11].
`fsstat`이 실패해도 성공 응답을 돌려주고 응답의 `evidence_type`이 앞의 값으로 남을 뿐 판별하지 못했다는 항목은 없다 [9][5].
주석은 가장 큰 NTFS 파티션을 찾는다고 적지만 코드는 표에서 처음 맞는 줄을 쓰고 Linux 파티션은 찾지 않는다 [8].
그래서 파티션이 여러 개인 Linux 이미지는 오프셋 0으로 `fsstat`을 돌리고 거기서 파일 시스템을 찾지 못하면 위와 같이 판별 없이 진행한다 [8][9].

### P01.03 내용·헤더 검사

**구현.** 메모리 덤프 후보는 Volatility 3의 `windows.info.Info` 플러그인으로 열어 본다 [2].
종료 코드가 0이거나 표준 출력에 `Kernel`이 있으면 메모리 덤프로 정하고 `memory_profiled` 능력을 준다 [2].
이 확인의 출력은 `mount_evidence` 호출 기록 항목과 원래 출력 파일로 남는다 [2].
조건을 채우지 못하면 디스크 이미지로 보고 P01.01의 마운트 경로로 넘어간다 [2][4].
확인에 `windows.info.Info`만 쓰므로 Windows 메모리 덤프만 메모리로 정한다 [2].

**예외.** 경로 어딘가에 `drive`나 `disk`라는 글자가 있으면 이 확인을 건너뛰고 디스크 이미지로 다룬다 [1].
이 비교는 대소문자를 구별해 `Disk`가 든 경로는 확인을 받는다 [1].
`vol`이 없거나 실행이 실패해도 디스크 이미지 경로로 넘어가고 응답은 메모리 확인을 하지 못했다는 사실을 알리지 않는다 [2][4].

### P01.04 방법과 형식·OS 대조

**구현.** 판별 결과는 분류 연산의 실행 조건과 방법론 기준 목록에 쓰인다.
`mount_evidence`는 메모리 덤프면 `memory_profiled`, 네트워크 캡처면 `network_capture_loaded`, `fsstat`이 Linux 파일 시스템을 보면 `linux_accessible`을 능력 집합에 더한다 [2][3][9].
메모리 연산은 `memory_profiled`나 그것으로 생기는 `memory_accessible`을, 네트워크 연산은 `network_capture_loaded`를, Linux 연산은 `linux_accessible`을 요구한다 [12].
서버는 분류 연산을 실행하기 전에 요구 능력을 가진 능력과 대조하고 모자라면 실행하지 않고 `CAPABILITY_BLOCKED`를 돌려준다 [13].
그래서 Linux 연산은 `fsstat`이 Linux 파일 시스템으로 판별한 이미지에서만 돈다 [9][12][13].
방법론 상태 기계는 넘겨받은 증거 종류로 기준 도구 목록을 고른다 [11].
`disk-linux`면 Linux 목록, `memory`면 메모리 목록, `pcap`이면 네트워크 목록, 그 밖은 Windows 목록이다 [11].

레지스트리·이벤트 로그·실행 흔적 연산은 OS를 요구하지 않고 파일 시스템이나 하이브 능력만 요구해 Linux·macOS 이미지에서도 대조를 지난다 [14].
`list_registry_hives`는 하이브를 찾지 못해도 성공으로 끝나 `registry_accessible`을 만든다 [14].
메모리 연산은 모두 Volatility 3의 `windows.` 플러그인을 고정해 부른다 [15].
그 가운데 `dump_process`를 뺀 10개는 `--output json`을 붙이는데 Volatility 3 2.28.0은 이를 출력 폴더 지정으로 읽는다 [15][16].
그래서 출력 폴더 안에 `json` 폴더가 없으면 이 연산들은 플러그인을 실행하기 전에 실패하고 이 사실은 I02에도 적었다 [16].

**예외.** `load_network_capture`는 앞선 파일 목록 출력에 캡처 파일 이름이 없어도 성공으로 끝나 `network_capture_loaded`를 만든다 [17].
그 뒤에는 디스크 이미지로 판별한 증거에서도 네트워크 연산이 능력 대조를 지난다 [12][13][17].
메모리 덤프와 네트워크 캡처 분기는 판별한 종류를 방법론 상태 기계에 넘기지 않고 돌아간다 [2][3][5].
그래서 메모리 덤프와 네트워크 캡처에도 Windows 기준 목록을 쓰고 메모리·네트워크 기준 목록은 쓰이지 않는다 [11].
이 목록이 권하는 작업은 P02에서 본다.
