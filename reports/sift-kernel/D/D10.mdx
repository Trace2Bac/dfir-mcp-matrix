# D10 산출물 식별·재생성 처리

### D10.01 실행 ID별 위치

**구현.** 이 방식은 원래 출력 파일과 비동기 출력 파일에 적용된다 [1][2].
원래 출력 파일 이름은 호출마다 새로 만든 호출 기록 항목 ID다 [3][1].
비동기 연산의 출력 파일 이름은 작업을 시작할 때 만든 job ID이고 그 ID는 밀리초 시각과 난수 6자로 만든다 [2].
호출 기록 항목에는 job ID가 들어가지 않는다 [2].

### D10.02 입력·작업별 고유 이름

**구현.** 이 방식은 보고서, 이미지에서 꺼낸 파일, Zimmerman 도구가 쓰는 CSV에 적용된다 [4][5][6].
보고서 이름에는 밀리초까지의 생성 시각이 들어가 보고서를 다시 만들어도 앞 파일과 이름이 다르다 [4].
꺼낸 파일 이름에는 inode와 이미지 안 파일 이름이 들어가 다른 파일을 꺼내면 이름이 다르다 [5].
이 이름은 입력마다 같은 값이라 같은 파일을 다시 꺼내면 같은 경로가 되고 서버는 앞 파일을 덮어쓴다 [5][7].
Zimmerman 도구를 부르는 연산(`parse_prefetch`·`parse_amcache` 등)은 출력 폴더를 CSV 출력 위치로 넘긴다 [8].
Zimmerman 도구는 실행 시각을 초 단위로 넣은 이름으로 새 CSV를 쓰므로 다시 실행해도 앞 실행의 CSV가 남는다 [6].

**한계.** 꺼낸 파일 이름에는 이미지 경로와 파티션 오프셋이 들어가지 않는다 [5].
다른 이미지나 파티션에서 같은 inode와 이름의 파일을 꺼내면 같은 경로가 되고 서버는 그 파일을 있는지 보지 않고 다시 쓴다 [5][7].
보고서도 같은 이름이 있는지 보지 않고 쓰므로 같은 밀리초에 같은 형식으로 만든 보고서는 앞 파일을 덮어쓴다 [4].
Zimmerman 도구는 같은 초에 다시 실행하면 같은 이름의 CSV를 덮어쓴다 [6].
SBECmd는 소스가 공개되지 않아 이 동작을 확인하지 못했다.

### D10.03 버전·이력 보존

**구현.** 이 방식은 `dump_process`가 부르는 Volatility의 덤프 파일 쓰기에 적용된다 [9][10].
`dump_process`는 출력 위치 인자 없이 Volatility를 실행하고 실행기의 작업 폴더가 출력 폴더라서 덤프 파일이 그 폴더에 생긴다 [9].
Volatility 3 2.28.0의 파일 핸들러는 같은 이름의 파일이 있으면 이름 뒤에 `-1`·`-2`를 붙여 새로 쓴다 [10].
그래서 `dump_process`를 다시 실행하면 앞 실행의 덤프 파일이 남고 새 덤프 파일은 이름 뒤의 번호로 구분된다 [9][10].

### D10.04 덮어쓰기 선택·충돌 감지

**구현.** 이 방식은 서버 코드가 아니라 `carve_files`가 부르는 `foremost`와 `analyze_unallocated`가 부르는 `bulk_extractor`에 있다 [11][12][13].
두 연산은 실행마다 같은 폴더 `carved/`·`be_out/`에 결과를 쓴다 [11].
`foremost`는 `carved/`가 비어 있지 않으면 오류를 내고 실행을 끝낸다 [12].
그래서 `carve_files`를 다시 실행하면 앞 결과가 그대로 남고 새 결과는 만들어지지 않는다 [11][12].
`foremost`는 한 실행 안에서 같은 이름이 나오면 앞 파일을 두고 새 파일 이름에 번호를 붙인다 [14].
`bulk_extractor`는 `be_out/report.xml`이 있으면 재시작으로 보고 앞 실행이 기록한 페이지를 건너뛰며 기존 결과 파일 뒤에 이어 쓴다 [13].
`parse_srum`이 부르는 `esedbexport`는 `-t`로 받은 이름 뒤에 `.export`를 붙여 `srum_export/.export` 폴더에 쓰고 그 폴더가 이미 있으면 오류로 끝난다 [15].
다만 서버는 `srum_export/`를 만들지 않고 `esedbexport`는 마지막 폴더 하나만 만들므로 `srum_export/`가 없으면 첫 실행부터 실패한다 [8][15].

서버 코드는 고정 경로에 앞 결과가 있는지 보지 않고 외부 도구를 실행하며 앞 결과를 돌려주거나 덮어쓸지 고르게 하는 인자도 없다 [11][8].
`recover_deleted`와 `generate_timeline`은 앞 결과를 알리지 않고 덮어쓰거나 이어 쓴다 [16][17].
`tsk_recover`는 `recovered/` 아래에 없는 폴더만 만들고 같은 경로의 파일은 `w+`로 열어 덮어쓴다 [16].
그래서 다시 실행하거나 한 실행 안에서 같은 폴더에 같은 이름이 나오면 나중 파일만 남고 앞 실행에서만 나온 파일은 그대로 남는다 [16].
`log2timeline`은 `timeline.plaso`가 이미 있으면 경고만 남기고 그 저장 파일을 쓰기 모드로 열어 기존 이벤트 뒤에 새 이벤트를 덧붙인다 [17].
`psort`는 분석 플러그인 없이 부르면 저장 파일을 읽기만 하므로 `filter_timeline`·`get_timeline_context`는 앞 실행과 새 실행의 이벤트를 함께 읽는다 [17].
regipy 연산이 쓰는 `regipy_out.json`은 서버가 읽은 뒤 바로 지우므로 다음 실행 때 앞 결과로 남지 않는다 [18].

**한계.** `carve_files`는 비동기 연산이라 `foremost`의 거부는 작업 상태 `failed`로만 남는다 [19][2].
실행기는 외부 도구가 0이 아닌 코드로 끝나면 표준 출력을 버리고 종료 코드만 적은 오류 문장을 돌려준다 [20].
`foremost`는 출력 폴더가 비어 있지 않다는 문장을 표준 출력에 쓰므로 작업 오류에는 거부한 이유가 남지 않는다 [12][20].
