# D01 파생물 보관

### D01.01 파생물 파일 보관

**구현.** 이 방식은 외부 도구를 실행하는 분류 도구 연산, `mount_evidence`의 메모리 분기, 이미지에서 파일을 꺼내는 경로, 보고서 생성에 적용된다 [1][2][3][4][5].
이 경로들은 분석 도구의 원래 출력 텍스트와, 분석 도구나 서버 코드가 만든 파일을 출력 폴더(`--output`, 주지 않으면 현재 작업 폴더의 `sift-output`) 아래에 남긴다 [6].

분류 도구 연산과 `mount_evidence`의 메모리 분기는 호출마다 원래 출력을 출력 폴더의 `raw` 폴더에 남긴다 [1][2][6].
공통 실행 경로는 호출 기록 항목을 만든 뒤 그 항목 ID로 원래 출력 문자열을 `raw/<항목 ID>.json`에 쓴다 [2][7].
파일 이름의 확장자는 `.json`이지만 내용은 도구 출력 문자열 그대로다 [7].
저장소는 임시 파일에 쓴 뒤 이름을 바꾸고 같은 이름의 파일이 이미 있으면 쓰지 않는다 [7].
외부 도구 연산은 표준 출력을, `mount_evidence`의 메모리 분기는 Volatility `windows.info.Info`의 표준 출력을 원래 출력으로 삼는다 [8][9].
분석 도구가 낸 원래 출력 텍스트는 서버 파서를 거치기 전의 문자열 그대로 남는다 [8][2].
파서를 거친 결과는 응답에만 실리고 파일로 남지 않는다 [2].
외부 실행이 실패하면 빈 문자열을 남기고 오류 문장은 호출 기록 항목의 `errorMessage`에만 들어간다 [8][2].
regipy 연산은 표준 출력 대신 regipy가 쓴 결과 파일 `regipy_out.json`의 내용을 원래 출력으로 삼고 그 결과 파일은 읽은 뒤 지운다 [8].

서버 안 처리기 연산과 `mount_evidence`의 pcap·디스크 분기가 같은 저장소에 남기는 원래 출력은 서버 코드가 만든 문자열이거나 마운트 명령의 출력이라 이 상세의 근거가 아니다 [10][1].
처리기 연산은 처리기가 돌려준 JSON 문자열을, pcap 분기는 서버 문장 `PCAP loaded: <경로>`를 남긴다 [10][1].
디스크 분기는 마운트 명령의 표준 출력·표준 오류를 남긴다 [11].
마운트가 실패했는데 `fls`로 이미지가 읽히면 `fls` 출력 앞 2,000자를 붙인 서버 문장을 남긴다 [11].

분석 도구나 서버 코드가 만든 파일은 서버가 출력 폴더 아래 쓰기 위치를 넣어 주는 외부 도구 연산, 이미지에서 파일을 꺼내는 경로, 보고서 생성이 남긴다 [3][4][5].
`recover_deleted`(`tsk_recover`)는 `recovered/`, `carve_files`(`foremost`)는 `carved/`, `analyze_unallocated`(`bulk_extractor`)는 `be_out/`에 결과 파일을 쓴다 [3].
`generate_timeline`(`log2timeline`)은 Plaso 저장 파일 `timeline.plaso`를 쓰고 `filter_timeline`·`get_timeline_context`가 그 파일을 읽는다 [3].
`parse_srum`은 `srum_export/`를, Zimmerman 도구를 부르는 연산(`parse_prefetch`·`parse_amcache` 등)은 출력 폴더를 CSV 출력 위치로 받는다 [12].
서버는 Zimmerman 도구의 CSV를 읽지 않고 그 도구의 표준 출력만 원래 출력으로 남기므로 분석 결과는 CSV 파일에만 있다 [12][8].
`dump_process`는 출력 위치 인자 없이 Volatility를 실행하고 실행기의 작업 폴더가 출력 폴더라서 덤프 파일이 그 폴더에 생긴다 [13].
이벤트 로그·레지스트리 연산은 이미지 안 경로를 받으면 `icat`으로 파일을 꺼내 출력 폴더의 `extracted_<inode>_<이름>`에 쓰고 그 파일을 분석한다 [4].
`generate_report`는 마크다운·HTML·JSON 보고서를 출력 폴더에 쓴다 [5].
서버는 이 파일들을 호출 뒤에 지우지 않는다.
`extract_files_from_pcap`은 출력 폴더가 아니라 조사 상태의 증거 경로 뒤 `pcap_export/`(증거 경로가 비면 `/tmp/pcap_export/`)를 `tshark` 내보내기 위치로 넘긴다 [14].

호출 기록 행에는 파서를 거친 결과의 해시와 원래 출력 파일 경로만 들어가므로 D01.03·D01.04에는 연결하지 않는다 [2][15].
SQLite 파일에 `findings` 테이블과 저장 함수 `saveFinding`이 정의돼 있지만 서버 코드는 그 함수를 부르지 않는다 [16].

비동기로 실행되는 `generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`는 `raw` 폴더를 쓰지 않는다 [17].
이 네 연산은 실행이 끝나면 표준 출력을 출력 폴더의 `async-<job ID>.txt`에 쓰고 앞 2,000자와 그 파일 경로를 서버 메모리의 job 목록에 둔다 [17].

보관 기간·용량·대상을 정하는 설정이나 코드는 없어 D01.05에는 연결하지 않는다.
`--fresh`로 서버를 실행하면 출력 폴더 전체를 지운다 [18].

**한계.** 원래 출력 파일에 도구 출력 전체가 남지 않는 연산이 있다.
성공한 외부 실행은 표준 출력만 남기고 표준 오류는 버린다 [8].
`search_filename`·재귀 `list_directory`·이벤트 로그 연산은 서버가 정한 줄 상한과 시간 제한을 받고 그 상한에서 끊긴 출력도 성공으로 처리돼 끊긴 부분까지만 남는다 [19][8].
`search_filename`은 `fls` 출력을 `pattern` 정규식으로 거른 뒤의 줄만 원래 출력으로 남긴다 [20].

실행마다 같은 경로에 쓰는 파일 파생물은 다시 실행할 때 앞 실행의 파일이 남는지 서버가 정하지 않는다 [3][12].
`timeline.plaso`·`recovered/`·`carved/`·`be_out/`·`srum_export/`는 실행마다 같은 경로이고 앞 결과가 있을 때의 동작은 외부 도구마다 다르다 [3][12].
`log2timeline`은 `timeline.plaso`가 이미 있으면 경고만 남기고 그 저장 파일을 쓰기 모드로 열어 기존 이벤트 뒤에 새 이벤트를 덧붙인다 [21].
`psort`는 분석 플러그인 없이 부르면 저장 파일을 읽기만 하므로 `filter_timeline`·`get_timeline_context`는 앞 실행과 새 실행의 이벤트를 함께 읽는다 [21].
`tsk_recover`는 `recovered/` 아래에 없는 폴더만 만들고 같은 이름의 파일은 `w+`로 열어 덮어쓰며 앞 실행에서만 나온 파일은 그대로 남는다 [22].
`foremost`는 `carved/`가 비어 있지 않으면 오류를 내고 실행을 끝낸다 [23].
`bulk_extractor`는 `be_out/report.xml`이 있으면 재시작으로 보고 앞 실행이 기록한 페이지를 건너뛰며 기존 결과 파일 뒤에 이어 쓴다 [24].
`esedbexport`는 `-t`로 받은 이름 뒤에 `.export`를 붙여 `srum_export/.export` 폴더에 쓰고 그 폴더가 이미 있으면 오류로 끝난다 [25].
서버는 `srum_export/`를 만들지 않고 `esedbexport`는 마지막 폴더 하나만 만들므로 `srum_export/`가 없으면 첫 실행부터 실패한다 [12][25].
같은 inode와 이름의 파일을 다시 꺼내면 `extracted_<inode>_<이름>`을 새로 열어 앞 파일을 덮어쓴다 [4][26].
Zimmerman 도구는 `--csv` 폴더 안에 실행 시각을 초 단위로 넣은 새 CSV를 써서 앞 실행의 CSV는 남고 같은 초에 다시 실행할 때만 같은 이름을 덮어쓴다 [12][27].
SBECmd는 소스가 공개되지 않아 이 동작을 확인하지 못했다.
`dump_process`의 덤프 파일은 같은 이름이 있으면 `-1`·`-2`를 붙여 새로 쓰므로 다시 실행할 때마다 출력 폴더에 쌓인다 [13][28].
