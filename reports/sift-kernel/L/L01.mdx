# L01 기록 방식

### L01.07 공통 요청 처리 단계에서 기록

**구현.** 이 방식은 분류 도구 14개가 `operation`으로 고르는 연산 전부와 커널 도구 `verify_integrity`에 적용된다 [1][2].
호출 처리기는 분류 도구 호출을 `operation`이 가리키는 내부 연산 이름으로 바꾼 뒤 같은 처리기 안의 능력 검사와 실행 단계로 넘긴다 [1].
실행 단계는 외부 도구 대응이 있으면 외부 도구를 실행하고 없으면 서버 안 처리기를 부르며 둘 다 없으면 실패 결과를 만든다 [3].
그 뒤 한 곳에서 호출 기록 항목을 만들어 쓰고 응답에 그 항목의 `ledger_entry_id`를 싣는다 [4].
성공과 실패를 가리지 않고 실행이 끝난 호출은 모두 이 자리를 지난다 [4].
호출 기록은 출력 폴더의 SQLite 파일 `ledger.db`이고 서버를 만들 때 연다 [5].

오래 걸리는 연산 4개(`generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`)는 같은 실행 단계에서 백그라운드 실행을 시작한 직후 항목을 쓰고 응답을 돌려준다 [6].
그 실행이 끝난 뒤에는 항목을 더하지 않는다 [6].
`verify_integrity`는 커널 도구지만 앞에서 돌아가는 자기 분기가 없고 외부 도구 대응이 있어 이 단계를 지난다 [2].
외부 명령을 실행하는 `ProcessExecutor`는 호출 기록을 넘겨받지 않아 실행마다 항목을 쓰지 않는다 [5].
그래서 한 호출이 경로를 찾으려고 외부 명령을 여러 번 실행해도 항목은 하나이고 항목에 무엇이 담기는지는 L02에서 본다.

**한계.** 커널 도구 27개 가운데 `mount_evidence`와 `verify_integrity`를 뺀 25개는 실행 단계 앞의 자기 분기에서 응답을 돌려주고 기록하지 않는다 [7].
발견사항을 등록하는 `register_finding`, 보고서를 쓰는 `generate_report`, 호출 기록을 지우는 `reset_investigation`, 체인을 검사하는 `verify_chain`, 기록을 내보내는 `export_audit_log`가 여기에 포함된다 [7][8].
서버가 모델에게 주는 조사 절차 안내는 모든 도구 응답에 `ledger_entry_id`가 붙는다고 적지만 이 25개 도구의 응답에는 없다 [9][8].
저장소 루트의 `CLAUDE.md`도 모든 도구 호출이 호출 기록 항목을 자동으로 남긴다고 적는다 [10].

실행 단계에 닿기 전에 돌아가는 반환 지점도 기록을 남기지 않는다.
분류 도구 호출에 `operation`이 없거나 그 분류에 없는 연산이면 `MISSING_OPERATION`·`INVALID_OPERATION` 오류를 돌려준다 [1].
연산의 선행 능력이 없거나 능력 그래프에 없는 이름이면 `CAPABILITY_BLOCKED` 오류를 돌려준다 [11].

### L01.08 도구별 기록 호출

**구현.** 이 방식은 커널 도구 `mount_evidence`에 적용된다 [12].
`mount_evidence`는 공통 실행 단계 앞의 자기 분기에서 처리하고 메모리 덤프, 패킷 캡처, 디스크 이미지 세 경우마다 본문에서 항목을 만들어 호출 기록에 넣는다 [12].
메모리 덤프로 보이는 파일을 `vol`이 확인하지 못하면 디스크 이미지로 보고 그 경우의 항목을 쓴다 [12].
디스크 이미지 경우는 마운트가 실패해도 항목을 쓴 뒤 `MOUNT_FAILED` 오류를 돌려준다 [13].

**한계.** `image_path`가 없으면 항목을 쓰기 전에 오류를 돌려준다 [14].
