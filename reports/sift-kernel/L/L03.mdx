# L03 기록 실패 처리

### L03.03 알림 없이 계속

**구현.** 이 방식은 호출 기록에 항목을 쓰는 다섯 곳 모두에 적용된다.
다섯 곳은 공통 실행 단계 끝, 백그라운드 연산을 시작한 직후, `mount_evidence`의 세 경우다 [1].
백그라운드 연산을 뺀 네 곳은 도구 실행이나 마운트를 마친 뒤 항목을 쓴다 [1].

항목을 쓰는 `SqliteLedgerStore.append`는 SQL 문을 준비하고 실행하는 동안 난 예외를 처리해 `LEDGER_ERROR` 오류 결과로 돌려준다 [2].
SQL 문 실행 함수 `run`은 better-sqlite3 11.10.0에서 실행이 실패하면 예외를 던진다 [3].
그래서 쓰기 실패는 예외가 아니라 `append`의 반환값으로만 나온다 [2][3].
다섯 곳 모두 이 반환값을 받지 않는다 [1].
쓰기가 실패해도 도구 결과를 그대로 돌려주고 응답에도 서버 로그에도 실패를 남기지 않는다 [1][4].

응답에는 쓰지 못한 항목의 `ledger_entry_id`가 그대로 실린다 [4].
그 ID를 근거로 `register_finding`을 부르면 호출 기록에 없는 ID라는 오류로 거부된다 [5].
항목 앞에 저장하는 원래 출력 파일도 저장이 실패하면 항목의 `rawOutputPath`를 비워 두고 알리지 않는다 [4][6].

**한계.** 항목을 쓰기 전에 앞 항목의 해시를 구하려고 `getLastEntry`로 마지막 항목을 읽는다 [4][7].
`append`의 예외 처리는 이 읽기를 감싸지 않으므로 better-sqlite3가 던진 예외가 호출 처리기 밖으로 올라간다 [7][3].
MCP SDK 1.29.0은 처리기가 던진 예외를 JSON-RPC 오류 응답으로 바꾼다 [8].
그래서 DB를 읽지 못하는 실패에서는 도구를 실행한 뒤 결과를 돌려주지 않고 호출이 오류로 끝난다 [4][8].
