# L02 기록 구성

### L02.02 서버가 변환한 연산·인자 기록

**구현.** 호출 기록 항목은 도구 이름 `tool`과 인자 객체 `params`를 따로 가진다 [1].
SQLite 저장소는 `params`를 JSON 문자열 열에 넣고 읽을 때 객체로 되돌린다 [2].
외부 도구와 서버 안 처리기를 부르는 공통 경로는 실행이 끝난 뒤 이 항목을 만든다 [3].

기록하는 도구 이름과 인자는 서버가 바꾼 뒤의 값이다.
서버는 분류 도구 호출의 도구 이름을 `operation`이 가리키는 내부 연산 이름으로 바꾸고 `operation`을 인자에서 뺀다 [4].
레지스트리 연산에 경로가 없으면 기본 하이브 경로를 넣는다 [5].
이미지 안 경로를 받은 이벤트 로그·레지스트리 연산은 파일을 출력 폴더로 꺼낸 뒤 `path`를 꺼낸 파일의 경로로 바꾼다 [5].
`list_directory`·`search_filename`은 `path`로 찾은 inode를 `inode`에 넣고 `path`를 지운다 [6].
이 inode는 경로 일부만 찾았을 때 마지막으로 찾은 항목의 것이어서 기록된 `inode`와 꺼낸 파일 경로만으로는 요청 경로 전체를 찾았는지 알 수 없다 [5][6].
호출 기록에는 이렇게 바뀐 값이 남고 서버는 이 값으로 외부 도구의 인자 배열을 만든다 [3][7].
서버는 매핑이 읽지 않는 인자를 `toolParams`에서 빼지 않으므로 그런 인자도 항목의 `params`에 남는다 [3][8].
예를 들어 `search_events`의 매핑은 `path`만 읽지만 모델이 함께 준 `event_id`·`time_start`·`time_end`도 그 호출 항목의 `params`에 들어간다 [3][8].

모델이 보낸 원래 값은 바뀐 뒤 남지 않는다 [6].
외부 도구에 넘긴 인자 배열과 그때 더하는 증거 경로·파티션 오프셋·출력 폴더도 항목에 없다 [1][7].
경로를 따라가려고 서버가 부른 `fls`·`icat`은 호출 기록에 항목이 남지 않는다 [5][6].

**한계.** `mount_evidence`는 바꾼 인자 대신 `image_path`와 형식만 남긴다 [9].

### L02.05 결과 상태·실행 시점 기록

**구현.** 서버의 호출 기록 항목은 `success`·`timestamp`·`durationMs`와 실패 때의 `errorMessage`를 담는다 [1][3].
공통 실행 경로는 처리가 끝난 뒤 항목을 남기므로 완료 상태와 그 시점의 기록이다 [3].
비동기 경로는 접수 직후 `success: true`·`durationMs: 0`으로 기록하며 응답은 작업이 시작되었음을 알린다 [10].
그 기록을 실행 완료의 성공으로 읽어서는 안 된다.

**한계.** 비동기 작업의 접수 항목에는 접수·완료를 가르는 단계 필드가 없다 [10].
완료나 실패가 나도 같은 항목의 상태를 고치거나 최종 항목을 이어 쓰지 않는다 [10].
최종 상태는 메모리의 작업 표에만 바뀌므로 저장한 `success: true`만으로 최종 결과를 판별할 수 없다 [10].

### L02.06 결과 참조·요약값 기록

**구현.** 이 방식은 공통 실행 경로가 남기는 항목에 적용된다 [3][11].
`outputHash`는 파싱한 결과를 JSON 문자열로 바꿔 계산한 해시이며 원출력 파일의 바이트 해시가 아니다 [3].
원출력 저장을 시도한 뒤 저장에 성공하면 그 경로를 `rawOutputPath`로 항목에 넣는다 [11].
비동기 접수 항목은 `outputHash`·`rawOutputPath`가 빈 문자열이고 완료 출력 파일은 작업 표에만 연결된다 [10].
이 경로는 결과 참조를 기록하는 공통 실행 경로와 구별한다.
