# D04 출력 경로 제한

### D04.01 서버가 출력 위치 결정

**구현.** 이 방식은 파일을 만드는 외부 도구 연산, 이미지에서 꺼낸 파일, 원래 출력 파일, 비동기 출력 파일, 보고서에 걸린다 [1][2][3].
서버는 출력 폴더(`--output`) 아래 고정 경로를 외부 도구의 쓰기 위치로 넣는다 [1][4].
`recover_deleted`는 `recovered/`, `carve_files`는 `carved/`, `analyze_unallocated`는 `be_out/`, `generate_timeline`은 `timeline.plaso`, regipy 연산은 `regipy_out.json`, `parse_srum`은 `srum_export/`를 받는다 [1][4].
Zimmerman 도구 연산은 출력 폴더 자체를 CSV 출력 위치로 받는다 [4].
입력 schema는 `recover_deleted`·`analyze_unallocated`의 `output_dir`과 `extract_file`의 `output_name`을 내놓지만 외부 도구 인자를 만드는 함수는 이 값을 쓰지 않는다 [5][1].
`extract_file`은 `icat`의 표준 출력을 원래 출력으로 받을 뿐 파일을 따로 쓰지 않는다 [6].

이미지에서 꺼낸 파일은 출력 폴더의 `extracted_<inode>_<이름>`에 쓴다 [2].
이름 부분은 모델이 준 이미지 안 경로의 마지막 조각에서 영숫자와 `.`·`_`·`-` 밖의 문자를 `_`로 바꾼 값이다 [2].
보고서 이름은 증거 경로의 파일 이름에서 확장자를 떼고 영숫자와 `_`·`-` 밖의 문자를 `_`로 바꾼 뒤 생성 시각을 붙인 값이다 [7].
원래 출력 파일은 `raw/<호출 기록 항목 ID>.json`, 비동기 출력 파일은 `async-<job ID>.txt`이다 [3][8].
그래서 모델이 주는 값은 경로 구분자가 없는 이름 조각으로만 파일 이름에 들어간다 [2][7].

지우는 대상도 서버가 정한다.
regipy 연산이 읽은 뒤 지우는 파일은 고정 경로 `regipy_out.json`이다 [9].
`reset_investigation`은 인자 없이 호출 기록 행을 모두 지운다 [10].
`--fresh`는 운영자가 `--output`으로 준 폴더를 통째로 지운다 [11].
저장된 파생물을 ID로 골라 고치거나 지우는 도구는 없어 D04.03에는 연결하지 않는다.
모델이 준 목적지를 실제 경로로 풀어 허용 폴더와 대조하는 곳이 없어 D04.02에도 연결하지 않는다.

같은 연산을 다시 실행할 때 앞 결과와 구분하는 방식이 없는 연산도 있다.
`recovered/`·`carved/`·`be_out/`·`timeline.plaso`·`srum_export/`·`regipy_out.json`은 실행마다 같은 경로다 [1][4].
서버는 그 경로에 앞 결과가 있는지 보지 않고 외부 도구를 실행한다 [1][4].
앞 결과를 돌려주거나 덮어쓸지 고르게 하는 인자는 없어 D04.07·D04.08에는 연결하지 않는다.

**예외.** `extract_files_from_pcap`은 출력 폴더가 아니라 조사 상태의 증거 경로 뒤 `pcap_export/`를 `tshark`의 내보내기 위치로 넘긴다 [12].
그 증거 경로는 모델이 `mount_evidence`에 준 `image_path`이고 증거 경로가 비면 `/tmp/pcap_export/`가 된다 [12][13].
그 위치가 증거 폴더와 겹치는 문제는 E03에서 본다.
`dump_process`는 출력 위치 인자 없이 Volatility를 실행하고 덤프 파일은 실행기의 작업 폴더인 출력 폴더에 생긴다 [14].
`dump_process`의 덤프 파일, Zimmerman 도구의 CSV, `tsk_recover`·`foremost`·`bulk_extractor`·`esedbexport`가 폴더 안에 만드는 파일의 이름은 외부 도구가 정한다 [1][4][14].
그 이름이 앞 결과와 겹치는지, 이미지 안의 이름이 폴더 밖을 가리킬 수 있는지는 서버 코드로 확인하지 못했다.

### D04.04 이름·확장자·충돌 검사

**구현.** 이 방식은 원래 출력 저장소에 걸린다 [8].
저장소는 항목 ID가 영숫자·`_`·`-`로만 이뤄졌는지 보고 만든 경로가 `raw` 폴더 안인지 `normalize` 뒤 문자열 앞부분으로 본다 [8].
같은 이름의 파일이 이미 있으면 쓰지 않고 오류를 돌려준다 [8].
항목 ID는 서버가 `nanoid`로 만들므로 이 검사가 모델 입력을 거르는 일은 없다 [15].
꺼낸 파일과 보고서는 이름의 문자를 바꿀 뿐 거부하지 않고 같은 이름이 있는지도 보지 않는다 [2][7][16].

### D04.05 실행 ID별 위치

**구현.** 이 방식은 원래 출력 파일과 비동기 출력 파일에 걸린다 [3][8].
원래 출력 파일 이름은 호출마다 새로 만든 호출 기록 항목 ID다 [15][3].
비동기 연산의 출력 파일 이름은 실행을 띄울 때 만든 job ID이고 그 ID는 밀리초 시각과 난수 6자로 만든다 [8].
호출 기록 항목에는 job ID가 들어가지 않으며 이 연결은 D02에서 본다 [8].

### D04.06 유일 파일명·시각·번호

**구현.** 이 방식은 보고서와 이미지에서 꺼낸 파일에 걸린다 [7][2].
보고서 이름에는 밀리초까지의 생성 시각이 들어가 보고서를 다시 만들어도 앞 파일과 이름이 다르다 [7].
꺼낸 파일 이름에는 inode와 이미지 안 파일 이름이 들어가 다른 파일을 꺼내면 이름이 다르다 [2].

**예외.** 꺼낸 파일 이름에는 이미지 경로와 파티션 오프셋이 들어가지 않는다 [2].
다른 이미지나 파티션에서 같은 inode와 이름의 파일을 꺼내면 같은 경로가 되고 서버는 그 파일을 있는지 보지 않고 다시 쓴다 [2][16].
보고서도 같은 이름이 있는지 보지 않고 쓰므로 같은 밀리초에 같은 형식으로 만든 보고서는 앞 파일을 덮어쓴다 [7].
