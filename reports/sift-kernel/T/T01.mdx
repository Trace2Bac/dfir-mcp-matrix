# T01 입력 검증

### T01.01 인자 구조·값 검사

**구현.** 서버 코드가 인자를 검사하는 곳은 커널 도구 일부다.
`mount_evidence`는 `image_path`가 없으면 실행하지 않고 오류를 돌려준다 [1].
`register_finding`은 `type`·`description`이 없거나 `evidence`가 배열이 아니면 거부한다 [2].
이어서 `createFinding`이 빈 `evidence` 배열을 거부한다 [3].
`activate_workflow`는 받은 이름을 워크플로 정의 목록 `WORKFLOW_DEFINITIONS`와 대조하고 없으면 `success: false`를 돌려준다 [4].
분류 도구가 연산 이름을 고르는 검사는 T02.07에서 본다.

검사는 값이 있는지만 보고 자료형과 허용 값은 보지 않는다.
`register_finding`의 입력 schema는 `type`을 `enum`으로 적지만 서버 코드는 받은 값을 그 목록과 대조하지 않는다 [2].
서버가 쓰는 MCP SDK 1.29.0의 `Server`는 `tools/call` 요청의 모양만 검사하고 `arguments`를 도구의 입력 schema와 대조하지 않는다 [5].
`description`이 문자열이 아닌 값이어도 검사를 통과해 발견사항이 등록된다 [6].
그 뒤 `description`을 문자열로 다루다 예외가 나 호출은 오류로 끝나지만 등록한 발견사항은 남는다 [6].
`generate_report`는 `min_confidence`가 정한 값이 아니면 모든 신뢰 등급의 발견사항을 보고서에 넣는다 [7].
`search_filename`의 `pattern`이 정규식으로 만들어지지 않으면 거르지 않은 파일 목록 전체를 돌려준다 [8].
외부 도구를 쓰는 분류 연산은 모델 값을 문자열로 바꿔 인자 배열에 넣기만 하고 형식을 보지 않는다 [9].

### T01.07 고정 입력 경로 사용

**구현.** 디스크 이미지를 읽는 분류 연산은 모델에게 이미지 경로를 받지 않는다 [10].
서버는 시작 인자 `--evidence`나 앞선 `mount_evidence` 호출이 `investigationState.imagePath`에 적은 이미지를 인자 배열의 정해진 자리에 넣는다 [10][11].
Sleuth Kit 도구, `foremost`, `bulk_extractor`, `log2timeline`, `yara`, `ewfverify`를 부르는 연산이 여기에 든다 [11].
`list_directory`·`search_filename`의 `path`는 `fls`로 이미지 안의 inode로 풀어 inode로 실행한다 [12].
이벤트 로그·레지스트리 연산의 `path`는 이미지 안에서 찾아 `icat`으로 출력 폴더에 꺼낸 뒤 그 파일 경로로 바꾼다 [13].
레지스트리 연산 일부는 `path`가 없으면 이미지 안의 기본 하이브 경로를 쓴다 [13].
서버 안 처리기는 인자를 읽지 않고 앞선 호출이 저장한 원래 출력과 호출 기록 항목만 재료로 쓴다 [14].

이미지를 정하는 `mount_evidence`는 `image_path`를 허용 폴더와 대조하지 않고 그대로 마운트 명령에 넘긴다 [1][15].
경로를 마운트 지점 안으로 제한하는 `FsEvidenceStore.validatePath`가 있지만 서버는 그 객체를 만들기만 하고 함수를 부르지 않는다 [16].
모델이 준 경로를 호스트 경로로 그대로 외부 도구에 넘기는 연산도 있다 [17].
Volatility 연산은 `memory_path`를 주면 이미지 대신 그 경로를 읽는다 [17].
tshark 연산·`extract_strings`·`hash_and_lookup`·`parse_srum`·`parse_usnjrnl`·EZ Tools 연산은 `path`를 그대로 읽는다 [17].
`scan_yara`·`scan_memory_yara`의 룰 경로 `rules`도 그대로 넘긴다 [17].

**예외.** 이벤트 로그·레지스트리 연산은 `path`의 첫 조각부터 이미지 안에서 찾지 못하거나 꺼내기에 실패하면 받은 값을 바꾸지 않고 `evtx_dump`·`regipy-plugins-run`에 넘긴다 [13].
이때 그 값은 서버 호스트의 파일 경로로 읽힌다 [13].
경로 일부만 찾으면 마지막으로 찾은 항목을 꺼내 그 파일 경로로 바꾸고 이 경로는 T01.08에서 본다 [13].
`path`가 출력 폴더 경로로 시작하면 이미 꺼낸 파일로 보고 이미지 안 풀이를 건너뛴다 [13].
이 비교는 문자열 접두어만 보므로 출력 폴더 뒤에 `..`을 붙인 값도 서버가 이미지 안 풀이 없이 호스트 경로로 외부 도구에 넘긴다 [13].

`mount_evidence`는 마운트 명령이 성공한 경우 이미 이미지가 정해져 있으면 `investigationState.imagePath`를 바꾸지 않는다 [18].
응답과 호출 기록에는 새로 받은 `image_path`를 적지만 뒤의 연산은 앞의 이미지를 계속 읽는다 [18].

### T01.08 입력 부재 시 다른 입력으로 대체

**구현.** 이 방식은 이미지 안 경로를 받는 레지스트리·이벤트 로그 연산과 `list_directory`·`search_filename`에 적용된다 [19][20].
서버는 `path`를 `/`로 나눈 조각마다 `fls`를 실행해 이름이 같은 항목의 inode를 따라간다 [19].
조각을 찾지 못하거나 `fls`가 실패하면 따라가기를 멈추지만 앞에서 찾은 inode는 그대로 남는다 [19][21].
레지스트리·이벤트 로그 연산은 첫 조각부터 찾지 못하거나 `fls`가 처음부터 실패하면 `path`를 바꾸지 않고 그대로 외부 도구에 넘긴다 [19][20].
중간 조각에서 멈추면 마지막으로 찾은 항목의 inode를 `icat`으로 꺼내 `extracted_<그 inode>_<요청한 마지막 조각 이름>`에 쓰고 `path`를 그 파일 경로로 바꾼다 [19][20].
이 꺼내기가 실패하면 원래 `path`를 넘긴다 [20].
원래 `path`를 넘기면 이미지 안의 경로가 호스트 경로로 쓰이므로 호스트에 같은 경로의 파일이 있으면 증거가 아닌 그 파일이 분석 입력이 된다 [20].
모델이 `path`를 주지 않은 레지스트리 연산은 기본 하이브 경로로 같은 일을 겪는다 [20].
마지막으로 찾은 항목은 보통 폴더이고 폴더 inode에 `icat`을 실행한 결과는 확인하지 않았다 [20].
`list_directory`·`search_filename`은 첫 조각부터 찾지 못하면 `path`를 그대로 둔 채 실행한다 [21].
두 연산의 `fls` 인자는 `path`를 쓰지 않고 inode만 쓰므로 이때는 이미지 루트부터 나열하거나 검색한다 [21].
중간 조각에서 멈추면 마지막으로 찾은 폴더의 inode를 `inode`에 넣고 `path`를 지워 요청한 폴더가 아닌 그 폴더를 나열하거나 검색한다 [21].
응답과 호출 기록에는 입력을 바꿨다는 표시가 없다.
