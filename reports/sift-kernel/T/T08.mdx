# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 서버가 실행하는 외부 도구는 모두 공통 실행기의 `execute`나 `extractToFile`을 거치고 두 함수가 종료 코드를 본다 [1][2].
`execute`는 프로세스가 0이 아닌 코드로 끝나면 실패를 돌려주고 0이면 성공을 돌려준다 [1].
서버는 실행기가 실패를 돌려주면 연산을 `success: false`로 정하고 실행 오류의 `message`를 응답과 호출 기록의 오류로 싣는다 [3].
이 `message`에는 종료 코드만 들어가고 표준 오류는 들어가지 않는다 [4].
`mount_evidence`는 마운트 명령의 종료 코드가 0일 때만 마운트 성공으로 본다 [5].
이미지에서 파일을 꺼내는 `extractToFile`은 종료 코드가 0이 아니고 받은 바이트도 없을 때만 실패로 본다 [2].

**한계.** `execute`는 `close` 이벤트의 종료 코드가 `null`이면 0으로 바꿔 성공을 돌려준다 [1].
Node.js는 자식 프로세스가 신호로 끝났을 때 이 값을 `null`로 준다 [6].
실행기가 시간 제한·출력 상한으로 끊은 경우는 따로 다루지만 그 밖의 신호로 끝난 도구는 그때까지의 출력과 함께 성공으로 처리된다 [1][3].
`extractToFile`은 종료 코드가 0이 아니어도 받은 바이트가 있으면 성공을 돌려준다 [2].
서버는 그 파일로 `path`를 바꿔 레지스트리·이벤트 로그 도구를 실행하고 꺼내기가 실패 코드로 끝났다는 표시를 남기지 않는다 [7].

### T08.02 시간 제한·종료 신호 처리

**구현.** 실행기는 실행마다 시간 제한을 걸고 시간이 지나면 `SIGTERM`을 보낸 뒤 5초 뒤에 `SIGKILL`을 보낸다 [8].
기본 시간 제한은 45초다 [9].
서버는 `search_filename`과 재귀 `list_directory`에 30초, 이벤트 로그 연산에 35초를 주고 비동기 연산에는 300초를 준다 [10][11].
실행기는 표준 출력이 줄 수 상한이나 바이트 상한을 넘을 때도 같은 `killed` 표시를 세우고 프로세스를 끊는다 [12].
끊긴 실행에 표준 출력이 없으면 시간 초과 오류를 돌려주고 출력이 있으면 종료 코드 -1과 그 출력을 돌려준다 [13].
시간 초과 오류는 다시 시도할 오류로 표시되고 실행기는 같은 명령을 처음 실행까지 합쳐 3번까지 실행한다 [4][14].
표준 오류에 `EAGAIN`·`EBUSY` 같은 문구가 있는 실패도 다시 시도한다 [4][14].
다시 시도하는 횟수는 exponential-backoff 3.1.3의 `numOfAttempts` 동작을 따른다 [15].
다시 시도하는 조건은 오류 종류만 보고 부하나 다른 실행의 유무는 보지 않는다 [14].
다시 시도 사이의 대기는 500밀리초에서 시작해 두 배씩 늘리고 무작위 jitter를 둔다 [14].
다시 시도는 `serialize`가 큐에 넣은 함수 안에서 `backOff`로 하므로 다시 시도하는 동안에도 큐 자리를 놓지 않고 다른 실행은 큐에서 기다린다 [14][16].

실행기는 외부 도구를 한 번에 하나만 실행하고 시간 제한은 차례가 와서 프로세스를 시작할 때부터 잰다 [16].
호출 처리기는 요청 객체만 받고 클라이언트의 호출 취소를 실행기에 전하는 코드가 없다 [17].
그래서 클라이언트가 기다림을 멈춰도 실행과 다시 시도는 이어진다.

**한계.** 시간 제한이나 출력 상한으로 끊긴 실행에 출력이 있으면 서버는 종료 코드 -1을 성공으로 처리한다 [13][18].
응답과 호출 기록에는 끊겼다는 표시가 없고 시간 초과와 출력 상한도 구별되지 않는다 [18].
비동기 연산도 같은 결과를 `completed`로 둔다 [19].
이 상태는 T08.05에서 본다.

실행기의 실행 파일 대체 목록은 짝끼리 서로를 가리킨다 [20].
두 이름이 모두 없는 도구는 `ENOENT`가 날 때마다 시간 제한 타이머를 지우고 다른 이름으로 다시 실행하므로 시간 제한이 적용되지 않고 실행이 끝나지 않는다 [21].
실행기는 한 번에 하나만 실행하므로 이 실행이 끝나지 않으면 뒤의 외부 도구 실행도 차례를 받지 못한다 [16].
`--sudo`로 서버를 실행하면 신호를 받는 프로세스는 `sudo`이고 그 아래 도구 프로세스까지 끝나는지는 확인하지 못했다 [22].

### T08.03 오류·출력 내용 판독

**구현.** 출력 내용으로 성공을 가르는 곳은 `mount_evidence`, 파일 꺼내기, regipy 연산이다 [23][2][24].
`mount_evidence`는 메모리 덤프 확장자면 `vol`로 `windows.info.Info`를 실행하고 종료 코드가 0이거나 출력에 `Kernel`이 있으면 메모리 덤프로 받는다 [23].
마운트가 실패하면 `fls` 출력이 비지 않았을 때만 직접 읽기로 성공을 정하고 `mmls` 출력도 비지 않았을 때만 분할 정보를 읽는다 [25].
`extractToFile`은 받은 바이트가 0이면 `No data extracted`로 실패를 돌려준다 [2].
regipy 연산은 표준 출력 대신 결과 JSON 파일을 읽고 그 파일이 비지 않았을 때만 내용을 결과로 쓴다 [24].

공통 실행 경로는 도구 출력의 오류 문구를 읽지 않는다.
종료 코드 0으로 끝나고 출력이 빈 실행은 `status`가 `completed`인 결과로 성공 처리한다 [26].
파서는 실패를 돌려주지 않고 전용 파서가 없는 연산은 원래 출력을 그대로 결과에 넣는다 [27].
여러 플러그인을 한 번에 실행하는 레지스트리 연산도 실행 하나의 성공·실패만 정하므로 T08.04에는 연결하지 않는다 [28].
서버 안 처리기는 분석 라이브러리를 부르지 않고 앞선 원래 출력을 읽는 서버 코드라서 T08.08에는 연결하지 않는다 [29].

**한계.** regipy 결과 파일이 없거나 비면 서버는 표준 출력을 결과로 두고 성공으로 처리한다 [24].
코드 주석은 이 표준 출력이 플러그인 진행 문구뿐이라고 적는다 [24].

### T08.05 비동기 최종 상태 조회

**구현.** `generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`는 배경 작업으로 실행한다 [30].
서버는 작업 ID를 만들어 `running` 상태로 작업 목록에 넣고 작업 ID와 `get_job_status` 안내를 바로 돌려준다 [19][31].
배경 작업으로 실행할 연산은 서버 코드에 고정한 `ASYNC_TOOLS` 4개이고 이 연산은 늘 바로 작업 ID를 돌려준다 [30][31].
모델이나 사용자는 배경 실행 여부를 고르지 못한다 [30].
배경 작업은 일반 호출과 같은 실행기의 큐를 나눠 쓰고 큐에서 기다리는 동안에도 작업 목록에는 `running`으로 적힌다 [19][16].
실행이 끝나면 실행기 결과가 성공일 때 `completed`와 출력 앞 2000자·출력 파일 경로를, 실패일 때 `failed`와 오류 문구를 작업에 적는다 [19].
`get_job_status`는 작업 ID를 받으면 그 작업을, 받지 않으면 모든 작업을 돌려준다 [32].
호출 기록 항목은 작업을 시작할 때 성공으로 남고 작업이 끝난 뒤 고치지 않는다 [33].

**한계.** 작업 상태는 실행기 결과가 성공인지만 보고 정하므로 300초 시간 제한으로 끊겨 출력 일부만 남은 실행도 `completed`가 된다 [13][19].
작업 목록은 서버 객체의 메모리에만 있어 서버를 다시 시작하면 앞선 작업은 `Job not found`가 된다 [30][32].
HTTP 전송은 요청마다 서버 객체를 새로 만들므로 다른 요청에서 시작한 작업은 `get_job_status`가 찾지 못한다 [34].

export function executionError(
  tool: string,
  exitCode: number | null,
  stderr: string,
  timedOut: boolean,
): ExecutionError {
  const message = timedOut
    ? `Tool "${tool}" timed out`
    : `Tool "${tool}" exited with code ${exitCode}`;
  const guidance = timedOut
    ? `The tool took too long. Try with a smaller scope or increase timeout.`
    : `Check stderr for details: ${stderr.slice(0, 200)}`;
  // Mark as retriable if timedOut or if stderr hints at transient resource issues
  const retriable = timedOut || /EAGAIN|EBUSY|EIO|EMFILE|resource temporarily/i.test(stderr);
  return { kind: "EXECUTION_ERROR", tool, exitCode, stderr, timedOut, retriable, message, guidance };
}
