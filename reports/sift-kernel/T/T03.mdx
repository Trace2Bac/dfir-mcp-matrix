# T03 실행 조건 확인

### T03.01 선행 결과 대조

**구현.** 서버는 도구와 분류 도구의 연산마다 실행에 필요한 능력(`requires`)과 성공한 뒤 생기는 능력(`produces`)을 명세로 둔다 [1].
예를 들어 `list_directory`는 `evidence_mounted`와 `integrity_verified`를 요구하고 성공하면 `filesystem_accessible`을 만든다 [1].
서버가 지금 가진 능력은 `CapabilityGraph`의 메모리 집합 `held`에 있다 [2].

명세를 대조하는 곳은 분류 도구의 연산을 실행하는 경로다.
모델이 분류 도구를 부르면 서버는 `operation` 인자로 내부 연산을 고른다 [3].
외부 도구를 실행하기 직전에 그 연산의 `requires`를 `held`와 대조한다 [4].
모자란 능력이 있으면 실행하지 않고 `CAPABILITY_BLOCKED` 오류를 돌려준다 [4].
오류에는 모자란 능력, 가진 능력, 다음 작업 권고가 들어간다 [4].
마운트 전에 `list_directory`를 부르자 `evidence_mounted`·`integrity_verified`가 모자라 거부됐다 [5].

실행이 성공으로 끝나면 `produce`가 그 연산의 `produces`를 `held`에 더한다 [6].
실패한 연산은 능력을 만들지 않는다 [6].
다음 호출의 대조는 이렇게 늘어난 집합을 쓴다.
능력은 메모리에만 있어 HTTP 전송처럼 요청마다 서버를 새로 만들면 다음 요청에 남지 않는다 [7].

**한계.** 명세에 요구 능력이 있는 `register_finding`·`register_hypothesis`·`reassess_finding`·`corroborate_finding`·`challenge_finding`·`generate_report`는 능력 대조보다 앞의 분기에서 처리되고 돌아간다 [8].
마운트 전에 `register_hypothesis`를 부르자 가설이 등록됐다 [8].

능력은 연산이 확인하려던 사실과 다르게 생길 수 있다.
`verify_integrity`는 `ewfverify`를 부르는데 실행 파일이 없으면 실행기가 해시를 계산하지 않는 `img_stat`으로 바꿔 부른다 [9].
`img_stat`이 성공하면 `integrity_verified`가 생긴다 [6][9].
`list_registry_hives`는 파일 목록 기록이 없어도 성공으로 끝나 `registry_accessible`을 만든다 [10].
능력은 증거와 묶이지 않고 `held`에 더해지기만 하므로 다른 이미지를 다시 마운트해도 앞의 확인이 그대로 쓰인다 [2][6].

### T03.02 조사 단계 검사

**구현.** 방법론 상태 기계는 증거 종류별 기준 도구와 상관 분석 도구를 시도하면서 단계를 옮기고 마지막에 `REPORT` 단계에 이른다 [11].
`generate_report`는 `REPORT` 단계가 아니면 남은 기준 도구 가운데 요구 능력을 채운 도구를 센다 [12].
발견사항이 하나도 없고 그런 도구가 남았으면 `INVESTIGATION_INCOMPLETE`로 거부한다 [12].
그 밖에는 상태 기계를 `REPORT`로 옮기고 보고서를 만든다 [12].

**한계.** 요구 능력을 채운 기준 도구가 하나도 없으면 발견사항이 없어도 검사를 통과한다 [12].
기준 도구는 모두 파일시스템·레지스트리·이벤트 로그 능력을 요구하므로 마운트 전에는 이 경우에 해당한다 [13].

### T03.09 원격 호출자 인증

**구현.** 이 방식은 서버를 `--transport http`로 실행했을 때의 HTTP 전송에 적용된다 [14].
HTTP 전송으로 서버를 실행할 때 `--token`이 없으면 서버가 오류를 적고 끝난다 [14].
요청마다 `Authorization` 헤더가 `Bearer <token>`과 같은지 보고 다르면 401 응답을 돌려준다 [15].
`OPTIONS` 요청은 인증 전에 204로 끝나지만 도구를 부르지 못한다 [15].
토큰은 명령줄 인자로 받아 같은 호스트의 프로세스 목록에 보인다 [16].
헤더 비교는 `!==` 문자열 비교이고 응답에는 모든 출처를 허용하는 CORS 헤더가 붙는다 [15].
stdio 전송에는 이 검사가 없다.

### T03.12 동시 실행 수 제한

**구현.** 이 방식은 외부 도구를 실행하는 `ProcessExecutor`의 두 경로 `execute`·`extractToFile`에 적용된다 [17][18].
두 경로는 모두 Promise 큐 하나에 이어 붙어 한 번에 외부 도구 하나만 실행한다 [17][18].
한도 1은 서버 코드에 고정되어 있고 사용자나 모델이 바꾸지 못한다 [17].
주석은 증거 이미지의 I/O 경합을 막으려는 제한이라고 적는다 [17].
앞선 실행이 실패해도 큐는 다음 실행을 시작한다 [17].
큐는 서버 객체를 만들 때 생기는 실행기 하나에 딸리므로 이 제한은 서버 객체 하나 안의 실행에 적용된다 [19].
큐에서 기다리는 시간에는 상한이 없고 실행 시간 제한은 큐를 지나 외부 도구 프로세스를 시작한 뒤부터 잰다 [20].
메모리·CPU 사용률은 보지 않는다.

배경 작업으로 실행되는 `generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`도 같은 실행기의 `execute`를 불러 같은 큐에 들어간다 [21][22].
배경 작업의 시간 제한은 300초이고 작업 목록에는 큐에서 기다리는 동안에도 처음부터 `running`으로 적힌다 [22].
그래서 배경 작업이 큐에서 기다리거나 실행되는 동안 뒤에 들어온 일반 호출은 그 작업이 끝날 때까지 큐에서 기다린다 [17][22].
실행기 파일의 한 주석은 기본 시간 제한 45초가 MCP 클라이언트의 60초 시간 제한보다 짧아야 한다고 적는다 [23].
큐 대기 시간은 이 시간 제한에 포함되지 않으므로 앞선 실행이 길면 일반 호출의 대기와 실행을 합친 시간이 60초를 넘을 수 있다 [20][23].
이 내용은 코드로만 확인했고 실행하지 않았다.

**한계.** 실행기는 `createSiftKernelServer`가 서버를 만들 때 하나 생긴다 [19].
HTTP 전송은 요청마다 서버를 새로 만들어 요청마다 큐가 따로 생긴다 [7].
그래서 동시에 들어온 HTTP 요청의 외부 도구는 서로 기다리지 않고 함께 실행된다.
