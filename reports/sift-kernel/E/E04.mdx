# E04 분석 입력 준비

### E04.02 선택 추출

**구현.** 이미지에서 파일을 꺼내 분석 입력으로 쓰는 곳은 이벤트 로그 연산 3개와 레지스트리 연산 12개다 [1].
`parse_event_log`·`search_events`·`parse_powershell_logs`와 `registry` 분류의 하이브 연산, `parse_shimcache`·`parse_bam`·`parse_muicache`·`parse_userassist`가 여기에 포함된다 [1].
레지스트리 연산 8개는 모델이 `path`를 주지 않으면 연산마다 정해 둔 하이브 경로(`/Windows/System32/config/SYSTEM`·`SOFTWARE`·`SAM`)를 넣는다 [1].

서버는 `path`를 이미지 안의 경로로 보고 `/`로 나눈 조각마다 `fls`를 실행해 이름이 같은 항목의 inode를 따라간다 [2].
이름은 대소문자를 가리지 않고 통째로 대조한다 [2].
inode를 하나라도 찾으면 마지막으로 찾은 inode의 내용을 `icat`으로 출력 폴더의 `extracted_<inode>_<요청한 마지막 조각 이름>` 파일에 쓰고 `path`를 그 파일 경로로 바꾼다 [2][3][4].
외부 도구(`evtx_dump`·`regipy-plugins-run`·`AppCompatCacheParser`)는 바뀐 호스트 경로를 입력으로 받는다 [3][5].
꺼내는 것은 고른 파일 하나뿐이다.
하이브의 트랜잭션 로그(`.LOG1`·`.LOG2`)는 꺼내지 않고 로그를 하이브에 적용하는 단계도 없다 [3].

`list_directory`·`search_filename`도 `path`를 같은 방식으로 inode로 바꾸지만 파일을 꺼내지 않고 그 inode를 `fls` 인자로 넘긴다 [6].
`extract_file`은 `icat` 출력을 그대로 결과로 돌려줄 뿐 다른 연산의 입력으로 잇지 않는다 [7].
`recover_deleted`·`carve_files`·`analyze_unallocated`가 출력 폴더에 쓰는 파일도 서버가 다른 연산의 입력으로 잇지 않는다 [7].

다른 연산은 받은 경로를 그대로 외부 도구에 넘기고 입력을 따로 준비하지 않는다.
`extract_strings`·네트워크 연산·`hash_and_lookup`·`parse_srum`·`parse_usnjrnl`과 EZ Tools 연산(`parse_prefetch` 등)이 여기에 포함되고 이 `path`는 호스트 경로로 쓰인다 [8].
`parse_prefetch`는 `path`가 없으면 호스트의 `/Windows/Prefetch`를 넘긴다 [8].
Sleuth Kit·Volatility·YARA 연산은 조사 상태의 이미지 경로를 그대로 받는다(E03).
EWF 이미지의 `.E02` 이후 조각은 서버가 찾지 않고 Sleuth Kit과 `ewfverify`가 첫 조각 이름으로 찾는다 [9].
`mount_evidence`는 이미지를 마운트하는 명령을 실행하지만 분석 연산은 마운트 지점이 아니라 이미지 파일 경로를 읽는다(E03) [10].
분석 범위를 한 파티션으로 좁히는 방식은 E04.03에서 본다.

**예외.** inode를 하나도 얻지 못하거나 꺼내기에 실패해 원래 `path`로 실행하는 경로는 T01.08에서 본다 [2][3].
경로 일부만 찾으면 요청한 파일이 아니라 마지막으로 찾은 항목(보통 폴더)을 요청한 파일 이름으로 꺼낸다 [2][3].
폴더 inode에 `icat`을 실행한 결과는 확인하지 않았다 [3].

추출 함수는 `icat`이 0이 아닌 종료 코드로 끝나도 쓴 바이트가 있으면 성공으로 돌려준다 [4].
이렇게 일부만 쓴 파일도 분석 입력이 된다.
추출에는 크기 상한이 없지만 실행기의 기본 시간 제한 45초가 적용된다 [3][4].
45초 안에 끝나지 않으면 추출이 실패로 끝나고 서버는 원래 `path`를 외부 도구에 넘긴다(T01.08) [3][4].

조각을 대조할 때 `fls` 출력에서 이름이 같은 첫 줄을 고르고 삭제 표시(`*`)를 보지 않는다 [2].
같은 폴더에 이름이 같은 삭제 항목이 먼저 나오면 그 inode를 꺼낸다.
실제 이미지에서 이런 줄이 먼저 나오는지는 확인하지 않았다.

`path`가 출력 폴더 경로 문자열로 시작하면 추출을 건너뛰고 그 파일을 그대로 쓴다 [2].
앞서 다른 이미지에서 꺼낸 파일도 이 경로로 넘기면 지금 증거와 구별 없이 입력이 된다.

### E04.03 전체·부분 마운트

**구현.** sift-kernel은 마운트 지점을 분석 입력으로 쓰지 않고 파티션 시작 위치를 Sleuth Kit에 넘겨 그 파티션의 파일시스템만 읽게 한다.
Sleuth Kit 연산과 파일 추출은 조사 상태의 파티션 시작 위치 `partitionOffset`을 `-o` 인자로 넘긴다 [2][11].
서버가 이 값을 정하는 곳은 `mount_evidence`의 한 분기뿐이다 [12].
마운트 명령이 실패하고 `fls -o 0`으로 이미지가 읽히면 `mmls` 출력에서 설명에 NTFS·Win95·FAT가 든 첫 줄을 찾아 그 시작 섹터를 `partitionOffset`에 적는다 [12].
찾지 못하면 값을 바꾸지 않는다 [12].
모델은 `list_partitions`로 파티션 표를 볼 수 있지만 시작 위치를 정하는 인자는 없다 [11][13].

**예외.** 주석은 가장 큰 NTFS 파티션을 고른다고 적지만 코드는 조건에 맞는 첫 줄을 고른다 [12].
시작 섹터를 읽는 정규식은 슬롯 칸이 `000:000` 모양인 줄에 맞지 않는다 [12][14].
저장소의 파서 테스트에 실린 DOS 파티션 표의 NTFS 줄이 이 모양이라 이 줄에서는 시작 위치를 읽지 못한다 [14].

마운트 명령이 성공한 경로와 메모리·pcap 분기는 `partitionOffset`을 정하지도 0으로 되돌리지도 않는다 [15].
`reset_investigation`도 이 값을 지우지 않는다(E01) [16].
그래서 앞 증거에서 정한 시작 위치가 다음 증거의 Sleuth Kit 연산에 그대로 쓰인다.

`mount_evidence`의 입력 형식은 `partition_index`를 받지만 서버 코드는 이 값을 읽지 않는다 [13].

### E04.05 추출·생략 범위 기록

**구현.** 파일을 꺼내면 서버가 도구 인자의 `path`를 꺼낸 파일 경로로 바꾼 뒤 그 인자로 호출 기록 항목을 만든다 [3][17].
그래서 호출 기록의 `params.path`에는 `extracted_<inode>_<이름>` 경로가 남아 어느 inode를 꺼냈는지 알 수 있다 [17].
`list_directory`·`search_filename`은 `path` 대신 찾은 `inode`가 호출 기록에 남는다 [6][17].
응답에는 도구 인자가 실리지 않아 꺼낸 파일 경로는 호출 기록에만 있다 [18].

**예외.** 추출에 실패하면 호출 기록에는 모델이 준 `path`가 그대로 남는다 [3][17].
그 값만으로는 추출을 시도했다가 실패했는지 처음부터 호스트 경로였는지 구별할 수 없다.
경로 일부만 찾은 경우에도 `params.path`는 `extracted_<마지막으로 찾은 inode>_<요청한 파일 이름>`으로 기록된다 [3][17].
그래서 기록만으로는 요청한 파일을 꺼낸 경우와 구별되지 않는다.
추출 함수가 돌려주는 바이트 수는 버리고 일부만 꺼낸 경우도 따로 적지 않는다 [3][4].
