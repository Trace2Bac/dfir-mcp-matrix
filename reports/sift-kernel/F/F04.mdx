# F04 발견사항 기록 관리

### F04.02 발견사항 필드 구분 저장

**구현.** 발견사항은 커널 도구 `register_finding`으로 받는다 [1].
받는 필드는 분류 `type`, 설명 `description`, 근거 `evidence`, 사건 시각 `temporal_range`, `mitre_technique`·`mitre_tactic`, `affected_hosts`, `iocs`, 지지·반박 가설 ID `supports_hypotheses`·`contradicts_hypotheses`다 [1].
서버는 발견사항 ID, 확신도 `confidence`, 등록 시각 `registeredAt`을 직접 정한다 [2].
확신도는 근거 항목 수와 근거 도구의 분류 수로 정한다 [3].
근거 1개면 `INFERRED`, 2개 이상이고 분류가 하나면 `SUPPORTED`, 분류가 둘 이상이면 `CONFIRMED`다 [3].
제목·심각도 필드는 따로 없다 [1].

서버가 보는 것은 `type`·`description`이 비어 있지 않고 `evidence`가 배열인지뿐이다 [4].
`type`의 값 목록은 입력 schema에만 있다 [5].
MCP SDK 1.29.0의 `Server`는 `tools/call` 요청의 모양만 검사하고 인자를 도구의 입력 schema와 대조하지 않는다 [6].
그래서 목록 밖의 `type`이나 형식이 다른 `mitre_tactic`도 그대로 남고 F04.10에는 연결하지 않는다 [1][4][6].

발견사항은 서버 프로세스 메모리의 `Map`에만 있다 [7].
SQLite 파일에 `findings` 테이블과 저장 함수 `saveFinding`이 있지만 서버는 그 함수를 부르지 않는다 [8].
그래서 서버를 다시 시작하면 발견사항이 사라지고 F04.06에는 연결하지 않는다.
HTTP 전송은 요청마다 서버 객체를 새로 만들어 발견사항 `Map`도 요청마다 새로 생긴다 [9].
`reset_investigation`은 발견사항과 가설을 흔적 없이 비운다 [10].

`reassess_finding`은 근거 항목을 덧붙이고 확신도를 다시 계산해 덮어쓴 뒤 `lastReassessed`에 시각을 넣는다 [11].
앞 확신도는 그 호출의 응답에만 나가고 저장되지 않는다 [12].
발견사항을 철회하거나 설명을 고치는 도구는 없다.
가설 상태도 덮어쓰기만 한다(F04.08).
그래서 F04.05에는 연결하지 않는다.
판정 필드 없이 자유 글만 남기는 노트 도구도 없어 F04.01에는 연결하지 않는다.

### F04.03 근거 증거·호출 참조

**구현.** 이 방식은 `register_finding`과 `reassess_finding`에 적용된다 [13][11].
`evidence`는 호출 기록 항목 ID 목록이고 비어 있으면 등록을 거부한다 [13].
목록의 ID가 하나라도 호출 기록에 없으면 등록을 거부하고 없는 ID를 오류 문장에 적는다 [13].
`reassess_finding`이 덧붙이는 `additional_evidence`도 같은 대조를 거친다 [11].
근거 증거 파일이나 파생물 경로를 받는 필드는 없고 호출 기록 항목이 원래 출력 파일을 가리킨다 [1].

### F04.04 사건 시각과 작성 시각 분리

**구현.** 이 방식은 `register_finding`에 적용된다 [1][2].
사건 시각은 모델이 넘기는 선택 인자 `temporal_range`(`start`·`end`)이고 작성 시각 `registeredAt`은 서버가 등록할 때 기록한다 [1][2].
`reassess_finding`은 다시 평가한 시각을 `lastReassessed`에 따로 둔다 [11].
서버는 `temporal_range`의 형식을 보지 않고 받은 값을 그대로 둔다 [1].

### F04.07 가설 지지·반박 근거 연결

**구현.** 이 방식은 `register_hypothesis`와 `register_finding`에 적용된다 [14][15].
`register_hypothesis`는 설명만 받아 `OPEN` 상태의 가설을 만들고 지지·반박 발견사항 목록을 비워 둔다 [14].
`register_finding`에 `supports_hypotheses`·`contradicts_hypotheses`를 주면 그 가설의 `supportingFindings`·`contradictingFindings`에 새 발견사항 ID를 덧붙인다 [15][16].
`get_hypothesis_status`는 가설마다 상태와 지지·반박 발견사항 수를 돌려준다 [17].
연결은 발견사항을 등록할 때만 하고 `reassess_finding`은 가설 쪽을 바꾸지 않는다 [11][12].
가설도 서버 메모리의 `Map`에만 있다 [7].

**한계.** `register_finding`은 받은 가설 ID가 있는지 보지 않고 발견사항의 `supportsHypotheses`·`contradictsHypotheses`에 그대로 넣는다 [1].
가설을 갱신할 때는 없는 ID를 건너뛴다 [15].
그래서 발견사항은 어떤 가설을 지지한다고 적혀 있는데 그 가설에는 연결이 없을 수 있다.

### F04.08 가설 상태 관리

**구현.** 이 방식은 `register_finding`이 가설을 갱신할 때 적용된다 [15].
상태는 `OPEN`·`SUPPORTED`·`REFUTED`이고 서버 규칙으로 정한다 [18].
반박이 지지보다 많으면 `REFUTED`, 지지가 2개 이상이고 반박이 없으면 `SUPPORTED`, 그 밖에는 `OPEN`이다 [18].
갱신할 때마다 상태를 다시 계산하고 `SUPPORTED`·`REFUTED`가 되면 `resolvedAt`에 시각을 넣는다 [16].
가설에는 지금 상태와 `resolvedAt`만 남는다 [16].
다음 갱신이 상태를 바꾸면 앞 상태와 `resolvedAt`을 덮어쓰고 `OPEN`으로 돌아가면 `resolvedAt`을 지운다 [16].
지지 목록과 반박 목록이 따로 쌓여 지지와 반박이 들어온 차례도 다시 볼 수 없다 [16].
그래서 가설 상태가 바뀐 차례는 F04.05에 해당하지 않는다.

```typescript
export function computeConfidence(
  evidence: readonly LedgerEntryId[],
  getCategoryForEntry: (id: LedgerEntryId) => ArtifactCategory | undefined,
): ConfidenceLevel {
  if (evidence.length === 0) return "HYPOTHESIZED";
  if (evidence.length === 1) return "INFERRED";

  // Check if evidence comes from different artifact categories
  const categories = new Set<ArtifactCategory>();
  for (const id of evidence) {
    const cat = getCategoryForEntry(id);
    if (cat) categories.add(cat);
  }

  if (categories.size >= 2) return "CONFIRMED";
  return "SUPPORTED";
}
```

```typescript
export function updateHypothesis(
  hypothesis: Hypothesis,
  action: { type: "support" | "contradict"; findingId: FindingId },
): Hypothesis {
  const supporting = action.type === "support"
    ? [...hypothesis.supportingFindings, action.findingId]
    : hypothesis.supportingFindings;
  const contradicting = action.type === "contradict"
    ? [...hypothesis.contradictingFindings, action.findingId]
    : hypothesis.contradictingFindings;

  const status = computeHypothesisStatus(supporting, contradicting);
  const resolvedAt = (status === "SUPPORTED" || status === "REFUTED")
    ? new Date().toISOString()
    : undefined;

  return {
    ...hypothesis,
    supportingFindings: supporting,
    contradictingFindings: contradicting,
    status,
    resolvedAt,
  };
}
```

```typescript
export function computeHypothesisStatus(
  supporting: readonly FindingId[],
  contradicting: readonly FindingId[],
): HypothesisStatus {
  if (supporting.length === 0 && contradicting.length === 0) return "OPEN";
  if (contradicting.length > supporting.length) return "REFUTED";
  if (supporting.length >= 2 && contradicting.length === 0) return "SUPPORTED";
  if (supporting.length > 0 && contradicting.length === 0) return "OPEN"; // Not enough to confirm
  return "OPEN"; // Mixed evidence — still investigating
}
```
