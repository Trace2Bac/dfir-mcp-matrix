# P03 조사 진척 판단

### P03.01 기준 작업 목록 대조

**구현.** 방법론 상태 기계는 증거 종류마다 기준 도구 목록을 둔다 [1].
Windows 디스크 목록은 18개, Linux 디스크 목록은 8개, 메모리 목록은 7개, 네트워크 캡처 목록은 6개다 [1].
분류 연산이 성공하면 그 이름을 수행한 도구 집합에 넣고 실패하면 실패한 도구 집합에 넣는다 [2].
`getRemainingSteps`는 기준 목록에서 두 집합 어디에도 없는 도구를 남은 작업으로 세고 `suggest_next_action`이 이것을 `remaining_steps`로 돌려준다 [3][4].
`get_methodology_coverage`는 분류별로 수행한 도구와 비율을 돌려준다 [5].
`overall_coverage`는 증거 종류에 맞춘 분류들에서 수행한 도구의 비율이고 실패한 도구는 분모에서 뺀다 [6].

**한계.** 대조는 도구 이름으로만 한다 [2][3].
수행한 도구 집합은 증거 항목과 묶이지 않아 다른 이미지를 마운트해도 앞 이미지에서 실행한 도구가 수행한 것으로 남는다 [2].
남은 작업 수는 실패한 도구도 시도한 것으로 보고 뺀다 [3].
백그라운드로 실행되는 `generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`는 작업을 시작하는 순간 수행한 도구로 적고 작업이 실패해도 고치지 않는다 [7].
서버 안 처리기는 재료가 되는 앞선 출력이 없으면 `no_data` 같은 결과를 성공으로 돌려주므로 분석하지 않은 기준 도구도 수행한 것으로 센다 [8][2].
`detect_timestomping`·`correlate_logon_events`가 이렇게 끝날 수 있는 기준 도구다 [8].
Linux 기준 목록의 `parse_auth_log`를 비롯한 Linux 연산 6개도 대상 파일을 꺼냈다고 판단하지 못하면 `file_not_extracted`를 성공으로 돌려준다 [1][9].
브라우저·사용자 활동 연산 일부는 재료가 있어도 분석하지 않고 성공으로 끝난다.
`parse_browser_history`는 DB를 꺼내지 않았다고 판단하면 `databases_not_extracted`를 성공으로 돌려주고 DB를 읽는 경로는 없다 [10].
실행 파일 매핑이 없는 `parse_recent_docs`·`parse_mru_lists`·`parse_rdp_cache`·`parse_clipboard_history`는 파일 목록에서 이름을 찾으면 `artifacts_located`를 성공으로 돌려준다 [11].
그래서 이 연산들은 분석 없이 `overall_coverage`와 분류별 비율의 수행한 도구로 세어진다 [2][5][6].
메모리 덤프와 네트워크 캡처도 Windows 기준 목록과 대조한다.
수행한 도구 집합은 프로세스 메모리에만 있어 서버를 다시 시작하면 비고 남은 작업을 처음부터 다시 센다 [12].

### P03.02 단계 상태·완료 조건 대조

**구현.** 상태 기계의 단계는 `COLLECTION`·`TRIAGE`·`CLASSIFY`·`INVESTIGATE`·`TIMELINE`·`CORRELATE`·`REPORT`다 [13].
상태 기계는 `COLLECTION`에서 `evidence_mounted`·`integrity_verified` 능력이 모두 있으면 `TRIAGE`로 옮기고 `TRIAGE`에서 `list_directory`가 성공하고 `search_filename`을 시도하면 `CLASSIFY`로 옮긴다 [14].
상태 기계는 `INVESTIGATE`에서 기준 도구와 켜진 조사 경로의 도구를 모두 시도해야 `TIMELINE`으로 옮기고 `TIMELINE`에서 `generate_timeline`을 시도해야 `CORRELATE`로 옮긴다 [14].
상태 기계는 `CORRELATE`에서 상관 분석 도구 2개를 시도하고 열린 가설이 있으면 `get_hypothesis_status`까지 시도해야 `REPORT`로 옮긴다 [14].
시도에는 성공과 실패가 모두 포함되고 요구 능력을 만들 도구가 없는 도구는 건너뛴다 [15].
`TRIAGE`의 `list_directory` 조건만은 성공한 호출만 센다 [14].
`suggest_next_action`은 단계마다 `complete`·`active`·`pending`을 매긴 `phase_progress`와 `REPORT` 단계인지에 따른 `investigation_status`를 돌려준다 [4][16].
추론 엔진 응답의 `comeback_triggered`는 추론기의 수렴 상태만 `EXPLORING`으로 되돌리고 상태 기계 단계는 바꾸지 않는다 [17].
보고 준비 여부는 상태 기계가 `REPORT` 단계인지로만 정한다 [17].
README가 Rough-set 결정 근사의 조사 중단 기준으로 소개하는 `shouldStopInvestigating`은 서버 코드에서 부르는 곳이 없다 [18].
`get_investigation_state`와 리소스 `forensic://investigation/state`의 `phase`는 상태 기계 단계가 아니라 가진 능력으로 정한 `MOUNTED`·`TRIAGING` 같은 값이다 [19].

**한계.** `get_hypothesis_status`는 커널 도구 분기에서 처리하고 돌아가 상태 기계에 시도로 적히지 않는다 [20].
그래서 모델이 그 도구를 불러도 `CORRELATE`의 가설 조건이 풀리지 않고 가설이 발견사항으로 지지·반박되어 닫힐 때까지 같은 권고가 되풀이된다 [20].
`generate_report`도 시도로 적히지 않아 보고서를 만든 뒤에도 `REPORT` 단계는 `generate_report`를 계속 권하고 조사가 끝났다는 빈 권고에 이르지 않는다 [21].
`generate_report`는 `REPORT` 단계가 아니어도 발견사항이 하나라도 있으면 상태 기계를 `REPORT`로 옮긴 뒤 보고서를 만든다 [22].
markdown·html 보고서는 단계가 `REPORT`가 아니면 미완료 경고와 시도하지 않은 도구를 싣도록 쓰여 있지만 단계를 옮긴 뒤에 읽어 이 경고는 실리지 않고 단계는 `REPORT`로 적힌다 [23].
단계와 시도 기록은 프로세스 메모리에만 있어 서버를 다시 시작하면 단계가 `COLLECTION`으로 돌아간다 [12].

### P03.03 미조사 범위·생략 사유 보고

**구현.** `get_coverage_gaps`는 연산 명세의 도구 가운데 성공하지 않은 도구를 빈 곳으로 돌려준다 [24].
보고·수집 분류는 빼고 항목마다 분류, 설명, 중요도, 모자란 능력 `missingCapabilities`를 싣는다 [25].
기준 목록과 켜진 경로의 분류를 앞에, 실행할 수 있는 도구를 앞에, 중요도가 높은 도구를 앞에 둔다 [25].
`suggest_next_action`은 그 앞 3개를 `top_gaps`로, 남은 기준 도구를 `remaining_steps`로 싣는다 [4].
서버 안 처리기는 재료가 되는 앞선 출력이 없으면 무엇을 먼저 불러야 하는지 응답에 적는다 [8].

**한계.** 빈 곳 목록은 실패한 도구와 부르지 않은 도구를 구별하지 않는다 [25].
`overall_coverage`는 실패한 도구를 실행 환경에 실행 파일이 없는 경우로 보고 분모에서 빼지만 실패 원인을 보지 않는다 [6].
`INVESTIGATE` 단계는 요구 능력을 만들 도구가 이미 시도됐거나 없는 기준 도구를 건너뛰고 응답에 건너뛴 도구와 사유를 싣지 않는다 [15].
서버 안 처리기가 재료 없이 성공으로 돌려준 도구는 빈 곳 목록에서 빠진다 [8][25].
P03.02에서 본 대로 보고서의 시도하지 않은 도구 목록도 실리지 않는다.
모델이 대상별 진행을 적는 도구는 없어 P03.04에는 연결하지 않는다.
