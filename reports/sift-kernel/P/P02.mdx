# P02 다음 작업 결정

### P02.01 고정 문서·프로필 반환

**구현.** 커널 도구 `get_investigation_protocol`은 조사 절차 문서를 코드 안의 고정 문자열로 돌려준다 [1].
문서는 분류 도구를 부르는 법, 마운트에서 보고서까지의 차례, 분류별 연산 목록과 규칙을 적고 `suggest_next_action`이 알려 주는 연산을 그대로 따르라고 한다 [1].
MCP 리소스 `forensic://methodology/windows-ir`·`forensic://methodology/memory-analysis`·`forensic://artifact-types`는 코드 상수를 그대로 돌려준다 [2][3].
앞의 둘은 Windows 사고 대응과 메모리 분석의 단계를 차례로 적은 문서다 [3].
네 번째 리소스 `forensic://investigation/state`는 단계·능력·범위 비율·발견사항 수만 돌려주고 작업을 권하지 않는다 [2].
MCP 프롬프트 `start_investigation`·`quick_triage`·`deep_analysis`도 고정 문자열이다 [4].
`start_investigation`은 `suggest_next_action`을 불러 권고를 따르고 `READY_FOR_REPORT`가 나올 때까지 되풀이하라고 적는다 [5].
`quick_triage`는 마운트·무결성 확인 뒤 Windows 산출물 연산의 차례를, `deep_analysis`는 빈 곳이 가장 큰 분류 하나를 끝까지 보라는 차례를 적는다 [6].
`list_workflows` 응답의 `hint`도 분류 도구를 부르는 법을 적은 고정 문구다 [7].
이 문서와 프롬프트는 증거 종류나 조사 상태에 따라 바뀌지 않는다 [1][3][4].

**예외.** `start_investigation`은 상태 기계가 `REPORT`에 이르지 않으면 `generate_report`가 호출을 거부한다고 적는다 [5].
같은 프롬프트는 풀리지 않은 가설이 보고서 생성을 막는다고 적는다 [5].
`generate_report`는 발견사항이 하나도 없고 요구 능력을 채운 기준 도구가 남은 경우에만 거부하고 그 밖에는 상태 기계를 `REPORT`로 옮겨 보고서를 만든다 [8].
`generate_report`는 가설 상태를 보지 않는다 [8].

### P02.02 규칙·조사 상태로 추천

**구현.** 다음 작업은 방법론 상태 기계 `MethodologyTracker`가 정한다 [9].
상태 기계는 `COLLECTION`·`TRIAGE`·`CLASSIFY`·`INVESTIGATE`·`TIMELINE`·`CORRELATE`·`REPORT` 단계마다 정해진 도구나 남은 기준 도구를 권한다 [9].
`INVESTIGATE` 단계의 후보는 증거 종류별 기준 도구 목록과 도구 출력에서 감지한 신호가 켠 조사 경로의 도구다 [10].
켜진 조사 경로의 분류에 속한 도구를 먼저, 그 안에서는 필수 도구를 먼저 권한다 [11].
이미 성공하거나 실패한 도구는 건너뛰고 요구 능력이 모자라면 그 능력을 만드는 도구를 대신 권한다 [11].
신호는 성공한 연산의 원래 출력을 소문자로 바꿔 신호별 낱말이 들어 있는지로 정한다 [12].

커널 도구 `suggest_next_action`은 이 권고와 함께 상태 기계 단계, 켜진 조사 경로, 감지한 신호, 단계 진행, 빈 곳 3개, 남은 기준 도구를 돌려준다 [13].
빈 곳 도구와 상태 기계 권고는 추론 엔진의 기대 자유 에너지 점수로 다시 매기고 다른 도구가 다음 후보보다 0.1 넘게 낮으면 권고를 그 도구로 바꾼다 [14].
권고에는 분류 도구로 부르는 모양 `call_as`가 붙고 온톨로지에 그 도구 항목이 있으면 판단 기준 `directive`가 붙는다 [13][15].
`suggest_next_action`은 지금 단계와 권고 도구에 맞는 workflow를 켜지만 도구 목록은 workflow와 관계없이 늘 모든 도구를 보인다 [16].
분류 연산의 응답마다 같은 상태 기계 권고가 `suggested_next_actions`로 붙고 요구 능력이 모자라 거부한 응답에도 권고가 실린다 [17][18].
서버의 권고 추종 집계는 공통 실행 경로 응답에 실은 상태 기계 권고만 기억해 다음 호출의 도구와 비교한다 [19].
`suggest_next_action`의 기대 자유 에너지 대체 권고는 집계에 기록되지 않아 모델이 그 권고를 따르면 이탈로 세어진다 [19][20].

상태를 보고 권고 문구를 만드는 커널 도구가 셋 더 있다.
`get_questions_to_investigate`는 능력 단계, 빈 곳 앞 3개, 근거가 하나뿐인 발견사항으로 조사 질문을 만든다 [21].
`corroborate_finding`은 발견사항의 근거 호출이 속하지 않은 분류에서 정해진 차례로 첫 도구를 3개까지 권한다 [22].
이 권고는 증거 종류를 보지 않아 Linux 이미지의 발견사항에도 Windows 레지스트리 분류의 첫 도구를 권할 수 있고 그 도구가 신뢰도를 `CONFIRMED`로 올린다고 적는다 [22].
`get_investigation_health`는 범위 비율, 근거가 하나뿐인 발견사항 수, 충돌 수로 권고 문구를 만든다 [23].
`challenge_finding`은 발견사항과 관계없이 정해 둔 반증 전략 3개를 돌려준다 [22].
`challenge_finding`이 권하는 `detect_anti_forensics_summary`는 연산 명세에 없는 이름이다 [22][24].
이 권고들은 응답 내용이고 권고를 따르지 않은 호출을 막는 일은 T03에서 본다.
서버 안에서 모델을 불러 계획을 세우는 경로는 없어 P02.03에는 연결하지 않는다.

**예외.** 메모리 덤프와 네트워크 캡처를 마운트하는 분기는 증거 종류를 상태 기계에 넘기지 않는다 [25].
상태 기계는 자기가 가진 증거 종류로 분류 단계를 건너뛸지 정하므로 메모리 덤프와 캡처에도 `list_partitions`·`list_directory`·`search_filename`과 Windows 기준 도구를 권한다 [9][26].
P01.02에서 본 대로 마운트 명령이 성공해 파일 시스템을 판별하지 않은 디스크 이미지와 파일 시스템을 알 수 없는 이미지도 Windows 기준 목록을 따른다 [27].

신호 낱말에는 `svchost`·`lsass`·`csrss` 같은 Windows 기본 프로세스 이름과 `SAM`·`password`·`history`·`archive` 같은 흔한 낱말이 들어 있다 [12].
비교가 부분 문자열이라 Windows 시스템 폴더 목록처럼 악성 징후가 없는 출력에서도 `MALWARE_INDICATORS`·`CREDENTIAL_ACCESS` 같은 신호가 켜질 수 있다 [12].
응답은 이 신호를 `observed_signals`에, 켠 경로를 `active_investigation_paths`에 싣고 권고 이유 앞에 `Malware & Persistence Analysis` 같은 경로 이름을 붙인다 [10][13].

  private investigateCandidates(): readonly { tool: string; reason: string; critical: boolean }[] {
    const out: { tool: string; reason: string; critical: boolean }[] = [];
    const seen = new Set<string>();
    // 1. Comprehensive baseline — evidence-type-aware, every investigation.
    for (const b of this.getBaseline()) {
      out.push({ tool: b.tool, reason: `[Baseline · ${b.category}] ${b.reason}`, critical: true });
      seen.add(b.tool);
    }
    // 2. Signal-driven depth — extra tools from paths the evidence activated.
    for (const path of [...this.getActivePaths()].sort((a, b) => a.priority - b.priority)) {
      for (const t of path.tools) {
        if (seen.has(t.tool)) continue;
        out.push({ tool: t.tool, reason: `[${path.name}] ${t.reason}`, critical: t.critical });
        seen.add(t.tool);
      }
    }
