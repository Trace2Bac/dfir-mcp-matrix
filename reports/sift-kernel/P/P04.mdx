# P04 조사 문맥 관리

### P04.05 세션·프로세스 상태 분리

**구현.** 서버에는 사건 ID가 없고 조사를 묶는 단위는 서버 프로세스와 그 출력 폴더다 [1][2].
기본인 stdio 전송은 프로세스에 서버 하나를 만들고 능력·방법론 상태·발견사항·가설을 그 프로세스 메모리에 따로 둔다 [3][4].
출력 폴더는 시작 인자 `--output`이고 주지 않으면 현재 작업 폴더의 `sift-output`이다 [1].
호출 기록 DB `ledger.db`, 원래 출력 폴더 `raw/`, 외부 도구의 작업 폴더가 모두 이 폴더에 놓인다 [1][2].
보고서는 같은 폴더에 이미지 파일 이름과 만든 시각으로 이름을 지어 쓴다 [5].
사용자가 조사마다 다른 `--output`으로 서버를 실행해야 조사 자료가 나뉜다 [1].
호출 기록 항목에는 사건이나 세션을 가리키는 필드가 없다 [6].
문서는 조사 세션마다 고유 ID를 주고 호출 기록 항목에 세션 ID를 남긴다고 적지만 기준 커밋 코드에는 세션 ID를 만들거나 기록하는 곳이 없다 [6][7].
그래서 P04.01~P04.03에는 연결하지 않고 서버가 사건마다 폴더·DB를 나누는 장치도 없어 P04.04에도 연결하지 않는다.

**예외.** 같은 출력 폴더로 서버를 다시 시작하면 앞 조사의 `ledger.db`를 그대로 이어 쓴다 [8].
서버 안 처리기는 호출 기록 전체 항목의 원래 출력을 재료로 받으므로 앞 조사에서 다른 이미지를 읽은 출력도 이번 분석에 들어간다 [9].
`reset_investigation`은 호출 기록 행과 메모리 상태를 지우지만 `raw/`·보고서·추출 파일과 조사 상태의 이미지 경로는 남긴다 [10].
이미지 안의 파일을 꺼낸 파일 이름은 `extracted_<inode>_<파일 이름>`이라 같은 폴더에서 다른 이미지의 같은 inode·이름이면 같은 경로를 쓴다 [11].
백그라운드 작업은 `reset_investigation` 뒤에도 계속 돌아 출력 폴더에 결과 파일을 쓴다 [12][10].
마운트 명령의 대상 `/mnt/ewf/`·`/dev/nbd0`·`/mnt/aff/`·`/mnt/evidence/`는 고정 경로라 같은 호스트의 서버 프로세스들이 함께 쓴다 [13].

### P04.07 요청마다 새로 생성

**구현.** HTTP 전송(`--transport http`)은 HTTP 요청마다 새 전송 객체와 새 서버를 만든다 [14].
새 서버는 능력, 방법론 상태, 발견사항, 가설, 백그라운드 작업 목록을 새로 만든다 [3].
HMAC 키도 환경변수 `SIFT_KERNEL_HMAC_SECRET`이 없으면 서버를 만들 때마다 새 난수로 정한다 [15].
같은 출력 폴더의 `ledger.db`와 `raw/`는 요청마다 다시 열어 요청 사이에 이어진다 [2][8].
기본인 stdio 전송은 프로세스에 서버 하나를 만들어 이 경로에 해당하지 않는다 [4].

**예외.** 주석은 세션마다 전송과 서버를 만든다고 적지만 코드는 HTTP 요청마다 만든다 [14].
전송 객체는 `sessionIdGenerator`를 준 세션 모드로 만든다 [14].
MCP SDK 1.29.0의 이 전송은 초기화 요청을 받지 않은 객체에 초기화가 아닌 요청이 오면 400 `Server not initialized`로 거부한다 [16].
그래서 초기화 다음의 도구 목록·도구 호출 요청은 새로 만든 전송 객체에서 거부되어 서버에 닿지 않는다 [14][16].

### P04.08 프로세스 메모리에만 보관

**구현.** 능력 집합, 방법론 상태 기계, 켠 workflow, 추론 엔진, 발견사항, 가설, 조사 상태(이미지 경로·파티션 오프셋·증거 종류), 권고 추종 집계, 백그라운드 작업 목록은 서버 객체 안의 변수다 [3].
HMAC 키도 환경변수가 없으면 서버 객체를 만들 때 정한 난수다 [15].
이 상태에는 유효 시간이나 개수 한도가 없고 프로세스가 끝나면 사라진다 [3].
발견사항과 가설은 메모리에만 있어 다시 시작한 서버의 보고서에는 앞 프로세스에서 등록한 발견사항이 없다 [3][17].

### P04.09 조사 상태를 파일·DB에 저장

**구현.** 호출 기록은 출력 폴더의 SQLite DB `ledger.db`의 `ledger` 표에 들어간다 [8][18].
항목마다 도구, 인자, 출력 해시, 원래 출력 경로, 시각, 앞 항목 해시, 그때 가진 능력, 성공 여부, 오류 문구가 남는다 [6][18].
원래 출력은 `raw/` 아래 항목 ID 이름의 파일로 쓰고 같은 이름의 파일이 있으면 덮어쓰지 않는다 [19].
백그라운드 작업의 출력, 이미지에서 꺼낸 파일, 보고서도 출력 폴더의 파일로 남는다 [12][11][5].
같은 DB에 `findings`·`hypotheses`·`investigation_state`·`methodology_state` 표와 저장 함수가 있지만 기준 커밋에서 그 저장 함수를 부르는 곳이 없어 표는 비어 있다 [17].
능력·방법론 상태·발견사항·가설은 P04.08에서 본 대로 파일·DB에 쓰지 않는다.

### P04.10 재시작 뒤 자동 복구

**구현.** 서버를 같은 출력 폴더로 다시 시작하면 `SqliteLedgerStore`가 있는 `ledger.db`를 열고 표가 있으면 그대로 쓴다 [8].
새 호출 기록 항목은 DB의 마지막 항목 해시를 이어 받는다 [20].
`register_finding`은 DB에 있는 모든 항목 ID를 근거로 받으므로 앞 프로세스의 호출도 발견사항의 근거로 쓸 수 있다 [21].
서버 안 처리기도 앞 프로세스 항목의 원래 출력을 읽는다 [9].
능력·방법론 상태·발견사항·가설은 되살리지 않아 모델이 `mount_evidence`와 `verify_integrity`를 다시 불러야 분석 연산을 쓸 수 있다 [3].
`MethodologyTracker.restoreState`는 주석에 세션 재개용이라고 적혀 있지만 부르는 곳이 없다 [22].

**예외.** 시작 인자 `--fresh`를 주면 출력 폴더를 통째로 지우고 시작해 이어 쓸 기록이 없다 [1].
README와 사용 안내의 MCP 클라이언트 설정 예시에 `--fresh`가 들어 있어 클라이언트가 그 설정으로 서버를 실행할 때마다 기록이 지워진다 [23].
