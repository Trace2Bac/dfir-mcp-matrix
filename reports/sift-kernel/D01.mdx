# D01 파생물 보관

### D01.01 도구 출력 파일 저장

**구현.** 분류 도구 연산의 공통 실행 경로와 `mount_evidence`가 호출마다 원래 출력을 파일로 남긴다 [1][2].
서버는 출력 폴더(`--output`, 주지 않으면 현재 작업 폴더의 `sift-output`) 아래 `raw` 폴더를 원래 출력 저장소로 연다 [3].
공통 실행 경로는 호출 기록 항목을 만든 뒤 그 항목 ID로 원래 출력 문자열을 `raw/<항목 ID>.json`에 쓴다 [2][4].
파일 이름의 확장자는 `.json`이지만 내용은 도구 출력 문자열 그대로다 [4].
저장소는 임시 파일에 쓴 뒤 이름을 바꾸고 같은 이름의 파일이 이미 있으면 쓰지 않는다 [4].
외부 도구 연산은 표준 출력을, 서버 안 처리기 연산은 처리기가 돌려준 JSON 문자열을 원래 출력으로 삼는다 [5][6].
외부 실행이 실패하면 빈 문자열을 남기고 오류 문장은 호출 기록 항목의 `errorMessage`에만 들어간다 [5][2].
regipy 연산은 표준 출력 대신 regipy가 쓴 결과 파일 `regipy_out.json`의 내용을 원래 출력으로 삼는다 [5].

파서를 거친 결과는 응답에만 실리고 파일이나 DB에 남지 않는다 [2].
호출 기록 행에는 그 결과의 해시와 원래 출력 파일 경로만 들어가므로 D01.03·D01.04에는 연결하지 않는다 [2][7].
SQLite 파일에 `findings` 테이블과 저장 함수 `saveFinding`이 정의돼 있지만 서버 코드는 그 함수를 부르지 않는다 [8].
발견사항 저장은 D05에서 본다.

비동기로 도는 `generate_timeline`·`carve_files`·`analyze_unallocated`·`recover_deleted`는 이 저장소를 쓰지 않는다 [9].
이 네 연산은 실행이 끝나면 표준 출력을 출력 폴더의 `async-<job ID>.txt`에 쓰고 앞 2,000자와 그 파일 경로를 서버 메모리의 job 목록에 둔다 [9].
이 파일 쓰기가 실패할 때의 처리는 D09에서 본다.

보관 기간·용량·대상을 정하는 설정이나 코드는 없어 D01.05에는 연결하지 않는다.
`--fresh`로 서버를 띄우면 출력 폴더 전체를 지우고 이 삭제는 P05에서 본다 [10].

**예외.** 원래 출력 파일에 도구 출력 전체가 남지 않는 연산이 있다.
성공한 외부 실행은 표준 출력만 남기고 표준 오류는 버린다 [5].
`search_filename`·재귀 `list_directory`·이벤트 로그 연산은 서버가 정한 줄 상한과 시간 제한을 받고 그 상한에서 끊긴 출력도 성공으로 처리돼 끊긴 부분까지만 남는다 [11][5].
`search_filename`은 `fls` 출력을 `pattern` 정규식으로 거른 뒤의 줄만 원래 출력으로 남긴다 [12].

### D01.02 도구가 만든 파생물 유지

**구현.** 서버가 출력 폴더 아래 쓰기 위치를 넣어 주는 외부 도구 연산, 이미지에서 파일을 꺼내는 경로, 보고서 생성이 파일 파생물을 남긴다 [13][14][15].
`recover_deleted`(`tsk_recover`)는 `recovered/`, `carve_files`(`foremost`)는 `carved/`, `analyze_unallocated`(`bulk_extractor`)는 `be_out/`에 결과 파일을 쓴다 [13].
`generate_timeline`(`log2timeline`)은 Plaso 저장 파일 `timeline.plaso`를 쓰고 `filter_timeline`·`get_timeline_context`가 그 파일을 읽는다 [13].
`parse_srum`은 `srum_export/`를, Zimmerman 도구를 부르는 연산(`parse_prefetch`·`parse_amcache` 등)은 출력 폴더를 CSV 출력 위치로 받는다 [16].
서버는 Zimmerman 도구의 CSV를 읽지 않고 그 도구의 표준 출력만 원래 출력으로 남기므로 분석 결과는 CSV 파일에만 있다 [16][5].
`dump_process`는 출력 위치 인자 없이 Volatility를 실행하고 실행기의 작업 폴더가 출력 폴더라서 덤프 파일이 그 폴더에 생긴다 [17].
이벤트 로그·레지스트리 연산은 이미지 안 경로를 받으면 `icat`으로 파일을 꺼내 출력 폴더의 `extracted_<inode>_<이름>`에 쓰고 그 파일을 분석한다 [14].
`generate_report`는 마크다운·HTML·JSON 보고서를 출력 폴더에 쓴다 [15].
서버는 이 파일들을 호출 뒤에 지우지 않는다.
regipy 결과 파일 `regipy_out.json`만 읽은 뒤 지우고 그 내용은 D01.01의 원래 출력 파일로 남는다 [5].
`extract_files_from_pcap`은 출력 폴더가 아니라 조사 상태의 증거 경로 뒤 `pcap_export/`(증거 경로가 비면 `/tmp/pcap_export/`)를 `tshark` 내보내기 위치로 넘기고 그 위치는 E03·D04에서 본다 [18].

**예외.** 실행마다 같은 경로에 쓰는 파생물은 다시 실행할 때 앞 실행의 파일이 남는지 서버가 정하지 않는다 [13][16].
`timeline.plaso`·`recovered/`·`carved/`·`be_out/`·`srum_export/`는 실행마다 같은 경로이고 앞 결과를 둘지, 덮어쓸지, 실행을 거부할지는 외부 도구의 동작에 달렸다 [13][16].
이 외부 도구들은 의존성 파일에 버전이 없어 그 동작을 확인하지 못했다.
같은 inode와 이름의 파일을 다시 꺼내면 `extracted_<inode>_<이름>`을 새로 열어 앞 파일을 덮어쓴다 [14][19].
Zimmerman 도구의 CSV, Volatility 덤프 파일, `esedbexport` 결과의 파일 이름은 외부 도구가 정해 출력 폴더에 무엇이 얼마나 남는지 서버 코드로 확인하지 못했다 [16][17].
다시 실행할 때 앞 파생물과 구분하는 방식은 D04에서 본다.
