# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 분류 도구는 `operation`이 없거나 목록에 없으면 `MISSING_OPERATION`·`INVALID_OPERATION`과 MCP 오류 결과 `isError`를 돌려준다 [1].
능력이 모자란 `CAPABILITY_BLOCKED`, 마운트 실패 `MOUNT_FAILED`, 발견사항 등록 거부도 `error` 값과 `isError`를 싣는다 [2].
연산이 실패하면 서버는 응답 전체에 `error`를 더하고 `isError`를 참으로 둔다 [3].
외부 실행이 출력 없이 시간 제한에 걸리거나 0이 아닌 종료 코드로 끝나면 실행기는 오류를 돌려주고 서버는 그 메시지를 `error`에 넣는다 [4][5].
시간 초과와 종료 코드 실패는 `error`의 문장으로만 갈린다 [5].

비동기 연산 4개는 `ASYNC_JOB_STARTED` 상태와 job ID를 돌려준다 [6].
`get_job_status`는 job마다 `running`·`completed`·`failed` 가운데 하나를 `status`에 싣고 없는 job이면 `isError`를 돌려준다 [6].
커널 도구 가운데 `trace_provenance`·`corroborate_finding`·`challenge_finding`은 없는 발견사항이면 `error` 값만 싣고 `isError`는 쓰지 않는다 [7].
`generate_report`도 조사가 끝나지 않았으면 `INVESTIGATION_INCOMPLETE`를 `error`에 싣고 `isError`는 쓰지 않는다 [7].

시간 초과나 부분 완료를 가르는 상태 값은 없어 R03.04에는 연결하지 않는다 [4][5].
`hashdeep -r`·`fls -r`·`yara -r`처럼 여러 입력을 훑는 연산에도 입력별 성공·실패 목록은 없고 성공한 실행의 표준 오류는 응답에 싣지 않아 R03.03에는 연결하지 않는다 [4].

**한계.** 줄 상한이나 시간 제한에 걸려 끊긴 실행도 그때까지의 출력이 있으면 실행기가 종료 코드 -1과 출력을 돌려준다 [8].
서버는 이 결과를 성공으로 처리해 `isError`도 끊겼다는 값도 싣지 않는다 [4].

비동기 job은 실행기가 결과를 돌려주면 종료 코드를 보지 않고 `completed`로 적는다 [6].
그래서 5분 시간 제한에 걸려 끊긴 job도 출력이 있으면 `completed`가 된다 [6][8].

서버 안 처리기는 결과 글과 함께 성공 여부를 돌려주는데 몇몇 처리기는 실패를 돌려주면서 오류 문장 `error`를 채우지 않는다 [9].
서버는 `error`가 비어 있으면 실패한 호출도 `isError` 없는 보통 응답으로 돌려준다 [3][10].
`compare_timelines`·`detect_timeline_anomalies`·`get_timeline_statistics`와 데이터베이스를 뽑은 뒤의 브라우저 연산이 이 경로를 탄다 [9].
이 호출은 호출 기록에 실패로 남는다 [10].

### R03.02 찾지 못함과 실패 구분

**구현.** 서버 안 처리기는 결과 JSON의 `result`에 상태 값을 적는다 [11].
재료가 될 앞선 출력이 없으면 `no_data`·`no_event_data`·`no_timeline` 같은 값을, 살펴본 뒤 찾은 것이 없으면 `clean`·`no_hijacking_detected` 같은 값을 쓴다 [11].
예를 들어 `detect_timestomping`은 파일 메타데이터 출력이 없으면 `no_data`를, 비교한 결과 이상이 없으면 `clean`을 돌려준다 [11].
이 JSON은 기본 처리를 거쳐 `result.raw`의 문자열 값으로 응답에 실린다 [12].
외부 도구가 빈 출력으로 성공하면 서버는 `status`가 `completed`인 결과를 만들고 실패는 R03.01의 `isError`로 가른다 [3][13].

**한계.** `detect_timestomping`은 `list_directory` 출력도 재료로 세지만 시각 쌍은 `istat` 형식의 `$STANDARD_INFORMATION`·`$FILE_NAME` 절에서만 뽑는다 [11].
`list_directory` 출력만 있으면 비교할 쌍이 하나도 없어도 `clean`을 돌려준다 [11].
`detect_log_clearing`·`detect_log_gaps`는 `evtx_dump` JSONL에서 레코드를 뽑지 못해 늘 `clean`을 돌려준다 [14].

브라우저와 Linux 로그 연산은 처리기 결과가 다시 전용 파서를 거친다 [12].
`parse_browser_history`·`parse_browser_downloads`의 처리기는 데이터베이스를 뽑지 않았으면 `databases_not_extracted`를 담은 한 줄 JSON을 돌려준다 [15].
브라우저 파서는 그 줄을 `|`로 나눠 앞부분을 `timestamp`, 뒷부분을 `url`에 넣으므로 검색 정규식의 `|`에서 갈린 기록 한 건이 생긴다 [15][16].
`parse_auth_log`·`parse_syslog`의 처리기 결과 JSON은 syslog 줄 정규식에 맞지 않아 파서가 늘 빈 배열을 돌려준다 [17].
그래서 대상 파일을 뽑지 않았다는 `file_not_extracted`도, 뽑아서 읽은 결과도 응답에는 빈 `data`로만 나간다 [17].

### R03.05 실행 중 경과·생존 알림

**구현.** 서버는 오래 걸린다고 정한 연산 9개를 실행할 때 MCP 진행 알림 `notifications/progress`를 보낸다 [18].
알림은 시작할 때 0, 실행 파일을 부를 때 10, 파싱할 때 90, 끝나거나 실패할 때 100을 보낸다 [3][18].
이 값은 처리 단계에 붙인 고정 값이고 분석이 얼마나 진행됐는지를 재지 않는다 [18].
9개 가운데 `generate_timeline`·`carve_files`·`analyze_unallocated`는 비동기 연산이라 알림을 보내기 전에 job ID를 돌려준다 [6][18].

**한계.** MCP 규격은 진행 알림이 요청에서 받은 `progressToken`만 쓰도록 요구한다 [19].
서버는 요청의 `progressToken`을 읽지 않고 알림 다섯 곳 모두 토큰 자리에 연산 이름을 넣는다 [18][20].
클라이언트가 진행 알림을 요청하지 않은 호출에도 같은 알림을 보낸다 [20].
그래서 클라이언트가 보낸 토큰이 이 서버의 내부 연산 이름과 같을 때만 알림이 그 호출과 이어진다 [20].
그러려면 클라이언트가 이 서버의 연산 이름을 미리 알고 토큰으로 골라야 한다.
같은 연산을 동시에 부르거나 토큰을 보내지 않은 호출에서는 이어지지 않는다.
확인한 예로 MCP TypeScript SDK 1.29.0의 클라이언트는 요청 ID를 `progressToken`으로 보내고 받은 알림의 토큰을 숫자로 바꿔 그 요청의 처리기를 찾는다 [21].
연산 이름은 숫자로 바뀌지 않아 처리기를 찾지 못하고 SDK는 알림을 오류로 보고 버린다 [21].

export function executionError(
  tool: string,
  exitCode: number | null,
  stderr: string,
  timedOut: boolean,
): ExecutionError {
  const message = timedOut
    ? `Tool "${tool}" timed out`
    : `Tool "${tool}" exited with code ${exitCode}`;
  const guidance = timedOut
    ? `The tool took too long. Try with a smaller scope or increase timeout.`
    : `Check stderr for details: ${stderr.slice(0, 200)}`;
  // Mark as retriable if timedOut or if stderr hints at transient resource issues
  const retriable = timedOut || /EAGAIN|EBUSY|EIO|EMFILE|resource temporarily/i.test(stderr);
  return { kind: "EXECUTION_ERROR", tool, exitCode, stderr, timedOut, retriable, message, guidance };
}

  // Find prior fls/istat outputs that contain timestamp data

  if (istatEntries.length === 0) {

Run list_directory or get_file_metadata first to collect timestamp data for analysis.", suggestion: { tool: "list_directory", reason: "Collect filesystem timestamps for stomping detection" } }) };
  }

  // Extract timestamp pairs from raw istat outputs
  const pairs: TimestampPair[] = [];
  for (const entry of istatEntries) {
    const raw = ctx.rawOutputs.get(entry.id as string) ?? "";
    // Parse SI vs FN timestamps from istat output
    const siCreated = extractTimestamp(raw, "STANDARD_INFORMATION", "Created");
    const fnCreated = extractTimestamp(raw, "FILE_NAME", "Created");
    const siModified = extractTimestamp(raw, "STANDARD_INFORMATION", "Modified");
    const fnModified = extractTimestamp(raw, "FILE_NAME", "Modified");
    if (siCreated && fnCreated) {
      pairs.push({ siCreated, fnCreated, siModified: siModified ?? siCreated, fnModified: fnModified ?? fnCreated, filename: entry.tool, inode: entry.id as string });
    }
  }

  const anomalies = detectTimestomping(pairs);
  return { success: true, output: JSON.stringify({ result: anomalies.length > 0 ? "timestomping_detected" : "clean", anomalies_found: anomalies.length, details: anomalies, analyzed_entries: istatEntries.length }) };
