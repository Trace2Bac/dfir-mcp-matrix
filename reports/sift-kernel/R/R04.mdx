# R04 도구 결과 해석 주의

### R04.01 도구별 정적 주의

**구현.** 서버 코드의 `FORENSIC_GUIDANCE`는 연산 15개에 해석 주의 `caveat`와 교차 확인 도구 `corroborate_with`를 적는다 [1].
분류 도구 연산의 응답을 만들 때 서버는 연산 이름으로 이 표를 찾아 `forensic_context`의 `guidance`·`corroboration`으로 붙인다 [2][3].
예를 들어 `parse_shimcache`에는 ShimCache가 파일이 있었다는 것만 증명하고 실행은 증명하지 않는다는 주의가 붙는다 [1].
`parse_prefetch`에는 Prefetch가 없다고 실행하지 않은 것은 아니라는 주의가, `scan_yara`에는 알려진 패턴만 찾는다는 주의가 붙는다 [1].
주의 문구는 연산마다 하나로 고정돼 있다 [1][2].
표에 없는 연산과 커널 도구의 응답에는 주의가 없고 도구 설명에도 해석 한계 문구는 없다 [2][4].

**한계.** 표에 있는 `generate_timeline`은 비동기 연산이라 `forensic_context`를 붙이기 전에 job ID만 담은 응답을 돌려준다 [5].
job 결과를 조회하는 `get_job_status`도 주의를 붙이지 않는다 [6].
그래서 이 연산의 주의와 교차 확인 도구는 모델에게 가지 않는다 [1][5].

### R04.02 결과 조건별 주의

**구현.** 파서가 이상 징후를 찾으면 `forensic_context.guidance` 앞에 `⚠️ ANOMALIES DETECTED —`를 붙인다 [2].
이 표시는 `FORENSIC_GUIDANCE`에 있는 연산에만 붙는다 [2].

### R04.03 추가 확인 도구·증거 추천

**구현.** 분류 도구 연산의 응답에서는 `forensic_context.corroboration`이 확인할 다른 연산을 적는다 [1][2].
예를 들어 `list_directory`에는 `get_file_metadata`로 시각을 확인하라고 적는다 [1].
`parse_shimcache`에는 Prefetch나 Sysmon 이벤트로 실행을 확인하라고 적는다 [1].

커널 도구 `corroborate_finding`은 발견사항의 근거 호출이 속하지 않은 분류에서 분류마다 첫 연산 하나씩 3개까지 권한다 [7].
권하는 이유에는 다른 분류로 교차 확인하면 CONFIRMED로 오른다고 적는다 [7].
`challenge_finding`은 시간 대조·다른 설명·반증 이벤트 검색 3가지 전략과 그 도구를 돌려준다 [7].
`get_questions_to_investigate`는 근거가 하나뿐인 발견사항마다 더 확인할 수 있는지 묻는 문장을 싣고 `get_investigation_health`는 그런 발견사항에 `corroborate_finding`을 쓰라고 적는다 [8].

MCP 리소스 Windows IR 방법론은 보고 단계에 근거가 하나뿐인 발견사항을 교차 확인하라고 적고 메모리 분석 안내는 디스크 아티팩트와 대조하라고 적는다 [9].
MCP 프롬프트 `start_investigation`·`deep_analysis`도 약한 발견사항을 `corroborate_finding`으로 보강하고 다른 분류와 대조하라고 적는다 [10].
이 두 프롬프트는 사용자가 클라이언트에서 골라야 모델에게 전달된다.
서버는 지침 `instructions`를 두지 않는다 [11].
리소스와 프롬프트는 조사 단계와 할 일을 적고 부재가 무죄를 뜻하지 않는다 같은 조사 전체의 해석 원칙은 적지 않는다 [9][10].
부재를 어떻게 읽을지는 R04.01의 `parse_prefetch`·`detect_log_clearing` 주의와 아래 `directive`의 `ifAbsent`처럼 연산별로만 적는다 [1][12].

커널 도구 `suggest_next_action`은 다음에 부를 연산을 권할 때 그 연산의 온톨로지 항목에서 판단 기준 `directive`를 붙인다 [13][14].
`directive`에는 악성일 때와 정상일 때의 모습, 확인 기준, 확인됐을 때 할 일 `ifConfirmed`와 찾지 못했을 때 할 일 `ifAbsent`가 들어간다 [13].
`ifAbsent`에는 부재를 어떻게 읽을지에 관한 주의와 확인 권고가 들어 있다 [12].
예를 들어 `parse_prefetch` 항목은 실행 흔적이 없으면 실행하지 않았거나 Prefetch가 꺼졌거나 지워졌을 수 있다고 적는다 [12].
`parse_shimcache` 항목은 실행 파일이 ShimCache 기록 기간보다 먼저 있었을 수 있다고 적는다 [12].
EFE 점수로 다른 연산을 고르면 서버는 권고를 새로 만들고 `directive` 없이 연산과 이유만 싣는다 [14].
분류 도구 응답의 `suggested_next_actions`에는 연산, 이유, 우선순위, 부를 방법만 들어가고 `directive`는 없다 [15].

**한계.** `challenge_finding`이 권하는 `detect_anti_forensics_summary`는 능력 명세에 없는 이름이다 [7][16].
명세의 연산 이름은 `get_anti_forensics_summary`다 [16].
`challenge_finding`의 전략 3가지는 발견사항의 내용과 관계없이 늘 같다 [7].
`generate_timeline`의 교차 확인 도구는 R04.01의 한계와 같은 이유로 응답에 실리지 않는다 [5].

`detect_log_clearing` 항목의 `ifAbsent`는 로그가 온전하니 로그를 파싱하라는 "Logs intact" 문구를 적는다 [12].
그런데 이 탐지는 이벤트 로그 호출의 원래 출력이 `evtx_dump` JSONL이면 레코드를 하나도 읽지 못한 채 `clean`을 돌려준다 [17].
그래서 이 문구는 레코드를 하나도 읽지 못한 `clean` 결과도 로그가 온전하다는 뜻으로 읽게 한다 [12][17].
`list_directory` 온톨로지 항목은 넷이지만 서버는 연산 이름이 맞는 첫 항목만 고르므로 루트 폴더 항목의 `directive`만 붙고 Prefetch 폴더 항목의 부재 주의는 붙지 않는다 [13][18].

  function suggestCorroboration(finding: Finding): Array<{ tool: string; reason: string }> {
    const suggestions: Array<{ tool: string; reason: string }> = [];
    const existingCategories = new Set<string>();
    const allEntries = ledgerStore.getAllEntries();
    for (const evId of finding.evidence) {
      const entry = allEntries.find((e) => e.id === evId);
      if (entry) existingCategories.add(capabilityGraph.getCategory(entry.tool) ?? "");
    }
    // Suggest tools from categories NOT already used as evidence
    const allCategories: ArtifactCategory[] = ["filesystem", "timeline", "registry", "event_logs", "execution_artifacts", "persistence", "memory", "network"];
    for (const cat of allCategories) {
      if (!existingCategories.has(cat)) {
        const tools = capabilityGraph.getToolsByCategory(cat);
        if (tools.length > 0) {
          suggestions.push({ tool: tools[0]!.tool, reason: `Cross-reference with ${cat} evidence (would upgrade to CONFIRMED)` });
        }
      }
    }
    return suggestions.slice(0, 3);
  }

  const evtxEntries = ctx.ledgerEntries.filter(e => e.tool === "parse_event_log" || e.tool === "search_events");
  if (evtxEntries.length === 0) {
    return { success: true, output: JSON.stringify({ result: "no_data", message: "No event log data available. Parse event logs first.", suggestion: { tool: "parse_event_log", reason: "Collect event log data for gap analysis" } }) };
  }

  // Parse event records from raw outputs
  const records: EventRecord[] = [];
  for (const entry of evtxEntries) {
    const raw = ctx.rawOutputs.get(entry.id as string) ?? "";
    const parsed = parseEventRecords(raw);
    records.push(...parsed);
  }

  const gaps = detectLogGaps(records);
  return { success: true, output: JSON.stringify({ result: gaps.length > 0 ? "log_clearing_detected" : "clean", gaps_found: gaps.length, details: gaps, analyzed_records: records.length }) };
