# R04 해석 한계 안내

### R04.01 도구별 정적 주의

**구현.** 서버 코드의 `FORENSIC_GUIDANCE`는 연산 15개에 해석 주의 `caveat`와 교차 확인 도구 `corroborate_with`를 적는다 [1].
분류 도구 연산의 응답을 만들 때 서버는 연산 이름으로 이 표를 찾아 `forensic_context`의 `guidance`·`corroboration`으로 붙인다 [2][3].
예를 들어 `parse_shimcache`에는 ShimCache가 파일이 있었다는 것만 증명하고 실행은 증명하지 않는다는 주의가 붙는다 [1].
`parse_prefetch`에는 Prefetch가 없다고 실행하지 않은 것은 아니라는 주의가, `scan_yara`에는 알려진 패턴만 찾는다는 주의가 붙는다 [1].
주의 문구는 연산마다 하나로 고정돼 있다 [1][2].
표에 없는 연산과 커널 도구의 응답에는 주의가 없고 도구 설명에도 해석 한계 문구는 없다 [2][4].

**한계.** 표에 있는 `generate_timeline`은 비동기 연산이라 `forensic_context`를 붙이기 전에 job ID만 담은 응답을 돌려준다 [5].
job 결과를 조회하는 `get_job_status`도 주의를 붙이지 않는다 [6].
그래서 이 연산의 주의와 교차 확인 도구는 모델에게 가지 않는다 [1][5].

### R04.02 결과 조건별 주의

**구현.** 파서가 이상 징후를 찾으면 `forensic_context.guidance` 앞에 `⚠️ ANOMALIES DETECTED —`를 붙인다 [2].
이 표시는 `FORENSIC_GUIDANCE`에 있는 연산에만 붙는다 [2].

분류 도구 연산의 응답에는 추론 엔진 상태로 고른 `self_correction_trigger`가 붙는다 [7].
증거 충돌도가 0.3을 넘으면 우세 가설을 다시 보라는 `CONFLICT`를, 엔트로피가 멈추면 우세 가설을 반증해 보라는 `STUCK`을, 엔트로피가 늘면 새 가설을 세우라는 `DIVERGING`을 싣는다 [7].
앞의 세 경우가 아니고 편향 경고가 있으면 다른 설명을 생각해 보라는 `BIAS`를 싣는다 [7].
편향 경고 `bias_warnings`는 6번 이상의 조사 행동 가운데 75%를 넘는 수가 우세 가설을 겨누면 확증 편향 위험을 적고 그 가설을 반증할 도구를 권한다 [8].
anchoring 경고는 8번 이상의 조사 행동에서 첫 행동 뒤 행동의 85%를 넘는 수가 첫 행동과 같은 분류일 때 붙는다 [9].
tunnel vision 경고는 8번 이상의 조사 행동 뒤 한 번도 겨누지 않은 가설이 12개 가운데 3개 이상일 때 붙는다 [9].
행동이 겨눈 가설은 모델이 밝힌 의도가 아니라 서버가 호출 분류별 후보 가운데 지금 신념이 가장 높은 가설로 추정한 값이다 [10].
분류별 후보에는 `ransomware`와 `benign_anomaly`가 없어 이 두 가설은 늘 겨누지 않은 가설로 세어진다 [10].
그래서 8번째 조사 행동부터는 나머지 가설 10개를 모두 한 번 이상 겨누지 않는 한 tunnel vision 경고가 붙는다 [9][10].
실행 흔적 연산은 분류 이름 `execution_artifacts`가 대상 가설 표에 없어 대상 가설이 `null`이 되고 이 어긋남은 D06.03에서 본다 [10].
실패한 호출과 규칙이 발화하지 않은 호출도 행동 이력에 들어가 편향 계산에 쓰인다 [11].
이 문구들은 이번 호출의 출력을 합친 뒤의 추론 상태와 그때까지의 호출 이력으로 고른다 [7][8].

### R04.03 추가 확인 도구·증거 추천

**구현.** 분류 도구 연산의 응답에서는 `forensic_context.corroboration`이 확인할 다른 연산을 적는다 [1][2].
예를 들어 `list_directory`에는 `get_file_metadata`로 시각을 확인하라고 적는다 [1].
`parse_shimcache`에는 Prefetch나 Sysmon 이벤트로 실행을 확인하라고 적는다 [1].

커널 도구 `corroborate_finding`은 발견사항의 근거 호출이 속하지 않은 분류에서 분류마다 첫 연산 하나씩 3개까지 권한다 [12].
권하는 이유에는 다른 분류로 교차 확인하면 CONFIRMED로 오른다고 적는다 [12].
`challenge_finding`은 시간 대조·다른 설명·반증 이벤트 검색 3가지 전략과 그 도구를 돌려준다 [12].
`get_questions_to_investigate`는 근거가 하나뿐인 발견사항마다 더 확인할 수 있는지 묻는 문장을 싣고 `get_investigation_health`는 그런 발견사항에 `corroborate_finding`을 쓰라고 적는다 [13].

MCP 리소스 Windows IR 방법론은 보고 단계에 근거가 하나뿐인 발견사항을 교차 확인하라고 적고 메모리 분석 안내는 디스크 아티팩트와 대조하라고 적는다 [14].
MCP 프롬프트 `start_investigation`·`deep_analysis`도 약한 발견사항을 `corroborate_finding`으로 보강하고 다른 분류와 대조하라고 적는다 [15].
이 두 프롬프트는 사용자가 클라이언트에서 골라야 모델에게 전달된다.
서버는 지침 `instructions`를 두지 않는다 [16].
리소스와 프롬프트는 조사 단계와 할 일을 적고 부재가 무죄를 뜻하지 않는다 같은 조사 전체의 해석 원칙은 적지 않아 R04.05에는 연결하지 않는다 [14][15].
부재를 어떻게 읽을지는 R04.01의 `parse_prefetch`·`detect_log_clearing` 주의처럼 연산별로만 적는다 [1].

**한계.** `challenge_finding`이 권하는 `detect_anti_forensics_summary`는 능력 명세에 없는 이름이다 [12][17].
명세의 연산 이름은 `get_anti_forensics_summary`다 [17].
`challenge_finding`의 전략 3가지는 발견사항의 내용과 관계없이 늘 같다 [12].
`generate_timeline`의 교차 확인 도구는 R04.01의 예외와 같은 이유로 응답에 실리지 않는다 [5].

### R04.04 불확실성·추정 범위 표시

**구현.** 분류 도구 연산의 응답 `reasoning`에는 추론 엔진의 엔트로피·충돌도·수렴 상태와 우세 가설이 실린다 [7].
우세 가설은 가설 ID와 함께 Dempster-Shafer 신념 구간의 하한 `belief`와 상한 `plausibility`를 싣는다 [18].
`belief`가 0.01 이하면 우세 가설을 `null`로 둔다 [18].
수렴 상태는 성공하고 규칙이 하나 이상 발화한 호출에서만 갱신되고 그 밖의 호출의 응답은 앞 상태를 그대로 싣는다 [19].

서버 안 탐지 처리기의 결과 항목은 `confidence`(0~1)와 오탐 가능성 `falsePositiveRate`를 싣는다 [20].
예를 들어 타임스탬핑 탐지는 `$SI` 생성 시각이 `$FN`보다 앞서면 `confidence` 0.95와 `falsePositiveRate` `LOW`를 적는다 [21].
발견사항의 신뢰 등급도 서버가 근거 호출 수와 분류 수로 정해 `register_finding` 응답에 싣고 그 규칙은 D07.03에서 본다 [22].

**한계.** 탐지 처리기의 결과 JSON 글은 기본 처리를 거쳐 `result.raw`에 실리고 1만 자를 넘으면 잘린다 [23].
결과 항목이 많으면 뒤쪽 항목의 `confidence`·`falsePositiveRate`가 응답에 보이지 않는다 [20][23].

/** Confirmation bias: >75% of actions target the leading hypothesis */
function checkConfirmationBias(
  history: readonly ActionRecord[],
  leadingHypothesis: string | null
): BiasWarning | null {
  if (!leadingHypothesis || history.length < 6) return null;

  const targetingLeading = history.filter(a => a.targetedHypothesis === leadingHypothesis).length;
  const ratio = targetingLeading / history.length;

  if (ratio > CONFIRMATION_THRESHOLD) {
    const severity = ratio > 0.9 ? "HIGH" as const : "MEDIUM" as const;
    return {
      type: "confirmation" as BiasType,
      severity,
      description: `${(ratio * 100).toFixed(0)}% of ${history.length} actions target the leading hypothesis "${leadingHypothesis}". ` +
        `Confirmation bias risk: investigating only what supports the current theory.`,
      suggestion: `Test alternative hypotheses. Run tools that could DISPROVE "${leadingHypothesis}" — ` +
        `e.g., if hypothesis is "insider threat", check for external C2 indicators that would suggest APT instead.`,
    };
  }
  return null;

/** Anchoring: first finding drives 85%+ of subsequent actions */
function checkAnchoring(history: readonly ActionRecord[]): BiasWarning | null {
  if (history.length < 8) return null;

  // Check if the category of the first finding dominates subsequent actions
  const firstCategory = history[0]?.category;
  if (!firstCategory) return null;

  const subsequent = history.slice(1);
  const sameCategoryCount = subsequent.filter(a => a.category === firstCategory).length;
  const ratio = sameCategoryCount / subsequent.length;

  if (ratio > ANCHORING_THRESHOLD) {
    return {
      type: "anchoring" as BiasType,
      severity: "MEDIUM",
      description: `${(ratio * 100).toFixed(0)}% of actions remain in the "${firstCategory}" category. ` +
        `Anchoring risk: first finding may be overly influencing investigation direction.`,
      suggestion: `Broaden investigation scope. Consider other artifact categories: ` +
        `registry, event logs, network, user activity. The first finding may not be the most significant.`,
    };
  }
  return null;
}

export function computeConfidence(
  evidence: readonly LedgerEntryId[],
  getCategoryForEntry: (id: LedgerEntryId) => ArtifactCategory | undefined,
): ConfidenceLevel {
  if (evidence.length === 0) return "HYPOTHESIZED";

  // Check if evidence comes from different artifact categories
  const categories = new Set<ArtifactCategory>();
  for (const id of evidence) {
    const cat = getCategoryForEntry(id);
    if (cat) categories.add(cat);
  }

  if (categories.size >= 2) return "CONFIRMED";
  return "SUPPORTED";
}
