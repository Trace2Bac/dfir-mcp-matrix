# R01 도구 출력 가공

### R01.01 가공 없이 전달

**구현.** 분류 도구의 연산은 외부 도구의 표준 출력을 `parseToolOutput`에 넘기고 그 결과의 `data`를 응답의 `result`에 싣는다 [1][2].
전용 파서가 없는 연산은 기본 처리로 가고 기본 처리는 출력 글을 `data.raw`에 그대로 담는다 [3].
전용 파서 13개가 맡는 연산은 코드에 정해져 있다 [4].
`extract_file`(`icat`)·`extract_strings`와 `list_processes`·`scan_memory_yara`를 뺀 Volatility 연산이 기본 처리를 받는다 [4].
그래서 이 연산들의 응답에는 외부 도구가 낸 글이 서버가 바꾸지 않은 채 `result.raw`로 실린다 [2][3].
기본 처리가 출력을 1만 자에서 자르는 것은 R02에서 본다.

**한계.** 실행기 `ProcessExecutor.execute`는 외부 도구의 표준 출력 바이트를 모두 UTF-8 문자열로 바꾼 뒤 넘긴다 [5].
`extract_file`은 `icat`이 내보내는 이미지 안 파일의 내용을 이 경로로 받는다 [6].
그래서 이진 파일의 바이트 가운데 UTF-8로 읽히지 않는 바이트는 대체 문자 U+FFFD로 바뀌고 응답에는 바뀌었다는 표시가 없다 [5][6].

### R01.02 구조화 파싱·필드 선택

**구현.** 전용 파서는 `fls`·`mmls`·`istat`·Plaso·이벤트 로그·YARA·tshark·hashdeep·Volatility `pslist`·regipy·PECmd 출력과 브라우저·Linux 처리기의 결과를 필드로 나눈다 [4].
다만 `list_processes`를 비롯한 Volatility 연산 10개는 `--output json` 때문에 출력 폴더 안에 `json` 폴더가 없으면 실행 전에 실패해 이 파서와 기본 처리까지 가지 않는다 [7].
파서는 요약 `summary`, 건수 `recordCount`, 이상 징후 `anomalies`, 본문 `data`를 만든다 [3].
서버는 이 가운데 `data`와 `anomalies`만 응답에 싣는다 [1][2].
`fls` 파서는 줄마다 `type`·`inode`·`name`·`path`·`deleted`·`reallocated`를 만든다 [8].
`istat` 파서는 inode의 종류·크기·소유자와 시각 목록을 만든다 [9].
이벤트 로그 파서는 `evtx_dump` JSONL 줄에서 `eventId`·`timestamp`·`source`·`computer`·`user`·`recordId`·`channel`을 고르고 `EventData`를 JSON 글로 바꾼 앞 500자와 원래 줄 앞 1000자를 함께 둔다 [10].
regipy 파서는 플러그인 결과 JSON의 항목을 `key`·`value`·`data`·`timestamp`·`type`으로 옮긴다 [11].

**한계.** `list_directory`·`search_filename`은 `fls`를 `-l`과 함께 부른다 [12].
Sleuth Kit은 `-l` 출력에서 이름 뒤에 탭으로 시각 4개와 크기·gid·uid를 붙인다 [13].
`fls` 파서의 정규식은 콜론 뒤의 나머지 글을 모두 이름으로 읽으므로 `name`·`path`에 이 열들이 함께 들어간다 [8].
이름이 `.exe`·`.dll` 같은 확장자로 끝나는지 보는 의심 실행 파일 검사는 값이 uid 숫자로 끝나므로 이 줄들을 골라내지 못한다 [8].

`filter_timeline`은 `psort`를 `-o l2tcsv`로 부른다 [14].
Plaso의 l2tcsv 출력은 date·time·timezone·MACB·source 차례의 열 이름 줄로 시작한다 [15].
Plaso 파서는 JSON이 아닌 줄을 쉼표로 나눠 첫째 열을 `timestamp`, 둘째 열을 `timestampDesc`, 셋째 열을 `source`, 넷째 열을 `sourceLong`, 다섯째 열을 `filename`에 넣고 나머지를 `message`로 잇는다 [16].
그래서 `timestamp`에는 날짜만, `timestampDesc`에는 시각이, `source`에는 시간대가, `filename`에는 source 약칭이 들어간다 [15][16].
열 이름 줄도 사건 하나로 들어간다 [15][16].

regipy 파서는 플러그인 결과가 배열일 때만 항목으로 옮긴다 [11].
regipy 6.2.1의 `timezone_data`·`shutdown` 플러그인은 결과를 제어 집합 키 경로를 키로 하는 `dict`로 낸다 [17].
`get_system_config`는 경로를 주지 않으면 SYSTEM 하이브에 이 두 플러그인을 실행한다 [18].
두 플러그인의 결과는 응답의 `entries`에 들어가지 않고 빠졌다는 표시도 없다 [11].

브라우저·Linux 로그 연산은 서버 안 처리기가 낸 한 줄 JSON을 줄 단위 글을 읽는 전용 파서에 넘긴다 [19].
그래서 처리기의 상태 값이 엉뚱한 필드에 들어가거나 결과가 빈 배열이 되며 이것은 R03.02에서 본다.

### R01.03 형식 변환·집계

**구현.** 파서는 레코드를 세거나 묶어 이상 징후를 만들고 서버는 이것을 응답의 `anomalies`에 싣는다 [2].
`fls` 파서는 삭제된 파일 수를, 이벤트 로그 파서는 로그 삭제·서비스 설치·로그온 실패 이벤트 수를 센다 [8][20].
`mmls` 파서는 미할당 영역의 비율을, hashdeep 파서는 같은 해시를 가진 경로를 묶는다 [20].

매핑이 없는 연산은 서버 안 처리기가 맡는다 [21].
서버는 그때까지의 호출 기록 항목과 그 원래 출력을 모두 읽어 처리기에 넘긴다 [21].
처리기는 앞선 호출의 원래 출력을 다시 훑어 건수와 판정을 만든다.
예를 들어 `detect_log_clearing`은 이벤트 로그 출력에서 레코드를 뽑아 레코드 번호의 빈 구간을 찾는다 [22].
처리기 결과는 기본 처리를 거쳐 JSON 글 그대로 `result.raw`에 실린다 [3][21].

**한계.** 이벤트 로그 출력을 다시 읽는 `parseEventRecords`는 `Event ID:`·`Record number:` 꼴의 글 줄을 찾는다 [22].
`parse_event_log`·`search_events`의 원래 출력은 `evtx_dump`의 JSONL이고 이벤트 로그 파서는 그 키 `EventID`·`EventRecordID`에서 값을 꺼낸다 [10].
JSON 글에서는 `EventID` 바로 뒤에 따옴표가 오므로 정규식 `Event\s*(?:ID|identifier):`에 맞지 않는다 [22].
JSONL에는 레코드를 가르는 빈 줄도 없다 [22].
그래서 `detect_log_clearing`과 같은 처리를 쓰는 `detect_log_gaps`는 `analyzed_records`가 0인 채 `clean`을 돌려준다 [22].
`get_security_summary`도 이벤트 로그 호출의 원래 출력에 같은 정규식을 대므로 원래 출력이 `evtx_dump` JSONL이면 `event_id_distribution`과 `notable`이 빈 채로 돌아간다 [23].

### R01.05 가공 사실·대상 표시

**구현.** 분류 도구 연산의 응답에는 `inference_constraint`가 붙는다 [24].
이상 징후가 있으면 서버가 파싱과 이상 탐지를 해 해석한 자료라는 L4 문구를, 없으면 원래 출력을 파싱해 JSON으로 바꿨다는 L3 문구를 적는다 [24].
응답의 `ledger_entry_id`는 원래 출력을 저장한 파일의 이름이다 [25].
저장한 원래 출력을 읽어 주는 도구가 없다는 것은 R02에서 본다.
`mount_evidence`를 비롯한 커널 도구의 응답에는 이 표시가 없다 [24].

**한계.** 문구는 이상 징후가 있는지로만 고른다 [24].
기본 처리로 출력 글을 그대로 담은 응답에도 typed JSON으로 파싱했다는 L3 문구가 붙는다 [3][24].
서버 안 처리기의 결과에도 같은 문구가 붙어 그 결과가 외부 도구 출력이 아니라 앞선 호출의 원래 출력이나 등록된 발견사항으로 서버가 만든 것이라는 사실이 드러나지 않는다 [21][24].
처리기 결과는 재료로 쓴 호출 기록 항목의 ID를 대개 싣지 않고 `analyzed_entries` 같은 건수만 싣는다 [26].
