# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 결과 항목에 증거 파일 경로가 실리는 연산은 `scan_yara`다 [1].
`scan_yara`는 마운트한 증거 이미지 경로를 YARA의 검사 대상으로 넘긴다 [1].
YARA는 일치마다 규칙 이름과 검사한 파일 경로를 한 줄에 출력한다 [2].
YARA 파서는 그 줄의 마지막 부분을 일치 항목의 `file`에 넣는다 [3].

다른 분류 도구 연산의 응답에는 증거 이미지를 가리키는 필드가 없다 [4].
서버는 증거 이미지 경로를 조사 상태에서 꺼내 실행 인자를 만들 때만 붙인다 [5].
응답의 `ledger_entry_id`로 찾는 호출 기록 항목의 `params`는 모델이 준 인자와 서버가 바꾼 인자만 담고 증거 이미지 경로는 담지 않는다 [6].
증거 이미지 경로는 `mount_evidence`의 응답과 그 호출 기록 항목에만 있다 [7].

서버가 모델에게 주는 참조 지식은 MCP 리소스의 방법론 문서와 아티팩트 유형 표, 분류 도구 응답의 `forensic_context`, 다음 작업 권고의 `directive`, 서버 안 처리기 `map_mitre_techniques`·`check_dll_search_order`가 싣는 ATT&CK 값이다 [8][9][10][11][12].
이 가운데 앞의 네 가지는 서버 코드에 적은 상수이고 지식의 원문 위치를 가리키는 필드가 없다 [8][9][10].
`directive`의 `ifConfirmed` 글에는 등록할 발견사항의 ATT&CK 기법 ID가 들어가지만 이 값은 권고 문장의 일부이고 그 지식이 나온 원문을 가리키지 않는다 [10][13].
ATT&CK 원문 ID를 결과 항목에 싣는 두 처리기는 R05.09에서 본다.
`forensic_context`는 도구 결과 `result`와 다른 필드에 들어가지만 코드와 설명은 이 필드가 증거가 아니라고 밝히지 않아 R05.10에도 연결하지 않는다 [9].

### R05.02 증거 내부 경로

**구현.** `list_directory`·`search_filename`은 `fls`를 `-p`와 함께 불러 디스크 이미지 안 파일의 경로를 줄마다 찍게 한다 [14].
`fls` 파서는 그 경로를 항목의 `name`·`path`에 넣는다 [15].
`-l` 열이 같은 값에 붙는 것은 R01.02에서 본다 [14].
이벤트 로그 결과 항목에는 이벤트 로그 파일의 경로가 없고 채널 이름 `channel`만 있다 [16].

**한계.** 모델이 `path`를 주면 서버는 `fls`로 그 경로를 한 단계씩 따라가 inode를 찾고 `path` 인자를 지운 뒤 그 inode에서 `fls`를 시작한다 [17].
Sleuth Kit은 폴더를 훑을 때 경로 버퍼를 빈 문자열에서 시작하므로 `-p`로 출력하는 경로는 시작한 폴더 기준의 상대 경로다 [18].
응답에는 시작한 폴더를 가리키는 값이 없고 호출 기록 항목에도 `path` 대신 inode만 남는다 [6][17].
그래서 이 경우 `path`는 이미지 안의 전체 경로가 아니다 [15][18].
경로의 첫 조각부터 찾지 못하면 `path`가 남고 `fls`는 이미지 루트에서 시작한다 [17].
경로 일부만 찾으면 마지막으로 찾은 폴더에서 시작해 요청한 폴더가 아닌 그 폴더 기준의 상대 경로가 나온다 [17][18].

### R05.03 레코드 키·번호

**구현.** `fls` 파서는 항목마다 메타데이터 주소 `inode`를 싣는다 [15].
이벤트 로그 파서는 `evtx_dump` JSONL의 `EventRecordID`를 `recordId`에 싣는다 [16].
regipy 파서는 플러그인 항목의 `path`나 `key`를 항목의 `key`에 싣는다 [19].
Volatility `pslist` 파서는 프로세스마다 `pid`·`ppid`를 싣는다 [20].
이 파서는 `list_processes`가 성공해야 쓰이고 그 연산은 출력 폴더 안에 `json` 폴더가 없으면 실행 전에 실패한다 [21].

`detect_timestomping`은 결과 문장에 파일 이름 대신 연산 이름을, inode 대신 호출 기록 항목 ID를 넣는다 [22].
이 값은 증거 안 레코드를 가리키지 않는다 [22].

**한계.** regipy 파서는 플러그인 항목에 `path`·`key`가 없으면 `name`을, 그것도 없으면 플러그인 이름을 `key`에 넣는다 [19].
regipy 6.2.1의 `computer_name` 항목은 컴퓨터 이름 값을 `name`에 두므로 `get_system_config` 결과의 `key`에는 키 경로가 아니라 컴퓨터 이름이 들어간다 [19][23].
`appcert_dlls` 항목은 키 경로를 `key_path`에 두므로 `key`에는 플러그인 이름이 들어가고 키 경로는 `data`의 JSON 글 안에만 남는다 [19][23].

### R05.04 바이트·섹터·행 오프셋

**구현.** `list_partitions`의 `mmls` 파서는 파티션마다 시작·끝 섹터와 길이를 `start`·`end`·`length`에 싣는다 [24].
Volatility `pslist` 파서의 `offset`은 프로세스 객체의 가상 주소 열 `Offset(V)`라 덤프 파일 안 위치가 아니다 [20].
`scan_yara`는 YARA에 문자열 출력 옵션 `-s`를 넘기지 않으므로 YARA가 일치 위치를 출력하지 않고 `strings`는 비어 있다 [1][2][3].

### R05.09 참조 지식 원문 출처

**구현.** 이 방식은 서버 안 처리기 연산 `map_mitre_techniques`와 `check_dll_search_order`의 결과에 적용된다 [11][12].
`map_mitre_techniques`는 등록된 발견사항마다 `mapped_findings` 항목을 만들고 서버 코드의 표에서 발견사항 유형에 맞는 ATT&CK tactic ID(`TA0001` 등)를 `mitre`에, tactic 이름을 `tactic`에 싣는다 [11].
이 표에는 기법 ID가 없어 서버가 고르는 원문 ID는 tactic ID뿐이다 [11].
표에 없는 유형 `anti_forensics`·`anomaly`·`ioc`의 발견사항은 `mitre`가 `unmapped`, `tactic`이 `Unknown`이다 [11][25].
`check_dll_search_order`는 결과에 기법 ID와 이름을 붙인 `technique` 값 `T1574.001 - DLL Search Order Hijacking`을 싣는다 [12].
두 처리기 모두 원문 주소는 싣지 않는다 [11][12].

**한계.** `map_mitre_techniques`의 `mitre`에는 모델이 `register_finding`의 `mitre_technique`로 넣은 값이 있으면 그 값이 표의 tactic ID보다 먼저 들어간다 [11].
서버는 이 인자 값을 검사하지 않고 그대로 발견사항에 둔다 [25].
그래서 한 결과 안에서 모델이 넣은 값과 서버가 표에서 고른 tactic ID가 같은 `mitre` 필드에 섞이고 어느 쪽인지 가리키는 표시가 없다 [11].
`tactic`은 `mitre`에 모델이 넣은 값이 들어가도 발견사항 유형으로만 정한다 [11].
