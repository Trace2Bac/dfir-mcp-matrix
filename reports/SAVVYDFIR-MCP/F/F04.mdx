# F04 발견사항·결론 기록 관리

### F04.02 발견사항 필드 구분 저장

**구현.** 이 방식은 모델이 부르는 `add_finding`·`submit_finding`과 추출 도구가 결과를 기록하는 경로가 함께 거치는 `CaseStateManager.add_finding`에 적용된다 [1][2][3].
발견사항은 `Finding` 모델의 필드로 나뉘어 저장된다 [4].
설명 `description`, 종류 `finding_type`, 증거 영역 `artifact_type`, 인식 구분 `evidence_kind`, 상태 `finding_status`, 확신도 `confidence`, ATT&CK `mitre_tactic`·`mitre_technique`가 따로 들어간다 [4].
`evidence_kind`는 관찰·추론·가설·배제 네 값이고 `finding_status`는 ACTIVE·CORRECTED·CONFIRMED·REJECTED 네 값이다 [4].
정상 대안 설명 `alternative_hypothesis`, 그 대안이 맞다면 보일 증거, 대안을 배제한 관찰, 처분 `disposition`도 필드로 받는다 [4].
`submit_finding`은 기록한 전문 하위 에이전트 이름 `assigned_agent`도 남긴다 [2].
`assigned_agent`나 분석 갈래 `lane_id`가 비면 `submit_finding`은 기록하지 않고 오류를 돌려준다 [2][5].
추출 도구가 탐지 규칙 결과를 그대로 남긴 발견사항은 `finding_kind`를 `raw_detector_hit`로 두어 검토한 발견사항과 나눈다 [4][6].
발견사항의 설명, 상태, 확신도를 고치거나 철회하는 MCP 도구는 없다 [7].
`flag_discrepancy`와 `compare_disk_and_memory`는 모순 표시 `contradicted_by`만 고친다 [8][9].

### F04.03 근거 증거·호출 참조

**구현.** 이 방식은 `add_finding`·`submit_finding`과 상태 관리자의 저장 경로에 적용된다 [1][2][3].
발견사항은 근거 실행 ID `execution_id`, 증거 파일 경로 `artifact_path`, 증거 안 위치 `artifact_offset`, 지표 `supporting_indicators`를 필드로 남긴다 [4].
보강하는 발견사항 ID나 출처 분류는 `corroborated_by`, 모순되는 쪽은 `contradicted_by`, 관련 발견사항은 `related_finding_ids`에 남긴다 [4].
경로와 역할을 담은 `raw_evidence_refs`도 둘 수 있고 역할은 `input`·`output`·`derived`·`handle` 가운데 하나여야 한다 [4].
`OBSERVATION` 발견사항은 `artifact_path`가 비면 거부한다 [4][5].

**한계.** 실행 ID를 주지 않으면 상태 관리자는 같은 도구 이름의 최근 실행이나 가장 최근 실행을 찾아 그 ID를 채운다 [1].
모델이 부르는 두 도구의 도구 이름은 `state.add_finding`·`state.submit_finding`이고 이 이름으로는 실행 기록이 남지 않아 가장 최근 실행으로 채워진다 [1][3][2].
채운 출처는 `confidence_support_inputs.execution_id_source`에 남는다 [1].
실행 기록이 하나도 없으면 새 실행 ID를 만들어 채운다 [1].
`corroborated_by`와 `related_finding_ids`의 발견사항 ID가 상태 파일에 있는지는 저장할 때 보지 않는다 [1][10].

### F04.04 사건 시각과 작성 시각 분리

**구현.** 이 방식은 `submit_finding`과 상태 관리자의 저장 경로에 적용된다 [2][1].
사건 시각은 `timestamp_observed`로 받고 작성 시각 `created_at`과 고친 시각 `updated_at`은 서버가 넣는다 [4][1].
`submit_finding`은 ISO-8601 시각을 UTC로 바꿔 저장한다 [11].
`add_finding`에는 사건 시각 인자가 없다 [3].

**한계.** `submit_finding`은 `timestamp_observed`가 시각으로 읽히지 않으면 그 값을 버리고 발견사항을 저장한다 [11].
응답에는 값을 버렸다는 표시가 없었다 [5].

### F04.05 수정·철회 이력

**구현.** 이 방식은 `compare_disk_and_memory`가 발견사항에 모순을 표시하는 경로와 확정 검사가 등급을 낮추는 경로에 적용된다 [9][12].
`compare_disk_and_memory`는 판정이 난 발견사항의 `contradicted_by`에 규칙 이름을 더하고 호출 기록에 `correction` 항목을 남긴다 [9].
이 항목에는 발견사항 ID, 앞 설명 280자, 앞 확신도 등급, 모순 요약, 시각이 들어간다 [9][13].
CONFIRMED로 받은 발견사항을 확정 검사가 ACTIVE로 낮추면 낮춘 사유를 `confidence_support_inputs.confirmed_gate_blocks`에 남긴다 [12].
상태 관리자가 확신도를 곱해 바꾸면 바꾸기 전 값을 `base_confidence`와 `fk_confidence_note`에 남긴다 [14].
상태 관리자가 발견사항을 고칠 때는 `updated_at`만 바꾸고 앞 값을 따로 두지 않는다 [15].

**한계.** `flag_discrepancy`와 다른 출처가 맞을 때 등급을 올리는 경로는 발견사항을 고치지만 호출 기록에 `correction` 항목을 남기지 않는다 [8][16].
등급을 올리는 경로는 앞 상태와 확신도를 남기지 않고 올린 방법만 `promotion_method`에 적는다 [16].
`correction` 항목은 확신도를 한 단계 낮췄다고 적지만 발견사항의 `confidence`는 바뀌지 않았다 [9][5].
`record_hypotheses`는 같은 `hypothesis_id`의 가설을 받은 값으로 통째로 바꾸고 앞 상태와 바뀐 시각을 남기지 않는다 [17].
`generate_graph`의 그래프는 호출 기록에서 `completed` 항목에 붙은 `correction_event`만 읽는다 [18].
`correction` 항목은 `event_type`이 `correction`이므로 그래프에 수정 노드가 그려지지 않았다 [18][5].

### F04.06 파일·DB에 저장

**구현.** 이 방식은 상태 관리자가 쓰는 `state.json`에 적용된다 [19].
발견사항, 가설, 실행 기록은 `SAVVYDFIR_ANALYSIS_DIR`(기본 `./analysis`) 아래 `state.json` 하나에 들어간다 [20][19].
서버는 바꿀 때마다 임시 파일에 쓴 뒤 이름을 바꾼다 [19].
서버를 다시 시작하면 같은 파일을 다시 읽는다 [21].

**한계.** 상태 파일은 사건마다 나뉘지 않는다 [20].
`state.json`에 다른 `case_id`가 들어 있으면 `load`가 오류를 내므로 같은 폴더로 두 사건을 다루려면 환경변수로 폴더를 바꿔 서버를 다시 시작해야 한다 [21].

### F04.07 가설 지지·반박 근거 연결

**구현.** 이 방식은 `record_hypotheses`에 적용된다 [17].
가설은 발견사항과 따로 상태 파일의 `hypotheses`에 남는다 [17][22].
가설 항목에는 공격 유형 `attack_class`, 첫 확인 대상 `initial_pivot`, 예상 증거 사슬, 근거로 쓴 지식 묶음 `CTX-NNN` 목록, 순위, 상태, 연결한 발견사항 ID `related_finding_ids`, ATT&CK 기법이 들어간다 [22].
`related_finding_ids`는 그 가설을 지지하거나 반박한 발견사항을 함께 담는다 [22].

**한계.** 지지 근거와 반박 근거를 나누는 필드가 없다 [22].
`related_finding_ids`의 ID가 상태 파일에 있는지 보지 않아 없는 ID도 그대로 저장되었다 [17][5].

### F04.08 가설 상태 관리

**구현.** 이 방식은 `record_hypotheses`와 `generate_report`에 적용된다 [17][23].
가설 상태는 ACTIVE·INVESTIGATING·CONFIRMED·REFUTED·SUSPENDED 다섯 값이다 [22].
서버 규칙은 CONFIRMED 가설에 연결한 발견사항 가운데 CONFIRMED이고 `corroborated_by`가 둘 이상인 것이 없으면 SUSPENDED로 바꾼다 [24].
연결한 발견사항에 그런 발견사항이 있는데 가설이 REFUTED면 SUSPENDED로 바꾼다 [24].
바꾸면 사유를 `status_gate_reason`에 남긴다 [24].
`generate_report`는 상태 파일에서 가설을 읽어 같은 규칙을 다시 적용한 상태를 보고서에 싣는다 [23].

**한계.** `record_hypotheses`에서는 이 규칙이 적용되지 않는다 [24][25].
규칙은 상태 값을 문자열로 바꿔 CONFIRMED·REFUTED와 비교하는데 `record_hypotheses`가 넘기는 값은 열거형이라 문자열이 `HypothesisStatus.CONFIRMED`가 된다 [24][25].
연결한 발견사항이 ACTIVE 하나뿐인 CONFIRMED 가설을 기록하자 `verdict_downgrades`는 비었고 상태 파일에 CONFIRMED로 남았다 [25].
같은 조건의 REFUTED 가설은 상태 파일에 REFUTED로 남았고 보고서에서만 SUSPENDED로 실렸다 [5].
연결한 발견사항이 `corroborated_by`에 출처 분류 이름만 셋 적은 것이어도 규칙은 보강 둘 이상으로 본다 [24][5].

### F04.09 판정·분류 값 기준 대조

**구현.** 이 방식은 상태 관리자가 발견사항과 가설을 저장하기 전 검사에 적용된다 [1][17].
`evidence_kind`, `finding_status`, `artifact_type`은 코드에 정한 값과 별칭 표에 없으면 거부한다 [26].
`confidence`는 0.0부터 1.0 사이여야 하고 `disposition`은 정한 네 값과 빈 값만 받는다 [4].
`description`은 10자보다 짧으면 거부한다 [4][5].
가설의 상태는 열거형 다섯 값만 받고 `source_context_refs`는 `CTX-NNN` 모양이어야 한다 [22].
`finding_kind`는 `validated`·`raw_detector_hit` 두 값만 받는다 [27].
그래서 아티팩트가 없다고 기록하는 `_record_artifact_absent_audit`가 `finding_kind`를 `documented_gap`으로 둔 부재 발견사항은 거부된다 [27][28][29].
서버는 이 예외를 처리해 발견사항 없이 진행한다 [28][29].

**한계.** ATT&CK 기법 ID와 tactic ID는 모양만 검사하고 기법 표와 대조하지 않는다 [4].
없는 기법 `T9999`를 받아 그대로 저장했다 [5].
서버에는 기법을 tactic으로 바꾸는 라우팅 표가 있지만 기록할 때 쓰지 않는다 [30].

### F04.10 근거·확신도 필드 필수 입력

**구현.** 이 방식은 `submit_finding`의 `confidence`에 적용된다 [2][31].
`submit_finding`은 `confidence`를 기본값 없는 실수 인자로 둔다 [2].
FastMCP 4.0.9는 인자를 입력 schema로 검사해 `confidence`가 없거나 `null`이거나 숫자가 아니면 도구를 실행하지 않고 오류를 돌려준다 [31].

**한계.** 근거 실행 ID `source_execution_id`는 필수 인자가 아니고 비면 상태 관리자가 채운다 [2][1].
증거 경로 `artifact_path`도 필수 인자가 아니고 인식 구분이 `OBSERVATION`인 발견사항만 이 값이 비면 상태 관리자가 거부한다 [2][4][5].
`add_finding`은 `confidence` 기본값이 0.5라서 확신도 없이도 받는다 [3].

### F04.12 저장 시 같은 제출 확인

**구현.** 이 방식은 모델이 부르는 `add_finding`·`submit_finding`과 추출 도구가 결과를 기록하는 경로가 함께 거치는 `CaseStateManager.add_finding`에 적용된다 [1][2][3].
서버는 저장할 때 도구 이름, 경로, 종류, 사건 시각, 기법과 설명 앞 160자(묶음 키 `group_key`가 있으면 그 값)로 내용 키를 계산하고 같은 키가 이미 있으면 새로 기록하지 않고 앞 발견사항의 ID를 돌려준다 [32][33].
`add_finding`·`submit_finding`은 그 ID로 상태 파일의 앞 발견사항을 읽어 응답에 싣는다 [34][35].

**한계.** 내용 키에 상태와 확신도가 들어가지 않으므로 같은 내용을 REJECTED로 다시 내도 앞 발견사항의 ID만 돌아오고 상태는 그대로다 [32][5].
`add_finding`·`submit_finding`은 이 경우에도 `status`를 `ok`로 돌려주고 새로 저장하지 않았다는 필드를 싣지 않는다 [34][35][5].
내용 키에는 도구 이름이 들어가고 두 도구는 도구 이름을 `state.add_finding`·`state.submit_finding`으로 따로 두므로 같은 내용을 두 도구로 나눠 내면 발견사항 두 개로 저장된다 [32][3][2].
이 동작은 코드로 확인했고 실행하지 않았다.

    aliases = ", ".join(sorted(_ARTIFACT_TYPE_ALIASES))

        f"Unsupported artifact_type {value!r}. "
        f"valid_artifact_types=[{supported}]; supported_aliases=[{aliases}]"
    )
