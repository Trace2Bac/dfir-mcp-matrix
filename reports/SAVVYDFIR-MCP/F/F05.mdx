# F05 발견사항·결론 근거 검증

### F05.01 근거 참조 존재 확인

**구현.** 이 방식은 상태 관리자가 CONFIRMED로 받은 발견사항을 저장하기 전 검사와 `generate_report`의 보고서 전 검사에 적용된다 [1][2].
`add_finding`·`submit_finding`과 추출 도구가 남기는 발견사항이 모두 이 저장 경로를 거친다 [3].
검사는 발견사항의 `execution_id`가 상태 파일의 실행 기록에 있는지 본다 [1].
ID가 비었거나 `E-000`이거나 서버가 새로 만들어 채운 ID이거나 실행 기록에 없으면 통과하지 못한다 [1].
통과하지 못한 CONFIRMED 발견사항은 거부하지 않고 ACTIVE로 낮춰 저장하며 `requires_re_extraction`을 참으로 두고 사유를 `confirmed_gate_blocks`에 남긴다 [4].
`generate_report`는 CONFIRMED 발견사항 가운데 `requires_re_extraction`이 참인 것이 있으면 보고서를 쓰지 않고 `needs_re_extraction`을 돌려준다 [2].
이 검사는 CONFIRMED에만 적용되고 ACTIVE 등 다른 상태의 발견사항은 근거 ID 없이도 받는다 [4].
없는 실행 ID `E-999`를 인용한 CONFIRMED 발견사항은 ACTIVE로 저장되었다 [5].

**한계.** 모델이 실행 ID를 주지 않으면 상태 관리자가 가장 최근 실행 ID를 채우고 이 ID는 실행 기록에 있으므로 검사를 통과한다 [3][1].
그래서 근거를 인용하지 않은 CONFIRMED 발견사항이 그 발견사항과 관계없는 실행을 근거로 CONFIRMED로 저장되었다 [5].
검사는 실행 기록에 그 ID가 있는지만 보고 그 실행이 발견사항의 내용과 관계있는지 보지 않는다 [1].
실행 기록을 찾다가 예외가 나면 통과시킨다 [1].
`generate_report`에 `allow_partial=True`를 주면 보고서 전 검사를 건너뛴다 [2].
`corroborated_by`에 적은 발견사항 ID는 있는지 확인하지 않는다 [6].

### F05.03 출처 수·범주로 등급 산정

**구현.** 이 방식은 상태 관리자의 저장 전 검사와 추출 도구가 부르는 자동 승격 함수 `promote_corroborated_findings`에 적용된다 [7][8].
서버는 발견사항의 도구 이름, 종류, 기법, 설명으로 출처 분류 `fk_source_class`를 정한다 [9].
분류는 ShimCache, Amcache, UserAssist, ShellBags, Prefetch, Run 키, MFT 시각 조작, 메모리 프로세스, EVTX 4688, 보강된 Sigma 결과 열 가지다 [9][10].
분류가 정해지면 분류마다 정해 둔 배수를 확신도에 곱해 저장한다 [7][10].
ShimCache는 0.70, Run 키는 0.85, Prefetch는 1.00을 곱한다 [10].
ShimCache·Amcache·UserAssist·ShellBags·Run 키·MFT 시각 조작으로 분류되면 더 필요한 출처 분류를 `corroboration_outstanding`에 넣는다 [7][10].
`corroborated_by`에 적은 출처 분류 이름이나 발견사항 ID의 분류가 그 목록을 채우면 목록에서 뺀다 [6].
CONFIRMED로 받은 발견사항에 남은 출처가 있으면 ACTIVE로 낮추고 사유를 남긴다 [4].
`promote_corroborated_findings`는 추출 도구가 새로 읽은 경로나 파일 이름이 남은 출처를 기다리는 발견사항과 맞으면 그 출처를 `corroborated_by`에 더하고 남은 목록을 줄인다 [8].
실행 흔적이면 출처 조합 표로 확신도를 다시 정하고 다른 흔적이면 0.15를 더한다 [8][11].
남은 출처가 없어지면 CONFIRMED로 올린다 [8].
Run 키로 분류된 CONFIRMED 발견사항은 ACTIVE로 저장되고 확신도가 0.9에서 0.765로 바뀌었다 [5].

**한계.** `corroborated_by`에 발견사항 ID 대신 출처 분류 이름을 적어도 그 출처를 확인한 것으로 본다 [6].
Run 키 발견사항에 `prefetch`, `amcache`, `evtx_process_creation` 세 이름만 적자 남은 출처 없이 CONFIRMED로 저장되었다 [5].
`artifact_type`을 `correlation`으로 낸 발견사항에는 더 필요한 출처 목록을 만들지 않는다 [7].
`submit_finding`의 도구 이름은 `state.submit_finding`이라 도구 이름으로 정하는 분류가 적용되지 않는다 [9].
이 도구로 낸 발견사항은 종류가 `persistence`·`timestomping`이거나 기법이 T1070.006일 때만 분류되고 설명에 4688이 있어도 분류되지 않는다 [9].
분류가 없으면 출처 수와 관계없이 이 검사를 거치지 않는다 [7].
자동 승격은 경로가 달라도 파일 이름만 같으면 같은 대상으로 본다 [8].
자동 승격으로 CONFIRMED가 된 발견사항도 다시 저장 전 검사를 거치므로 처분 값이 없는 추출 도구 발견사항은 ACTIVE로 다시 낮아진다 [8][4].
이때 승격 함수는 그 발견사항을 승격한 목록에 넣어 돌려준다 [8][12].

### F05.04 교차 확인·반론 검토

**구현.** 이 방식은 상태 관리자가 CONFIRMED로 받은 발견사항을 저장하기 전 검사와 `generate_report`의 보고서 전 검사에 적용된다 [13][2].
서버는 처분 `disposition`과 대안 설명 필드를 본다 [13].
처분이 `ruled_out`이면 대안 설명 `alternative_hypothesis`와 배제한 관찰 `evidence_against_it` 하나 이상이 있어야 하고 `not_applicable`이면 그 이유가 있어야 한다 [13].
처분이 `not_resolved`나 `partially_plausible`이거나 비어 있으면 통과하지 못한다 [13].
통과하지 못한 CONFIRMED 발견사항은 ACTIVE로 낮춰 저장하고 사유를 남긴다 [4].
`generate_report`는 처분이 빠진 CONFIRMED 발견사항이 남아 있으면 `needs_alternative_hypothesis`를 돌려주고 보고서를 쓰지 않는다 [2].
처분이 빈 것과 `not_resolved`인 CONFIRMED 발견사항은 ACTIVE로 저장되었고 `ruled_out`에 대안 설명과 관찰을 채운 것은 CONFIRMED로 저장되었다 [5].

**한계.** 서버는 대안 설명과 배제한 관찰이 비어 있는지만 보고 그 내용이 근거와 맞는지 보지 않는다 [13].
`not_applicable`과 아무 이유 글을 함께 내면 대안 설명 없이 통과한다 [13].
`generate_report`에 `allow_partial=True`를 주면 보고서 전 검사를 건너뛴다 [2].
