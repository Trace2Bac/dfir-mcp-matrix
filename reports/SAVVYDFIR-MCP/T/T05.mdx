# T05 분석 도구 검증

### T05.01 저장소·의존성 고정

**구현.** 이 방식은 저장소에 들어 있는 참조 자료에 적용된다.
아티팩트 해석 주의를 담은 `data/forensic-knowledge`의 YAML은 `_forensic_envelope`가 도구 응답에 `forensic_caveat`·`corroborate_with`로 붙이고 보고서의 확인 방향 제안에도 쓰인다 [1][2].
ATT&CK 기법별 필요 아티팩트를 담은 `sift_mcp/routing/attack_routing.yaml`은 리소스 `file:///attack_routing/techniques`로 모델에게 돌아간다 [3].
`sigma_hunt`는 인자로 매핑 파일을 받지 않으면 저장소의 `rules/chainsaw-sigma-mapping.yml`을 먼저 찾아 Chainsaw `--mapping`에 넘긴다 [4].
`get_heuristic`·`prepare_hypothesis_context`는 저장소의 `.claude/agents/<아티팩트>-analyst.md`에서 절을 잘라 모델에게 돌려준다 [5].
이 파일들은 서버 코드 위치 기준의 정해진 경로로 읽으므로 기준 커밋이 내용을 정한다 [1][3][4][5].
`data/hunt-evil-baseline.json`도 저장소에 있고 서버는 시작할 때 이 파일을 읽지만 응답에는 파일 경로를 적은 안내 문구만 붙인다 [6].

분석 도구는 저장소가 버전을 고정하지 않는다.
`requirements.txt`는 `pydantic`·`pandas`·`mitreattack-python`·`asteval` 같은 의존성을 `>=` 하한으로만 적는다 [7].
`install.sh`는 Volatility 3가 없으면 `pipx install volatility3`로 버전 없이 받고 Chainsaw가 없으면 GitHub의 최신 릴리스를 받는다 [8].
Sigma 룰은 `/opt/sigma/rules/windows`가 없을 때 SigmaHQ 저장소 기본 브랜치를 `--depth=1`로 받는다 [8].
Zimmerman 도구, Sleuth Kit, libewf 도구, Plaso, YARA, Hayabusa, libvshadow 도구, `esedbexport`는 설치 스크립트가 설치하지 않고 SIFT Workstation에 있는 것을 쓴다 [9].
Prefetch 해석 라이브러리 `pyscca`는 `requirements.txt`와 설치 스크립트에 없어 저장소가 버전을 정하지 않는다 [10].
받은 파일의 해시를 대조하는 코드는 설치 스크립트와 서버 어디에도 없다.

**한계.** `data/forensic-knowledge`는 `/opt/savvydfir-knowledge/packages/forensic-knowledge/data`가 있으면 그 폴더를 먼저 쓴다 [1].
이 폴더가 있는 환경에서는 응답에 붙는 해석 주의가 기준 커밋의 YAML이 아닌 그 폴더의 내용으로 정해진다 [1][2].
`install.sh`는 저장소 매핑 파일을 `~/.config/chainsaw/mappings/sigma-mapping.yml`로 복사하지만 `sigma_hunt`는 저장소 파일을 먼저 찾으므로 저장소 파일이 없을 때만 그 복사본을 쓴다 [8][4].

### T05.02 설정·호출 인자로 지정

**구현.** 이 방식은 `sigma_hunt`·`hayabusa_hunt`의 룰 위치와 YARA 도구의 룰 파일에 적용된다 [11][12][13].
`sigma_hunt`는 `sigma_rules_path`로 Sigma 룰 폴더를, `chainsaw_mapping`으로 매핑 파일을 받는다 [11][4].
룰 폴더를 주지 않으면 `/opt/sigma-rules/rules/windows`, `/opt/sigma/rules/windows`, `/usr/share/chainsaw/rules`, `/opt/chainsaw/rules`, `~/sigma/rules/windows` 가운데 처음 있는 폴더를 쓰고 모두 없으면 거부한다 [11].
`hayabusa_hunt`는 `rules_dir`로 룰 폴더를 받고 주지 않으면 `/opt/hayabusa/rules`를 쓰며 그 폴더가 없으면 거부한다 [12].
Hayabusa 설정 폴더는 룰 폴더 아래 `config`로 정한다 [12].
`scan_files`·`scan_memory`는 필수 인자 `rules_path`로 YARA 룰 파일을 받는다 [13].
서버는 받은 위치의 룰과 매핑의 버전을 읽지 않는다.
외부 도구 실행 파일의 위치를 정하는 설정이나 환경변수는 없다 [14].

**한계.** `chainsaw_mapping`으로 받은 파일은 있는지 보지 않고 `--mapping`에 넘긴다 [4].
매핑을 주지 않았는데 후보 위치에 매핑 파일이 하나도 없으면 거부하지 않고 `--mapping` 없이 Chainsaw를 실행한다 [4][15].

### T05.04 참조 자료 버전·식별값 조회

**구현.** 이 방식은 `sigma_hunt`의 매핑 파일과 `get_heuristic`·`prepare_hypothesis_context`가 읽는 지식 문서에 적용된다 [16][17].
`sigma_hunt`는 실행에 쓴 매핑 파일의 SHA-256을 계산한다 [16].
이 값을 기대값과 대조하지는 않는다 [16].
`get_heuristic`·`prepare_hypothesis_context`는 `.claude/agents/` 문서 전체의 SHA-256 `source_hash`와 잘라 낸 절의 `excerpt_hash`를 계산한다 [17].
Sigma 룰 폴더의 커밋이나 룰 수의 기준값, Hayabusa 룰의 버전, YARA 룰, `data/forensic-knowledge`·`attack_routing.yaml`의 버전이나 해시는 읽지 않는다 [1][3].

외부 도구 실행 파일의 버전도 읽지 않는다.
`sigma_hunt`는 Chainsaw 후보마다 `--version`을 실행하지만 종료 코드가 0인 첫 후보를 고르는 데만 쓰고 출력은 버린다 [18].
`analyze_vss`도 `vshadowinfo`·`vshadowmount`를 `--version`으로 실행해 종료 코드가 0이나 1인 첫 후보를 고르는 데만 쓴다 [19].
`hayabusa_hunt`는 후보를 `help`로 실행해 출력에 `Yamato Security`가 있는지만 본다 [20].
그래서 `csv-timeline` 명령이 없는 버전 기준 Hayabusa v4.1.0도 이 확인을 통과해 실행에 쓰인다 [21][22].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.
`environment_preflight`도 도구가 있는지만 확인하고 버전을 묻지 않는다 [23].

    """Load one artifact's FK YAML (external-first, vendored fallback). {} if absent."""
    name = str(artifact or "").strip()
    if not name:
        return {}
    for base in _fk_bases():
        # FK artifact namespaces (keep in sync with server.py _load_fk()).
        for platform in ("windows", "analysis_outputs", "linux", "macos"):
            p = base / "artifacts" / platform / f"{name}.yaml"
            if p.exists():
                try:
                    import yaml
                    return yaml.safe_load(p.read_text(encoding="utf-8")) or {}
                except Exception:
                    return {}
    return {}
