# T07 도구 부재 처리

### T07.01 실행 전 도구·참조 자료 가용성 검사

**구현.** 이 방식은 `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`, `extract_prefetch`에 적용된다 [1][2][3][4].
`sigma_hunt`는 Chainsaw 후보 다섯 곳을 `--version`으로 시험 실행하고 종료 코드가 0인 첫 후보를 쓴다 [1].
후보가 모두 없으면 Chainsaw를 실행하지 않는다 [1].
`sigma_rules_path`를 받지 않으면 Sigma 룰 폴더 후보 다섯 곳을 차례로 보고 모두 없으면 실행하지 않는다 [5].
`hayabusa_hunt`는 후보 네 곳을 `help`로 시험 실행하고 종료 코드가 0이며 출력에 `Yamato Security`가 있는 첫 후보를 쓴다 [2].
룰 폴더 `rules_dir`(기본값 `/opt/hayabusa/rules`)가 폴더가 아니면 실행하지 않는다 [6].
`analyze_vss`는 vshadowinfo 후보 세 곳을 `--version`으로 시험 실행하고 종료 코드가 0이나 1이면 쓴다 [3].
`extract_prefetch`는 `pyscca` 모듈을 불러와 보고 실패하면 Prefetch 파일을 읽지 않는다 [4].

다른 분석 도구는 실행 전에 실행 파일이 있는지 확인하지 않는다.
Zimmerman 도구, Volatility 3, Plaso, YARA, Sleuth Kit을 실행하는 도구는 실행기 `SafeRunner.run`으로 바로 실행한다 [7].
`SafeRunner.run`은 시간 초과만 처리하므로 실행 파일이 없으면 `subprocess.run`이 낸 예외가 도구 처리기로 올라가고 처리기는 그 예외 문구를 오류로 돌려준다 [7][8].
실행 확인에서 Plaso가 없는 컨테이너의 `build_timeline`은 `[Errno 2] No such file or directory: 'log2timeline.py'`를 돌려줬다 [9].
`extract_shimcache`는 `/usr/bin/dotnet`과 AppCompatCacheParser DLL을 확인하지 않고 실행하고 실행 예외를 처리하지 않는다 [10].

**한계.** `sigma_hunt`는 매핑 파일 후보를 하나도 찾지 못해도 멈추지 않고 `--mapping` 없이 Chainsaw를 실행한다 [11].
Chainsaw v2.16.5는 Sigma 룰 폴더 `-s`를 줄 때 `--mapping`을 함께 요구하므로 이 경우 Chainsaw가 인자 오류로 끝나고 서버는 종료 코드 오류를 돌려준다 [12][13].
`sigma_rules_path`로 받은 폴더는 있는지 확인하지 않고 Chainsaw에 넘긴다 [5].
`chainsaw_mapping`으로 받은 매핑 파일도 있는지 확인하지 않고 Chainsaw에 넘긴다 [11].
`hayabusa_hunt`의 시험 실행은 서버가 넘기는 `csv-timeline` 명령이 그 실행 파일에 있는지 보지 않는다 [2].
버전 기준 Hayabusa v4.1.0은 `help` 출력에 `Yamato Security`가 들어가 이 확인을 통과한다 [14].
그러나 v4.1.0에는 `csv-timeline` 명령이 없어 Hayabusa가 종료 코드 2로 끝나고 서버는 종료 코드 오류를 돌려준다 [15][16].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.

### T07.02 대체 없는 실패 처리·도구 부재 알림

**구현.** 이 방식은 `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`, `extract_prefetch`가 도구나 룰 폴더를 찾지 못한 경우에 적용된다 [17][18][3][4].
`sigma_hunt`는 Chainsaw를 찾지 못하면 상태 값 `tool_not_found`, 설치 명령을 적은 `error`, Chainsaw 없이 조사를 이어 가라는 `hint`를 돌려준다 [17].
같은 경우 호출 기록의 `completed` 항목은 종료 코드 127과 `chainsaw binary not found`를 남긴다 [17].
`hayabusa_hunt`도 실행 파일을 찾지 못하면 `tool_not_found`와 내려받을 주소를 돌려주고 호출 기록에 종료 코드 127을 남긴다 [18].
`analyze_vss`는 vshadowinfo를 찾지 못하면 `tool_not_found`와 설치 명령을 돌려준다 [3].
`extract_prefetch`는 `pyscca`를 불러오지 못하면 상태 값 `error`와 `pyscca not installed. Run: pip3 install libscca`를 돌려준다 [4].
Sigma 룰 폴더와 Hayabusa 룰 폴더를 찾지 못하면 내려받을 주소나 넘길 인자를 적은 오류를 돌려준다 [5][6].
실행 확인에서 Chainsaw가 없는 컨테이너의 `sigma_hunt`는 `tool_not_found`를, `pyscca`가 없는 컨테이너의 `extract_prefetch`는 위 문구를 돌려줬다 [9].

다른 도구는 도구가 없다는 사실을 따로 구분하지 않는다.
Volatility·Plaso·Zimmerman 도구 실행기의 `classify_error`는 종료 코드 127을 `tool_not_found`나 `dotnet_not_found`로 나눈다 [19].
실행 파일이 없으면 종료 코드가 생기기 전에 예외가 나므로 이 분류는 쓰이지 않고 응답에는 예외 문구만 실린다 [7][8][19].
실행 확인에서 `list_processes`는 `Runner error: [Errno 2] No such file or directory: '/usr/local/bin/vol'`을 돌려줬다 [9].

**한계.** `extract_prefetch`는 상태 값을 `error`로 두고 모듈이 없다는 사실을 `error_message` 문구로만 알린다 [4].

### T07.03 알림 없는 대체 실행

**구현.** 이 방식은 `extract_registry_run_keys`와 `extract_registry_fileaccess`의 RECmd 실행, `analyze_vss`의 E01 처리, `extract_windows_artifacts`의 파일 목록 실행, `run_analysis`의 질의 계산에 적용된다 [20][21][22][23][24].
`extract_registry_run_keys`는 시스템 하이브를 RECmd에 넘기기 전에 하이브의 트랜잭션 로그(`.LOG1`·`.LOG2`)를 반영하는 `rla`를 실행한다 [20].
`rla` 실행이 예외로 끝나면 원래 하이브와 트랜잭션 로그를 그대로 복사해 RECmd에 넘긴다 [20].
응답과 호출 기록에는 이 대체를 알리는 필드가 없다 [20].
`extract_registry_fileaccess`는 RECmd 배치 파일 `DFIRBatch.reb`를 찾지 못하면 `--bn` 없이 RECmd를 실행한다 [21].
이때 경고를 싣지 않고 호출 기록의 명령 문자열은 여전히 `RECmd.dll --bn DFIRBatch over per-profile NTUSER hives`다 [21].
`analyze_vss`는 E01 이미지에 `ewfmount`가 실패하면 `losetup -j`로 그 이미지를 쓰는 루프 장치를 찾는다 [22].
루프 장치도 없으면 E01 파일 경로를 그대로 vshadowinfo에 넘기고 응답에는 어느 대상을 읽었는지 싣지 않는다 [22].
`extract_windows_artifacts`는 `fls -r -p`가 0이 아닌 종료 코드로 끝나면 `-p`를 빼고 다시 실행한다 [23].
바꿔 실행한 사실은 응답과 호출 기록의 명령 문자열로만 알 수 있다 [23].
Sleuth Kit 4.11.1의 `fls`는 `-p`가 없으면 하위 폴더를 따라가도 전체 경로 대신 이름만 출력한다 [25].
서버는 이 출력의 경로로 추출할 아티팩트를 고르므로 다시 실행한 목록에서는 고르는 파일이 달라진다 [23][26].
`run_analysis`의 작업 프로세스는 질의를 `asteval` 해석기로 계산하고 `asteval`을 불러오지 못하면 Python `eval`로 계산한다 [24].
`asteval`은 `requirements.txt`에 적힌 의존성이고 응답에는 어느 쪽으로 계산했는지 싣지 않는다 [24][27].

**한계.** `extract_registry_fileaccess`가 배치 파일 없이 실행할 때 RECmd가 어떤 키를 읽는지는 확인하지 못했다 [21].

### T07.04 실행 환경별 경로 분기

**구현.** 이 방식은 Zimmerman 도구, Volatility 3, Chainsaw, Hayabusa, vshadowinfo·vshadowmount의 실행 파일과 Sigma 룰 폴더, Chainsaw 매핑 파일, RECmd 배치 파일에 적용된다 [28][29][1][2][3][30][5][11][31].
Zimmerman 도구는 `/usr/local/bin/<도구 이름>` 래퍼가 있으면 그것을, 없으면 `dotnet`으로 `/opt/zimmermantools/` 아래 DLL을 실행한다 [28].
Volatility 3은 서버를 불러올 때 `/usr/local/bin/vol`, `/usr/local/bin/vol3`, `/usr/bin/vol`, `/usr/bin/vol3` 가운데 있는 첫 경로를 `VOL_PATH`로 정하고 없으면 `/usr/local/bin/vol`을 쓴다 [29].
Chainsaw는 `PATH`의 `chainsaw`부터 `~/.cargo/bin/chainsaw`까지, Hayabusa는 `PATH`의 `hayabusa`부터 `/opt/hayabusa/hayabusa`까지 정해 둔 차례로 고른다 [1][2].
vshadowinfo와 vshadowmount는 `PATH`의 이름, `/usr/bin`, `/usr/local/bin` 차례로 고른다 [3][30].
Sigma 룰 폴더는 `/opt/sigma-rules/rules/windows`부터 `~/sigma/rules/windows`까지 다섯 곳을 차례로 본다 [5].
Chainsaw 매핑 파일은 저장소의 `rules/chainsaw-sigma-mapping.yml`을 먼저 보고 사용자 설정 폴더와 `/opt`, `/usr/share` 아래 파일을 차례로 본다 [11].
RECmd 배치 파일은 `/opt/zimmermantools` 아래 두 곳과 `/usr/local/share/zimmermantools` 아래 한 곳을 차례로 본다 [31].
고른 실행 파일은 명령 문자열에 남고 매핑 파일과 Sigma 룰 폴더는 `sigma_hunt` 응답의 `mapping_file`과 `sigma_rules`에 남는다 [7][32].
`extract_shimcache`와 `rla` 실행은 `/usr/bin/dotnet` 한 경로만 쓴다 [10][33].

**한계.** Volatility 3 후보는 절대 경로 네 개뿐이라 다른 곳에 설치된 `vol`은 `PATH`에 있어도 고르지 않는다 [29].
실행 확인에서 `vol`이 `/opt/venv/bin/vol`에만 있는 컨테이너의 `VOL_PATH`는 `/usr/local/bin/vol`이었고 메모리 도구는 실행 파일이 없다는 예외 문구를 돌려줬다 [9].

### T07.05 대체 사실을 응답·기록에 표시

**구현.** 이 방식은 `extract_registry_run_keys`의 배치 파일 부재와 `extract_shellbags`·`extract_registry_fileaccess`의 `rla` 실패에 적용된다 [31][34][35].
`extract_registry_run_keys`는 `batch_mode`가 참인데 `DFIRBatch.reb`를 찾지 못하면 배치 파일 없이 RECmd를 실행한다 [31][36].
응답의 `batch_file_used`는 `None`이고 `batch_warning`에 찾아본 경로 세 곳과 기본 모드로 바꾼 사실을 적는다 [31][37].
`extract_shellbags`와 `extract_registry_fileaccess`는 `rla`가 0이 아닌 종료 코드로 끝나거나 예외를 내면 트랜잭션 로그를 반영하지 않은 하이브로 파싱을 계속한다 [34][35].
그 하이브는 응답의 `parser_failures`에 하이브 경로, `status` `replay_error`, 사유 `reason`(`rla_nonzero`나 예외 이름)과 함께 남는다 [34][35].
그 하이브에서 나온 행은 CSV의 `parser_status` 열에 `replay_error`를 단다 [34].

**한계.** `batch_warning`은 응답과 상태 파일의 캐시 항목에만 남고 호출 기록에는 남지 않는다 [37][38].

### T07.06 대체에 따른 검증·입력 범위 변화 표시

**구현.** 이 방식은 `extract_registry_run_keys`의 배치 파일 부재와 `extract_shellbags`·`extract_registry_fileaccess`의 `rla` 실패에 적용된다 [31][34][35].
`batch_warning`은 기본 모드가 배치 파일이 고르는 키 대신 모든 키를 읽는다고 적는다 [31].
`extract_shellbags`와 `extract_registry_fileaccess`의 `parser_failures` 항목은 트랜잭션 로그 없이 건진 행 수를 `recovered_rows`에 싣는다 [34][35].
실패 항목이 하나라도 있으면 응답의 상태 값은 `partial_collection`이고 `partial_failure_count`에 실패 항목 수를 싣는다 [39].

**한계.** `partial_collection` 응답의 `note`는 실패한 출처가 CSV에서 빠졌다고 적는다 [39].
`replay_error` 하이브에서 건진 행은 CSV에 들어가므로 `recovered_rows`가 0보다 크면 `note`의 문구와 CSV의 내용이 다르다 [34][39].

### T07.08 일부 제외 후 계속 실행

**구현.** 이 방식은 `analyze_vss`의 `mmls`·vshadowmount 단계와 `extract_registry_run_keys`·`extract_shimcache`의 `rla` 단계에 적용된다 [40][30][20][10].
`analyze_vss`는 파티션 오프셋을 받지 않았는데 `mmls` 실행 파일이 없으면 오프셋 없이 vshadowinfo를 실행한다 [40].
vshadowmount를 찾지 못하면 그림자 복사본 목록만 만들고 복사본 안의 아티팩트 확인 단계를 뺀다 [30].
이때 그림자 복사본마다 `note`에 vshadowmount가 없다는 사실과 설치할 패키지를 적는다 [30].
vshadowmount가 0이 아닌 종료 코드로 끝날 때도 복사본 안의 아티팩트 확인 단계를 빼고 그림자 복사본 목록을 돌려준다 [41].
`extract_registry_run_keys`와 `extract_shimcache`는 `rla`가 0이 아닌 종료 코드로 끝나면 트랜잭션 로그를 반영하지 않은 하이브 사본으로 파싱을 계속한다 [20][10][33].

**한계.** `rla` 단계를 뺀 사실은 두 도구의 응답과 호출 기록에 남지 않는다 [20][10][33].
`mmls`가 없어 오프셋을 정하지 못한 사실은 응답의 `partition_offset_sectors`가 `None`인 것으로만 알 수 있다 [40].
vshadowmount가 없을 때 복사본마다 `artifacts_missing`에는 확인하지 않은 아티팩트 목록 전체가 들어간다 [30].
vshadowmount가 0이 아닌 종료 코드로 끝나면 복사본마다 `artifacts_found`와 `artifacts_missing`이 빈 값으로 남고 `note`도 달지 않는다 [41].

### T07.09 별도 점검 도구로 가용성 알림

**구현.** 이 방식은 `environment_preflight`에 적용된다 [42].
`environment_preflight`는 분석 도구가 실행 전에 하는 확인과 별도인 조회 도구다 [42].
이 도구는 `ewfmount`·`mmls`·`fls`·`icat`·`dotnet` 실행 파일, Zimmerman 도구 4개(EvtxECmd, MFTECmd, AmcacheParser, RECmd), RECmd 배치 파일 `DFIRBatch.reb`가 있는지 항목마다 확인한다 [42].
결과의 `checks`는 항목마다 이름 `name`, 있는지 `ok`, 찾은 경로 `path`를 담고 `missing`과 `recommended_next_actions`는 없는 항목과 다음 조치 안내를 담는다 [42].
없는 항목이 있으면 상태 값은 `warning`이고 다른 도구의 실행은 막지 않는다 [42].
점검 항목에는 Chainsaw, Hayabusa, Volatility 3, Plaso, YARA, vshadowinfo가 없다 [42].
`start_investigation`은 이 도구를 다음에 부를 도구로 안내하지만 다른 도구가 그 결과를 읽지 않는다 [42][43].
