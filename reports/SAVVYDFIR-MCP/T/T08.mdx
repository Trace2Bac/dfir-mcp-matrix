# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 외부 프로그램을 실행하는 도구 모두에 적용된다 [1][2].
실행기 `SafeRunner.run`은 종료 코드를 `RunResult.exit_code`에 담고 `ok`는 종료 코드가 0이고 시간 초과가 아닐 때만 참이다 [1].
Volatility 3, Plaso, YARA를 실행하는 도구는 `ok`가 거짓이면 종료 코드와 표준 오류 앞부분을 담은 오류 응답을 돌려준다 [3].
사용자 활동 도구는 하이브나 프로필마다 `ok`를 보고 거짓이면 그 항목을 `parser_error` 상태의 실패로 기록한다 [4].
실행기를 거치지 않고 `subprocess.run`을 직접 부르는 `sigma_hunt`, `hayabusa_hunt`, `extract_shimcache`, 그래프 도구 3개도 종료 코드가 0이 아니면 오류를 돌려준다 [2].
`extract_windows_artifacts`는 `fls`의 종료 코드가 0이 아니면 오류로 끝내고 파일마다 실행한 `icat`의 종료 코드가 0이 아니면 그 파일을 실패 목록에 넣는다 [5][6].
실행 확인에서 종료 코드 2로 끝나는 시험용 Chainsaw로 부른 `sigma_hunt`는 `Chainsaw exited with code 2`를 돌려줬다 [7].
버전 기준 Hayabusa v4.1.0에는 서버가 넘기는 `csv-timeline` 명령이 없어 Hayabusa가 종료 코드 2로 끝나므로 `hayabusa_hunt`는 언제나 이 오류 응답을 돌려준다 [8][2].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.

다음 도구는 종료 코드가 0이 아니고 출력 파일이나 표준 출력도 없을 때만 실패로 본다 [9].

- `get_amcache`, `extract_mft_timeline`, `extract_usn_journal`, `summarize_evtx`, `extract_registry_run_keys`는 Zimmerman 도구가 실패해도 CSV 파일이 있으면 그 CSV를 읽어 계속한다 [9].
- `list_deleted_files`는 `fls`가 실패해도 표준 출력이 있으면 계속한다 [9].

**한계.** 이 도구들은 종료 코드가 0이 아닌데 출력으로 계속한 경우 응답에 그 종료 코드나 실패 사실을 싣지 않는다 [9].
실행 확인에서 CSV를 쓰고 종료 코드 1로 끝나는 시험용 MFTECmd로 부른 `extract_mft_timeline`은 상태 값 `success`와 1행을 돌려줬고 호출 기록의 `completed` 항목에는 종료 코드 1이 남았다 [7].
`analyze_vss`는 vshadowinfo의 종료 코드를 보지 않고 출력에서 그림자 복사본을 찾는다 [10].
그래서 vshadowinfo가 실패하면 그림자 복사본 0개의 성공으로 처리하고 VSS가 꺼졌거나 지워졌을 수 있다는 발견사항을 만든다 [10][11].
실행 확인에서 종료 코드 1로 끝나는 시험용 vshadowinfo로 부르면 상태 값 `success`, `total_shadows` 0과 이 문구의 발견사항이 나왔다 [7].
vshadowmount가 0이 아닌 종료 코드로 끝나면 복사본 안 아티팩트 확인을 하지 않고 응답에 그 사실을 싣지 않는다 [12].

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 서버가 실행하는 외부 프로그램과 `run_analysis`의 작업 프로세스에 적용된다 [1][13][14].
`SafeRunner.run`은 실행기마다 정한 시간 제한을 `subprocess.run`에 넘기고 시간 제한을 넘으면 프로세스를 끝낸 뒤 `timed_out`을 참, 종료 코드를 -1로 둔다 [1].
이때 끊기 전에 나온 표준 출력과 표준 오류는 `RunResult`에 남는다 [1].
호출 기록의 출력 요약은 `collection_timeout: process exceeded its timeout budget and was killed`로 쓴다 [15].
실행 확인에서 30초 동안 멈추는 시험용 프로그램을 시간 제한 2초로 실행하면 `timed_out`이 참, 종료 코드가 -1이었고 끊기 전 출력 한 줄이 남았다 [7].

실행 대상마다 시간 제한을 따로 정해 둔다 [16].

- Volatility 3 플러그인은 300초이고 `windows.malfind`는 환경변수 `SAVVYDFIR_MALFIND_TIMEOUT`(기본 900초)을 쓴다 [16].
- `windows.psscan`은 메모리 이미지 크기에 따라 300초에 1GB당 60초를 더하고 1,800초를 넘지 않는다 [16].
- Zimmerman 도구는 1,800초이고 `extract_usn_journal`은 `$J` 크기에 따라 1,800초에서 3,600초 사이로 정한다 [16].
- log2timeline은 7,200초, psort와 pinfo는 600초다 [16].
- Chainsaw는 300초, Hayabusa는 1,800초, `icat`은 파일마다 300초다 [16].
- `run_analysis`의 작업 프로세스는 환경변수 `SAVVYDFIR_ANALYSIS_TIMEOUT_SECS`(기본 240초, 최소 10초)를 쓴다 [16].

시간 초과를 알아차린 뒤의 처리는 도구마다 다르다.

- `build_timeline`, `query_timeline`, `scan_files`, `scan_memory`는 시간 초과를 다른 실패와 나눠 시간 초과 문구의 오류를 돌려준다 [17].
- `scan_processes`는 psscan이 시간 초과로 끝나면 그 시간 제한의 두 배로 한 번 다시 실행한다 [18].
- `sigma_hunt`는 EVTX 폴더 전체가 시간 초과로 끝나면 `Security.evtx` 등 정해 둔 채널 파일 가운데 있는 첫 파일 하나로 Chainsaw를 다시 실행한다 [19].
- `sigma_hunt`는 이렇게 다시 실행한 응답에 `fallback_applied`, `fallback_reason` `directory_timeout`, `fallback_targets`를 싣고 나머지 채널을 하나씩 검사할 `recommended_next_calls`를 붙인다 [19][20].
- `extract_windows_artifacts`는 `icat`이 시간 초과로 끝난 파일을 지우고 실패 목록에 `icat timeout after 300s`로 넣는다 [6].
- `run_analysis`는 작업 프로세스가 시간 제한을 넘으면 `AnalysisBudgetError`로 처리해 오류를 돌려주고 호출 기록에 종료 코드 137을 남긴다 [14][21].

**한계.** 종료 코드가 0이 아니어도 CSV가 있으면 계속하는 Zimmerman 도구 5개는 시간 초과로 끝난 경우에도 끊기 전에 쓴 CSV가 있으면 성공으로 처리한다 [9][1].
이 경우 호출 기록에는 `collection_timeout`이 남지만 응답에는 시간 초과 사실이 없다 [15][9].
`sigma_hunt`가 다시 실행한 단일 파일도 시간 초과로 끝나면 응답만 돌려주고 호출 기록에 `completed` 항목을 쓰지 않는다 [19].
`hayabusa_hunt`도 시간 초과로 끝나면 `completed` 항목 없이 오류를 돌려준다 [22].
버전 기준 Hayabusa v4.1.0에서는 Hayabusa가 명령 해석 단계에서 끝나므로 `hayabusa_hunt`는 1,800초 시간 제한과 이 시간 초과 경로에 이르지 않는다 [8].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 Volatility 3 도구, `build_timeline`, `sigma_hunt`, `hayabusa_hunt`, `extract_shimcache`, 사용자 활동 도구, `extract_windows_artifacts`에 적용된다 [23][24][25][26][27][28][29].
Volatility 3 실행기는 실패한 실행의 표준 오류 문구로 `missing_symbols`, `incompatible_profile`, `unsupported_plugin`, `corrupted_dump`를 나누고 도구 응답의 `volatility_error`에 싣는다 [23][3].
앞의 두 분류이면 호출 기록의 출력 요약 앞에 `tool_incompatible:`을 붙인다 [23].
`build_timeline`은 log2timeline이 성공해도 `pinfo.py`가 알린 이벤트 수가 0이면 오류로 돌려준다 [24].
`pinfo.py`가 실패하거나 이벤트 수를 읽지 못하면 성공으로 두고 `pinfo_validation_error`에 그 사실을 싣는다 [24].
`sigma_hunt`는 출력 JSON 파일을 먼저 읽고 없거나 비면 표준 출력을 읽어 탐지 결과를 모은다 [25].
결과가 0건이면 상태 값을 `no_hits`로 두고 Chainsaw 표준 오류의 불러온 문서 수와 룰 수, 대상 폴더의 EVTX 파일 수로 `zero_hit_diagnostic` 문구를 고른다 [25].
`hayabusa_hunt`는 출력 CSV가 있고 비어 있지 않을 때만 행을 읽고 행이 없으면 `no_hits`로 둔다 [26].
`extract_shimcache`는 AppCompatCacheParser가 0으로 끝났는데 CSV가 없으면 아티팩트 부재(`artifact_absent`)로 기록한다 [27].
사용자 활동 도구는 행이 하나도 없을 때 찾은 원본이 없으면 `artifact_absent`, 찾았지만 파싱 실패가 있으면 `collection_failed`, 찾았고 실패가 없으면 `no_data`로 나눈다 [28].
`extract_windows_artifacts`는 실패한 `icat`의 표준 오류 문구로 NTFS 압축 해제 오류를 골라 그림자 복사본에서 복구할 대상으로 분류한다 [29].
디스크 도구 다수는 결과 0건인데 입력 경로가 있으면 상태 값을 `warning`으로 바꾼다 [30].

**한계.** Chainsaw v2.16.5는 불러온 파일 수를 `Loaded N forensic artefacts`로, 탐지가 나온 문서 수를 `Detections found on N documents`로 표준 오류에 적는다 [31][32].
서버의 정규식은 `Loaded N (forensic) document` 꼴만 찾으므로 이 버전에서는 `documents_loaded`가 언제나 `None`이다 [33][31].
그래서 0건 진단은 대상 폴더의 EVTX 파일 수가 0일 때만 문서 0개 문구를 고른다 [25].
Volatility 3 도구는 표준 출력을 JSON으로 해석하지 못하면 빈 목록으로 처리해 성공 응답을 돌려준다 [34].
실행 확인에서 JSON이 아닌 글을 출력하고 종료 코드 0으로 끝나는 시험용 `vol`로 부르면 `list_processes`는 `success`와 프로세스 0개를, `detect_profile`은 `success`와 `Windows (unknown)`을 돌려줬다 [7].
`hayabusa_hunt`는 출력 CSV가 없어도 `no_hits`로 처리하고 CSV를 읽다 예외가 나면 그때까지 센 행으로 계속한다 [26].
실행 확인에서 CSV를 쓰지 않고 종료 코드 0으로 끝나는 시험용 Hayabusa로 부르면 상태 값은 `no_hits`였다 [7].
버전 기준 Hayabusa v4.1.0에서는 `hayabusa_hunt`가 출력 CSV를 읽기 전에 종료 코드 오류로 끝나므로 CSV 해석 경로에 이르지 않는다 [8][2].

### T08.04 입력별 부분 완료 집계

**구현.** 이 방식은 사용자 활동 도구 8개, `extract_windows_artifacts`, `analyze_vss`에 적용된다 [35][36][37].
사용자 활동 도구는 프로필, 하이브, 파일마다 상태를 정하고 실패한 항목을 `parser_failures`에 프로필, 경로, 상태, 사유, 건진 행 수와 함께 넣는다 [4][35].
응답에는 확인한 프로필 `profiles_checked`, 행을 낸 프로필 `profiles_with_data`, 실패 항목 수 `partial_failure_count`를 싣는다 [35].
실패 항목이 있고 행도 있으면 상태 값은 `partial_collection`이고 호출 기록에 종료 코드 1과 실패한 출처 목록을 남긴다 [35].
실행 확인에서 `$Recycle.Bin`에 해석할 수 있는 `$I` 파일 하나와 해석할 수 없는 파일 하나를 두고 `extract_recycle_bin`을 부르면 상태 값 `partial_collection`, 1행, `partial_failure_count` 1이었다 [7].
`extract_windows_artifacts`는 파일마다 `icat` 실패를 `failures`에 넣고 아티팩트 종류마다 추출한 파일이 있는지 나눈다 [6][36].
응답에는 `failures_count`, `families_with_artifacts`, `families_empty`, `critical_failures_count`, 추출한 파일 수를 싣는다 [36].
상태 값은 실패와 빈 종류가 없으면 `ok`, 하나라도 있으면 `partial_success`, 추출한 파일이 없으면 `warning`이다 [36].
`analyze_vss`는 그림자 복사본마다 찾은 아티팩트 `artifacts_found`와 없는 아티팩트 `artifacts_missing`을 싣는다 [37].

`extract_prefetch`는 `.pf` 파일 하나를 읽다 예외가 나면 그 파일을 건너뛰고 건너뛴 수를 세지 않는다 [38].

**한계.** `extract_windows_artifacts`는 추출한 파일이 하나도 없는 `warning`도 호출 기록에 종료 코드 0으로 남긴다 [39].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 서버 프로세스 안에서 증거를 해석하는 도구와 `run_analysis`에 적용된다 [40][21].
`server.py`의 도구 처리기 대부분은 본문 전체를 `try`로 감싸고 예외가 나면 상태 값 `error`와 예외 문구를 돌려준다 [40].
사용자 활동 도구 가운데 서버 코드로 파싱하는 `extract_recycle_bin`, `extract_powershell_history`, `extract_scheduled_tasks`는 파일 하나의 해석 예외를 그 파일의 `parser_error` 실패로 기록하고 나머지 파일을 계속 읽는다 [41].
실행 확인에서 형식 버전이 9인 `$I` 파일은 `parser_failures`에 `parser_error:ValueError`와 `unknown_i_format_version:9`로 남았다 [7].
`run_analysis`는 작업 프로세스가 거부한 질의를 `SafeAnalysisError`, 메모리나 시간 한도를 넘은 경우를 `AnalysisBudgetError`, 그 밖의 예외를 일반 실패로 나눠 오류를 돌려준다 [21].
세 경우 모두 호출 기록에 종료 코드 2, 137, 1을 각각 남긴다 [21].

**한계.** `extract_shimcache`는 예외를 처리하지 않아 `rla`나 AppCompatCacheParser 실행 파일이 없으면 예외가 도구 밖으로 나간다 [42].
`extract_prefetch`는 `.pf` 파일 하나의 해석 예외를 실패로 기록하지 않고 건너뛰며 나머지 파일로 `success`를 돌려준다 [38].
`hayabusa_hunt`는 CSV 해석 예외를 처리 없이 넘기고 성공 응답을 돌려준다 [26].
버전 기준 Hayabusa v4.1.0에서는 `hayabusa_hunt`가 CSV를 읽기 전에 오류로 끝나 이 예외 경로에 이르지 않는다 [8][2].
