# T06 실행 환경정보 표시

### T06.01 응답 메타데이터에 버전 표시

**구현.** 이 방식은 `sigma_hunt`의 성공 응답에 적용된다 [1].
`sigma_hunt`는 Chainsaw에 넘긴 매핑 파일의 경로를 `mapping_file`에, 그 파일 내용의 SHA-256을 `mapping_sha256`에 싣는다 [1].
같은 응답의 `rules_loaded`에는 Chainsaw가 표준 오류에 적은 불러온 룰 수를 읽어 싣는다 [2].
Sigma 룰은 폴더 경로 `sigma_rules`만 싣고 룰 저장소의 커밋이나 룰 파일의 해시는 싣지 않는다 [1].
실행 확인에서 시험용 Chainsaw로 부른 `sigma_hunt` 응답의 `mapping_file`은 저장소의 `rules/chainsaw-sigma-mapping.yml`이었고 `mapping_sha256`에는 64자 해시가 실렸다 [3].
같은 응답에 Chainsaw 실행 파일의 버전을 담은 필드는 없었다 [3].

서버는 분석 도구 실행 파일의 버전을 응답에 싣지 않는다.
`sigma_hunt`는 Chainsaw 후보를 `--version`으로 실행해 종료 코드만 보고 출력은 버린다 [4].
`hayabusa_hunt`는 `help` 출력에 `Yamato Security`가 있는지만 보고 응답에는 룰 폴더 경로 `rules_dir`만 싣는다 [5].
`build_timeline`은 `pinfo.py` 출력에서 이벤트 수만 읽는다 [6].
외부 프로그램을 실행하는 공통 실행기 `SafeRunner.run`의 결과는 표준 출력, 표준 오류, 종료 코드, 걸린 시간, 명령 문자열, 실행 ID, 시간 초과 여부로 이루어지고 버전 키가 없다 [7].
`environment_preflight`는 실행 파일과 Zimmerman 도구의 경로와 존재 여부만 돌려주고 버전은 돌려주지 않는다 [8].

사건이 열려 있으면 서버는 정해 둔 분석 도구의 응답에 해석 안내 `applicable_heuristics`를 붙인다 [9].
이 안내는 `.claude/agents/`의 분석가별 Markdown 문서에서 잘라 낸 글이고 문서 경로 `source_path`와 문서 전체의 SHA-256 `source_hash`를 함께 싣는다 [9].
같은 사건에서 같은 부분을 다시 붙일 때는 `ref_only` 표시, 문맥 ID `ctx_id`, 문서 경로 `source_path`를 싣고 `source_hash`는 싣지 않는다 [9].
실행 확인에서 같은 인자로 `sigma_hunt`를 두 번 부르면 첫 응답에만 `source_hash`가 있었다 [3].
`prepare_hypothesis_context`도 사건 발견사항에서 나온 아티팩트마다 안내를 붙이고 처음 붙인 부분 가운데 4개까지만 응답에 `source_hash`를 싣는다 [10].
이 안내는 도구가 결과를 만드는 데 쓰지 않는다.

서버는 분석 도구 응답에 아티팩트 지식 `forensic_caveat`·`corroborate_with`를 붙인다 [11].
이 YAML은 아티팩트마다 외부 지식 폴더를 먼저, 저장소의 `data/forensic-knowledge`를 다음으로 찾아 읽는다 [11].
응답에는 읽은 파일의 경로나 식별값을 싣지 않는다 [11].

서버는 FastMCP에 이름과 지침만 주고 버전을 주지 않는다 [12].
실행 확인에서 초기화 응답의 `serverInfo.version`은 FastMCP의 버전 `4.0.9`였다 [3].
서버는 모델을 부르지 않는다.

**한계.** `mapping_sha256`은 매핑 파일을 찾았을 때만 계산하고 파일을 읽지 못하면 `None`이다 [1].
코드 주석은 이 해시를 모든 응답과 호출 기록 항목에 남긴다고 적지만 호출 기록의 `completed` 항목에는 호출 인자만 남는다 [1][13].
실행 확인에서 `sigma_hunt`의 `completed` 항목에 `mapping_sha256`은 없었다 [3].
Chainsaw가 0이 아닌 종료 코드로 끝난 경우의 오류 응답에는 매핑 파일의 경로와 해시가 없다 [14].

### T06.02 호출 기록 메타데이터에 버전 표시

**구현.** 이 방식은 응답에 해석 안내를 붙이는 분석 도구, `get_heuristic`, `prepare_hypothesis_context`에 적용된다 [9][15][10].
서버는 안내 문서의 한 부분을 처음 붙일 때 호출 기록에 `context_bundle` 항목을 쓴다 [9][16].
이 항목에는 문서 경로 `heuristic_source_path`, 문서 전체의 SHA-256 `heuristic_source_hash`, 붙인 부분의 SHA-256 `heuristic_excerpt_hash`, 그 안내를 붙인 도구 `triggered_by`가 들어간다 [16].
분석 도구가 붙이면 항목의 `execution_id`는 그 도구 호출의 실행 ID다 [9][16].
`get_heuristic`은 안내 글 자체를 돌려주는 도구이고 실행 ID가 없어 항목의 `execution_id`에 문맥 ID를 넣는다 [15][16].
`prepare_hypothesis_context`는 안내를 붙인 아티팩트마다 처음 붙인 부분의 `context_bundle` 항목을 쓴다 [10].
이 도구도 실행 ID를 넘기지 않으므로 항목의 `execution_id`에는 문맥 ID가 들어간다 [10][16].
`get_heuristic`의 응답에는 문서 경로만 있고 문서 해시는 이 호출 기록 항목에만 있다 [15].
실행 확인에서 `list_processes`, `sigma_hunt`, `get_heuristic`을 부른 뒤 호출 기록에 `heuristic_source_hash`가 들어간 `context_bundle` 항목이 생겼다 [3].

도구 실행의 `started`·`completed` 항목은 인자, 명령 문자열, 종료 코드, 걸린 시간, 출력 요약 같은 필드로 이루어지고 분석 도구나 룰의 버전이 없다 [13].
실행 확인에서 호출 기록 항목의 키 가운데 버전을 담은 것은 기록 형식 버전 `schema_version` 하나였다 [3].

**한계.** 같은 사건에서 같은 부분을 다시 붙이면 새 `context_bundle` 항목을 쓰지 않으므로 두 번째 호출의 실행 ID에는 이 항목이 없다 [9].
분석 도구가 붙이는 경로에서 호출 기록 쓰기가 실패하면 응답에 `audit_write_warning`만 붙이고 항목 없이 계속한다 [9].
`get_heuristic`은 사건이 열려 있지 않거나 상태 파일 쓰기가 실패하면 항목 없이 `CTX-pending`으로 안내 글을 돌려준다 [15][17].
호출 기록 쓰기만 실패하면 새 문맥 ID를 돌려주지만 그 ID의 `context_bundle` 항목은 없다 [17].
같은 사건에서 같은 부분을 다시 부르면 새 항목 없이 이전 문맥 ID를 돌려준다 [18].

### T06.03 파생물 manifest에 버전 표시

**구현.** 이 방식은 사건 폴더에 CSV를 남기는 디스크 도구 11개의 재사용 기록 파일에 적용된다 [19][20].
대상은 `extract_mft_timeline`, `extract_usn_journal`, `summarize_evtx`와 사용자 활동 도구 8개다 [19][20][21].
도구는 CSV 옆에 `<CSV 경로>.savvyreuse.json` 파일을 쓰고 그 `parser_signature`에 도구마다 코드에 적어 둔 파서 식별값을 넣는다 [19][22].
외부 도구나 라이브러리를 쓰는 도구의 식별값은 `MFTECmd/mft_timeline_v1`처럼 그 도구 이름과 서버 처리 버전 `_v1`을 이은 글이다 [19].
서버 코드로 파싱하는 도구의 식별값은 `native_recycle_i_v1`처럼 서버 파서 이름과 버전이다 [19].
같은 파일에는 입력 파일들의 경로·크기·수정 시각 목록의 SHA-256과 인자의 SHA-256도 들어간다 [22].
다음 호출은 식별값, 입력 목록 해시, 인자 해시가 모두 같을 때만 파싱하지 않고 이 CSV를 재사용한다 [23].
사용자 활동 도구는 실패한 출처 없이 행이 있을 때만 이 파일을 쓰고 MFT·USN·EVTX 도구는 영속 CSV를 남기면 쓴다 [21][20].
실행 확인에서 `extract_recycle_bin`이 성공하자 이 파일의 `parser_signature`는 `native_recycle_i_v1`이었다 [3].
같은 입력으로 다시 부르면 응답의 `reuse_confidence`가 `fingerprint_verified`였고 명령 문자열은 `CACHE_HIT disk.extract_recycle_bin`이었다 [3].
`parser_signature` 값은 응답과 호출 기록에 실리지 않는다 [23][13].

**한계.** `parser_signature`는 코드에 적은 문자열이라 실제로 실행한 Zimmerman 도구의 버전과 묶이지 않는다 [19].
그래서 Zimmerman 도구를 다른 버전으로 바꿔도 식별값이 같고 이전 실행 파일로 만든 CSV를 재사용한다 [19][23].
`extract_mft_timeline`은 MFTECmd가 0이 아닌 종료 코드로 끝나도 CSV가 있으면 이 파일을 쓴다 [24].
실행 확인에서 CSV를 쓰고 종료 코드 1로 끝나는 시험용 MFTECmd로 부르면 `parser_signature`가 `MFTECmd/mft_timeline_v1`인 파일이 생겼다 [3].
`$I` 파일 하나를 해석하지 못한 `extract_recycle_bin`의 `partial_collection` 결과에는 이 파일이 없었다 [3].
