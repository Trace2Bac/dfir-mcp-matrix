# P04 조사 단위 관리

### P04.01 사건 시작 시 ID 확정

**구현.** 이 방식은 `start_investigation`에 적용된다 [1].
`start_investigation`은 매니페스트 JSON의 `case_id`를 읽고 값이 없으면 `UNKNOWN`을 쓴다 [1].
읽은 사건 ID로 `CaseStateManager.load`를 불러 상태 파일을 읽거나 새로 만든다 [1][2].
상태 파일에 다른 사건 ID가 있으면 `CaseStateError`로 거부하고 사건마다 상태 파일을 따로 쓰라는 문장을 돌려준다 [2].
같은 분석 폴더에서 `CASE-A`를 연 뒤 `CASE-B` 매니페스트로 부르자 이 문장이 담긴 오류가 돌아왔다 [3].
사건을 연 뒤 사건 ID를 받지 않는 도구는 불러온 상태의 사건 ID를 발견사항과 출력 폴더에 쓴다 [4].

**한계.** 사건 ID의 문자는 검사하지 않는다 [1].
`extract_windows_artifacts`·`extract_shimcache`·`extract_srum`은 폴더 이름에 쓸 때 일부 문자를 `_`로 바꾸지만 다른 추출 도구의 출력 폴더와 보고서 폴더는 사건 ID를 그대로 쓴다 [4][5][6].

### P04.02 호출마다 사건 ID 전달·검사

**구현.** 이 방식은 사건 ID를 인자로 받아 `_state_manager.load`를 부르는 도구에 적용된다 [7].
`read_state`, `get_finding`, `get_findings`, `record_analysis_lane`, `get_investigation_gates`, `coverage_report`, `prepare_hypothesis_context`, `record_hypotheses`, `generate_report`, `sigma_scan`, `compare_disk_and_memory`가 여기에 속한다 [7].
`load`는 상태 파일의 `case_id`와 받은 값을 대조해 다르면 오류로 거부한다 [2].
`CASE-A` 상태 파일이 있는 서버에 `read_state("CASE-B")`를 부르자 오류가 돌아왔다 [3].
대조 대상은 프로세스가 연 사건이 아니라 상태 파일에 적힌 값이다 [2].

**한계.** 상태 파일이 없으면 대조하지 않고 받은 사건 ID로 새 상태를 만든다 [2].
`extract_prefetch`·`summarize_evtx` 같은 디스크 추출 도구는 `case_id`를 받지만 대조하지 않고 발견사항에는 불러온 상태의 사건 ID를 쓴다 [8].
`extract_windows_artifacts`·`extract_shimcache`·`extract_srum`은 받은 `case_id`로 출력 폴더를 정하고 열린 사건과 대조하지 않는다 [5][6].
`CASE-A`를 연 서버에서 `extract_windows_artifacts`에 다른 사건 ID를 주자 꺼낸 파일이 그 ID의 폴더에 생겼다 [3].
`add_finding`과 `submit_finding`은 받은 `case_id`를 발견사항에 그대로 적는다 [9].
`CASE-A`를 연 서버에서 `add_finding`에 `CASE-B`를 주자 `case_id`가 `CASE-B`인 발견사항이 `CASE-A` 상태 파일에 저장되었다 [3].

### P04.03 폴더·DB·manifest에 사건 ID 연결

**구현.** 이 방식은 상태 파일, 실행 기록, 발견사항, 추출 출력 폴더, 보고서 폴더, 그래프 병합에 적용된다 [10][11][4][12][13].
상태 파일 `state.json`은 최상위에 `case_id`를 두고 실행 기록과 발견사항에도 `case_id`를 넣는다 [10][11].
추출 도구의 CSV는 `OUTPUT_BASE/<case_id>/artifacts/<도구>`에, 이미지에서 꺼낸 파일은 `OUTPUT_BASE/<case_id>/artifacts/raw`에 둔다 [4][5].
메모리 도구의 CSV는 그 아래 덤프 파일 이름으로 만든 하위 폴더에 둔다 [14].
보고서는 `./reports/<case_id>`에 쓴다 [12].
`merge_host_graphs`는 `reports/<case_id>/graph.json`을 모으고 `cases` 인자로 합칠 사건 ID를 고른다 [13].

**한계.** 호출 기록 `audit.jsonl`의 항목에는 사건 ID 칸이 없다 [15].
호출 기록은 상태 파일과 같은 분석 폴더에 있다는 것으로만 사건에 이어진다 [16].
`extract_shimcache`와 `extract_srum`의 중간 출력은 `OUTPUT_BASE`가 아니라 고정 경로 `/cases/shimcache/<case_id>`와 `/cases/srum/<사건 ID 앞 20자>`에 생긴다 [6].

### P04.04 사건별 폴더·DB 분리

**구현.** 이 방식은 추출 출력 폴더와 보고서 폴더에 적용된다 [4][12].
추출 도구와 보고서는 사건 ID로 만든 폴더 아래에 써서 사건마다 따로 둔다 [4][12].
상태 파일과 호출 기록은 사건마다 나뉘지 않고 분석 폴더 하나에 하나씩 있다 [16].
분석 폴더는 환경변수 `SAVVYDFIR_ANALYSIS_DIR`이고 없으면 서버를 실행한 폴더의 `./analysis`다 [16].
서버 주석은 호스트마다 이 값을 사건 폴더로 정해 서버를 따로 실행하는 방식을 적는다 [16].
같은 분석 폴더로 두 번째 사건을 열면 상태 파일의 사건 ID가 달라 거부된다 [2][3].

**한계.** 상태 파일과 호출 기록을 사건마다 나누려면 사용자가 서버를 실행할 때마다 `SAVVYDFIR_ANALYSIS_DIR`을 다르게 정해야 한다 [16].
`load_memory`가 ZIP을 푸는 폴더의 기본값은 사건과 관계없는 `/evidence/memory`다 [17].
전문 에이전트 작업 대기열 `/tmp/savvydfir_delegate_queue.json`은 모든 사건이 함께 쓰고 항목마다 `case_id`를 적는다 [18].
