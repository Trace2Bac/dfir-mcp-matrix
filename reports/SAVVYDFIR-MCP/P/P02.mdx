# P02 다음 작업 결정

### P02.01 고정 문서·프로필 반환

**구현.** 이 방식은 `start_investigation` 응답의 `workflow_contract`, MCP 리소스 `file:///attack_routing/techniques`와 리소스 템플릿, `get_heuristic`, `describe_tool_catalog`, 도구 응답에 붙는 참조 지식에 적용된다 [1][2][3][4][5].
`workflow_contract`는 `doc_reference`에 `CLAUDE.md`의 7단계 조사 흐름을 가리키는 고정 문장을 둔다 [1].
`analysis_contract`는 `csv_path`나 `output_path`를 돌려준 도구마다 `run_analysis`로 열을 확인하고 `submit_finding`으로 발견사항을 남긴 뒤 다음 추출로 가라고 적는다 [1].
`heuristic_reference_routing`은 추출 도구마다 읽을 `.claude/agents/<artifact>-analyst.md`를, `concrete_pattern`은 다섯 단계의 차례를 적는다 [1].
`do_not_start_artifact_collection_until`은 `environment_preflight`, 디스크 이미지 준비, 메모리 덤프 준비가 끝나기 전에 아티팩트 수집을 시작하지 말라고 적는다 [6].
이 글들은 코드에 적은 문자열이라 사건 상태와 관계없이 같다 [1][6].

리소스 `file:///attack_routing/techniques`는 `routing/attack_routing.yaml`의 ATT&CK 기법 ID 목록을 돌려준다 [2][7].
리소스 템플릿 `file:///attack_routing/technique/{technique_id}`는 기법마다 실행할 도구 이름 `required_artifacts`, 교차 확인 자료, 해석 메모를 돌려준다 [2][7].
`get_heuristic`은 `.claude/agents/<artifact>-analyst.md`에서 요청한 절을 잘라 `<HEURISTIC>` 태그로 감싸 돌려준다 [3][8].
`describe_tool_catalog`는 코드에 적은 도구 분류표를 분류별로 돌려준다 [4].
`_forensic_envelope`는 도구마다 정해 둔 참조 지식 YAML의 `corroborate_with`를 그 도구의 처음 세 응답에 붙여 다음에 볼 아티팩트를 알린다 [5].

서버 지침 `instructions`는 서버를 소개하는 189자 문장 하나이고 조사 절차를 적지 않는다 [9][10].
지침은 도구가 43개라고 적지만 실제로 등록된 도구는 65개다 [9][10].
`.claude/` 훅과 `CLAUDE.md`도 조사 차례를 적지만 이 둘은 Claude Code가 읽는 클라이언트 설정이다 [11].

### P02.02 규칙·조사 상태로 추천

**구현.** 이 방식은 `start_investigation`, `get_investigation_gates`, `coverage_report`, `read_state`, `record_analysis_lane`, 디스크 도구의 오류 응답, `extract_windows_artifacts`의 `data_gaps`에 적용된다 [12][13][14][15][16][17][18].
`start_investigation`은 매니페스트의 디스크 이미지와 메모리 덤프마다 먼저 부를 도구를 `next_required_tools`에 싣는다 [12].
메모리 덤프가 없으면 `next_action`에 메모리 단계를 건너뛰고 디스크 단계부터 시작하라고 적는다 [12].
매니페스트의 `investigative_taxonomy`가 파일 접근 묶음을 요구하면 파일 접근 추출 도구 8개를 `next_required_tools`와 보고서 필수 도구 목록에 더한다 [19].
디스크 이미지 하나와 빈 `memory_dumps`를 적은 매니페스트로 부르자 `next_required_tools`에 `environment_preflight`, `mount_image`, 파일 접근 도구 8개가 실렸다 [20].

`get_investigation_gates`는 필수 레인이 `PENDING`·`IN_PROGRESS`·`FAILED`이거나 없으면 `blocking_reasons`에 적는다 [13].
작업 기록은 있는데 맡은 에이전트가 없는 레인에는 정해 둔 전문 에이전트를 부르거나 `record_analysis_lane`으로 기록하라는 권고를 싣는다 [13].
`coverage_report`는 발견사항의 `mitre_tactic`과 기법에서 정한 전술로 다루지 않은 전술을 고르고 전술마다 정해 둔 도구를 `suggested_next_tools`로 돌려준다 [14][21].
`read_state`의 `analysis_debt.next_required_actions`는 추출만 하고 분석 발견사항이 없는 CSV 경로와 실행 ID를 싣는다 [15][22].
브라우저 기록을 추출한 뒤 `read_state`를 부르자 그 CSV가 `next_required_actions`에 실렸다 [20].

`record_analysis_lane`은 거부할 때 다음에 부를 도구를 함께 돌려준다 [16].
EVTX 실행 기록 없이 `event_auth`를 완료로 기록하려 하면 `summarize_evtx`를, 다시 시도해야 할 파서 실패가 남아 있으면 `extract_windows_artifacts`를 `next_required_tool`로 싣는다 [16][23].
디스크 도구는 입력 경로를 찾지 못하면 `recommended_tool_call`에 `extract_windows_artifacts` 호출문을 싣는다 [17].
`extract_windows_artifacts`는 중요한 아티팩트를 꺼내다 압축 해제 오류가 나면 그 `data_gaps` 항목에 `next_required_tool`로 `disk.analyze_vss`를 적는다 [18].
`generate_report`는 보고서 조건을 채우지 못하면 빠진 도구 목록과 첫 도구를 `next_required_tool`로 돌려준다 [24].

필수 분석 레인 넷이 끝나면 `record_analysis_lane`은 `synthesis-analyst`를 부르라는 작업 항목을 `/tmp/savvydfir_delegate.json`과 레인별 대기열에 쓴다 [25].
이 파일은 클라이언트 훅 `scripts/agent_trigger.py`가 읽는다 [25][11].

**한계.** `start_investigation`의 `next_required_tools`와 `next_action`은 디스크 이미지마다 `mount_image`를 부르라고 적지만 `mount_image`는 MCP 도구로 등록되어 있지 않다 [12][26].
도구 설명과 `next_action`이 가리키는 도구가 목록에 없다는 사실은 응답에 나오지 않는다 [12].
매니페스트 항목이 견본처럼 `path`를 가진 객체이면 `mount_image`와 `load_memory` 권고의 인자에는 경로 대신 그 객체를 문자열로 바꾼 값이 들어간다 [12][27].
`path`·`host`·`image_type`을 적은 디스크 이미지 항목으로 부르자 `mount_image`의 `image_path`가 그 객체를 문자열로 바꾼 값으로 돌아왔다 [28].
파일 접근 도구 8개의 권고는 디스크 이미지가 여럿이어도 첫 항목의 `path` 하나만 인자로 싣고 첫 항목이 객체가 아니면 인자를 비운다 [19].
디스크 이미지 두 개를 적은 매니페스트에서 파일 접근 도구 8개의 `image_path`는 모두 첫 이미지 경로였다 [28].
`get_investigation_gates`는 `start_investigation`이 만들지 않는 `synthesis_corroboration` 레인을 필수 레인으로 보고 빠졌다고 적는다 [13][29].
이 경우의 권고는 레인을 끝내거나 빈 곳을 기록하라는 일반 문장 하나다 [13][20].
`coverage_report`가 권하는 도구 이름은 `disk.summarize_evtx`처럼 내부 이름이고 MCP 도구 이름과 다르다 [21].

### P02.04 서버 코드에 고정한 분석 절차

**구현.** 이 방식은 `compare_disk_and_memory`와 `sigma_scan`에 적용된다 [30][31].
`compare_disk_and_memory`는 사건 상태의 디스크·메모리 발견사항을 읽어 코드에 정한 교차 검사 10개를 차례로 실행하고 어긋난 항목을 한 목록으로 합친다 [30].
어긋난 항목마다 `recommended_action`을 싣고 관련 발견사항의 `contradicted_by`를 고친다 [30].
메모리 덤프가 없는 사건이면 메모리와 디스크를 맞춰 보는 검사 3개를 건너뛰었다는 `memory_checks_skipped`를 싣는다 [32].
`sigma_scan`은 사건 상태의 발견사항을 탐지기 10개에 차례로 넘기고 결과를 합친다 [31][33].
첫 단계 탐지기 7개와 둘째 단계 상관 탐지기 3개가 있고 매니페스트의 `enabled_detectors`로 고를 수 있다 [33][34].
모델은 도구와 사건 ID만 고르고 그 안의 단계는 서버 코드가 정한다.
서버 안에서 모델을 불러 계획을 세우는 경로는 없다.

**한계.** `compare_disk_and_memory`의 서버 도구 설명은 검사가 6개라고 적고 실제 함수는 10개를 실행한다 [35][30].
`sigma_scan`의 도구 설명은 탐지기 5개를 적지만 실제로 실행하는 탐지기는 10개이고 이름도 다르다 [31][33].
둘째 단계 탐지기는 전체 실행 시간이 정해 둔 상한을 넘으면 건너뛰고 경고만 남긴다 [33].

```python
def group_tool_catalog(*, domain: Optional[str] = None) -> dict[str, list[dict[str, Any]]]:
    selected_domain = str(domain).strip().lower() if domain else None
    if selected_domain and selected_domain not in ALLOWED_TOOL_DOMAINS:
        raise ValueError(f"Unsupported domain filter {domain!r}.")

    grouped: dict[str, list[dict[str, Any]]] = {}
    for entry in iter_catalog_entries():
        if selected_domain and entry.tool_domain != selected_domain:
            continue
        grouped.setdefault(entry.tool_domain, []).append(entry.to_dict())
    return grouped
```
