# P03 조사 진척 판단

### P03.01 기준 작업 목록 대조

**구현.** 이 방식은 `generate_report`의 보고서 조건 `evaluate_ir_coverage_gate`와 분석 부채 계산 `compute_analysis_debt`에 적용된다 [1][2].
`evaluate_ir_coverage_gate`는 메모리 도구 3개와 디스크 도구 8개를 대상 유형별 필수 목록으로 둔다 [3].
메모리 목록은 사건에 메모리 덤프가 있을 때만 적용한다 [1].
실행 기록에서 같은 도구의 성공 실행이 있는지 대조해 없는 도구를 `missing`에 싣는다 [1].
성공 실행은 종료 코드가 0이고 실행 시간이 0보다 크며 완료 호출 기록의 해시가 있는 실행이다 [4].
발견사항에 정해 둔 조건이 있으면 `detect_injection`, 연결이 있는 PID의 `list_dlls`, 안티 포렌식 신호에 따른 `analyze_vss`·`extract_shimcache`·`extract_srum`을 목록에 더한다 [1].
파일 접근 묶음이 필요한 사건은 파일 접근 추출 도구 8개를 더하고 성공 실행이나 부재 기록이 있으면 채운 것으로 본다 [1].

`compute_analysis_debt`는 추출 도구 카탈로그로 실행마다 만든 CSV·JSON 경로를 모은다 [2][5].
그 경로나 실행을 가리키는 분석 발견사항이나 부재 기록이 없으면 남은 일로 본다 [2].
`run_analysis` 질의만 한 경로는 남은 일로 둔다 [2].
파일 접근 묶음이 필요한 사건의 파일 접근 도구 경로는 막는 항목, 나머지는 경고 항목이다 [2].
남은 일은 `read_state` 요약의 `analysis_debt`, `generate_report`의 `missing_coverage`, `record_analysis_lane`의 거부 응답에 실린다 [6][1][7].
브라우저 기록을 추출한 뒤 `read_state`를 부르자 그 CSV 경로와 실행 ID가 막는 항목으로 돌아왔다 [8].

**한계.** 같은 도구의 실행 기록에 종료 코드와 실행 시간 필드가 모두 없으면 실행 기록이 있다는 것만으로 채운 것으로 본다 [1].
파일 접근 도구는 실행 기록 요약의 `status`나 `reason`이 `collection_timeout`이나 `tool_incompatible`이어도 채운 것으로 본다 [1][9].
필수 목록은 도구 이름 단위로 대조하므로 디스크 이미지가 여럿이어도 이미지마다 실행했는지는 보지 않는다 [1].

### P03.02 단계 상태·완료 조건 대조

**구현.** 이 방식은 `get_investigation_gates`와 `record_analysis_lane`에 적용된다 [10][7].
`start_investigation`은 사건마다 분석 레인 6개를 만들고 상태 값은 `PENDING`·`IN_PROGRESS`·`COMPLETE`·`COMPLETE_WITH_GAPS`·`FAILED` 가운데 하나다 [11][12].
`get_investigation_gates`는 필수 레인이 모두 끝났는지와 작업 기록이 있는 레인에 맡은 에이전트가 있는지로 `report_ready`를 정한다 [10].
`record_analysis_lane`은 레인을 기록하기 전에 적은 실행 ID와 발견사항 ID가 사건 상태에 있는지 대조하고 없으면 거부한다 [13].
`COMPLETE`나 `COMPLETE_WITH_GAPS`로 기록하려면 그 레인의 다시 시도해야 할 파서 실패가 같은 파서의 뒤 성공 실행으로 풀려 있어야 한다 [7][14].
`event_auth`는 `summarize_evtx` 실행이나 발견사항이 있어야 완료로 기록된다 [7].
`COMPLETE`는 그 레인이 맡은 분석 부채가 없어야 하고 남아 있으면 `COMPLETE_WITH_GAPS`로 다시 기록하라는 거부를 돌려준다 [7].
메모리 덤프가 없는 사건이면 `memory` 레인을 처음부터 `COMPLETE`로 둔다 [15].
`load_memory`가 덤프 경로를 돌려주면 서버는 필수가 아닌 `evidence_access` 레인을 `COMPLETE`로 기록하고 요약에 덤프 경로를 잇는다 [11][16].
없는 실행 ID를 적은 기록과 EVTX 실행 없이 `event_auth`를 완료로 적은 기록이 각각 거부되었다 [17].

**한계.** `get_investigation_gates`는 `start_investigation`이 만들지 않는 `synthesis_corroboration` 레인을 필수로 보고 빠졌다고 적는다 [10][11].
같은 사건으로 `start_investigation`을 다시 부르면 기록한 레인의 상태, 맡은 에이전트, 요약, 완료 시각이 처음 값으로 돌아간다 [11][18].
매니페스트에 적은 메모리 덤프가 없어 오류로 끝나는 호출도 레인을 처음 값으로 되돌린 뒤 오류를 돌려준다 [11][19].
`COMPLETE_WITH_GAPS`는 분석 부채가 남아 있어도 받아들인다 [7].
`evidence_access` 레인의 `COMPLETE`는 덤프 하나의 준비만으로 정해지고 매니페스트의 다른 덤프나 디스크 이미지를 준비했는지는 보지 않는다 [16].

### P03.03 미조사 범위·생략 사유 보고

**구현.** 이 방식은 부재 기록 함수 `_record_artifact_absent_audit`를 쓰는 디스크 도구, `extract_windows_artifacts`, `summarize_evtx`, `start_investigation`, `compare_disk_and_memory`, `classify_missing_artifact`에 적용된다 [20][21][22][15][23][24].
`_record_artifact_absent_audit`는 확인한 경로와 사유를 응답에 싣고 실행 기록 요약에 `status=artifact_absent`를 남긴다 [20].
`extract_prefetch`·`get_amcache`·`extract_shimcache`·`extract_srum`·`extract_pca`가 이 함수를 쓴다 [25].
`extract_windows_artifacts`는 꺼낸 파일이 없는 종류마다 `data_gaps`에 `not_found`와 맡을 레인을 적고 실패한 파일은 `failures`에 남긴다 [21].
종류 7개 가운데 4개가 없는 ext4 이미지에서 이 4개가 `not_found` 항목으로 돌아왔다 [8].
`summarize_evtx`는 기준 채널과 고가치 채널 가운데 비었거나 없는 채널을 `coverage_debt`로 사건 상태의 `artifact_coverage`에 남긴다 [22].
메모리 덤프가 없는 사건이면 `start_investigation`이 `memory` 레인의 `data_gaps`에 `no_memory_image`를 적는다 [15].
`compare_disk_and_memory`는 그런 사건에서 건너뛴 검사 이름을 `memory_checks_skipped`에 싣는다 [23].
`classify_missing_artifact`는 모델이 준 값(파일이 있는지, 파서 성공, 건수, 크기, 정황)으로 `not_collected`·`outside_manifest_scope`·`parser_failed`·`wiped`·`empty`·`present`를 정해 응답으로만 돌려준다 [24][17].

**한계.** `summarize_evtx`의 응답에는 채널 건수만 싣고 비었거나 없는 채널 목록은 사건 상태에만 남긴다 [26].
`extract_pca`는 `PcaAppLaunchDic.txt`가 없으면 Windows 11 22H2 이전 시스템이라는 사유를 적지만 OS 버전은 확인하지 않는다 [27].
`_record_artifact_absent_audit`는 `evidence_access_gap` 발견사항도 저장하려 하지만 `finding_kind` 값 `documented_gap`을 `Finding` 모델이 받지 않아 발견사항은 남지 않는다 [28][29].
Windows 폴더만 있는 시험 폴더에서 부재를 기록한 세 도구의 `findings_created`는 비어 있었다 [30].

### P03.04 모델이 적은 진행 기록 보관

**구현.** 이 방식은 `record_analysis_lane`에 적용된다 [7].
모델은 레인마다 상태, 맡은 에이전트, 실행 ID, 발견사항 ID, `data_gaps`, `anti_forensics_warnings`, `unresolved_discrepancies`, `next_pivots`, `summary`, `confidence_notes`를 적는다 [31].
서버는 이를 사건 상태의 `analysis_lanes`에 저장하고 호출 기록에 기록 항목을 남긴다 [31].
같은 레인을 다시 적으면 ID와 `data_gaps` 같은 목록은 합치고 상태와 요약은 새 값으로 바꾼다 [32].
레인 이름은 정해 둔 7개만 받는다 [33].
`anti_forensics_recovery`를 `COMPLETE_WITH_GAPS`와 요약, `data_gaps`, `next_pivots`로 기록하자 응답의 레인에 그 값이 그대로 남았다 [17].
`read_state`와 `get_investigation_gates`가 저장한 레인을 돌려준다 [6][10].

**한계.** 같은 사건으로 `start_investigation`을 다시 부르면 저장한 상태와 요약이 지워지고 목록만 남는다 [18].
레인은 조사 영역 단위이고 디스크 이미지나 호스트를 구별하는 칸이 없다 [31].

def _execution_was_successful(ex: dict[str, Any]) -> bool:
    """Universal success predicate for an execution record.

    Used by every mandatory-tool check, not just sigma_hunt. review
    round-2 #M2: prior implementation only required tool suffix presence,
    meaning a failed parser counted toward coverage.
    """
    try:
        exit_code = ex.get("exit_code")
        if exit_code is None:
            return False
        if int(exit_code) != 0:
            return False
    except (TypeError, ValueError):
        return False
    try:
        duration = float(ex.get("duration_seconds") or 0.0)
    except (TypeError, ValueError):
        duration = 0.0
    if duration <= 0.0:
        return False
    if not ex.get("audit_completed_entry_hash"):
        return False
    return True

def classify_missing_artifact_record(
    *,
    artifact_family: str,
    is_mandatory: bool,
    exists: bool | None = None,
    parser_succeeded: bool | None = None,
    record_count: int | None = None,
    file_size_bytes: int | None = None,
    corroborating_signals: list[str] | None = None,
    reason: str | None = None,
    lane_id: str | None = None,
) -> dict[str, Any]:
    signals = [str(signal) for signal in (corroborating_signals or []) if str(signal).strip()]
    classification = "unknown"
    if exists is False:
        classification = "not_collected" if is_mandatory else "outside_manifest_scope"
    elif parser_succeeded is False:
        classification = "parser_failed"
    elif record_count == 0 or (file_size_bytes is not None and file_size_bytes < 131072):
        classification = "wiped" if signals else "empty"
    elif exists and parser_succeeded:
        classification = "present"
    return {
        "artifact_family": artifact_family,
        "classification": classification,
        "reason": reason or "",
        "lane_id": lane_id,
        "corroborating_signals": signals,
    }
