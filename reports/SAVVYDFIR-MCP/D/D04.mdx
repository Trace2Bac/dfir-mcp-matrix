# D04 출력 경로 제한

### D04.01 서버가 출력 위치 결정

**구현.** 이 방식은 디스크·메모리 아티팩트 파일, 이미지 안 파일 꺼내기, 탐지·타임라인 결과, 보고서, 기본 경로의 그래프, 상태 파일에 적용된다 [1][2][3][4][5][6][7][8].
디스크·메모리 추출 도구는 `OUTPUT_BASE/<case_id>/artifacts/<도구 이름>/` 아래 도구마다 정한 이름(`mft_timeline.csv`, `prefetch.csv`, `deleted_files.json` 등)에 쓴다 [1].
이 `case_id`는 `start_investigation`이 manifest에서 읽어 상태에 둔 값이고 이 도구들이 받는 `case_id` 인자는 출력 위치에 쓰지 않는다 [1][9].
메모리 CSV는 메모리 덤프 파일 이름에서 확장자를 떼고 영숫자와 `.`·`_`·`-` 밖의 문자를 `_`로 바꾼 64자 이하의 폴더에 둔다 [2].
`extract_windows_artifacts`는 `case_id` 인자에서 영숫자와 `.`·`_`·`-` 밖의 문자를 `_`로 바꾸고 앞뒤의 `.`·`_`를 뗀 값으로 `artifacts/raw/` 폴더를 정한다 [3].
꺼낸 파일의 이름은 이미지 안 경로의 마지막 조각에서 허용 문자 밖을 `_`로 바꾼 값이고 사용자 `NTUSER.DAT` 계열에는 사용자 이름을 앞에 붙인다 [10].
`sigma_hunt`·`hayabusa_hunt`는 분석 폴더 아래 `<case_id>/sigma_hunt/chainsaw_<UTC 시각>.json`과 `<case_id>/hayabusa/hayabusa_<UTC 시각>.csv`로 정한다 [4].
`build_timeline`은 작업 폴더의 `./analysis/<case_id>/` 폴더에 `case_id`의 허용 문자 밖을 `_`로 바꾼 이름의 `.plaso` 파일을 정한다 [5].
`query_timeline`은 `./analysis/psort_out_<UTC 시각>.csv`로 정한다 [5].
`extract_shimcache`는 `OUTPUT_BASE`와 관계없이 `/cases/shimcache/<case_id>/`를 CSV 폴더로 정한다 [11].
`extract_srum`은 `case_id`의 영숫자 밖 문자를 `_`로 바꾼 앞 20자로 `/cases/srum/<값>`을 정한다 [12].
`generate_report`는 작업 폴더의 `./reports/<case_id>/`에 `report.html`과 `report.json`을 정한다 [6].
`generate_report`는 먼저 그 `case_id`로 상태를 불러오므로 상태 파일의 사건 ID와 다른 값을 주면 오류로 끝난다 [13].
`generate_graph`는 `output_path`가 없으면 `./reports/<case_id>/graph.html`로 정하고 이때 `case_id`의 `/`·`\`는 `_`로 바꾼다 [7].
`state.json`과 `audit.jsonl`은 분석 폴더 안의 고정 이름이다 [8].
`build_timeline`, `query_timeline`, `generate_report`, `generate_graph`의 기본 위치는 분석 폴더 환경변수와 관계없이 작업 폴더 기준이다 [5][6][7].

그 밖의 출력 위치는 호출 인자를 그대로 쓴다.
`generate_graph`의 `output_path`, `merge_host_graphs`의 `output_path`·`reports_dir`, `build_reports_index`의 `reports_dir`은 `resolve()`만 하고 허용 폴더와 대조하지 않는다 [7][14].
`load_memory`는 ZIP을 풀 폴더 `output_dir`를 허용 폴더와 대조하지 않고 그대로 만들어 `7z`에 넘기며 기본값은 `/evidence/memory`다 [15].
`generate_graph`에 보고서 폴더 밖의 `output_path`를 주자 그 위치에 HTML과 `graph.json`을 썼다 [16].
서버에는 쓰기 허용 폴더 목록 `OUTPUT_PATHS`와 `validate_path(write=True)`가 있지만 출력 위치를 정하는 코드는 이 함수를 부르지 않는다 [17].

**한계.** 서버가 정한 위치가 `case_id` 값을 따라 사건·분석 폴더 밖으로 가는 경로가 있다 [4][5][6][11].
`sigma_hunt`·`hayabusa_hunt`·`extract_shimcache`·`generate_report`와 `build_timeline`의 폴더 부분은 `case_id` 인자를 검사하지 않고 경로에 넣는다 [4][5][6][11].
`sigma_hunt`와 `build_timeline`에 상위 폴더로 가는 `case_id`를 주자 분석 폴더 밖에 결과 파일을 썼다 [18].
버전 기준 Hayabusa v4.1.0에는 `csv-timeline` 명령이 없어 `hayabusa_hunt`는 `case_id`로 정한 폴더를 만들지만 CSV는 쓰지 않는다 [4][19].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.
manifest의 `case_id`도 검사 없이 디스크·메모리 아티팩트 폴더 이름에 들어간다 [1][9].
이 경로는 코드로만 따라갔고 실행하지 않았다.

### D04.03 파생물 ID로만 수정·삭제

**구현.** 이 방식은 발견사항의 모순 표시에 적용된다 [20][21].
`flag_discrepancy`는 서버가 매긴 발견사항 ID 두 개를 받아 상태에서 찾고 하나라도 없으면 오류를 돌려준다 [20].
두 발견사항의 `contradicted_by`에 서로의 ID를 더해 그 자리에서 고친다 [20].
`compare_disk_and_memory`가 모순을 찾았을 때도 발견사항 ID로 대상을 골라 `contradicted_by`를 고친다 [21].
파일 파생물을 고치거나 지우는 MCP 도구는 없다.

### D04.04 이름·확장자·충돌 검사

**구현.** 이 방식은 `extract_windows_artifacts`가 이미지 안 이름으로 짓는 파일 이름에 적용된다 [10][22].
같은 호출 안에서 앞서 정한 대상 경로와 같은 이름이 다시 나오면 그 파일을 꺼내지 않고 건너뛴다 [22].
건너뛴 파일은 `failures`나 `data_gaps`에 남기지 않는다 [22].
디스크에 같은 이름의 파일이 이미 있는지는 보지 않고 `wb` 모드로 연다 [22].
이름의 다른 문자는 거부하지 않고 `_`로 바꾼다 [10].
`load_memory`는 보관 파일 안 항목 이름을 검사하지 않고 보관 파일 전체를 `7z`로 푼다 [15].

**한계.** 대상 이름이 이미지 안 경로의 마지막 조각만으로 정해지므로 다른 폴더에 있는 같은 이름의 파일은 처음 나온 것만 꺼내진다 [10][22].
사용자 이름을 붙이는 `NTUSER.DAT` 계열만 이 경우에서 벗어난다 [10].

```python
def _dump_identifier(dump_path: str) -> str:
    """Derive a filename-safe identifier from a memory dump path.

    E.1: in multi-dump cases (enterprise scope with
    one .img per host), pslist/psscan artifacts must be partitioned per
    dump so the gate's psscan_only_count comparison pairs the right
    pslist with the right psscan. Identifier is the basename minus
    extension, with non-safe characters replaced.
    """
    name = Path(dump_path or "").stem or "dump"
    import re as _re
    return _re.sub(r"[^A-Za-z0-9._-]", "_", name)[:64] or "dump"
```
