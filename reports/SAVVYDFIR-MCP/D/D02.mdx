# D02 파생물 추적

### D02.01 ID·경로 참조

**구현.** 이 방식은 `_finalize_tool_response`를 거치는 도구의 실행 기록, 그 도구가 만든 발견사항, 모델이 기록한 발견사항에 적용된다 [1][2][3].
`SafeRunner`는 실행마다 `E-NNN` 실행 ID를 매기고 호출 기록 `audit.jsonl`의 시작 항목에 실행한 명령 문자열을 남긴다 [4].
그래서 외부 도구가 읽은 증거와 입력 파일의 경로는 명령 인자로 남는다 [4].
응답에 실행 ID가 있고 상태가 `error`가 아니면 `_finalize_tool_response`가 응답의 경로 필드와 `provenance`의 경로를 모아 `raw_evidence_refs`를 만든다 [1][5].
경로마다 붙이는 역할은 필드 이름과 경로 앞부분으로 정한다 [6].
`/evidence/`·`/mnt/`·`/media/` 아래 경로는 `input`, 분석 폴더·`/cases/`·`/tmp/` 아래 경로는 `derived`, `output_path`·`report_path`·`export_dir` 필드는 `output`이다 [6].
이 목록과 발견사항 ID는 호출 기록의 `linked` 항목과 `state.json`의 실행 기록에 함께 들어간다 [1].
도구가 만든 발견사항에는 그 실행 ID가 들어가고 `_sync_finding_provenance`가 같은 경로 목록을 발견사항의 `raw_evidence_refs`에 합친다 [1][7].
`get_provenance`는 `finding_ids_generated`에 그 발견사항 ID가 들어 있는 호출 기록 항목을 모두 돌려준다 [8].
`list_deleted_files`가 만든 발견사항으로 `get_provenance`를 부르자 시작·완료·`linked` 항목이 돌아왔고 `linked` 항목에 `deleted_files.json`의 경로와 해시가 있었다 [9].
`list_deleted_files`는 실행한 `fls` 명령 문자열을 JSON 파일 안에도 넣는다 [10].

상태 캐시로 앞 CSV를 다시 쓰는 호출은 완료 항목의 출력 요약에 앞 실행 ID를 문자열로 넣는다 [11].
이 호출의 응답 `provenance`에는 `cache_source_execution_id`가 실리지만 상태의 실행 기록에는 이 값이 남지 않았다 [12].
`extract_shimcache`·`extract_srum`은 `_finalize_tool_response`를 거치지 않고 `_record_tool_success_audit`로 CSV 경로 하나만 `derived`로 남긴다 [13].

모델이 `submit_finding`·`add_finding`으로 기록하는 발견사항은 근거 실행 ID를 `source_execution_id`·`execution_id` 인자로 받는다 [2][3].
이 값을 주지 않으면 `CaseStateManager.add_finding`이 같은 도구 이름의 마지막 실행 ID를 넣고 그런 실행이 없으면 아무 도구의 마지막 실행 ID를 넣는다 [14].
어느 방식으로 정했는지는 발견사항의 `confidence_support_inputs.execution_id_source`에 적는다 [14].

`compare_disk_and_memory`처럼 앞 도구의 CSV를 읽는 도구는 상태에서 그 도구의 마지막 CSV를 찾아 읽는다 [15].
읽은 CSV의 경로와 그 CSV를 만든 실행 ID는 응답과 기록에 남기지 않는다 [15].

**한계.** 참조가 근거 실행이나 지금 파일 내용에 이어지지 않는 경로가 있다.
모델이 기록한 발견사항으로 `get_provenance`를 부르면 근거 실행이 아니라 기록 호출의 항목만 돌아온다 [8][16].
`source_execution_id`를 준 `submit_finding` 발견사항은 `submit_finding` 자신의 시작·완료 항목만 돌려받았고 `add_finding` 발견사항은 빈 목록을 돌려받았다 [16].
실행 ID 없이 `add_finding`으로 기록하자 앞서 실행한 `list_deleted_files`의 실행 ID가 `auto_linked_latest_tool_execution`으로 들어갔다 [16].
같은 이름으로 파생물을 다시 만들면 앞 실행 기록의 경로가 새 내용을 가리킨다 [17].
`list_deleted_files`를 두 번 부르자 첫 실행 기록에는 첫 해시가 남았고 같은 경로의 파일은 둘째 실행의 내용으로 바뀌었다 [17].
`generate_graph`의 응답 필드 `graph_html_path`·`graph_json_path`와 `generate_report`의 `report_json_path`는 경로 목록에 들어가지 않는다 [5][18].
`merge_host_graphs`·`build_reports_index`·`load_memory`는 출력 경로를 실행 기록에 남기지 않는다 [19][20].
`load_memory`는 원래 ZIP 경로를 응답의 `original_path`에만 싣고 푼 덤프 경로는 응답의 `raw_dump_path`와 상태 파일의 `evidence_access` 분석 갈래 요약 글에 적는다 [20].

### D02.02 입출력 해시 연결

**구현.** 이 방식은 `_finalize_tool_response`를 거치는 도구 가운데 입력 파일 경로를 응답의 `provenance.artifact_paths`에 싣는 도구에 적용된다 [5][21].
`extract_mft_timeline`은 `$MFT`, `get_amcache`는 `Amcache.hve`, `list_processes` 같은 메모리 도구는 메모리 덤프 파일을 이 목록에 싣는다 [21].
`_derive_artifact_hashes`는 `input` 역할이 아닌 경로가 파일이면 내용 전체의 SHA-256을 계산해 `artifact_hashes`에 `role: output`으로 넣는다 [22][23].
`artifact_paths`의 입력 파일이 `/evidence/`·`/mnt/`·`/media/` 밖에 있으면 `derived`로 분류되므로 출력 CSV와 같은 기록에 입력 해시도 들어간다 [6][22].
`extract_mft_timeline`의 실행 기록에는 사건 폴더 CSV의 해시와 입력 `$MFT`의 해시가 둘 다 `role: output`으로 들어갔다 [24].
`input` 역할 경로는 다시 해시하지 않는다 [22].
앞 실행 기록에 같은 경로의 해시가 있으면 그 값을 입력 해시로 쓰고 없으면 `hash_status: unhashed_primary_input`만 붙인다 [22][25].
`verify_integrity`의 결과는 알고리즘이 SHA-256일 때만 이렇게 다시 쓸 해시 기록이 된다 [26].
입력이 폴더인 `extract_prefetch`·`summarize_evtx`·`extract_registry_run_keys`는 폴더를 해시하지 않으므로 입력 해시가 없다 [21][23].

**한계.** 입력 해시가 빠지거나 입력과 출력이 구별되지 않는 경로가 있다.
입력 해시에도 `role: output`이 붙어 기록만으로는 어느 해시가 입력인지 가리지 못한다 [22][24].
`/evidence/`·`/mnt/`·`/media/` 아래 입력 파일은 앞 실행의 해시 기록이 없으면 해시 없이 경로만 남는다 [22].
`verify_integrity`는 `ewfverify`를 다이제스트 옵션 없이 실행하므로 E01 이미지를 검사해도 SHA-256 해시 기록이 생기지 않았다 [27].

### D02.03 파생물 측 manifest

**구현.** 이 방식은 재사용 판단을 하는 디스크 아티팩트 추출 도구의 CSV에 적용된다 [28].
그런 도구는 `extract_mft_timeline`, `extract_usn_journal`, `summarize_evtx`와 사용자 활동 추출 도구 8개다 [28].
이 도구들은 파싱이 성공하면 CSV 곁에 `<CSV 이름>.savvyreuse.json`을 쓴다 [29].
이 파일에는 도구 이름 `tool`, 파서 이름과 버전 문자열 `parser_signature`, 인자 JSON의 SHA-256 `parameter_fingerprint`, CSV 경로가 들어간다 [29].
입력은 `source_set_fingerprint`에 파일·폴더마다 경로, 크기, `mtime_ns`로 적고 그 목록 전체의 SHA-256을 함께 적는다 [30].
입력 파일 내용의 해시, 출력 CSV의 해시, 실행 ID, 만든 시각은 들어가지 않는다 [29][30].
`extract_mft_timeline`을 실행하자 CSV 곁에 입력 `$MFT`의 경로·크기·`mtime_ns`를 적은 부속 자료가 생겼다 [24].
`extract_prefetch`·`get_amcache`·`extract_registry_run_keys`·`list_deleted_files`와 메모리·탐지·보고서 도구의 파일 곁에는 이런 파일을 두지 않는다 [31].

**한계.** 부속 자료를 쓰다 `OSError`가 나면 알리지 않고 부속 자료 없이 끝난다 [29].

```python
def _guess_ref_role(path: str, *, key_hint: Optional[str] = None) -> str:
    hint = (key_hint or "").lower()
    normalized = _normalize_path_ref(path) or path
    if hint == "handle":
        return "handle"
    if hint in {"csv_path", "storage_path"}:
        return "derived"
    if hint in {"output_path", "report_path", "export_dir"}:
        return "output"
    if normalized.startswith(("/evidence/", "/mnt/", "/media/")):
        return "input"
    if normalized.startswith((str(_ANALYSIS_DIR), "/cases/", "/tmp/")):
        return "derived"
    if hint.endswith("_path"):
        return "input"
    return "derived"
```

```python
def _sha256_file(path: str) -> Optional[str]:
    target = Path(path)
    if not target.is_file():
        return None
    digest = hashlib.sha256()
    with target.open("rb") as fh:
        for chunk in iter(lambda: fh.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()
```
