# L01 기록 방식

### L01.02 도구별 기록 호출

**구현.** 이 방식은 본문이 기록 함수나 기록하는 도우미 함수를 부르는 도구와 결과를 돌려주기 전에 `_finalize_tool_response`를 부르는 도구에 적용된다 [1].
서버는 FastMCP 서버를 만들 때 미들웨어를 붙이지 않고 도구 65개를 `@mcp.tool()`로 하나씩 등록한다 [2].
그래서 모든 호출이 지나며 항목을 쓰는 공통 단계는 없다.
모든 항목은 프로세스에 하나인 `AuditLogger` 객체 `_audit_logger`를 거쳐 `SAVVYDFIR_ANALYSIS_DIR`(값이 없으면 `./analysis`) 아래 `audit.jsonl`에 한 줄씩 덧붙는다 [3].

도구 본문은 다음 방법으로 항목을 쓴다.

- `compare_disk_and_memory`, `find_temporal_clusters`, `generate_graph`, `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`, `extract_pca`, `extract_windows_artifacts`, `record_analysis_lane`, `submit_finding`, `generate_report`, `sigma_scan`, `run_analysis`는 본문에서 `log_execution`과 `log_result`를 불러 `started`·`completed` 항목을 쓴다 [4].
- 도우미 `_record_tool_success_audit`, `_record_artifact_absent_audit`, `_persist_parser_retry_execution`은 `started`·`completed` 항목을 잇달아 쓴다 [5].
- 이 도우미는 `extract_shimcache`·`extract_srum`의 성공 경로, `extract_prefetch`·`get_amcache`·`extract_pca`·`extract_shimcache`·`extract_srum`의 아티팩트 없음 경로, `extract_mft_timeline`·`summarize_evtx`의 재추출 필요 경로가 부른다 [5].
- 캐시에 남은 파생물을 다시 쓰는 경로는 `record_cache_hit`로 `CACHE_HIT <도구 이름>`을 명령 글로 담은 두 항목을 쓴다 [6].
- `_finalize_tool_response`는 응답 상태가 `error`가 아니고 응답에 `execution_id`가 있으면 그 ID로 `linked` 항목을 쓴다 [7].
- 사건이 열려 있지 않으면 상태 파일에서 실행을 찾는 처리가 먼저 실패해 `linked` 항목을 쓰지 않고 그 예외 문구를 응답의 `phase7_link_warning`에 넣는다 [7].
- 사건이 열려 있으면 `_finalize_tool_response`는 그 앞에서 `_attach_heuristic_slice`로 아티팩트 지식 발췌를 응답에 붙이고 `context_bundle` 항목을 쓴다 [7][8].
- `get_heuristic`과 `prepare_hypothesis_context`는 `_emit_context_bundle_for_slice`로 `context_bundle` 항목을 쓴다 [9].
- `compare_disk_and_memory`가 발견사항 사이의 모순을 찾으면 `_add_contradiction`이 `log_correction`으로 `correction` 항목을 쓴다 [10].

`compare_disk_and_memory`를 부르자 같은 ID의 `started`·`completed`·`linked` 항목이 남았고 `get_heuristic`을 부르자 `context_bundle` 항목 하나가 남았다 [11].

다음 도구 22개는 어떤 항목도 쓰지 않는다 [12].

- 사건 상태를 읽거나 안내만 돌려주는 도구 15개다: `get_provenance`, `read_state`, `get_finding`, `get_findings`, `export_trace`, `summarize_run`, `describe_tool_catalog`, `serve_graph`, `get_investigation_gates`, `coverage_report`, `classify_missing_artifact`, `environment_preflight`, `detect_triage_layout`, `query_sigma_results`, `_ntfs_mount_argv` [12].
- 사건 상태를 바꾸는 도구 4개다: `start_investigation`, `add_finding`, `flag_discrepancy`, `record_hypotheses` [12].
- 외부 프로그램을 실행하는 도구 3개다: `merge_host_graphs`와 `build_reports_index`는 서버의 `scripts/` 스크립트를, `load_memory`는 `file`과 `7z`를 실행한다 [12].

이 가운데 18개를 실행하자 `audit.jsonl`에 항목이 늘지 않았고 `build_reports_index`는 스크립트를 실행하고도 항목을 남기지 않았다 [13].
`query_sigma_results`는 응답에 `execution_id`를 싣지 않아 `_finalize_tool_response`를 거쳐도 항목이 생기지 않는다 [7][12].
없는 도구 이름으로 온 호출은 FastMCP가 거부하고 항목을 남기지 않았다 [11].

**한계.** `_finalize_tool_response`는 첫머리에서 메모리 감시 함수 `_memory_watchdog`를 부른다 [7][14].
이 함수는 서버 프로세스의 메모리가 4096MB를 넘으면 `memory.watchdog` 항목을 쓰도록 되어 있지만 `log_execution`에 없는 인자 이름(`tool`, `status` 등)으로 부른다 [14][15].
그래서 `TypeError`가 나고 함수는 예외를 처리해 아무것도 하지 않는다 [14].
메모리 값을 5000MB로 바꿔 도구를 부르자 감시 항목은 남지 않았고 같은 인자로 `log_execution`을 부르자 `TypeError`가 났다 [16].

### L01.03 공통 실행 함수에서 기록

**구현.** 이 방식은 실행기 `SafeRunner.run`으로 외부 명령을 실행하는 도구에 적용된다 [17].
서버는 불러올 때 `init_all_tools`로 도구 모듈의 실행기에 같은 `_audit_logger`를 넘긴다 [18].
`SleuthKitRunner`, `EZToolsRunner`, `VolatilityRunner` 같은 실행기는 `SafeRunner`를 물려받아 명령 목록을 만들고 `run`에 넘긴다 [17].
`run`은 금지 명령과 경로 검사를 통과한 명령마다 `next_execution_id`로 ID를 받아 실행 전에 `started` 항목을, 끝난 뒤 `completed` 항목을 쓴다 [19].
증거 확인, 메모리 분석, 디스크 아티팩트 추출, 타임라인, YARA 도구가 이 실행기를 쓴다 [18].
한 호출이 실행기를 여러 번 부르면 실행마다 ID와 항목이 따로 생긴다 [20].
`extract_registry_run_keys`는 시스템 하이브와 사용자 `NTUSER.DAT`마다 RECmd를 실행한다 [20].
`verify_integrity`를 부르자 `ewfverify` 실행 전후의 `started`·`completed` 항목과 `linked` 항목이 같은 ID로 남았다 [11].

실행기를 거치지 않고 `subprocess`를 직접 부르는 도구와 함수도 있다 [21].

- `generate_graph`, `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`, `extract_shimcache`, `extract_srum`, `extract_windows_artifacts`, `run_analysis`는 본문의 기록 호출로 항목을 쓴다 [4][5].
- `merge_host_graphs`, `build_reports_index`, `load_memory`는 항목을 쓰지 않는다 [12].
- 하이브 로그를 반영하는 `replay_hive_with_rla`는 `rla`를 직접 실행하고 따로 항목을 쓰지 않는다 [21].

**한계.** `run`은 `subprocess.run`의 시간 초과만 처리하고 다른 예외는 처리하지 않는다 [22].
그래서 실행 파일이 없으면 `completed` 항목 없이 예외가 호출한 쪽으로 올라간다 [22].
Volatility 3 실행 파일이 서버가 찾는 위치에 없는 환경에서 `list_processes`를 부르자 `started` 항목 하나만 남고 응답은 실행기 오류였다 [23].

### L01.04 클라이언트의 MCP 호출 기록

**구현.** 이 방식은 저장소의 Claude Code 설정 `.claude/settings.json`으로 Claude Code를 실행할 때만 적용된다 [24].
이 설정은 모든 도구 호출 뒤(PostToolUse)에 `scripts/agent_trigger.py`를 실행한다 [24].
`agent_trigger.py`의 `process_event`는 호출마다 `_debug_trace`로 시각, 도구 이름, 이벤트 키 목록, 세션 ID를 한 줄 덧붙인다 [25].
이 파일은 `SAVVYDFIR_HOOK_DEBUG_LOG`가 정하고 값이 없으면 `/tmp/savvydfir_hook_debug.log`다 [25].
MCP 도구는 이름이 `mcp__savvydfir__`로 시작해 이 줄에서 식별된다 [26].
이 줄에는 인자, 결과, 서버 기록의 `execution_id`가 없다 [25].
훅은 결과를 보고 하위 에이전트에게 분석을 맡겨야 한다고 판단하면 `delegation_required` 줄에 시각, 세션 ID, lane, 하위 에이전트, 도구 이름을 담아 `/tmp/savvydfir_delegation_ledger.jsonl`에 쓴다 [27].
시험용 PostToolUse 입력 세 개를 주자 debug log에 MCP 도구 두 개와 `Bash` 한 개의 줄이 남았고 `extract_prefetch` 결과에는 `delegation_required` 줄 하나가 남았다 [26].
`Bash` 같은 클라이언트 도구의 줄도 같은 파일에 남지만 이 상세의 근거는 아니다 [26].
다른 MCP 클라이언트로 서버에 붙으면 이 기록은 남지 않는다.
`.claude/hooks/post-tool-use.py`도 `agent_trigger.py`를 실행하지만 `settings.json`에 등록되어 있지 않다 [28].
Stop 훅 `stop.py`가 서버의 `audit.jsonl`에 덧붙이는 waiver 항목은 MCP 도구 호출 기록이 아니다 [29].

**한계.** 두 파일 쓰기는 실패해도 알리지 않는다 [25][27].
`delegation_ledger.append_row`는 세션 ID를 찾지 못하면 줄을 쓰지 않는다 [27].
두 파일의 기본 경로는 `/tmp`의 고정 이름이어서 여러 사건과 세션의 줄이 한 파일에 이어진다 [25][27].

```python
def _debug_trace(message: str) -> None:
    """Append a single timestamped line so we can verify hook invocation
    from the agent's actual run (independent of audit.jsonl).
    Best-effort; never raises.
    """
    try:
        from datetime import datetime as _dt, timezone as _tz

        line = f"{ts} {message}\n"
        fd = os.open(
            _DEBUG_LOG_PATH,

            0o666,
        )

            os.write(fd, line.encode("utf-8"))
        finally:
            os.close(fd)
        try:
            os.chmod(_DEBUG_LOG_PATH, 0o666)
        except OSError:
            pass
```

```python
def _audit_append(record: dict, audit_path: Path) -> tuple[bool, str]:
    """Append a JSONL record to audit.jsonl, fsync, and return (ok, error_text).

    fsync is required because crash durability matters when a record is the
    only artifact of an audited waiver consumption.
    """
    try:
        with open(audit_path, "a", encoding="utf-8") as fh:
            fh.write(json.dumps(record) + "\n")
            fh.flush()
            try:
                os.fsync(fh.fileno())
            except OSError as exc:
                # fsync may legitimately fail on non-disk fs (procfs, tmpfs
                # variants). Treat as soft warning, not fatal — the data is
                # in the page cache and will be visible to the next reader.
                return (True, f"fsync_warning:{exc}")
        return (True, "")
    except OSError as exc:
        return (False, f"audit_append_failed:{exc}")
```
