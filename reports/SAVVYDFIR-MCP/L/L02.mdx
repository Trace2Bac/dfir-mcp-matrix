# L02 기록 구성

### L02.01 MCP 요청 기록

**구현.** 이 방식은 본문이 항목을 쓰면서 받은 인자를 그대로 `parameters`에 넣는 도구에 적용된다 [1].
`compare_disk_and_memory`, `find_temporal_clusters`, `generate_graph`, `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`, `extract_pca`, `generate_report`, `sigma_scan`은 도구 인자를 모두 받은 값 그대로 `parameters`에 담는다 [1].
같은 항목의 `command_line`에는 도구 이름과 인자를 함수 호출 모양의 글로 적는다 [1].
`tool` 필드에는 MCP 도구 이름 대신 `correlation.compare_disk_and_memory`처럼 영역 이름을 붙인 서버 안 이름이 들어간다 [1][2].
형식이 틀린 `response_format`을 `generate_report`에 주자 `started` 항목의 `parameters`에 그 값이 그대로 남았다 [3].

실행기 `SafeRunner.run`을 거치는 도구의 항목에는 MCP 인자가 따로 남지 않는다 [4].
`run`의 `parameters` 기본값은 빈 `dict`이고 실행기 메서드는 이 값을 넘기지 않는다 [4][5].
그래서 이 도구들의 `parameters`는 비어 있고 인자 값은 `command_line` 안에만 들어간다 [3].
`verify_integrity`와 `list_processes`의 항목에서 `parameters`는 `{}`였다 [3].

### L02.02 서버가 변환한 연산·인자 기록

**구현.** 이 방식은 본문이나 도우미가 인자를 바꾸거나 서버가 정한 값을 더해 `parameters`에 넣는 경로에 적용된다 [6].

- `record_analysis_lane`은 lane ID와 상태, 하위 에이전트 이름을 앞뒤 공백을 빼고 상태는 대문자로 바꾼 값으로 남긴다 [6].
- `extract_windows_artifacts`는 아티팩트 계열 목록을 소문자로 바꾸고 정렬한 `families`를 남긴다 [7].
- `run_analysis`는 실제 경로로 바꾼 `data_path`와 질의의 SHA-1, 서버 설정의 메모리 상한과 시간 제한을 남긴다 [8].
- `submit_finding`은 받은 인자 일부와 정리한 하위 에이전트 이름, 근거 실행 ID가 비었을 때 저장된 발견사항에서 가져온 `source_execution_id`를 남긴다 [9].
- `_record_artifact_absent_audit`은 서버가 확인한 아티팩트 이름과 확인한 경로를 `parameters`로 남긴다 [10].
- 캐시 재사용 항목은 캐시 키 계산에 쓴 값과 `_cache_key`를 남긴다 [11].

### L02.03 외부 실행 명령 기록

**구현.** 이 방식은 실행기 `SafeRunner.run`으로 외부 명령을 실행하는 도구에 적용된다 [4].
`run`은 실제로 넘기는 인자 목록을 공백으로 이어 `command_line`을 만들고 `started`·`completed` 항목에 모두 넣는다 [4].
`list_processes`의 항목에는 `/usr/local/bin/vol -f <덤프 경로> -r json windows.pslist`가 남았다 [12].
`extract_registry_run_keys`의 항목에는 서버가 하이브를 복사해 둔 임시 폴더와 `--sync`까지 RECmd에 넘긴 인자가 남았다 [12].

실행기를 거치지 않고 외부 프로그램을 실행하는 도구는 인자 목록을 그대로 남기지 않는다 [13].

- `generate_graph`, `sigma_hunt`, `hayabusa_hunt`, `analyze_vss`는 `command_line`에 MCP 도구 호출 모양의 글만 적고 실제로 실행한 Python 스크립트, Chainsaw, Hayabusa, `mmls`·`ewfmount`·`vshadowinfo` 등의 인자는 남기지 않는다 [13].
- `extract_shimcache`와 `extract_srum`은 실행한 단계를 사람이 읽도록 이어 쓴 글을 `command_line`에 적는다 [14].
- `extract_windows_artifacts`는 `fls` 명령 한 줄만 적고 아티팩트마다 실행하는 `icat`은 적지 않는다 [15].
- `merge_host_graphs`, `build_reports_index`, `load_memory`는 항목을 쓰지 않는다 [16].

**한계.** `command_line`은 인자를 공백으로 이어 공백이 들어간 인자 하나와 인자 여러 개를 기록에서 가를 수 없다 [4].

### L02.05 결과 상태·실행 시점 기록

**구현.** 이 방식은 `started`·`completed` 항목을 쓰는 모든 경로에 적용된다 [17].
두 항목 모두 UTC 시각 `timestamp`를 담고 `completed` 항목은 종료 코드 `exit_code`와 걸린 시간 `duration_seconds`를 담는다 [17].
실행기는 시간 제한을 넘기면 `exit_code`를 -1로, `outputs_summary`를 `collection_timeout: …`으로 남긴다 [18].
서버 안에서 처리하는 도구는 예외 없이 끝나면 `exit_code` 0, 예외로 끝나면 1과 `error: <예외 문구>`를 남긴다 [19].
`audit.py` 설명은 `completed` 항목이 없는 `started` 항목을 서버가 실행 도중 멈춘 흔적으로 적는다 [20].

**한계.** 서버가 멈추지 않았는데도 `completed` 항목 없이 끝나는 경로가 있다 [21][22][23][3].

- 실행기는 시간 초과가 아닌 실행 예외에서 `completed` 항목을 쓰지 않는다 [21].
- `generate_report`는 `started` 항목을 쓴 뒤 `response_format`을 검사하고 틀리면 오류만 돌려준다 [22].
- `sigma_hunt`의 Chainsaw 시간 초과 경로와 `hayabusa_hunt`의 시간 초과 경로도 `completed` 항목 없이 오류를 돌려준다 [23].
- Volatility 3 실행 파일이 없는 환경의 `list_processes`와 형식이 틀린 `generate_report`는 `started` 항목만 남겼다 [3].

버전 기준 Hayabusa v4.1.0에서는 `csv-timeline` 명령이 없어 Hayabusa가 곧바로 종료 코드 2로 끝나므로 `hayabusa_hunt`는 시간 초과 경로가 아니라 `completed` 항목을 쓰는 실패 경로로 간다 [24][25].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.

`extract_windows_artifacts`는 `started` 항목 쓰기가 실패하면 `completed` 항목만 남긴다 [15].
`started` 항목 쓰기를 실패하게 하자 `completed` 항목 하나만 남았다 [26].

`_record_tool_success_audit`은 하이브나 데이터베이스를 처리한 뒤 `started`·`completed` 항목을 함께 쓴다 [27].
그래서 `extract_shimcache`와 `extract_srum`의 성공 항목은 `started` 시각이 작업이 끝난 뒤의 시각이다 [27].
`_utcnow_iso`는 초 단위까지와 밀리초를 `datetime.now`를 두 번 불러 따로 얻는다 [28].
그래서 두 호출 사이에 초가 바뀌면 기록 시각이 실제보다 1초 가까이 이를 수 있다 [28].

### L02.06 결과 참조·요약값 기록

**구현.** 이 방식은 `completed` 항목의 `outputs_summary`와 `linked` 항목에 적용된다 [18][29].
실행기는 `outputs_summary`에 종료 코드, 표준 출력 줄 수, 표준 오류 앞 120자를 이어 500자까지 남긴다 [18].
표준 출력 자체나 그 해시는 항목에 없다 [18].
서버 안에서 처리하는 도구는 `0 discrepancies found`처럼 도구마다 정한 요약 글을 남긴다 [19].
`verify_integrity`의 `completed` 항목에는 `exit=0; stdout_lines=1`이 남았다 [3].

`_finalize_tool_response`는 응답에서 입력과 파생물 경로를 모아 `linked` 항목의 `artifact_refs`·`raw_evidence_refs`에 남긴다 [29][30].
경로의 역할은 응답 키 이름과 경로 위치로 정한다 [30].
`csv_path`·`storage_path`는 파생물, `output_path`·`report_path`는 출력, `/evidence/`·`/mnt/`·`/media/` 아래 경로는 입력, 분석 폴더·`/cases/`·`/tmp/` 아래 경로는 파생물로 본다 [30].
입력이 아닌 경로가 파일이면 그때 파일을 읽어 SHA-256을 계산하고 `artifact_hashes`에 경로와 함께 넣는다 [30].
그래서 해시는 분석 도구가 쓴 CSV 같은 원래 출력 파일이나 서버가 파싱 결과를 쓴 파일의 해시이고 `linked` 항목을 쓰는 때의 내용이다 [30].
입력 경로는 다시 해시하지 않고 `verify_integrity`가 남긴 SHA-256이 상태 파일에 있으면 그 값을 넣는다 [30].
실패 응답, `execution_id`가 없는 응답, 사건이 열려 있지 않을 때의 응답에는 `linked` 항목이 없다 [29].

**한계.** 응답의 `dump_path`·`image_path` 같은 키가 `/cases/`나 `/tmp/` 아래의 증거 파일을 가리키면 그 파일을 파생물로 보고 파일 전체를 해시해 출력 해시로 남긴다 [30].
이 경로는 코드로만 확인했고 실행하지 않았다.

### L02.07 호출 ID로 항목 연결

**구현.** 이 방식은 `execution_id`를 받는 모든 항목에 적용된다 [31].
`next_execution_id`는 `E-001`처럼 늘어나는 ID를 주고 한 실행의 `started`·`completed`·`linked` 항목은 같은 ID를 쓴다 [31][4][29].
`_finalize_tool_response`가 붙이는 `context_bundle` 항목도 그 응답의 `execution_id`를 쓴다 [32].
`extract_registry_run_keys` 호출 하나의 `started`·`completed`·`context_bundle`·`linked` 항목이 모두 `E-002`로 남았다 [12].
상태 파일 `state.json`의 실행 행은 같은 ID와 그 실행의 `started`·`completed`·`linked` 항목 해시를 담는다 [33].

**한계.** 실행 ID는 실행기 실행 하나나 본문의 기록 묶음 하나에 붙고 MCP 호출 하나를 가리키는 ID는 없다 [4][31].
그래서 한 호출이 실행기를 여러 번 부르면 각 실행은 다른 ID를 받고 그 ID들을 잇는 필드가 없다 [34].
`extract_registry_run_keys`가 사용자 하이브마다 실행한 RECmd의 항목은 응답의 `execution_id`와 다른 ID를 받는다 [34].

`compare_disk_and_memory`가 쓰는 `correction` 항목에는 그 호출의 실행 ID가 들어가지 않는다 [35].
`_add_contradiction`은 실행 ID를 받지 못하면 상태 파일에서 가장 최근의 `compare_disk_and_memory` 실행 ID를 찾는다 [35].
이 호출의 실행 행은 비교가 끝난 뒤 상태 파일에 들어가므로 찾은 ID는 앞선 호출의 ID다 [35][36].
앞선 호출이 없으면 발견사항의 실행 ID나 `E-correlation`을 쓴다 [35].
이 동작은 코드로만 확인했고 실행하지 않았다.

`get_heuristic`과 `prepare_hypothesis_context`의 `context_bundle` 항목은 실행 ID 자리에 `CTX-001` 같은 지식 발췌 ID를 넣는다 [37].

    def next_execution_id(self) -> str:
        """Allocate and return the next monotonic execution ID.

        Returns
        -------
        str
            An ID of the form ``E-001``, ``E-002``, … (zero-padded to at
            least 3 digits).  IDs are allocated atomically under the
