# R03 분석 상태 알림

### R03.01 구조화 status·error

**구현.** 이 방식은 모든 MCP 도구의 응답에 적용된다.
도구 함수는 결과를 `dict`로 돌려주고 그 `status` 필드로 성공과 실패를 가른다 [1].
도구 래퍼 대부분은 도구 함수가 낸 예외를 처리해 `status`가 `error`이고 예외 문구를 `error`에 담은 `dict`로 돌려준다 [1].
`status`의 성공 값은 도구마다 `success`·`ok`로 다르고 실패는 `error`다 [1][2].
오류 문구를 담는 키도 도구마다 `error`나 `error_message`로 다르다 [1][3].
래퍼의 `try` 밖에서 예외가 나면 FastMCP가 MCP 오류 결과 `isError`로 오류 문구를 돌려준다 [4][5].
(실행 확인) 실행 전 기록 쓰기가 실패한 `compare_disk_and_memory`와 `generate_report`는 `isError` 결과로 끝났다 [5].

**한계.** `_finalize_tool_response`는 응답과 호출 기록을 잇는 처리에서 예외가 나면 `phase7_link_warning`에 문구만 남기고 `status`를 바꾸지 않는다 [6].
(실행 확인) 사건을 열지 않고 `extract_powershell_history`를 부르자 `status`는 `success`이고 `phase7_link_warning`에 상태 관리자가 초기화되지 않았다는 문구가 실렸다 [6].

### R03.02 찾지 못함과 실패 구분

**구현.** 이 방식은 사용자 활동 도구, 탐지 도구, 아티팩트가 없는 경우를 기록하는 추출 도구, `_warn_if_empty`를 거치는 추출 도구에 적용된다 [7][8][9][10].
사용자 활동 도구(`extract_shellbags`·`extract_lnk_files`·`extract_jump_lists`·`extract_browser_history`·`extract_registry_fileaccess`·`extract_recycle_bin`·`extract_powershell_history`·`extract_scheduled_tasks`)는 결과가 0행이면 세 상태 값으로 나눈다 [7].
찾은 아티팩트가 없으면 `artifact_absent`, 찾았지만 파싱이 실패했으면 `collection_failed`, 찾아서 파싱했는데 행이 없으면 `no_data`다 [7].
`extract_recycle_bin`은 휴지통이 옛 형식 `INFO2`만 있으면 `tool_incompatible`을 돌려준다 [11].
이 도구들은 `image_path`가 Windows 볼륨이 아니면 `error`를 돌려준다 [12].
(실행 확인) `extract_powershell_history`에 사용자 폴더만 있는 볼륨을 주자 `artifact_absent`를, Windows 볼륨이 아닌 폴더를 주자 `error`와 `reason` `no_windows_volume_at_image_path`를 돌려줬다 [7][12].
`sigma_hunt`·`hayabusa_hunt`·`query_sigma_results`는 일치가 없으면 `no_hits`를 돌려주고 Chainsaw나 Hayabusa가 없으면 `tool_not_found`를 돌려준다 [8][13].
`extract_prefetch`·`get_amcache`·`extract_pca`·`extract_shimcache`·`extract_srum`은 아티팩트가 없다고 판단하면 `artifact_absent`와 확인한 경로 `checked_paths`를 돌려준다 [9].
`extract_prefetch`·`get_amcache`는 아티팩트 파일을 찾지 못하면 입력 경로 아래에서 Windows 폴더를 대소문자와 관계없이 찾는다 [14][15].
Windows 폴더를 찾으면 `artifact_absent`를 돌려주고 찾지 못하면 `error`를 돌려준다 [15].
(실행 확인) Windows 폴더만 있는 시험 폴더에서는 두 도구가 `artifact_absent`를, Windows 폴더가 없는 시험 폴더에서는 `error`를 돌려주었다 [16].
`_warn_if_empty`는 결과가 0건인데 입력 경로가 있으면 `status`를 `warning`으로 바꾸고 경고 문구를 붙인다 [10].

**한계.** `get_finding`은 없는 발견사항 ID를 받으면 `found`를 거짓으로 두지만 `status`도 `error`로 돌려준다 [17].
`_warn_if_empty`는 `min_expected` 인자를 받지만 비교에 쓰지 않고 0건일 때만 `warning`으로 바꾼다 [10].
`_windows_volume_resolves`는 Windows 폴더를 찾다가 예외가 나면 찾은 것으로 보므로 두 도구는 이때 `artifact_absent`를 돌려준다 [14].
`extract_shimcache`·`extract_srum`·`extract_pca`는 Windows 폴더를 확인하지 않고 파일이 없으면 `artifact_absent`를 돌려준다 [18].
Windows 폴더가 없는 시험 폴더에서도 `extract_srum`은 `artifact_absent`를 돌려주었다 [16].
`extract_registry_run_keys`에 `sync_batch`를 참으로 주면 시스템 하이브를 처리하는 RECmd 실행은 배치 파일을 내려받은 뒤 하이브를 처리하지 않고 종료 코드 0으로 끝난다 [19][20].
서버는 이 실행의 CSV가 없어도 빈 목록으로 읽고 사용자 하이브 행이 있으면 `status`를 `success`로 돌려준다 [21][22].
RECmd의 이 동작은 소스로 확인했고 RECmd를 실행하지 않았다.
버전 기준 Hayabusa v4.1.0에는 서버가 넘기는 `csv-timeline` 명령이 없어 `hayabusa_hunt`는 일치가 있든 없든 `no_hits`가 아니라 `error`를 돌려준다 [23][24].
Hayabusa의 이 동작은 소스로 확인했고 Hayabusa를 실행하지 않았다.

### R03.03 입력별 성공·실패·생략 목록

**구현.** 이 방식은 `extract_windows_artifacts`와 사용자 활동 도구에 적용된다 [25][26].
`extract_windows_artifacts`는 아티팩트 계열마다 꺼낸 파일 경로 목록을 `extracted`에 싣는다 [25].
꺼내지 못한 파일은 계열, 증거 안 경로, 메타데이터 주소, 표준 오류를 담아 `failures`에 하나씩 싣는다 [27].
파일을 하나도 꺼내지 못한 계열은 `families_empty`에 싣고 중요한 파일의 실패는 `critical_failures`와 `data_gaps`에 따로 싣는다 [25].
상위 `status`는 실패나 빈 계열이 있으면 `partial_success`, 꺼낸 파일이 하나도 없으면 `warning`이다 [28].
사용자 활동 도구는 파싱에 실패한 파일마다 프로필, 파일 경로, 상태, 이유를 `parser_failures`에 싣는다 [26].
이때 행이 일부 있으면 `status`를 `partial_collection`으로 두고 `note`에 빠진 출처를 적는다 [29].

### R03.04 시간 초과·부분 완료 표시

**구현.** 이 방식은 `sigma_hunt`에 적용된다 [30].
`sigma_hunt`는 EVTX 폴더 전체를 대상으로 한 Chainsaw 실행이 300초 안에 끝나지 않으면 정해 둔 채널 파일 하나로 다시 실행한다 [30].
이때 응답에 `fallback_applied`를 참으로, `fallback_reason`을 `directory_timeout`으로 싣고 다시 실행할 채널별 호출 목록을 `recommended_next_calls`에 싣는다 [31].
다른 도구의 시간 초과는 `status`가 `error`인 응답의 문구로만 알린다 [32].
psort와 YARA는 "timed out" 문구를 `error`에 싣고 `run_analysis`는 시간·메모리 상한 초과를 `error` 문구로 알린다 [32].
`extract_windows_artifacts`는 파일 하나를 꺼내다 300초가 지나면 그 파일의 `failures` 항목 `stderr`에 "icat timeout after 300s"를 적는다 [27].

**한계.** 다시 실행한 결과의 `status`는 일치 여부에 따라 `success`나 `no_hits`이고 부분 결과라는 사실은 `fallback_*` 필드에만 있다 [31].

def _warn_if_empty(result: dict, tool_name: str, path: str, min_expected: int = 1) -> dict:
    """Upgrade status to 'warning' if records=0 but path exists.

    Silent 0-record success is the worst failure mode - it looks like
    a clean system when the tool silently failed. This makes it loud.
    """
    count = result.get("records_count", len(result.get("data", [])))
    if count == 0 and os.path.exists(path):
        result = dict(result)
        result["status"] = "warning"
        result["warning"] = (
            f"{tool_name} found 0 records but path exists: {path}. "
            f"Verify mount point and tool parameters. "
            f"A clean Windows system should always have records here."
        )
    return result
```

def _windows_volume_resolves(image_path: str) -> bool:
    """True if a Windows volume root resolves (case-insensitive) under image_path.

    1c positive-absence guard (review 2026-06-06): only call an artifact
    'absent' when the Windows root actually resolves but the artifact is missing
    (genuine absence, e.g. pre-Win8 Amcache, Server-OS Prefetch). If the root
    itself is unresolvable it is a path/mount FAILURE (retryable error), NOT
    absence - prevents the XP uppercase-path (WINDOWS) false-absence overclaim.
    On any internal error, returns True to preserve genuine documented-absence.
    """
    try:
        from sift_mcp.tools.disk import _candidate_windows_volume_roots, _ci_resolve
        roots = _candidate_windows_volume_roots(str(image_path))
        return any(_ci_resolve(r, "Windows") is not None for r in roots)
    except Exception:
        return True
```
