# R01 결과 가공

### R01.01 가공 없이 전달

**구현.** 이 방식은 `sigma_hunt`의 `detailed` 응답과 `analyze_vss`에 적용된다 [1][2].
`sigma_hunt`는 `response_format`이 `detailed`이면 Chainsaw JSON에서 읽은 hit 객체 가운데 기준 등급 이상인 것을 바꾸지 않고 `hits`에 싣는다 [1].
`analyze_vss`는 `vshadowinfo`의 표준 출력 끝부분을 바꾸지 않고 `vshadowinfo_output`에 싣는다 [2].
그 밖의 외부 도구 출력은 아래처럼 서버가 파싱한 필드로 응답에 실린다.

### R01.02 구조화 파싱·필드 선택

**구현.** 이 방식은 외부 도구 출력을 읽는 디스크·메모리·탐지 도구에 적용된다.
EZ 도구 CSV를 읽는 도구는 행을 `MftEntry`·`EventRecord` 같은 pydantic 모델로 바꾼다 [3].
공통 응답 함수 `build_contract_response`를 거치는 도구는 앞 20개 레코드에서 도구마다 고른 필드만 `normalized_observations`에 싣는다 [4].
이 함수를 거치는 도구는 Prefetch·Amcache·MFT·EVTX·레지스트리 추출 도구와 `detect_injection`, `build_timeline`, `query_timeline`이다 [4].
`extract_mft_timeline`의 `normalized_observations`는 항목 번호, 이름, `$SI`·`$FN` 생성 시각, 삭제 여부만 싣는다 [4].
`summarize_evtx`는 이벤트 ID, 채널, 시각, 컴퓨터, provider만 싣는다 [4].
`summarize_evtx`는 EvtxECmd 행의 `PayloadData1`이나 `MapDescription`을 500자까지 `message_summary`에 두고 나머지 열을 `extra_fields`에 둔다 [5].
응답에 싣는 표본에서는 `ScriptBlockText`와 `PayloadData2`~`PayloadData6` 열을 빼고 1,024자를 넘는 값을 자른다 [5][6].
`sigma_hunt`와 `query_sigma_results`의 `actionable_hits`는 Chainsaw hit에서 규칙 이름, 등급, 이벤트 ID, 시각, 기법, 채널, 컴퓨터, 사용자, tactic을 골라 만든 값이다 [7].
`extract_shimcache`는 AppCompatCacheParser CSV에서 `CacheEntryPosition`·`Path`·`LastModifiedTimeUTC`·`Executed` 열만 읽어 항목을 만든다 [8].
`get_findings`는 `summary` 형식에서 발견사항마다 정한 필드만 남기고 `detailed` 형식에서도 `include_raw_hit`가 거짓이면 `raw_hit`을 뺀다 [9].

**한계.** `_mft_entry_from_row`는 `FileName` 열이 있으면 그 값을 `file_path`로 쓴다 [10].
MFTECmd 2026-05-10 커밋의 CSV는 부모 폴더 경로 `ParentPath`와 이름 `FileName`을 다른 열로 쓴다 [11].
그래서 MFT 결과의 `file_path`에는 부모 폴더 경로 없이 파일 이름만 들어간다 [10][11].

`_compact_sigma_hit`는 이벤트 ID, 채널, 컴퓨터, 사용자, tactic을 hit 최상위 키에서 읽고 키가 없으면 `?`를 넣는다 [7].
Chainsaw v2.16.5의 JSON 항목은 사건 내용을 `document.data` 아래에 두고 최상위에는 규칙 이름, 등급, 시각, 태그 같은 규칙 정보만 둔다 [12].
그래서 `actionable_hits` 항목의 이벤트 ID, 채널, 컴퓨터, 사용자, tactic은 늘 `?`가 된다 [7][12].
(실행 확인) Chainsaw v2.16.5 JSON 구조로 만든 hit을 `query_sigma_results`로 읽자 다섯 필드가 모두 `?`였고 규칙 이름, 등급, 시각, 기법만 값이 있었다 [13].

### R01.03 형식 변환·건수 집계

**구현.** 이 방식은 탐지 도구, EVTX와 레지스트리 추출, 메모리 도구의 `summary` 형식, `run_analysis`에 적용된다 [14][15][16][17][18][19].
`sigma_hunt`와 `query_sigma_results`는 hit을 등급별·기법별로 세어 `severity_breakdown`·`technique_breakdown`에 싣는다 [14].
`sigma_hunt`는 기준 등급 아래 hit을 규칙별로 묶어 건수, 처음·마지막 시각, 표본 위치 3개를 싣고 건수가 1,000을 넘는 규칙을 `noise_rules`로 따로 싣는다 [15].
`summarize_evtx`는 CSV 전체를 한 번 읽으며 채널별 건수를 세고 응답의 `preview`를 건수가 많은 채널 5개로 채운다 [16].
`extract_registry_run_keys`는 지속성 유형별 건수 `persistence_type_counts`와 묶음 요약 `suppression_summary`를 싣는다 [17].
`scan_network`·`detect_injection`·`list_dlls`는 `summary` 형식에서 `data`를 빼고 그 길이를 `connection_count`·`injection_count`·`dll_count`로 싣는다 [18].
`run_analysis`는 질의 결과를 `output_format`에 따라 pipe 표, JSON, CSV 글로 바꾸고 숫자 열마다 최솟값, 최댓값, 평균을 `insights`에 싣는다 [19].
`run_analysis`의 질의 식은 모델이 보내고 그 결과를 응답 글로 바꾸는 일은 서버가 한다 [19][20].

### R01.04 가공 사실·대상 표시

**구현.** 이 방식은 `build_contract_response`를 거치는 도구와 사용자 활동 도구, `run_analysis`에 적용된다 [21][22][19].
`build_contract_response`는 응답에 서버가 쓴 요약 `summary`와 출처 정보 `provenance`를 더한다 [21].
`summary`는 처리한 입력 경로와 건수를 적는다 [21].
예를 들어 `extract_mft_timeline`은 "`MFT timeline returned N rows from <$MFT 경로> with N timestomping candidates.`" 문장을 싣는다 [4].
`provenance`에는 도구 이름 `tool_name`, 실행 ID, 실행한 명령 `raw_command`, 결과 CSV 경로 `csv_path`, 입력 경로 `artifact_paths`가 들어간다 [23].
사용자 활동 도구(`extract_shellbags`·`extract_powershell_history` 등)는 행마다 원래 파일 경로, 파서 이름 `parser_command`, 파싱 상태 `parser_status`를 붙인다 [22].
`run_analysis`는 실행한 질의 `query`와 읽은 파일 `data_source`를 결과에 싣는다 [19].
공통 응답 함수를 거치지 않는 `sigma_hunt`·`extract_shimcache`·`extract_pca`는 `provenance` 없이 `raw_command`나 결과 파일 경로만 싣는다 [24].

### R01.06 응답 항목 선별

**구현.** 이 방식은 `sigma_hunt`와 `summarize_evtx`에 적용된다 [25][26].
`sigma_hunt`는 hit을 등급으로 나눠 기준 등급 이상만 `actionable_hits`에 하나씩 싣고 그 아래 등급은 항목으로 싣지 않는다 [25].
기준 등급의 기본값은 `medium`이고 사용자가 환경변수 `SAVVYDFIR_SIGMA_INLINE_LEVEL`로 바꾼다 [27].
`summarize_evtx`는 모델이 `event_ids`를 주지 않으면 서버가 정한 이벤트 ID 목록을 EvtxECmd에 넘겨 결과를 거른다 [26].
사건에 발견사항이 없으면 26개 ID 목록 `DFIR_ESSENTIAL_EIDS`를 쓰고 발견사항이 있으면 발견사항의 ATT&CK 기법에 따라 ID를 더한 목록을 쓴다 [26][28].

**한계.** 서버가 고른 ID 목록은 결과 CSV를 다시 쓰는 캐시 키에 들어가지 않는다 [29].
같은 폴더·채널·기간으로 다시 부르면 발견사항이 늘어 목록이 바뀌어도 앞서 만든 CSV를 다시 읽는다 [29].

### R01.07 응답 선별 사실·건수 표시

**구현.** 이 방식은 `sigma_hunt`의 기준 아래 hit과 `summarize_evtx`의 이벤트 ID 목록에 적용된다 [30][31].
`sigma_hunt`는 항목으로 싣지 않은 기준 아래 hit의 수를 `below_threshold_total`에, 기준 등급을 `actionable_threshold`에 싣는다 [30].
기준 아래 hit은 규칙별 건수 요약 `below_threshold_summary`로 응답에 들어간다 [15][30].
`detection_gap_invariant`는 기준 이상 hit 수, 기준 등급, 기준 아래 hit 수, 원래 hit 전체를 둔 파일 경로를 한 문장으로 적는다 [32].
`summarize_evtx`는 모델이 `event_ids`를 주지 않았을 때 서버가 고른 이벤트 ID 목록을 `event_id_filter`에, 그 목록을 고른 방식(`default`·`adaptive`)을 `event_id_strategy`에 싣는다 [26][31].

**한계.** 모델이 `event_ids`를 주면 `event_id_strategy`는 `explicit`이 되고 `event_id_filter`에는 모델이 준 목록이 그대로 실린다 [26][31].
캐시한 CSV를 다시 읽으면 `event_id_filter`와 `event_id_strategy`에는 그 CSV를 만들 때의 목록과 방식이 실리고 이번 호출에서 고른 목록은 실리지 않는다 [29][33].
`sigma_hunt`의 `detection_gap_invariant` 문구는 기준 아래 hit을 늘 `low`·`informational`로 적는다 [32].
그래서 사용자가 기준 등급을 `medium`이 아닌 값으로 바꾸면 문구의 등급과 실제로 항목에서 뺀 등급이 다르다 [25][27][32].

    """Compact projection of a Chainsaw hit - preserves the fields the agent
    needs to triage (rule, severity, technique, who/when/where) without the
    full event document body that bloats response size (Run-4 evidence: 50 raw
    hits = 89k chars; compact = ~300 chars each).

    The full raw event remains in the persisted CSV/JSON at csv_path; use
    query_sigma_results(case_id=..., rule_name=...) for deep drill-down.
    """
    return {
        "rule_name": str(hit.get("name", hit.get("rule", f"hit_{index}")))[:140],
        "level": _normalize_sigma_level(hit.get("level")),
        "event_id": str(hit.get("event_id", hit.get("EventID", "?")))[:16],
        "timestamp": str(hit.get("system_time", hit.get("timestamp", "unknown")))[:32],
        "techniques": _extract_sigma_techniques(hit),
        "channel": str(hit.get("channel", hit.get("Channel", "?")))[:64],
        "computer": str(hit.get("computer", hit.get("Computer", "?")))[:64],
        "user": str(hit.get("user", hit.get("User", "?")))[:64],
        "tactic": str(hit.get("tactic", "?"))[:64],
        "hit_index": index,  # for back-reference into csv_path via query_sigma_results
    }

```python
def _strip_data_for_summary(response: Any, response_format: str = "summary",
                            count_key: str = "count") -> Any:
    """Context-budget discipline: when caller asks for summary format,
    strip the heavy ``data`` array but keep counts + handles. Mirrors the
    pattern used by disk tools via _apply_response_format.

    This applies to memory tools (scan_network, detect_injection, list_dlls)
    which previously returned full record arrays on every call - a typical
    list_dlls response is 200+ DLLs ≈ 30 KB of context per PID.
    """
    if not isinstance(response, dict):
        return response
    fmt = (response_format or "summary").strip().lower()
    if fmt == "detailed":
        return response
    # Default = summary - drop heavy fields, keep counts + handles + status.
    out = dict(response)
    data = out.get("data")
    if isinstance(data, list):
        out[count_key] = len(data)
        # Keep first 3 records as a tiny preview so the LLM has something
        # to anchor on without context bloat.
        out["preview"] = data[:3]
        out.pop("data", None)
    out["response_format"] = "summary"
    return out
```
