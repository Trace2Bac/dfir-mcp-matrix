# T08 실행 종료 판별

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 STDIO 래퍼가 Autopsy HTTP 서버에 보내는 모든 요청(`tools/list`, `tools/call`)에 적용된다 [1].
래퍼는 요청마다 `AbortController`를 만들고 `CALL_TIMEOUT_MS`(30,000밀리초)가 지나면 요청을 끊는다 [1].
끊긴 요청에서 나는 `AbortError`는 다른 연결 오류와 따로 처리해 `Autopsy MCP timed out after 30s (<메서드>)` 오류로 바꾸고 기록 파일에 남긴다 [1].
`tools/call`에서는 이 오류가 `isError`가 참인 글 응답이 되고 `tools/list`에서는 대체 도구 하나만 담은 목록이 된다 [2][3].
기준 커밋의 래퍼 소스를 Node.js 24.21.0으로 실행하면 응답이 75초 늦는 호출이 30초에 시간 초과 오류로 끝났다 [4].

**한계.** 설치본 Autopsy 4.23.1의 `autopsy-mcp-stdio.exe`에서는 이 시간 제한이 적용되지 않았다 [5].
같은 호출에서 실행 파일은 75초 동안 기다린 뒤 HTTP 서버의 응답을 성공 결과로 돌려주었다 [5].
실행 파일을 만드는 `package` 스크립트는 pkg 대상을 Node.js 18로 정한다 [6].
설치본 실행 파일은 실행할 때 fetch가 실험 기능이라는 경고를 출력했다 [5].
실행 파일에서 시간 제한이 적용되지 않는 원인은 확인하지 못했다.
실행 파일은 저장소에 없고 `.gitignore`가 그 폴더를 뺀다 [7].
`build.xml`은 Windows에서 래퍼 소스 파일이 실행 파일보다 새로울 때만 실행 파일을 다시 만들고 `package.json`과 잠금 파일이 바뀐 것은 보지 않는다 [8].
그래서 배포되는 실행 파일에 묶인 MCP TypeScript SDK와 Node.js 버전은 저장소의 잠금 파일과 다를 수 있다.

래퍼는 `fetch`가 응답 헤더를 받으면 바로 타이머를 지우므로 시간 제한은 응답 헤더를 받기 전까지만 적용되고 본문을 읽는 `res.json()`에는 적용되지 않는다 [1].
Java 쪽 처리기에는 시간 제한이나 취소 코드가 없어 래퍼가 요청을 끊어도 Autopsy 안의 질의는 끝날 때까지 계속 실행된다 [9].
래퍼는 MCP 클라이언트가 보낸 취소 알림 `notifications/cancelled`를 받아도 진행 중인 HTTP 요청을 끊지 않는다 [10][11].
MCP TypeScript SDK 1.27.1은 취소된 요청의 처리기에 취소 신호를 보내고 그 요청의 응답을 보내지 않지만 래퍼의 도구 호출 처리기는 그 신호를 `fetch`에 넘기지 않는다 [10][12].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 Java 쪽 요청 처리기 `McpProtocolHandler.handle`이 받는 모든 요청에 적용된다 [13].
도구 대부분은 케이스 DB를 조회하지만 `get_file_content`는 Sleuth Kit의 `AbstractFile.read`로 이미지의 파일시스템을 해석해 파일 내용을 읽는다 [14][15].
도구 처리 중 Sleuth Kit이 던진 `TskCoreException`이나 서버 코드에서 난 다른 예외는 처리기에서 처리되고 처리기는 `SEVERE` 수준으로 기록한 뒤 JSON-RPC 오류 코드 -32603과 예외 문구를 담은 오류 응답을 만든다 [13].
`query_files`·`query_timeline`·`summarize_timeline`의 시각 인자는 서버 코드가 `Instant.parse`로 읽으므로 형식이 맞지 않는 시각 값도 `DateTimeParseException`으로 같은 -32603 오류가 된다 [16][13].
`McpException`은 기록 없이 그 예외에 정한 코드로, JSON 해석 실패는 -32700으로 응답한다 [13].
요청 본문을 읽다가 예외가 나거나 오류 응답을 만드는 데도 실패해 처리기 밖으로 예외가 나오면 `McpServer.handleMcpRequest`가 HTTP 500으로 응답한다 [17].
이 응답은 오류 코드 -32603과 `Internal error`를 싣고 `data` 필드에 예외 문구를 싣는다 [17].
래퍼는 HTTP 상태가 성공이 아니거나 응답에 `error`가 있으면 그 호출을 실패로 정하고 `isError`가 참인 글 응답을 돌려준다 [2][18].
Sleuth Kit의 `getAbstractFileById`는 없는 ID에 `null`을 돌려주므로 `get_file_content`에 없는 객체 ID를 주면 `NullPointerException`이 나고 같은 -32603 오류가 된다 [19][14].
이 오류의 문구는 JRE 15부터 기본으로 켜진 자세한 NPE 글이다 [20].
`get_file_content`와 `get_report_content`는 읽은 바이트가 요청보다 적으면 배열을 줄여 `bytesRead`에 실제 수를 적고 실패로 다루지 않는다 [14][21].

**한계.** 다음 경로에서는 라이브러리 예외나 읽기 실패가 호출 실패가 되지 않고 빈 값이나 기본값으로 응답에 실린다.

- `query_data_artifacts`·`query_analysis_results`는 `artifactType`으로 유형을 찾다가 `TskCoreException`이 나면 그 유형의 결과가 없을 때와 같은 빈 목록을 돌려준다 [22].
- 파일 항목은 고유 경로를 읽지 못하면 부모 경로와 이름을 이어 붙인 값으로, 확장 속성을 읽지 못하면 빈 목록으로 채운다 [23].
- 디스크 이미지 데이터 소스는 해시와 획득 정보를 읽다가 예외가 나면 그 필드를 `null`로 채운다 [24].
- `get_case_summary`는 아티팩트 수를 세다가 `SQLException`이 나면 `totalArtifacts`를 0으로 돌려준다 [25].
- Sleuth Kit의 `Report.read`는 보고서 파일을 읽다가 `IOException`이 나면 기록만 남기고 그때까지 읽은 바이트 수를 돌려주고 경로가 폴더이면 0을 돌려준다 [26].
- Sleuth Kit의 `FsContent.readInt`는 데이터 소스가 이미지 경로 없는 `Image`이면 읽지 않고 0을 돌려준다 [27].

`get_file_content`는 `objectId`가 없을 때 `TskCoreException`을 직접 던지므로 이 입력 오류도 라이브러리 실패와 같은 -32603 오류가 된다 [14].

async function callJava(method, params) {
    const token = readToken(); // fresh read each call — handles case reopen
    log("INFO", `-> ${method}`);

    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), CALL_TIMEOUT_MS);

    let res;
    try {
        res = await fetch(`${MCP_BASE_URL}/mcp`, {
            method: "POST",
            headers: {
                "Content-Type": "application/json",
                "Authorization": `Bearer ${token}`
            },
            body: JSON.stringify({ jsonrpc: "2.0", id: "1", method, params }),
            signal: controller.signal
        });
    } catch (err) {
        clearTimeout(timer);
        if (err.name === "AbortError") {
            const msg = `Autopsy MCP timed out after ${CALL_TIMEOUT_MS / 1000}s (${method})`;
            log("ERROR", msg);
            throw new Error(msg);
        }
        throw err;
    }
    clearTimeout(timer);

            String requestBody = ctx.body();
            String response = protocolHandler.handle(requestBody);
            ctx.contentType("application/json").result(response);
        } catch (Exception ex) {
            logger.log(Level.SEVERE, "MCP protocol handler threw unexpectedly", ex);
            String msg = ex.getMessage() != null ? ex.getMessage() : "Internal error";
            Map<String, Object> errorDetail = new LinkedHashMap<>();
            errorDetail.put("code",    McpProtocolHandler.ERR_INTERNAL_ERROR);
            errorDetail.put("message", "Internal error");
            errorDetail.put("data",    msg);
            Map<String, Object> envelope = new LinkedHashMap<>();
            envelope.put("jsonrpc", "2.0");
            envelope.put("error",   errorDetail);
            envelope.put("id",      null);
            String body;
            try {
                body = MAPPER.writeValueAsString(envelope);
            } catch (Exception jsonEx) {
                logger.log(Level.SEVERE, "Failed to serialize MCP error response", jsonEx);
                body = "{\"jsonrpc\":\"2.0\",\"error\":{\"code\":" + McpProtocolHandler.ERR_INTERNAL_ERROR + ",\"message\":\"Internal error\"},\"id\":null}";
            }
            ctx.status(500).contentType("application/json").result(body);
        }
    }
