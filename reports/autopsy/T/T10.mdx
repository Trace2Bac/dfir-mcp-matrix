# T10 도구 명세 구성

### T10.02 처리기와 따로 둔 명세

**구현.** 이 방식은 서버의 18개 도구 모두에 적용된다 [1].
도구 명세는 `TskQueryService.listTools()`가 코드 안의 표로 만들고 도구를 처리하는 코드는 `McpProtocolHandler.dispatchToolCall()`의 `switch`와 `TskQueryService`의 메서드에 따로 있다 [1][2].
`get_server_status`는 `switch` 앞에서 `buildServerStatus()`가 처리한다 [2].
명세 표의 이름 18개와 처리 코드의 이름 18개는 같다 [1][2].

명세 한 항목은 `name`, `description`, `inputSchema`로 이루어지고 `inputSchema`는 `type`이 `object`인 `properties`와 선택 항목 `required`만 담는다 [3].
인자 하나는 `param()`이 만드는 `type`과 `description`뿐이고 열거값, 최솟값·최댓값, 기본값은 schema에 없다 [3].
허용하는 값과 기본값, 상한은 인자 설명 글에만 적혀 있다 [1].
`required`는 `get_file_content`·`get_account_relationships`·`get_object_children`·`get_report_content`의 4개 도구에만 있다 [4].
`get_server_status`를 뺀 17개 도구는 `toolWithNote()`로 만들어 설명 끝에 응답의 `caseId`가 바뀌면 사용자에게 알리라는 문장 `CASE_ID_NOTE`가 붙는다 [5].
명세에는 출력 schema와 annotation이 없다 [3].

Java 쪽은 `tools/list`를 케이스와 묶이지 않은 질의 서비스 `TOOLS_LIST_SERVICE`로 처리하므로 케이스가 열려 있든 아니든 같은 목록을 돌려준다 [6].
STDIO 래퍼는 도구 명세를 두지 않고 Java 쪽이 돌려준 목록을 `tools`에 그대로 담아 돌려준다 [7].
래퍼가 Autopsy HTTP 서버에서 목록을 받지 못하면 대체 도구 `UNAVAILABLE_TOOL` 하나만 돌려준다 [7].
이 대체 도구의 이름은 Java 쪽 도구와 같은 `get_server_status`이지만 설명은 Autopsy에 연결되지 않으니 Autopsy와 MCP 서버를 켠 뒤 다시 시도하라는 글이다 [7][8].
토큰 파일이 없는 상태에서 래퍼에 `tools/list`를 보내면 이 대체 도구 하나만 돌아왔다 [8].

래퍼는 MCP 서버를 만들 때 `capabilities`에 빈 `tools`만 선언하고 `listChanged`를 선언하지 않는다 [9].
그래서 Autopsy가 나중에 실행되어도 서버가 목록 변경을 알리지 않고 클라이언트가 `tools/list`를 다시 보내야 18개 도구가 보인다 [7][9].
서버는 리소스, 프롬프트, 서버 지침을 두지 않는다 [9].
Java 쪽 `initialize` 처리도 `tools` 능력만 적지만 클라이언트는 래퍼만 실행하므로 이 응답을 받지 않는다 [10].
실행 설정이나 클라이언트에 따라 명세를 바꾸는 코드는 없다 [1][7].

**한계.** 설명 글이 알리는 동작과 처리 코드의 동작이 다른 도구가 있다.

`get_file_content`와 `get_report_content`의 설명은 1,048,576바이트를 넘는 `maxBytes` 요청을 거부한다고 적는다 [11].
처리 코드는 `maxBytes`가 0 이하이거나 1,048,576을 넘으면 거부하지 않고 65,536으로 바꿔 읽는다 [12].
`get_file_content`의 설명은 UTF-8로 해석하지 못한 바이트를 `?`로 바꾼 UTF-8 글을 돌려준다고 적는다 [11].
처리 코드는 `CodingErrorAction.REPLACE`만 지정하고 대체 문자를 정하지 않으므로 Java의 UTF-8 decoder는 기본 대체 문자 U+FFFD를 넣는다 [13][14].

`query_analysis_results`의 설명은 점수의 significance 값을 `NOTABLE`, `LIKELY_NOTABLE`, `LIKELY_NONE`, `NONE`, `UNKNOWN`으로 적는다 [15].
처리 코드는 `getSignificance().getName()`을 싣고 Sleuth Kit 4.15.0에서 이 값은 `Notable`, `LikelyNotable`, `LikelyNone`, `None`, `Unknown`이다 [16][17].

`query_timeline`과 `summarize_timeline`의 설명은 둘 다 `endTime`이 범위에 포함된다고 적는다 [18].
`query_timeline`은 끝 시각에 1초를 더해 Sleuth Kit에 넘기므로 끝 시각의 사건을 포함한다 [19].
`summarize_timeline`은 끝 시각을 그대로 `countEventsByType`에 넘기고 Sleuth Kit 4.15.0의 이 메서드는 시작과 끝이 같을 때만 1초를 더해 `time < 끝` 조건으로 센다 [20][21].
그래서 `summarize_timeline`의 집계에는 끝 시각과 같은 초의 사건이 빠지고 `endTime`을 생략하면 케이스의 마지막 사건 시각에 있는 사건도 빠진다 [20][21].

`get_os_accounts`의 설명은 계정이 나온 데이터 소스의 인스턴스 유형을 `LAUNCHED`, `ACCESSED`, `REFERENCED`로 적는다 [22].
처리 코드는 `getInstanceType().getName()`을 싣고 Sleuth Kit 4.15.0에서 이 값은 `Launched`, `Accessed`, `Referenced`다 [23][24].
`query_files`의 `knownState` 인자 설명은 값으로 `NOTABLE`을 적지만 응답의 `knownState`는 열거형 이름을 실어 같은 상태를 `BAD`로 적는다 [25].
`query_files`의 `modifiedBefore`·`createdBefore` 설명은 그 날짜 전의 파일을 고른다고 적는다 [26].
처리 코드의 조건은 `mtime <= …`·`crtime <= …`이므로 시각이 기록되지 않아 0인 파일도 고른다 [27].
`get_communications_accounts`의 설명은 통신 자료에서 찾은 계정을 나열한다고 적고 고를 수 있는 유형에 `CREDIT_CARD`를 넣는다 [28].
처리 코드가 부르는 Sleuth Kit 4.15.0의 `getAccountDeviceInstancesWithRelationships`는 관계가 하나 이상 있는 계정만 돌려주므로 관계가 없는 계정은 이 도구에 나오지 않는다 [29][30].

        String toolName = params.path("name").asText();

        // Tools that work regardless of whether a case is open

                Map.of("message", "No case is currently open in Autopsy."), null);

        if (qs == null) {
            throw new McpException(
                "No case is currently open in Autopsy. Open a case first to use MCP tools.",
                McpException.ERR_INTERNAL_ERROR);
        }
