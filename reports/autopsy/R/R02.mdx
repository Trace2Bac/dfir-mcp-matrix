# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 목록을 돌려주는 도구 가운데 5개가 항목 수에 상한을 둔다.
`query_files`는 기본 50개, 최대 500개이고 상한을 SQL `LIMIT`으로 넘긴다 [1].
`query_data_artifacts`·`query_analysis_results`는 기본 50개, 최대 500개다 [2].
`query_timeline`은 기본 100개, 최대 1,000개다 [3].
`get_communications_accounts`는 기본 100개, 최대 500개다 [4].
모델이 `limit`에 0 이하나 최댓값을 넘는 값을 주면 서버는 거부하지 않고 기본값(50 또는 100)으로 되돌린다 [1][2][3][4].

`query_data_artifacts`·`query_analysis_results`는 속성 필터(`attributeType`·`attributeValue`)가 없을 때만 상한을 SQL `LIMIT`으로 넘긴다 [2].
속성 필터가 있으면 조건에 맞는 유형의 아티팩트를 모두 읽은 뒤 Java에서 걸러 상한까지 싣는다 [2].
`query_timeline`은 Sleuth Kit `TimelineManager.getEvents`가 기간 안의 이벤트를 모두 돌려준 뒤 Java에서 상한까지 싣는다 [3][5].
`get_communications_accounts`도 관계가 있는 계정을 모두 읽은 뒤 상한까지 싣는다 [4].
`orderBy` 없는 `query_files`, 아티팩트 두 도구, `get_communications_accounts`는 정렬 조건 없이 자르므로 상한에 닿을 때 어느 항목이 남는지는 DB가 돌려주는 차례에 달려 있다 [1][2][4].
`query_timeline`은 시각 차례로 읽은 이벤트 가운데 이른 것부터 남긴다 [3][5].

다음 도구의 응답에는 항목 수 상한이 없다.
`get_hosts`·`query_data_sources`·`get_data_source_tree`·`list_reports`는 사건의 호스트, 데이터 소스, 저장 구조, 보고서를 모두 싣는다 [6].
`query_tags`는 사용 중인 태그 이름마다 태그된 파일과 아티팩트를 모두 싣는다 [7].
`get_os_accounts`는 OS 계정을 모두 싣고 계정마다 확장 속성과 데이터 소스 인스턴스를 모두 싣는다 [8].
`get_account_relationships`는 대상 계정과 관계가 있는 계정을 모두 싣고 `get_object_children`은 객체의 자식을 모두 싣는다 [9][10].
아티팩트 항목에 붙는 속성 목록과 파일 항목의 `attributes`에도 개수 상한이 없다 [2][11].

Java HTTP 서버와 STDIO 래퍼에는 응답 전체의 크기를 재거나 자르는 코드가 없다 [12].

**한계.** 목록 도구의 상한 설명과 실제 처리가 다르다.
`get_communications_accounts`를 뺀 네 도구의 설명은 `limit`의 최댓값을 적지만 그 값을 넘는 요청은 최댓값이 아니라 기본값으로 처리되고 응답에는 적용한 상한이 실리지 않는다 [1][2][3][13].
`get_communications_accounts`의 설명은 기본값 100만 적고 최댓값 500은 적지 않는다 [4][13].
사용자 문서는 결과가 1MB를 넘을 수 없다고 적는다 [14].
서버 코드에서 1,048,576바이트는 내용을 읽는 두 도구의 `maxBytes` 최댓값으로만 쓰이고 응답 전체에는 적용되지 않는다 [15][16].

### R02.02 전체·반환 건수 표시

**구현.** 이 방식은 내용을 읽는 `get_file_content`와 `get_report_content`에 적용된다 [15][16].
두 도구는 파일 전체 크기 `fileSize`, 읽기 시작 위치 `offset`, 이번에 읽은 바이트 수 `bytesRead`, 남은 내용이 있는지를 뜻하는 `truncated`를 함께 싣는다 [15][16].

목록 도구 5개는 상한으로 자른 응답에 전체 건수나 잘렸다는 표시를 싣지 않는다 [1][2][3][4].
그래서 모델은 상한과 같은 수의 항목을 받았을 때 결과가 더 있는지 응답으로 알 수 없다 [1][2][3][4].

**한계.** `truncated`는 파일 크기에서 `offset`을 뺀 값이 요청 크기보다 큰지로만 정하고 실제로 읽은 바이트 수와 대조하지 않는다 [15][16].
Sleuth Kit은 이미지 경로가 없는 데이터 소스의 파일을 읽으면 0바이트를 돌려준다 [17].
보고서 파일 읽기에서 `IOException`이 나면 그때까지 읽은 바이트 수를 돌려준다 [18].
이때 응답은 `bytesRead`가 0이거나 요청보다 작으면서 `truncated`가 `false`일 수 있고 읽지 못했다는 표시가 없다 [15][16].
Sleuth Kit `Report.getSize()`는 보고서 파일 크기를 읽다가 `IOException`이 나면 0을 돌려준다 [19].
그러면 `get_report_content`는 `fileSize` 0, `eof: true`, 빈 `content`를 돌려주고 이 응답은 빈 보고서의 응답과 구별되지 않는다 [16][19].

### R02.03 페이지·커서 조회

**구현.** `get_file_content`와 `get_report_content`는 인자 `offset`과 `maxBytes`로 내용의 다음 구간을 이어서 읽게 한다 [15][16].
두 도구의 설명은 큰 파일을 `offset`과 `maxBytes`로 나눠 읽으라고 적는다 [13].
`offset`이 파일 크기 이상이면 빈 `content`와 `eof: true`를 돌려준다 [15][16].
`get_report_content`는 정상 응답에도 `eof`를 `truncated`의 반대 값으로 싣는다 [16].
`get_file_content`의 정상 응답에는 `eof`가 없고 `truncated`만 있다 [15].
음수 `offset`은 거부하지 않고 0으로 바꿔 읽으며 응답의 `offset`에는 바뀐 값 0이 실린다 [15][16].

목록 도구에는 `offset`이나 커서 인자가 없어 상한 뒤의 항목을 이어서 읽는 길이 없다 [13].

### R02.06 값 단위 잘림

**구현.** `get_file_content`와 `get_report_content`는 파일이나 보고서 하나의 내용을 `maxBytes`바이트에서 자른다 [15][16].
`maxBytes`의 기본값은 65,536바이트이고 최댓값은 1,048,576바이트다 [15][16].
자른 내용은 UTF-8로 해석한 글로 싣는다 [15][16].

**한계.** 두 도구의 설명은 1,048,576바이트를 넘는 `maxBytes` 요청을 거부한다고 적지만 서버는 그 값을 거부하지 않고 65,536바이트로 바꿔 읽는다 [13][15][16].
설명은 65,536바이트보다 큰 파일에 `maxBytes`를 따로 주어야 한다고 적지만 서버는 `maxBytes` 없이도 앞 65,536바이트를 읽어 돌려준다 [13][15].
자르는 위치는 바이트 단위이므로 여러 바이트로 된 UTF-8 문자가 구간 경계에서 나뉘면 앞뒤 응답의 경계 문자가 대체 문자로 바뀐다 [15][16].
