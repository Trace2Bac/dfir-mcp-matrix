# R05 결과 출처 표시

### R05.01 증거·파일 ID

**구현.** 케이스 DB 객체를 돌려주는 도구는 결과 항목에 Autopsy 케이스 DB의 객체 ID를 싣는다.
`query_files`는 파일의 `objectId`와 그 파일이 속한 데이터 소스의 `dataSourceId`를 싣는다 [1].
`query_data_artifacts`·`query_analysis_results`는 아티팩트의 `objectId`와 아티팩트가 붙은 객체의 `sourceFileId`, `dataSourceId`를 싣는다 [2].
`query_timeline`은 사건마다 `sourceFileId`, `artifactId`, `dataSourceId`를 싣는다 [3].
`query_tags`는 태그된 파일이나 아티팩트의 `objectId`를 싣고 `get_os_accounts`는 계정이 나타난 데이터 소스의 `dataSourceId`를 싣는다 [4][5].
`query_data_sources`·`get_hosts`는 데이터 소스의 `objectId`와 디스크 이미지 파일의 경로 `paths`를 싣는다 [6].
그래서 결과 항목의 `dataSourceId`를 `query_data_sources`의 `objectId`와 맞추면 증거 이미지 파일의 경로를 찾을 수 있다 [6].
STDIO 래퍼로 받는 도구 결과 가운데 `get_server_status`를 뺀 결과에는 케이스를 가리키는 `caseId`가 붙는다 [7][8].
케이스가 열려 있지 않을 때 `get_case_summary`의 `caseId`는 `null`이다 [8].

다음 도구의 결과 항목에는 그 값이 나온 파일이나 아티팩트의 ID가 없다.
`get_communications_accounts`와 `get_account_relationships`는 계정 유형, 계정 식별값, 장치 ID, 관계 수만 싣고 관계의 출처가 된 메시지·통화 아티팩트의 ID를 싣지 않는다 [9].
`get_os_accounts`의 확장 속성 항목은 유형과 값만 싣는다 [5].
Sleuth Kit의 OS 계정 속성 객체에는 그 속성을 찾은 출처 객체 ID가 있지만 서버는 이 값을 싣지 않는다 [5][10].
`summarize_timeline`과 `get_case_summary`는 출처 ID 없이 건수와 케이스 이름이나 기간만 싣는다 [11].
`query_tags`는 태그된 객체의 `objectId`만 싣고 태그를 붙인 사용자를 싣지 않으며 파일이 아닌 객체에 붙은 내용 태그도 `itemType`을 `file`로 싣는다 [4][12].
분석 결과의 해시셋 이름 `TSK_SET_NAME`과 다른 케이스 목록 `TSK_OTHER_CASES`는 해시 DB나 다른 케이스 같은 참조 자료에서 온 값이지만 응답은 다른 속성과 같은 꼴로 싣고 그 참조 자료를 따로 표시하지 않는다 [2][13].

**한계.** `caseId`는 케이스 표시 이름이므로 표시 이름이 같은 케이스끼리는 이 값으로 구별되지 않는다 [7].

### R05.02 증거 내부 경로

**구현.** `query_files`와 `get_object_children`의 파일 항목은 Sleuth Kit `getUniquePath()`가 만든 경로를 `path`에 싣는다 [1][14].
이 경로는 데이터 소스 안의 파일 위치를 나타내고 `query_files`는 부모 경로 `parentPath`도 싣는다 [1].
`get_file_content`의 응답은 파일 이름 `fileName`만 싣고 경로를 싣지 않는다 [15].

**한계.** `getUniquePath()`가 `TskCoreException`을 던지면 서버는 `parentPath`와 파일 이름을 이은 값을 `path`에 싣는다 [1][14].
이 값은 `getUniquePath()`의 결과와 모양이 다를 수 있지만 응답에는 대체 값이라는 표시가 없다 [1][14].

### R05.03 레코드 키·번호

**구현.** `query_files`는 파일 시스템의 메타데이터 주소 `metaAddr`와 순번 `metaSeq`를 싣는다 [1].
Sleuth Kit은 `metaAddr`를 메타데이터 구조의 주소로, `metaSeq`를 NTFS에서만 쓰이고 구조를 다시 할당할 때마다 늘어나는 순번으로 설명한다 [16].
`get_object_children`의 파일 항목에는 이 두 값이 없다 [14].

### R05.04 바이트·섹터·행 오프셋

**구현.** `get_data_source_tree`와 `get_object_children`은 저장 구조 항목의 위치를 싣는다 [17][18].
볼륨 항목에는 시작 섹터 `startSector`와 섹터 수 `lengthSectors`, 파일 시스템 항목에는 이미지 안 바이트 오프셋 `imageOffset`, 볼륨 시스템 항목에는 `offset`이 있다 [17][18].
파일, 아티팩트, 타임라인 사건 항목에는 이미지 안의 오프셋이 없다 [1][2][3].
`query_tags`는 내용 태그가 가리키는 바이트 범위(`getBeginByteOffset`·`getEndByteOffset`)를 싣지 않는다 [4][12].
