# P04 조사 단위 관리

### P04.12 호스트 프로그램의 열린 사건에 연결

**구현.** 조사 단위는 Autopsy 케이스이고 케이스를 만들거나 여는 일은 사용자가 Autopsy에서 한다.
MCP에는 케이스를 만들거나 여는 도구가 없고 서버는 케이스 ID를 정하거나 검사하지 않는다 [1].
서버는 Autopsy의 `CURRENT_CASE` 이벤트를 구독하고 케이스가 열리면 그 케이스를 질의하는 객체(질의 서비스) `TskQueryService`를 새로 만든다 [2][3].
`updateCase`는 열린 케이스의 `getSleuthkitCase()`와 `getDisplayName()`으로 `TskQueryService`를 만들고 이후 도구 호출은 모두 이 객체로 처리된다 [3][4].
서버가 켜질 때 Autopsy에 이미 열린 케이스가 있으면 그 케이스로 같은 처리를 한다 [2].
`get_server_status` 밖의 도구 응답은 `caseId`와 `result`로 감싸지고 `caseId`에는 질의에 쓴 질의 서비스의 케이스 표시 이름이 들어간다 [4].
도구 설명 끝에는 호출 사이에 `caseId`가 바뀌면 사용자에게 알리라는 문장이 붙는다 [5].
케이스가 닫히면 `clearCase`가 질의 서비스를 비우고 그 뒤 `get_server_status`·`get_case_summary` 밖의 도구 호출은 케이스가 열려 있지 않다는 오류를 받는다 [3][4].

케이스 자료는 Autopsy 본체가 케이스마다 만든 케이스 DB에 있고 서버는 지금 열린 케이스의 DB 하나만 질의한다 [3].
서버가 쓰는 파일은 `%LOCALAPPDATA%\autopsy\mcp` 아래의 토큰 파일, 포트 설정 파일, STDIO 래퍼의 `mcp-stdio.log`와 `mcp-stdio.log.1`이고 케이스 단위의 폴더나 DB는 만들지 않는다 [6][7].
HTTP 연결이나 STDIO 래퍼 프로세스가 여럿이어도 질의 서비스는 하나이므로 모든 연결이 같은 케이스를 질의한다 [4].
도구는 케이스 ID를 인자로 받지 않으므로 서버는 호출이 어느 케이스를 대상으로 했는지 대조하지 않는다 [1].
서버는 진행 중인 호출이 있어도 케이스 닫기나 전환을 미루지 않는다 [2].
서버는 도구 이름에 서버를 가리키는 접두어를 붙이지 않고 응답에 `caseId`만 싣는다 [1][4].
사용자 문서는 다른 MCP 서버와 함께 열어 둔 채 프롬프트에서 도구를 밝히지 않으면 두 서버의 자료가 섞일 수 있다고 경고한다 [8].

**한계.** 사용자가 호출 사이에 케이스를 바꾸면 다음 호출은 별도 알림 없이 새 케이스를 질의하고 바뀐 사실은 응답의 `caseId`로만 드러난다 [4].
`caseId`는 사용자가 정하는 케이스 표시 이름이므로 표시 이름이 같은 두 케이스는 `caseId`로 구별되지 않는다 [3][9].
표시 이름은 질의 서비스를 만들 때 한 번 읽는다 [3].
케이스가 열린 채 사용자가 표시 이름을 바꾸면 Autopsy는 `CURRENT_CASE`가 아니라 `NAME` 이벤트를 보내므로 서버는 케이스를 다시 열 때까지 옛 이름을 `caseId`로 싣는다 [2][10].
케이스를 닫을 때 Autopsy는 `CURRENT_CASE` 이벤트를 구독자에게 같은 스레드에서 먼저 전달한 뒤 케이스 DB를 닫는다 [11][12][13].
진행 중인 호출은 비우기 전에 가져온 질의 서비스로 계속 질의하므로 닫히는 DB를 쓰게 되고 이때 어떤 응답이 나오는지는 확인하지 못했다 [4].
서버를 켜는 `startServer`는 서버 객체를 필드에 넣은 뒤에 `Case.getCurrentCase()`로 열린 케이스를 읽어 질의 서비스를 만든다 [14].
Autopsy는 케이스를 닫을 때 `CURRENT_CASE` 닫힘 이벤트를 먼저 보내고 닫기 작업이 끝날 때까지 현재 케이스를 그 케이스로 남겨 둔다 [15].
`Case`의 주석도 닫힘 이벤트와 열림 이벤트 사이에 `getCurrentCase`를 부르지 말라고 적는다 [16].
그래서 서버를 켜는 순간 케이스가 닫히면 닫힘 이벤트로 질의 서비스를 비운 뒤에 닫히는 케이스로 질의 서비스를 다시 만들 수 있다 [14][15].
이 경우 다음 케이스 이벤트까지 도구 호출은 닫힌 케이스 DB를 질의하고 이 경로는 실행으로 확인하지 않았다 [14][15].

const MAX_LOG_BYTES = 1 * 1024 * 1024; // 1 MB — rotate when exceeded

function log(level, message) {
    // Only ERROR level is persisted to disk. INFO/DEBUG calls are no-ops
    // by design — they would be too noisy in production and are visible
    // during development via a debugger or by temporarily removing this guard.
    if (level !== "ERROR") return;
    try {
        // Rotate if the log has grown too large
        try {
            if (fs.statSync(LOG_PATH).size > MAX_LOG_BYTES) {
                fs.renameSync(LOG_PATH, LOG_PATH + ".1");
            }
        } catch { /* file doesn't exist yet — that's fine */ }

        const line = `${new Date().toISOString()} [${level}] ${message}\n`;
        fs.appendFileSync(LOG_PATH, line, "utf8");
    } catch { /* never let logging crash the process */ }
}
