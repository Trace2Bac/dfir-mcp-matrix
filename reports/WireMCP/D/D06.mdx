# D06 산출물 식별·재생성 처리

### 미구현

**판단.** 서버가 만드는 파일은 실시간 캡처 도구 4개가 tshark에 쓰게 하는 `temp_capture.pcap` 하나이고 그 이름은 모든 호출에서 같다 [1].
이름에 호출, 시각, 인터페이스, 난수처럼 호출마다 다른 값을 넣지 않는다 [1].
서버 코드는 캡처 전에 그 이름의 파일이 이미 있는지 보지 않는다 [1].
Wireshark 4.0.17의 `dumpcap`은 `-w`로 받은 파일을 `O_TRUNC`와 `O_CREAT`로 열어 이미 있는 파일을 비우고 다시 쓴다 [2].
오류로 끝난 호출이 남긴 18,983,592바이트의 파일은 다음 캡처 호출이 같은 inode에 284바이트로 다시 썼고 그 호출이 성공한 뒤 지워졌다 [3].
서버가 만들지 않은 같은 이름의 파일을 현재 폴더에 두고 `get_conversations`를 부르자 응답은 성공이었고 앞 파일이 있었다는 내용이 없었으며 그 파일은 호출 뒤 남지 않았다 [3].

두 캡처 호출이 겹치면 두 호출이 같은 파일을 쓰고 지운다 [1][4].
`capture_packets`를 3초로 부른 동안 `get_summary_stats`를 1초로 부르자 뒤 호출은 성공했고 앞 호출은 tshark가 `temp_capture.pcap`이 없다고 알린 오류로 끝났다 [3].
`capture_packets`의 3초 호출과 1초 호출을 겹쳐 부른 다른 실행에서는 두 호출이 모두 캡처 파일이 패킷 중간에서 끊겼다는 tshark 오류로 끝났다 [5].
그 실행에서는 두 호출이 끝난 뒤 `temp_capture.pcap`이 현재 폴더에 남았다 [5].
`analyze_pcap`과 `extract_credentials`는 파일을 만들지 않고 같은 인자로 다시 부르면 pcap을 다시 읽어 새 응답을 만든다 [6].

    try {
      const tsharkPath = await findTshark();
      const { interface, duration } = args;
      const tempPcap = 'temp_capture.pcap';
      console.error(`Capturing packets on ${interface} for ${duration}s`);

      await execAsync(
        `${tsharkPath} -i ${interface} -w ${tempPcap} -a duration:${duration}`,
        { env: { ...process.env, PATH: `${process.env.PATH}:/usr/bin:/usr/local/bin:/opt/homebrew/bin` } }
      );

      const { stdout, stderr } = await execAsync(
        `${tsharkPath} -r "${tempPcap}" -T json -e frame.number -e ip.src -e ip.dst -e tcp.srcport -e tcp.dstport -e tcp.flags -e frame.time -e http.request.method -e http.response.code`,
