# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 이 방식은 `capture_packets`와 `analyze_pcap`의 패킷 JSON에 적용된다 [1][2].
두 도구는 패킷 배열을 `JSON.stringify`로 만든 글이 720,000자(`maxChars`)를 넘으면 `720000 / 글 길이`의 비율만큼 앞쪽 패킷만 남긴다 [1][2].
남은 패킷 수는 전체 패킷 수에 이 비율을 곱해 내린 값이다 [1][2].
잘랐다는 사실은 서버의 표준 오류에 `Trimmed packets from … to … to fit 720000 chars` 줄로만 쓰고 응답에는 싣지 않는다 [1][2].
3,000자가 넘는 URI를 담은 HTTP 요청 230개의 시험 pcap으로 `analyze_pcap`을 부르자 패킷 468개 가운데 앞의 410개만 실렸다 [3].
응답에는 잘렸다는 표시도 전체 패킷 수도 없었다 [3].
나머지 패킷을 이어서 읽는 도구나 남겨 둔 파일은 없다 [4].

`get_summary_stats`, `get_conversations`, `check_threats`, `check_ip_threats`, `extract_credentials`의 응답에는 서버가 정한 상한이 없다 [5][6][7].

**한계.** 상한은 패킷 JSON에만 적용되고 `analyze_pcap`이 그 앞에 붙이는 IP, URL, 프로토콜 목록에는 적용되지 않는다 [2].
위 시험에서 URL 목록은 230개가 모두 실렸고 응답 전체는 1,420,593자였다 [3].
남길 패킷 수를 글 길이의 비율로 정하므로 자른 뒤의 패킷 JSON도 720,000자를 넘을 수 있다 [2].
위 시험에서 자른 뒤의 패킷 JSON은 723,734자였다 [3].

이 상한은 `tshark` 출력이 아래의 1 MiB 실행 상한 안에 들어온 경우에만 적용된다 [8].
`tshark`의 JSON은 들여쓰기를 담고 있어 공백을 뺀 `JSON.stringify`의 글은 원래 출력보다 짧다 [3].
시험 pcap의 원래 출력과 다시 만든 글의 길이 비율은 보통 패킷에서 약 51~52%였고 긴 URI 패킷에서 87%였다 [3].
1 MiB 안의 출력이 다시 만든 뒤 720,000자를 넘으려면 이 비율이 68.7%보다 커야 한다 [8][3].
보통 패킷만 담은 `udp.pcap`은 이 상한에 닿기 전에 실행 상한으로 거부되었다 [3].

### R02.05 상한 초과 시 거부

**구현.** 이 방식은 서버가 `execAsync`로 실행하는 모든 `tshark` 명령에 적용된다 [9][10].
서버는 `maxBuffer`를 주지 않으므로 Node.js 22.17.0의 기본값 1 MiB가 표준 출력과 표준 오류에 각각 쓰인다 [9][8].
출력이 이 값을 넘으면 Node.js가 `tshark` 프로세스를 끝내고 `stdout maxBuffer length exceeded` 오류로 Promise를 거부한다 [10].
처리기는 이 오류를 `isError` 참인 응답으로 돌려주고 받은 출력 일부를 싣지 않는다 [11].
출력이 15,168,897바이트인 pcap 파일로 `analyze_pcap`을 부르자 `Error: stdout maxBuffer length exceeded` 응답만 왔다 [3].
루프백에 UDP 패킷을 계속 보내며 `capture_packets`를 3초 동안 부르자 같은 오류 응답이 왔다 [3].

**한계.** 이 상한은 서버가 정한 값이 아니라 Node.js의 기본값이고 오류 문구에는 상한 값이나 출력 크기가 없다 [9][10].
같은 pcap 파일로 부른 `extract_credentials`는 필드 몇 개만 읽어 출력이 이 값 안에 들어와 성공 응답을 돌려주었다 [3].
