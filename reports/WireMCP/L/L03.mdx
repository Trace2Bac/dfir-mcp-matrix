# L03 기록 실패 처리

### L03.06 쓰기 실패 시 프로세스 종료

**구현.** 이 방식은 도구 처리기 7개가 실행 전에 쓰는 줄에 적용된다 [1][2][3].
서버의 기록은 `console.error`로 프로세스의 표준 오류에 쓰는 줄이다 [4].
처리기는 모두 `tshark`를 실행하거나 URLhaus 목록을 받기 전에 줄을 하나 이상 쓴다 [1][2][3].
`tshark`를 쓰는 처리기는 `findTshark`의 `Found tshark at:` 줄을, `check_ip_threats`는 `Checking IP <ip> against URLhaus blacklist` 줄을 먼저 쓴다 [1][2][3].
서버 코드는 이 쓰기의 결과를 확인하지 않는다 [1][2][3].

Node.js 22.17.0의 전역 `console`은 쓰기 오류를 무시하도록 만들어지고 쓰는 동안 난 동기 예외를 처리해 호출한 쪽으로 넘기지 않는다 [5].
그러나 표준 오류를 `/dev/full`에 연결해 서버를 실행하자 다음처럼 동작했다 [6].

- 서버가 시작할 때 쓴 `WireMCP Server is running...` 줄은 실패했지만 서버는 계속 실행되었고 초기화 응답도 나갔다 [6].
- 그 뒤 도구 호출에서 처리기가 첫 줄을 쓰자 `ENOSPC` 쓰기 오류가 처리되지 않은 예외로 올라와 서버 프로세스가 종료 코드 1로 끝났다 [6].
- 예외는 `check_ip_threats`에서는 `Checking IP` 줄을 쓰는 곳에서, `capture_packets`에서는 `findTshark`가 `Found tshark at:` 줄을 쓰는 곳에서 났다 [6][2][1].
- `capture_packets` 호출 뒤 작업 폴더에 `temp_capture.pcap`이 생기지 않아 `tshark`는 실행되지 않았다 [6].

프로세스가 끝나므로 호출한 쪽은 도구 결과도 오류 응답도 받지 못한다 [6].
MCP TypeScript SDK 클라이언트는 이 호출에 `MCP error -32000: Connection closed`를 받았고 같은 세션의 다음 요청은 `Not connected`로 끝났다 [6].

**한계.** 처음 실패한 쓰기는 알림 없이 지나가므로 서버 시작 줄처럼 도구 호출 밖에서 쓰기가 실패하면 그 사실이 남지 않는다 [5][6].
서버를 시작할 때부터 표준 오류가 가득 찬 경우만 실행했고 호출 도중에 쓰기가 처음 실패하는 경우와 파이프가 닫힌 경우는 실행하지 않았다.

처리되지 않은 예외를 파일에 남기는 `-r` 모듈을 붙여 같은 실행을 되풀이하자 예외는 `ENOSPC: no space left on device, write`였다.
호출 위치는 [`index.js:259`](https://github.com/0xKoda/WireMCP/blob/7f45f8b2b4adeb76be8c6227eefb38533fdd6b1e/index.js#L259)(`check_ip_threats`)와 [`index.js:20`](https://github.com/0xKoda/WireMCP/blob/7f45f8b2b4adeb76be8c6227eefb38533fdd6b1e/index.js#L20)(`findTshark`)였다.
같은 컨테이너에서 한 틱 안에 `console.error`를 세 번 부른 Node.js 스크립트는 종료 코드 0으로 끝났고 타이머로 두 번째 틱에 다시 부른 스크립트는 종료 코드 1로 끝났다.
