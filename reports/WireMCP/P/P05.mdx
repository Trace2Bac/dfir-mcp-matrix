# P05 사건 자료 정리

### P05.03 자동 정리

**구현.** 이 방식은 실시간 캡처 도구 4개(`capture_packets`, `get_summary_stats`, `get_conversations`, `check_threats`)의 캡처 파일 `temp_capture.pcap`에 적용된다 [1][2].
네 도구는 `tshark -i`로 서버 프로세스의 작업 폴더에 `temp_capture.pcap`을 쓰고 `tshark -r`로 그 파일을 읽어 응답을 만든다 [1][2][3].
응답을 돌려주기 전에 `fs.unlink`로 이 파일을 지운다 [1][2].
`check_threats`는 URLhaus 목록을 내려받지 못한 경우에도 그 예외를 따로 처리하므로 파일을 지우는 단계까지 실행한다 [4].
응답은 캡처 파일을 지웠다는 사실을 적지 않는다 [1][2].

사건 자료를 지우거나 초기화하는 MCP 도구와 사용자 명령은 없다 [5].
`analyze_pcap`과 `extract_credentials`는 받은 pcap 파일을 읽기만 하고 지우지 않는다 [6].

**한계.** 파일을 지우는 단계는 도구가 성공한 경로에만 있다 [1][2].
캡처 명령이나 읽기 명령이 실패하거나 출력 해석이 예외로 끝나면 `catch`가 오류 응답을 돌려주고 파일을 지우지 않는다 [1][2].
Node.js 22.17.0의 `exec`는 하위 프로세스의 표준 출력이 `maxBuffer` 기본값 1 MiB를 넘으면 그 프로세스를 끝내고 오류로 처리한다 [7].
그래서 읽기 명령의 출력이 1 MiB를 넘는 캡처에서도 캡처 파일은 작업 폴더에 남는다 [1][7].
남은 파일은 다음 실시간 캡처 호출이 같은 이름으로 다시 쓰고 지울 때까지 그대로 있다 [2].
루프백 인터페이스에 트래픽을 많이 보내는 동안 `capture_packets`를 부르자 `maxBuffer` 오류로 끝났고 캡처 파일이 작업 폴더에 남았다 [8].
이어서 부른 `get_summary_stats`는 같은 inode에 파일을 다시 쓰고 성공한 뒤 그 파일을 지웠다 [8].
지우기에 실패하면 서버는 표준 오류에 한 줄을 남기고 응답에는 그 사실을 싣지 않는다 [1].

### P05.04 원본 증거까지 삭제 대상에 포함

**구현.** 이 방식은 실시간 캡처 도구 4개의 자동 정리에 적용된다 [1][2].
지우는 파일은 서버가 서버 호스트의 인터페이스에서 캡처한 패킷을 담은 파일이다 [1].
네 도구는 캡처한 패킷을 이 파일에만 쓰고 다른 곳으로 옮기거나 사본을 남기지 않는다 [1][2].
응답에는 도구마다 정해 둔 필드나 통계만 실린다 [1][2].
그래서 호출이 성공하면 캡처한 패킷 자체는 남지 않는다 [1].
서버는 지울 파일이 그 호출에서 쓴 파일인지 확인하지 않고 작업 폴더의 고정 이름으로 지운다 [1][2].
서버가 만들지 않은 같은 이름의 파일을 작업 폴더에 두고 `get_conversations`를 부르자 응답은 성공이었고 앞 파일이 있었다는 내용이 없었으며 그 파일은 호출 뒤 남지 않았다 [8].
`capture_packets`를 3초로 부른 동안 `get_summary_stats`를 1초로 부르자 뒤 호출은 성공했고 앞 호출은 tshark가 `temp_capture.pcap`이 없다고 알린 오류로 끝났다 [8].

작업 폴더에 직접 쓴 21바이트 글 파일 `temp_capture.pcap`을 두고 `get_conversations`를 부르자 응답은 대화 통계였고 호출 뒤 파일이 없었다.
`capture_packets`를 3초로 부르고 0.3초 뒤에 `get_summary_stats`를 1초로 부르자 `get_summary_stats`는 성공했고 `capture_packets`는 `isError`가 참인 응답에 `tshark -r` 실패를 실었다.
그때 서버 표준 오류에는 `temp_capture.pcap`이 없다는 tshark 문장이 남았다.
