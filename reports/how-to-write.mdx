# 원고 작성 가이드

이 문서는 새 서버를 분석해 원고를 쓰는 순서를 처음부터 끝까지 안내합니다.
원고 파일의 형식은 [reports/ — 서버별 원고](README.mdx)에, 판단 기준은 [CONTRIBUTING.md의 판단 기준](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/CONTRIBUTING.md#판단-기준)에 있습니다.
용어는 [용어 사전](/docs/glossary)을 봅니다.

## 1. 준비하기

1. 이 저장소에서 Python 가상환경을 만들고 `pip install -r requirements.txt`를 실행합니다.
2. 분석 대상 서버의 저장소를 클론합니다.
   - 기본 위치는 이 저장소의 부모 폴더이고, 클론 폴더 이름은 서버 이름과 같아야 합니다.
   - 다른 곳에 두었다면 클론을 모아 둔 폴더를 환경변수 `DFIR_CLONES`에 지정합니다.
   - 도구가 기준 커밋을 `git show`로 읽으므로 그 커밋을 checkout하지 않아도 됩니다.
3. 분석할 기준 커밋(40자)을 정합니다. 원고의 줄 번호와 링크는 모두 이 커밋 기준입니다.

## 2. 틀 만들기

```
python tools/pilot.py new <서버> --repo <소유자/이름> --commit <40자 커밋>
```

- 서버 개요(`reports/<서버>/index.mdx`)와 시범 셀(`matrix/config.yaml`의 `pilot_cells`) 원고의 틀을 만들고, `config.yaml`의 `servers`에 서버를 더합니다.
- 셀을 더 만들 때는 `python tools/pilot.py new <서버> <셀ID> …`를, 모든 셀은 `python tools/pilot.py new <서버> all`을 실행합니다.
- 틀은 머리말 `details`가 비어 있어 화면에서 미확인으로 보이고, `validate`가 "작성 중인 틀"로 알립니다.

## 3. 서버 개요 쓰기

서버 개요에는 그 서버의 모든 원고에 공통인 정보를 씁니다.

- **범위**: 어느 폴더와 프로그램을 서버로 보는지, 같은 저장소의 클라이언트나 CLI를 어떻게 다루는지 씁니다.
- **확인 방법**: 코드를 어떻게 읽었고 무엇을 실행해 확인했는지 씁니다.
- 저장소가 외부 도구의 버전을 정하지 않았다면 버전 기준을 하나 정해 여기에 적습니다. 정하는 법은 [CONTRIBUTING.md의 특수한 경우](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/CONTRIBUTING.md#특수한-경우)에 있습니다.

## 4. 셀 원고 쓰기

셀마다 다음 순서로 씁니다.

1. **셀 정의를 읽습니다.** 셀 틀의 주석에 확인 사항과 상세 목록이 있습니다. 확인 범위, 다른 셀과 차이점, 상세의 포함·제외 기준은 사이트의 셀 화면이나 `matrix/cells/<축>/<셀ID>.mdx`에서 봅니다.
2. **서버가 해당하는 상세를 정합니다.**
   - 여러 상세에 해당할 수 있습니다. 머리말 `details`에 해당하는 상세를 소제목 차례대로 적습니다.
   - 어느 상세에도 해당하지 않으면 `not_implemented`(미구현)나 `not_applicable`(비적용) 하나를 적습니다.
   - 기준에 맞는 새 방식을 찾았는데 맞는 상세가 없으면 셀 정의에 상세를 더합니다. `matrix/candidates.yaml`에 그 방식이 후보로 있으면 그 항목을 셀 정의로 옮깁니다. 상세를 더하는 일은 언제든 해도 됩니다([상세 다루기](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/matrix/README.md#상세-다루기)).
3. **단락을 씁니다.**
   - 상세마다 `### <상세 번호> <상세 이름>` 소제목 아래 **구현.** 단락을 씁니다. 첫머리에 그 방식이 서버의 어느 도구나 경로에 적용되는지 적습니다.
   - 그 범위 안에서 방식이 적용되지 않는 경로나 조건이 있으면 **한계.** 단락에 사실로 씁니다.
   - 미구현이나 비적용이면 `### 미구현`(또는 `### 비적용`) 아래 **판단.** 단락에 이유를 씁니다.
4. **문장 규칙을 지킵니다.** 한 줄에 문장 하나를 쓰고 "~다"로 끝냅니다. 코드 이름이 든 문장에는 근거 표지 `[번호]`를 답니다. 좋고 나쁨을 매기는 말 대신 "해당한다", "적용되지 않는다"처럼 사실로 씁니다([작성 규칙](/docs/writing-rules)). 원고는 그 셀만 다루므로 다른 셀에 속하는 동작은 그 셀의 원고에 쓰고, 본문에는 셀·상세 번호를 쓰지 않습니다.
5. **근거를 씁니다.** `### 근거` 아래 번호마다 확인할 동작을 한 문장으로 쓰고, 코드는 손으로 옮기지 않고 `@발췌 경로:시작-끝` 한 줄을 둡니다.

**셀 정의로 판정이 갈리면** 정의를 고치지 않습니다. 지금 정의대로 판정하고 GitHub 이슈나 토론에 올립니다. 정의는 검토 주기에 모아서 고칩니다.

## 5. 검사하기

```
python tools/pilot.py fill <서버>        # @발췌를 기준 커밋 코드로 채우고 `경로:줄`을 링크로 바꾼다
python tools/pilot.py renumber <서버>    # 문장을 옮겼으면 근거 번호를 다시 매긴다
python tools/pilot.py check <서버>       # 형식, 근거 표지, 발췌 원문, 문장 규칙을 검사한다
cd web && npm start                      # 화면으로 본다
```

`check`가 낸 오류를 모두 고칩니다.
여러 사람이 한 서버를 나눠 쓰면 `check <서버>:<셀ID>,<셀ID>`처럼 자기 셀만 검사할 수 있습니다.

## 6. 기능 빠짐 확인하기 (선택)

서버의 도구나 SDK 메서드가 많으면 `reports/<서버>/coverage.mdx` 머리말에 기능 목록을 두고 `python tools/coverage.py <서버>`를 실행합니다.
본문에 이름이 나오지 않는 기능을 하나씩 보고, 공통 처리기와 다른 고유한 처리(판정 규칙, 상한, 입력 준비, 명세와 다른 동작)가 있으면 해당 셀 원고에 씁니다.

## 7. 마치기

- 셀 틀의 "작성 중" 주석을 지웠는지, `validate`에 "작성 중인 틀" 오류가 남지 않았는지 확인합니다.
- 서버 개요의 `matrix_version`이 지금 매트릭스 버전(`matrix/config.yaml`의 `version`)과 같은지 확인합니다.
- 다 쓴 원고만 커밋합니다. 쓰는 중인 틀이 남아 있으면 `validate`가 실패하고, 버전 태그를 올릴 때 CI도 배포하지 않습니다.
