# F02 발견사항·결론 도출

### F02.01 규칙·키 기반 판정·상관

**구현.** 이 방식은 `findevil-agent-mcp`의 `detect_contradictions`, `judge_findings`, `correlate_findings`, `find_ai_signatures`와 `findevil-mcp`의 `bits_parse`, `hashset_lookup`, `wmi_persist_parse`, `oe_dbx_parse`, `lecmd` 실행 파일이 없을 때의 `ez_parse`에 적용된다 [1][2][3][4][5][6][7][8][9].
`findevil-agent-mcp`의 네 도구는 클라이언트가 넘긴 발견사항이나 글을 판정하고 결과를 응답으로만 돌려준다 [1][2][3][4].
`detect_contradictions`는 Pool A와 Pool B의 발견사항 쌍마다 다음 규칙을 차례로 대어 하나라도 맞으면 모순 기록을 만든다 [10].

- 같은 `tool_call_id`를 한쪽은 CONFIRMED, 다른 쪽은 HYPOTHESIS로 인용한 쌍이 모순이다 [10].
- 같은 호출과 같은 `artifact_path`에 ATT&CK 기법을 다르게 적은 쌍이 모순이다 [10].
- 같은 `artifact_path`를 인용하고 설명 글의 낱말이 30% 미만으로 겹치는 쌍이 모순이다 [10][11].
- 같은 파일 이름이나 해시를 두고 한쪽은 있다고 적고 다른 쪽은 없다고 적은 쌍이 모순이다 [10].
- 같은 파일 이름이나 해시를 두고 적은 시각이 서로 겹치지 않는 쌍이 모순이다 [10].

`detect_contradictions`는 두 pool을 합친 발견사항에서 서비스, 네트워크 연결, 로그 삭제, 실행 흔적을 정규식으로 찾는다 [12].
함께 있어야 할 다른 흔적이 없으면 다섯 가지 단서 가운데 하나로 기록을 만든다 [12].
`judge_findings`는 `tool_call_id`, `artifact_path`, `mitre_technique`, pool 접두어를 뺀 `finding_id`가 모두 같은 발견사항을 한 주장으로 묶는다 [13].
`correlate_findings`는 설명 글과 `mitre_technique`로 실행 주장인지, 어느 전술 검사에 해당하는지 정한다 [14].
그다음 설명 글에 나오는 아티팩트 분류로 등급을 낮출지 정한다 [14][15].
`find_ai_signatures`는 정해 둔 서명 목록을 받은 글과 파일에 대어 LLM 도구나 에이전트 흔적을 단서로 낸다 [4][16].
`bits_parse`는 URL의 호스트가 IPv4 주소이거나 URL이 실행 파일 확장자로 끝나면 의심 URL로 보고 그 수를 `suspicious_url_count`에 싣는다 [5].
`hashset_lookup`은 사용자가 준 해시 목록과 대조해 `known_bad`와 `known_good`에 모두 있으면 `known_bad`로 판정한다 [6].
`wmi_persist_parse`는 WMI consumer, filter, binding이 모두 있으면 `persistence_pattern_present`를 참으로 싣는다 [7].
`oe_dbx_parse`는 뉴스그룹 이름에 `hack`, `crack`, `warez` 같은 정해 둔 낱말이 들어간 것을 `hacking_newsgroups`에 따로 싣는다 [8].
`ez_parse`는 `lecmd` 실행 파일을 찾지 못하면 LNK 파일 경로가 `Recent`나 `NetHood` 폴더 아래이고 `staged`, `anony` 같은 정해 둔 낱말이 들어간 경우에만 그 경로를 한 행으로 낸다 [9].
시험 입력에서 `detect_contradictions`는 Pool A·B 쌍 두 개를 모순으로, EID 1102 로그 삭제 발견사항 하나를 `LOG_WIPE` 단서로 돌려줬다 [17].

**한계.** `findevil-agent-mcp`의 규칙은 발견사항의 설명 글, 경로, 기법 문자열만 보고 인용한 호출의 출력은 읽지 않는다 [10][12][14].
`detect_contradictions`는 `pool_a` 목록에서 `pool_origin`이 A이거나 비어 있는 발견사항만, `pool_b` 목록에서 B이거나 비어 있는 발견사항만 비교한다 [10].
나머지 발견사항은 비교에서 빠지고 응답의 `pool_a_count`·`pool_b_count`는 뺀 것까지 포함한 입력 수다 [10][1].
`ez_parse`의 이 규칙에 맞지 않는 LNK 파일은 행 없이 돌려주고 응답에는 정해 둔 낱말 목록이 실리지 않는다 [9].

### F02.03 통계·점수 산정

**구현.** 이 방식은 `findevil-agent-mcp`의 `judge_findings`와 `detect_contradictions`에 적용된다 [2][11].
`judge_findings`는 등급을 CONFIRMED 1.0, INFERRED 0.6, HYPOTHESIS 0.3으로 바꾸고 pool마다 신뢰도를 곱해 점수를 낸다 [18][19].
pool의 신뢰도는 그 pool의 검증 결과 가운데 `approved`와 `downgraded`의 비율에 1.2를 곱한 값이고 검증 결과가 없으면 비율을 0.5로 둔다 [20].
두 pool이 같은 주장을 냈고 두 pool의 발견사항 가운데 그 주장과 다른 아티팩트 분류가 있으면 두 점수에 1.2를 더 곱한다 [19].
아티팩트 분류는 `artifact_path`와 설명 글에 디스크, 로그, 메모리 낱말이 있는지로 정한다 [21].
합친 점수는 두 점수의 합을 두 신뢰도의 합으로 나눈 값이고 0.8 이상이면 CONFIRMED, 0.5 이상이면 INFERRED, 그 밖은 HYPOTHESIS다 [19][21].
`detect_contradictions`는 같은 `artifact_path`를 인용한 두 발견사항의 설명 낱말 집합이 겹치는 비율(Jaccard)을 계산해 0.3 미만이면 모순으로 판정한다 [11][10].
두 pool이 같은 주장을 낸 시험 입력에서 합친 점수는 0.92였고 CONFIRMED로 나왔다 [17].

**한계.** 한 pool만 낸 CONFIRMED·INFERRED 발견사항은 합친 점수와 관계없이 원래 등급을 유지한다 [22].
`FIND_EVIL_REQUIRE_COUNTER_HYPOTHESIS`를 `1`로 두어야 이 발견사항에도 점수로 정한 등급이 붙는다 [22].
한 pool만 낸 CONFIRMED 발견사항은 합친 점수 0.667에도 CONFIRMED로 나왔고 이 환경변수를 켜자 INFERRED로 나왔다 [17][23].
신뢰도의 바탕인 검증 결과는 호출자가 `pool_a_verifier_actions`·`pool_b_verifier_actions`로 넘긴 값을 그대로 쓴다 [24].
`verify_finding`을 부르지 않고 `approved`를 적어 넘긴 시험 입력도 받아들여 신뢰도 계산에 쓰였다 [17].

### F02.05 사용 근거·변환 기록

**구현.** 이 방식은 `findevil-agent-mcp`의 `judge_findings`, `correlate_findings`, `detect_contradictions`, `verify_finding`의 응답에 적용된다 [25][3][1][26].
`judge_findings`는 합친 발견사항마다 두 pool의 점수, 두 신뢰도, 교차 확인 여부 `corroborated`, 고른 pool `chosen_pool`, 합친 점수를 싣는다 [25].
`correlate_findings`는 발견사항마다 적용한 검사, 사유, 받는 분류 조합, 빠진 분류를 싣는다 [3].
`detect_contradictions`는 모순 기록마다 두 발견사항의 요약과 인용한 `tool_call_id`를 싣는다 [1][27].
`verify_finding`은 다시 실행한 도구 이름, 인자의 SHA-256, 기록된 출력 해시와 다시 실행한 출력 해시, 출력에서 다시 읽은 값을 `replay_artifact`에 싣는다 [26].
네 도구는 이 기록을 응답으로만 돌려주고 호출 기록에는 클라이언트가 `audit_append`로 남긴다 [28].

**한계.** `detect_contradictions`의 기록에는 어느 규칙이 맞았는지 적은 사유 글이 없다 [27][1].
규칙 함수는 사유 글을 만들지만 기록으로 바꾸는 단계에서 빠진다 [10][27].
두 pool이 같은 주장을 내면 `judge_findings`는 설명 글이 더 긴 발견사항을 고르고 길이가 같으면 Pool A의 것을 고른다 [29].
`judge_findings`의 합친 기록은 고른 발견사항 하나만 싣고 함께 묶인 다른 pool 발견사항의 ID를 싣지 않는다 [19][25].
검증에서 `rejected`된 발견사항은 합치기 전에 빠지고 뺐다는 사실도 응답에 실리지 않는다 [30].
시험 입력에서 두 pool의 같은 주장을 합친 기록에는 Pool A의 `finding_id`만 있었고 `rejected`로 넘긴 Pool B 발견사항은 응답 어디에도 없었다 [17].

### F02.06 규칙 기반 공격 단계 분류·흐름 서술

**구현.** 이 방식은 `findevil-agent-mcp`의 `correlate_findings`에 적용된다 [3].
`correlate_findings`는 발견사항의 `mitre_technique` 앞부분을 표에 대어 LATERAL_MOVEMENT, PRIVILEGE_ESCALATION, PERSISTENCE, CREDENTIAL_ACCESS, DEFENSE_EVASION, COMMAND_AND_CONTROL 가운데 하나로 나눈다 [31][14].
기법 ID로 정해지지 않으면 T1059 같은 실행 기법 ID나 실행 낱말이 있는 발견사항을 EXECUTION으로 본다 [14][32].
그 밖의 발견사항은 설명 글의 전술 낱말로 나눈다 [14].
나눈 결과는 응답 `outcomes`의 `gate`에 실린다 [3].
보고서 스크립트가 공격 흐름과 Navigator 층을 만들 때 쓰는 `attackflow`는 `findevil_agent` 패키지에 있지만 서버 프로세스는 이 모듈을 불러오지 않는다 [33].

**한계.** 발견사항마다 처음 맞는 검사 하나만 고른다 [14][31].
기법 ID 없이 횡적 이동과 프로세스 생성을 함께 적은 시험 입력은 실행 낱말 때문에 EXECUTION으로 나뉘었다 [17].

### F02.08 확신 수준·추정 범위 표시

**구현.** 이 방식은 `findevil-agent-mcp`의 `judge_findings`, `correlate_findings`, `verify_finding`, `find_ai_signatures`에 적용된다 [25][3][26][4].
`judge_findings`는 합친 발견사항에 CONFIRMED·INFERRED·HYPOTHESIS 등급과 합친 점수를 싣는다 [25][19].
`correlate_findings`는 등급을 낮춘 발견사항을 `refined`에 싣고 `outcomes`의 `action`에 `downgraded`를 적는다 [3][34].
`verify_finding`은 발견사항마다 `approved`, `downgraded`, `rejected` 가운데 하나를 돌려준다 [26].
`find_ai_signatures`는 모든 일치를 단서로 보고 응답에 `confidence_tier`를 HYPOTHESIS로, `lead_only`를 참으로 싣는다 [4].

**한계.** `detect_contradictions`의 단서 기록에는 등급 필드가 없고 HYPOTHESIS라는 말은 Pool B 쪽 문구 안에만 들어 있다 [27][12].

def _token_overlap(a: str, b: str) -> float:
    """Jaccard token overlap on lowercased word-ish tokens."""
    tokens_a = set(_WORD_RE.findall(a.lower()))
    tokens_b = set(_WORD_RE.findall(b.lower()))
    if not tokens_a and not tokens_b:
        return 1.0  # both empty = perfectly agree (trivially)
    if not tokens_a or not tokens_b:
        return 0.0
    return len(tokens_a & tokens_b) / len(tokens_a | tokens_b)

    """Group findings that make the *same claim* so the A+B judge can corroborate.

    Keyed on ``(tool_call_id, artifact_path, mitre_technique, claim_id)`` where

        f.mitre_technique or "",
        _claim_id(f.finding_id or ""),
