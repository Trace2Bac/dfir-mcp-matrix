# L04 기록 위변조 방지

### L04.01 해시 체인

**구현.** 이 방식은 `findevil-agent-mcp`가 `AuditLog`로 쓰는 JSONL 파일에 적용된다 [1].
사건의 `audit.jsonl`에는 서버 도구가 쓰는 항목과 엔진 `scripts/find_evil_auto.py`가 `audit_append`로 쓰는 항목이 함께 들어가고 `expert_miss_capture`의 `expert_misses.jsonl`도 같은 방식으로 쓰인다 [1][2].
`AuditLog.append`는 항목의 `prev_hash`에 앞 줄 바이트의 SHA-256을 넣고 첫 항목에는 빈 문자열을 넣는다 [1][3].
줄은 키를 정렬하고 공백 없이 ASCII로 바꾼 JSON이다 [3].
`AuditLog`는 열릴 때 파일의 마지막 줄을 해시해 다음 항목의 `prev_hash`로 쓴다 [4].
`audit_append`, `memory_remember`, `memory_recall`, `pool_handoff`를 같은 파일로 부르자 항목 6개의 `prev_hash`가 앞 줄의 해시로 이어졌다 [5].

`manifest_finalize`는 체인을 다시 읽어 마지막 줄의 해시 `audit_log_final_hash`와 항목 수 `audit_log_record_count`를 기록 밖 파일 `run.manifest.json`에 남긴다 [6][7].
두 서버의 `injection_alerts.jsonl`과 `findevil-agent-mcp`의 표준 오류 항목에는 앞 항목의 해시가 없다 [8][9].

**한계.** 파일을 고칠 수 있는 쪽은 바꾼 항목부터 체인을 다시 계산해 쓸 수 있다.
같은 쓰기 함수로 한 항목의 값을 바꿔 체인 전체를 다시 쓰자 `audit_verify`는 `ok`가 참인 결과를 돌려줬다 [10].
이렇게 바꾼 것은 `run.manifest.json`의 끝 값과 대조할 때만 드러난다 [7][10].
끝 항목을 지운 파일은 남은 체인이 그대로 이어져 `audit_verify`가 `ok`가 참인 결과를 돌려줬다 [10].
`audit_append`는 호출한 쪽이 준 경로, `kind`, `payload`를 그대로 받으므로 서버 도구가 쓰는 종류의 항목도 체인 끝에 이어 쓸 수 있다 [2].
`manifest_finalize`는 봉인하기 전에 체인을 검증하지 않는다 [11].

### L04.02 일련번호

**구현.** 이 방식은 `AuditLog`로 쓰는 같은 JSONL 파일에 적용된다 [1].
항목의 `seq`는 0부터 하나씩 늘어난다 [1].
`AuditLog`는 열릴 때 파일의 줄 수가 마지막 항목의 `seq`에 1을 더한 값과 다르면 `AuditLogError`를 올리고 그 파일에 쓰지 않는다 [4].
`AuditLog.verify`는 줄마다 `seq`가 그때까지 읽은 줄 수와 같은지 대조한다 [12].
중간 줄 하나를 지운 사본으로 `audit_append`와 `audit_verify`를 부르자 두 호출 모두 `seq-count mismatch` 오류를 받았고 사본에 줄이 더해지지 않았다 [10].

**한계.** 끝 항목을 지우면 남은 번호가 이어지므로 일련번호로는 드러나지 않는다 [10].

### L04.03 검증 도구

**구현.** 이 방식은 `findevil-agent-mcp`의 `audit_verify`와 `manifest_verify`에 적용된다 [13][14].
`audit_verify`는 `AuditLog.verify`로 파일을 처음부터 다시 읽는다 [13][12].
줄마다 JSON 객체인지, `seq`가 이어지는지, `prev_hash`가 앞 줄의 해시와 같은지, 정규화한 JSON과 바이트가 같은지 대조한다 [12].
처음 어긋난 곳에서 멈추고 `ok`를 거짓으로, 그 까닭을 `error`에 담아 돌려준다 [13].
중간 항목의 값 하나를 바꾼 사본으로 부르자 `seq 4: prev_hash break`를 담은 결과가 돌아왔다 [10].

`manifest_verify`는 `verify_manifest`로 체인을 다시 읽은 뒤 기록에서 항목 수, 마지막 줄의 해시, 잎 목록을 다시 계산해 manifest에 적힌 값과 대조한다 [14][7].
Ed25519 서명은 manifest 본문으로 다시 검증한다 [15].
끝 항목을 지운 사본은 항목 수가 다르다는 결과를, 체인을 다시 쓴 사본은 끝 해시가 다르다는 결과를 받았다 [10].

**한계.** `audit_verify`는 파일이 없으면 `ok`가 참이고 항목 수가 0인 결과를 돌려준다 [13].
없는 경로로 부르자 그 결과가 돌아왔다 [5].
중간 줄이 빠진 파일은 `AuditLog`를 만드는 단계에서 예외가 나므로 `audit_verify`는 `ok`가 거짓인 결과 대신 `kind`가 `handler`인 오류 결과를 돌려줬다 [4][10].
`manifest_verify`는 서명 종류가 `stub`나 `sigstore`이면 서명이 검증되지 않아도 다른 대조가 통과할 때 `overall`을 참으로 둔다 [16].

### L04.05 기록 밖 항목 해시 대조

**구현.** 이 방식은 `manifest_finalize`가 쓰는 `run.manifest.json`의 잎 목록 `leaves`와 그것을 대조하는 `manifest_verify`에 적용된다 [6][14].
`_walk_audit_log`는 `finding_approved` 항목마다 그 줄의 SHA-256을 잎 값으로 삼는다 [17].
`tool_call_output` 항목은 항목 줄의 해시가 아니라 `payload`의 `output_hash` 값을 잎 값으로 삼는다 [17].
`output_hash`가 64자리 16진수가 아니면 그 항목 줄의 해시를 잎 값으로 삼는다 [17].
잎마다 `seq`, 종류, `finding_id`나 `tool_call_id`를 함께 적는다 [17].
`manifest_verify`는 기록에서 잎 목록을 다시 만들어 manifest의 목록과 대조하고 다르면 `audit_chain_ok`를 거짓으로 둔다 [7].
`tool_call_output`과 `finding_approved` 항목을 하나씩 넣은 기록으로 봉인하자 `leaves`에 `output_hash` 값과 `finding_approved` 줄의 해시가 들어갔다 [5].

**한계.** `tool_call_output` 항목에서 `output_hash`와 `tool_call_id` 말고 다른 필드가 바뀐 것은 잎 대조로 드러나지 않는다 [17].
대조 결과는 잎 목록이 다르다는 문구 하나이고 어느 항목이 바뀌었는지, 사라졌는지 알려 주지 않는다 [7].
같은 `tool_call_id`나 `finding_id`가 겹친 항목을 따로 찾지 않는다 [17][7].
잎 대조는 체인 검증과 항목 수, 끝 해시 대조를 통과한 뒤에만 한다 [7].
그래서 기록의 항목이 바뀌거나 사라지면 잎 대조에 앞서 체인 검증이나 항목 수, 끝 해시 대조에서 드러난다 [7][12].

### L04.07 서명·MAC

**구현.** 이 방식은 `findevil-agent-mcp`의 `manifest_finalize`가 쓰는 `run.manifest.json`에 적용된다 [6][18].
`build_manifest`는 체인의 끝 해시 `audit_log_final_hash`, 항목 수 `audit_log_record_count`, Merkle 루트, 잎 목록을 담은 본문을 정규화한 바이트에 서명한다 [19].
`signer`의 기본값은 `ed25519`이고 서버는 `FINDEVIL_SIGNING_KEY`나 `~/.findevil/signing.key`의 로컬 Ed25519 키로 서명한다 [18][15].
키 파일이 없으면 서버가 새 키를 만들어 그 경로에 쓴다 [15].
서명 묶음에는 공개 키, 서명, 본문의 SHA-256 `payload_sha256`, 공개 키의 SHA-256 `cert_fingerprint`가 들어간다 [15].
`ed25519`로 봉인한 manifest의 본문 값을 고친 사본은 `manifest_verify`에서 `overall`이 거짓이었다 [20].

**한계.** `manifest_verify`는 서명 묶음에 들어 있는 공개 키로만 서명을 검증하고 기대하는 공개 키 지문과 대조하지 않는다 [15].
다시 쓴 체인을 다른 키로 봉인한 manifest는 `manifest_verify`에서 `overall`이 참이었다 [10].
`manifest_finalize`는 이미 봉인한 기록인지 보지 않고 같은 출력 경로의 manifest를 새로 쓴다 [21].
체인을 다시 쓴 기록으로 같은 서버의 `manifest_finalize`를 다시 부르자 앞과 같은 공개 키 지문의 manifest가 생겼고 `manifest_verify`의 `overall`이 참이었다 [22].
`manifest_verify`는 서명 종류를 서명 대상 밖인 manifest의 `signature.kind`에서 읽고 이 값이 `stub`이나 `sigstore`이면 서명을 검증하지 않는다 [23][24].
`ed25519`로 봉인한 manifest의 본문과 서명 종류를 함께 고친 사본은 `overall`이 참이었다 [20].
서명 키를 읽거나 만들지 못하면 서명기가 `stub`으로 바뀌어 키를 쓰지 않은 값이 서명 자리에 남는다 [18][25].
서명 키 경로를 일반 파일 아래로 둔 서버에서 봉인한 manifest는 `signer_effective`가 `stub`이었고 `manifest_verify`의 `overall`은 참이었다 [26].

### L04.08 외부 투명성 기록 고정

**구현.** 이 방식은 `findevil-agent-mcp`의 `manifest_finalize`에서 `anchor_transparency`가 참이고 `FINDEVIL_REKOR_ENABLE`이 켜져 있을 때 적용된다 [27].
`manifest_finalize`는 잎으로 만든 Merkle 루트를 `anchor_merkle_root`로 Sigstore Rekor에 올리고 실패하면 RFC 3161 시각 인증 서버에 시각 인증을 요청한다 [27][28].
돌려받은 기록은 `transparency_log` 블록으로 manifest에 더하고 manifest 파일을 다시 쓴다 [27].
이 블록은 서명한 뒤에 더하므로 서명 대상 본문에서 빠진다 [23].
`manifest_verify`는 `verify_anchor`로 블록의 대상 다이제스트를 manifest의 `merkle_root_hex`와 대조하고 Rekor 포함 증명이나 RFC 3161 토큰을 확인해 결과를 `transparency_ok`에 싣는다 [29][30].

**한계.** 실제 Rekor 등록과 시각 인증 요청은 실행으로 확인하지 않았다.
`FINDEVIL_REKOR_ENABLE`을 켜고 네트워크가 없는 환경에서 부르자 `transparency_kind`가 `none`인 결과가 왔다 [31].
두 곳에 모두 올리지 못하면 오류 없이 `kind`가 `none`인 블록을 남긴다 [28].
`transparency_ok`는 `overall`에 반영되지 않는다 [29][16].
같은 출력 경로로 다시 봉인하면 `manifest_finalize`가 manifest를 새로 쓰므로 앞 봉인의 블록은 그 파일에 남지 않는다 [21].
이 루트에는 잎만 들어가고 체인의 끝 값은 들어가지 않는다 [6][17].

```python
def canonicalize_json(obj: Any) -> bytes:
    """Return the RFC-8785-compatible canonical bytes for ``obj``.

    ``sort_keys=True`` + tightest separators + UTF-8 + escape
    non-ASCII to ``\\uXXXX``. Two logically-equal Python dicts
    produce byte-identical output regardless of key-insertion order.
    """
    return json.dumps(
        obj,
        sort_keys=True,
        separators=_CANONICAL_SEPARATORS,
        ensure_ascii=True,
    ).encode("ascii")


def hash_line(line: bytes) -> str:
    """SHA-256 of a full JSONL line (without the trailing newline)."""
    h = hashlib.sha256()
    h.update(line.rstrip(b"\n"))
    return h.hexdigest()
```

```python
class FallbackSigner:
    """Tries a primary signer (real sigstore) and honestly degrades to a
    fallback (stub) when the primary fails — the typical offline / no-token
    case. The returned bundle carries ``kind="stub"`` and a non-empty
    ``fallback_reason`` so the release gate reads the *effective* signer, not
    the *requested* one, and never crashes a run just because Fulcio/Rekor
    (or an OIDC token) was unavailable.
    """

    def __init__(self, primary: Signer, fallback: Signer) -> None:
        self._primary = primary
        self._fallback = fallback

    def sign(self, payload: bytes) -> SignedBundle:
        try:
            return self._primary.sign(payload)
        except Exception as exc:  # degrade on ANY primary-signer failure
            bundle = self._fallback.sign(payload)
            reason = f"primary signer failed, degraded to {bundle.kind}: {exc}"
            if bundle.fallback_reason:  # nested fallback — keep the inner story
                reason = f"{reason} (after: {bundle.fallback_reason})"
            return replace(bundle, fallback_reason=reason)
```

```python
def verify_anchor(block: dict[str, Any], merkle_root_hex: str) -> bool | str:
    """Offline-verify a ``transparency_log`` block against ``merkle_root_hex``.

    Pure/offline — contacts no network. Confirms the block's subject digest
    equals the manifest's Merkle root, then verifies the transparency evidence:
    a Rekor inclusion proof is re-derived from its embedded body/hashes/root
    (sigstore's own RFC-6962 verifier), and an RFC-3161 token is checked with
    ``openssl ts``. Returns ``True`` or an honest reason string. Never raises.
    """
    if not isinstance(block, dict):
        return "transparency_log block is not an object"
    subject = _subject_digest(block)
    if subject != merkle_root_hex:
        return (
            f"transparency subject digest {subject!r} != manifest merkle root "
            f"{merkle_root_hex!r}"
        )
    kind = block.get("kind")
    if kind == "none":
        return str(block.get("fallback_reason") or "root was not anchored")
    if kind == "rekor":
        return _verify_rekor_block(block)
    if kind == "rfc3161":
        return _verify_tsa_block(block, merkle_root_hex)
    return f"unknown transparency kind {kind!r}"
```
