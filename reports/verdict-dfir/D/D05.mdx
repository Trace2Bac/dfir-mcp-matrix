# D05 파생물 저장 실패 처리

### D05.01 오류·부분 완료 표시

**구현.** 이 방식은 `findevil-mcp`의 `case_open`·`disk_mount`·`disk_extract_artifacts`·`bulk_extract`·`pst_parse`와 `findevil-agent-mcp`의 파일 쓰기 도구에 적용된다 [1][2][3][4][5].
`findevil-mcp`의 이 도구들은 사건 폴더나 출력 폴더를 만들거나 파일과 기록을 쓰다 난 입출력 오류를 오류 값으로 돌려준다 [1][2][3][4].
서버는 입력 탓이 아닌 오류 값을 JSON-RPC 오류 코드 `-32603`과 문구로 응답한다 [6].
`FINDEVIL_HOME`을 일반 파일 아래로 두고 `case_open`을 부르자 `-32603` 오류와 만들지 못한 사건 폴더 경로가 왔다 [7].
사건 폴더의 `extracted`를 일반 파일로 바꾸고 `disk_extract_artifacts`·`bulk_extract`·`pst_parse`를 부르자 세 도구 모두 `-32603` 오류와 만들지 못한 경로를 돌려주었다 [7].
`disk_extract_artifacts`는 크기 상한을 넘어 지운 파일 수를 `artifacts_skipped_oversize`에, 꺼내지 못한 삭제 항목 수를 `deleted_recovery_failed`에 담아 응답한다 [8].

`findevil-agent-mcp`의 서버는 도구 처리 중 난 예외를 `error` 객체에 `kind`와 예외 문구를 담은 응답 글로 돌려준다 [5].
`manifest_finalize`의 `output_path`와 `memory_remember`의 `store_path`를 일반 파일 아래로 주자 `NotADirectoryError`와 경로를 담은 이 응답이 왔다 [9].

**한계.** `findevil-agent-mcp`는 예외 응답을 보통 응답과 같은 방식으로 돌려주므로 결과의 `isError`가 거짓이다 [5].
쓸 수 없는 경로로 부른 두 도구의 결과도 `isError`가 거짓이었다 [9].
`disk_extract_artifacts`는 파일을 모두 꺼낸 뒤 `session_resources.json`을 쓰므로 기록 쓰기가 실패하면 꺼낸 파일은 남고 기록에는 그 추출이 없다 [10].
`bulk_extract`는 `bulk_extractor`를 실행하기 전에 앞 출력 폴더를 지우므로 이번 실행이나 결과 읽기가 실패하면 앞 결과도 남지 않는다 [11].
`pst_parse`는 내보내기 결과를 읽다 실패하면 내보내기 폴더를 지우지 않고 오류를 돌려준다 [12].
`manifest_finalize`는 manifest 파일을 쓴 뒤에 투명성 기록 요청을 허용하는 `FINDEVIL_REKOR_ENABLE`을 확인한다 [13].
그래서 이 환경변수 없이 `anchor_transparency`를 주면 `handler` 오류 응답이 오지만 서명한 manifest 파일은 남는다 [13][5].
이 네 경로는 코드로만 확인했다.

### D05.03 알림 없이 계속

**구현.** 이 방식은 `findevil-mcp`의 `disk_extract_artifacts`가 삭제 항목이 아닌 파일을 꺼낼 때 적용된다 [14].
`icat`이 0이 아닌 값으로 끝나면 쓰던 파일을 지우고 그 파일을 건너뛴다 [14].
삭제 항목이 아니면 이 실패를 세는 필드가 없어 응답과 `session_resources.json`에 실패가 나타나지 않는다 [14][8].
시험용 `icat`이 한 inode에서 1로 끝나게 하자 그 파일 없이 성공 응답이 왔고 응답의 개수와 실패 수 필드에 그 파일이 나타나지 않았다 [15].

### D05.04 재시도·대체 저장

**구현.** 이 방식은 `findevil-agent-mcp`의 `manifest_finalize`가 manifest에 서명할 때 적용된다 [16].
`manifest_finalize`는 `signer`가 `ed25519`이면 `stub`을, `sigstore`이면 `ed25519`와 `stub`을 차례로 대체 서명기로 둔다 [16].
서명기가 예외로 실패하면 `FallbackSigner`가 다음 서명기로 서명하고 실패 문구를 `fallback_reason`에 넣는다 [17].
`build_manifest`는 실제로 쓴 서명기의 `kind`와 `fallback_reason`을 manifest의 `signature`에 적는다 [18].
응답에는 실제로 쓴 서명기가 `signer_effective`에, 바꾼 이유가 `fallback_reason`에 실린다 [19].
서명 키 경로를 일반 파일 아래로 둔 서버에서 `manifest_finalize`를 부르자 `signer_effective`가 `stub`이고 `fallback_reason`에 실패 문구가 들어간 manifest가 생겼다 [20].
네트워크가 없는 환경에서 `signer: sigstore`로 부르자 `signer_effective`가 `ed25519`로 바뀌었다 [20].

[17] `FallbackSigner`는 앞 서명기가 실패하면 다음 서명기로 서명하고 실패 문구를 `fallback_reason`에 넣는다.

```python
class FallbackSigner:
    """Tries a primary signer (real sigstore) and honestly degrades to a
    fallback (stub) when the primary fails — the typical offline / no-token
    case. The returned bundle carries ``kind="stub"`` and a non-empty
    ``fallback_reason`` so the release gate reads the *effective* signer, not
    the *requested* one, and never crashes a run just because Fulcio/Rekor
    (or an OIDC token) was unavailable.
    """

    def __init__(self, primary: Signer, fallback: Signer) -> None:
        self._primary = primary
        self._fallback = fallback

    def sign(self, payload: bytes) -> SignedBundle:
        try:
            return self._primary.sign(payload)
        except Exception as exc:  # degrade on ANY primary-signer failure
            bundle = self._fallback.sign(payload)
            reason = f"primary signer failed, degraded to {bundle.kind}: {exc}"
            if bundle.fallback_reason:  # nested fallback — keep the inner story
                reason = f"{reason} (after: {bundle.fallback_reason})"
            return replace(bundle, fallback_reason=reason)
```
