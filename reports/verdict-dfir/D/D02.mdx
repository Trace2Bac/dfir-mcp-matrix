# D02 파생물 추적

### D02.01 ID·경로 참조

**구현.** 이 방식은 `findevil-mcp`의 `disk_mount`·`disk_extract_artifacts` 기록과 `case_open`의 `case.json`, `findevil-agent-mcp`의 `manifest_finalize`가 쓰는 manifest에 적용된다 [1][2][3].
`disk_extract_artifacts`는 추출마다 `extract_id`를 매기고 사건 폴더의 `session_resources.json`에 그 ID와 부모 마운트 ID `parent_id`, 읽은 증거 이미지 경로, 출력 폴더를 남긴다 [1].
같은 항목의 `artifacts`에는 꺼낸 파일마다 이미지 안 경로 `source_path`, 꺼낸 경로 `extracted_path`, 크기, 삭제 항목 복구 여부가 들어간다 [1].
응답에도 같은 ID와 경로를 싣는다 [1].
`disk_mount`의 기록에는 마운트 ID, 증거 이미지 경로, 마운트 지점, 실행한 명령이 들어간다 [4].
추출은 마운트한 파일 시스템이 아니라 마운트 기록에 적힌 이미지 경로를 Sleuth Kit으로 직접 읽는다 [5].
`case_open`의 `case.json`은 사건 ID, 증거 경로, 증거 SHA-256을 함께 적는다 [2].
시험용 실행 파일로 두 번 추출하자 `session_resources.json`에 마운트 항목 하나와 그 마운트 ID를 `parent_id`로 가진 추출 항목 둘이 남았다 [6].

`manifest_finalize`가 쓰는 manifest의 leaf는 호출 기록의 순번 `seq`, 종류, 기록 ID를 담는다 [3].
기록 ID는 `tool_call_output` 기록이면 `tool_call_id`이고 `finding_approved` 기록이면 `finding_id`다 [3].
`finding_approved` 기록의 `tool_call_id`가 그보다 앞선 `tool_call_output` 기록에 없으면 manifest를 만들지 않는다 [7].
사용자 CLI `find_evil_auto.py`는 `tool_call_start` 기록에 도구 인자를 넣으므로 발견사항의 `tool_call_id`에서 그 호출의 입력 경로까지 이어진다 [8].
없는 호출 ID를 인용한 `finding_approved` 기록으로 `manifest_finalize`를 부르자 `UncitedFindingError`를 담은 응답이 왔고 manifest 파일은 생기지 않았다 [9].

`vss_mount`는 마운트 ID를 응답에만 싣고 `session_resources.json`에 남기지 않는다 [10].
`bulk_extract` 응답은 특징 파일의 사건 폴더 기준 경로를 싣지만 읽은 이미지의 경로는 싣지 않고 서버는 응답을 남기지 않는다 [11].
`pst_parse` 응답과 서버 기록에는 내보내기 폴더의 경로가 없다 [12].
`memory_remember`의 행은 사건 ID와 사건 경로를 담고 그 값을 만든 호출의 ID는 담지 않는다 [13].

**한계.** 호출 기록 항목의 `tool_call_id`, 인자, `output_hash`는 `audit_append`를 부르는 쪽이 정한 값이고 서버가 채우지 않는다 [14].
`manifest_finalize`는 인용한 ID의 `tool_call_output` 기록이 있는지만 보고 `tool_call_start` 기록과 그 인자가 있는지는 보지 않는다 [7].
`disk_mount`를 `mode: mock`으로 부르면 서버는 마운트하지 않고 호출 인자 `mount_point`의 폴더를 자원의 `fs_root`로 적는다 [15].
`disk_extract_artifacts`는 이 자원의 이미지를 Sleuth Kit으로 읽지 못하면 `fs_root` 폴더의 파일을 아티팩트로 복사한다 [15].
이때 `source_path`는 그 폴더 안 경로이고 추출 항목의 실행 명령은 `fls`·`icat`으로 적혀 폴더에서 복사했다는 사실은 부모 마운트 항목의 명령 `mock`으로만 드러난다 [15][16].
`mode: mock`과 작업 폴더 안의 `mount_point`로 `disk_mount`를 부른 뒤 `disk_extract_artifacts`를 부르자 그 폴더의 파일이 사건 폴더에 복사되었다 [17].
`disk_unmount`는 마운트 항목의 실행 명령을 해제할 때의 값으로 고쳐 쓰므로 마운트할 때 실행한 명령은 해제 뒤 기록에 남지 않는다 [18].

### D02.02 입출력 해시 연결

**구현.** 이 방식은 `findevil-agent-mcp`의 `manifest_finalize`가 쓰는 manifest에 적용된다 [3].
manifest는 입력인 호출 기록 파일의 마지막 줄 SHA-256 `audit_log_final_hash`와 기록 수 `audit_log_record_count`를 담는다 [3].
leaf마다 `tool_call_output` 기록의 `output_hash`나 `finding_approved` 기록 줄의 SHA-256을 담고 leaf들의 Merkle root를 `merkle_root_hex`로 남긴다 [3][19].
같은 파일의 서명 블록에는 manifest 본문을 정규화한 바이트의 SHA-256 `payload_sha256`이 들어간다 [20].
manifest는 입력 파일을 경로가 아니라 파일 이름 `audit_log_path`로만 적는다 [3].
에이전트 서버로 manifest를 만들자 `audit_log_final_hash`, `merkle_root_hex`, `payload_sha256`이 한 파일에 남았다 [9].

`findevil-mcp`의 파생물 기록에는 이런 해시 연결이 없다 [1][2].
`session_resources.json`은 꺼낸 파일의 크기만 적고 `case.json`은 증거 해시만 적는다 [1][2].
`bulk_extract` 응답은 특징 파일의 SHA-256을 싣지만 입력 이미지의 해시는 싣지 않는다 [11].

**한계.** `tool_call_output` leaf의 값은 호출한 쪽이 준 `output_hash`이고 서버는 그 값을 응답과 대조하지 않는다 [19][14].
`output_hash`가 64자리 16진수가 아니면 그 기록 줄의 SHA-256을 대신 쓴다 [19].
`payload_sha256`은 서명 블록과 투명성 기록 `transparency_log`를 뺀 본문의 해시다 [20].
`manifest_finalize`는 `audit_log_path`에 파일이 없으면 기록 0건으로 manifest를 만들어 쓴다 [21].

### D02.03 파생물 측 manifest

**구현.** 이 방식은 `findevil-mcp`의 `disk_extract_artifacts`가 꺼낸 파일에 적용된다 [1].
꺼낸 파일이 있는 사건 폴더의 `session_resources.json`에 추출마다 입력 이미지 경로, 추출 ID와 부모 마운트 ID, 실행 명령 `fls`·`icat`, 만든 시각 `created_at`이 들어간다 [1].
이 파일은 출력 폴더 안이 아니라 사건 폴더 바로 아래에 있고 한 사건의 마운트와 추출 기록을 모두 담는다 [1][22].
이 파일에는 입력이나 꺼낸 파일의 해시가 없고 추출을 부른 MCP 호출의 ID도 없다 [1].
`bulk_extract`와 `pst_parse`의 출력 폴더 곁에는 이런 파일을 두지 않는다 [11][12].

```python
def _uncited_findings(audit_log: AuditLog) -> list[str]:
    """finding_approved records whose tool_call_id is absent from the chain
    so far. Chain order matters: a finding cannot cite a future tool call."""
    seen_tool_calls: set[str] = set()
    uncited: list[str] = []
    for record in audit_log.iter_records():
        if record.kind == "tool_call_output":
            tcid = str(record.payload.get("tool_call_id") or "")
            if tcid:
                seen_tool_calls.add(tcid)
        elif record.kind == "finding_approved":
            cited = str(record.payload.get("tool_call_id") or "")
            if not cited or cited not in seen_tool_calls:
                uncited.append(str(record.payload.get("finding_id") or f"seq-{record.seq}"))
    return uncited
```

```python
def _payload_digest(payload: dict[str, Any], key: str) -> str | None:
    val = payload.get(key)
    if isinstance(val, str) and len(val) == 64:
        try:
            bytes.fromhex(val)
            return val
        except ValueError:
            return None
    return None
```

```python
def _to_json_safe(manifest: RunManifest, *, exclude_signature: bool = False) -> dict[str, Any]:
    """Convert the dataclass to a JSON-safe dict.

    Used both for canonicalizing-then-signing (with
    ``exclude_signature=True``) and for the on-disk write (with
    the signature included).
    """
    out: dict[str, Any] = asdict(manifest)
    if exclude_signature:
        out.pop("signature", None)
        # The transparency anchor is attached AFTER signing, so it must never be
        # part of the signed bytes — strip it on the sign/verify path exactly
        # like ``signature``. The on-disk write (exclude_signature=False) keeps
        # both, so a re-write that adds the anchor does not invalidate the
        # already-computed signature.
        out.pop("transparency_log", None)
    return out
```
