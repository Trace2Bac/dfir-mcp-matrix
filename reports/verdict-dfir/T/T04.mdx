# T04 실행 방식

### T04.01 서버 프로세스 안 분석

**구현.** 이 방식은 `findevil-mcp`의 파일 해석 도구와 `findevil-agent-mcp`의 도구 12개에 적용된다 [1][2].
`findevil-mcp`의 `evtx_query`, `prefetch_parse`, `mft_timeline`, `usnjrnl_query`, `yara_scan`, `browser_history`, `thumbcache_parse`, `exif_parse`, `email_parse`는 저장소가 정확한 버전으로 고정한 Rust 크레이트(`evtx`, `frnsc-prefetch`, `mft`, `usnjrnl-forensic`, `yara-x`, `rusqlite`, `cfb`, `kamadak-exif`, `mail-parser`)를 서버 프로세스 안에서 불러 증거 파일을 해석한다 [1][3].
`registry_query`는 저장소 안의 하이브 해석 코드 `regf.rs`를 쓴다 [4].
`sysmon_network_query`, `zeek_summary`, `cloud_audit`, `oe_dbx_parse`, `bits_parse`, `wmi_persist_parse`, `hashset_lookup`과 `case_open`의 해시 계산도 서버 프로세스 안에서 처리한다 [1].
`plaso_parse`의 `recycle_bin_info2` 파서와 Eric Zimmerman 도구가 없을 때의 `ez_parse` `lecmd`도 외부 도구를 실행하지 않고 서버 코드로 경로 문자열만 뽑는다 [5].
`findevil-agent-mcp`는 `verify_finding`과 `expert_miss_capture`를 뺀 도구 12개의 판정, 모순 탐지, 상관 분석, 기억 검색, 서명을 서버 프로세스 안의 `findevil_agent` 패키지 코드로 처리한다 [2].
`findevil-mcp`는 도구 처리기의 panic을 `catch_unwind`로 받아 그 호출만 오류로 돌려주고 서버는 계속 실행한다 [6].

### T04.02 같은 권한의 별도 프로세스

**구현.** 이 방식은 외부 도구를 실행하는 `findevil-mcp` 도구 25개와 `findevil-agent-mcp`의 `verify_finding`에 적용된다 [7][8].
`findevil-mcp`는 Rust 표준 라이브러리의 `std::process::Command`로 실행 파일 경로와 인자 배열을 따로 넘겨 자식 프로세스를 만든다 [7].
자식 프로세스는 서버의 환경변수와 계정을 그대로 물려받는다 [7].
`vol_run`과 `plaso_parse`는 공통 실행기 `proc_runner::run_with_timeout`을 거친다 [9].
이 실행기는 자식 프로세스를 새 프로세스 그룹으로 만들고 표준 입력을 닫은 채 실행한다 [9].
다른 도구는 `Command::output()`이나 `status()`로 바로 실행한다 [7].
`findevil-agent-mcp`의 `verify_finding`은 `subprocess.Popen`으로 인자 배열을 넘겨 실행한다 [8].
두 서버의 코드에는 셸 명령 문자열로 외부 도구를 실행하는 곳이 없다 [7][8][10].
`expert_miss_capture`는 GitHub 이슈를 만들려고 `subprocess.run`으로 `gh`를 실행한다 [10].
`manifest_finalize`와 `manifest_verify`는 RFC 3161 시각 인증 값을 만들거나 확인하려고 `subprocess.run`으로 `openssl`을 실행한다 [11].
두 실행은 증거 파일을 읽지 않는다 [10][11].
시험용 실행 파일은 서버를 실행한 계정으로 실행되었고 작업 위치는 서버의 작업 위치(`~/vdrun/src`, `findevil-agent-mcp`는 `services/agent_mcp`)였다 [12].

저장소의 실행 구성도 도구를 서버와 다른 곳에서 실행하지 않는다.
`.mcp.json.docker`는 두 서버를 `docker exec`로 컨테이너 `findevil-dfir` 안에서 실행하고 외부 도구도 같은 컨테이너에서 서버와 같은 계정 `analyst`로 실행된다 [13].
`.mcp.json.sift`는 SSH로 SIFT 가상 머신에서 두 서버를 실행하고 외부 도구는 그 가상 머신에서 서버와 같은 계정으로 실행된다 [14].

### T04.04 권한을 나눈 실행

**구현.** 이 방식은 `findevil-mcp`의 `disk_mount`와 `disk_unmount`가 `mode: auto`로 실행하는 마운트·해제 명령에 적용된다 [15].
두 도구는 공통 함수 `run_sudo_fixed`로 `sudo -n <실행 파일> <인자>`를 실행해 서버 계정과 달리 root 권한으로 실행한다 [15].
- `.E01` 같은 EWF 이미지는 처음부터 `sudo -n ewfmount`로 마운트하고 그 안의 NTFS 볼륨도 `sudo -n mount -t ntfs3 -o ro,loop`로 마운트한다 [16].
- raw 이미지는 `mount -o ro,loop`를 서버 권한으로 먼저 실행하고 실패하면 `sudo -n mount`로 다시 실행한다 [17].
- 파티션 오프셋을 찾는 `mmls`는 EWF 장치에서는 `sudo -n mmls`로, 파티션 목록을 만들 때는 먼저 서버 권한으로 실행한 뒤 실패하면 `sudo -n`으로 실행한다 [18].
- `disk_unmount`는 `umount`를 서버 권한으로 먼저 실행하고 실패하면 `sudo -n umount`로 다시 실행한다 [19].
권한을 높이는 방향이고 다른 도구와 이미지 추출(`fls`, `icat`)은 서버 권한으로 실행한다 [7].
`-n`을 주므로 비밀번호를 묻지 않고 실행할 수 있는 sudo 권한이 없으면 명령은 실패한다 [15].
`docker/dfir.Dockerfile`은 컨테이너 계정 `analyst`에 비밀번호 없는 sudo 권한을 주고 주석에 이 함수를 그 이유로 적는다 [20].
기록만 하고 실패하는 시험용 `mount`·`sudo`·`ewfmount`를 두고 `disk_mount`를 부르자 서버는 raw 파일에 `mount -o ro,loop`, 이어 `sudo -n mount -o ro,loop`를, `.E01` 파일에 `sudo -n ewfmount`를 실행했다 [21].

**한계.** raw 이미지를 `sudo`로 다시 마운트하는 단계는 마운트 실행 파일 이름이 기본값 `mount`일 때만 실행된다 [17].
환경변수 `FINDEVIL_MOUNT_BIN`을 정하면 raw 이미지는 서버 권한의 마운트만 시도한다 [17].
`docker/dfir.Dockerfile`은 이 값을 `/bin/mount`로 정한다 [22].
`FINDEVIL_MOUNT_BIN`을 시험용 `mount` 경로로 정하자 raw 파일은 `sudo` 없이 한 번만 마운트를 시도했고 `.E01` 파일은 그대로 `sudo -n ewfmount`를 실행했다 [21].

### T04.05 실행별 작업 폴더

**구현.** 이 방식은 `pcap_triage`가 `analyzer: zeek`으로 Zeek을 실행하는 경로에 적용된다 [23].
이 경로는 호출마다 임시 폴더 아래 `findevil-zeek-<프로세스 번호>-<나노초>` 폴더를 새로 만들고 그 폴더를 작업 위치(`cwd`)로 두어 `zeek -r <pcap>`를 실행한다 [23].
Zeek이 작업 위치에 쓴 로그를 `zeek_summary`로 읽은 뒤 그 폴더를 지운다 [23].
같은 pcap으로 두 번 부르자 시험용 `zeek`의 작업 위치는 호출마다 다른 폴더였고 호출이 끝난 뒤 두 폴더는 남지 않았다 [24].

다른 외부 도구는 서버의 작업 위치에서 실행된다 [7].
`hayabusa_scan`은 작업 위치를 규칙 폴더 `HAYABUSA_RULES_BASE`로 바꾸지만 이 폴더는 호출마다 새로 만드는 폴더가 아니다 [25].
`ez_parse`, `mac_triage`, `suricata_eve`, `plaso_parse`는 호출마다 임시 출력 폴더나 파일을 만들지만 작업 위치는 바꾸지 않는다 [26].

pub fn run_with_timeout(mut command: Command, timeout: Duration) -> Result<RunOutput, RunError> {
    #[cfg(unix)]

        // Own process group: isolates the child's subtree from the server's group
        // so the timeout teardown (and any operator `kill -- -<pgid>`) acts on the
        // child tree alone. `process_group` is a safe std builder method.
        command.process_group(0);

    let run = |cmd: &mut Command| -> Option<String> {

            .status
