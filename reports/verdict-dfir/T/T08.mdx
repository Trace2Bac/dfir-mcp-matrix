# T08 실행 종료 판별

### T08.01 종료 코드 확인

**구현.** 이 방식은 `findevil-mcp`가 외부 실행 파일을 부르는 도구와 `findevil-agent-mcp`의 `expert_miss_capture`, 시간 기록 경로의 `openssl` 실행에 적용된다 [1][2][3].
`findevil-mcp`의 도구는 실행 파일이 0이 아닌 종료 코드로 끝나면 `SubprocessFailed`를 내고 종료 코드와 표준 오류의 끝부분을 오류 글에 싣는다 [1].
실행 확인에서 종료 코드 3으로 끝나는 시험용 `vol`로 `vol_pslist`를 부르자 JSON-RPC 오류 -32603과 `volatility exited 3: fake vol error`가 왔다 [4].
`expert_miss_capture`는 `gh`의 종료 코드가 0이 아니면 이슈 주소를 `null`로 두고 시간 기록 경로는 `openssl`을 `check=True`로 실행해 0이 아닌 종료 코드를 예외로 받는다 [2][3].

몇 도구는 종료 코드만으로 실패를 정하지 않는다.
`ausearch`는 종료 코드 1이고 표준 오류에 `<no matches>`가 있으면 빈 결과로 본다 [5].
`pcap_triage`는 `tshark`의 종료 코드가 0이 아니어도 표준 출력이 비어 있지 않으면 그 출력을 분석한다 [6].
코드 주석은 마지막 패킷이 잘린 캡처에서 `tshark`가 0이 아닌 값으로 끝나면서 읽은 패킷은 모두 출력한다고 적는다 [6].
`vss_list`는 종료 코드를 보지 않고 출력에서 `Store:` 줄을 찾지 못하면 스냅숏이 없다고 본다 [7].
`vss_mount`는 종료 코드가 0이 아니면 `status`를 `unavailable`로 둔다 [7].
실행 확인에서 종료 코드 1과 `<no matches>`를 내는 시험용 `ausearch`의 응답은 빈 `rows`였고 종료 코드 2와 한 줄을 내는 시험용 `tshark`의 `pcap_triage` 응답은 대화 1건을 담은 성공 응답이었다 [4].

**한계.** `pcap_triage`는 `tshark`의 표준 오류를 직렬화하지 않아 0이 아닌 종료 코드로 끝난 실행의 응답에 종료 코드도 경고 문구도 남지 않는다 [6][8].
실행 확인의 위 `pcap_triage` 응답에도 종료 코드나 잘림 경고가 없었다 [4].
`vss_mount`는 종료 코드가 0이 아닐 때 종료 코드와 표준 오류를 응답에 싣지 않는다 [7].

### T08.02 시간 제한·종료 신호 처리

**구현.** 이 방식은 `findevil-mcp`의 `vol_run`과 `plaso_parse`, `findevil-agent-mcp`의 `verify_finding`, `judge_findings`, `expert_miss_capture`, 시간 기록 경로에 적용된다 [9][10][11][12][2][3].
`vol_run`과 `plaso_parse`는 실행 파일을 공용 실행기 `run_with_timeout`으로 실행한다 [9].
이 실행기는 하위 프로세스를 새 프로세스 그룹으로 시작하고 50밀리초마다 끝났는지 확인한다 [9].
제한 시간이 지나면 `/proc`에서 그 그룹에 속한 프로세스 ID를 모아 `kill -KILL` 명령 하나로 `SIGKILL`을 보내고 그룹의 첫 프로세스에도 `SIGKILL`을 직접 보낸 뒤 끝나기를 기다려 `RunError::Timeout`을 돌려준다 [9].
두 도구는 이를 시간 초과 오류로 바꾸고 오류 글에 제한 시간과 그 값을 바꾸는 환경변수를 적는다 [10].
기본 제한은 `vol_run`이 1800초(`FINDEVIL_VOL_TIMEOUT_SECS`)이고 `plaso_parse`는 `log2timeline.py`와 `psort.py` 단계마다 3600초(`FINDEVIL_PLASO_TIMEOUT_SECS`)다 [10].
환경변수 값이 양의 정수가 아니면 기본값을 쓴다 [9].
실행 확인에서 `FINDEVIL_VOL_TIMEOUT_SECS`를 2로 두고 8초 동안 멈춰 있는 시험용 `vol`로 `vol_run`을 부르자 2.1초 뒤 `volatility exceeded its 2 s time budget and was killed`가 왔다 [4].
그 시험용 `vol`이 8초 뒤 만들게 한 표시 파일은 생기지 않았다 [4].

`verify_finding`은 `findevil-mcp`를 새 하위 프로세스로 시작하고 응답 한 줄을 1800초까지 기다린다 [11].
그 시간이 지나면 `MCP request timed out after` 문구의 오류가 나고 다시 실행한 결과는 `replay_error`, 발견사항은 `rejected`가 된다 [11].
`verify_finding`은 호출을 마칠 때 하위 프로세스의 표준 입력을 닫고 5초 안에 끝나지 않으면 프로세스를 끝낸다 [11].
`judge_findings`는 서버 프로세스 안의 병합에 기본 120초 제한을 두고 병합 차례마다 지난 시간을 확인한다 [12].
제한을 넘으면 `budget_exceeded`를 참, `merged`를 빈 목록으로 두고 몇 건을 병합한 뒤 멈췄는지를 `budget_detail`에 적는다 [12].
실행 확인에서 `budget_seconds`를 1e-9로 주자 응답의 `budget_exceeded`는 참, `merged`는 빈 목록이었다 [13].
`expert_miss_capture`의 `gh` 실행과 시간 기록 경로의 `openssl` 실행과 시간 기록 요청은 30초 제한을 쓴다 [2][3].

**한계.** `vol_pslist`, `vol_psscan`, `vol_psxview`, `vol_malfind`, `hayabusa_scan`, `vel_collect`, `ez_parse`, `pcap_triage`, `bulk_extract` 같은 나머지 외부 실행은 시간 제한 없이 끝날 때까지 기다린다 [14].
`findevil-mcp`는 요청을 한 줄씩 차례로 처리하므로 이런 실행이 끝나지 않으면 다음 요청도 처리하지 못한다 [15].
`judge_findings`는 제한을 넘으면 그때까지 병합한 결과를 버린다 [12].

### T08.03 오류·출력 내용 판독

**구현.** 이 방식은 `findevil-mcp`가 외부 실행 파일의 출력을 해석하는 도구와 `findevil-agent-mcp`의 `verify_finding`에 적용된다 [16][17][18][19].
Volatility 도구는 표준 출력이 비어 있으면 빈 결과로 보고 JSON으로 해석하지 못하면 `OutputParse` 오류를 낸다 [16].
실행 확인에서 출력이 없는 시험용 `vol`의 `vol_pslist` 응답은 빈 `processes`였고 JSON이 아닌 출력을 낸 경우는 -32603과 `could not parse volatility JSON output`이 왔다 [4].
`hayabusa_scan`은 결과 파일을 읽지 못하면 `OutputParse`를 내고 `ez_parse`와 `mac_triage`는 CSV 파일이 하나도 생기지 않으면 `NoCsvProduced`를 낸다 [17].
`plaso_parse`는 두 단계가 모두 성공했는데 결과 파일이 없으면 사건 0건으로 본다 [18].
`srum_parse`는 내보낸 폴더에서 네트워크 사용량 표를 찾지 못하면 `table_found`를 거짓으로 둔다 [17].
`verify_finding`의 클라이언트는 응답 줄이 JSON이 아니거나 표준 출력이 닫히면 `McpClientError`를, 응답에 `error`가 있으면 `McpRpcError`를 낸다 [19].
두 예외 모두 다시 실행한 결과를 `replay_error`로 만든다 [11].

**한계.** `plaso_parse`는 결과 파일에서 JSON 객체가 아닌 줄을 세지 않고 건너뛴다 [18].
Volatility 도구는 행마다 정해 둔 필드 이름 후보를 찾고 없으면 0이나 빈 값을 넣으므로 출력 형식이 달라져도 오류가 나지 않는다 [20].
Volatility 도구의 빈 결과는 표준 출력이 비었던 경우와 행이 0개였던 경우를 구별하지 않고 표준 오류는 `stderr_tail`로만 넘긴다 [16].

### T08.04 입력별 부분 완료 집계

**구현.** 이 방식은 `findevil-mcp`의 레코드 파서, `yara_scan`, `disk_extract_artifacts`, `hashset_lookup`에 적용된다 [21][22][23][24].
`evtx_query`, `mft_timeline`, `usnjrnl_query`, `sysmon_network_query`는 레코드마다 해석을 시도하고 실패한 레코드 수를 `parse_errors`에, 읽은 레코드 수를 `records_seen`에 센다 [21].
`evtx_query`는 레코드가 있었는데 모두 실패하면 `EvtxParseAllFailed` 오류를 낸다 [21].
`thumbcache_parse`는 해석하지 못한 곳의 설명을 `parse_errors` 목록에 담는다 [21].
`yara_scan`은 검사한 파일 수 `files_scanned`와 검사에 실패한 파일 수 `scan_errors`를 따로 센다 [22].
`disk_extract_artifacts`는 꺼낸 수, 크기 상한으로 건너뛴 수, 삭제된 항목의 복구 성공 수, 실패 수, 건너뛴 수를 응답에 싣는다 [23].
`hashset_lookup`은 해시 집합마다 읽기 결과를 `sets_loaded`에 두고 실패한 집합에는 `error`를 적는다 [24].
실행 확인에서 없는 파일을 해시 집합으로 주자 그 집합의 항목에 `error`가 붙었다 [4].

**한계.** `yara_scan`과 레코드 파서는 실패한 수만 세고 어느 파일이나 레코드가 실패했는지는 적지 않는다 [21][22].
`disk_extract_artifacts`는 삭제되지 않은 파일의 `icat` 실행이 실패하면 그 파일을 건너뛰고 어느 수에도 더하지 않는다 [25].
`registry_query`의 응답은 `parse_errors` 필드를 두지만 이 값을 늘리는 코드가 없어 늘 0이다 [26].

### T08.06 프로세스 안 분석 예외를 실패로 구별

**구현.** 이 방식은 `findevil-mcp`의 도구 43개와 `findevil-agent-mcp`의 도구 14개에 적용된다 [27][28].
`findevil-mcp`는 도구 처리기를 `catch_unwind`로 감싸 처리기에서 패닉이 나면 그 호출만 `tool '<도구>' panicked` 문구의 내부 오류로 돌려주고 다음 요청을 계속 받는다 [27].
코드 주석은 하이브나 이미지를 읽는 외부 크레이트가 처리하지 못하는 형식에서 멈추는 경우를 그 이유로 적는다 [27].
서버 안 파서가 낸 오류는 도구마다 정한 오류 종류로 돌려주고 레코드 하나의 해석 실패는 그 레코드만 빼고 센다 [21].
`findevil-agent-mcp`는 처리기가 낸 모든 예외를 받아 `{"error":{"kind":"handler","message":"<예외 종류>: <문구>"}}` 형태의 글로 돌려준다 [28].
입력 모델 검사에 실패하면 `kind`가 `validation`이고 등록되지 않은 도구 이름은 `unknown_tool`이다 [28].
실행 확인에서 `verdict.json`이 없는 폴더로 `accuracy_compare`를 부르자 `kind`가 `handler`이고 `FileNotFoundError`로 시작하는 글이 왔다 [13].

**한계.** `findevil-mcp`의 패닉 처리는 실행으로 확인하지 않았다 [27].
