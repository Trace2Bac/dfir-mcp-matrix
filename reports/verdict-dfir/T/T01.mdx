# T01 입력 검증

### T01.01 인자 구조·값 검사

**구현.** 이 검사는 `findevil-mcp`의 도구 43개와 `findevil-agent-mcp`의 도구 14개의 인자에 적용된다 [1][2].
`findevil-mcp`는 직접 구현한 JSON-RPC 처리기에서 `tools/call`의 `arguments`를 도구마다 정한 입력 구조체로 `serde_json::from_value`에 넘겨 해석한다 [1].
해석에 실패하면 도구를 실행하지 않고 JSON-RPC 오류 `-32602`와 `invalid args:`로 시작하는 문구를 돌려준다 [1].
입력 구조체 44개는 모두 `#[serde(deny_unknown_fields)]`를 달아 모르는 필드를 거부한다 [3].
자료형이 맞지 않는 값, 빠진 필수 필드, 열거형 밖의 값(`mode`, `artifact_kinds`, `scanners`, `disposition`)도 같은 오류가 된다 [1][4].
`vol_run`에 모르는 필드와 음수 `pid`를, `bulk_extract`에 목록 밖의 `scanners` 값을 주자 모두 `-32602`로 끝났다 [5].

도구 처리기는 이어서 다음 값을 검사하고 어긋나면 외부 도구를 실행하지 않고 `-32602`를 돌려준다 [1].
- `hayabusa_scan`은 `min_level`을 `informational`부터 `critical`까지 5개 값과 대조한다 [6].
- `usnjrnl_query`는 `reasons`의 이름을 USN 이유 목록과 대조하고 `mft_timeline`·`sysmon_network_query`는 시각 필터가 ISO 8601 형식인지 본다 [7].
- `hashset_lookup`은 해시가 1개 이상 10,000개 이하인지와 각 값이 32·40·64자리 16진수인지 본다 [8].
- `vel_collect`는 `artifact`가 256자 이하이고 점으로 나눈 영문·숫자·밑줄 이름인지 본다 [9].
- `thumbcache_parse`는 512MiB를 넘는 입력 파일과 썸네일 캐시 머리글이 없는 파일을, `browser_history`는 알려진 브라우저 기록 표가 없는 SQLite 파일을 거부한다 [10].
- `bulk_extract`는 `find_regexes` 항목에 줄바꿈이나 NUL 문자가 있으면 거부한다 [11].
`hayabusa_scan`의 `bogus` 등급, `hashset_lookup`의 3글자 해시, `vel_collect`의 `;`가 들어간 이름을 주자 모두 `-32602`로 끝났다 [5].

`findevil-agent-mcp`의 검사는 두 단계다 [2].
MCP Python SDK 1.27.0의 저수준 `Server`는 처리기를 부르기 전에 인자를 도구의 입력 schema와 `jsonschema`로 대조하고 어긋나면 `isError`가 참인 결과를 돌려준다 [12].
입력 schema는 서버가 도구마다 정한 pydantic 모델에서 만든다 [13].
그래서 모르는 필드(`extra="forbid"`), `Literal` 값 목록, `memory_recall`의 `limit` 범위 1~100, `memory_remember`의 `sha256` 형식은 이 단계에서 검사된다 [14].
이어 처리기 `call_tool`이 같은 pydantic 모델로 인자를 다시 검사한다 [2].
schema에 나타나지 않는 검사기는 이 단계에서만 적용되고 실패하면 `isError`가 거짓인 `{"error": {"kind": "validation", ...}}` 글을 돌려준다 [2][15].
`find_ai_signatures`의 범주 목록 대조와 입력 존재 검사, `judge_findings`의 발견사항마다 검증 결과가 하나씩 있는지 보는 검사가 여기에 해당한다 [15].
`memory_recall`의 `limit: 1000`은 `isError: true`로, `find_ai_signatures`의 모르는 범주와 `judge_findings`의 검증 결과 없는 발견사항은 `isError: false`인 검사 오류로 끝났다 [16].

**한계.** `evtx_query`의 `xpath`, `journalctl_query`의 `since`·`until`, `vel_collect`의 `args` 값은 자료형만 검사하고 값을 검사하지 않는다 [17].
`memory_remember`와 `memory_recall`의 `kind`는 설명에 다섯 값을 적지만 그 목록과 대조하지 않는다 [18][19].
`memory_remember`에 설명 목록에 없는 `kind`를 주자 받아들였다 [16].

### T01.02 입력 존재·읽기 가능 검사

**구현.** 이 방식은 증거 경로를 받는 `findevil-mcp`의 도구와 `findevil-agent-mcp`의 `accuracy_compare`에 적용된다 [20][21].
`findevil-mcp`의 도구는 분석이나 외부 도구 실행 전에 경로를 보고 없으면 `-32602`로 거부한다 [20][22].
- `vol_run`·`vol_pslist`·`vol_psscan`·`vol_psxview`·`vol_malfind`, `pcap_triage`, `journalctl_query`, `login_accounting`, `ausearch`, `nfdump_query`, `suricata_eve`, `indx_parse`, `srum_parse`, `pst_parse`, `bulk_extract`, `sysmon_network_query`, `disk_mount`, `prefetch_parse`, `mft_timeline`, `registry_query`, `usnjrnl_query`, `browser_history`, `thumbcache_parse`는 일반 파일인지까지 본다 [20].
- `hayabusa_scan`은 `evtx_dir`가 폴더인지 보고 `rule_set`은 있는지만 본다 [6].
- `yara_scan`, `plaso_parse`, `ez_parse`, `mac_triage`, `cloud_audit`, `oe_dbx_parse`, `email_parse`, `exif_parse`, `bits_parse`, `wmi_persist_parse`, `vss_list`, `vss_mount`, `zeek_summary`는 경로가 있는지만 본다 [20].
`evtx_query`는 경로가 없으면 `-32602`로 거부하고 일반 파일이 아니면 처리기 오류 `-32603`으로 거부한다 [23].
`case_open`은 링크를 따라가지 않는 `symlink_metadata`로 경로를 보고 일반 파일이 아니면 거부하므로 심볼릭 링크도 거부한다 [24].
`case_open`, `disk_extract_artifacts`와 `mode: auto`의 `disk_mount`는 `.E01` 같은 분할 EWF의 첫 조각을 받으면 같은 폴더의 조각을 모으고 중간 번호가 빠져 있으면 거부한다 [25][26].
`case_open`에 심볼릭 링크, 폴더, `.E02` 없이 `.E01`·`.E03`만 있는 분할 EWF를 주자 모두 `-32602`로 거부되었다 [27].
`plaso_parse`에 폴더를 주자 이 검사를 통과했다 [27].
`accuracy_compare`는 `case_dir`에 `verdict.json`이 없거나 기대 결과 파일을 찾지 못하면 채점하지 않고 처리기 오류를 돌려준다 [21].

다른 도구는 입력이 없어도 거부하지 않는다.
- `hashset_lookup`은 읽지 못한 해시 목록 파일을 `sets_loaded`의 `error`에 적고 나머지 목록으로 조회한다 [28].
- `find_ai_signatures`는 읽지 못한 경로를 `read_errors`에 적고 건너뛴다 [29].
- `audit_verify`는 없는 파일을 빈 기록으로 보고 `ok: true`를 돌려준다 [30].
- `memory_recall`은 `store_path`가 없으면 폴더와 SQLite 파일을 만든 뒤 빈 결과를 돌려준다 [31].
- `manifest_finalize`는 `audit_log_path`에 파일이 없으면 기록 0건으로 manifest를 만들어 쓴다 [32].
`audit_verify`에 없는 파일을 주자 `ok: true`, `record_count: 0`이 돌아왔고 `memory_recall`에 없는 `store_path`를 주자 `{"hits":[]}`가 돌아오며 그 경로에 파일이 생겼다 [16].
`manifest_finalize` 처리 함수에 없는 `audit_log_path`를 주자 `audit_log_record_count`와 `leaf_count`가 0인 manifest 파일이 생겼다 [33].

### T01.04 문자열 경로 검사

**구현.** 이 방식은 사건 폴더 `$FINDEVIL_HOME/cases/<case_id>`를 쓰는 `findevil-mcp` 도구 7개(`disk_mount`, `disk_extract_artifacts`, `disk_unmount`, `vss_mount`, `bulk_extract`, `srum_parse`, `pst_parse`)의 `case_id`에 적용된다 [34][35].
공통 함수 `is_valid_case_id`는 값이 비어 있지 않고 모든 글자가 영문·숫자·`-`·`_`일 때만 참이므로 `/`, `\`, `.`, NUL 문자가 들어간 값을 거부한다 [34].
도구는 이 검사를 `case_id`를 경로에 잇기 전에 한다 [35].
`disk_mount`와 `bulk_extract`에 `../x`를 주자 둘 다 거부되었다 [36].
거부 응답의 오류 코드는 도구마다 다르다 [37].
`bulk_extract`와 `vss_mount`는 `-32602`를, `disk_mount`·`disk_extract_artifacts`·`disk_unmount`·`srum_parse`·`pst_parse`는 처리기 오류 `-32603`을 돌려준다 [37].
`disk_mount`의 거부는 `-32603`, `bulk_extract`의 거부는 `-32602`였다 [36].

**한계.** `bulk_extract`, `srum_parse`, `pst_parse`는 외부 실행 파일을 찾지 못하면 `case_id`를 보기 전에 실행 파일이 없다는 빈 결과를 성공으로 돌려준다 [38].
`esedbexport`가 없는 환경에서 `srum_parse`에 `../x`를 주자 성공 응답이 돌아왔다 [36].

### T01.05 등록된 ID와 대조

**구현.** 이 방식은 사건 폴더를 쓰는 `findevil-mcp` 도구 7개의 `case_id`와 `disk_extract_artifacts`·`disk_unmount`의 `mount_id`에 적용된다 [35][39].
`case_id`는 `case_open`이 UUID4로 정하고 `$FINDEVIL_HOME/cases/<case_id>` 폴더를 만들어 등록한 값이다 [40].
사건 폴더를 쓰는 도구는 그 폴더가 없으면 `case not found`로 거부한다 [35].
`mount_id`는 `disk_mount`가 사건 폴더의 `session_resources.json`에 적은 자원 ID다 [41].
두 도구는 이 파일에서 같은 ID의 `disk_mount` 자원을 찾지 못하면 `mount resource not found`로 거부한다 [39].
`mode: auto`로 등록한 자원이면 `disk_extract_artifacts`는 찾은 자원에 적힌 `image_path`를 읽을 이미지로 쓰므로 이 도구에는 모델이 이미지 경로를 넘기지 않는다 [39].
없는 사건 `nocase`와 없는 `mount_id`를 주자 각각 `case not found`와 `mount resource not found`로 거부되었다 [36].

사건 폴더를 쓰지 않는 도구는 `case_id`를 대조하지 않는다 [42].
`vol_run`, `plaso_parse`, `ez_parse` 같은 도구의 입력 구조체는 `case_id`를 호출 기록과 맞추는 용도로만 받는다고 적고 처리기는 이 값을 읽지 않는다 [42].
`findevil-agent-mcp`의 `verify_finding`은 발견사항의 `tool_call_id`를 모델이 같은 호출에 넘긴 `tool_call_index`에서 찾고 서버가 남긴 호출 기록은 읽지 않는다 [43].
`findevil-agent-mcp`의 `manifest_finalize`는 `finding_approved` 기록의 `tool_call_id`를 앞선 `tool_call_output` 기록의 `tool_call_id`와 대조하지만 두 값은 모두 `audit_append` 호출자가 `payload`에 넣은 값이다 [44].

**한계.** 사건 폴더 대조는 `cases/<case_id>`가 폴더인지만 보고 `case_open`이 남긴 `case.json`은 보지 않는다 [35].

### T01.07 입력 부재 시 다른 입력으로 대체

**구현.** 이 방식은 `findevil-mcp`의 `disk_extract_artifacts`가 `mode: mock`으로 등록한 자원을 읽을 때 적용된다 [45].
`disk_mount`를 `mode: mock`으로 부르면 서버는 마운트하지 않고 호출 인자 `mount_point`의 폴더(주지 않으면 사건 폴더 아래 새 폴더)를 자원의 `fs_root`로 적는다 [26].
`disk_extract_artifacts`는 이 자원의 이미지를 Sleuth Kit으로 읽어 파일 목록을 얻지 못하면 `fs_root` 폴더의 파일을 아티팩트로 사건 폴더에 복사한다 [45].
`mode: mock`으로 등록한 자원으로 `disk_extract_artifacts`를 부르자 `mount_point` 폴더의 파일이 사건 폴더에 복사되었다 [46].

**한계.** 응답에는 파일을 이미지에서 꺼냈는지 `fs_root` 폴더에서 복사했는지 가르는 필드가 없다 [47].
시험에서도 응답 항목에는 그 파일이 이미지가 아닌 폴더에서 왔다는 표시가 없었다 [46].
이 경우에도 `session_resources.json`의 추출 항목에는 명령 `fls`·`icat`과 Sleuth Kit으로 이미지에서 꺼냈다는 문구가 적힌다 [48].

def _uncited_findings(audit_log: AuditLog) -> list[str]:
    """finding_approved records whose tool_call_id is absent from the chain
    so far. Chain order matters: a finding cannot cite a future tool call."""
    seen_tool_calls: set[str] = set()
    uncited: list[str] = []
    for record in audit_log.iter_records():

            tcid = str(record.payload.get("tool_call_id") or "")
            if tcid:

            if not cited or cited not in seen_tool_calls:
