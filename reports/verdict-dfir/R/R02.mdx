# R02 대량 결과 전달

### R02.01 문자·항목 상한

**구현.** 이 방식은 `findevil-mcp`의 결과 목록을 돌려주는 도구 대부분과 `findevil-agent-mcp`의 `find_ai_signatures`, `memory_recall`에 적용된다 [1][2][3][4][5].
`findevil-mcp`는 응답 전체의 크기를 제한하지 않고 도구마다 결과 항목 수를 제한한다 [6].

모델이 인자 `limit`으로 바꿀 수 있는 상한이 여러 도구에 있다 [1][7].
- 외부 도구나 파서의 레코드를 싣는 도구 대부분은 기본 10,000개에서 목록을 자른다 [1].
- `yara_scan`은 규칙 일치 1,000개에서 파일 검사를 멈춘다 [7].
- `thumbcache_parse`와 `disk_extract_artifacts`의 기본 상한은 500개다 [2].
- `pcap_triage`는 tshark에 `-c`로 기본 500,000개 패킷만 읽게 한다 [8].
- `zeek_summary`는 모든 기록 파일을 합쳐 기본 100,000줄에서 읽기를 멈춘다 [9].

`findevil-mcp`는 이 `limit` 값의 최댓값을 두지 않는다 [1].
`findevil-agent-mcp`는 pydantic 입력 검사로 `find_ai_signatures`의 `limit`을 1~10,000, `memory_recall`의 `limit`을 1~100으로 제한한다 [4][5].
`find_ai_signatures`의 기본 상한은 500개이고 `memory_recall`은 10개다 [3][5].

코드에 정해 둔 상한도 있다.
- `pcap_triage`는 대화 50개, DNS 질의 25개, HTTP 호스트 25개, HTTP 요청 300개까지 싣는다 [8].
- `zeek_summary`는 상위 값 목록을 10개씩, `notable_connections`를 50개까지 싣는다 [9].
- `email_parse`는 메시지 5,000개까지 해석하고 목록마다 200개까지 싣는다 [10].
- `pst_parse`는 메시지와 집계 목록을 500개까지 싣는다 [11].
- `srum_parse`는 행 5,000개와 상위 앱 20개까지 싣는다 [12].
- `oe_dbx_parse`는 목록마다 50개, `wmi_persist_parse`는 50개, `bits_parse`는 200개, `exif_parse`의 `other_fields`는 100개, `vss_list`는 저장소 256개까지 싣는다 [13].

결과 목록을 만드는 데 읽는 입력의 크기에도 상한이 있다.
`email_parse`는 256 MiB, `bits_parse`와 `oe_dbx_parse`는 64 MiB, `exif_parse`는 128 MiB, `wmi_persist_parse`는 512 MiB까지만 파일을 읽는다 [10][13].
`find_ai_signatures`는 파일마다 8,000,000바이트까지만 읽는다 [3].

**한계.** 다음 도구의 결과 목록에는 항목 수 상한이 없다.
`yara_scan`은 규칙 하나의 패턴 일치를 모두 싣는다 [7].
`vss_mount`의 경로 목록과 `findevil-agent-mcp`의 `detect_contradictions`, `judge_findings`, `correlate_findings` 결과 목록도 상한 없이 싣는다 [14][15].
`zeek_summary`의 100,000줄 상한과 `pst_parse`의 폴더 항목 500,000개 상한은 닿아도 응답에 표시되지 않는다 [9][11].
`email_parse`, `exif_parse`, `bits_parse`, `oe_dbx_parse`, `wmi_persist_parse`는 파일이 읽기 상한을 넘으면 앞부분만 해석하고 응답에 표시하지 않는다 [10][13][16].
`pcap_triage`의 패킷 상한과 `registry_query`의 재귀 깊이 상한 16도 닿아도 응답에 표시되지 않는다 [8][17].

### R02.02 전체·반환 건수 표시

**구현.** 이 방식은 `findevil-mcp`에서 상한 앞의 전체 수를 따로 싣는 도구에 적용된다 [18][19][20].
Volatility 도구는 `*_seen`에, `suricata_eve`는 `events_seen`에, `vol_run`·`nfdump_query`·`journalctl_query`·`login_accounting`·`ausearch`·`mac_triage`·`vel_collect`·`ez_parse`·`indx_parse`는 `rows_seen`에 상한 앞의 전체 행 수를 싣는다 [18][19].
`hayabusa_scan`의 `alerts_seen`, `cloud_audit`과 `plaso_parse`의 `events_seen`, `bulk_extract`의 `features_seen`, `thumbcache_parse`의 `entries_seen`도 상한 앞의 수다 [20].
`email_parse`와 `pst_parse`는 `message_count`에, `srum_parse`는 `row_count`에, `vss_list`는 `store_count`에 상한 앞의 전체 수를 싣는다 [10][11][12][21].
`bits_parse`는 `url_count`와 `local_path_count`에 상한 앞의 고유 값 수를 싣는다 [13].
돌려준 수는 응답 목록의 길이로 알 수 있고 잘렸다는 필드는 따로 없다 [18].
시험에서 객체 3줄과 목록 1줄을 둔 `eve.json`으로 `suricata_eve`에 `limit` 1을 주자 `events`에는 1개, `events_seen`에는 4가 실렸다 [22].

응답에 싣지 않은 나머지 결과를 이어서 읽는 인자나 도구는 없다 [6].
`bulk_extract`가 사건 폴더에 남긴 특성 파일과 `disk_extract_artifacts`가 꺼낸 파일의 경로는 응답에 실리지만 그 파일 내용을 그대로 돌려주는 MCP 도구는 없다 [6][23].

**한계.** 전체 수 필드 가운데 상한 앞의 전체 수가 아닌 것이 있다.
`evtx_query`, `mft_timeline`, `usnjrnl_query`, `sysmon_network_query`는 `limit`에 닿으면 레코드 읽기를 멈추므로 `records_seen`은 멈춘 곳까지 읽은 수다 [24].
`browser_history`는 SQL `LIMIT`을 건 뒤 돌려준 행 수를 `rows_seen`에 싣는다 [25].
`disk_extract_artifacts`의 `artifacts_seen`은 꺼낸 파일 수다 [26].
`suricata_eve`의 `events_seen`은 객체가 아닌 JSON 줄도 세고 그 줄은 `events`에 싣지 않는다 [19].
그래서 이 도구들에서는 응답만으로 결과가 잘렸는지 알 수 없다.

`limit` 0의 처리가 도구마다 다르다 [18][24].
Volatility 도구 4개, `evtx_query`, `mft_timeline`, `usnjrnl_query`, `sysmon_network_query`는 항목을 넣은 뒤 상한을 비교하므로 `limit` 0에도 1개를 싣는다 [18][24].
시험에서 `vol_pslist`에 `limit` 0을 주자 `processes`에 1개가 실렸다 [27].
`vol_run`과 `suricata_eve`는 `limit` 0이면 빈 목록과 전체 수를 싣는다 [22][27].

다음 집계 값은 전체 수를 싣지 않는다.
`pst_parse`는 보낸 사람과 제목의 고유 값 수를, `email_parse`는 받는 사람과 첨부 이름의 고유 값 수를 싣지 않는다 [10][11].
`wmi_persist_parse`는 상한 설명과 달리 명령 문자열과 스크립트 문자열의 전체 수를 싣지 않는다 [13].
`exif_parse`의 `field_count`는 `other_fields`에서 뺀 전용 필드까지 센 수라 `other_fields`의 전체 수와 다르다 [28].

### R02.06 값 단위 잘림

**구현.** 이 방식은 `findevil-mcp`의 `stderr_tail`, `registry_query`, `vol_malfind`, `yara_scan`, `pcap_triage`, `wmi_persist_parse`, `bits_parse`와 `findevil-agent-mcp`의 `find_ai_signatures`에 적용된다 [29][30][31][32][33][13][34].
외부 도구를 실행하는 도구 대부분은 표준 오류를 4,096바이트까지 `stderr_tail`에 싣는다 [29].
`pcap_triage`는 표준 오류를 응답에 싣지 않는다 [35].
`registry_query`는 이진 값을 4,096바이트까지 16진 문자열로 싣고 뒤에 `…[truncated, full N bytes]`를 붙인다 [30].
`vol_malfind`는 표본을 16진 128자까지, `yara_scan`은 일치한 바이트를 64바이트까지 16진으로 싣는다 [31][32].
`yara_scan`은 잘린 표본과 함께 일치 길이 `length`를 싣는다 [32].
`pcap_triage`는 HTTP 요청 URI를 뒤쪽 256바이트만 남기고 앞에 `…`를 붙인다 [33].
`wmi_persist_parse`와 `bits_parse`는 2,048자를 넘는 문자열을 그 길이에서 자른다 [13].
`find_ai_signatures`는 일치한 곳 앞뒤를 `preview_chars`(기본 80, 최대 400) 너비로 잘라 미리보기를 만든다 [34].
시험에서 `pcap_triage`에 300바이트가 넘는 ASCII URI를 주자 `…`와 뒤쪽 256자가 실렸다 [36].

**한계.** `vol_malfind`, `yara_scan`, `wmi_persist_parse`, `bits_parse`의 잘림에는 잘렸다는 표시가 없다 [31][32][13].
`pcap_triage`의 URI 자르기 함수는 자르는 곳이 문자 경계인지 확인하지 않는다 [33].
시험에서 2바이트 문자로 된 긴 URI를 주자 자르는 곳이 문자 안에 놓여 처리기가 중단되었고 호출 전체가 JSON-RPC 오류 `-32603`으로 끝났다 [36].
`pst_parse`는 머리글 파일을 256 KiB까지만 읽고 그 뒤를 알리지 않는다 [11].
`bulk_extract`, `disk_mount`, `disk_unmount`는 표준 오류의 뒤쪽 4,096바이트만 남기고 잘렸다는 표시를 붙이지 않는다 [37].

### R02.07 건수 없는 잘림 표시

**구현.** 이 방식은 `findevil-mcp`의 `stderr_tail`, `thumbcache_parse`와 `findevil-agent-mcp`의 `find_ai_signatures`에 적용된다 [29][38][3].
`truncate_to`를 쓰는 도구의 `stderr_tail`은 4,096바이트를 넘으면 앞부분만 남기고 `…[truncated]`를 붙이며 원래 길이는 적지 않는다 [29].
`thumbcache_parse`는 레코드 100,000개에서 검사를 멈추면 `parse_errors`에 상한에 닿았다는 문장을 싣는다 [38].
`find_ai_signatures`는 일치 수가 `limit`에 닿으면 `truncated`를 참으로 싣고 남은 파일을 검사하지 않는다 [3].
같은 도구는 8,000,000바이트를 넘는 파일을 앞부분만 검사하고 `read_errors`에 잘랐다는 문장을 싣는다 [3].
시험에서 `limit` 1로 일치가 둘 이상인 파일을 검사하자 `matches` 1개와 `truncated` 참이 실렸다 [39].

**한계.** `find_ai_signatures`의 `truncated`는 상한을 넘는 일치를 하나 더 찾았을 때만 참이 된다 [3].
그래서 일치 수가 `limit`과 같으면 남은 파일을 검사하지 않았어도 거짓으로 실린다 [3].
`thumbcache_parse`는 XP 형식에서 같은 상한에 닿으면 문장 없이 멈춘다 [38].

```rust
fn finalize_tool_output(name: &str, payload: &Value) -> Result<Value, ToolError> {
    let (payload, sanitized) = crate::sanitize::sanitize_value(payload);
    let payload_text = serde_json::to_string(&payload)
        .map_err(|e| ToolError::Internal(format!("serialize tool output: {e}")))?;
    let sha = sha256_hex(payload_text.as_bytes());

    let mut meta = json!({
        "tool": name,
        "output_sha256": sha,
    });
    if !sanitized.is_empty() {
        meta["sanitized"] = sanitized.to_json();
        // Mirror the `_meta.sanitized` counts into the best-effort, counts-only
        // injection-alert SIDECAR ledger. This runs AFTER hashing and never
        // touches `payload`, `sha`, or `meta`, so the sealed output and a
        // verify_finding replay are unaffected — the ledger is not the audit
        // chain. `sha` is recorded as the correlation key (the same sanitized
        // -output digest the audit chain stores), never the payload.
        injection_ledger::record_neutralization(name, &sha, &sanitized);
    }
    Ok(json!({
        "content": [
            {
                "type": "text",
                "text": payload_text,
            }
        ],
        "_meta": meta,
    }))
}
```

```rust
fn truncate_to(mut s: String, max: usize) -> String {
    if s.len() > max {
        // Walk to the nearest char boundary so a multi-byte UTF-8 codepoint
        // (Suricata warnings can carry non-ASCII rule metadata) doesn't panic
        // `String::truncate`. The walk is bounded at 4 bytes per codepoint.
        let mut boundary = max;
        while boundary > 0 && !s.is_char_boundary(boundary) {
            boundary -= 1;
        }
```
