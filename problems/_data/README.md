# problems/_data — 문제 매트릭스 데이터

`problems/`의 페이지는 이 폴더의 CSV에서 `tools/problems_build.py`가 만든다. 페이지 파일은 손으로 고치지 않고 커밋하지도 않는다. 데이터를 고친 뒤 다시 만든다(배포 때는 CI가 만든다).
같은 스크립트가 화면 데이터 `problems.json`도 만든다. 사이트의 `problems-data` 플러그인이 이 파일을 `web/static/data/`로 옮기고, 첫 화면 지도와 항목 화면이 이 파일을 읽는다.

```
python tools/problems_build.py
```

| 파일 | 내용 |
|---|---|
| `chapters.csv` | 장 1~4 |
| `cells.csv` | 항목 1.1~4.4와 이름 |
| `ch1/`, `ch3/` (`headings.csv`, `problems.csv`, `findings.csv`) | 1장과 3장. 문제 칸은 문제ID, 소제목ID, 문제, 전제, 결함, 피해, 경계, 목적, ASTM, CWE다. 근거의 판정은 관찰됨, 문제 없음, 판단 불가다 |
| `ch2/`, `ch4/` (`headings.csv`, `problems.csv`, `findings.csv`) | 2장과 4장. 문제 칸은 문제ID, 소제목ID, 문제, 설명(원인 → 결과 한 문장), CWE, ASTM, 목적이다. 근거의 판정은 1·3장과 같이 관찰됨, 문제 없음, 판단 불가이고 줄이 없으면 기능 없음이다. 관찰됨 줄은 첫 칸에 사례ID(`P2049-001`)가 있고, 문제 없음·판단 불가 줄은 사례ID를 비운다. 문제 없음·판단 불가 줄이 하나도 없는 장은 근거가 없는 서버를 "관찰되지 않음"으로 보인다. 판정 기준은 정적 분석 작업 폴더의 `2장_판정기준.md`·`4장_판정기준.md`에 있다 |
| `cwe.csv` | CWE 번호, 공식 영어 이름, 한국어 이름, MITRE 매핑 허용 여부(허용, 검토 후 허용, 권장 안 함, 금지. 권장 안 함·금지는 문제 화면에 표시된다) |
| `servers.csv` | 서버와 저장소 |
| `snapshots.csv` | 분석 회차: 서버, 커밋, 커밋일, 분석일, 범위, 메모 |
| `ch<N>/verifications.csv` | 그 장 문제의 실행 검증: 문제ID, 서버, 방법(PoC·시험·모델 실험), 수준, 커밋, 결과, 근거, 메모 |

## 문제로 다루는 범위

문제는 서버를 정상적으로 쓸 때 생기는 것만 다룬다. 정상 사용에는 다음이 들어간다.

- 모델이 도구 설명대로 도구를 부르는 흐름. 모델이 잘못된 형식이나 값의 인자를 넘기는 것도 들어간다.
- 임의의 증거 내용. 증거 안의 파일 이름, 글, 값은 공격자가 만든 것일 수 있다.
- 서버 문서가 안내하는 설치와 설정.
- 서버가 지키겠다고 한 파일(호출 기록, 기준값, 파생물 등)이 바뀌는 경우.

다음은 다루지 않는다.

- 기본 설정과 문서가 안내하는 설정에서는 생기지 않고, 사용자가 설정을 겹치게 둘 때만 생기는 경우. 예를 들어 기록 폴더를 증거 폴더 아래에 두는 설정이다.
- 서버 코드나 설치 환경을 고치는 경우.

범위는 MCP 서버 코드다. 같은 저장소의 클라이언트와 CLI는 보지 않는다. 다만 서버가 호출 기록을 클라이언트에 맡긴 사실과, 서버 저장소가 클라이언트에 주는 절차 파일과 hook은 본다.

## 문제 칸

| 칸 | 적는 것 | 필수 |
|---|---|---|
| 문제 | 정의를 찾아보기 위한 짧은 이름 | 예 |
| 전제 | 어떤 처리나 기능이 있을 때 이 문제가 걸리는가. "~할 때", "~하는 서버에서"로 끝낸다. 이 기능이 없는 서버는 기능 없음이다 | 예 |
| 결함 | 서버가 무엇을 하지 않거나 잘못하는가. 맞으면 관찰됨이다 | 예 |
| 피해 | 그래서 무엇이 잘못 전달되거나 훼손되는가 | 예 |
| 경계 | 비슷하지만 이 문제에 들어가지 않는 것. "~는 포함하지 않는다"로 쓴다 | 같은 소제목의 문제와 헷갈릴 때 |
| 목적 | 훼손되는 목적. `결과 정확성`, `증거 무결성`, `추적성`, `기밀성`, `시스템 안전` 가운데 하나 이상 | 예 |
| ASTM | 결과 오류 범주. `INCOMP`, `INAC_EX`, `INAC_ALT`, `INAC_AS`, `INAC_COR`, `MISINT` 가운데 하나 이상 | 목적에 `결과 정확성`이나 `증거 무결성`이 있을 때 |
| CWE | 원인에 맞는 CWE 번호 | 맞는 것이 있을 때 |

판정은 정의(전제, 결함, 피해, 경계)로 한다. 정의에는 서버 이름과 코드 이름을 쓰지 않고, 같은 문제의 여러 경우를 늘어놓지 않으며, 다른 문제 번호를 쓰지 않는다. 사례는 근거에 있다.
이름은 결과와 원인을 한 문장으로, 한 단계의 추상 수준으로 쓴다. 결함이 걸리는 기능은 이름에 남기고, 여러 경우를 늘어놓지 않는다. "조사자로서 나는 [이름]을 걱정한다"로 읽히고 이름에서 막는 방법이 하나 떠올라야 한다(SOLVE-IT 약점 이름 규칙을 참고했다). 괄호와 가운데점을 쓰지 않는다.
정의를 바꿔 범위가 넓어지거나 좁아지면, 바뀐 부분을 모든 서버에서 다시 판정한다.

목적은 피해 문장의 피해가 직접 가는 것만 적는다. 이어서 생길 수 있는 피해는 적지 않는다.

| 목적 | 뜻 |
|---|---|
| 결과 정확성 | 도구 결과가 증거 내용을 빠짐없이 바르게 나타낸다 |
| 증거 무결성 | 원본 증거, 증거 사본, 증거 기준값이 바뀌지 않고, 바뀌면 알아챈다. 서버가 만든 파생물과 호출 기록은 증거가 아니다 |
| 추적성 | 무엇을 어떤 입력과 설정으로 실행해 어떤 결과를 얻었는지 기록으로 되짚을 수 있다 |
| 기밀성 | 증거와 비밀 값이 허락되지 않은 곳으로 나가지 않는다 |
| 시스템 안전 | 분석 시스템과 대상 시스템이 서버 동작으로 손상되거나 바뀌지 않는다 |

ASTM은 피해 문장이 말하는 오류 종류만 고른다. ASTM 범주는 ASTM E3016-18의 오류 범주를 참고로 쓴다. SOLVE-IT가 약점을 나눌 때 쓰는 범주와 같다. 범주는 여러 개를 적을 수 있다.
CWE와 ASTM은 정의의 구절에 맞춰 붙인다. CWE는 결함 문장에, ASTM은 피해 문장에 댄다. 두 문장은 "~하거나"로 여러 경우를 이을 수 있다.

- 적은 분류마다 그 문장의 한 구절에 맞아야 한다. 일부 사례에만 맞고 문장의 어느 구절에도 맞지 않는 분류는 적지 않는다.
- 그 문장의 모든 구절이 적은 분류 가운데 하나 이상에 맞아야 한다. ASTM은 추적성, 기밀성, 시스템 안전에만 해당하는 구절에는 적지 않아도 된다.
- CWE는 구절마다 맞는 것 가운데 가장 낮은 수준(Variant, Base)을 고르고, 없을 때만 Class를 쓴다. MITRE의 Vulnerability Mapping Notes가 DISCOURAGED나 PROHIBITED로 둔 CWE와 Pillar는 쓰지 않는다.
- 맞는 CWE가 없는 구절이 있으면 CWE를 비운다.

CWE 이름은 MITRE 공식 영어 이름(CWE 5.0)으로 `cwe.csv`에 둔다.

## 문제 묶기와 배치

- 소제목은 서버가 수행하는 처리 단계다. 문제는 핵심 수정이 있는 처리의 소제목에 둔다.
- 한 문제는 원인 하나와 막는 방법 하나에 해당한다. 소제목을 부정형으로 바꿔 쓴 것처럼 넓게 잡지 않는다.
- 같은 소제목 안에서 다음 가운데 하나면 한 문제로 합친다.
  - 한 문제가 다른 문제의 특수한 경우다. 예를 들어 보호 대상이 빈 것은 보호 대상을 일부만 잡은 것의 극단이다.
  - 원인과 막는 방법이 같아, 새 사례를 어느 쪽에 넣을지 가를 수 없다.
- 피해가 같아도 원인이나 막는 방법이 다르면 따로 둔다.
- 소제목을 넘어 묶지 않는다. 다른 문제를 가리키는 문장도 쓰지 않는다.
- 서버 한 곳에서만 나온 사례도 문제로 둘 수 있다. 다른 서버의 판정은 코드로 다시 본다.

서버가 만들어 남기는 자료는 다음처럼 나눈다.

- 이 매트릭스에서 파생물은 서버나 서버가 부른 프로그램이 조사 중에 만들어 남기는 자료(파일, DB 항목, 작업 결과)를 모두 가리킨다. 증거에서 그대로 꺼낸 작업 사본과 서버가 고쳐 쓰는 상태 정보도 포함한다. 일반 포렌식 용어의 파생물(증거를 처리해 만든 결과물)보다 넓다.
- 호출 기록은 3.1에서 다룬다.
- 작업 사본이 원본과 같은지와 증거 기준값의 내용은 1.5에서 다룬다. 기준값은 그 값이 무엇의 해시인지로 정한다. 서버가 만든 파일에 담겨 있어도 증거의 해시이면 증거 기준값이다.
- 그 밖의 파생물의 위치, 이름, 저장 완료, 고쳐 쓰기, 재사용은 3.2에서 다룬다.

새 서버의 사례는 다음 차례로 넣는다.

1. 서버가 수행하는 처리 단계로 소제목을 정한다. 서버가 만들어 남기는 자료에 관한 사례는 위의 나눔을 따른다.
2. 그 소제목에서 전제와 결함이 맞는 문제에 넣는다.
3. 둘 이상 맞으면 경계 문장으로 가른다.
4. 맞는 문제가 없으면 새 문제를 만든다. 서버 한 곳이어도 된다. 새 문제를 만든 뒤 위 합치는 기준으로 기존 문제와 겹치는지 본다.

## 판정

판정은 서버의 한 커밋에서 문제 하나를 본 결과다. 직접 적는 판정은 둘뿐이다.

- `관찰됨`: 문제가 있다. 근거에 문제가 있는 코드 위치를 적는다.
- `문제 없음`: 기능이 있는데 그 문제가 보이지 않는다. 코드 확인(정적 분석)으로는 문제가 없음을 증명할 수 없으므로, 고친 PR이나 시험으로 확인한 줄이 아니면 `추정`을 `예`로 둔다.

폴더로 관리하는 1장과 3장은 코드만으로 가를 수 없는 칸을 `판단 불가`로 적고, 근거에 이유를 적는다. 화면에는 확인 안 함으로 보인다.

나머지는 계산한다.

| 화면의 판정·변화 | 계산 |
|---|---|
| 기능 없음 | 그 회차의 범위 안인데 근거 줄이 없다 |
| 확인 안 함 | 어느 회차의 범위에도 들지 않았다(새 서버, 새 문제, 분모를 정하지 않은 문제) |
| 확인 커밋 | 그 문제의 판정이 있는 가장 늦은 회차의 커밋 |

`추정`이 `예`인 `문제 없음`은 "그 문제를 찾아 코드를 보았으나 발견하지 못했다. 다만 문제가 있을 수 있다"는 판정이다. 근거에 확인한 코드 위치와 요지를 적는다.
근거 대장의 묶음 분모에서 옮긴 줄(출처 `대장`, 코드 위치 없음)도 `추정`이 `예`이지만, 이 줄은 그 서버에 기능이 있다고 판정했을 뿐 이 문제를 찾아 코드를 보지는 않았다. 그 문제로 코드를 보면 이 줄을 지우고 코드 위치를 적은 줄을 더한다.
고친 PR이나 시험으로 문제가 없음을 확인한 줄만 `추정`을 비운다.
`출처`가 `대장`인 줄은 `problems_export_from_ledger.py`가 다시 쓴다. 사람이 더한 줄은 출처를 비우고, 내보내기가 덮어쓰지 않는다.

코드로 판정할 때는 다음을 따른다.

- 외부 프로그램에 맡긴 처리: 서버가 원본 경로를 그대로 넘기고 외부 프로그램의 실패 신호를 응답에 전달하면 `문제 없음`으로 두고, 요지에 "결과는 외부 프로그램 동작에 따라 달라질 수 있다"를 적는다. 서버가 자기 몫의 확인을 하지 않으면 그 점으로 판정한다.
- 문서나 주석에 밝힌 설계라도 문제를 어기면 `관찰됨`으로 두고, 요지에 "문서에 밝혀 둔 설계"를 적는다.
- 사용자가 설정을 겹치게 둘 때만 생기면 `문제 없음`으로 두고 그 조건을 적는다.
- 문제가 전제하는 기능이 서버에 없으면 근거 줄을 적지 않는다(기능 없음). 기능이 없다는 것 자체를 문제로 만들지 않는다.

## 분석 회차

회차 하나는 서버의 한 커밋에서 어디까지 봤는지다. 서버마다 커밋일 차례로 놓는다.

- 범위는 `전체`, 항목(`1.3`), 문제(`P1025`)를 공백으로 나열하고, 앞에 `-`를 붙이면 뺀다. 예: `전체 -P1003`, `1.3 P4101`.
- 서버마다 첫 `전체` 회차의 커밋이 기준 커밋이다.
- 근거 줄은 그 회차의 범위 안 문제에만 적을 수 있다. 범위 밖이면 `problems_build.py`가 멈춘다.
- 서버의 새 버전에서 일부 문제만 다시 보면 그 문제만 범위로 하는 회차를 더하고, 본 결과를 근거로 적는다. 나머지 문제는 앞 회차의 판정이 그대로 남는다.
- 새 서버는 회차를 더하고 본 문제만 범위로 적는다. 아직 보지 않은 문제는 확인 안 함으로 보인다.
- 새 문제를 더하면, 그 문제를 범위에 넣은 회차가 없는 서버는 모두 확인 안 함이 된다.
- 폴더로 관리하는 장의 문제는 범위에서 빼지 않는다. 확인하지 못한 칸은 `판단 불가` 줄로 적는다.

## 검증 방법

모든 근거는 코드 확인(정적 분석)에서 시작한다. 실행으로 더 확인하면 그 장의 `ch<N>/verifications.csv`에 한 줄을 더한다. dfir-mcp-bench의 PoC 결과는 `python tools/import_bench_pocs.py <bench 경로> ch1,ch3`처럼 자기 장만 골라 가져온다(장을 적지 않으면 모든 장. 사례ID 칸이 채워지고, 근거는 bench 사이트의 그 사례 PoC 화면을 가리킨다. 다시 돌리면 그 줄만 새로 쓴다). 동적 분석은 정적 분석으로 찾은 사례를 걸러 내는 단계다. 재현되지 않거나 조건이 억지스러운 사례는 `findings.csv`에서 뺀다.

| 방법 | 하는 일 | 결과 |
|---|---|---|
| PoC | 그 서버에 맞춘 재현 스크립트를 돌려 문제를 보인다 | 재현됨 · 재현 안 됨 |
| 시험 | 정한 판정 기준으로 통과·실패를 가린다. 같은 시험을 여러 서버와 커밋에 돌릴 수 있다 | 통과 · 실패 |
| 모델 실험 | 결함이 있을 때와 고쳤을 때 AI의 답을 여러 번 비교한다 | 영향 있음 · 영향 없음 |

수준은 `함수`, `MCP`, `에이전트`로 적고, 모르면 비운다. PoC와 시험의 코드와 기록은 dfir-mcp-bench에 둔다.

## 식별자

- 소제목ID는 `<항목>.<순서>`다(`1.3.2`). 항목 안에서 소제목의 차례가 바뀌면 함께 바뀐다.
- 문제ID는 `P`와 네 자리 번호이고 첫 자리가 장 번호다(`P1025`, `P2049`, `P3089`, `P4192`). 2026-11-26에 1·3장을, 2026-11-27에 2·4장을 `P0025`→`P1025`, `P0049`→`P2049`처럼 뒤 세 자리를 그대로 두고 바꿨다. 소제목과 따로 매기므로 문제를 같은 장의 다른 소제목으로 옮겨도 바뀌지 않는다. 지운 번호는 다시 쓰지 않고, 새 문제는 그 장에서 마지막 번호 다음 번호를 받는다. 다른 장으로 옮기면 그 장의 번호를 새로 받는다.
- 사례ID(2·4장)는 `<문제ID>-<세 자리>`다(`P4192-010`). dfir-mcp-bench의 PoC(`pocs/<문제ID>/<서버>/<사례ID>/`)가 이 번호로 사례를 가리킨다. 사례를 다른 문제로 옮겨도 사례ID는 그대로 둔다.

1장과 3장은 `ch1/`, `ch3/` 폴더에서 직접 관리한다. 2026-11-26에 근거 대장의 사례를 21개 서버 코드로 다시 판정하고 정의를 새로 써서 옮겼고, 그 뒤로는 폴더 파일을 고친다. 빌드는 폴더가 있는 장을 폴더에서만 읽는다.
네 장 모두 `ch1/`~`ch4/` 폴더에서 직접 관리한다(2026-11-27부터). `tools/problems_export_from_ledger.py`(저장소 밖 근거 대장에서 내보내기)는 공용 `problems.csv`·`headings.csv`·`findings.csv`를 쓰는데, 빌드는 이 파일들을 읽지 않는다. 내보내기를 계속 쓸지는 아직 정하지 않았다.
