# problems/_data — 문제 매트릭스 데이터

`problems/`의 페이지는 이 폴더의 CSV에서 `tools/problems_build.py`가 만든다. 페이지 파일은 손으로 고치지 않는다. 데이터를 고친 뒤 다시 만든다.
같은 스크립트가 화면 데이터 `problems.json`도 만든다. 사이트의 `problems-data` 플러그인이 이 파일을 `web/static/data/`로 옮기고, 첫 화면의 격자와 원고 화면의 패널이 이 파일을 읽는다.

```
python tools/problems_build.py
```

| 파일 | 내용 |
|---|---|
| `chapters.csv` | 축: 가이드라인의 장 1~4 |
| `cells.csv` | 셀: 원고 1.1~4.4와 이름 |
| `headings.csv` | 소제목: 원고의 구현방안 소제목과 소제목ID(`1.3.2` = 원고 1.3의 두 번째 소제목, 가이드라인 초안 2026-11-24 기준) |
| `problems.csv` | 문제: 문제ID(`P0001`), 속한 소제목ID, 문제, 현상과 피해, 해당 기능이 있는 서버, 문제가 관찰된 서버, 근거 대장의 묶음(대장ID) |
| `observations.csv` | 문제가 관찰된 서버의 사례: 문제ID, 요지, 코드 위치, 저장소, 기준 커밋 |
| `snapshots.csv` | 분석 회차: 서버, 분석한 커밋, 분석일, 범위(`전체`·`일부`), 메모. 서버마다 첫 `전체` 스냅샷이 기준 커밋이다 |
| `checks.csv` | 기준 커밋 뒤의 스냅샷에서 다시 확인한 결과: 문제ID, 서버, 스냅샷 커밋, 결과(남아 있음·고쳐짐·기능 바뀜), 근거(PR 등) |
| `experiments.csv` | 수정 전후 검증 실험(Trace2Bac/dfir-mcp-bench)과 문제ID의 대응 |
| `servers.csv` | 서버 21개의 저장소 |

## 새 버전 확인

일반적인 코드 스캐닝 도구처럼, 발견한 문제는 하나로 두고 분석 회차(스냅샷)마다 상태를 쌓는다.

- `observations.csv`의 사례는 기준 커밋(서버의 첫 `전체` 스냅샷)에서 찾은 것이고, 뒤에 고치지 않는다. 사례 화면은 늘 그 커밋의 코드를 보여 준다.
- 서버의 새 버전을 보면 `snapshots.csv`에 한 줄을 더하고, 본 결과를 `checks.csv`에 더한다. 결과는 `남아 있음`, `고쳐짐`, `기능 바뀜`(해당 기능이 없어지거나 구조가 바뀌어 비교할 수 없음) 가운데 하나다.
- `전체` 스냅샷은 그 서버에서 관찰된 모든 문제의 결과가 있어야 한다. 빠지면 `problems_build.py`가 멈춘다. 결과가 없는 것과 확인하지 않은 것을 가르기 위해서다.
- `일부` 스냅샷(예: 머지된 PR이 다룬 문제만 확인)은 적힌 문제만 갱신하고, 나머지는 앞 상태를 둔다.
- 새 버전에서 처음 생긴 문제는 `observations.csv`에 새 사례로 더한다.
- 같은 문제와 서버는 가장 늦은 스냅샷의 결과가 현재 상태다.

## 식별자

- 소제목ID는 `<원고>.<순서>`다(`1.3.2`). 원고 안에서 소제목의 차례가 바뀌면 함께 바뀐다.
- 문제ID는 `P`와 네 자리 번호다(`P0001`). 소제목과 따로 매기므로 문제를 다른 소제목으로 옮겨도 바뀌지 않는다. 지운 번호는 다시 쓰지 않고, 새 문제는 마지막 번호 다음 번호를 받는다.
- 사례ID는 근거 대장의 식별자를 그대로 쓴다.

이 CSV는 저장소 밖의 근거 대장에서 `tools/problems_export_from_ledger.py`로 내보낸다. 근거 대장은 사례마다 근거의 강도(원자료로 재현, 코드 확인 등)와 시험 기록을 관리하며, 이 매트릭스는 그 가운데 문제와 서버만 싣는다. "해당 기능이 있는 서버"는 매트릭스 셀 상세에서 정한 묶음 분모이고, 21개 서버를 코드로 다시 판정한 묶음(지금은 1.3 B2)만 그 결과로 바꿨다.
