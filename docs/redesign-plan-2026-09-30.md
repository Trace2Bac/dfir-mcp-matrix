# 보고서·코드 근거·매트릭스 통합 개편안

작성일: 2026-09-30. 이 문서는 보고서 작성·근거 배치·매트릭스 셀 구성·기능 발견 절차의 **설명과 배경**이다. 셀 구조와 정의의 원본은 [`matrix/`](../matrix/)(축 `axes.yaml`, 셀마다 `cells/<ID>.yaml`), 새 결정은 [`docs/decisions/`](decisions/)에 쓴다. 이 문서의 6.2절·10절은 `matrix/`를, 12절은 첫 버전 전 결정의 git 이력을 가리킨다.

검토 자료: 현행 작업지침·문장 기준·규격, mcp_dfir·sift-kernel·regipy 보고서의 해당 절, mcp_dfir·sift-kernel의 기준 커밋 코드, 앞선 49셀·42건 구현 관찰 대응 자료.

읽는 순서: 2~5절은 보고서와 코드 발췌, 6~7절은 매트릭스 원칙과 기능 발견, 10절은 전체 셀·기존 항목 대응이다.

## 1. 개편 범위와 확인한 사례

**보고서의 설명 순서, 코드 근거의 배치, 매트릭스의 관찰 목적을 함께 바꾼다.** 코드 링크만 부록으로 옮기면 구현 설명이 축약된 문제는 남는다. 셀 이름만 바꾸면 서로 다른 목적의 기록 필드가 같은 셀에 계속 섞인다.

현행 작업지침 4.7절은 모든 주장 뒤에 코드 줄 링크를 붙이고 셀 절의 첫 문장을 판정 파일 설명과 같은 뜻으로 쓰도록 정한다. 문장 기준도 코드 문장에 직접 링크를 붙이도록 한다(작업지침, 문장 기준).

| 현재 사례 | 설명에서 개선할 내용 |
|---|---|
| mcp_dfir F3 | 첫 문장은 기록 필드·출력 파일을 압축해 열거한다. 이후에는 ID·인자·해시의 부족을 길게 설명한다. 명령 생성부터 요약 JSON·출력 파일 저장까지의 실제 순서를 먼저 설명할 필요가 있다 |
| sift-kernel B5 | 첫 문단에 조건 명세·검사·능력 생성과 예외가 함께 들어간다. 상태가 만들어지고 다음 호출을 제어하는 과정을 풀어 쓴 뒤 적용되지 않는 경로를 설명하면 읽기 쉽다 |
| regipy C4 | 읽기 모드로 열고 메모리 사본에서 파싱한다는 설명이 먼저 나온다. 구현부터 설명하는 방식은 재사용할 수 있다. 후속 상세 코드 근거는 본문에서 분리할 수 있다 |

확인한 세 보고서에는 소스 코드 블록이 없다. 현재 가독성 개선의 대상은 본문에 반복되는 파일 경로·줄 번호 링크와 판정 중심 설명 순서다. 원래 보고서 전체가 설명을 생략했다거나 코드 인용이 불필요하다고 일반화하지 않는다.

## 2. 새 보고서 구조

보고서는 프로젝트의 기능 흐름을 먼저 설명하고 관찰 셀별로 필요한 구현을 풀어 쓴다. 셀 절의 마지막에는 **그 절의 설명을 뒷받침하는 짧은 코드 발췌와 고정 커밋 링크**를 둔다. 본문 문장은 번호 표지로 그 근거를 가리킨다.

| 위치 | 내용 |
|---|---|
| 프로젝트·검토 범위 | 역할, 기준 커밋, 진입점·모드, 연동 경계, 읽은 범위와 실행 확인 범위 |
| 기능 목록·처리 흐름 | 셀에 맞추기 전의 기능 목록과 입력에서 출력·저장까지의 주요 경로 |
| 셀별 구현 설명 | 연결한 상세 항목마다 구현(입력·처리·출력·상태)과 †인 항목의 예외(4절, 12절 25번) |
| 셀별 근거 | 구현·예외 설명이 끝난 직후, 본문 번호 표지 순서로 중요한 분기·호출·저장 코드를 짧게 제시하고 파일·줄 링크를 붙임 |
| 매트릭스 대응 | 해당 셀·상세 항목과 보고서 절을 연결한 목록 |
| 새 구현·셀 후보 | 대응하지 않거나 일부만 대응한 기능과 새 상세·셀 제안 |
| 별도 확인 자료 | 문서 선언 대조, 재현 환경·입력·출력, 미확인 사항 |

본문은 A~H 관찰 영역으로 묶되 실제 기능에 필요한 절만 길게 쓴다. 셀 하나를 한 줄 판정으로 끝내지 않는다. 기능 하나가 여러 셀에 걸리면 주된 기능 절에서 흐름을 설명하고 다른 셀 절에서도 **그 셀의 관찰 목적에 해당하는 작동·예외·코드 근거**를 설명한다. 독자가 다른 절을 읽지 않아도 해당 셀의 구현을 이해할 수 있어야 한다.

미구현·비적용 항목은 근거와 사유를 짧게 남긴다. 이전 질문에 없던 기능은 확인하지 않고 미구현으로 처리하지 않는다.

문서의 보안 선언과 실제 코드의 대조는 별도 표로 보존한다. 중요한 불일치가 기능의 범위를 바꾸면 해당 셀의 미비점 설명에도 적는다. 선언 대조 자체를 공통 구현방식 셀로 유지할 필요는 없다.

## 3. 코드 근거를 남기는 방식과 위치

### 3.1. 본문에 번호 표지를 달고 셀 절의 마지막에 근거를 둔다

1. 본문에서 **구현 흐름 → DFIR 의미 → 적용 범위·미비점**을 설명한다.
2. 코드·문서·실행 결과를 말하는 본문 문장에는 `[1]` 같은 **번호 표지**를 붙인다. 한 근거가 여러 문장을 뒷받침하면 같은 번호를 다시 쓴다.
3. 설명이 끝난 바로 아래에 **근거** 소절을 두고 표지 번호 순서로 근거를 적는다.
4. 근거 한 항목은 확인할 동작 한 줄, 코드 발췌, 기준 커밋이 고정된 **파일·줄 링크** 순서로 쓴다. 발췌가 필요 없는 근거는 링크만 둔다.
5. 다른 호출 경로가 예외라면 그 예외를 보여 주는 분기·호출도 같은 소절에 번호를 붙여 둔다.

긴 파일 경로와 줄 번호가 본문 문장을 끊지 않고 독자는 표지 번호로 그 문장의 근거를 바로 찾는다. 절 끝에 발췌만 모으면 어느 문장을 어느 발췌가 뒷받침하는지 독자가 짝을 맞춰야 하므로 표지를 생략하지 않는다(2026-09-30 결정). 중요한 사실과 결론은 발췌 전에 글로 설명한다. 코드 블록만으로 구현 설명을 대신하지 않는다.

셀별 배치 예시는 5절의 실제 코드 기반 재작성에 적용했다. 발췌는 해당 기준 커밋의 원문과 일치해야 하며 생략·수정한 코드를 원문 발췌인 것처럼 싣지 않는다.

### 3.2. 발췌할 코드의 선택

**모든 주장에 근거를 남기는 원칙은 유지한다.** 한 문장을 쓸 때마다 함수 전체를 다시 붙일 필요는 없다. 한 발췌가 여러 문장을 뒷받침한다면 같은 설명 절 끝에서 한 번 보여 주고 그 기능·범위를 밝힌다.

우선 발췌할 부분은 설정이 실제 호출에 전달되는 지점, 입력 변환, 허용·거부 분기, 결과·기록 저장, 예외 경로다. 긴 함수·라이브러리 전체는 고정 커밋 줄 링크로 연결하고 판단에 필요한 부분만 발췌한다.

**부재 주장은 한두 줄로 입증하기 어려울 수 있다.** “기록하지 않는다”, “다른 경로가 없다” 같은 주장은 확인한 등록 지점·호출 경로·저장 구조를 설명하고 각각의 관련 코드 링크를 붙인다. 짧은 발췌가 전체 경로 조사까지 증명한다고 적지 않는다. 부재 주장과 수치에도 표지를 붙이고 근거 소절에 확인한 경로의 링크를 둔다.

기준 커밋·자료 성격도 구별한다. 저장소 설명·설정 문서, 호출 가능한 구현, 실제 실행 확인은 같은 수준의 근거가 아니다. 실행 확인 사실에는 환경·입력·출력 기록의 위치를 함께 남긴다.

### 3.3. 원고·게시·검사

현행 `tools/md2storage.py`는 fenced code block을 Confluence 코드 매크로로 변환한다. 셀 아래의 코드 블록은 이 경로를 사용할 수 있다. 다만 새 셀 제목·배치 규칙·근거 링크 검사는 현행 `check_report.py` 등과 함께 개정해야 한다.

보고서의 코드를 붙일 때는 기준 커밋의 실제 줄과 발췌가 일치하는지, 줄 링크가 같은 범위를 가리키는지 확인한다. 같은 기능을 여러 셀에서 다른 관찰 목적으로 설명하면 해당 셀의 근거 범위를 각각 확인한다. 새 자료 구조가 확정되기 전에는 현행 원고·페이지에 이 형식을 기계적으로 섞지 않는다.

## 4. 기능별 설명을 쓰는 순서

셀 절은 연결한 상세 항목마다 소제목을 두고 그 아래에 **구현**과 **예외**를 나눠 쓴다. 근거는 셀 절 끝에 모은다(12절 25번).

1. **구현.** 그 방식이 어떤 입력·상태·배포 모드에서 작동하는지, 누가 어떤 변환·검사·실행·저장을 어떤 순서로 하는지, 응답·파생물·기록·상태가 어디에 남는지 쓴다.
2. **예외.** †를 붙인 항목에만 쓰고 †를 붙였으면 반드시 쓴다. 그 방식이 걸리지 않는 도구·인자·모드·설정과 확인하지 못한 범위를 쓴다.
3. **근거.** 셀 절 끝에 본문 표지 번호 순서로 구현과 예외를 확인할 코드 조각·고정 커밋 링크를 둔다.

원고는 문장 하나를 한 줄에 쓰고 단락 사이에만 빈 줄을 둔다. 화면은 그 줄바꿈을 그대로 보여 준다(12절 32번).

`미구현`·`비적용` 항목은 **판단** 하나에 왜 그 항목인지와 근거 표지를 쓴다. 방식의 DFIR 의미는 따로 쓰지 않는다(12절 26번).

고정 문단 수·최대 글자 수를 새로 강제하지 않는다. 해당 기능에 필요한 사항을 설명한다. “일부만”, “없음”, 상세 항목 이름 또는 함수 목록 한 줄만으로 구현 설명을 대신하지 않는다.

잘 작동하는 범위와 구현상 제약을 함께 적는다. 예외가 결론을 바꾸면 눈에 띄게 남기되 설명을 예외 목록으로 시작해서 정상 동작 과정을 생략하지 않는다. 상세 재현·수정 제안은 확인 자료·기여 후보로 연결한다.

**기술과 의미를 구별한다.** JSON 포장은 데이터 구조화이며 그것만으로 프롬프트 인젝션 차단을 보장하지 않는다. 해시 체인은 기록 연결 장치이며 삭제·재생성까지 탐지하는지는 추가로 확인한다. 읽기 전용 볼륨은 해당 접근 경로의 변경을 막으며 다른 호스트 경로까지 보호한다고 적지 않는다.

## 5. 코드 기반 재작성 예시

다음 예시는 12절 25번 전의 모양이고 상세 번호도 27·29번 전의 번호라 셀 전체에 DFIR 효과와 범위·예외를 한 번씩 쓴다. 지금 모양은 이 저장소의 시범 원고(`reports/`)에 있다. 예시는 이번에 읽은 기준 코드로 설명 순서를 구성했다. 새 판정 값이나 전체 경로의 검증 결과를 확정한 보고서가 아니다. 이번 작업에서 실제 도구 실행은 수행하지 않았다. 본문 문장의 `[n]` 표지는 절 끝 **근거** 소절의 같은 번호를 가리킨다(3.1절).

### 5.1. mcp_dfir: 컨테이너 증거 볼륨의 읽기 전용 연결

**연결할 상세 항목:** E03.01.

**구현 흐름.** 서버는 사건 폴더의 `evidence`를 컨테이너의 `/evidence`에 읽기 전용으로, `artifacts`를 `/artifacts`에 읽기·쓰기로 연결하도록 설정한다 [1]. 새 포렌식 컨테이너를 만들 때 이 설정을 Docker 실행에 넘기고 네트워크는 `none`으로 둔다 [2]. 컨테이너 안에서 이 마운트로 증거를 읽는 도구에는 마운트의 쓰기 제한이 적용된다.

분석 도구가 새 파일을 만들 위치와 원본을 읽는 위치를 나눈 구성이다. 이 구분으로 읽기 전용 증거를 분석하면서 파생물을 만들 수 있다.

**DFIR 효과.** 컨테이너의 증거 마운트에서 원본을 바꾸는 접근을 막는다. 도구 함수 이름이 "읽기"인지를 믿는 대신 컨테이너의 파일 접근 경로에 제약을 둔다. 적용 대상은 그 읽기 전용 마운트로 닿는 접근이다.

**범위·예외.** 같은 이름의 컨테이너가 이미 있으면 서버는 실행 중이든 멈춰 있든 생성 설정을 다시 적용하거나 마운트를 대조하지 않고 재사용한다 [3]. 호스트에서 도는 노트 도구는 이 보호 밖에 있다. `add_analyst_note`의 `title`을 검사하지 않고 `analysis/analyst_notes` 아래 파일 이름으로 쓰므로 `../../evidence/x`를 주면 호스트의 `evidence/x.md`가 생긴다 [4]. 이 예외가 E03 결론을 바꾸므로 본문에 둔다. 같은 결론을 되풀이하는 심볼 도구 경로 같은 나머지 예외는 부록에 둔다.

**근거.**

[1] 증거·분석 폴더는 읽기 전용, 심볼·파생물(`artifacts`) 폴더는 읽기·쓰기로 설정한다.

### 5.2. mcp_dfir: 실제 실행 명령을 문자열로 기록

**연결할 상세 항목:** L02.01. 실행 경과는 L02, 도구 출력 보관은 D01에서 연결한다.

**입력과 처리.** Docker 실행 관리기는 포렌식 명령을 인수 배열로 받아 컨테이너에 실행을 요청하고 실행 중에는 stdout만 모은다 [1]. 수집이 끝나면 명령 문자열·수집한 출력·종료 코드로 `CommandRecord`를 만들어 기록 관리기에 넘긴다. 기록의 명령 문자열은 실행에 쓴 배열을 공백으로 이어 만든다 [1].

**저장과 반환.** 기록 관리기는 현재 요약 목록 길이로 번호를 정하고 `number`·`command`·`date_run`·`exit_code`를 요약 JSON에 저장한다. 출력 본문은 같은 번호의 `.txt` 파일에 쓴다. 관리기는 요약 객체를 호출한 도구에 돌려준다 [2].

이 기록은 호스트의 분석 폴더에 저장된다. 컨테이너의 `/analysis`가 읽기 전용인 설정과 호스트 서버의 파일 저장은 다른 접근 경로다.

**DFIR 효과.** 어떤 명령 문자열을 실행했는지와 그 실행에서 모은 출력을 번호로 찾아볼 자료가 남는다. 요청 기록의 표현을 비교할 때는 "명령 문자열 기록", 자료 보관을 비교할 때는 "도구 출력 파일 저장"에 각각 연결한다.

**표현상 제약.** 인수를 공백으로 합치므로 공백이 든 인수 하나와 여러 인수를 기록에서 가를 수 없다 [1]. `date_run`은 실행 뒤 `CommandRecord`를 만드는 시각이고 요약은 그 값을 복사한다 [3]. 시작 시각은 따로 남기지 않는다. 이 내용은 L02의 인수 표현 범위와 L02의 실행 경과에서 설명한다.

출력 해시의 기록·파생물과 호출의 연결은 D02의 질문으로 대조한다. 이 L02 설명에 관련 없는 누락 필드를 모두 넣어 기록 구조의 동작 설명을 가리지 않는다. Docker 실행 경로의 예이므로 전체 MCP 도구가 같은 방식으로 기록된다고 일반화하지 않는다.

### 5.3. sift-kernel: 선행 능력 상태로 호출 제어

**연결할 상세 항목:** T03.01.

**입력과 상태.** 도구 명세에는 실행에 필요한 `requires`와 성공 뒤 만들 `produces`가 있다. 예를 들어 `list_directory`는 증거 마운트와 무결성 확인 상태를 요구한다 [1]. 그래프는 현재 보유 상태를 서버 메모리의 집합으로 관리한다.

**DFIR 효과.** 이 경로는 앞선 준비·검증 상태를 다음 분석 호출의 허용 조건으로 잇는다. 다음 작업 추천은 P02에서, 상태 조회(`get_investigation_state`)는 P03에서 함께 관찰할 기능이다 [5].

**범위·예외.** `verify_integrity`를 뺀 커널 도구는 공통 검사 앞에서 처리되고 돌아간다. 그래서 `generate_report`는 명세에 선행 능력이 있어도 이 검사에 닿지 않는다. 자체 검사는 발견사항이 0개이고 실행 가능한 기준 도구가 남았을 때만 막는다. 마운트 전에는 기준 도구가 모두 능력이 모자라 실행 가능한 도구로 세지 않으므로 막지 못한다 [6]. 능력을 만드는 조건인 `success`도 조건을 채웠다는 뜻이 아니다. `ewfverify`가 없으면 해시를 계산하지 않는 `img_stat`이 대신 돌아 `integrity_verified`가 생기고 `list_registry_hives`는 하이브를 찾지 못해도 성공으로 끝나 능력을 만든다 [7].

## 6. 새 상세 항목 구조에 맞춘 셀 재편성

이 문서 10절에 축·셀·상세 항목 후보와 현행 셀 대응을 모두 적었다.

축의 차례·이름·다루는 내용은 [`matrix/axes.yaml`](../matrix/axes.yaml)에 있다. 셀 수는 `matrix/cells/`의 파일 수다.

셀 구성의 원본은 `matrix/cells/`다. 12절 36번에서 옛 A~D축의 셀 30개를 목적이 같은 것끼리 합쳐 17개로 줄였고(공통 16개, 조건부 1개) 37번에서 옛 E~H축의 셀 32개를 18개로 줄였다(조건부 없음). 39번에서 축 글자를 축 이름의 영어 첫 글자로 바꾸고 셀 번호도 그에 맞췄다. 41번에서 결이 다른 질문이 섞인 셀 6개를 나눴다. 결이 다른 질문은 합치지 않는다. 셀은 질문 하나이고 구현·미구현은 셀의 질문에 대해 판단한다. 세부 방식의 차이는 상세 항목으로 남긴다. 수량을 맞추기 위해 셀을 추가·삭제하지 않는다.

새 표는 `관찰 셀 → 상세 항목 정의 → 해당 프로젝트 → 보고서 구현 절 → 근거`로 연결한다. 판정형·택일형·목록형 구분과 독립된 구현 위치 필드는 사용하지 않는다. 적용 모드·담당 구성 요소·예외는 실제 동작 설명에 남긴다.

**구현이 없는 프로젝트도 항목으로 둔다(2026-09-30 결정).** 셀의 어느 구현 방식에도 들지 않는 프로젝트는 그 셀의 `미구현` 항목에 넣는다. 전제가 되는 일을 하지 않는 프로젝트는 `비적용`, 아직 조사하지 않은 프로젝트는 `미확인` 항목에 넣는다. 그래서 모든 프로젝트가 셀마다 한 항목 이상에 나타난다. 상태·적용 주체·요약 같은 별도 필드는 두지 않는다. 같은 일을 다른 주체(서버 코드·실행 환경·클라이언트·백엔드)가 해서 방식이 달라지면 상세를 나눈다.

**표본이 없는 후보 항목은 정의만 둔다(2026-09-30 결정).** 지금 표본 가운데 해당하는 곳이 없는 항목(예: E02 분할·논리 범위 해시)은 상세 항목 정의에만 남긴다. 매트릭스에는 해당 표본이 생길 때 보인다.

**정보의 성질을 유지한다.** 구현방식뿐 아니라 기록 내용·전달 범위·상태 표현도 상세 항목이 될 수 있다. 모든 셀에 같은 종류의 방법 이름을 강제로 넣지 않는다. 한 프로젝트가 같은 셀의 여러 상세에 연결되는 것을 허용한다.

앞선 개편안의 조사 방법·절차·수행 범위·입력 준비·해석 주의·근거 심사 관찰을 새 상세 항목 형식으로 구성했다. 새 발견을 현재 셀에 강제로 넣지 않는 기능 발견 원칙도 그대로 적용한다.

### 6.2. 상세 항목 정의

상세 항목 정의의 원본은 `matrix/cells/<ID>.yaml`이다(12절 31번의 "유일한 원본"을 이 파일로 옮겼다). 정의를 쓰지 않은 셀은 상세 이름만 있다.

**†의 뜻(12절 28번).** 보고서의 구현에 적은 적용 범위 **안에서** 그 방식이 걸리지 않는 경우에만 †를 붙인다. 우회 경로, 설정·인자로 끄는 경우, 오류 때 통과시키는 경우, 설명과 다르게 동작하는 경우, 확인하지 못한 경로가 여기에 든다. 그 방식이 서버의 어느 도구·경로에 있는지는 구현 첫머리에 적고 †로 표시하지 않는다. 셀마다 적용 범위를 표 위에 적는다.

표시와 안내는 모델이 읽을 정보를 더할 뿐이고 차단이 아니다. 표본 예는 [셀 검토 자료](cell-review-2026-09-30.md)의 E08 메모(지금의 R07)에 있다(TheHiveMCP·Camel은 판정 전 코드 확인).

고정 커밋 코드 대조(2026-09-30): Camel의 Execute는 스크립트가 log 등으로 쌓은 문자열을 텍스트 content 블록으로 돌리고 별도 감사 식별 블록을 붙인다. 서버가 증거 문자열을 JSON 필드로 자동 포장하거나 신뢰 불가라고 표시하는 경로는 확인되지 않는다. 호출 스크립트가 직접 JSON 문자열을 출력하는 경우는 서버의 R07.01 구현으로 세지 않는다([MCPServer.cs:230-259](https://github.com/allisterb/Camel/blob/63f4cb2e26a2469a35f847bee607516cf6184e91/src/Camel.Server/MCPServer.cs#L230-L259), [MCPServer.cs:399-403](https://github.com/allisterb/Camel/blob/63f4cb2e26a2469a35f847bee607516cf6184e91/src/Camel.Server/MCPServer.cs#L399-L403)).

trudi는 미들웨어가 증거 결과로 분류한 dict의 _metadata에 data_provenance와 순환 discipline_reminder를 붙이고 구조화 결과와 한 개의 텍스트 블록을 동기화한다([_enrich.py:28-60](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/tools/_enrich.py#L28-L60), [_enrich.py:75-103](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/tools/_enrich.py#L75-L103), [middleware.py:786-833](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/core/middleware.py#L786-L833)). 안내문 다섯 종류 중 증거 속 지시를 무시하라는 문구는 하나이며 매 호출에 그 문구가 나오지는 않는다. 분류는 R07.01·R07.02와 해당 문구가 붙는 호출의 R07.05로 하되, 문구를 읽는 모델의 행동이나 공격 문구 차단을 보장한다고 적지 않는다. dict가 아닌 반환값과 enrich 예외 경로에는 표시가 빠질 수 있다.

E03.01에는 선택적 Docker 경로의 mulder도 연결할 수 있다. 지원 경로와 조건을 보고서에 남기고 네이티브 모드의 보호로 확대해 해석하지 않는다.

위 상세들은 기능을 묶는 후보이며 프로젝트마다 전부 사용하는 항목이 아니다. 미구현·비적용·미확인과 실제 예외 사유는 보고서·프로젝트 연결 자료에 남긴다. 이름이 비슷하다는 이유로 연결하지 않는다.

### 6.3. E03의 프로젝트 연결 시범

이 표에는 현행 C4 판정의 연결 사례를 새 상세 ID로 옮겨 적었다. 12절 36번에서 옛 상세 7개를 주체별 3개로 합쳤으므로 포함 기준 칸에 옛 상세 이름을 남긴다. 프로젝트 전체의 새 분류를 확정한 결과는 아니다. †의 뜻은 6.2절 머리에 적었다(12절 28번).

| 상세 항목 | 포함 기준 | 프로젝트 예시 |
|---|---|---|
| E03.01 실행 환경의 읽기 전용 강제 | 컨테이너 증거 볼륨의 읽기 전용 마운트: 분석 컨테이너가 접근하는 증거 볼륨에 읽기 전용 제약을 적용. 증거 파일시스템의 읽기 전용 마운트: 실제 증거 접근에 사용하는 파일시스템을 읽기 전용으로 마운트 | mcp_dfir†, mulder†, ChainsawMCP†, trudi† |
| E03.02 서버 코드의 원본 쓰기 제한 | 접근 API의 읽기 전용 모드: 파일·DB를 여는 API에서 읽기 전용 모드를 지정. 출력 대상 검사: 생성·수정 대상이 원본 증거·원본 영역과 겹치는지 검사하고 겹치면 거부. 원본과 작업 입력의 분리: 해당 분석 경로가 원본에서 만든 파일·메모리 사본을 작업 입력으로 사용 | regipy, mulder†, trudi†, MyIRTeam† |
| E03.03 외부 도구·플랫폼에 위임 | 외부 도구에 의존: 읽기만 하는 외부 도구·라이브러리에 원본 보호를 맡김. 외부 플랫폼 권한에 위임: 플랫폼 계정 권한에 원본 보호를 맡김 | ChainsawMCP†, sift-kernel†, agentic-velociraptor-mcp† |

동일 프로젝트가 여러 상세에 들어갈 수 있다. mulder의 Docker 증거 볼륨은 선택적 실행 경로다. [README의 Docker 실행](https://github.com/calebevans/mulder/blob/3164843baf74c7fe69e7121dbd6150f8f77ce660/README.md#L65-L82)과 [Makefile 실행 대상](https://github.com/calebevans/mulder/blob/3164843baf74c7fe69e7121dbd6150f8f77ce660/Makefile#L66-L70)을 확인한다. 네이티브 실행에 같은 제약이 자동 적용되지는 않는다.

sift-kernel은 출력 폴더를 정하지만 원본 증거와 겹치는지 검사하지 않으므로 E03.02에 넣지 않는다. 원시 이미지의 읽기 전용 마운트 시도는 실패 시 직접 읽기 경로로 바뀌고 마운트 지점이 후속 분석 입력인지 별도로 확인해야 하므로 E03.01에도 자동 연결하지 않는다([server.ts:1644-1679](https://github.com/Sathvik-1007/sift-kernel/blob/ea51bec90d4cb543e4aa6063af6e85ae3e4d9396/src/server.ts#L1644-L1679)). agentic-velociraptor-mcp는 E03.03에 예외 표시로 둔다. 원본 보호를 Velociraptor 계정 권한에 맡긴 구조는 코드로 확인되지만 계정 권한이나 아티팩트가 실제로 원본 변경을 막는지는 확인되지 않았다(실제 보호 미확인). read_only 정책과 변경 RPC 제한은 T02의 작업 제어에서도 본다.

작업 입력 분리로 E03.02에 연결하는 것은 그 분리의 범위가 확인될 때다. 사본 생성만으로 다른 도구의 원본 쓰기 경로까지 제한됐다고 판단하지 않는다. sift-kernel의 읽기 전용 마운트 시도도 실제 분석 경로가 사용하지 않으면 이 표의 마운트 방식에 연결하지 않는다.

### 6.4. 용어

- **셀 이름**은 묻는 일을 명사로 쓴다.
- **셀**은 관찰 질문 하나다. **상세 항목**은 그 질문에 답하는 구현 방식이다. 방식이 없는 프로젝트는 `미구현`, 전제가 없는 프로젝트는 `비적용`, 조사하지 않은 프로젝트는 `미확인` 항목에 둔다. 줄여서 "상세"라고도 쓴다.
- **참조 자료**는 분석 도구가 실행 중에 읽는 룰·시그니처·심볼·플러그인·매핑·지식 시트다. 컨테이너 이미지는 실행 파일 쪽에 둔다.
- **파생물**은 서버나 도구가 만든 파일·자료다. D08의 보고서만 "보고 산출물"이라 쓴다.
- **해시**는 해시일 때 쓰고 무엇을 해시했는지 함께 적는다(파일 내용, 요청 필드, 파일 상태값). 심볼 GUID나 룰 커밋처럼 해시가 아닌 식별자는 "식별값"이라 쓴다. "지문"은 쓰지 않는다.
- **manifest**는 파일 목록과 파일마다의 해시·출처를 적은 목록 파일이다.
- flow·label(Velociraptor), digest(컨테이너 이미지), namespace(Linux), cursor는 영어 원어로 둔다.
- **외부 도구**는 MCP 서버가 실행하거나 불러 쓰는 포렌식 프로그램·라이브러리다(Sleuth Kit, Chainsaw, pytsk3 등). MCP가 노출하는 도구(tool)와 구별한다.
- **대상 시스템**은 조사하는 살아 있는 단말·서버다. 증거 사본이나 이미지가 아니다(T09).
- 옛 C06의 "부속 자료"와 "입력 일관성"은 E04의 상세 이름에 그대로 쓴다.
- 현행 49셀의 이름(B1 "호출자 신원 확인" 등)과 기존 원고에서 가져온 관찰 제목(10.6절 V5 등)은 현행 규격·원고의 표기라 이 문서에서 바꾸지 않는다. 원고를 새 구조로 다시 쓸 때 이 절의 용어를 적용한다.

## 7. 기능 발견·보고서·매트릭스의 연결 자료

### 7.1. 기능을 먼저 조사한다

**현재 셀·상세 항목 목록으로 프로젝트의 조사 범위를 제한하지 않는다.** 현행 규격 35절의 기능 목록 원칙을 이어받는다. 기준 커밋과 진입점·도구·리소스·프롬프트·설정·내부 처리기·공식 실행 스크립트를 먼저 읽는다.

1. 지원 배포 모드·설정·OS·증거 형식·대체 실행 경로를 확인한다.
2. 의미 있는 사용자 기능·상태 관리·보호 장치마다 입력, 처리, 출력·파생물, 상태 변화를 적는다.
3. 코드가 선언한 기능, 실제 호출 경로에 연결된 구현, 실행으로 확인한 결과를 구별한다.
4. 기능의 동작마다 기존 셀과 상세 항목을 대응시킨다. 한 기능에 여러 셀을 연결할 수 있다.
5. 기존 셀에 일부만 담기면 남은 동작과 근거를 보존하고 새 상세·셀 후보를 검토한다.
6. 기능 목록·보고서·매트릭스 연결을 대조해 누락을 확인한다. 분석 중 새 기능을 발견하면 목록에도 추가한다.

공개 도구 이름만 읽고 조사를 마치지 않는다. 요청의 인수 변환, 내부 분석·추천·오케스트레이션, 기록·파생물·상태의 생성·삭제·초기화, 비동기 완료, 증거 교체와 실패 경로까지 확인한다.

### 7.2. 새 상세와 새 셀을 나누는 기준

| 발견 | 처리 |
|---|---|
| 기존 셀의 목적과 상세의 포함 기준에 맞음 | 기존 상세에 연결하고 프로젝트 보고서에 실제 모드·범위·예외를 적음 |
| 목적은 같지만 방식·대상·DFIR 효과가 다름 | 그 셀의 새 상세 항목 후보 |
| 기능 일부만 기존 셀에 대응함 | 대응한 부분을 연결하고 남은 동작을 별도 후보로 보존 |
| 현재 셀이 묻지 않는 DFIR 기능임 | 다른 프로젝트에도 적용 가능한 질문으로 새 셀 후보 |
| 기존 셀의 여러 목적이 서로 다른 설명을 요구함 | 셀 분리·명칭·범위 조정 후보 |
| 겹치는 셀이 같은 목적을 반복함 | 병합·경계 조정 후보 |
| 문서에만 있거나 호출 경로가 확인되지 않음 | 구현 소속을 확정하지 않고 확인할 사항으로 남김 |

프로젝트 고유 명칭을 셀 이름으로 그대로 쓰지 않는다. sift-kernel의 capability graph에서는 선행 상태에 따른 호출 거부(T03), 다음 작업 추천(P02), 상태 조회·단계 표시(P03), 능력 상태가 요청·재시작 사이에 남는지(P04)를 각각 분석한다. graph 이름을 발견했다는 사실만으로 T03 조사를 완료하거나 새 셀을 자동 생성하지 않는다.

후보는 한 프로젝트에서만 나와도 남긴다. 둘 이상의 표본에서 반복되는지는 정의를 다듬는 자료다. 새 정의를 채택하면 기존 프로젝트에도 적용 가능한지 다시 확인한다. 조사하지 않은 기존 프로젝트를 미구현으로 바꾸지 않는다.

### 7.3. 상세 항목과 프로젝트 연결

상세 항목에는 **이름·하는 일·포함·제외 기준**을 한 번 정의한다. 프로젝트 연결은 해당 상세 ID·보고서 절·기준 커밋·적용 조건·중요한 예외를 가리킨다. 화면에는 프로젝트 이름만 나열하고 적용 범위 안의 예외가 있으면 †를 붙인다(6.2절 머리).

프로젝트가 같은 셀의 여러 방식에 속하면 모두 연결한다. 기본 모드 이외에도 저장소가 지원하는 Docker·설정·OS·증거 종류·fallback 경로를 포함한다. 작동하지 않는 설정 조각·호출되지 않는 함수·임의 운영자 배포는 구현 목록에 연결하지 않는다.

**미구현·비적용·미확인을 구별한다.** 셋은 각각 셀의 항목으로 둔다(6절). 일부 모드에서 방식이 작동하면 해당 상세에 연결하고 다른 모드의 공백은 보고서에 남긴다. 문서 주장만 있고 코드 연결이 확인되지 않으면 문서 대조·미확인으로 다루고 구현으로 확정하지 않는다.

프로젝트마다 긴 설명을 매트릭스 셀에 다시 쓰지 않는다. 보고서의 셀 절이 실제 구현과 미비점을 설명하고 바로 아래 코드 발췌를 보여 준다. 공통 방식 이름이 같아도 보호·추적 수준이 같다는 뜻은 아니다.

### 7.4. 새 구현 누락 점검

- 진입점·공개 기능·지원 모드와 중요한 내부 장치가 기능 목록에 들어갔는가.
- 기능의 입력·처리·출력·상태 변화 가운데 DFIR에 닿는 동작을 남겼는가.
- 기존 셀과 맞는 부분, 남은 동작, 확인하지 않은 부분의 위치가 있는가.
- 대응 셀이 없는 구현을 후보·축 밖 구현 관찰·단순 기능 기록에 보존했는가.
- 구현 방식과 중요한 미비점을 보고서에서 각각 설명했는가.

**셀을 전부 채웠다는 사실은 기능을 전부 찾았다는 근거가 아니다.** 축 밖 관찰에는 매트릭스가 표현하지 못한 실제 구현과 DFIR 의미를 적는다. 미비점은 해당 구현 절에 남기며 축 밖 구현 발견을 결함 목록으로 대체하지 않는다.

### 7.5. 표준 요건으로 옮길 때

방식별 프로젝트 수를 안전성 순위로 사용하지 않는다. 상세 항목이 달성하려는 DFIR 성질과 반례를 따로 정한다. 예를 들어 E03.01의 읽기 전용 증거 볼륨을 표준 요건으로 검토할 때는 컨테이너 밖 접근·기존 컨테이너 재사용·보호 실패 뒤 처리도 확인한다.

기능 목록·상세 항목·보고서 연결은 한 원본에서 관리할 수 있지만 **개편 논의 문서는 이 파일 하나에서 갱신한다.** 새 항목을 만들 때마다 별도의 개편안 파일을 만들지 않는다.

## 10. 전체 셀 구성과 현행 항목 대응

아래의 상세 이름은 비교할 구현·기록 특성의 후보이며 프로젝트 전체의 소속을 새로 확정한 목록은 아니다. 셀마다 질문·상세 후보는 `matrix/cells/<ID>.yaml`에 있고 시범 셀(E03·T03·R02·L02)과 R07은 포함 기준까지 정의했다. 필요하면 새 셀·상세를 추가·분리·병합한다.

### 10.1. 축과 셀

셀마다 질문·상세 후보·경계 설명은 [`matrix/cells/`](../matrix/cells/)의 `<ID>.yaml`에 있다. 축 차례는 [`matrix/axes.yaml`](../matrix/axes.yaml)을 따른다. 화면에서는 빌드한 매트릭스로 본다.

- **T 도구 실행 통제.** 실행 전 검사와 실행 과정을 한 축으로 합쳤다(12절 38번). T01~T03은 모델이 고른 호출을 실행하기 전의 검사, T04~T09는 실제 도구를 실행하는 과정이다(T09는 조건부).
- **D 파생물 관리.** D01·D03·D04는 E축과 같은 짜임이다. D01은 E01(등록), D03은 E02(무결성 검증), D04는 E03(원본 변경 방지)의 짝이고 D02는 파생물을 입력·실행에 잇는 계보를 본다.

### 10.2. 지원 기능에 따라 관찰할 셀

조건부 셀은 `conditional: true`이고 `applies_to`에 적용 범위가 있다. 그 기능이 없는 서버를 비적용으로 가를 수 있으면 조건부로 두지 않는다(결정 0009).

옛 B07(원격 호출자 인증)은 T03의 상세 T03.09·T03.10으로, 옛 C07(수집 관리)은 E01의 수집 상세와 T08의 수집 작업 상태로 옮겼다(12절 36번). stdio 서버의 프로세스 실행 권한·작업 권한은 프로필에서 확인하고 T03.09가 없는 것을 stdio 표본의 공통 결함·점수로 사용하지 않는다. 옛 H12(부재 주장 범위 검사)와 H13(가설·반론 수정 이력)은 발견사항 기능을 가진 서버에서 보는 질문이라 D07·D05의 상세로 옮겼다(12절 37번). 발견사항 기능이 없는 서버는 D05·D07가 비적용이다.

### 10.3. 별도 셀 여부를 검토할 후보

**P04 조사 문맥 관리.** 옛 A05(조사 상태 수명·복구)는 사건 개념이 없는 서버도 상태가 요청·세션·재시작 사이에 유지되는지 비교하려고 12절 23번에서 공통 셀로 되살렸다. 36번에서 옛 A06(사건 식별)·A07(사건별 분리)과 합쳐 사건·세션·프로세스 단위를 한 셀에서 본다. 사건 개념이 없는 서버도 세션·프로세스 상세로 들어간다. regipy는 적재한 하이브를 프로세스 전역 상태에 두고 sift-kernel의 HTTP 전송은 요청마다 서버를 새로 만든다.

### 13.1. 유지할 관찰 질문

A01/A02는 대상 유형 판별과 선택한 분석 방법의 입력 적합성 검사, A03/A04는 다음 작업 결정과 수행 범위·완료 판단이다. B01~B06은 각각 작업 권한, 도구 활성화, 조치 승인, 입력·환경 준비, 선행 조사 상태, 실행 연산 제한을 묻는다. B07은 살아 있는 대상의 대응 조치, B08은 원격 MCP 호출자 인증에만 조건부로 둔다. B08에 백엔드 접속 자격증명 관리나 stdio의 별도 인증 부재를 섞지 않는다.

C01~C07의 증거 등록, 해시 계산, 변경 대조, 원본 변경 방지, 읽기 범위, 입력 준비, 부속 자료 반영은 다른 동작이다. C02의 **해시를 얻음**과 C03의 **기준값과 다시 대조함**을 합치지 않는다. C08은 수집·헌트 기능이 있을 때만 연다. D01/D02는 실행 호출 방식과 격리, D03/D04/D05는 실제 버전의 확인·해당 실행과의 연결·기준값 대조, D06/D07은 종료 상태 판별과 재실행 자료 보존으로 구분한다.

E01~E09의 출력 가공, 대량 전달, 상태 통지, 출처 표기, 출처 재조회, 파생물 정보 전달, 시간 표현, 증거 텍스트와 지시의 구분, 해석 주의는 별개 질문이다. E04/E05는 식별자 **표기/재조회 가능성**, E06/F05는 **응답에 파생물 정보를 표시함/입력·호출·파생물 관계를 추적함**으로 경계를 둔다. F01~F06의 기록 범위·경과·요청 내용·기록 실패·입출력 연결·기록 무결성도 구분할 수 있다. G01~G05는 목적지·연동 활성화·전송 내용·실행 도구 통신 제약·외부 요청 기록을 각각 본다. H01~H09 및 H11/H12는 사건 식별·분리, 출력 경로, 보관, 재실행 버전, 보관 실패, 발견사항 관리·상관·근거 심사, 부재 주장·반론이라는 독립 목적이 있다. **현재 질문 전체를 삭제할 근거는 없다.** 아래에서 지적한 것은 범위와 상세의 수정이다.

| B04·B06 | 옛 B3 판정 문장이 두 곳에 복사돼 있다. **인자·입력·환경 검사**와 **명령·플러그인·질의 허용 범위**를 코드 경로별로 다시 나눈다. regipy 내부 플러그인도 외부 프로세스가 없다는 이유만으로 비적용 처리하지 않는다. |
| C01 | 사건 폴더나 등록부가 없어도 파일 증거를 읽는다면 관찰 대상이다. MyIRTeam·regipy의 옛 비적용을 자동 승계하지 말고 등록 정보의 부재 또는 실제 정보 전달로 재조사한다. |
| C04·C06·H03 | C04.04는 원본과의 **충돌 검사**에만 연결한다(6.3절 수정). 출력 폴더만 정하면 H03이다. C04.05는 사본 생성(C06)이 아니라 변경 경로가 사본으로 제한될 때만 연결한다. 선택적 Docker 경로는 적용 모드를 남긴다. |
| D01·D02 | regipy는 내부 라이브러리로 하이브와 플러그인을 실행하므로 D01의 라이브러리 내부 호출에 해당한다([server.py:237-289](https://github.com/mkorman90/regipy/blob/1293544148a4b4dc11d2811e11c9fd7e64fa9c04/regipy_mcp_server/server.py#L237-L289)). D02의 별도 프로세스는 같은 권한·파일·네트워크에 닿으면 격리 장치로 세지 않는다. 실제 제한된 권한·파일시스템·네트워크·작업 공간을 구분한다. |
| D03·D04·D05 | 저장소 고정과 호출 인자 지정은 **선언·선택**이며 실제 실행 버전 확인이 아니다. D03은 선언 판/실행 시 확인 버전을 구분하고 D04는 해당 결과에 어느 쪽이 연결됐는지 표시한다. D05는 사용 직전의 실제 대상과 기대 해시·서명·digest 대조를 본다. |
| D06·E03·F02 | 비동기 시작 응답이나 실행기 종료 코드만으로 최종 완료라고 보지 않는다. D06에 러너 소실·시간 초과 뒤 하위/원격 작업의 최종 상태 확인을 추가하고 그 사실이 E03 응답과 F02 기록에 있는지 따로 본다. |
| E02 | 현재 상세는 상한과 전체 건수 위주여서 **상한 초과 시 거부**(mcp_dfir)와 **값 하나를 잘라 반환**(regipy)을 담기 어렵다. 초과 거부, 값 단위 잘림, 잘림·생략 고지를 상세 후보로 더한다. 두 표본을 옛 E2의 비적용에서 그대로 옮기지 않는다. |
| E05 | 별도 검증 도구 연계는 결과 식별자로 **같은 출처·범위**를 찾아 대조할 때만 포함한다. 도구를 다시 실행할 수 있다는 일반 가능성은 재조회 기능이 아니다. |
| E08 | JSON 필드는 표면상 분리일 뿐 신뢰 불가 표시나 차단이 아니다. 경계 태그·위조 무력화·무시 안내·내용 차단과 효과 수준을 섞어 세지 않는다. 증거 문자열이 서버 추천 규칙을 바꾸는 경로는 A03의 규칙 입력·오탐 경로에 적는다. |
| F01~F06·H06 | F01은 기록이 없으면 미구현이다. 기록을 전제로 하는 F02/F03/F04/F06은 전제 없음을 일관되게 표시하되 F01의 부재를 가리지 않는다. F05는 응답·파생 결과의 입출력 관계도 묻기에 기록·사건 DB가 없다는 이유만으로 비적용으로 옮기지 않는다. H06의 기록 저장 실패는 F04와 겹치므로 **원래 출력·파생물·보고 산출물 저장 실패**로 좁힌다. |
| G04·G06 | 로컬 참조 자료 사용만으로 도구 통신이 제한된 것은 아니다. 실제 네트워크 차단·오프라인 옵션·목적지 강제를 G04에 넣는다. G06은 **추출 민감정보의 노출 제어**와 **서버 자격증명의 저장·주입·기록 제거**를 섞었으므로 두 셀로 나누는 편이 낫다. |
| H10 | **보고 내용 구성**과 보고 파일의 **서명·HMAC 봉인 및 재검증**은 다른 성질이다. 서명·봉인을 H10 구성 상세에서 빼고 실제 봉인 기능에 적용하는 별도 조건부 셀을 제안한다(셀 검토 자료 S8). |

추가로 다음 상세는 **효과의 수준**을 포함 기준에 적는다.

- **B03 승인 인자 검사:** 모델이 같은 요청에서 참으로 채울 수 있는 확인 인자는 별도 승인자의 동의 확인과 다르다. 승인 생성 주체·보관 위치·요청 내용 결합·재사용 가능성을 구분한다. **B01 백엔드 권한**도 계정의 실제 권한이 확인된 경우에만 연결한다.
- **C04 읽기 전용 접근 API:** 서버 라이브러리가 읽기 모드로 여는 경로와 운영체제·마운트가 쓰기를 거부하는 경로를 별도 상세로 유지한다. 한 경로의 보호를 다른 경로로 확대하지 않는다.
- **D07 분석 상태 저장·복원:** A05를 채택하면 상태의 저장·수명·복구는 A05로 옮긴다. D07은 같은 분석을 재실행할 실제 입력·설정·모델 판단 자료의 보존에 집중한다.
- **F06 일련번호·외부 기준점:** 단순 연속 번호만으로 삭제·재생성·전체 교체를 탐지한다고 볼 수 없다. 외부에 고정한 기준점이나 독립 검증과 구분한다.
- **H09 사람 검토, H11 한정된 부재 결론:** 검토자에게 보여 주기만 하는 기능과 검토 전 발견사항 확정을 막는 게이트를 구분한다. 범위·누락 검사가 없는 한정 문구는 H11의 범위 검사 구현으로 세지 않고 보고 표현으로 기록한다.

C02의 자동/요청 시점과 전체/부분 범위, C03의 대조 값과 대조 시점처럼 **독립된 특성은 한 프로젝트가 여러 상세에 속하게** 둔다. 미구현·비적용·미확인은 매트릭스에 남기되 구현 방식과 구별되는 **별도 행**으로 보이게 한다. 상태 필드를 새로 만들 필요는 없다. 비적용은 장치의 부재가 아니라 셀의 전제가 되는 동작이 없을 때 쓴다. 부분 모드의 보호를 전체 보호로 늘려 읽지 않도록 프로젝트 연결에 적용 조건을 남긴다.

### 13.3. 추가·분리할 질문의 우선순위

1. **A05 조사 상태 수명·복구 방식(공통 셀 채택 권고).** 상태를 어디에 두고 세션·요청·사건·재시작·초기화 경계에서 어떻게 유지·복구·폐기하는가. B05는 그 상태로 호출을 거부하는지, A04는 완료 판단, H02는 사건 간 분리, D07은 재실행 상태를 본다. sift-kernel의 요청 단위 상태, trudi의 세션 파일, ChainsawMCP·regipy의 메모리 상태가 서로 다른 답을 준다.
2. **사건 자료 삭제·초기화 통제 방식(공통 셀 채택 권고).** 모델 도구·운영자 CLI·자동 정리별로 증거·기록·파생물·조사 상태 중 무엇을 지우는지, 원본 제외·승인·삭제 전 보관·삭제 사실 기록이 있는지 묻는다. F06/H04/C04/B03에 흩어진 사실만으로 **삭제 기능의 대상과 조건**을 한 곳에서 비교할 수 없다. sift-kernel reset, trudi clear, mcp_dfir clear, mulder replace, ChainsawMCP 재스테이징이 근거다. 의도치 않은 기록 소실도 실행 경로를 구별해 남긴다.
3. **대체 실행·입력 경로 선택과 결과 의미 표시 방식(공통 셀 채택 권고).** 원래 방법이 불가능할 때 다른 실행 파일·파서·직접 읽기 경로로 바꾸는 조건, 실제 선택 경로, 빠지는 검증·입력 범위, 응답·기록 고지를 묻는다. D01은 호출 형태, D04는 환경정보, E03은 상태만 본다. sift-kernel의 ewfverify→img_stat과 마운트 실패→fls는 결과의 의미가 달라지는 사례다.
4. **서버 안 모델 판단은 우선 기존 셀에 흡수.** 모델 결과가 B05 게이트나 H09 심사를 정하는지 확인하고 D07에 모델·버전·설정, 입력·응답, 프롬프트·정책 식별값, 실패 시 통과·거부의 보존을 상세로 더한다. 일반 재실행 자료로 표현되지 않는 사례가 더 나오면 조건부 독립 셀로 분리한다.

| 질문 후보 | 현재 표본으로 정의할 상세 후보 |
|---|---|
| A05 상태 수명·복구 | 요청·세션 메모리에만 둠 / 사건별 파일·DB에 저장 / 재시작 후 복구 / 사건·세션 전환 시 상태 검사 / 초기화·만료 |
| 사건 자료 삭제·초기화 | 모델 도구로 실행 / 운영자 CLI로 실행 / 자동 정리·교체 / 대상별 원본 제외 검사 / 별도 승인·확인 / 삭제 전 보관 / 삭제 사실 기록 |
| 대체 실행·입력 경로 | 대체 없이 실패 통지 / 사전 정의한 대체 경로 사용 / 검증·입력 범위 차이 대조 / 실제 선택 경로 응답 표시 / 선택 경로와 의미 차이 기록 |

이들은 **서로 배타적인 등급**이 아니다. 프로젝트 하나가 여러 상세에 들어갈 수 있다. 방식 이름만으로 실제 차단·복구·검증의 성공을 인정하지 않고 범위·실패 경로를 보고서에 남긴다.

위 권고를 채택할 때 **셀 ID와 총수를 다시 매긴다.** 현재 10절의 55+5를 최종 수로 인용하지 않는다. 새 질문의 포함·제외 기준을 정한 뒤 8개 표본에 재적용하고 옛 비적용·일부만을 기계적으로 변환하지 않는다.
