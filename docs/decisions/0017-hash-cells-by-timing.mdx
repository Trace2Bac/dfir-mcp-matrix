# 0017. D03·E02 상세를 기준값 계산과 검증 시점으로 나눕니다

- 날짜: 2026-10-02
- 상태: 채택
- 결정한 사람: 결정권자(팀)

## 배경

sift-kernel 전체 적용에서 D03.07 "서명·MAC 검증"이 문제가 되었습니다.
이 상세는 MAC을 붙이는 일과 검증하는 일을 하나로 묶고 있었습니다. 그래서 HMAC을 붙이기만 하는 서버를 담지 못했습니다.

D03과 E02의 상세에는 서로 다른 기준이 섞여 있었습니다.

- 해시 범위: 파일 전체인지 일부인지
- 기준값을 남기는 곳: 응답인지 기록인지
- 대조 방법: 해시 재계산, MAC, 크기
- 대조 시점

그 결과 한 서버의 같은 동작이 여러 상세에 나뉘어 적혔습니다. 또 E02.06과 E02.07에는 정의가 없었습니다.

## 결정

두 셀의 상세를 같은 구조로 맞춥니다. 각 셀에는 다음 다섯 가지 상세를 둡니다.

| 상세 종류 | D03 | E02 |
|---|---|---|
| 기준값을 자동으로 계산하는 상세 | D03.01 "생성 시 기준값 자동 계산" | E02.01 "등록 시 기준값 자동 계산" |
| 도구를 요청해 기준값을 계산하는 상세 | D03.02 "도구를 요청해 기준값 계산" | E02.02 "도구를 요청해 기준값 계산" |
| 도구 호출 중 자동 검증 | D03.09 "도구 호출 중 자동 검증" | E02.07 "도구 호출 중 자동 검증" |
| 도구를 요청해 검증 | D03.11 "도구를 요청해 검증" | E02.09 "도구를 요청해 검증" |
| 불일치 시 중단·경고 | D03.10 "불일치 시 중단·경고" | E02.08 "불일치 시 중단·경고" |

세부 내용은 원고의 **구현** 단락에 씁니다. 어느 상세에 무엇을 쓰는지는 다음과 같습니다.

- 기준값 상세: 해시 범위, MAC·서명, 기준값을 남기는 곳
- 검증 상세: 대조 방법, 기준값을 가져오는 곳

기존 상세는 다음과 같이 합칩니다.

- D03.03·D03.04·D03.05·D03.07 → D03.01
- D03.06·D03.08 → D03.11
- E02.03·E02.04 → E02.02
- E02.05·E02.06 → E02.09

## 영향

각 서버의 상세 연결이 다음과 같이 바뀌었습니다. †(예외 표시)는 원고의 구현 단락에 적은 적용 범위 안에서 그 방식이 적용되지 않는 경우가 있다는 표시입니다.

- mulder: D03은 D03.01·D03.11†, E02는 E02.01†·E02.02가 되었습니다.
- sift-kernel: D03은 D03.01†, E02는 E02.02·E02.09†·E02.08†가 되었습니다.
- Camel: E02는 E02.02·E02.09†·E02.08†가 되었습니다.

sift-kernel D03.01에는 †를 더했습니다. `format`이 `json`이면 HMAC이 없기 때문입니다.
