# 0046. findevil 검토 주기에 E02·D03·F01·F05·L01·L02·T06의 범위와 기준을 고칩니다

- 날짜: 2026-10-08
- 상태: 채택
- 결정한 사람: 결정권자(팀)

## 배경

findevil의 `finalize_report`는 발견사항과 결론을 주장 목록으로 받습니다.
서버는 확정 주장을 증거 원본을 다시 읽어 확인하고 주장끼리 모순이 있으면 마무리 전체를 거부합니다.
하지만 받은 주장을 저장하지 않고 통과·거부 결과를 응답 글로만 돌려주며 보고 산출물도 만들지 않습니다.

F05 `scope`는 두 경로만 적용 범위로 적었습니다.

- 서버가 발견사항, 결론, 부재 주장을 받아 저장하거나 고치거나 합치는 도구와 경로
- 보고 산출물을 쓰거나 내보내기 전에 근거를 심사해 보고를 막는 경로

`finalize_report`는 두 경로 어디에도 속하지 않아 글자 그대로는 적용 범위 밖이었습니다.
그런데 F05 `not_applicable`(받거나 저장하거나 보고하는 경로가 없음)에는 받는 경로가 있어 맞지 않았습니다.
`not_implemented`(서버가 근거를 확인하지 않음)에도 서버가 근거를 확인하므로 맞지 않았습니다.
`scope`와 미구현·비적용 기준 사이에 이 경우를 둘 자리가 없었습니다.

같은 도구의 확정 주장 검사는 F05.02와 F05.04 어디에도 문구가 맞지 않았습니다.

- 서버는 주장이 가리키는 증거 원본(인증 로그, 파일시스템 루트 등)을 다시 읽어 주장의 값과 대조합니다. 서버는 도구 출력을 저장하지 않으므로 인용한 호출의 저장된 출력과 대조하지 않습니다.
- F05.02 `include`는 대조 대상을 "인용한 호출의 저장된 출력"으로만 적어 이 대조를 담지 못했습니다.
- F05.04 `include`의 "다른 출처나 도구로 다시 확인"에도 맞지 않았습니다. 서버는 같은 증거를 처음 발견사항을 만든 도구와 같은 파서로 다시 읽습니다.
- 기존 사례를 보면 F05.02(sift-kernel `register_finding`, trudi `misc.submit_finding`)는 서버가 주장 내용과 근거를 직접 비교하는 방식이었습니다. F05.04(trudi의 보강 도구·대안 가설 게이트)는 서버가 내용을 비교하지 않고 다른 출처의 확인이나 반론 처리가 기록에 있는지를 확정 조건으로 삼는 방식이었습니다.

findevil의 L01.10 연결도 정의 문구와 어긋났습니다.

- `scripts/extract_token_usage.py`는 Claude Code가 남긴 세션 대화 기록에서 findevil 도구 호출(도구 이름, 인자, `tool_use_id`)을 꺼내 `token_usage.jsonl`에 남깁니다. 이 기록은 MCP 도구 호출을 식별할 수 있고 서버 기록과 별도입니다.
- 하지만 이 스크립트는 사용자가 따로 실행하는 사용자 CLI입니다. L01.10 `include`의 주체는 "클라이언트 코드, 훅, 설정"이었고, 사용자 CLI를 주체로 둔 곳은 F06(옛 D08, 결정 0013·0028)뿐이었습니다.
- Camel은 저장소의 훅·설정이 Claude Code 대화 기록을 사건 폴더로 복사하는 경로를 L01.10에 연결했습니다. 외부 클라이언트의 대화 기록을 원천으로 쓰는 것은 연결을 막는 사유가 아니었습니다.

L02와 T06에서도 findevil의 기록과 파생물을 둘 자리가 문구로 정해지지 않았습니다.

- L02.01은 "SDK가 해석한 인자"만 명시하고 L02.02는 변환의 예로 "dispatch, 기본값, 경로 변환"만 들었습니다. 서버 코드가 JSON 문자열을 객체로 해석해 기록하는 것(`verify_finding`)과 값을 상한으로 줄여 기록하는 것(`hexdump`)이 어느 상세인지 갈렸습니다.
- findevil `baseline_create`는 기준 파일의 `_metadata`에 FIM 코드의 식별값 `tool_version`(`findevil-fim-1`)을 적습니다. T06.05는 표시 위치에 파생물이 없었고, 후보 T06.03의 "도구"가 서버 안의 분석 코드를 포함하는지 정해져 있지 않았습니다.

E02와 D03은 확인 사항과 미구현을 "해시 기준값", "해시를 계산하지 않는 경우"로 적었습니다.

- 상세는 이미 해시보다 넓었습니다. D03.01은 키를 쓴 MAC과 서명을, D03 `scope`와 E02.07은 크기·수정 시각 같은 상태 값의 대조를 담았습니다.
- 그래서 해시는 계산하지 않고 상태 값만 대조하는 서버가 나오면 E02 미구현 정의와 E02.07 포함 기준이 서로 부딪쳤습니다.
- findevil의 `baseline_create`·`baseline_diff`는 기준값을 계산해 대조하는 겉모양이 E02와 같지만, 깨끗한 시스템에서 만든 기준선과 조사 대상을 비교해 바뀐 파일을 찾고 불일치를 `LIKELY COMPROMISE`라는 침해 판정으로 냅니다. 같은 증거의 처음 값과 지금 값을 대조하는 E02와 대조 대상과 불일치의 뜻이 다릅니다.

F01에서는 늘 같은 문구로 결론 확인 절차를 안내하는 경우가 서버마다 다른 상세에 놓이거나 어디에도 놓이지 않았습니다.

- F01 `question`은 해석 원칙, 서술 방식, 확인 방식을 묻지만 고정된 확인 안내를 받을 상세가 없었습니다. Camel은 "독립된 출처 둘 이상으로 확인하라"를 F01.01에, findevil은 `get_audit_trail`·`verify_finding` 설명의 확인 절차를 어디에도 두지 못했습니다.
- F01.03 `include`는 "내용·근거 수·등급에 따라 고른" 단서라고 하면서 고정된 글인 도구 설명과 리소스를 함께 들었습니다. sift-kernel은 내용과 관계없이 늘 같은 `challenge_finding` 전략을 F01.03에 두고 한계로 적었습니다.

## 결정

F05 `scope`에 두 문장을 더합니다.

- 서버가 발견사항, 결론, 부재 주장을 받아 저장하지 않고 판정 결과만 응답으로 돌려주는 도구도 적용 범위입니다.
- 서버 지침이나 도구 설명이 그 도구의 판정을 통과해야만 발견사항이나 결론을 확정할 수 있다고 밝혔으면 그 도구를 게이트로 봅니다.

서버가 판정 결과를 강제하지 못하는 경로(클라이언트가 판정을 따르지 않고 보고서를 쓰는 경우 등)는 원고의 한계 단락에 씁니다.

F05.02와 F05.04를 다음 기준으로 나눕니다.

- F05.02는 서버가 주장 내용을 근거와 직접 비교하는 방식입니다. `include`의 대조 대상에 "주장이 가리키는 증거 원본"을 더하고 "증거 원본은 서버가 다시 읽어 대조합니다"를 덧붙입니다.
- F05.04는 서버가 내용을 비교하지 않고 다른 출처·도구의 확인이나 반론 처리를 확정 조건으로 삼는 방식입니다. `exclude`에 "서버가 주장 내용을 근거와 직접 대조하는 경우는 F05.02에서 봅니다"를 더합니다.

L01에서 클라이언트 쪽 기록의 주체에 사용자 CLI를 더합니다.

- L01.10 `include`: "같은 저장소가 함께 제공하는 클라이언트 코드, 훅, 설정이나 사용자 CLI가 MCP 도구 호출을 식별할 수 있는 기록을 서버 기록과 별도로 남기는 경우입니다."
- L01 `scope`와 `not_implemented`의 "같은 저장소의 클라이언트"도 "클라이언트나 사용자 CLI", "클라이언트와 사용자 CLI"로 맞춥니다.
- 사용자가 따로 실행해야 남는 기록이라는 점, 서버 기록과 이어 주는 키가 없다는 점은 원고에 사실로 씁니다.

L02.01과 L02.02를 "값의 뜻이 바뀌었는가"로 나눕니다.

- L02.01 `include`를 "모델이 보낸 MCP 도구 이름과 인자를, 서버가 값의 뜻을 바꾸기 전 값으로 실행 명령과 별도 필드에 기록하는 경우입니다."로 고칩니다. SDK가 인자를 해석한 값과 서버 코드가 JSON 문자열을 객체로 해석한 값은 값의 뜻이 그대로이므로 이 문장에 해당합니다. 그래서 "SDK가 해석한 인자를 기록한 경우도 해당합니다"는 지웁니다.
- L02.02 `include`를 "서버가 dispatch, 기본값, 경로 변환, 값 범위 조정처럼 인자 값의 뜻을 바꾼 뒤의 연산과 인자를 기록하는 경우입니다."로 고칩니다.

T06에서 파생물에 적는 버전을 봅니다.

- 후보 T06.03 「파생물 manifest에 버전 표시」를 셀 정의로 옮깁니다. findevil `baseline_create`가 기준 파일의 `_metadata`에 FIM 코드의 식별값 `tool_version`을 적는 경로가 첫 사례입니다.
- T06.03 `include`의 "도구"에 서버 안의 분석 코드를 포함한다고 밝힙니다. `exclude`에 파생물 파일의 형식만 가리키는 스키마 버전은 해당하지 않고 서버 자신의 패키지 버전·커밋·코드 해시는 T06.05에서 본다는 문장을 더합니다.
- T06.02 `exclude`의 "(후보 T06.03)"을 "T06.03에서 봅니다"로 고칩니다.

E02와 D03에서 "해시 기준값"을 "기준값"으로 바꿉니다.

- 두 셀의 `question`·`scope`·`not_implemented`와 E02.01·E02.02·D03.01 `include`의 "해시"를 "기준값"으로 바꿉니다.
- 두 셀의 `scope`에 기준값의 뜻을 둡니다. "기준값은 내용의 해시, 키를 쓴 MAC이나 서명, 또는 상태 값(크기, 수정 시각, inode)을 묶은 값입니다."
- 같은 `scope`에 메타데이터 표시를 뺍니다. "상태 값은 서버가 기준값으로 남기거나 대조에 쓸 때만 기준값으로 봅니다. 응답에 파일 메타데이터를 보여 주기만 하는 것은 해당하지 않습니다."
- E02.07 `include`의 상태 값 문장은 `scope`로 옮겼으므로 지웁니다.
- E01과 D09 `boundary`의 "해시"도 "기준값"으로 맞춥니다.
- E02 `boundary`에 "참조 기준선과 비교해 바뀐 파일을 찾아 침해를 판정하는 분석(파일 무결성 감시 등)은 F02에서 봅니다."를 더합니다.
- 원고는 구현 단락에 기준값의 종류(해시, MAC·서명, 상태 값)와 대조 방법을 씁니다(결정 0017). 상태 값만 대조하면 내용이 바뀌어도 상태 값이 같으면 알아채지 못한다는 점을 한계 단락에 씁니다.

F01에 확인 절차 안내를 담는 상세를 둡니다.

- F01.05 「공통 확인 절차 안내」를 더합니다. 발견사항·결론을 기록하거나 보고하기 전에 근거가 된 호출이나 증거를 다시 확인하라는 안내를 발견사항의 내용과 관계없이 늘 같은 문구로 싣는 경우이고, 반대 근거나 다른 출처를 찾아보라는 안내도 포함합니다.
- F01.03 이름을 「발견사항별 보완 안내」로 바꾸고 `include`를 발견사항·결론마다 내용·근거 수·등급을 보고 보완할 점(더할 근거, 확인할 도구, 등급, 빠진 값, 나눌 주장)을 싣는 경우로 좁히고, 도구 설명이나 리소스의 고정된 글은 조건을 달아 안내할 때만 해당한다고 밝힙니다.
- F01.02 `exclude`에 반대 근거나 다른 출처를 찾아보라는 확인 안내는 F01.05에서 본다는 문장을 더합니다.

셀 번호는 바뀌지 않습니다.

## 영향

- 매트릭스 버전을 2026-10-08로 올립니다(`matrix/config.yaml`).
- 다시 본 셀은 E02, D03, F01, F05, L01, L02, T06입니다.
  - findevil: `finalize_report`의 확정 주장 검사와 `verify_finding`을 F05.04에서 F05.02로 옮깁니다. F05.10 연결은 그대로입니다.
  - trudi의 F05.04 연결과 trudi·sift-kernel의 F05.02 연결은 새 기준에서도 그대로입니다.
  - mulder, sift-kernel, trudi, Camel: 발견사항을 저장하는 경로가 이미 적용 범위 안에 있어 판정이 바뀌지 않습니다.
  - protocol-siftpp: 서버에 발견사항을 받는 경로가 없어 비적용을 유지합니다.
  - mcp_dfir, regipy: F05 원고가 없습니다.
  - L02: findevil은 `verify_finding`을 L02.01에 두고 `hexdump`·`baseline_create`·`baseline_diff`를 L02.02에 둡니다. Camel·mulder의 L02.01과 Camel·sift-kernel의 L02.02 연결은 새 문구에서도 그대로입니다.
  - T06: findevil을 미구현에서 T06.03으로 바꿉니다. trudi가 trace·보고서 JSON에 적는 `schema_version`은 파일 형식 버전이라 T06.03에 해당하지 않고, mulder의 `SCHEMA_VERSION`은 자산 설치 상태 파일의 형식 번호라 사건 파생물이 아닙니다. 다른 서버의 T06 판정은 바뀌지 않습니다.
  - E02·D03: 기존 연결은 모두 해시·MAC·서명이나 이미 연결한 상태 값 대조(protocol-siftpp·trudi의 E02.07, trudi의 D03.09)라 바뀌지 않습니다. 메타데이터를 보여 주기만 하는 도구를 연결한 원고는 없습니다. Camel·findevil의 D03 미구현도 그대로입니다.
  - E02(findevil): `baseline_create`·`baseline_diff`를 E02에서 빼 E02.09·E02.08 연결을 지우고 `hash_file`의 E02.02만 남깁니다. 파일 무결성 감시 판정은 findevil F02에 이미 있습니다. 이런 비교를 E02에 연결한 다른 서버는 없습니다(Camel의 SHA-1 기준값은 같은 증거의 보관 연속성 확인입니다).
  - F01: Camel(리소스의 독립 출처 확인과 반대 근거 조회 점검), findevil(`get_audit_trail`·`verify_finding` 설명), sift-kernel(`build_attack_narrative`의 확인 연산 안내와 `challenge_finding`의 고정 전략)을 F01.05에 연결합니다. 세 서버의 F01.01·F01.02·F01.03 연결은 다른 내용으로 그대로 해당합니다. mulder·trudi의 F01.03은 발견사항마다 다른 안내라 바뀌지 않습니다.
  - L01: findevil의 L01.10 연결을 유지합니다. Camel·mulder·protocol-siftpp의 L01.10은 클라이언트 코드나 훅·설정이 남기는 기록이라 그대로이고, trudi·sift-kernel은 L01.10에 연결하지 않아 바뀌지 않습니다.
