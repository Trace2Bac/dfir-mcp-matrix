# 0008. R05는 결과 출처 표시만 보고, 클라이언트 쪽 상세에는 저장소의 클라이언트를 센다

- 날짜: 2026-10-01
- 상태: 채택
- 결정한 사람: 결정권자(팀)

## 배경

R05 결과 출처 추적은 결과 항목의 출처를 어떻게 표시하는지와 그 식별자로 다시 읽고 대조하는지를 함께 물었다.
mulder 원고에서 다시 읽기·대조로 연결한 사실은 저장한 출력을 다시 읽는 `get_raw_output`(R02와 같은 사실), 파생물끼리 대조하는 `verify_evidence_integrity`(D03과 같은 사실), 결과의 inode를 다른 도구로 넘겨 원본을 다시 읽는 보통의 호출이었다.
R축은 결과를 돌려줄 때의 일을 보는데 다시 읽기는 뒤의 다른 호출에서 일어난다.

T02.03 클라이언트 도구 선택은 상세 이름부터 클라이언트 쪽 방식을 묻지만 mulder 원고 머리(`reports/mulder/index.md`)는 오케스트레이터를 구현으로 세지 않는다고 적어 연결할 수 없었다.

## 결정

- R05 이름을 "결과 출처 표시"로 바꾸고 질문을 "각 결과 항목이 어느 증거·파일·레코드에서 나왔는지 응답에 어떻게 표시하는가?"로 줄인다.
- R05.05~08(원본 범위 재읽기, 작업 사본·저장 출력 조회, 재조회 시 해시·내용 대조, 별도 검증 도구 연계)을 지운다. 저장한 출력을 다시 읽는 방식은 R02, 파생물 대조는 D03, 원본 증거 대조는 E02에서 본다.
- 상세가 클라이언트 쪽 방식을 묻는 경우(예: T02.03)에는 같은 저장소가 함께 내놓는 클라이언트(오케스트레이터)의 동작도 구현으로 센다. 다른 클라이언트로 붙으면 걸리지 않는다는 점은 예외에 적는다. 그 밖의 셀에서는 클라이언트 동작을 원고에 사실로만 적는다.

## 영향

mulder의 R05 원고에서 R05.05·06·08 절을 뺐다. 보조 파티션의 inode를 다른 파티션에서 읽는 결함은 이 절에만 있었으므로 필요하면 다른 셀(E04 또는 T01)에서 다시 적는다.
mulder T02 원고에 T02.03(†)을 더했고 `reports/mulder/index.md`의 범위 문장을 고쳤다.
