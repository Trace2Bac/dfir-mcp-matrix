# 0009. 사례마다 검증 방법과 분석 회차를 따로 기록합니다

- 날짜: 2026-11-24
- 상태: 제안
- 결정한 사람:

## 배경

문제 매트릭스의 사례는 대부분 코드 확인(정적 분석)으로 찾았다. 화면에서는 실행으로 확인한 사례와 코드만 본 사례가 구분되지 않았고, 서버의 새 버전에서 고쳐졌는지도 남길 곳이 없었다.
모든 사례를 같은 방법으로 검증할 수도 없다. 함수 하나를 부르면 드러나는 문제가 있고, 서버마다 따로 재현해야 하는 문제가 있고, 모델이 도구를 부르는 조사에서만 영향이 드러나는 문제가 있다.

## 결정

- 검증 방법을 코드 확인, PoC, 시험, 모델 실험 넷으로 나누고, 사례마다 쓴 방법과 실행 수준(함수, MCP, 에이전트)을 `verifications.csv`에 적는다. 시스템 공학의 검증 방법 구분(검사, 시연, 시험, 분석)과 소프트웨어 시험 수준(단위, 통합, 시스템)을 따랐다.
- 서버의 분석 회차를 `snapshots.csv`에 두고, 첫 전체 분석의 커밋을 기준 커밋으로 한다. 뒤 회차에서 본 결과(남아 있음, 고쳐짐, 기능 바뀜)는 `checks.csv`에 쌓는다. 결함 관리 도구가 발견 항목을 하나로 두고 스캔마다 상태를 쌓는 방식을 따랐다.
- 전체 분석 회차는 관찰된 모든 문제의 결과가 있어야 한다. 확인하지 않은 것과 고쳐져서 없는 것을 가르기 위해서다.
- PoC와 시험의 코드와 실행 기록은 dfir-mcp-bench에 두고, 매트릭스는 결과와 링크만 싣는다.

## 영향

- `experiments.csv`는 `verifications.csv`의 모델 실험 줄로 옮겼다.
- `servers.csv`의 기준 커밋은 `snapshots.csv`로 옮겼다.
- 앞으로 코드 확인 사례 가운데 무작위 표본을 PoC나 시험으로 재현해, 코드 확인의 정밀도를 함께 공개한다.
