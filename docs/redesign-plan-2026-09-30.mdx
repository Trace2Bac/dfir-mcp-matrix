# 보고서·코드 근거·매트릭스 통합 개편안

작성일: 2026-09-30.

이 문서는 다음 네 가지를 어떻게 바꾸는지에 대한 **설명과 배경**을 담고 있습니다.

- 보고서 작성
- 근거 배치
- 매트릭스 셀 구성
- 기능 발견 절차

원본 자료는 다음 위치에 있습니다.

- 셀 구조와 정의의 원본은 [`matrix/`](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/tree/main/matrix)에 있습니다. 축은 `axes.yaml`에, 셀은 셀마다 `cells/<ID>.mdx`에 있습니다.

이 문서의 6.2절과 10절은 `matrix/`를 가리킵니다. 12절은 첫 버전 이전에 내린 결정의 git 이력을 가리킵니다.

이 문서에서 자주 쓰는 말은 다음과 같습니다. 자세한 용어 정의는 6.4절에 있습니다.

- **셀**: 관찰 질문 하나입니다.
- **상세 항목**(줄여서 "상세"): 그 질문에 답하는 구현 방식 하나입니다.
- **축**: 셀을 묶는 큰 갈래입니다.
- **예외 표시(†)**: 보고서의 **구현** 단락에 적은 적용 범위 안에서 그 방식이 적용되지 않는 경우가 있다는 표시입니다. 정확한 기준은 6.2절에 있습니다.

검토한 자료는 다음과 같습니다.

- 현행 작업지침, 문장 기준, 규격
- mcp_dfir, sift-kernel, regipy 보고서의 해당 절
- mcp_dfir, sift-kernel의 기준 커밋 코드
- 앞선 49셀·42건 구현 관찰 대응 자료

절마다 다루는 내용은 다음과 같습니다. 필요한 부분부터 읽으세요.

- 2~5절: 보고서와 코드 발췌
- 6~7절: 매트릭스 원칙과 기능 발견
- 10절: 전체 셀과 기존 항목의 대응

## 1. 왜 개편하나요? 범위와 확인한 사례

**이 개편안은 다음 세 가지를 함께 바꿉니다.**

- 보고서의 설명 순서
- 코드 근거의 배치
- 매트릭스의 관찰 목적

하나만 바꾸면 문제가 남습니다. 코드 링크만 부록으로 옮기면, 구현 설명이 지나치게 줄어든 문제는 그대로 남습니다. 셀 이름만 바꾸면, 목적이 서로 다른 기록 필드가 계속 같은 셀에 섞입니다.

개편 전 현행 규칙(2026-09-30 기준)은 다음과 같습니다.

- 작업지침 4.7절은 모든 주장 뒤에 코드 줄 링크를 붙이도록 정하고 있습니다. 또 셀 절의 첫 문장을 판정 파일 설명과 같은 뜻으로 쓰도록 정하고 있습니다.
- 문장 기준도 코드를 다루는 문장에 링크를 직접 붙이도록 합니다(작업지침, 문장 기준).

현재 보고서에서 확인한 사례와, 설명에서 개선할 내용은 다음과 같습니다.

| 현재 사례 | 설명에서 개선할 내용 |
|---|---|
| mcp_dfir F3 | 첫 문장이 기록 필드와 출력 파일을 압축해 나열합니다. 그 뒤로는 ID, 인자, 해시가 부족하다는 점을 길게 설명합니다. 실제 처리 순서를 먼저 설명해야 합니다. 명령을 만드는 단계부터 요약 JSON과 출력 파일을 저장하는 단계까지입니다 |
| sift-kernel B5 | 첫 문단에 조건 명세, 검사, 능력 생성, 예외가 한꺼번에 들어 있습니다. 먼저 상태가 만들어지고 그 상태가 다음 호출을 제어하는 과정을 풀어 씁니다. 그다음에 적용되지 않는 경로를 설명하면 읽기 쉽습니다 |
| regipy C4 | 읽기 모드로 열고 메모리 사본에서 파싱한다는 설명이 먼저 나옵니다. 이렇게 구현부터 설명하는 방식은 그대로 재사용할 수 있습니다. 뒤에 나오는 상세 항목의 코드 근거는 본문에서 떼어 낼 수 있습니다 |

확인한 세 보고서에는 소스 코드 블록이 없습니다. 이번 개편에서 가독성을 높이려고 손볼 대상은 다음 두 가지입니다.

- 본문에 반복되는 파일 경로·줄 번호 링크
- 판정을 중심으로 짠 설명 순서

주의: 이 세 보고서만 보고, 원래 보고서 전체가 설명을 생략했다거나 코드 인용이 필요 없다고 일반화하지 않습니다.

## 2. 새 보고서 구조

보고서는 먼저 프로젝트의 기능 흐름을 설명합니다. 그다음 관찰 셀별로 필요한 구현을 풀어 씁니다. 셀 절의 마지막에는 **그 절의 설명을 뒷받침하는 짧은 코드 발췌와 고정 커밋 링크**를 둡니다. 본문 문장은 번호 표지로 그 근거를 가리킵니다.

보고서는 다음 순서로 구성합니다.

| 위치 | 내용 |
|---|---|
| 프로젝트·검토 범위 | 역할, 기준 커밋, 진입점·모드, 연동 경계, 읽은 범위와 실행 확인 범위 |
| 기능 목록·처리 흐름 | 셀에 맞추기 전의 기능 목록과 입력에서 출력·저장까지의 주요 경로 |
| 셀별 구현 설명 | 연결한 상세 항목마다 구현(입력·처리·출력·상태). †를 붙인 항목은 예외도 씁니다(4절, 12절 25번) |
| 셀별 근거 | 구현·예외 설명이 끝난 바로 뒤에 둡니다. 중요한 분기·호출·저장 코드를 짧게 발췌하고 파일·줄 링크를 붙입니다. 순서는 본문 번호 표지 순서를 따릅니다 |
| 매트릭스 대응 | 해당 셀·상세 항목과 보고서 절을 연결한 목록 |
| 새 구현·셀 후보 | 대응하지 않거나 일부만 대응한 기능과 새 상세·셀 제안 |
| 별도 확인 자료 | 문서 선언 대조, 재현 환경·입력·출력, 미확인 사항 |

본문은 A~H 관찰 영역으로 묶습니다. 모든 절을 길게 쓰지는 않고, 실제 기능에 필요한 절만 길게 씁니다. 그렇다고 셀 하나를 한 줄 판정으로 끝내지는 않습니다.

기능 하나가 여러 셀에 걸치면 다음과 같이 씁니다.

- 주된 기능 절에서 흐름을 설명합니다.
- 다른 셀 절에서도 **그 셀의 관찰 목적에 해당하는 작동·예외·코드 근거**를 설명합니다.

독자가 다른 절을 읽지 않아도 해당 셀의 구현을 이해할 수 있어야 합니다.

미구현·비적용 항목은 근거와 사유를 짧게 남깁니다. 이전 질문에 없던 기능이라도, 확인하지 않은 채 미구현으로 처리하지 않습니다.

문서에 적힌 보안 선언과 실제 코드를 대조한 결과는 별도 표로 보존합니다. 중요한 불일치가 기능의 범위를 바꾸면, 해당 셀의 미비점 설명에도 그 내용을 적습니다. 다만 선언 대조 자체를 공통 구현방식 셀로 유지할 필요는 없습니다.

## 3. 코드 근거를 남기는 방식과 위치

### 3.1. 본문의 번호 표지와 셀 절 끝의 근거

보고서 작성자는 다음 순서로 씁니다.

1. 본문에서 **구현 흐름 → DFIR 의미 → 적용 범위·미비점** 순서로 설명합니다.
2. 코드, 문서, 실행 결과를 말하는 본문 문장에는 `[1]` 같은 **번호 표지**를 붙입니다. 한 근거가 여러 문장을 뒷받침하면 같은 번호를 다시 씁니다.
3. 설명이 끝난 바로 아래에 **근거** 소절을 둡니다. 근거는 표지 번호 순서로 적습니다.
4. 근거 한 항목은 다음 순서로 씁니다: 확인할 동작 한 줄, 코드 발췌, 기준 커밋이 고정된 **파일·줄 링크**. 발췌가 필요 없는 근거는 링크만 둡니다.
5. 다른 호출 경로가 예외라면, 그 예외를 보여 주는 분기나 호출에도 번호를 붙여 같은 소절에 둡니다.

이렇게 하면 긴 파일 경로와 줄 번호가 본문 문장을 끊지 않습니다. 독자는 표지 번호로 그 문장의 근거를 바로 찾을 수 있습니다.

표지는 생략하지 않습니다(2026-09-30 결정). 절 끝에 발췌만 모아 두면, 어느 발췌가 어느 문장을 뒷받침하는지 독자가 직접 짝을 맞춰야 하기 때문입니다.

중요한 사실과 결론은 발췌보다 먼저 글로 설명합니다. 코드 블록만으로 구현 설명을 대신하지 않습니다.

이 배치를 셀별로 적용한 예시는 5절에 있습니다. 5절은 실제 코드를 바탕으로 보고서를 다시 쓴 예입니다. 발췌는 해당 기준 커밋의 원문과 일치해야 합니다. 일부를 생략하거나 고친 코드를 원문 발췌인 것처럼 싣지 않습니다.

### 3.2. 발췌할 코드의 선택

**모든 주장에 근거를 남긴다는 원칙은 그대로 유지합니다.** 하지만 문장을 하나 쓸 때마다 함수 전체를 다시 붙일 필요는 없습니다. 한 발췌가 여러 문장을 뒷받침한다면, 같은 설명 절 끝에서 한 번만 보여 줍니다. 이때 그 발췌가 다루는 기능과 범위를 밝힙니다.

발췌할 때는 다음 부분을 우선합니다.

- 설정이 실제 호출에 전달되는 지점
- 입력 변환
- 허용·거부 분기
- 결과·기록 저장
- 예외 경로

긴 함수나 라이브러리 전체는 고정 커밋 줄 링크로 연결합니다. 발췌는 판단에 필요한 부분만 합니다.

**무언가가 없다는 주장(부재 주장)은 한두 줄로 입증하기 어려울 수 있습니다.** “기록하지 않는다”, “다른 경로가 없다” 같은 주장이 그렇습니다. 이런 주장에는 확인한 등록 지점, 호출 경로, 저장 구조를 설명하고, 각각에 관련 코드 링크를 붙입니다. 짧은 발췌 하나가 전체 경로를 조사한 결과까지 증명한다고 쓰지 않습니다. 부재 주장과 수치에도 표지를 붙이고, 근거 소절에 확인한 경로의 링크를 둡니다.

기준 커밋과 자료의 성격도 구별합니다. 다음 셋은 같은 수준의 근거가 아닙니다.

- 저장소 설명이나 설정 문서
- 호출 가능한 구현
- 실제 실행 확인

실행으로 확인한 사실에는 실행 환경, 입력, 출력 기록이 어디에 있는지를 함께 남깁니다.

### 3.3. 원고·게시·검사

현행 `tools/md2storage.py`는 fenced code block을 Confluence 코드 매크로로 변환합니다. 그래서 셀 아래의 코드 블록은 이 변환 경로를 그대로 쓸 수 있습니다. 다만 새 셀 제목, 배치 규칙, 근거 링크를 검사하는 부분은 현행 `check_report.py` 등과 함께 고쳐야 합니다.

보고서에 코드를 붙일 때는 다음을 확인합니다.

- 발췌가 기준 커밋의 실제 줄과 일치하는지
- 줄 링크가 같은 범위를 가리키는지

같은 기능을 여러 셀에서 서로 다른 관찰 목적으로 설명한다면, 셀마다 근거 범위를 따로 확인합니다.

새 자료 구조가 확정되기 전에는 이 형식을 현행 원고나 페이지에 기계적으로 섞지 않습니다.

## 4. 기능별 설명을 쓰는 순서

셀 절에는 연결한 상세 항목마다 소제목을 둡니다. 소제목 아래에는 **구현**과 **예외**를 나눠 씁니다. 근거는 셀 절 끝에 모읍니다(12절 25번).

1. **구현.** 그 방식이 어떤 입력, 상태, 배포 모드에서 작동하는지 씁니다. 누가 어떤 변환·검사·실행·저장을 어떤 순서로 하는지 씁니다. 응답, 파생물, 기록, 상태가 어디에 남는지도 씁니다.
2. **예외.** †를 붙인 항목에만 씁니다. 반대로 †를 붙였다면 반드시 씁니다. 그 방식이 적용되지 않는 도구, 인자, 모드, 설정을 쓰고, 확인하지 못한 범위도 씁니다.
3. **근거.** 셀 절 끝에 둡니다. 구현과 예외를 확인할 코드 조각과 고정 커밋 링크를 본문 표지 번호 순서로 놓습니다.

원고는 한 줄에 문장 하나를 쓰고, 빈 줄은 단락 사이에만 둡니다. 화면에는 그 줄바꿈이 그대로 보입니다(12절 32번).

`미구현`·`비적용` 항목에는 **판단** 단락 하나를 씁니다. 그 단락에 왜 그 항목에 넣었는지와 근거 표지를 씁니다. 그 방식의 DFIR 의미는 따로 쓰지 않습니다(12절 26번).

문단 수를 정해 두거나 최대 글자 수를 새로 강제하지 않습니다. 해당 기능에 필요한 내용을 설명하면 됩니다. 다만 다음 것만으로 구현 설명을 대신하지는 않습니다.

- “일부만”, “없음”
- 상세 항목 이름
- 함수 목록 한 줄

잘 작동하는 범위와 구현상 제약을 함께 적습니다. 예외가 결론을 바꾼다면 눈에 띄게 남깁니다. 그래도 설명을 예외 목록으로 시작해서 정상 동작 과정을 빼먹지는 않습니다. 자세한 재현 과정과 수정 제안은 확인 자료나 기여 후보로 연결합니다.

**기술과 그 기술의 의미를 구별합니다.** 예를 들면 다음과 같습니다.

- JSON 포장은 데이터를 구조화하는 것입니다. 그것만으로 프롬프트 인젝션 차단을 보장하지 않습니다.
- 해시 체인은 기록을 서로 잇는 장치입니다. 삭제나 재생성까지 탐지하는지는 따로 확인해야 합니다.
- 읽기 전용 볼륨은 해당 접근 경로로 하는 변경을 막습니다. 다른 호스트 경로까지 보호한다고 적지 않습니다.

### 5.2. mcp_dfir: 실제 실행 명령을 문자열로 기록

**연결할 상세 항목:** L02.01. 실행 경과는 L02, 도구 출력 보관은 D01에서 연결한다.

**입력과 처리.** Docker 실행 관리기는 포렌식 명령을 인수 배열로 받아 컨테이너에 실행을 요청하고 실행 중에는 stdout만 모은다 [1]. 수집이 끝나면 명령 문자열·수집한 출력·종료 코드로 `CommandRecord`를 만들어 기록 관리기에 넘긴다. 기록의 명령 문자열은 실행에 쓴 배열을 공백으로 이어 만든다 [1].

**저장과 반환.** 기록 관리기는 현재 요약 목록 길이로 번호를 정하고 `number`·`command`·`date_run`·`exit_code`를 요약 JSON에 저장한다. 출력 본문은 같은 번호의 `.txt` 파일에 쓴다. 관리기는 요약 객체를 호출한 도구에 돌려준다 [2].

이 기록은 호스트의 분석 폴더에 저장된다. 컨테이너의 `/analysis`가 읽기 전용인 설정과 호스트 서버의 파일 저장은 다른 접근 경로다.

**DFIR 효과.** 어떤 명령 문자열을 실행했는지와 그 실행에서 모은 출력을 번호로 찾아볼 자료가 남는다. 요청 기록의 표현을 비교할 때는 "명령 문자열 기록", 자료 보관을 비교할 때는 "도구 출력 파일 저장"에 각각 연결한다.

**표현상 제약.** 인수를 공백으로 합치므로 공백이 든 인수 하나와 여러 인수를 기록에서 가를 수 없다 [1]. `date_run`은 실행 뒤 `CommandRecord`를 만드는 시각이고 요약은 그 값을 복사한다 [3]. 시작 시각은 따로 남기지 않는다. 이 내용은 L02의 인수 표현 범위와 L02의 실행 경과에서 설명한다.

출력 해시의 기록·파생물과 호출의 연결은 D02의 질문으로 대조한다. 이 L02 설명에 관련 없는 누락 필드를 모두 넣어 기록 구조의 동작 설명을 가리지 않는다. Docker 실행 경로의 예이므로 전체 MCP 도구가 같은 방식으로 기록된다고 일반화하지 않는다.

### 5.3. sift-kernel: 선행 능력 상태로 호출 제어

**연결할 상세 항목:** T03.01.

**입력과 상태.** 도구 명세에는 실행에 필요한 `requires`와 성공 뒤 만들 `produces`가 있다. 예를 들어 `list_directory`는 증거 마운트와 무결성 확인 상태를 요구한다 [1]. 그래프는 현재 보유 상태를 서버 메모리의 집합으로 관리한다.

**검사 흐름.** 공통 능력 확인에 닿은 호출은 필요한 상태와 보유 집합을 대조한다 [2]. 빠진 상태가 있으면 서버가 `CAPABILITY_BLOCKED` 응답을 돌려준다. 응답에는 모자란 상태·현재 상태와 방법론 모듈의 다음 작업 추천이 들어간다 [3].

서버가 실행을 성공으로 처리하면 `produce`가 명세의 생성 상태를 보유 집합에 더한다 [4]. 이후 호출의 조건 검사는 이 갱신된 상태를 쓴다.

**DFIR 효과.** 이 경로는 앞선 준비·검증 상태를 다음 분석 호출의 허용 조건으로 잇는다. 다음 작업 추천은 P02에서, 상태 조회(`get_investigation_state`)는 P03에서 함께 관찰할 기능이다 [5].

**범위·예외.** `verify_integrity`를 뺀 커널 도구는 공통 검사 앞에서 처리되고 돌아간다. 그래서 `generate_report`는 명세에 선행 능력이 있어도 이 검사에 닿지 않는다. 자체 검사는 발견사항이 0개이고 실행 가능한 기준 도구가 남았을 때만 막는다. 마운트 전에는 기준 도구가 모두 능력이 모자라 실행 가능한 도구로 세지 않으므로 막지 못한다 [6]. 능력을 만드는 조건인 `success`도 조건을 채웠다는 뜻이 아니다. `ewfverify`가 없으면 해시를 계산하지 않는 `img_stat`이 대신 돌아 `integrity_verified`가 생기고 `list_registry_hives`는 하이브를 찾지 못해도 성공으로 끝나 능력을 만든다 [7].

같은 기능의 정상 제어 과정과 예외를 나눴다. 그래프가 있다는 사실만으로 모든 도구·증거에 조건이 걸린다고 결론 내리지 않는다.

## 6. 새 상세 항목 구조에 맞춘 셀 재편성

축, 셀, 상세 항목 후보와 현행 셀의 대응은 이 문서 10절에 모두 적었습니다.

축의 차례, 이름, 다루는 내용은 [`matrix/axes.yaml`](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/matrix/axes.yaml)에 있습니다. 셀 수는 `matrix/cells/`에 있는 파일 수와 같습니다.

셀 구성의 원본은 `matrix/cells/`입니다. 셀 구성은 12절의 다음 결정에서 바뀌었습니다.

- 36번: 옛 A~D축의 셀 30개를 목적이 같은 것끼리 합쳐 17개로 줄였습니다(공통 16개, 조건부 1개).
- 37번: 옛 E~H축의 셀 32개를 18개로 줄였습니다(조건부 없음).
- 39번: 축 글자를 축 이름의 영어 첫 글자로 바꾸고, 셀 번호도 그에 맞췄습니다.
- 41번: 성격이 다른 질문이 섞여 있던 셀 6개를 나눴습니다.

셀을 나누고 합칠 때는 다음 원칙을 지킵니다.

- 성격이 다른 질문은 한 셀로 합치지 않습니다.
- 셀 하나는 질문 하나입니다. 구현인지 미구현인지는 그 셀의 질문을 기준으로 판단합니다.
- 세부 방식의 차이는 상세 항목으로 남깁니다.
- 셀 수를 맞추려고 셀을 추가하거나 삭제하지 않습니다.

새 표는 `관찰 셀 → 상세 항목 정의 → 해당 프로젝트 → 보고서 구현 절 → 근거` 순서로 연결합니다. 셀을 판정형·택일형·목록형으로 나누던 구분은 쓰지 않습니다. 구현 위치를 따로 적는 필드도 쓰지 않습니다. 적용 모드, 담당 구성 요소, 예외는 실제 동작을 설명하는 글 안에 남깁니다.

**구현이 없는 프로젝트도 항목에 넣습니다(2026-09-30 결정).** 그래서 모든 프로젝트가 셀마다 한 항목 이상에 나타납니다. 프로젝트는 상황에 따라 다음 항목에 넣습니다.

- `미구현`: 셀의 어느 구현 방식에도 해당하지 않는 프로젝트
- `비적용`: 그 셀의 전제가 되는 일을 하지 않는 프로젝트
- `미확인`: 아직 조사하지 않은 프로젝트

상태, 적용 주체, 요약 같은 별도 필드는 두지 않습니다. 같은 일이라도 그 일을 하는 주체가 달라서 방식이 달라지면 상세를 나눕니다. 여기서 주체는 서버 코드, 실행 환경, 클라이언트, 백엔드를 말합니다.

**표본이 없는 후보 항목은 정의만 둡니다(2026-09-30 결정).** 지금 표본 가운데 해당하는 곳이 없는 항목은 상세 항목 정의에만 남깁니다. E02의 분할·논리 범위 해시가 그 예입니다. 이런 항목은 해당하는 표본이 생기면 매트릭스에 나타납니다.

**정보의 성질을 유지합니다.** 상세 항목이 될 수 있는 것은 구현 방식만이 아닙니다. 기록 내용, 전달 범위, 상태 표현도 상세 항목이 될 수 있습니다. 그러니 모든 셀에 같은 종류의 방법 이름을 억지로 넣지 않습니다. 한 프로젝트가 같은 셀의 여러 상세에 연결되어도 됩니다.

### 6.1. 재편성의 주요 변경

현행 셀의 내용이 새 구조에서 어디로 옮겨 갔는지는 다음과 같습니다.

기능 발견 원칙도 그대로 적용합니다. 새로 발견한 기능을 현재 셀에 억지로 넣지 않는다는 원칙입니다.

### 6.2. 상세 항목 정의

상세 항목 정의의 원본은 `matrix/cells/<ID>.mdx`입니다. 12절 31번에서 정한 "유일한 원본"을 이 파일로 옮겼습니다. 정의를 쓰지 않은 셀에는 상세 이름만 있습니다.

**†의 뜻(12절 28번).** †는 보고서의 **구현** 단락에 적은 적용 범위 **안에서** 그 방식이 적용되지 않는 경우에만 붙입니다. 다음 경우가 여기에 해당합니다.

- 우회 경로
- 설정이나 인자로 끄는 경우
- 오류가 났을 때 통과시키는 경우
- 설명과 다르게 동작하는 경우
- 확인하지 못한 경로

반면 그 방식이 서버의 어느 도구나 경로에 있는지는 **구현** 단락 첫머리에 적고, †로 표시하지 않습니다. 적용 범위는 셀마다 표 위에 적습니다.

표시와 안내는 모델이 읽을 정보를 더할 뿐이고, 차단이 아닙니다. 표본 예는 [셀 검토 자료](cell-review-2026-09-30.mdx)의 E08 메모(지금의 R07)에 있습니다(TheHiveMCP·Camel은 판정 전 코드 확인).

고정 커밋 코드 대조(2026-09-30): Camel의 Execute는 스크립트가 log 등으로 쌓은 문자열을 텍스트 content 블록으로 돌려줍니다. 여기에 별도의 감사 식별 블록을 붙입니다. 서버가 증거 문자열을 JSON 필드로 자동 포장하거나, 신뢰할 수 없다고 표시하는 경로는 확인되지 않았습니다. 호출 스크립트가 직접 JSON 문자열을 출력하는 경우는 서버의 R07.01 구현으로 인정하지 않습니다([MCPServer.cs:230-259](https://github.com/allisterb/Camel/blob/63f4cb2e26a2469a35f847bee607516cf6184e91/src/Camel.Server/MCPServer.cs#L230-L259), [MCPServer.cs:399-403](https://github.com/allisterb/Camel/blob/63f4cb2e26a2469a35f847bee607516cf6184e91/src/Camel.Server/MCPServer.cs#L399-L403)).

trudi에서는 미들웨어가 결과를 증거 결과로 분류하면, 그 dict의 _metadata에 data_provenance와 discipline_reminder를 붙입니다. discipline_reminder는 순환하며 바뀝니다. 그리고 구조화 결과와 텍스트 블록 하나의 내용을 동기화합니다([_enrich.py:28-60](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/tools/_enrich.py#L28-L60), [_enrich.py:75-103](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/tools/_enrich.py#L75-L103), [middleware.py:786-833](https://github.com/nebulae/trudi/blob/88fbca78186b6a0ca40423cf5e37a9dc46ae051e/core/middleware.py#L786-L833)).

안내문은 다섯 종류이고, 그 가운데 증거 속 지시를 무시하라는 문구는 하나입니다. 그 문구가 매 호출에 나오지는 않습니다. 이 문서는 trudi를 다음 상세로 분류합니다.

- R07.01·R07.02
- 그 문구가 붙는 호출에 대해서는 R07.05

다만 문구를 읽는 모델의 행동이나 공격 문구 차단을 보장한다고 적지는 않습니다. dict가 아닌 반환값과 enrich 예외 경로에서는 표시가 빠질 수 있습니다.

mulder도 선택적 Docker 경로로 실행할 때는 E03.01에 연결할 수 있습니다. 이때는 지원 경로와 조건을 보고서에 남깁니다. 이 보호가 네이티브 모드에도 있다고 넓혀 해석하지 않습니다.

위 상세들은 기능을 묶는 후보입니다. 모든 프로젝트가 이 항목을 전부 쓰는 것은 아닙니다. 미구현·비적용·미확인과 실제 예외 사유는 보고서나 프로젝트 연결 자료에 남깁니다. 이름이 비슷하다는 이유로 연결하지 않습니다.

### 6.3. E03의 프로젝트 연결 시범

이 표는 현행 C4 판정의 연결 사례를 새 상세 ID로 옮겨 적은 것입니다. 프로젝트 전체의 새 분류를 확정한 결과는 아닙니다.

12절 36번에서 옛 상세 7개를 주체별로 3개로 합쳤습니다. 그래서 포함 기준 칸에 옛 상세 이름을 남겼습니다. †의 뜻은 6.2절 첫머리에 적었습니다(12절 28번).

| 상세 항목 | 포함 기준 | 프로젝트 예시 |
|---|---|---|
| E03.01 실행 환경의 읽기 전용 강제 | 컨테이너 증거 볼륨의 읽기 전용 마운트: 분석 컨테이너가 접근하는 증거 볼륨에 읽기 전용 제약을 적용. 증거 파일시스템의 읽기 전용 마운트: 실제 증거 접근에 사용하는 파일시스템을 읽기 전용으로 마운트 | mcp_dfir†, mulder†, ChainsawMCP†, trudi† |
| E03.02 서버 코드의 원본 쓰기 제한 | 접근 API의 읽기 전용 모드: 파일·DB를 여는 API에서 읽기 전용 모드를 지정. 출력 대상 검사: 생성·수정 대상이 원본 증거·원본 영역과 겹치는지 검사하고 겹치면 거부. 원본과 작업 입력의 분리: 해당 분석 경로가 원본에서 만든 파일·메모리 사본을 작업 입력으로 사용 | regipy, mulder†, trudi†, MyIRTeam† |
| E03.03 외부 도구·플랫폼에 위임 | 외부 도구에 의존: 읽기만 하는 외부 도구·라이브러리에 원본 보호를 맡김. 외부 플랫폼 권한에 위임: 플랫폼 계정 권한에 원본 보호를 맡김 | ChainsawMCP†, sift-kernel†, agentic-velociraptor-mcp† |

한 프로젝트가 여러 상세에 들어갈 수 있습니다.

mulder의 Docker 증거 볼륨은 선택적인 실행 경로입니다. [README의 Docker 실행](https://github.com/calebevans/mulder/blob/3164843baf74c7fe69e7121dbd6150f8f77ce660/README.md#L65-L82)과 [Makefile 실행 대상](https://github.com/calebevans/mulder/blob/3164843baf74c7fe69e7121dbd6150f8f77ce660/Makefile#L66-L70)을 확인합니다. 네이티브로 실행할 때는 같은 제약이 자동으로 적용되지 않습니다.

sift-kernel은 E03.02에 넣지 않고, E03.01에도 자동으로 연결하지 않습니다. 이유는 다음과 같습니다.

- E03.02: 출력 폴더를 정하지만, 그 폴더가 원본 증거와 겹치는지는 검사하지 않습니다.
- E03.01: 원시 이미지를 읽기 전용으로 마운트하려고 시도하지만, 실패하면 직접 읽기 경로로 바뀝니다. 또 그 마운트 지점이 후속 분석의 입력인지 따로 확인해야 합니다([server.ts:1644-1679](https://github.com/Sathvik-1007/sift-kernel/blob/ea51bec90d4cb543e4aa6063af6e85ae3e4d9396/src/server.ts#L1644-L1679)).

agentic-velociraptor-mcp는 E03.03에 넣고 예외 표시(†)를 붙여 둡니다. 원본 보호를 Velociraptor 계정 권한에 맡기는 구조는 코드로 확인됩니다. 하지만 계정 권한이나 아티팩트가 실제로 원본 변경을 막는지는 확인되지 않았습니다(실제 보호 미확인). read_only 정책과 변경 RPC 제한은 T02의 작업 제어에서도 살펴봅니다.

작업 입력 분리를 근거로 E03.02에 연결하려면, 그 분리가 어디까지 적용되는지 확인되어야 합니다. 사본을 만들었다는 것만으로 다른 도구가 원본에 쓰는 경로까지 제한되었다고 판단하지 않습니다. sift-kernel의 읽기 전용 마운트 시도도 마찬가지입니다. 실제 분석 경로가 그 마운트를 사용하지 않으면 이 표의 마운트 방식에 연결하지 않습니다.

### 6.4. 용어

- **셀**은 관찰 질문 하나입니다.
- **셀 이름**은 그 셀이 묻는 일을 명사로 씁니다.
- **상세 항목**은 그 질문에 답하는 구현 방식입니다. 줄여서 "상세"라고도 씁니다. 프로젝트는 상황에 따라 다음 항목에 둡니다.
  - `미구현`: 방식이 없는 프로젝트
  - `비적용`: 전제가 없는 프로젝트
  - `미확인`: 조사하지 않은 프로젝트
- **참조 자료**는 분석 도구가 실행 중에 읽는 자료입니다. 룰, 시그니처, 심볼, 플러그인, 매핑, 지식 시트가 여기에 해당합니다. 컨테이너 이미지는 참조 자료가 아니라 실행 파일 쪽에 둡니다.
- **파생물**은 서버나 도구가 만든 파일과 자료입니다. D08의 보고서만 "보고 산출물"이라고 부릅니다.
- **해시**라는 말은 실제로 해시일 때만 쓰고, 무엇을 해시했는지 함께 적습니다(파일 내용, 요청 필드, 파일 상태값). 심볼 GUID나 룰 커밋처럼 해시가 아닌 식별자는 "식별값"이라고 씁니다. "지문"이라는 말은 쓰지 않습니다.
- **manifest**는 파일 목록과 파일마다의 해시·출처를 적은 목록 파일입니다.
- flow·label(Velociraptor), digest(컨테이너 이미지), namespace(Linux), cursor는 영어 원어 그대로 씁니다.
- **외부 도구**는 MCP 서버가 실행하거나 불러 쓰는 포렌식 프로그램과 라이브러리입니다(Sleuth Kit, Chainsaw, pytsk3 등). MCP가 노출하는 도구(tool)와 구별합니다.
- **대상 시스템**은 조사 대상인 살아 있는 단말이나 서버입니다. 증거 사본이나 이미지가 아닙니다(T09).
- 옛 C06의 "부속 자료"와 "입력 일관성"은 E04의 상세 이름에 그대로 씁니다.
- 현행 49셀의 이름(B1 "호출자 신원 확인" 등)과 기존 원고에서 가져온 관찰 제목(10.6절 V5 등)은 이 문서에서 바꾸지 않습니다. 현행 규격과 원고의 표기이기 때문입니다. 이 절의 용어는 원고를 새 구조로 다시 쓸 때 적용합니다.

## 7. 기능 발견, 보고서, 매트릭스를 잇는 자료

### 7.1. 기능을 먼저 조사합니다

**프로젝트를 조사할 때 지금 있는 셀과 상세 항목 목록 안에서만 찾지 않습니다.** 프로젝트가 실제로 가진 기능을 먼저 모두 찾고, 그 뒤에 셀에 대응시킵니다. 이 원칙은 현행 규격 35절의 기능 목록 원칙을 이어받은 것입니다.

조사자는 기준 커밋과, 그 커밋의 다음 항목을 먼저 읽습니다.

- 진입점
- 도구, 리소스, 프롬프트
- 설정
- 내부 처리기
- 공식 실행 스크립트

그다음 아래 순서로 조사합니다.

1. 지원하는 배포 모드, 설정, OS, 증거 형식, 대체 실행 경로를 확인합니다.
2. 의미 있는 사용자 기능, 상태 관리, 보호 장치를 하나씩 보며 각각의 입력, 처리, 출력과 파생물, 상태 변화를 적습니다.
3. 다음 세 가지를 서로 구별해 적습니다. 코드가 선언한 기능, 실제 호출 경로에 연결된 구현, 실행해서 확인한 결과입니다.
4. 기능의 동작마다 기존 셀과 상세 항목을 대응시킵니다. 한 기능을 여러 셀에 연결할 수 있습니다.
5. 기능의 일부만 기존 셀에 담기면, 남은 동작과 근거를 버리지 않고 보존합니다. 그리고 그 나머지를 새 상세나 새 셀 후보로 검토합니다.
6. 기능 목록, 보고서, 매트릭스 연결을 서로 대조해 빠진 것이 없는지 확인합니다. 분석하다가 새 기능을 발견하면 기능 목록에도 추가합니다.

공개된 도구 이름만 읽고 조사를 끝내지 마세요. 도구 이름 뒤에서 실제로 일어나는 일까지 확인합니다.

- 요청 인수를 어떻게 변환하는지
- 서버 내부에서 분석, 추천, 오케스트레이션을 하는지
- 기록, 파생물, 상태를 만들거나 지우거나 초기화하는 동작
- 비동기 작업이 끝나는 방식
- 증거를 교체하는 동작
- 실패했을 때의 경로

### 7.2. 새 상세와 새 셀은 어떻게 나누나요?

| 발견 | 처리 |
|---|---|
| 기존 셀의 목적과 상세의 포함 기준에 맞음 | 기존 상세에 연결합니다. 실제로 작동하는 모드와 범위, 예외는 프로젝트 보고서에 적습니다 |
| 목적은 같지만 방식·대상·DFIR 효과가 다름 | 그 셀의 새 상세 항목 후보로 둡니다 |
| 기능 일부만 기존 셀에 대응함 | 대응하는 부분만 연결합니다. 남은 동작은 별도 후보로 보존합니다 |
| 현재 어느 셀도 묻지 않는 DFIR 기능임 | 다른 프로젝트에도 물을 수 있는 질문으로 다듬어 새 셀 후보로 둡니다 |
| 기존 셀 하나에 목적이 여럿 있어 각각 다른 설명이 필요함 | 셀 분리, 이름 변경, 범위 조정 후보로 둡니다 |
| 여러 셀이 겹쳐 같은 목적을 반복함 | 병합 또는 경계 조정 후보로 둡니다 |
| 문서에만 있거나 호출 경로가 확인되지 않음 | 어느 상세에 속하는 구현인지 정하지 않고, 확인할 사항으로 남깁니다 |

프로젝트가 붙인 고유 명칭을 셀 이름으로 그대로 쓰지 않습니다. 이름이 아니라 동작을 기준으로 나눠서 봅니다. 예를 들어 sift-kernel의 capability graph는 셀 하나로 다루지 않고, 동작별로 네 셀에서 분석합니다.

| 동작 | 셀 |
|---|---|
| 선행 상태에 따라 호출을 거부함 | T03 |
| 다음 작업을 추천함 | P02 |
| 상태를 조회하고 단계를 표시함 | P03 |
| 능력 상태가 요청이나 재시작 사이에 남는지 | P04 |

graph라는 이름을 발견했다고 해서 T03 조사를 끝내지 않습니다. 그 이름 때문에 새 셀을 자동으로 만들지도 않습니다.

후보는 한 프로젝트에서만 나와도 기록해 둡니다. 둘 이상의 표본에서 되풀이되는지는 후보를 남길 조건이 아니라, 정의를 다듬을 때 참고하는 자료입니다.

새 정의를 채택하면 기존 프로젝트에도 그 정의가 적용되는지 다시 확인합니다. 이때 아직 조사하지 않은 기존 프로젝트를 미구현으로 바꾸지 않습니다.

### 7.3. 상세 항목과 프로젝트 연결

상세 항목의 **이름, 하는 일, 포함·제외 기준**은 한 곳에서 한 번만 정의합니다. 프로젝트 연결은 그 정의를 다시 쓰지 않고, 다음을 가리키기만 합니다.

- 해당 상세 ID
- 보고서 절
- 기준 커밋
- 적용 조건
- 중요한 예외

매트릭스 화면에는 프로젝트 이름만 나열합니다. 적용 범위 안에 예외가 있으면 이름 옆에 †를 붙입니다(6.2절 머리).

한 프로젝트가 같은 셀의 여러 방식에 해당하면 모두 연결합니다. 기본 모드만 보지 말고, 저장소가 지원하는 Docker, 설정, OS, 증거 종류, fallback 경로도 포함합니다.

반대로 다음은 구현 목록에 연결하지 않습니다.

- 작동하지 않는 설정 조각
- 호출되지 않는 함수
- 운영자가 임의로 만든 배포

**미구현, 비적용, 미확인을 구별합니다.** 셋은 각각 셀 안의 별도 항목으로 둡니다(6절).

- 일부 모드에서만 방식이 작동하면, 해당 상세에 연결합니다. 다른 모드에서 빠진 부분은 보고서에 남깁니다.
- 문서에 주장만 있고 코드와의 연결을 확인하지 못했으면, 구현으로 확정하지 않습니다. 문서 대조나 미확인으로 다룹니다.

매트릭스 셀에는 프로젝트별 긴 설명을 다시 쓰지 않습니다. 실제 구현과 미비점은 보고서의 셀 절에서 설명하고, 그 바로 아래에 코드 발췌를 보여 줍니다.

참고: 두 프로젝트가 같은 이름의 방식에 연결돼 있어도, 보호하거나 추적하는 수준까지 같다는 뜻은 아닙니다.

### 7.4. 새 구현이 빠지지 않았는지 점검하기

- 진입점, 공개 기능, 지원 모드와 중요한 내부 장치가 기능 목록에 들어갔나요?
- 기능의 입력, 처리, 출력, 상태 변화 가운데 DFIR에 영향을 주는 동작을 기록했나요?
- 기존 셀과 맞는 부분, 셀에 담기지 않고 남은 동작, 확인하지 않은 부분을 각각 어디에 적었는지 분명한가요?
- 대응하는 셀이 없는 구현을 버리지 않고 보존했나요? 보존 방법은 후보, 축 밖 구현 관찰, 단순 기능 기록 중 하나입니다.
- 구현 방식과 중요한 미비점을 보고서에서 각각 설명했나요?

**셀을 모두 채웠다고 해서 기능을 모두 찾았다는 뜻은 아닙니다.** 매트릭스가 표현하지 못한 실제 구현은 축 밖 관찰에 적고, 그 구현이 DFIR에서 갖는 의미도 함께 적습니다.

미비점은 해당 구현을 설명하는 절에 남깁니다. 축 밖 관찰을 결함 목록처럼 쓰지 않습니다.

### 7.5. 표준 요건으로 옮길 때

어떤 방식을 쓰는 프로젝트가 많다고 해서 그 방식이 더 안전하다고 보지 않습니다. 방식별 프로젝트 수는 안전성 순위가 아닙니다. 표준 요건으로 옮길 때는 상세 항목이 지키려는 DFIR 성질과, 그 성질이 깨지는 반례를 따로 정합니다.

예를 들어 E03.01의 읽기 전용 증거 볼륨을 표준 요건으로 검토한다면, 다음도 함께 확인합니다.

- 컨테이너 밖에서 증거에 접근하는 경로
- 기존 컨테이너를 다시 쓰는 경우
- 보호가 실패한 뒤의 처리

기능 목록, 상세 항목, 보고서 연결은 한 원본에서 함께 관리해도 됩니다. 다만 **개편 논의 문서는 이 파일 하나에서 갱신합니다.** 새 항목이 생길 때마다 개편안 파일을 따로 만들지 마세요.

## 8. 실제 전환에 필요한 규격·도구 변경

| 대상 | 바꿀 내용 |
|---|---|
| 규격·작업지침·문장 기준 | 새 규칙을 넣습니다. 셀마다 설명을 먼저 쓰고, 마지막에 실제 코드 발췌와 고정 커밋 링크를 둡니다. 현행의 "판정 한 줄 우선" 규칙도 갱신합니다 |
| 상세 항목 정의 자료 | 셀 목적, 포함·제외 기준, 상세 ID, 변경 이력을 관리합니다 |
| 현행 경계 규칙 | 셀을 검토할 때 `규칙적용표.yaml` 88개와 규격 17~39절의 판정 규칙을 대조합니다. 새 셀과 상세의 포함·제외 기준에 맞는 규칙만 옮깁니다. 맞지 않는 규칙은 옮기지 않은 사유를 남깁니다 |
| 프로젝트 연결 자료 | 확인한 상세, 보고서 절, 근거, 모드, 예외를 연결합니다. 옛 판정 값을 보고 어느 상세에 속하는지 자동으로 추정하지 않습니다 |
| 보고서 골격 | 기능 흐름, DFIR 효과, 범위, 미비점을 쓴 뒤 코드 발췌를 배치하고 새 구현 후보를 남깁니다 |
| 근거 검사 | 네 가지를 확인합니다. 코드 발췌가 고정 커밋 원문과 같은지, 줄 링크 범위가 맞는지, 본문 번호 표지와 근거 항목이 짝을 이루는지, 코드를 말하는 문장에 표지가 빠지지 않았는지입니다 |
| 보고서 검사 | 고정된 49개 제목과 첫 문장을 복사했는지는 더 보지 않습니다. 대신 기능 설명, 상세 항목, 코드 근거가 서로 맞는지 확인합니다 |
| 매트릭스 생성기 | 기존 판정 값 대신, 상세 항목마다 해당 프로젝트 목록을 만들어 표시합니다 |
| Markdown·Confluence 변환 | 셀 안의 fenced code block을 Confluence 코드 매크로로 옮깁니다. 링크와 제목은 그대로 유지합니다 |
| 검토 절차 | 사람 검토자가 확인합니다. 구현 설명이 충분한지, 중요한 예외가 있는지, 새 기능이 빠지지 않았는지 봅니다 |

바꾸는 순서는 다음과 같습니다.

1. 규격, 정의, 소속 자료(프로젝트가 어느 상세에 속하는지 적은 자료)를 먼저 정합니다.
2. 그다음 보고서, 검사기, 생성기를 함께 바꿉니다.

주의: 기존 검사기를 새 형식의 원고에 그대로 돌린 뒤 통과했다고 선언하면 안 됩니다.

시범 전환에는 E03, L02, T03, R02처럼 성격이 서로 다른 셀을 고릅니다. 표본도 그 기능을 가진 프로젝트 여러 개를 씁니다. 고른 예 하나에 맞춰 상세 항목 정의를 굳히지 않습니다. 새 정의에 해당하는지 아직 살펴보지 않은 기존 프로젝트는 미확인으로 남깁니다.

## 9. 개편 후 검토 기준

- 보고서 본문만 읽고도 기능의 목적, 입력, 처리, 출력, 적용 범위를 설명할 수 있나요?
- 정상 동작과 DFIR 효과를 먼저 설명하고, 그 뒤에 중요한 예외와 한계를 적었나요?
- 본문 문장의 번호 표지를 따라가 근거를 찾을 수 있나요? 근거는 코드 발췌와 고정 링크입니다. 그 근거로 구현과 예외가 어디까지 뒷받침되는지 확인할 수 있어야 합니다.
- 소스 코드에서 본 것, 문서에서 본 것, 실행해서 확인한 것, 추론한 것을 서로 구별했나요?
- 상세 정의가 실제 프로젝트의 구현, 모드, 보고서와 맞나요?
- 어느 셀에도 대응하지 않은 기능도 기록했나요? 일부만 대응한 기능이라면 대응하지 않은 나머지 동작도 기록했나요?

링크 수, 문장 수, 셀 충족률은 위 점검을 대신하지 못합니다. 이런 숫자를 지표로 쓰지 마세요. 구현이 없는 기능의 설명을 늘리거나, 미비점만 모아 보고서를 길게 만들 필요도 없습니다.

## 10. 전체 셀 구성과 현행 항목 대응

이 절에 나오는 상세 이름은 프로젝트끼리 비교할 구현과 기록 특성의 후보입니다. 모든 프로젝트가 어느 상세에 속하는지 새로 확정한 목록은 아닙니다.

셀마다 질문과 상세 후보는 `matrix/cells/<ID>.mdx`에 있습니다. 시범 셀(E03·T03·R02·L02)과 R07은 포함 기준까지 정의해 두었습니다. 필요하면 새 셀이나 상세를 추가하고, 나누거나 합칩니다.

### 10.1. 축과 셀

셀마다 질문, 상세 후보, 다른 셀과의 경계 설명은 [`matrix/cells/`](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/tree/main/matrix/cells)의 `<ID>.mdx`에 있습니다. 축의 순서는 [`matrix/axes.yaml`](https://github.com/Trace2Bac/dfir-mcp-architecture-matrix-v2/blob/main/matrix/axes.yaml)을 따릅니다. 화면에서 보려면 빌드한 매트릭스를 확인하세요.

두 축은 구성을 따로 설명합니다.

- **T 도구 실행 통제.** 실행 전 검사와 실행 과정을 한 축으로 합쳤습니다(12절 38번).
  - T01~T03: 모델이 고른 호출을 서버가 실행하기 전에 하는 검사
  - T04~T09: 실제로 도구를 실행하는 과정(T09는 조건부)
- **D 파생물 관리.** D01·D03·D04는 E축과 같은 구조로, 각각 E축 셀과 짝을 이룹니다.
  - D01 ↔ E01(등록)
  - D03 ↔ E02(무결성 검증)
  - D04 ↔ E03(원본 변경 방지)
  - D02는 파생물을 입력, 실행과 잇는 계보를 봅니다.

### 10.2. 지원 기능에 따라 관찰할 셀

조건부 셀은 특정 기능이 있는 서버에서만 관찰하는 셀입니다. 셀 파일에 `conditional: true`로 표시하고, `applies_to`에 적용 범위를 적습니다. 다만 그 기능이 없는 서버를 비적용으로 구분할 수 있다면 조건부로 두지 않습니다(결정 0009).

다음 옛 셀은 별도 셀로 두지 않고 다른 셀의 상세로 옮겼습니다.

- 옛 B07(원격 호출자 인증)은 T03의 상세 T03.09·T03.10으로 옮겼습니다(12절 36번).
- 옛 C07(수집 관리)은 E01의 수집 상세와 T08의 수집 작업 상태로 옮겼습니다(12절 36번).

### 10.7. 새 프로젝트나 새 기능을 추가할 때

다음 순서로 진행합니다.

1. 기능 목록을 만듭니다.
2. 각 기능의 DFIR 의미를 적습니다.
3. 기존 셀과 상세에 대응시킵니다.
4. 남은 동작을 정리하고 새 후보를 적습니다.
5. 빠진 것이 없는지 점검합니다.

대응하는 셀이 없거나 일부만 대응하면, 그 구현을 보고서와 후보 기록에 남깁니다. 한 표본에서만 발견한 기능도 후보로 등록합니다.

새 정의를 채택하면 기존 프로젝트를 다시 대조합니다. 이전 질문에 없던 기능이라면, 다시 확인하기 전에는 미구현으로 처리하지 않습니다. 자세한 추가 절차는 이 문서의 7절을 따릅니다.

### 10.8. 남은 일

**관점 묶기(2026-10-01, 결정권자: 할 일로만 둔다).**

셀 하나가 여러 질문을 함께 묻는 경우가 있습니다. 예를 들어 E02는 언제 해시하는지와 어디까지 해시하는지를 함께 묻습니다. 한 서버가 여러 상세에 들어갈 수 있으므로, 이것만으로 셀을 나눌 필요는 없습니다. 하지만 두 질문의 항목이 한 목록에 섞이면 문제가 생깁니다. 한 사실이 두 항목에 걸치거나, 어느 항목에도 맞지 않게 됩니다.

그래서 셀 안에 "관점"을 두자는 제안이 나왔습니다. 관점은 셀이 묻는 하위 질문 하나입니다. 제안 내용은 다음과 같습니다.

- 셀의 항목을 관점 아래에 묶습니다.
- 서버는 관점마다 한 항목 이상(또는 관점 단위 `미구현`·`비적용`)에 해당하게 합니다.
- 관점들이 셀의 전제를 공유하면 관점으로 둡니다.
- 한 관점에만 따로 전제가 있어서, 많은 서버가 그 관점에서만 비적용이 된다면 셀을 나눕니다.

12절 36번에서 A~D축을 합친 뒤로 관점이 더 많아졌습니다. 같은 결정에서, 구현·미구현은 셀의 질문에 대해서만 판단하기로 했습니다. 따라서 관점 단위 `미구현`·`비적용`은 두지 않습니다. 관점은 상세를 묶어 읽기 쉽게 하는 용도로만 씁니다.

### 13.1. 유지할 관찰 질문

**결론: 현재 질문을 통째로 삭제할 근거는 없습니다.** 축마다 셀들이 서로 다른 목적을 묻고 있습니다. 아래에서 축별로 정리합니다.

**A축과 B축.**

- A01/A02는 대상 유형을 판별하는지, 선택한 분석 방법에 입력이 적합한지 검사하는지를 묻습니다.
- A03/A04는 다음 작업을 어떻게 결정하는지, 수행 범위와 완료를 어떻게 판단하는지를 묻습니다.
- B01~B06은 차례로 작업 권한, 도구 활성화, 조치 승인, 입력·환경 준비, 선행 조사 상태, 실행 연산 제한을 묻습니다.
- B07은 살아 있는 대상에 대응 조치를 하는 서버에만, B08은 원격 MCP 호출자 인증에만 조건부로 둡니다.
- B08에는 백엔드 접속 자격증명 관리를 섞지 않습니다. stdio 서버에 별도 인증이 없다는 사실도 B08에 섞지 않습니다.

**C축과 D축.**

- C01~C07은 증거 등록, 해시 계산, 변경 대조, 원본 변경 방지, 읽기 범위, 입력 준비, 부속 자료 반영을 묻습니다. 모두 서로 다른 동작입니다.
- C02의 **해시를 얻음**과 C03의 **기준값과 다시 대조함**은 합치지 않습니다.
- C08은 수집·헌트 기능이 있을 때만 엽니다.
- D01/D02는 실행 호출 방식과 격리를 봅니다.
- D03/D04/D05는 차례로 실제 버전을 확인하는지, 그 버전을 해당 실행과 연결하는지, 기준값과 대조하는지를 봅니다.
- D06/D07은 종료 상태 판별과 재실행 자료 보존을 봅니다.

**E~H축.**

- E01~E09는 출력 가공, 대량 전달, 상태 통지, 출처 표기, 출처 재조회, 파생물 정보 전달, 시간 표현, 증거 텍스트와 지시의 구분, 해석 주의를 묻습니다. 각각 별개의 질문입니다.
- E04와 E05의 경계: E04는 식별자를 **표기**하는지, E05는 그 식별자로 **재조회**할 수 있는지를 봅니다.

- F01~F06은 기록 범위, 경과, 요청 내용, 기록 실패, 입출력 연결, 기록 무결성을 묻습니다. 이들도 서로 구분할 수 있습니다.
- G01~G05는 차례로 목적지, 연동 활성화, 전송 내용, 실행 도구의 통신 제약, 외부 요청 기록을 봅니다.

| D06·E03·F02 | 비동기 시작 응답이나 실행기 종료 코드만으로 최종 완료라고 보지 않습니다. D06에 항목을 추가합니다. 러너가 사라지거나 시간이 초과된 뒤 하위/원격 작업의 최종 상태를 확인하는지 봅니다. 그 사실이 E03 응답과 F02 기록에 있는지는 따로 봅니다. |
| E02 | 현재 상세는 상한과 전체 건수 위주여서 **상한 초과 시 거부**(mcp_dfir)와 **값 하나를 잘라 반환**(regipy)을 담기 어렵습니다. 초과 거부, 값 단위 잘림, 잘림·생략 고지를 상세 후보로 더합니다. 두 표본의 옛 E2 비적용 판정을 그대로 옮기지 않습니다. |
| E05 | 별도 검증 도구 연계는 결과 식별자로 **같은 출처·범위**를 찾아 대조할 때만 포함합니다. 도구를 다시 실행할 수 있다는 일반적인 가능성은 재조회 기능이 아닙니다. |
| E08 | JSON 필드는 겉으로 분리돼 보일 뿐, 신뢰 불가 표시나 차단이 아닙니다. 경계 태그, 위조 무력화, 무시 안내, 내용 차단은 효과 수준이 다르므로 섞어서 하나로 보지 않습니다. 증거 문자열이 서버의 추천 규칙을 바꾸는 경로는 A03의 규칙 입력·오탐 경로에 적습니다. |
| F01~F06·H06 | F01은 기록이 없으면 미구현입니다. F02/F03/F04/F06은 기록이 있어야 물을 수 있는 셀입니다. 기록이 없으면 전제가 없다는 것을 일관되게 표시하되, 그 표시가 F01의 미구현을 가리지 않게 합니다. F05는 응답·파생 결과의 입출력 관계도 묻습니다. 그래서 기록이나 사건 DB가 없다는 이유만으로 비적용으로 옮기지 않습니다. H06의 기록 저장 실패는 F04와 겹치므로 **원래 출력·파생물·보고 산출물 저장 실패**로 좁힙니다. |
| G04·G06 | 로컬 참조 자료를 쓴다는 사실만으로 도구 통신이 제한됐다고 보지 않습니다. G04에는 실제 네트워크 차단, 오프라인 옵션, 목적지 강제를 넣습니다. G06은 **추출 민감정보의 노출 제어**와 **서버 자격증명의 저장·주입·기록 제거**를 섞고 있으므로 두 셀로 나누는 편이 낫습니다. |
| H10 | **보고 내용 구성**과 보고 파일의 **서명·HMAC 봉인 및 재검증**은 성질이 다릅니다. 서명·봉인은 H10 구성 상세에서 뺍니다. 대신 실제 봉인 기능이 있는 서버에 적용하는 별도 조건부 셀을 제안합니다(셀 검토 자료 S8). |

다음 상세는 포함 기준에 **효과의 수준**도 적습니다.

- **B03 승인 인자 검사:** 확인 인자를 모델이 같은 요청 안에서 참으로 채울 수 있다면, 그것은 별도 승인자의 동의를 확인하는 것과 다릅니다. 승인을 누가 만드는지, 어디에 보관하는지, 요청 내용과 묶이는지, 다시 쓸 수 있는지를 구분합니다. **B01 백엔드 권한**도 계정의 실제 권한이 확인된 경우에만 연결합니다.
- **C04 읽기 전용 접근 API:** 서버 라이브러리가 읽기 모드로 여는 경로와, 운영체제나 마운트가 쓰기를 거부하는 경로를 별도 상세로 유지합니다. 한 경로의 보호를 다른 경로로 넓혀 해석하지 않습니다.
- **D07 분석 상태 저장·복원:** A05를 채택하면 상태의 저장, 수명, 복구는 A05로 옮깁니다. D07은 같은 분석을 재실행하는 데 필요한 실제 입력, 설정, 모델 판단 자료를 보존하는지에 집중합니다.
- **F06 일련번호·외부 기준점:** 단순한 연속 번호만으로는 삭제, 재생성, 전체 교체를 탐지한다고 볼 수 없습니다. 외부에 고정한 기준점이나 독립 검증과 구분합니다.
- **H09 사람 검토, H11 한정된 부재 결론:** 검토자에게 보여 주기만 하는 기능과, 검토 전에는 발견사항이 확정되지 않도록 막는 게이트를 구분합니다. 서버가 범위나 누락을 검사하지 않고 결론에 한정 문구만 붙인다면, H11의 범위 검사 구현으로 인정하지 않습니다. 이런 경우는 보고 표현으로 기록합니다.

상세를 나누고 표시할 때는 다음을 따릅니다.

- **서로 독립된 특성은 한 프로젝트가 여러 상세에 속할 수 있게** 둡니다. 예를 들어 C02의 해시 시점(자동/요청)과 범위(전체/부분), C03의 대조 값과 대조 시점이 그렇습니다.
- 미구현, 비적용, 미확인은 매트릭스에 남깁니다. 다만 구현 방식과 구별되는 **별도 행**으로 보이게 합니다. 상태 필드를 새로 만들 필요는 없습니다.
- 비적용은 장치가 없다는 이유로 쓰지 않습니다. 셀의 전제가 되는 동작 자체가 없을 때 씁니다.
- 일부 모드에서만 작동하는 보호를 전체 보호로 넓혀 읽지 않도록, 프로젝트 연결에 적용 조건을 남깁니다.

### 13.3. 추가·분리할 질문의 우선순위

1. **A05 조사 상태 수명·복구 방식(공통 셀 채택 권고).** 서버가 조사 상태를 어디에 두는지 묻습니다. 그리고 세션, 요청, 사건이 바뀌거나 재시작, 초기화가 일어날 때 그 상태를 어떻게 유지하고 복구하고 폐기하는지 묻습니다. 관련 셀은 각각 다른 것을 봅니다. B05는 그 상태로 호출을 거부하는지, A04는 완료 판단, H02는 사건 간 분리, D07은 재실행 상태를 봅니다. 표본들은 이 질문에 서로 다르게 답합니다. sift-kernel은 요청 단위 상태, trudi는 세션 파일, ChainsawMCP·regipy는 메모리 상태입니다.
2. **사건 자료 삭제·초기화 통제 방식(공통 셀 채택 권고).** 삭제 수단(모델 도구, 운영자 CLI, 자동 정리)마다 증거, 기록, 파생물, 조사 상태 가운데 무엇을 지우는지 묻습니다. 또한 원본 제외, 승인, 삭제 전 보관, 삭제 사실 기록이 있는지 묻습니다. 당시 셀 구성에서는 관련 사실이 F06/H04/C04/B03에 흩어져 있어, **삭제 기능의 대상과 조건**을 한 곳에서 비교할 수 없습니다. 근거는 sift-kernel reset, trudi clear, mcp_dfir clear, mulder replace, ChainsawMCP 재스테이징입니다. 의도하지 않은 기록 소실도 어느 실행 경로에서 일어나는지 구별해 남깁니다.
3. **대체 실행·입력 경로 선택과 결과 의미 표시 방식(공통 셀 채택 권고).** 원래 방법을 쓸 수 없을 때 다른 실행 파일, 파서, 직접 읽기 경로로 바꾸는 조건을 묻습니다. 그리고 다음도 묻습니다.
   - 실제로 어느 경로를 골랐는지
   - 그 때문에 빠지는 검증과 입력 범위
   - 응답과 기록에서 그 사실을 알리는지

   관련 기존 셀은 이 중 일부만 봅니다. D01은 호출 형태, D04는 환경 정보, E03은 상태만 봅니다. sift-kernel의 ewfverify→img_stat과 마운트 실패→fls는 경로가 바뀌면서 결과의 의미가 달라지는 사례입니다.
4. **서버 안 모델 판단은 우선 기존 셀에 흡수.** 먼저 모델의 결과가 B05 게이트나 H09 심사를 정하는지 확인합니다. 그리고 D07에 상세를 더합니다. 다음을 보존하는지 보는 상세입니다.
   - 모델, 버전, 설정
   - 입력과 응답
   - 프롬프트와 정책의 식별값
   - 모델 호출이 실패했을 때 통과시켰는지, 거부했는지

   일반 재실행 자료로 표현되지 않는 사례가 더 나오면 조건부 독립 셀로 분리합니다.

위 상세 후보는 **서로 배타적인 등급**이 아닙니다. 프로젝트 하나가 여러 상세에 들어갈 수 있습니다. 방식의 이름만 보고 실제로 차단, 복구, 검증이 된다고 인정하지 않습니다. 범위와 실패 경로를 보고서에 남깁니다.

위 권고를 채택할 때는 **셀 ID와 총수를 다시 매깁니다.** 현재 10절의 55+5를 최종 개수로 인용하지 마세요. 새 질문의 포함·제외 기준을 정한 뒤 8개 표본에 다시 적용합니다. 이때 옛 비적용·일부만 판정을 기계적으로 변환하지 않습니다.
